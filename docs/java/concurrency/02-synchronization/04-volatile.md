# 2.4. volatile

## Где вы это уже видели

**Доска объявлений в офисе.** Начальник пишет на ней: «Совещание перенесено на 15:00». Все, кто заходит в офис, читают доску. Но вот незадача: у каждого сотрудника на столе лежит **своя копия** расписания, распечатанная утром. Пока он не подойдёт к доске, он будет думать, что совещание в 14:00. Если ему сказать «посмотри на доску» — увидит актуальное. Но пока не сказали — работает по старой копии.

**Светофор.** Горит красный. Вы стоите и ждёте. Вдруг загорается зелёный — вы едете. Между «загорелся зелёный» и «вы увидели зелёный» проходит мгновение, но обычно вы **видите** изменение. А вот если бы вы смотрели не на светофор, а на **фотографию** светофора, сделанную пять минут назад, — вы бы никогда не узнали, что уже можно ехать.

**Новости в мессенджере.** Вы в чате, где кто-то пишет «встречаемся у входа». Уведомление приходит мгновенно. А если у вас отключены уведомления — вы узнаете о сообщении, только когда сами откроете чат. Разница — в том, **обновляется ли ваша картина мира** автоматически или нет.

**Общее во всех случаях** одно: между «кто-то изменил данные» и «я вижу изменение» может быть задержка. В обычной жизни она маленькая, но в многопоточной программе может быть **очень** большой. И вот эта задержка — предмет главы.

## Теория

### Проблема видимости

До сих пор мы говорили о гонках данных: два потока одновременно пишут, и результат портится. Но есть **другая** проблема, менее очевидная: один поток пишет, другой **не видит** записанного. И это не гонка, а именно проблема **видимости**.

Вот пример:

```java
public class Main {
    private static boolean running = true;

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (running) {
                // работаем
            }
            System.out.println("Поток завершился");
        });
        worker.start();
        Thread.sleep(1000);
        running = false;
        System.out.println("main установил running = false");
    }
}
```

Вы ожидаете: `main` через секунду выставит `running = false`, поток `worker` увидит это, выйдет из цикла и напечатает «Поток завершился».

А что происходит на самом деле: **поток `worker` может не увидеть изменения**. Программа либо зависнет навсегда, либо завершится только когда вы нажмёте Ctrl+C. На современных JVM это происходит **регулярно**.

Почему? Потому что `running` — не `volatile`.

### Почему так происходит

Современные процессоры — многоядерные, и у каждого ядра есть **свой кэш**. Когда поток читает переменную, значение попадает в кэш ядра. Дальше поток читает из кэша — это быстро. А запись, сделанная другим потоком на другом ядре, попадает в **его** кэш, а не в ваш. Ваш кэш остаётся со старым значением.

Кроме того, JVM и компилятор **оптимизируют** код. Если в цикле `while (running)` переменная не меняется внутри цикла, компилятор может решить: «значение `running` не меняется, зачем перечитывать каждый раз? Прочитаю один раз и запомню». И поток крутится с закэшированным значением `true`, никогда не проверяя память заново.

В результате: `main` установил `running = false`, но поток `worker` об этом не знает. Не потому, что не хочет — а потому, что **не видит**.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> без синхронизации поток может видеть <em>устаревшее</em> значение переменной неограниченно долго. Это не баг JVM, а следствие того, как устроены процессоры и компиляторы. С этим надо жить и с этим надо работать.
</div>

### volatile — это обещание видимости

Ключевое слово `volatile` решает проблему видимости. Оно говорит JVM: «не кэшируй эту переменную, читай её из основной памяти каждый раз, и записывай в основную память сразу».

```java
private static volatile boolean running = true;
```

Теперь поток `worker` при каждой проверке `while (running)` будет читать **актуальное** значение из основной памяти. Как только `main` установит `false`, поток это увидит — в следующей итерации цикла или чуть позже, но **увидит**.

### Что volatile НЕ делает

А вот тут начинается самое важное, и на этом ловят почти всех.

`volatile` **гарантирует видимость**, но **не гарантирует атомарность**.

То есть `volatile` говорит: «если один поток записал значение, другой увидит новое значение». Но `volatile` **не** говорит: «операция `++` будет атомарной».

```java
private static volatile int counter = 0;
```

Если два потока делают `counter++` на `volatile`-переменной — **гонка остаётся**. Потому что `counter++` всё ещё состоит из трёх шагов (прочитать, увеличить, записать), и `volatile` не защищает эту последовательность от перемешивания.

Единственное, что даёт `volatile` для `counter++`: если поток A записал новое значение, поток B **увидит** его при следующем чтении. Но если B прочитал между шагами A, — B всё равно прочитал старое значение. `volatile` не мешает этому.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> <code>volatile</code> — это про видимость, а не про атомарность. Если вам нужна атомарность — используйте <code>synchronized</code>, <code>AtomicInteger</code> или другие средства из главы 2.6.
</div>

Проверим на практике:

```java
public class Main {
    private static volatile int counter = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(Main::incrementMany);
        Thread t2 = new Thread(Main::incrementMany);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Ожидали 2000, получили: " + counter);
    }

    private static void incrementMany() {
        for (int i = 0; i < 1000; i++) {
            counter++;
        }
    }
}
```

Результат будет нестабильным — то 2000, то 1997, то 1993. **`volatile` не помог.** И не должен был: он не для этого.

### Когда volatile достаточно

`volatile` полезен, когда **один поток пишет, а другие только читают** — и при этом сама запись атомарна (то есть это одно присваивание, а не последовательность).

Примеры, где `volatile` — правильный выбор.

**Флаг остановки.**

```java
private volatile boolean running = true;

public void shutdown() {
    running = false;
}
```

Один поток выставляет `false`, другие читают в цикле. Гонки нет — только видимость. `volatile` решает.

**Одноразовая инициализация.**

```java
private volatile Config config = null;

public Config getConfig() {
    if (config == null) {
        config = loadConfig(); // может выполниться несколько раз, но результат один
    }
    return config;
}
```

Здесь `volatile` гарантирует: если поток записал `config`, другие увидят полностью инициализированный объект, а не «полуготовый».

**Флаг смены режима.**

```java
private volatile Mode mode = Mode.NORMAL;

public void switchToMaintenance() {
    mode = Mode.MAINTENANCE;
}
```

**Счётчик, который пишет только один поток.**

```java
private volatile long lastHeartbeat;

public void updateHeartbeat() {
    lastHeartbeat = System.currentTimeMillis();
}
```

Один поток пишет, другие читают. `volatile` достаточно.

А вот где `volatile` **недостаточно**:

- `counter++` — не атомарно.
- `if (flag) { flag = false; doWork(); }` — check-then-act, не атомарно.
- `list.add(x)` — не атомарно, и сама коллекция не потокобезопасна.
- Любая операция «прочитал — проверил — изменил», которая должна быть неделимой.

### happens-before: формальное правило

В Java есть формальное правило, которое описывает, когда изменения, сделанные одним потоком, **гарантированно видны** другому. Оно называется **happens-before**.

Формулировка такая: если действие A **happens-before** действия B, то все изменения, сделанные до A, видны в B. Грубо говоря, «A произошло раньше B, и B об этом знает».

Для `volatile` правило такое: **запись в `volatile`-переменную happens-before чтение из неё**. Это значит, что если поток A записал значение в `volatile`-переменную, а потом поток B прочитал эту переменную — все изменения, которые A сделал до записи, видны в B после чтения.

Для `synchronized` правило похожее: **выход из `synchronized`-блока happens-before вход в блок с тем же монитором**. Это значит, что `synchronized` не только обеспечивает взаимное исключение, но и **видимость**. Если вы защищаете данные через `synchronized`, вам не нужен `volatile` — `synchronized` уже гарантирует видимость.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> <code>synchronized</code> решает обе проблемы — и атомарность, и видимость. <code>volatile</code> решает только видимость. Если вы уже используете <code>synchronized</code> для защиты переменной — <code>volatile</code> на ней не нужен.
</div>

Формальное определение `happens-before` мы подробно разберём в главе 2.5 (модель памяти Java). Пока достаточно запомнить: **`volatile` и `synchronized` — это не только «то, что нужно, чтобы работало», но и «то, что гарантирует видимость»**. Без одного из них поток может видеть старые значения неограниченно долго.

### volatile не заменяет synchronized

Ещё одно важное различие. `synchronized` — это взаимное исключение плюс видимость. `volatile` — только видимость.

Если вам нужно, чтобы два потока **не мешали** друг другу (взаимное исключение) — `volatile` не подходит, нужен `synchronized` (или `Lock`, или атомарные типы).

Если вам нужно, чтобы один поток **увидел** изменение другого, и при этом никаких «прочитал-проверил-записал» нет — `volatile` подходит.

### Аналогия с доской объявлений

Вернёмся к началу главы. `volatile`-переменная — это **доска объявлений**, на которую все смотрят. Кто-то написал — все видят. Никаких личных копий, никаких старых распечаток. Всегда актуальное значение.

Обычная (не `volatile`) переменная — это **личная копия**, которая лежит на столе у каждого. Пока не обновишь — работаешь по старой. `synchronized` — это когда все по очереди подходят к **одной** доске, читают, пишут, отходят. И очередь, и актуальность.

`volatile` — это когда доска общая, но к ней могут подойти **одновременно** двое. Оба увидят актуальное значение, но если оба начнут писать — кто-то затрёт чужое. Поэтому `volatile` — для чтения, а для записи «прочитал-изменил-записал» нужен `synchronized`.

## Микрозадача 1: флаг остановки

**Задача:** Напишите программу с потоком, который крутится в цикле `while (running)`. Без `volatile` на `running`. Убедитесь, что поток не завершается после того, как `main` установил `running = false`. Затем добавьте `volatile` и убедитесь, что поток завершается.

**Решение без volatile (зависает):**

```java
public class Main {
    private static boolean running = true;

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (running) {
                // работаем
            }
            System.out.println("Поток завершился");
        });
        worker.start();
        Thread.sleep(1000);
        running = false;
        System.out.println("main установил running = false");
    }
}
```

**Возможный вывод:**

```text
main установил running = false
```

И дальше — тишина. Поток `worker` не завершился. Программа висит.

**Разбор:** без `volatile` поток `worker` читает `running` из своего кэша и не видит, что `main` установил `false`. С точки зрения `worker`, `running` всё ещё `true`, и цикл продолжается вечно. JVM даже не пытается его прервать: программа формально не завершилась, потому что поток `worker` — обычный.

**Решение с volatile:**

```java
public class Main {
    private static volatile boolean running = true;

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            while (running) {
                // работаем
            }
            System.out.println("Поток завершился");
        });
        worker.start();
        Thread.sleep(1000);
        running = false;
        System.out.println("main установил running = false");
    }
}
```

**Вывод:**

```text
main установил running = false
Поток завершился
```

**Разбор:** с `volatile` поток `worker` читает `running` из основной памяти при каждой итерации. Как только `main` записал `false`, `worker` это увидел и вышел из цикла. Никакого `synchronized` не понадобилось, потому что гонки тут нет — только видимость.

## Микрозадача 2: volatile не спасает от гонки

**Задача:** Возьмите счётчик из главы 2.1, но сделайте `counter` `volatile`. Запустите несколько раз и убедитесь, что результат **по-прежнему нестабилен**.

**Решение:**

```java
public class Main {
    private static volatile int counter = 0;

    public static void main(String[] args) throws InterruptedException {
        counter = 0;
        Thread t1 = new Thread(Main::incrementMany);
        Thread t2 = new Thread(Main::incrementMany);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Получили: " + counter);
    }

    private static void incrementMany() {
        for (int i = 0; i < 1000; i++) {
            counter++;
        }
    }
}
```

**Возможный вывод:**

```text
Получили: 1995
```

**Разбор:** `volatile` гарантирует, что поток `t1` увидит значение `counter`, записанное потоком `t2`, но не гарантирует, что `counter++` выполнится как единая операция. Два потока всё ещё могут прочитать одно и то же значение, оба прибавить единицу, оба записать — и один инкремент потеряется. `volatile` не для этого. Для атомарности нужен `synchronized` или `AtomicInteger`.

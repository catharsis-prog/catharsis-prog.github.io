# 2.9. wait(), notify(), notifyAll()

## Где вы это уже видели

**Кофейня с заказом.** Вы платите бариста, он говорит: «Ждите, я позову». Вы отходите в сторону. Вы не стоите над ним, не спрашиваете каждые пять секунд «ну что?» — вы **ждёте сигнала**. Бариста закончит и позовёт вас по имени. Вы услышите и подойдёте. Это `wait()` и `notify()` в чистом виде.

**Дверной звонок.** Гость приходит и звонит. Вы слышите звонок и идёте открывать. Без звонка вам пришлось бы каждую минуту подходить к двери и проверять, не пришёл ли кто. Это `wait()` — ждать сигнала, а не проверять бесконечно.

**Уведомление в приложении.** Вы ждёте доставку. Не открываете приложение каждые тридцать секунд — оно само пришлёт уведомление, когда курьер будет рядом. `notify()` — это уведомление.

**Пациент у кабинета врача.** Сидит и ждёт, пока медсестра позовёт: «Следующий». Не дёргает ручку каждые две минуты. Ждёт сигнала. Медсестра знает, кто следующий, — она и зовёт.

**Общее во всех случаях** одно: есть тот, кто **ждёт**, и тот, кто **сообщает о готовности**. Ждущий не проверяет бесконечно — он **засыпает** до сигнала. Сообщающий не заставляет ждущего работать вхолостую — он его **будит**. Это и есть механизм `wait()`/`notify()`.

## Теория

### Зачем это нужно

`synchronized` даёт взаимное исключение: пока один поток в критической секции, другой ждёт снаружи. `volatile` даёт видимость. `AtomicInteger` даёт атомарность. Но ни один из этих механизмов не даёт **координации** — способа сказать: «я готов, начинай», или «я ещё не готов, подожди».

Пример: поток `consumer` должен обработать данные, которые произведёт поток `producer`. Пока данных нет, `consumer` должен **ждать**. Как только данные появились — **проснуться** и обработать.

Без `wait()`/`notify()` единственный вариант — busy wait: `consumer` в цикле проверяет, есть ли данные. Это работает, но сжигает CPU вхолостую. `wait()`/`notify()` — это «умное» ожидание: поток спит, пока не появится сигнал.

### Три метода

`wait()`, `notify()`, `notifyAll()` — методы класса `Object`, а не `Thread`. Они есть у **каждого** объекта в Java. Это важно: каждый объект может служить **точкой синхронизации** для ожидания.

**`wait()`** — усыпляет текущий поток до тех пор, пока другой поток не вызовет `notify()` или `notifyAll()` на том же объекте.

**`notify()`** — будит **один** (случайный) поток, который ждёт на этом объекте. Какой именно — не гарантируется.

**`notifyAll()`** — будит **все** потоки, ожидающие на этом объекте. Каждый из них проверит своё условие и либо продолжит, либо снова уснёт.

### Ключевое требование: только внутри synchronized

Все три метода **должны** вызываться внутри `synchronized`-блока или метода. Причём монитор должен быть тот же самый объект, на котором вы вызываете `wait()`/`notify()`.

```java
Object lock = new Object();

// Правильно:
synchronized (lock) {
    lock.wait();
}

// Неправильно — бросит IllegalMonitorStateException:
lock.wait(); // IllegalMonitorStateException
```

Почему так? Потому что `wait()` **отпускает монитор**, пока поток спит. Если бы вы вызывали `wait()` без монитора, отпускать было бы нечего, и логика ожидания нарушилась бы.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> <code>wait()</code>, <code>notify()</code>, <code>notifyAll()</code> — только внутри <code>synchronized</code> и только на том же объекте. Иначе <code>IllegalMonitorStateException</code>.
</div>

### Что делает wait()

`wait()` делает **три** вещи сразу, и все три важны.

1. **Отпускает монитор** того объекта, на котором вызван.
2. **Усыпляет** поток — он переходит в состояние `WAITING` (или `TIMED_WAITING`, если с таймаутом).
3. **Ждёт** вызова `notify()`/`notifyAll()` на этом же объекте. Когда разбудят — **снова захватывает монитор** и продолжает.

Обратите внимание на третье: чтобы продолжить выполнение после `wait()`, поток **заново захватывает монитор**. Это значит, что между пробуждением и продолжением может пройти время — пока монитор не освободится.

Отпускание монитора — это то, что отличает `wait()` от `sleep()`. `sleep()` монитор **не отпускает**. Если вы уснули в `synchronized`-блоке через `sleep()`, никто не войдёт в этот блок, пока вы не проснётесь. А `wait()` — отпускает, и другие потоки могут войти, чтобы выполнить `notify()`.

### Как выглядит правильное использование

Классическая схема «один ждёт, другой будит»:

```java
public class Main {
    private static final Object lock = new Object();
    private static boolean ready = false;

    public static void main(String[] args) throws InterruptedException {
        Thread waiter = new Thread(() -> {
            synchronized (lock) {
                while (!ready) {
                    try {
                        lock.wait();
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        return;
                    }
                }
                System.out.println("Дождался сигнала!");
            }
        }, "waiter");

        Thread notifier = new Thread(() -> {
            synchronized (lock) {
                System.out.println("Готовлю данные");
                ready = true;
                lock.notifyAll();
            }
        }, "notifier");

        waiter.start();
        Thread.sleep(500);
        notifier.start();

        waiter.join();
        notifier.join();
    }
}
```

**Вывод:**

```text
Готовлю данные
Дождался сигнала!
```

Обратите внимание на структуру `waiter` — это **канонический паттерн**, который нужно запомнить:

```java
synchronized (lock) {
    while (!condition) {
        lock.wait();
    }
    // делаем что-то, когда condition == true
}
```

### Почему while, а не if

Здесь начинается самое важное, и на этом ловят почти всех. Казалось бы, зачем `while`, если после `wait()` мы проснёмся, и `condition` точно будет `true`?

Причин три, и все три реальные.

**Причина первая: spurious wakeup (ложное пробуждение).** Спецификация Java **разрешает** `wait()` просыпаться без вызова `notify()`. Это может случиться из-за оптимизаций JVM, особенностей ОС или тонких багов в спецификации. Если вы используете `if`, а поток проснулся «ложно», вы продолжите выполнение, хотя `condition` всё ещё `false`. С `while` — снова проверите условие и снова уснёте. Правильно.

**Причина вторая: несколько ждущих потоков.** Если на объекте ждут несколько потоков, `notifyAll()` разбудит **всех**. Но продолжить может только один — тот, для кого `condition` стало `true`. Остальные должны снова заснуть. С `if` — каждый проснувшийся продолжит, даже если `condition` для него всё ещё `false`. С `while` — каждый проверит условие и, если не готов, снова уснёт.

**Причина третья: другой поток мог изменить condition обратно.** Пока вы спали, `condition` стал `true`, вы проснулись, но **до** того, как вы захватили монитор, другой поток снова сделал его `false`. С `if` — вы продолжите с устаревшим знанием. С `while` — проверите актуальное значение и снова уснёте.

Поэтому **всегда `while`**. Всегда. Даже если кажется, что «в моём случае `if` хватит». Не хватит.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> <code>wait()</code> в <code>if</code> — это <em>баг</em>, а не «упрощение». Он может проявляться раз в тысячу запусков, но проявится обязательно. Всегда <code>while</code>.
</div>

### notify() vs notifyAll()

Разница простая: `notify()` будит **один** поток (какой — не гарантировано), `notifyAll()` — **все**.

Что выбрать? Почти всегда — `notifyAll()`. Причины две.

**Первая: `notify()` может разбудить «не тот» поток.** Представьте, что на объекте ждут два потока с разными условиями: один ждёт `conditionA`, другой — `conditionB`. Вы сделали `notify()`, и просыпается поток, который ждёт `conditionB`, — а вы-то выставили `conditionA`. Проснувшийся поток проверит своё условие (в `while`), увидит, что не готов, и снова уснёт. А поток, который **мог бы** продолжить, так и не был разбужен. Starvation.

**Вторая: `notifyAll()` не намного дороже.** В большинстве случаев ждущих потоков немного, и разница в производительности незначительна. А безопасность — существенна.

`notify()` уместен только в очень специфических случаях: когда **все** ждущие потоки ждут **одного и того же** условия, и вы точно знаете, что любой из них может продолжить. На практике это редкость. По умолчанию — `notifyAll()`.

### Классическая ошибка: потерянный сигнал

Вот баг, который легко допустить и трудно найти.

```java
// Поток 1: ждёт
synchronized (lock) {
    if (!ready) {
        lock.wait();
    }
}

// Поток 2: уведомляет
synchronized (lock) {
    ready = true;
    lock.notify();
}
```

Что если поток 2 выполнится **до** того, как поток 1 войдёт в `synchronized`? `ready` станет `true`, `notify()` вызван — но никто не ждёт. Сигнал **потерян**. Поток 1 потом войдёт в `synchronized`, увидит `if (!ready)` — `ready` уже `true`, условие не выполнится, `wait()` не вызовется. Всё хорошо.

А теперь другой сценарий: поток 1 вошёл в `synchronized`, проверил `!ready` (true), **собирается** вызвать `wait()`, но планировщик переключил на поток 2. Поток 2 выставил `ready = true`, вызвал `notify()` — никто не ждёт. Поток 1 вернулся, вызвал `wait()` — и **уснул навсегда**. Сигнал уже был, но он его не увидел.

Это и есть **потерянный сигнал**. Решение — то самое `while`:

```java
synchronized (lock) {
    while (!ready) {
        lock.wait();
    }
}
```

С `while` поток 1 после входа в `synchronized` **снова** проверит `ready`. Если поток 2 уже выставил `true`, условие `!ready` будет `false`, и `wait()` не вызовется. Сигнал не потерян — он просто «поглощён» условием.

### Таймаут: wait(long)

`wait()` без аргументов ждёт вечно (пока не разбудят). `wait(timeout)` ждёт не дольше указанного времени. Если время вышло — поток просыпается сам, как будто его разбудили.

```java
synchronized (lock) {
    while (!ready) {
        lock.wait(1000); // ждать не дольше секунды
        if (!ready) {
            System.out.println("Не дождался за секунду");
            return;
        }
    }
}
```

Полезно, когда вы не хотите зависать, если сигнал почему-то не придёт. Но помните: `wait(timeout)` может проснуться и **до** истечения таймаута — из-за `notify()` или spurious wakeup. Так что `while` обязателен и здесь.

### Прерывание: InterruptedException

`wait()` бросает `InterruptedException`, как `sleep()` и `join()`. Обработка стандартная: восстановить флаг и выйти.

```java
try {
    lock.wait();
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
    return;
}
```

### Схема producer-consumer

`wait()`/`notify()` чаще всего используются в паттерне **producer-consumer** — «производитель-потребитель». Один поток кладёт данные в очередь, другой забирает. Если очередь пуста — потребитель ждёт. Если полна — производитель ждёт.

Упрощённая версия:

```java
public class Main {
    private static final Object lock = new Object();
    private static Integer data = null;

    public static void main(String[] args) {
        Thread producer = new Thread(() -> {
            while (true) {
                synchronized (lock) {
                    while (data != null) {
                        try { lock.wait(); } catch (InterruptedException e) { return; }
                    }
                    data = 42;
                    System.out.println("Произвёл 42");
                    lock.notifyAll();
                }
            }
        }, "producer");

        Thread consumer = new Thread(() -> {
            while (true) {
                synchronized (lock) {
                    while (data == null) {
                        try { lock.wait(); } catch (InterruptedException e) { return; }
                    }
                    System.out.println("Потребил " + data);
                    data = null;
                    lock.notifyAll();
                }
            }
        }, "consumer");

        producer.start();
        consumer.start();
    }
}
```

Обратите внимание: **оба** потока используют `while` и **оба** вызывают `notifyAll()`. Это классическая схема. Подробнее о ней — в модуле 5, где будет `BlockingQueue`, которая делает всё это за вас.

### Аналогия с кофейней

Вернёмся к началу. `wait()` — это «отойдите в сторону и ждите, я позову». `notify()` — это «ваш заказ готов». `notifyAll()` — это «всем внимание, заказы готовы, проверяйте свои номера».

`while (!condition) wait();` — это «пока моего номера нет в списке готовых, продолжаю ждать». Если я услышал «заказ 42 готов», а мой номер 43, я не иду получать чужой заказ. Проверяю свой номер, не подошёл — снова жду.

`if` вместо `while` — это «услышал какой-то номер, пошёл получать». Если это был не мой номер — я получу чужой заказ. В программе это означает, что я продолжу с неправильным условием.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> <code>while</code>, а не <code>if</code>. <code>notifyAll()</code>, а не <code>notify()</code>. И то, и другое — не «на всякий случай», а потому что альтернативы опасны.
</div>

## Микрозадача 1: правильное ожидание

**Задача:** Создайте поток `waiter`, который ждёт сигнала через `wait()`. Создайте поток `notifier`, который через секунду выставляет флаг и будит ждущего через `notifyAll()`. Используйте `while`, а не `if`.

**Решение:**

```java
public class Main {
    private static final Object lock = new Object();
    private static boolean ready = false;

    public static void main(String[] args) throws InterruptedException {
        Thread waiter = new Thread(() -> {
            synchronized (lock) {
                while (!ready) {
                    try {
                        lock.wait();
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        return;
                    }
                }
                System.out.println("Дождался!");
            }
        }, "waiter");

        Thread notifier = new Thread(() -> {
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
            synchronized (lock) {
                ready = true;
                lock.notifyAll();
            }
        }, "notifier");

        waiter.start();
        notifier.start();
        waiter.join();
        notifier.join();
    }
}
```

**Вывод:**

```text
Дождался!
```

**Разбор:** `waiter` входит в `synchronized`, проверяет `!ready` (true), вызывает `wait()` — отпускает монитор и засыпает. `notifier` через секунду входит в `synchronized`, выставляет `ready = true`, вызывает `notifyAll()`. `waiter` просыпается, **заново захватывает монитор**, возвращается из `wait()`, проверяет `!ready` — теперь `false`, выходит из `while`. Всё сработало.

Обратите внимание на порядок: `ready = true` **до** `notifyAll()`. Если бы наоборот, `waiter` мог проснуться и увидеть `ready == false` — и снова уснуть. `while` бы спас, но в этом случае мог бы ждать вечно.

## Микрозадача 2: if вместо while — ловушка

**Задача:** Возьмите предыдущий пример, но замените `while` на `if`. Создайте **два** потока, ожидающих на одном мониторе. Разбудите только **один** через `notify()`. Убедитесь, что второй остаётся ждать вечно — и объясните, почему `if` здесь опасен.

**Решение:**

```java
public class Main {
    private static final Object lock = new Object();
    private static boolean ready = false;

    public static void main(String[] args) throws InterruptedException {
        Runnable waiter = () -> {
            synchronized (lock) {
                if (!ready) {
                    try {
                        lock.wait();
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        return;
                    }
                }
                System.out.println(Thread.currentThread().getName() + " проснулся");
            }
        };

        Thread w1 = new Thread(waiter, "waiter-1");
        Thread w2 = new Thread(waiter, "waiter-2");
        w1.start();
        w2.start();

        Thread.sleep(500);

        synchronized (lock) {
            ready = true;
            lock.notify(); // будит только одного
        }

        w1.join(2000);
        w2.join(2000);

        System.out.println("waiter-1 жив: " + w1.isAlive());
        System.out.println("waiter-2 жив: " + w2.isAlive());

        // разбудим второго, чтобы программа завершилась
        synchronized (lock) {
            lock.notifyAll();
        }
    }
}
```

**Возможный вывод:**

```text
waiter-1 проснулся
waiter-1 жив: false
waiter-2 жив: true
```

**Разбор:** `notify()` разбудил **одного** из двух — скажем, `waiter-1`. Он проснулся, увидел `!ready == false`, вышел из `if` и продолжил. `waiter-2` остался спать: его никто не будил. Он жив на момент проверки `isAlive()`. В конце мы разбудили его через `notifyAll()`, чтобы программа завершилась, — иначе бы он висел вечно.

С `while` было бы так: если бы `notifyAll()` разбудил обоих, каждый проверил бы `!ready` — у обоих `false`, оба вышли бы из `while`. А с `notify()`, разбудившим только одного, второй так и остался бы ждать — но это уже правильное поведение: его **не будили**, и он ждёт сигнала. Проблема не в `notify()`, а в `notify()` + `if` — разбудили одного, а могли разбудить «не того», и он бы продолжил без условия.

## 🎯 Самостоятельная задача

Реализуйте **ограниченную очередь** на `wait()`/`notify()` без использования `java.util.concurrent`. Класс `BoundedQueue<T>`:

1. Внутренний массив `Object[]` размера `capacity`.
2. Метод `put(T item)` — кладёт элемент. Если очередь полна, **ждёт**, пока освободится место.
3. Метод `T take()` — забирает элемент. Если очередь пуста, **ждёт**, пока появится элемент.
4. Все методы работают под одним монитором (`synchronized`).

Требования к реализации:

- Используйте `while` для проверки условий, `notifyAll()` для пробуждения.
- При `put` на полную очередь — ждать, пока `size < capacity`.
- При `take` на пустую — ждать, пока `size > 0`.
- После `put` будить всех (мог освободиться элемент для `take`).
- После `take` будить всех (могло освободиться место для `put`).

**Проверка:**

1. Создайте `BoundedQueue<Integer>` ёмкостью 5.
2. Запустите два `producer`-потока, каждый кладёт 100 чисел.
3. Запустите два `consumer`-потока, каждый забирает 100 чисел.
4. Все четыре потока должны завершиться. Никаких `IllegalMonitorStateException`, никаких зависаний.

**Дополнительно:** замените `notifyAll()` на `notify()` и проверьте. Скорее всего, программа **зависнет** или завершится не полностью. Объясните, почему.

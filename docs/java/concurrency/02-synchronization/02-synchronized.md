# 2.2. Критическая секция и synchronized

## Где вы это уже видели

**Примерочная в магазине.** Одна кабинка. Кто-то зашёл — остальные стоят в очереди и ждут. Нельзя двоим переодеваться в одной примерочной одновременно: результат будет не тот, что ожидали. Примерочная — это ресурс, к которому нужен эксклюзивный доступ.

**Туалет с замком.** Все знают: зашёл — закройся. Пока ты внутри, никто не войдёт. Выйдешь — следующий. Без замка было бы неловко, а в программе — катастрофично.

**Переговорка.** В ней можно проводить встречу, но только одну за раз. Пока одна команда совещается, вторая стоит под дверью. Освободилось — заходит следующая.

**Общий документ.** Вы с коллегой редактируете один файл. Если оба пишете одновременно — правки затирают друг друга. Договорились: по очереди. Один пишет, второй ждёт. Закончил — передал эстафету.

**Общее во всех случаях** одно: есть ресурс, который **нельзя использовать двоим одновременно**. И есть механизм, который гарантирует: пока один работает, другой ждёт. В Java этот механизм называется `synchronized`.

## Теория

### Критическая секция

**Критическая секция** — это участок кода, который обращается к общим данным и не должен выполняться двумя потоками одновременно. В примере из прошлой главы критической секцией был весь блок `count++` — или, точнее, три операции, из которых он состоит.

Пример:

```java
public void increment() {
    count++; // критическая секция
}
```

Если два потока выполняют `count++` одновременно — получается гонка. Чтобы её устранить, нужно сделать так, чтобы в любой момент времени **только один поток** находился в критической секции. Тогда операции чтения, увеличения и записи не будут перемешиваться.

### Монитор: что это

В Java механизм взаимного исключения называется **монитор**. Каждый объект в Java имеет связанный с ним монитор. И у монитора есть ровно одно свойство: **в любой момент времени им может владеть только один поток**.

Если поток хочет войти в критическую секцию, защищённую монитором, он должен сначала этот монитор **захватить**. Если монитор свободен — поток заходит и владеет им. Если занят — поток **ждёт**, пока владелец не освободит монитор.

Пока поток владеет монитором, никакой другой поток не может его захватить. А значит, не может войти в критическую секцию. Это и есть взаимное исключение.

Монитор — это как примерочная с замком. Ключ один. У кого ключ — тот внутри. Остальные ждут под дверью.

### Как захватить монитор: synchronized

В Java есть два способа захватить монитор — и оба через ключевое слово `synchronized`. Оно может стоять в двух местах: перед методом или перед блоком кода.

### Способ первый: synchronized-метод

```java
public synchronized void increment() {
    count++;
}
```

Когда метод помечен `synchronized`, происходит следующее: поток, входящий в метод, **захватывает монитор объекта**, на котором метод вызван — то есть `this`. Пока метод не завершится, монитор занят. Другие потоки, которые попытаются вызвать тот же метод на том же объекте, будут стоять в `BLOCKED`, пока первый не выйдет.

```java
public class Counter {
    private int count = 0;

    public synchronized void increment() {
        count++;
    }

    public synchronized int get() {
        return count;
    }
}
```

Теперь, если два потока вызывают `increment()` на одном и том же объекте `Counter`, они будут выполняться **по очереди**, а не одновременно. Гонка исчезает: пока один поток внутри метода, второй стоит у входа.

А вот если два потока вызывают `increment()` на **разных** объектах `Counter` — мониторы у них разные, и потоки не мешают друг другу. Это важный момент, о котором ниже.

### Способ второй: synchronized-блок

Иногда помечать весь метод не хочется — в методе может быть много подготовительной работы, которая не требует защиты. Тогда используют блок:

```java
public void increment() {
    System.out.println("Начинаю инкремент"); // не защищено
    synchronized (this) {
        count++;                            // защищено
    }
    System.out.println("Закончил инкремент"); // не защищено
}
```

Синтаксис такой: `synchronized (объект) { ... }`. Поток захватывает монитор указанного объекта, выполняет блок, освобождает. Всё, что вне блока, выполняется свободно.

Первый вариант (метод) — это по сути то же самое, что `synchronized (this) { весь_метод }`. Только короче.

### Какой монитор захватывается

Вот тут начинается самая важная часть, и её часто путают.

**В `synchronized`-методе захватывается монитор `this`** — того объекта, на котором вызван метод. Не класса, не чего-то абстрактного, а именно объекта.

**В `synchronized (obj)` захватывается монитор именно `obj`** — того объекта, который указан в скобках.

**Ключевой принцип:** два потока мешают друг другу **только если захватывают один и тот же монитор**. Если мониторы разные — они идут параллельно, и `synchronized` ни от чего не защищает.

Это правило важнее всех остальных. Запомните его, и половина проблем с `synchronized` вас обойдёт.

Пример путаницы, которую все совершают хотя бы раз в жизни:

```java
public class Counter {
    public synchronized void increment() { ... }
}

Counter c1 = new Counter();
Counter c2 = new Counter();

// Два потока:
new Thread(() -> c1.increment()).start();
new Thread(() -> c2.increment()).start();
```

Тут два потока работают параллельно и не мешают друг другу, потому что у `c1` и `c2` разные мониторы. Если автор думал «я поставил `synchronized`, значит, всё защищено», — он ошибся. `synchronized` защищает не класс, не код, а **конкретный объект**.

### Что защищать: данные, а не код

Обратите внимание: `synchronized` защищает не «метод», не «блок кода». Он защищает **данные**, к которым обращаются через критическую секцию. И защищает только в том случае, если **все** обращения к этим данным идут через **один и тот же** монитор.

Если один метод инкрементирует счётчик под `synchronized`, а второй читает его без всякой синхронизации — гонка остаётся. Может быть, чуть менее вероятная, но остаётся.

```java
public class Counter {
    private int count = 0;

    public synchronized void increment() {
        count++; // защищено
    }

    public int get() {
        return count; // НЕ защищено
    }
}
```

Тут `get()` читает `count` без блокировки. Если один поток вызывает `increment()`, а другой одновременно `get()`, второй может увидеть промежуточное состояние или старое значение. Формально это тоже гонка — просто менее очевидная.

Правило простое: **если данные могут быть изменены, и этот же данные читаются или пишутся из другого потока — все обращения должны быть под одним монитором.** Все. Без исключений.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> <code>synchronized</code> защищает не код, а данные. И защищает только при условии, что <em>все</em> обращения к этим данным используют <em>один и тот же</em> монитор. Если хотя бы одно обращение идёт в обход — гонка остаётся.
</div>

### Сколько стоит synchronized

`synchronized` — не бесплатно. Захват монитора — это операция, которая требует взаимодействия с планировщиком. Когда поток не может захватить монитор, его состояние меняется на `BLOCKED`, а это переключение контекста. А переключение контекста — это дорого.

В современных JVM (начиная с HotSpot 1.6) есть оптимизации: если монитор не оспаривается несколькими потоками, `synchronized` работает почти бесплатно. Но если конкуренция высокая — цена растёт, потому что потоки стоят в очереди и переключаются туда-обратно.

Из этого следует практический вывод: **не бросайте `synchronized` куда попало**. Защищайте минимально необходимый участок — только то, что действительно требует взаимного исключения. Всё остальное выносите за блок.

Плохо:

```java
public synchronized void process() {
    loadFromDisk(); // не требует синхронизации — долго
    count++;        // требует
    writeToLog();   // не требует — долго
}
```

Хорошо:

```java
public void process() {
    loadFromDisk(); // свободно
    synchronized (this) {
        count++;    // только критическая секция
    }
    writeToLog();   // свободно
}
```

Разница в том, что в первом варианте потоки ждут друг друга, пока идёт чтение с диска и запись в лог. Во втором — ждут только один инкремент. Разница на практике может быть в десятки раз.

### Аналогия с примерочной

Вернёмся к примерочной. `synchronized` — это замок на двери. Поток захватывает монитор, как посетитель захватывает примерочную: зашёл, закрылся, переодевается. Остальные ждут под дверью — это `BLOCKED`.

Когда посетитель выходит — монитор освобождается, замок открывается, следующий заходит. Так работает до тех пор, пока **все** посетители пользуются замком. Если один войдёт через окно, не заперевшись, — весь механизм рушится. Так и с `synchronized`: если хотя бы одно обращение к данным идёт в обход монитора, защита перестаёт работать.

И ещё: в магазине примерочная одна, а посетителей десять. Если каждый переодевается по полчаса — очередь растянется на пять часов. Если каждый по пять минут — на пятьдесят. **Длительность критической секции определяет пропускную способность**. Поэтому `synchronized`-блок должен быть как можно короче.

## Микрозадача 1: устранить гонку

**Задача:** Возьмите программу со счётчиком из главы 2.1. Запустите её несколько раз и убедитесь, что результат нестабилен. Затем добавьте `synchronized` на метод `increment` и убедитесь, что теперь всегда 2000.

**Решение:**

```java
public class Main {
    private static int counter = 0;

    public static void main(String[] args) throws InterruptedException {
        counter = 0;
        Thread t1 = new Thread(Main::incrementMany);
        Thread t2 = new Thread(Main::incrementMany);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Получили: " + counter);
    }

    private static synchronized void incrementMany() {
        for (int i = 0; i < 1000; i++) {
            counter++;
        }
    }
}
```

**Вывод:**

```text
Получили: 2000
```

Каждый запуск — 2000. Ни разу меньше. Каждый запуск — 2000. Ни разу меньше.

**Разбор:** мы поставили `synchronized` на метод `incrementMany`. Теперь поток, вошедший в метод, захватывает монитор класса `Main` (потому что метод `static synchronized` — это монитор класса, а не `this`). Второй поток ждёт, пока первый не закончит все тысячу инкрементов. Результат всегда правильный.

Заметьте: такой вариант блокирует очень много — весь цикл из тысячи итераций. Если бы у нас было два разных счётчика, они бы ждали друг друга зря. Об этом в главе 2.3.

## Микрозадача 2: короткая критическая секция

**Задача:** Улучшите решение из микрозадачи 1: сделайте так, чтобы под `synchronized` был только `counter++`, а всё остальное (инициализация, вывод) — свободно.

**Решение:**

```java
public class Main {
    private static int counter = 0;
    private static final Object lock = new Object();

    public static void main(String[] args) throws InterruptedException {
        counter = 0;
        Thread t1 = new Thread(Main::incrementMany);
        Thread t2 = new Thread(Main::incrementMany);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Получили: " + counter);
    }

    private static void incrementMany() {
        for (int i = 0; i < 1000; i++) {
            synchronized (lock) {
                counter++;
            }
        }
    }
}
```

**Разбор:** теперь под `synchronized` только инкремент. Цикл `for` и всё остальное — свободно. Обратите внимание на отдельный объект `lock` — это правильная практика, если нужно защитить данные, к которым обращаются разные объекты. Если `counter` — статическое поле, `lock` тоже должен быть статическим; если поле экземпляра — `lock` тоже поле экземпляра.

Формально по скорости в этой задаче разница небольшая, потому что `counter++` в цикле и так занимает почти всё время. Но принцип важен: **критическая секция должна быть настолько короткой, насколько возможно**. В реальной программе это различие может быть существенным.

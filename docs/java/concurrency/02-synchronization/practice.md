# Практикум по модулю 2. Синхронизация

## Зачем это

Модуль 1 был про то, как запускать потоки. Модуль 2 — про то, как не дать им испортить друг другу жизнь. Мы прошли девять глав: гонки данных, `synchronized`, `volatile`, модель памяти, атомарные классы, deadlock, livelock, starvation, `wait`/`notify`. Пора собрать всё это в одном месте и проверить, работает ли оно вместе.

Задачи этого практикума **сложнее** тех, что были в уроках. Не потому, что требуют нового материала, а потому что требуют **комбинировать** несколько механизмов и **выбирать** подходящий. В реальной работе почти никогда не бывает «вот тебе задача на `volatile`» — бывает «вот тебе задача, реши её как знаешь». Этот навык и тренируем.

**Разборы** всех задач — на отдельной странице: **[Разборы практикума](/java/concurrency/02-synchronization/practice-solutions)**. Сначала попробуйте сами. Иначе смысла нет: вы прочитаете решение, кивнёте — и через неделю не вспомните.

## Задача 1. Один счётчик, три подхода

**Что комбинируется:** 2.2 (`synchronized`), 2.4 (`volatile`), 2.6 (атомарные классы).

У вас есть задача: два потока, каждый инкрементирует счётчик тысячу раз. Нужно получить ровно 2000. Реализуйте **три** версии:

1. Через `synchronized` на методе инкремента.
2. Через `AtomicInteger`.
3. Через `volatile int` и `synchronized`-блок только вокруг `counter++`.

Запустите каждую пять раз. Все три должны давать 2000 всегда.

**Вопросы в комментарии к коду:**

1. В чём разница между тремя версиями по производительности? Замерьте время.
2. Почему `volatile` без `synchronized` **не** даёт правильный результат, а `volatile` **внутри** `synchronized` — даёт? Что именно даёт `synchronized` в третьей версии, чего не даёт `volatile`?
3. В каком случае вы бы выбрали `synchronized`, а в каком — `AtomicInteger`?

## Задача 2. Найди три ошибки

**Что комбинируется:** 2.4 (`volatile`), 2.3 (монитор), 2.9 (`wait`/`notify`).

Вам дан код. В нём **три ошибки**, из-за которых программа либо зависает, либо выдаёт неверный результат. Найдите их, объясните и исправьте.

```java
public class Main {
    private static boolean ready = false;
    private static int data = 0;
    private static final Object lock = new Object();

    public static void main(String[] args) throws InterruptedException {
        Thread producer = new Thread(() -> {
            data = 42;
            ready = true;
        }, "producer");

        Thread consumer = new Thread(() -> {
            synchronized (lock) {
                if (!ready) {
                    try {
                        lock.wait();
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        return;
                    }
                }
                System.out.println("data = " + data);
            }
        }, "consumer");

        consumer.start();
        Thread.sleep(100);
        producer.start();
    }
}
```

**Задумано:** `consumer` ждёт, пока `producer` выставит `ready = true`, потом читает `data` и печатает 42.

**Что происходит на самом деле:** `consumer` либо висит вечно, либо печатает 0, либо печатает 42 — как повезёт.

**Подсказки:**

- Одна ошибка — в том, что `producer` **не** будит `consumer` через `notify`.
- Вторая — в том, что `ready` не `volatile` и не защищён тем же монитором, что и `consumer`.
- Третья — в том, что `if` вместо `while`.

## Задача 3. Цепочка happens-before

**Что комбинируется:** 2.5 (модель памяти), 2.4 (`volatile`).

Создайте три потока: `A`, `B`, `C`. Каждый пишет свою переменную: `dataA`, `dataB`, `dataC` — все `volatile int`.

- Поток `A` записывает `dataA = 1`, потом `dataB` (не пишет — его пишет B).
- Поток `B` ждёт, пока `dataA == 1`, потом записывает `dataB = 2`.
- Поток `C` ждёт, пока `dataB == 2`, потом читает `dataA` и печатает его.

**Вопрос:** гарантированно ли поток `C` увидит `dataA == 1`?

Ответ обоснуйте через правила happens-before. Если гарантированно — постройте цепочку. Если нет — объясните, какого звена не хватает.

**Дополнительно:** что произойдёт, если `dataA` сделать обычным `int`, а не `volatile`? Цепочка сохранится?

## Задача 4. Переводы без deadlock

**Что комбинируется:** 2.7 (deadlock), 2.2 (`synchronized`), 2.3 (мониторы).

Реализуйте `BankAccount` с полями `int id` и `int balance`, и методом `transfer(BankAccount to, int amount)`.

Требования:

1. У каждого счёта есть уникальный `id`.
2. `transfer` захватывает мониторы **обоих** счетов, но **в порядке возрастания `id`**. Если `this.id < to.id` — сначала `this`, потом `to`. Иначе — наоборот.
3. Внутри критической секции — снятие с одного счёта, добавление на другой.
4. Создайте **два** счёта с `id = 1` и `id = 2`, балансом 1000 каждый. Запустите **два** потока: один переводит с A на B, другой с B на A, каждый тысячу раз по рублю.
5. Сумма балансов в конце должна быть 2000. Программа **не должна зависать**.

**Дополнительно:** поменяйте порядок захвата так, чтобы он не зависел от `id` (каждый поток захватывает «свой» счёт первым). Убедитесь, что программа зависает через несколько секунд. Снимите thread dump (`jstack <pid>`) и найдите в нём сообщение о deadlock.

**Вопросы в комментарии к коду:**

1. Почему порядок по `id` предотвращает deadlock, а порядок «свой — чужой» — нет?
2. Что было бы, если бы оба потока переводили с A на B? Возник бы deadlock без порядка?
3. В чём преимущество порядка по `id` над глобальным монитором `BankAccount.class`?

## Задача 5. Ограниченный буфер

**Что комбинируется:** 2.9 (`wait`/`notify`), 2.2 (`synchronized`).

Реализуйте класс `BoundedBuffer<T>` — ограниченный буфер размера `capacity`:

1. Метод `put(T item)` — кладёт элемент. Если буфер полон — **ждёт**, пока освободится место.
2. Метод `T take()` — забирает элемент. Если буфер пуст — **ждёт**, пока появится элемент.
3. Оба метода работают под одним монитором.

Требования:

- Используйте `while` для проверки условий, `notifyAll()` для пробуждения.
- Проверьте: два `producer` кладут по 100 элементов, два `consumer` забирают по 100. Все завершаются, ничего не теряется.

**Дополнительно:** замените `notifyAll()` на `notify()`. Запустите десять раз. В скольких случаях программа зависнет? Почему?

## Задача 6. Справедливость и starvation

**Что комбинируется:** 2.8 (starvation), 2.7 (deadlock), 2.2 (`synchronized`).

Создайте класс `UnfairLock` — простую реализацию блокировки на `synchronized` и `wait`/`notify`:

```java
public class UnfairLock {
    private boolean locked = false;

    public synchronized void lock() throws InterruptedException {
        while (locked) {
            wait();
        }
        locked = true;
    }

    public synchronized void unlock() {
        locked = false;
        notify();
    }
}
```

Затем создайте **пять** потоков, каждый в цикле из ста итераций: захватывает `UnfairLock`, увеличивает общий счётчик (не защищённый, потому что защита — через `UnfairLock`), отпускает.

**Вопросы:**

1. Всегда ли пять потоков получают примерно равное количество итераций? Посчитайте, сколько итераций успел сделать каждый.
2. Может ли один поток «голодать» — сделать значительно меньше итераций, чем остальные?
3. Что произойдёт, если в `unlock` заменить `notify()` на `notifyAll()`? Запустите десять раз, сравните распределение итераций.
4. Как сделать этот лок **справедливым** — то есть чтобы поток, дольше всех ждущий, получал лок следующим?

## Задача 7. Диагноз по симптому

**Что комбинируется:** всё.

Вам даны три программы. Каждая **не работает** — но по-разному. Для каждой определите: это deadlock, livelock или starvation. Объясните, почему. Предложите исправление.

**Программа А:**

```java
public class A {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lockA) {
                sleep(100);
                synchronized (lockB) { System.out.println("t1"); }
            }
        });
        Thread t2 = new Thread(() -> {
            synchronized (lockB) {
                sleep(100);
                synchronized (lockA) { System.out.println("t2"); }
            }
        });
        t1.start();
        t2.start();
    }

    private static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
```

**Программа Б:**

```java
public class B {
    private static volatile boolean resourceBusy = false;

    public static void main(String[] args) {
        Runnable politeTask = () -> {
            while (!Thread.currentThread().isInterrupted()) {
                if (!resourceBusy) {
                    resourceBusy = true;
                    try {
                        System.out.println(Thread.currentThread().getName() + ": работаю");
                        Thread.sleep(10);
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                        return;
                    } finally {
                        resourceBusy = false;
                    }
                } else {
                    // уступаю
                    Thread.yield();
                }
            }
        };
        new Thread(politeTask, "t1").start();
        new Thread(politeTask, "t2").start();
    }
}
```

**Программа В:**

```java
public class V {
    private static final Object lock = new Object();

    public static void main(String[] args) {
        for (int i = 1; i <= 5; i++) {
            final int id = i;
            new Thread(() -> {
                for (int j = 0; j < 100; j++) {
                    synchronized (lock) {
                        System.out.println("Поток " + id + ": итерация " + j);
                    }
                }
            }).start();
        }
    }
}
```

**Подсказки:**

- А — оба потока активны в начале, но через 100 мс «замирают» и CPU почти не загружен.
- Б — оба потока активны, CPU загружен на 100%, но полезной работы почти нет.
- В — все потоки активны, работа идёт, но один из потоков может почти не получать доступа к `lock`.

## Задача 8. Резюме в одном приложении

**Что комбинируется:** всё.

Напишите программу, которая демонстрирует **все** ключевые концепции модуля за один запуск:

1. Создайте `volatile boolean running` — флаг работы программы.
2. Создайте `AtomicInteger totalOps` — атомарный счётчик выполненных операций.
3. Создайте `BoundedBuffer<Integer>` ёмкостью 10 (из задачи 5).
4. Запустите **три** `producer`-потока, каждый кладёт в буфер по 50 чисел.
5. Запустите **три** `consumer`-потока, каждый забирает из буфера по 50 чисел.
6. Запустите **демон** `monitor`, который каждые 100 мс печатает `totalOps.get()`.
7. Главный поток ждёт 2 секунды, потом выставляет `running = false`.
8. Все потоки должны корректно завершиться. `monitor` — по `interrupt`, `producer`/`consumer` — по сигналу от буфера.
9. В конце напечатайте: сколько всего операций сделано, сколько элементов осталось в буфере (должно быть 0), сумма всех произведённых элементов равна сумме всех потреблённых.

**Что проверяется:** умение собрать все механизмы модуля в одной программе — `volatile`, `AtomicInteger`, `synchronized`, `wait`/`notify`, `interrupt`, `daemon`, bounded buffer.

## 🎯 Проектное задание. Потокобезопасный кеш с TTL

Это задание сложнее предыдущих. Оно не про конкретный механизм, а про **дизайн**: как собрать из механизмов синхронизации структуру, которая работает корректно и эффективно.

### Постановка

Напишите класс `TTLCache<K, V>` — потокобезопасный кеш с временем жизни записи.

1. Принимает `capacity` — максимальное количество записей, и `ttlMillis` — время жизни записи.
2. Метод `put(K key, V value)` — кладёт значение. Если ключ уже есть — перезаписывает. Если кеш полон — **вытесняет** самую старую запись (по времени создания).
3. Метод `V get(K key)` — возвращает значение, если оно есть и не истекло. Иначе — `null`.
4. Метод `int size()` — текущее количество записей (только не истёкших).
5. Все методы должны быть потокобезопасны.
6. **Демон** `cleaner` раз в 100 мс удаляет истёкшие записи. Корректно завершается по `interrupt`.
7. **Демон** `reporter` раз в 500 мс печатает текущий размер кеша и количество попаданий/промахов.

### Требования к реализации

- Внутри — `HashMap<K, Entry>` с полями `value` и `createdAt`. Защита — через `synchronized` на одном мониторе.
- При `get` проверять срок жизни. Если истёк — удалять и возвращать `null`.
- При `put`, если кеш полон, — найти запись с самым старым `createdAt` и удалить её. **Не** использовать `LinkedHashMap` с `removeEldestEntry` — мы тренируем ручную реализацию.

### Тесты для проверки

1. Создайте `TTLCache<String, Integer>` с `capacity=5`, `ttlMillis=500`.
2. Запустите **три** потока, каждый делает 100 операций: случайно выбирает `put` или `get`, случайный ключ из `key-1..key-10`.
3. Дождитесь завершения.
4. Проверьте: `cache.size() <= 5`. Никаких исключений не было. Все операции завершились.

### Задание со звёздочкой

Подумайте над вопросами:

1. Почему `cleaner` и `reporter` — демоны, а потоки с операциями — обычные?
2. Что произойдёт, если `get` делать вне `synchronized` (то есть читать без блокировки)? Какие проблемы появятся? Будут ли гонки?
3. Как бы вы модифицировали кеш для случая, когда `get` гораздо чаще, чем `put`? Подумайте про `ConcurrentHashMap` и `ReadWriteLock` (последний будет в главе 3.5). Набросайте идею — синтаксис не обязателен.
4. Какие проблемы возникнут, если `capacity = 1_000_000`, а `ttlMillis = 1` (одна миллисекунда)? Как бы вы это исправили?

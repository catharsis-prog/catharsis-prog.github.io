# 2.7. Deadlock

## Где вы это уже видели

**Двое в дверях.** Один хочет войти, второй — выйти. Оба одновременно берутся за дверь, оба останавливаются и говорят: «проходите». Тот, кто входит, ждёт, пока выйдет другой, а тот, кто выходит, — пока войдёт первый. Оба стоят и смотрят друг на друга. Никто никуда не идёт.

**Узкий мост.** Две машины с двух сторон. Каждая въезжает до середины и видит: навстречу едет другая. Обе останавливаются. Разъехаться негде, назад сдавать — далеко. Стоят. Гудят.

**Узкая лестница в подъезде.** Один несёт диван наверх, второй — холодильник вниз. Встретились на площадке. Один не может поднять выше, второй не может опустить ниже. И ни тот, ни другой не может сдвинуться назад — за ними уже никого нет, а вперёд — занято.

**Общее во всех случаях** одно: два участника, каждый **держит** что-то своё и **ждёт** чего-то чужого. Пока держит — не может получить. Пока ждёт — не может отпустить. Круг замкнулся, движения нет. В программировании это называется **deadlock** — взаимная блокировка.

## Теория

### Что такое deadlock

**Deadlock** — ситуация, когда два или больше потоков навсегда заблокированы, потому что каждый ждёт ресурс, который удерживает другой. Никакой из потоков не может продвинуться. Программа висит. Никаких исключений, никаких сообщений об ошибке — просто тишина.

Главная особенность deadlock: **он не разрешается сам**. Никакой таймаут не сработает, никакой планировщик не придёт на помощь. Потоки будут стоять вечно, пока вы не убьёте программу.

### Классический пример

Самая известная иллюстрация — два потока, два монитора, и каждый захватывает их в разном порядке.

```java
public class Main {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lockA) {
                System.out.println("t1: захватил A");
                sleep(100);
                synchronized (lockB) {
                    System.out.println("t1: захватил B");
                }
            }
        }, "t1");

        Thread t2 = new Thread(() -> {
            synchronized (lockB) {
                System.out.println("t2: захватил B");
                sleep(100);
                synchronized (lockA) {
                    System.out.println("t2: захватил A");
                }
            }
        }, "t2");

        t1.start();
        t2.start();
    }

    private static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

**Возможный вывод:**

```text
t1: захватил A
t2: захватил B
```

И дальше — тишина. Программа висит.

**Что произошло.** `t1` захватил `lockA`, `t2` захватил `lockB`. Теперь `t1` хочет `lockB`, но он занят `t2`. `t2` хочет `lockA`, но он занят `t1`. Оба ждут друг друга. Ни один не может освободить свой монитор, потому что не может выйти из `synchronized`-блока — а не может выйти, потому что не вошёл во вложенный. Круг замкнулся.

### Диаграмма ожидания

Это называется **граф ожиданий**. Потоки — узлы, ресурсы — рёбра.

```text
     владеет          хочет
t1 ────────▶ lockA ◀─────── t2
 ▲                            │
 │                            │
 └──────── lockB ◀────────────┘
       хочет          владеет
```

`t1` владеет `lockA` и хочет `lockB`. `t2` владеет `lockB` и хочет `lockA`. Цикл замкнут — deadlock.

Если бы в этой диаграмме не было цикла — deadlock не возник бы. Один из потоков рано или поздно дождался бы своего ресурса.

### Четыре условия (Coffman)

В 1971 году Эдвард Коффман сформулировал четыре условия, при которых **возможен** deadlock. Все четыре должны выполняться одновременно.

1. **Взаимное исключение.** Ресурс может удерживаться только одним потоком в каждый момент.
2. **Удержание и ожидание.** Поток держит хотя бы один ресурс и при этом ждёт ещё.
3. **Отсутствие принудительного отъёма.** Ресурс нельзя отобрать у потока силой — только сам поток может его освободить.
4. **Циклическое ожидание.** Существует цикл из потоков, где каждый ждёт ресурс, удерживаемый следующим.

Первые три условия обычно выполняются в любой программе с блокировками. Единственное, что можно контролировать, — **четвёртое**. Если разорвать цикл ожидания, deadlock не возникнет. Именно на этом основаны все стратегии защиты.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> бороться с deadlock — это бороться с циклом ожидания. Взаимное исключение, удержание, отсутствие отъёма — это данность, а вот порядок захвата можно контролировать.
</div>

### Способ первый: глобальный порядок захвата

Самый надёжный способ предотвратить deadlock — **всегда захватывать блокировки в одном и том же порядке**. Если `t1` и `t2` оба захватывают `lockA` перед `lockB`, то deadlock невозможен: один захватит `lockA`, второй подождёт — и всё.

Вернёмся к примеру и исправим `t2`, чтобы он тоже захватывал `lockA` первым:

```java
Thread t2 = new Thread(() -> {
    synchronized (lockA) {
        System.out.println("t2: захватил A");
        sleep(100);
        synchronized (lockB) {
            System.out.println("t2: захватил B");
        }
    }
}, "t2");
```

Теперь оба потока захватывают `lockA` первым, потом `lockB`. Пока один держит `lockA`, другой стоит у входа. Когда первый освободит — второй захватит и спокойно дойдёт до `lockB`. Цикла нет, deadlock невозможен.

На практике «порядок» задают явно. Например, если у объектов есть уникальные идентификаторы, можно захватывать блокировки в порядке возрастания этих идентификаторов:

```java
void transfer(Account from, Account to, int amount) {
    Account first = from.id < to.id ? from : to;
    Account second = from.id < to.id ? to : from;

    synchronized (first) {
        synchronized (second) {
            // перевод
        }
    }
}
```

Здесь оба потока, как бы они ни вызывали `transfer`, захватывают сначала счёт с меньшим `id`, потом с большим. Порядок всегда один. Deadlock не возникнет.

Именно это решение мы упустили в самостоятельной задаче из главы 2.3. Если помните, там был вопрос: как защитить перевод между двумя счетами? Ответ — не просто «использовать общий монитор», а «захватывать блокировки в **определённом порядке**». Второй вариант (единый монитор `BankAccount.class`) работает, но сериализует все переводы. Порядок захвата — тоньше: параллельность сохраняется, а deadlock исчезает.

### Способ второй: tryLock с таймаутом

Второй способ — не блокироваться бесконечно. Если блокировку не удалось захватить за разумное время — **отступить**, освободить свои блокировки, подождать и попробовать снова.

У `synchronized` такой возможности нет: он ждёт бесконечно. Но у `ReentrantLock` (о нём — в главе 2.12) есть метод `tryLock(timeout)`:

```java
ReentrantLock lockA = new ReentrantLock();
ReentrantLock lockB = new ReentrantLock();

void doWork() {
    while (true) {
        if (lockA.tryLock(100, TimeUnit.MILLISECONDS)) {
            try {
                if (lockB.tryLock(100, TimeUnit.MILLISECONDS)) {
                    try {
                        // оба захвачены — работаем
                        return;
                    } finally {
                        lockB.unlock();
                    }
                }
            } finally {
                lockA.unlock();
            }
        }
        // не удалось — подождать и попробовать снова
        sleep(50);
    }
}
```

Этот способ используется, когда порядок захвата неизвестен или меняется динамически. Он не гарантирует отсутствие deadlock в строгом смысле, но **гарантирует, что deadlock рассосётся**: один из потоков отпустит свой лок, и второй сможет продвинуться.

### Способ третий: избегать вложенных блокировок

Третий способ — самый простой: **не захватывать одну блокировку, держа другую**. Если в вашем коде нет вложенных `synchronized`, deadlock невозможен: циклу из одного ресурса неоткуда взяться.

На практике это не всегда получается: иногда действительно нужно защитить две вещи одновременно. Но если можно обойтись без вложенности — обойдитесь. Часто это значит:

- Использовать один общий монитор вместо двух (как в варианте с `BankAccount.class`).
- Собирать нужные данные под блокировкой, отпускать её, потом работать с данными без блокировки.
- Использовать атомарные классы вместо `synchronized` там, где это возможно.

### Способ четвёртый: lock-free структуры

Четвёртый способ — вообще не использовать блокировки. `AtomicInteger`, `ConcurrentHashMap`, `BlockingQueue` — все они спроектированы так, чтобы не блокироваться (или блокироваться как можно меньше). Если удаётся выразить логику через них — deadlock становится невозможен в принципе.

Это не всегда получается: некоторые задачи требуют именно взаимного исключения. Но если получается — это самый надёжный путь. Подробнее — в модуле 5 (`ConcurrentHashMap`, `BlockingQueue`).

### Как обнаружить deadlock

Самый практичный способ — **снять thread dump** и посмотреть на состояния потоков. JVM умеет **сама обнаруживать deadlock** и печатать его в дампе.

Например, в `jstack`:

```text
Found one Java-level deadlock:
=============================
"t1":
  waiting to lock monitor 0x0000000000000001 (object 0x0000000000000002, a java.lang.Object),
  which is held by "t2"
"t2":
  waiting to lock monitor 0x0000000000000003 (object 0x0000000000000004, a java.lang.Object),
  which is held by "t1"

Java stack information for the threads listed above:
===================================================
"t1":
    at Main.lambda$main$0(Main.java:10)
    - waiting to lock <0x0000000000000002> (a java.lang.Object)
    - locked <0x0000000000000004> (a java.lang.Object)

"t2":
    at Main.lambda$main$1(Main.java:20)
    - waiting to lock <0x0000000000000004> (a java.lang.Object)
    - locked <0x0000000000000002> (a java.lang.Object)
```

JVM не только видит deadlock, но и показывает, кто чего ждёт и кто чем владеет. Это самый быстрый способ понять, что происходит.

Как снять thread dump: `jstack <pid>` в терминале, или `Ctrl+\` в консоли Java-программы, или кнопка «Thread dump» в IDE. Подробнее — в главе 7.4 про диагностику.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> при deadlock <em>ни одна из блокировок не выдаёт ошибку</em>. Программа просто висит. Именно поэтому deadlock так опасен: его не замечают до тех пор, пока он не случится на проде, и потом ищут часами. Thread dump — единственный быстрый способ диагностики.
</div>

### Сколько это стоит

Deadlock может случиться с двумя потоками — но также с тремя, четырьмя, двадцатью. Чем больше потоков и блокировок, тем сложнее цикл и тем труднее его обнаружить.

В реальных программах deadlock часто возникает не с двумя явными локами, а через цепочку: `t1` держит `lockA` и ждёт `lockB`, `t2` держит `lockB` и ждёт `lockC`, `t3` держит `lockC` и ждёт `lockA`. Цикл из трёх, четырёх, десяти потоков. В thread dump виден весь цикл.

Именно поэтому **порядок захвата** — самое надёжное средство. Если все блокировки в программе захватываются в едином порядке, циклов быть не может ни при какой длине.

### Аналогия с дверьми

Вернёмся к началу главы. `synchronized` — это захват двери. Пока вы её держите, никто не войдёт. Deadlock — это когда вы держите одну дверь и ждёте вторую, а её держит кто-то, кто ждёт вашу.

Глобальный порядок захвата — это правило «всегда сначала открываем левую дверь, потом правую». Тогда два человека, идущие навстречу, оба сначала берутся за левую, один захватывает, второй ждёт. Никакого «после вас», никакого «нет, после вас». Просто и надёжно.

`tryLock` — это «подёргал ручку, не открылось — отошёл, попробую через минуту». Может, повезёт, а может, придётся подождать. Но не вечно.

## Микрозадача 1: воспроизвести deadlock

**Задача:** Напишите программу с двумя потоками и двумя мониторами. Поток `t1` захватывает `lockA`, потом `lockB`. Поток `t2` захватывает `lockB`, потом `lockA`. Между захватами — пауза в 100 мс. Запустите и убедитесь, что программа зависает. Снимите thread dump и найдите в нём сообщение о deadlock.

**Решение:**

```java
public class Main {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> {
            synchronized (lockA) {
                System.out.println("t1: захватил A");
                sleep(100);
                synchronized (lockB) {
                    System.out.println("t1: захватил B");
                }
            }
        }, "t1");

        Thread t2 = new Thread(() -> {
            synchronized (lockB) {
                System.out.println("t2: захватил B");
                sleep(100);
                synchronized (lockA) {
                    System.out.println("t2: захватил A");
                }
            }
        }, "t2");

        t1.start();
        t2.start();
    }

    private static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

**Вывод** (и дальше — тишина):

```text
t1: захватил A
t2: захватил B
```

**Разбор:** `t1` захватил `lockA`, `t2` захватил `lockB`. Оба уснули на 100 мс. Проснулись, каждый попытался захватить второй лок — и застрял в `BLOCKED`, потому что второй лок занят другим. Оба ждут вечно. Программа висит.

Чтобы увидеть deadlock в дампе, откройте второй терминал, найдите PID процесса (`jps` или `ps aux | grep java`), выполните `jstack <pid>` и найдите в выводе блок «Found one Java-level deadlock». JVM покажет, что `t1` держит `lockA` и ждёт `lockB`, а `t2` — наоборот.

## Микрозадача 2: устранить через порядок захвата

**Задача:** Исправьте программу из микрозадачи 1 так, чтобы оба потока захватывали мониторы в **одном и том же** порядке: сначала `lockA`, потом `lockB`. Убедитесь, что программа больше не зависает.

**Решение:**

```java
public class Main {
    private static final Object lockA = new Object();
    private static final Object lockB = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> doWork("t1"), "t1");
        Thread t2 = new Thread(() -> doWork("t2"), "t2");
        t1.start();
        t2.start();
    }

    private static void doWork(String name) {
        synchronized (lockA) {
            System.out.println(name + ": захватил A");
            sleep(100);
            synchronized (lockB) {
                System.out.println(name + ": захватил B");
            }
        }
    }

    private static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
```

**Возможный вывод:**

```text
t1: захватил A
t1: захватил B
t2: захватил A
t2: захватил B
```

Или:

```text
t2: захватил A
t2: захватил B
t1: захватил A
t1: захватил B
```

**Разбор:** оба потока теперь захватывают сначала `lockA`, потом `lockB`. Пока один держит `lockA`, второй стоит у входа. Первый спокойно дойдёт до `lockB` — тот свободен, потому что второй поток даже не пытался его захватить. Когда первый освободит `lockA`, второй захватит его и повторит тот же путь. Цикла нет, deadlock невозможен.

Обратите внимание: порядок вывода — не «t1 всегда первым». Это нормально: планировщик решает, кто первым захватит `lockA`. Главное — **никогда не зависает**.

## 📌 Что дальше

В следующей главе — **«Livelock и starvation»**. Это две проблемы, которые часто путают с deadlock, но они другие. Livelock — когда потоки не заблокированы, но всё равно не могут продвинуться: они «уступают» друг другу бесконечно. Starvation — когда один поток никогда не получает ресурс, потому что другие его «обгоняют». А то ведь до сих пор мы говорили только о полной остановке. Пора поговорить о том, что бывает, когда **движение есть, а прогресса нет**.

# 2.8. Livelock и starvation

## Где вы это уже видели

**Двое в узком коридоре.** Один идёт навстречу другому. Оба останавливаются. Один делает шаг вправо — второй тоже вправо. Первый делает шаг влево — второй тоже влево. Оба извиняются, оба уступают, оба не могут пройти. Движение есть — прогресса нет. Это **livelock**.

**Очередь в столовую.** Студенты стоят в очереди. Но вот незадача: у входа дежурит староста, и каждый раз, когда подходит новенький, староста пропускает его вперёд — «он опаздывает, ему важнее». Очередь не движется, хотя все стоят и ждут. Один студент в самом конце ждёт уже третий час. Это **starvation**.

**Бесконечный рефакторинг.** Вы пишете код, потом решаете переписать — «сейчас сделаю красивее». Переписываете, снова переписываете, снова. Код всё время в процессе, но никогда не готов. Движение есть, прогресса нет. Тоже livelock, только не в программе, а в работе.

**Четыре машины на перекрёстке.** Классическая задача. Все четверо подъезжают одновременно, каждый ждёт, пока проедет другой, каждый кивает «проезжайте вы». Все стоят, все вежливы, никто не едет. Livelock.

**Общее во всех случаях** одно: **никто не заблокирован** — все активны, все что-то делают. Но **полезной работы не происходит**. Это отличает livelock и starvation от deadlock: там потоки спят, а тут — бегают, но не туда.

## Теория

### Livelock: активность без прогресса

**Livelock** — ситуация, когда потоки не заблокированы, но **не могут продвинуться**, потому что постоянно реагируют друг на друга. Каждый делает что-то осмысленное в ответ на действия другого, и в итоге оба топчутся на месте.

Ключевое отличие от deadlock: в deadlock потоки **стоят** (в состоянии `BLOCKED` или `WAITING`), а в livelock — **работают** (в состоянии `RUNNABLE`), но без результата. Планировщик выделяет им процессорное время, потоки выполняют код, но не выходят из цикла взаимных уступок.

### Классический пример

Два потока, у каждого есть ресурс. Оба хотят получить ресурс другого. Оба решают: «Я вежливый, отдам свой ресурс первым, чтобы другой мог продолжить».

```java
public class Main {
    private static final Object resourceA = new Object();
    private static final Object resourceB = new Object();

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> doWork(resourceA, resourceB, "t1"), "t1");
        Thread t2 = new Thread(() -> doWork(resourceB, resourceA, "t2"), "t2");
        t1.start();
        t2.start();
    }

    private static void doWork(Object own, Object need, String name) {
        while (true) {
            synchronized (own) {
                System.out.println(name + ": держу свой ресурс");
                // вежливо проверяем, не занят ли чужой
                if (isLocked(need)) {
                    System.out.println(name + ": чужой занят, уступаю");
                    continue; // отпускаем свой, пробуем снова
                }
                synchronized (need) {
                    System.out.println(name + ": работаю");
                    return;
                }
            }
        }
    }

    private static boolean isLocked(Object obj) {
        return !Thread.holdsLock(obj); // упрощение; в реальном коде нужен другой механизм
    }
}
```

**Возможный вывод** (бесконечный):

```text
t1: держу свой ресурс
t1: чужой занят, уступаю
t2: держу свой ресурс
t2: чужой занят, уступаю
t1: держу свой ресурс
t1: чужой занят, уступаю
...
```

И так до бесконечности. Программа не висит в смысле deadlock — потоки активны. Но и не работает.

Код с `Thread.holdsLock` здесь упрощённый: в реальной ситуации нужно что-то вроде `tryLock`, чтобы узнать, занят ли ресурс, не блокируясь. Но суть видна: два потока постоянно отпускают свои ресурсы, чтобы уступить другому, и никто не может продвинуться.

### Как отличить livelock от deadlock

Практическое различие — в **состояниях потоков**.

| | Deadlock | Livelock |
|---|---|---|
| Состояние потоков | `BLOCKED`, `WAITING` | `RUNNABLE` |
| Использование CPU | почти 0% | 100% (потоки активно крутятся) |
| Потоки продвигаются | нет | нет |
| Программа завершится | никогда | никогда (без вмешательства) |
| Виден в thread dump | да, JVM detects | нет, не виден как deadlock |

Это различие важно при диагностике. Если программа висит и CPU загружен на 100% — ищите livelock (или busy wait, о котором будет отдельный разговор). Если висит и CPU почти не загружен — ищите deadlock.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> livelock не виден в thread dump как deadlock. JVM не считает его проблемой — все потоки в <code>RUNNABLE</code>, значит, «работают». Искать livelock приходится вручную, по логам или по профилировщику.
</div>

### Как бороться с livelock

Livelock — это обычно **ошибка в логике уступок**, а не проблема синхронизации как таковой. Лечится изменением алгоритма.

**Способ первый: случайность.** Если оба потока уступают, пусть уступают **с разной вероятностью** или **в разное время**. Например, добавляйте случайную задержку перед повтором:

```java
if (не получилось) {
    Thread.sleep(random.nextInt(100));
    // повторить
}
```

Через некоторое время один из потоков «повезёт», и он продвинется. Это некрасиво, но работает. Так, кстати, решается проблема четырёх машин на перекрёстке: если каждый ждёт случайное время, кто-то поедет первым.

**Способ второй: приоритет.** Один из потоков получает «право первого хода». Например, если `id` одного меньше `id` другого — он не уступает, а идёт первым. Это детерминированно, но требует, чтобы приоритет был известен заранее.

**Способ третий: не уступать.** Если вы можете **попытаться** захватить ресурс и, если не удалось, подождать — сделайте именно это. `tryLock` с таймаутом работает лучше, чем «отпустить и повторить».

**Способ четвёртый: пересмотреть алгоритм.** Livelock почти всегда означает, что в алгоритме есть цикл взаимных уступок. Иногда достаточно переформулировать задачу: вместо «оба уступают» — «один захватывает, второй ждёт».

### Starvation: один не получает ресурс

**Starvation** (голодание) — ситуация, когда поток **никогда не получает** нужный ресурс, потому что другие потоки его **обгоняют**. Не потому, что он заблокирован — а потому, что до него просто не доходит очередь.

Пример: три потока, все увеличивают один счётчик под `synchronized`. Каждый захватывает монитор, что-то делает, отпускает. Второй ждёт. Третий ждёт. Но если у второго приоритет выше, планировщик может отдавать монитор второму снова и снова, а третий так и не дождётся.

Или: `wait()` без уведомления всех. Если один поток ждёт `notify()`, а вызывают `notify()` для другого — первый может ждать вечно. Об этом подробно в главе 2.9.

Или: `ReentrantLock` без `fairness`. По умолчанию `ReentrantLock` несправедлив: когда лок освобождается, его захватывает любой поток, а не тот, кто дольше всех ждал. В результате один поток может получать лок снова и снова, а другой — голодать.

### Классический пример starvation

```java
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Thread high = new Thread(() -> {
            while (true) {
                // бесконечная работа с высоким приоритетом
                System.out.println("high работает");
                Thread.yield();
            }
        });
        high.setPriority(Thread.MAX_PRIORITY);

        Thread low = new Thread(() -> {
            while (true) {
                System.out.println("low работает");
                Thread.yield();
            }
        });
        low.setPriority(Thread.MIN_PRIORITY);

        high.start();
        low.start();

        Thread.sleep(2000);
        high.interrupt();
        low.interrupt();
    }
}
```

**Возможный вывод:** `high` печатает гораздо чаще, чем `low`. Иногда `low` вообще не успевает напечатать ни строки за несколько секунд.

**Разбор:** высокий приоритет даёт `high` больше процессорного времени. При достаточно высокой разнице `low` может «голодать» — не получать процессор вообще. Как мы говорили в главе 1.7, приоритет — это подсказка, но в некоторых средах она работает достаточно, чтобы вызвать starvation.

Это одна из причин, почему приоритетам не стоит доверять: они не только «не гарантируют порядок», но и **могут привести к голоданию**.

### Где starvation встречается в реальности

Starvation реже, чем deadlock, но коварнее, потому что его **труднее заметить**. Программа работает, что-то делает, но один поток почему-то никогда не получает результата.

**Несправедливые блокировки.** `ReentrantLock` по умолчанию несправедлив. В высококонкурентной среде один поток может захватывать лок десятки раз подряд, пока другой ждёт. Решение: `new ReentrantLock(true)` — справедливый режим (о нём подробнее в главе 2.12).

**`notify()` вместо `notifyAll()`.** Если несколько потоков ждут, и вы вызываете `notify()`, просыпается **один случайный** поток. Если он не может продолжить (например, условие ещё не выполнено), он снова уснёт. Другой поток, который **мог бы** продолжить, так и не будет разбужен. Starvation.

**Бесконечные циклы с высоким приоритетом.** Поток с высоким приоритетом в бесконечном цикле не даёт низкоприоритетным потокам получить процессор. Решение: `yield()` в цикле или `sleep()`, чтобы дать другим шанс.

**Накопление задач в пуле.** Если пул потоков перегружен короткими задачами, длинная задача может стоять в очереди очень долго. Решение: отдельные пулы для разных типов задач, или приоритетная очередь.

**Нечестные планировщики.** Некоторые операционные системы и JVM не гарантируют справедливость. В Linux CFS (Completely Fair Scheduler) довольно справедлив, но на специализированных системах реального времени — не всегда.

### Как бороться со starvation

**Способ первый: справедливые блокировки.** `ReentrantLock(true)` обеспечивает FIFO-порядок: лок получает тот, кто дольше всех ждёт. Медленнее, но справедливо.

**Способ второй: `notifyAll()` вместо `notify()`.** Будит всех ждущих, каждый проверяет своё условие, кто может — продолжает, кто не может — снова спит. Starvation исчезает.

**Способ третий: приоритетные очереди.** Если есть задачи с разными приоритетами — используйте `PriorityBlockingQueue`. Она гарантирует, что высокоприоритетные задачи получат ресурс первыми, но с учётом «не голодать» — старые задачи постепенно поднимаются в приоритете.

**Способ четвёртый: таймауты.** `tryLock(timeout)` гарантирует: если не удалось за отведённое время — поток не ждёт вечно, а идёт дальше. Худший случай — «не получил ресурс за разумное время», а не «голодает вечно».

**Способ пятый: пересмотреть архитектуру.** Если starvation возникает в архитектуре — обычно это признак того, что потоки конкурируют за ресурс, который не предназначен для такого уровня конкуренции. Может быть, нужен другой алгоритм, другая структура данных, или больше ресурсов (например, несколько мониторов вместо одного).

### Ключевое различие: deadlock vs livelock vs starvation

Соберём все три проблемы в одну таблицу.

| | Deadlock | Livelock | Starvation |
|---|---|---|---|
| Потоки | заблокированы | активны | один активен, другие нет |
| Состояние | `BLOCKED`, `WAITING` | `RUNNABLE` | `RUNNABLE` или `BLOCKED` |
| CPU | почти 0% | 100% | варьируется |
| Прогресс | нет | нет | у одного потока нет |
| Виден в dump | да | нет | иногда |
| Лечение | порядок захвата, tryLock | случайность, приоритет | fairness, notifyAll, таймауты |

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> deadlock — это <em>общая остановка</em>. Livelock — <em>движение без прогресса</em>. Starvation — <em>прогресс всех, кроме одного</em>. Все три — разные проблемы с разными решениями. Путать их — значит лечить не ту болезнь.
</div>

### Аналогия с дверьми и очередью

Вернёмся к началу. **Deadlock** — двое в дверях: оба держатся за косяки, оба не могут пройти. Стоят **неподвижно**.

**Livelock** — двое в коридоре: оба шагают вправо, потом влево, потом снова вправо. Движение есть, но к выходу никто не приближается. **Двигаются, но не туда**.

**Starvation** — очередь в столовую, где староста всё время пропускает «важных». Кто-то проходит, но один студент в конце стоит уже третий час. **Движение есть, но не для всех**.

## Микрозадача 1: воспроизвести livelock

**Задача:** Напишите два потока, которые бесконечно «уступают» друг другу. Каждый поток в цикле: захватывает свой ресурс, проверяет, свободен ли чужой, если занят — отпускает свой и повторяет. Убедитесь, что программа не завершается, но CPU загружен.

**Решение:**

```java
public class Main {
    private static final Object resourceA = new Object();
    private static final Object resourceB = new Object();
    private static volatile boolean finished = false;

    public static void main(String[] args) {
        Thread t1 = new Thread(() -> politeWork(resourceA, resourceB, "t1"));
        Thread t2 = new Thread(() -> politeWork(resourceB, resourceA, "t2"));
        t1.start();
        t2.start();

        // через 2 секунды прервём, чтобы не висело вечно
        try {
            Thread.sleep(2000);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
        finished = true;
        t1.interrupt();
        t2.interrupt();
    }

    private static void politeWork(Object own, Object need, String name) {
        while (!finished && !Thread.currentThread().isInterrupted()) {
            synchronized (own) {
                synchronized (need) {
                    // ой, чужой занят — уступаем
                    System.out.println(name + ": уступаю");
                }
            }
            // отпустили оба, повторяем
            try {
                Thread.sleep(10);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
        }
    }
}
```

**Возможный вывод:**

```text
t1: уступаю
t2: уступаю
t1: уступаю
t2: уступаю
...
```

**Разбор:** оба потока активны, оба что-то печатают, но полезной работы не происходит. Это livelock в чистом виде: потоки не заблокированы (они в `RUNNABLE`), но прогресса нет. Обратите внимание: если убрать `sleep(10)`, CPU загрузится на 100% — потоки будут крутиться с максимальной скоростью, постоянно уступая друг другу.

Прервать эту программу можно только снаружи (по флагу `finished` или через `interrupt`). Сама она не завершится.

## Микрозадача 2: показать starvation

**Задача:** Создайте поток с `MIN_PRIORITY`, который в цикле выводит строку и делает `Thread.yield()`. Создайте поток с `MAX_PRIORITY`, который делает то же самое. Запустите на секунду и сравните, сколько раз успел напечатать каждый.

**Решение:**

```java
public class Main {
    private static volatile boolean stop = false;

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            int count = 0;
            while (!stop) {
                count++;
                Thread.yield();
            }
            System.out.println(Thread.currentThread().getName() + ": " + count);
        };

        Thread high = new Thread(task, "high");
        Thread low = new Thread(task, "low");
        high.setPriority(Thread.MAX_PRIORITY);
        low.setPriority(Thread.MIN_PRIORITY);
        high.start();
        low.start();

        Thread.sleep(1000);
        stop = true;
        high.join();
        low.join();
    }
}
```

**Возможный вывод:**

```text
high: 2347891
low: 312456
```

Или:

```text
high: 2103456
low: 2876540
```

**Разбор:** результат зависит от операционной системы и JVM. На Linux с CFS приоритеты почти не влияют — числа будут близки. На Windows или в некоторых старых JVM разница может быть заметна. Но **в любом случае** вы должны были увидеть, что один поток может «голодать» — получать меньше процессорного времени, чем другой.

Именно поэтому starvation так коварен: он нестабилен. Сегодня голодает один, завтра — другой. И вы никогда не знаете наверняка, что послужило причиной.

## 🎯 Самостоятельная задача

Реализуйте **эмуляцию перекрёстка с четырьмя машинами** — классическую задачу, где четыре потока подъезжают к перекрёстку одновременно и должны проехать по очереди.

Требования:

1. Четыре потока, каждый с именем `car-N` (`N` от 1 до 4).
2. Каждый поток пытается проехать через перекрёсток, используя общий ресурс — объект-перекрёсток.
3. Проезд занимает 100 мс (`sleep`).
4. **Запрещено** использовать `synchronized` на весь перекрёсток, потому что мы хотим показать проблему. Вместо этого используйте **флаг занятости** (`volatile boolean`):
   - Если перекрёсток свободен — машина занимает его, едет 100 мс, освобождает.
   - Если занят — машина **уступает**: ждёт немного и повторяет.
5. Запустите на 10 секунд. Посчитайте, сколько раз проехала каждая машина.

**Что вы должны увидеть:** если все четыре машины уступают друг другу одновременно, перекрёсток **не освобождается**. Всё время все четыре ждут, никто не едет.

- **Способ первый:** пусть каждая машина ждёт случайное время перед повтором. Через некоторое время кто-то проедет.
- **Способ второй:** пусть машины проезжают в порядке `id` — младшая уступает старшей, старшая едет первой.

## 📌 Что дальше

В следующей главе — **«`wait()`, `notify()`, `notifyAll()`»**. Это классический механизм координации потоков, который появился ещё в первых версиях Java. Мы разберём, как один поток может «уснуть» до определённого события, как другой поток может его «разбудить», и почему `wait()` всегда вызывается **в цикле `while`**, а не в `if`. А то ведь до сих пор мы разбирали только «не мешать» (`synchronized`) и «видеть» (`volatile`). Пора поговорить о том, как **координировать** действия потоков.

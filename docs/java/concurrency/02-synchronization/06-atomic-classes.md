# 2.6. Атомарные классы

## Где вы это уже видели

**Касса самообслуживания.** В магазине стоит автомат, который принимает наличные и выдаёт сдачу. Вы кладёте купюру — автомат **целиком** принимает её, проверяет, выдаёт сдачу. Нельзя «положить половину купюры»: либо купюра принята, либо нет. Промежуточного состояния не бывает.

**Банкомат.** Снимаете деньги. Банкомат либо выдаёт всю сумму, либо не выдаёт ничего. Если бы он мог «выдать половину и зависнуть» — вы бы очень расстроились, а банк — ещё больше.

**Светофор с переключением.** Красный — жёлтый — зелёный. Не бывает «наполовину красный, наполовину зелёный». В каждый момент — одно состояние.

**Общее во всех случаях** одно: есть операция, которая либо выполняется **целиком**, либо не выполняется вовсе. Промежуточного состояния нет. Это и называется **атомарностью**. `synchronized` даёт атомарность, но ценой блокировки. Атомарные классы дают её **без** блокировки — быстрее и часто проще.

## Теория

### Что такое атомарная операция

**Атомарная операция** — это операция, которая для наблюдателя выглядит как **одно неделимое действие**. Она либо выполнена полностью, либо не выполнена вовсе. Никакой другой поток не может увидеть её «в процессе».

`count++` — **не** атомарная операция, потому что состоит из трёх шагов: прочитать, увеличить, записать. Если вы помните главу 2.1 — именно из-за этого и возникла гонка.

Атомарные классы из пакета `java.util.concurrent.atomic` делают эту последовательность атомарной **на аппаратном уровне**, без `synchronized`. Процессоры поддерживают специальные инструкции (например, `CAS` — compare-and-swap), которые атомарно читают и записывают значение. Атомарные классы — это обёртки над такими инструкциями.

### AtomicInteger

Основной класс, с которым вы будете работать чаще всего, — `AtomicInteger`.

```java
import java.util.concurrent.atomic.AtomicInteger;

AtomicInteger counter = new AtomicInteger(0);

counter.incrementAndGet();  // ++counter, возвращает новое значение
counter.getAndIncrement();  // counter++, возвращает старое значение
counter.addAndGet(10);      // += 10, возвращает новое значение
counter.get();              // прочитать текущее
counter.set(42);            // установить значение
```

Теперь, если два потока одновременно вызывают `incrementAndGet()`, результат **всегда** правильный. Не «скорее всего», а **гарантированно**. Никакой гонки.

```java
public class Main {
    private static final AtomicInteger counter = new AtomicInteger(0);

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(Main::incrementMany);
        Thread t2 = new Thread(Main::incrementMany);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Получили: " + counter.get());
    }

    private static void incrementMany() {
        for (int i = 0; i < 1000; i++) {
            counter.incrementAndGet();
        }
    }
}
```

**Вывод** (всегда):

```text
Получили: 2000
```

Двести раз запустите — двести раз 2000. Не 1997, не 1993. Двести раз.

### Почему это быстрее synchronized

`synchronized` работает так: поток захватывает монитор, выполняет критическую секцию, отпускает монитор. Если монитор занят — поток **засыпает** (переходит в `BLOCKED`), и его нужно **разбудить**, когда монитор освободится. Засыпание и пробуждение — это переключение контекста, а переключение контекста — дорого (тысячи процессорных инструкций).

Атомарные классы работают иначе. Они не засыпают. Они используют **CAS-операцию**: «прочитай значение, проверь, что оно не изменилось, запиши новое». Если значение не изменилось — запись происходит. Если изменилось — попробуй ещё раз.

```text
Попытка CAS:
1. Прочитать current = value
2. Вычислить new = current + 1
3. Атомарно проверить: value всё ещё равно current?
   - Да → value = new. Успех.
   - Нет → вернуться к шагу 1 (повторить).
```

Это называется **оптимистичной блокировкой**: «я сделаю, и если что — повторю». Никакого засыпания, никакого переключения контекста. В большинстве случаев — одна итерация. Это существенно быстрее, чем `synchronized`.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> для простых атомарных операций (инкремент, установка, добавление) <code>AtomicInteger</code> почти всегда быстрее <code>synchronized</code>. Для сложной логики (несколько переменных, check-then-act) — <code>synchronized</code> или <code>Lock</code>.
</div>

### AtomicReference

`AtomicInteger` работает с числами. `AtomicReference<T>` — с любыми объектами.

```java
import java.util.concurrent.atomic.AtomicReference;

AtomicReference<String> ref = new AtomicReference<>("start");

ref.set("hello");
String current = ref.get();

// атомарная замена, если текущее значение равно "hello"
boolean success = ref.compareAndSet("hello", "world");
```

`compareAndSet(expected, newValue)` — это и есть та самая CAS-операция. Она делает следующее: «если текущее значение равно `expected` — установи `newValue` и верни `true`. Если не равно — ничего не делай и верни `false`».

Пример использования для одноразовой инициализации:

```java
AtomicReference<Config> configRef = new AtomicReference<>();

public Config getConfig() {
    Config current = configRef.get();
    if (current == null) {
        Config newConfig = loadConfig();
        // если кто-то ещё не успел записать — записываем мы
        // если уже записали — используем записанное
        if (configRef.compareAndSet(null, newConfig)) {
            return newConfig;
        } else {
            return configRef.get();
        }
    }
    return current;
}
```

Это ленивая инициализация без блокировки. Даже если десять потоков одновременно вызовут `getConfig()`, `loadConfig()` может выполниться несколько раз, но **записан** будет ровно один результат, и все увидят именно его.

### compareAndSet — сердце атомарности

Почти все атомарные классы построены на `compareAndSet` (CAS). Она есть у всех: `AtomicInteger`, `AtomicLong`, `AtomicReference`, `AtomicBoolean` и других.

```java
AtomicInteger counter = new AtomicInteger(5);

// Если текущее значение 5 — установить 10 и вернуть true
boolean ok = counter.compareAndSet(5, 10); // true
// Теперь counter == 10

// Если текущее значение 5 — установить 20. Но оно уже 10 — не сработает.
ok = counter.compareAndSet(5, 20); // false
// counter остался 10
```

Механика: аппаратная инструкция `CAS` сравнивает значение в памяти с ожидаемым и, если они равны, записывает новое. Всё это — **одна инструкция процессора**, неделимая. Промежуточного состояния нет.

### Цикл CAS: incrementAndGet изнутри

Как `incrementAndGet()` реализован через `compareAndSet`? Через цикл:

```java
public int incrementAndGet() {
    while (true) {
        int current = get();           // прочитать
        int next = current + 1;        // вычислить
        if (compareAndSet(current, next)) { // атомарно записать, если не изменилось
            return next;
        }
        // если не сработало — кто-то изменил между чтением и записью
        // повторяем
    }
}
```

Это и есть **оптимистичная блокировка**: «попробуй, если не вышло — повтори». В большинстве случаев срабатывает с первой попытки. В случае высокой конкуренции — повторяется несколько раз. Но никогда не блокируется.

### Проблема ABA

У CAS есть тонкая проблема, которая называется **ABA**.

Сценарий:

1. Поток A читает значение `X = 1`.
2. Поток B меняет `X` на `2`.
3. Поток B меняет `X` обратно на `1`.
4. Поток A делает `compareAndSet(1, 3)` — и это **успешно**, потому что текущее значение 1.

Но между шагами 1 и 4 значение менялось! Если для логики программы это важно — CAS может «проглотить» изменение.

Пример, где это ломается: реализация стека на CAS. Поток A хочет снять верхний элемент, читает голову. Поток B снимает два элемента и возвращает их (или добавляет новые). Поток A делает CAS — и получает в стеке «не то», что ожидал.

**Решение** — `AtomicStampedReference<T>`. Он хранит не только значение, но и **метку** (версию), и CAS проверяет и значение, и метку:

```java
import java.util.concurrent.atomic.AtomicStampedReference;

AtomicStampedReference<String> ref = new AtomicStampedReference<>("A", 0);

int[] stampHolder = new int[1];
String value = ref.get(stampHolder); // value = "A", stamp = 0

// Меняем значение и метку
ref.compareAndSet("A", "B", 0, 1);

// Теперь CAS с меткой 0 не сработает — метка уже 1
```

Для простых случаев ABA не проблема — например, для счётчика: увеличение на 1, потом на -1 — это просто «было 1, стало 1», и если вас интересует только итоговое значение, всё в порядке. Проблема возникает только когда важна **история** изменений.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> проблема ABA — редкость в реальной практике. Она возникает только в определённых структурах данных (стек, очередь) при определённом порядке операций. Для счётчиков и флагов она не важна. Но знать о ней надо — на случай, если вы её увидите.
</div>

### Другие атомарные классы

Помимо `AtomicInteger` и `AtomicReference`, есть ещё несколько.

- **`AtomicLong`** — как `AtomicInteger`, но для `long`.
- **`AtomicBoolean`** — для `boolean`. Часто используется как флаг «сделано/не сделано».
- **`AtomicIntegerArray`**, **`AtomicLongArray`**, **`AtomicReferenceArray`** — массивы с атомарным доступом к элементам.
- **`LongAdder`**, **`DoubleAdder`** — для случаев, когда нужно много потоков, каждый увеличивает счётчик. Внутри — набор счётчиков, что снижает конкуренцию. Быстрее `AtomicLong` при высокой нагрузке.
- **`LongAccumulator`**, **`DoubleAccumulator`** — обобщение adder: не только сложение, но любая ассоциативная операция.

`LongAdder` заслуживает отдельного упоминания: если у вас тысячи потоков одновременно увеличивают счётчик, `AtomicLong` начинает «пробуксовывать» — потоки повторяют CAS-операции, потому что конкуренция высока. `LongAdder` внутри держит **несколько** счётчиков (на каждый поток или группу потоков), и `sum()` складывает их при чтении. Это в разы быстрее при высокой конкуренции.

```java
import java.util.concurrent.atomic.LongAdder;

LongAdder adder = new LongAdder();
adder.increment();      // атомарно увеличить на 1
adder.add(10);          // атомарно добавить 10
long sum = adder.sum(); // сложить все внутренние счётчики
```

Обратите внимание: `sum()` — не атомарная операция. Она складывает все части, но если в это время кто-то добавляет — сумма может быть чуть устаревшей. Для счётчиков статистики это нормально; для финансов — нет.

### Когда что использовать

**`AtomicInteger` / `AtomicLong`** — обычный счётчик с одним-двумя потоками записи. Простой, быстрый, надёжный.

**`LongAdder`** — счётчик с высокой конкуренцией (много потоков пишут одновременно). Быстрее при нагрузке, но `sum()` не атомарен.

**`AtomicReference`** — замена ссылки на объект. Классика: одноразовая инициализация, «опубликовать результат».

**`AtomicBoolean`** — флаг «сделано/не сделано» без `synchronized`.

**`AtomicStampedReference`** — если важна проблема ABA. Редко, но иногда нужно.

**`synchronized`** — если операция включает несколько переменных или несколько шагов с логикой. Атомарные классы не заменяют `synchronized` для сложных случаев.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> атомарные классы — для <em>одной</em> переменной. Если нужно защитить <em>инвариант из нескольких переменных</em> («баланс A + баланс B = 2000»), никакой атомарный класс не поможет. Нужен <code>synchronized</code> или <code>Lock</code>.
</div>

### Аналогия с кассой самообслуживания

Вернёмся к началу главы. Атомарная операция — это **касса самообслуживания**. Вы кладёте купюру — автомат либо принимает её целиком, либо не принимает вовсе. Промежуточного состояния нет.

`synchronized` — это **живой кассир**. Он принимает купюру, проверяет, кладёт в ящик — всё по шагам. И пока он работает, он **занят**: другой покупатель ждёт. Медленнее, но надёжнее.

`AtomicInteger` — это **касса самообслуживания**. Быстро, без очереди, но только для простых операций. Если вам нужно что-то сложное (обмен валют, возврат, комбинированная покупка) — придётся идти к живому кассиру.

`compareAndSet` — это кнопка «подтвердить». Вы нажали — касса либо приняла, либо сказала «не могу, попробуйте снова». Нажали ещё раз — приняла. Никакого ожидания.

## Микрозадача 1: счётчик без гонки

**Задача:** Возьмите счётчик из главы 2.1 (два потока, каждый инкрементирует тысячу раз) и замените `int` на `AtomicInteger`. Убедитесь, что результат всегда 2000.

**Решение:**

```java
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    private static final AtomicInteger counter = new AtomicInteger(0);

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(Main::incrementMany);
        Thread t2 = new Thread(Main::incrementMany);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Получили: " + counter.get());
    }

    private static void incrementMany() {
        for (int i = 0; i < 1000; i++) {
            counter.incrementAndGet();
        }
    }
}
```

**Вывод** (всегда):

```text
Получили: 2000
```

**Разбор:** `incrementAndGet()` реализован через CAS-цикл. Даже если два потока одновременно попытаются увеличить счётчик, CAS гарантирует, что один из них сработает, а второй повторит попытку. Итог — ровно 2000. Никакого `synchronized`, никакой блокировки, никакого `BLOCKED`. Просто и быстро.

## Микрозадача 2: compareAndSet вручную

**Задача:** Реализуйте через `AtomicInteger` и `compareAndSet` операцию «увеличить, только если текущее значение меньше 100». Если значение уже 100 или больше — ничего не делать.

**Решение:**

```java
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    private static final AtomicInteger counter = new AtomicInteger(0);

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(Main::incrementIfBelow100);
        Thread t2 = new Thread(Main::incrementIfBelow100);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Получили: " + counter.get()); // всегда 100
    }

    private static void incrementIfBelow100() {
        while (true) {
            int current = counter.get();
            if (current >= 100) {
                return; // больше не инкрементируем
            }
            if (counter.compareAndSet(current, current + 1)) {
                // успешно увеличили — продолжаем
            }
            // если не сработало — цикл повторит попытку
        }
    }
}
```

**Вывод** (всегда):

```text
Получили: 100
```

**Разбор:** операция `if (current < 100) { current++ }` — это check-then-act, то есть **не** атомарная. Но мы построили её атомарно через CAS: читаем, проверяем, пытаемся записать. Если запись не удалась (кто-то изменил значение между чтением и записью) — повторяем. В результате счётчик вырастает ровно до 100, ни больше, ни меньше.

Обратите внимание: мы не использовали `synchronized` и не блокировали ничего. Просто CAS в цикле.

В следующей главе — **«Deadlock»**. Разберём, как два потока могут навсегда заблокировать друг друга, почему это происходит, и как от этого защищаться. А то ведь до сих пор все наши проблемы решались: гонка — `synchronized`, видимость — `volatile`, атомарность — `AtomicInteger`. Пора поговорить о том, что бывает, когда **блокировки блокируют друг друга**.

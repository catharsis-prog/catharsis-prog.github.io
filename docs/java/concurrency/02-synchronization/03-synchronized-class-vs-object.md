# 2.3. synchronized на уровне класса и объекта

## Где вы это уже видели

**Две примерочные в магазине.** В торговом центре их две, и это правильно: две посетительницы могут переодеваться одновременно, не мешая друг другу. Замок на каждой свой, ключи разные. Пока одна занята в первой, вторая свободна для следующей.

**Один туалет на этаже.** А вот туалет один. Все, кто на этаже, стоят в одной очереди. Замок один, ключ один, и неважно, из какого ты офиса — ждёшь вместе со всеми.

**Общий принтер.** В опенспейсе стоит один принтер. Пока один печатает, остальные ждут. Неважно, кто ты и из какого отдела, — принтер один на всех.

**Личный принтер в кабинете.** А вот у начальника свой принтер в кабинете. Пока он печатает, остальным нет дела — у них свой.

**Общее во всех случаях** одно: у каждого ресурса есть свой замок. Примерочная с ключом, туалет с ключом, принтер с очередью. Потоки в Java работают так же: **у каждого монитора своя очередь**. И самая частая ошибка — перепутать, какой именно монитор захватывает `synchronized` в конкретном случае.

## Теория

### Четыре комбинации

`synchronized` может стоять в четырёх местах, и в каждом случае захватывается **свой** монитор. Вот полная таблица.

| Где стоит `synchronized` | Какой монитор захватывается |
|---|---|
| `public synchronized void method()` | `this` — объект, на котором вызван метод |
| `public static synchronized void method()` | `ClassName.class` — объект класса |
| `synchronized (this) { ... }` | `this` — тот же объект |
| `synchronized (SomeObject.class) { ... }` | `SomeObject.class` — объект класса |

Разберём каждую строчку, потому что разница между ними — это разница между «работает» и «не работает».

### Случай первый: synchronized-метод экземпляра

```java
public class Counter {
    private int count = 0;

    public synchronized void increment() {
        count++;
    }
}
```

Здесь `synchronized` — это `synchronized (this)`. Поток, вошедший в метод, захватывает монитор **того объекта**, на котором вызван метод.

```java
Counter c1 = new Counter();
Counter c2 = new Counter();

// Поток A вызывает c1.increment()
// Поток B вызывает c2.increment()
```

Поток A захватывает монитор `c1`, поток B — монитор `c2`. Это **разные мониторы**. Потоки не мешают друг другу, работают параллельно. Счётчики `c1.count` и `c2.count` — независимые, и это правильно: каждый защищён своим монитором.

А теперь важный вопрос: что если оба потока вызывают `c1.increment()`? Тогда оба хотят захватить монитор `c1`. Один захватывает, второй ждёт в `BLOCKED`. Это и есть нужное поведение.

**Вывод:** `synchronized`-метод экземпляра защищает данные **одного объекта**. Два разных объекта защищены независимо.

### Случай второй: static synchronized-метод

```java
public class Counter {
    private static int count = 0;

    public static synchronized void increment() {
        count++;
    }
}
```

Здесь `synchronized` — это `synchronized (Counter.class)`. Захватывается монитор **объекта класса**, а он в JVM ровно один на весь класс, сколько бы экземпляров вы ни создали.

```java
Counter c1 = new Counter();
Counter c2 = new Counter();

// Поток A вызывает Counter.increment() (через класс)
// Поток B вызывает c2.increment() (тоже через класс, но через экземпляр)
```

Оба потока захватывают **один и тот же** монитор — `Counter.class`. Значит, мешают друг другу. Даже если вызывают через разные экземпляры (что для `static`-метода неважно), монитор один.

**Вывод:** `static synchronized` защищает **все** объекты класса и все статические данные. Это более «глобальная» блокировка.

### Случай третий: synchronized(this)

```java
public void increment() {
    synchronized (this) {
        count++;
    }
}
```

Это **эквивалент** первого случая. `synchronized (this)` захватывает монитор объекта, на котором вызван метод. Разница только в том, что блок защищает не весь метод, а только его часть.

Обычно `synchronized (this)` используется, когда в методе есть подготовительная работа, которую не нужно блокировать.

### Случай четвёртый: synchronized по объекту класса

```java
public void increment() {
    synchronized (Counter.class) {
        count++;
    }
}
```

Это **эквивалент** второго случая. `Counter.class` — это объект класса, он в JVM один. Все потоки, которые захватывают монитор `Counter.class` (через `static synchronized` или через `synchronized (Counter.class)`), стоят в одной очереди.

### Ключевое правило

Два потока мешают друг другу **только** если захватывают один и тот же монитор. Если мониторы разные — идут параллельно. Это правило важнее всех остальных.

```text
Поток A: synchronized (X) ─┐
                           ├─ МЕШАЮТ (один монитор X)
Поток B: synchronized (X) ─┘

Поток A: synchronized (X) ─┐
                           ├─ НЕ МЕШАЮТ (разные мониторы)
Поток B: synchronized (Y) ─┘
```

Отсюда следует простое правило проектирования: **если вы защищаете общие данные, все обращения к этим данным должны использовать один и тот же монитор**. Иначе защита не работает.

### Разбор самостоятельной задачи из главы 2.2

Теперь вернёмся к задаче про банк. Напомню постановку: два счёта, два потока делают переводы в разные стороны, сумма балансов должна остаться 2000. Вы сделали `transfer` синхронизированным — и, скорее всего, обнаружили, что это **не помогло**.

Вот почему.

```java
public class BankAccount {
    private int balance;

    public synchronized void transfer(BankAccount to, int amount) {
        this.balance -= amount;
        to.balance += amount;
    }
}
```

Поток A вызывает `accountA.transfer(accountB, 100)`. Он захватывает монитор `accountA` и начинает перевод: снимает со счёта A, потом собирается добавить на счёт B.

Поток B в это время вызывает `accountB.transfer(accountA, 100)`. Он захватывает монитор `accountB` — **другой монитор** — и тоже начинает перевод: снимает со счёта B, потом собирается добавить на счёт A.

Оба потока вошли в критическую секцию одновременно, потому что мониторы разные. Оба читают, оба пишут, **никакой защиты между ними нет**. Сумма балансов может разойтись.

Формально это частный случай той же ошибки, что и в главе 2.2: **synchronized защищает только тот монитор, который захвачен**. Здесь два потока захватывают разные мониторы, поэтому `synchronized` защищает не общие данные (сумму двух балансов), а каждый счёт по отдельности.

### Как исправить

Чтобы защитить перевод между двумя счетами, нужен **один общий монитор** для обоих счетов. Есть несколько способов.

**Способ первый: общий объект-замок, переданный в конструктор.**

```java
public class BankAccount {
    private int balance;
    private final Object lock;

    public BankAccount(int balance, Object lock) {
        this.balance = balance;
        this.lock = lock;
    }

    public void transfer(BankAccount to, int amount) {
        synchronized (lock) {
            this.balance -= amount;
            to.balance += amount;
        }
    }

    public int getBalance() {
        synchronized (lock) {
            return balance;
        }
    }
}
```

Оба счёта должны получить **один и тот же** объект `lock`. Тогда `transfer` на любом счёте захватывает один монитор, и переводы защищены друг от друга.

**Способ второй: монитор класса.**

```java
public class BankAccount {
    private int balance;

    public void transfer(BankAccount to, int amount) {
        synchronized (BankAccount.class) {
            this.balance -= amount;
            to.balance += amount;
        }
    }
}
```

Этот вариант проще, но грубее: **все** переводы между **любыми** счетами в программе сериализуются. Если у вас миллион счетов и миллион независимых переводов, они будут выполняться по очереди — плохо для производительности. Подходит для маленьких программ, не для реальных систем.

**Способ третий: атомарная операция через один общий монитор, но разный для разных пар.** Об этом — в главе про deadlock и в модуле 5 (`ConcurrentHashMap`). Пока просто запомните: **правильный выбор монитора — это ключ к защите**.

  <strong style="color: #B388FF;">Правило:</strong> защищая общие данные, используйте <em>один</em> монитор для <em>всех</em> обращений к этим данным. Если вы защищаете «сумму двух балансов», а мониторы разные — вы не защищаете ничего.
</div>

### Практический совет: отдельный объект-замок

Опытные разработчики часто заводят отдельное поле `private final Object lock = new Object()` и синхронизируются по нему, а не по `this`.

```java
public class Counter {
    private int count = 0;
    private final Object lock = new Object();

    public void increment() {
        synchronized (lock) {
            count++;
        }
    }
}
```

Почему это лучше, чем `synchronized(this)`? Потому что **никто снаружи не может захватить ваш монитор**. Если вы синхронизируетесь по `this`, то любой внешний код тоже может сделать `synchronized (counter) { ... }` и тем самым захватить ваш монитор, заблокировав ваш код. С отдельным объектом-замком такой возможности нет: он доступен только вашему классу.

Это маленькая деталь, но в реальных командах она становится стандартом.

### Аналогия с примерочными

Вернёмся к началу главы. Примерочная с замком — это монитор объекта. У каждой примерочной свой ключ. Посетительницы, которые хотят в **разные** примерочные, не мешают друг другу. А те, кто хочет в **одну и ту же**, — стоят в одной очереди.

`synchronized`-метод экземпляра — это замок на **своей** примерочной. `static synchronized` — это замок на **общей** примерочной, куда все ходят по очереди. Один замок на всех — на всех и очередь.

Ошибка, которую допустил автор в задаче про банк, — это попытка защитить «перевод между двумя примерочными», повесив замок только на одну. Вторая остаётся открытой, и через неё можно пройти в тот же момент. Правильное решение — повесить **один замок на обе** — то есть использовать общий монитор.

## Микрозадача 1: разные мониторы не мешают друг другу

**Задача:** Создайте два объекта `Counter` с `synchronized`-методом `increment`. Запустите по потоку на каждый и убедитесь, что они выполняются параллельно — то есть один не ждёт другого.

**Решение:**

```java
public class Counter {
    private int count = 0;

    public synchronized void incrementMany(String name) {
        long start = System.currentTimeMillis();
        for (int i = 0; i < 10_000_000; i++) {
            count++;
        }
        long elapsed = System.currentTimeMillis() - start;
        System.out.println("[" + name + "] готово за " + elapsed + " мс");
    }
}

public class Main {
    public static void main(String[] args) throws InterruptedException {
        Counter c1 = new Counter();
        Counter c2 = new Counter();

        Thread t1 = new Thread(() -> c1.incrementMany("c1"), "t1");
        Thread t2 = new Thread(() -> c2.incrementMany("c2"), "t2");

        long start = System.currentTimeMillis();
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        long total = System.currentTimeMillis() - start;
        System.out.println("Всего: " + total + " мс");
    }
}
```

**Возможный вывод:**

```text
[c1] готово за 150 мс
[c2] готово за 155 мс
Всего: 160 мс
```

**Разбор:** каждый поток работал со своим `Counter` и захватывал свой монитор. Они не мешали друг другу, поэтому общее время примерно равно времени одного потока, а не сумме. Если бы оба потока работали с **одним** `Counter`, второй ждал бы первого, и общее время было бы около 300 мс. Это и есть разница «разные мониторы» / «один монитор» на практике.

## Микрозадача 2: static synchronized блокирует всё

**Задача:** Сделайте `incrementMany` `static synchronized`. Запустите два потока на **разных** объектах `Counter`. Убедитесь, что теперь они **ждут** друг друга, потому что монитор один — монитор класса.

**Решение:**

```java
public class Counter {
    private static int count = 0;

    public static synchronized void incrementMany(String name) {
        long start = System.currentTimeMillis();
        for (int i = 0; i < 10_000_000; i++) {
            count++;
        }
        long elapsed = System.currentTimeMillis() - start;
        System.out.println("[" + name + "] готово за " + elapsed + " мс");
    }
}

public class Main {
    public static void main(String[] args) throws InterruptedException {
        Counter c1 = new Counter();
        Counter c2 = new Counter();

        Thread t1 = new Thread(() -> c1.incrementMany("c1"), "t1");
        Thread t2 = new Thread(() -> c2.incrementMany("c2"), "t2");

        long start = System.currentTimeMillis();
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        long total = System.currentTimeMillis() - start;
        System.out.println("Всего: " + total + " мс");
    }
}
```

**Возможный вывод:**

```text
[c1] готово за 150 мс
[c2] готово за 155 мс
Всего: 310 мс
```

**Разбор:** оба потока вызывают `static synchronized`-метод, который захватывает монитор `Counter.class`. Неважно, через `c1` или через `c2` вызван метод — монитор один. Потоки стоят в одной очереди. Общее время теперь примерно равно **сумме** времён двух потоков, а не максимуму. Это и есть цена «глобальной» блокировки.

## 📌 Что дальше

В следующей главе — **«`volatile`»**. Разберём ещё одну разновидность проблемы с общими данными: **видимость изменений**. Оказывается, даже без гонки `count++`, один поток может просто **не увидеть** изменений, сделанных другим, — из-за кэшей процессора и оптимизаций JVM. `volatile` решает эту проблему, но, как выяснится, **не решает** гонку. А то ведь до сих пор мы говорили только о взаимном исключении. Пора поговорить о том, что видят потоки.

# 2.1. Гонка данных

## Где вы это уже видели

Модуль первый был про то, как запускать потоки. Модуль второй — про то, как не дать им испортить друг другу жизнь. Начнём с самой неприятной вещи в многопоточности — с бага, который не валит программу, а тихо портит данные.

**Бронирование билета.** Два человека открывают приложение авиакомпании. На рейсе осталось одно место. Оба видят: «Свободно: 1». Оба нажимают «Забронировать». Оба получают подтверждение. Через день выясняется, что на одно место — два пассажира. Кто виноват? Не пилот, не бортпроводник. Программист.

**Лайки.** Видео на платформе. Сто лайков. Два человека одновременно ставят лайк. Система должна показать сто два. А показывает сто один. Потому что оба потока прочитали «100», оба прибавили единицу, оба записали «101».

**Аукцион.** Два человека в одну секунду ставят одинаковую максимальную ставку. Оба видят «ставка принята». А победитель один.

**Склад.** Десять единиц товара. Два кладовщика одновременно отгружают по одной. В системе должно остаться восемь. Остаётся девять. Один товар ушёл бесплатно.

**Общий знаменатель** у всех случаев один: два потока одновременно работают с одними и теми же данными, и результат зависит от того, кто успел первым. Это и называется гонкой данных. Баг этот страшнее прочих не потому, что валит программу с грохотом — такой вы найдёте за пять минут. А потому, что сидит тихо, проявляется раз в тысячу запусков и портит данные незаметно.

## Теория

### Что такое гонка данных

**Гонка данных** — ситуация, когда два или несколько потоков одновременно обращаются к общим данным, и хотя бы один из них пишет. Результат зависит от того, в каком порядке потоки получили доступ. А порядок этот непредсказуем: им управляет планировщик, а не ваша программа.

Гонка — это всегда баг. Даже если программа иногда выдаёт правильный результат. Правильный результат «по случайности» — это не правильный результат, а не обнаруженный баг.

### Почему count++ — это не одна операция

Вот код, который выглядит безобидно:

```java
public class Counter {
    private int count = 0;

    public void increment() {
        count++;
    }

    public int get() {
        return count;
    }
}
```

`count++` кажется одной операцией. На самом деле это три:

1. Прочитать `count` из памяти в регистр процессора.
2. Увеличить значение в регистре на единицу.
3. Записать значение обратно в память.

Между любыми двумя из этих шагов планировщик может переключить поток. И если два потока выполняют `count++` одновременно, возможен такой сценарий:

```text
Поток A                 Поток B                 count
─────────────────────────────────────────────────────
читает count (5)                                5
                        читает count (5)        5
увеличивает (6)                                 5
                        увеличивает (6)         5
записывает 6                                    6
                        записывает 6            6
```

Ожидалось 7, получилось 6. Один инкремент потерян. Заметьте: ни один поток не сделал ничего «неправильного». Каждый прочитал актуальное значение, каждый корректно прибавил единицу. Проблема в том, что операция **не атомарна** — её можно прервать посередине.

### Как увидеть это своими глазами

Создадим счётчик и два потока, каждый инкрементирует его тысячу раз. Ожидаем 2000. Получим — что получится.

```java
public class Main {
    private static int counter = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(Main::incrementMany);
        Thread t2 = new Thread(Main::incrementMany);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Ожидали: 2000, получили: " + counter);
    }

    private static void incrementMany() {
        for (int i = 0; i < 1000; i++) {
            counter++;
        }
    }
}
```

Запустите раз десять. Иногда увидите ровно 2000 — планировщик ни разу не переключил потоки в неудачный момент. Иногда 1999, 1998, 1995. В редких случаях меньше. Каждый запуск — новое число.

### Почему баг нестабилен

Гонка данных — это не «всегда ломается» и не «всегда работает». Это «зависит от того, как легли карты».

На одноядерной машине планировщик переключает потоки по таймеру, раз в несколько миллисекунд. Шанс, что переключение попадёт ровно между чтением и записью, невелик. На многоядерной машине потоки реально работают одновременно, и шанс попасть в неудачное окно выше.

На тестовом сервере с маленькой нагрузкой баг может годами не проявляться. А в продакшене, под нагрузкой, с тысячами запросов в секунду — вылезает через день. И искать его будет кто-то другой. Потому что вы к тому времени уже уволились.

### Не только count++: check-then-act

Проблема не только в инкременте. Любая последовательность «прочитал — проверил — сделал» уязвима.

```java
public void addIfSpace(int value) {
    if (list.size() < 10) {
        list.add(value);
    }
}
```

Два потока видят `size == 9`, оба проходят проверку, оба добавляют. В списке оказывается 11 элементов вместо максимум десяти. Проблема та же: проверка и действие не атомарны.

Такая гонка называется **check-then-act**: сначала проверяем условие, потом действуем. Между проверкой и действием условия может измениться. И если это происходит, мы действуем по устаревшей информации.

### Как обнаружить гонку

Три признака.

1. **Результат зависит от порядка выполнения.** Если поменять порядок потоков — результат меняется. Или хотя бы может измениться.
2. **Результат нестабилен.** Один и тот же код при одном и том же входе даёт разные результаты.
3. **Баг исчезает, когда поток становится один.** Или когда добавляешь `Thread.sleep()` — потому что тогда потоки перестают пересекаться.

Если видите хотя бы один признак — ищите гонку.

## Микрозадача 1: сколько раз из пяти

**Задача:** Запустите программу со счётчиком из этой главы пять раз подряд. Посчитайте, сколько раз из пяти получилось ровно 2000, а сколько — меньше.

**Решение:**

```java
public class Main {
    private static int counter = 0;

    public static void main(String[] args) throws InterruptedException {
        counter = 0;
        Thread t1 = new Thread(Main::incrementMany);
        Thread t2 = new Thread(Main::incrementMany);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Получили: " + counter);
    }

    private static void incrementMany() {
        for (int i = 0; i < 1000; i++) {
            counter++;
        }
    }
}
```

Запустите `main` пять раз вручную или оберните в цикл.

**Возможный вывод:**

```text
Получили: 2000
Получили: 1997
Получили: 2000
Получили: 1993
Получили: 2000
```

**Разбор:** в двух случаях из пяти программа выдала «правильный» результат. В трёх — потеряла несколько инкрементов. Причина — та же самая: планировщик в этих трёх случаях переключил потоки ровно между чтением и записью `counter`. Каждый запуск — новая лотерея. Именно поэтому баг и называется «нестабильным»: он не «есть» или «нет», он «проявляется или нет» в зависимости от обстоятельств.

## Микрозадача 2: check-then-act

**Задача:** Покажите гонку на операции «проверить и добавить». Создайте `ArrayList<Integer>`, два потока, каждый добавляет в список по одному элементу за раз, но только если в списке меньше десяти элементов. Дождитесь завершения и проверьте размер.

**Решение:**

```java
import java.util.ArrayList;
import java.util.List;

public class Main {
    private static final List<Integer> list = new ArrayList<>();

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(Main::addMany);
        Thread t2 = new Thread(Main::addMany);
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("Размер списка: " + list.size() + " (ожидали не больше 10)");
    }

    private static void addMany() {
        for (int i = 0; i < 100; i++) {
            if (list.size() < 10) {
                list.add(i);
            }
        }
    }
}
```

**Возможный вывод:**

```text
Размер списка: 11 (ожидали не больше 10)
```

Или 12, или 13 — в зависимости от того, сколько раз потоки успели «проскочить» проверку одновременно.

**Разбор:** оба потока видят `size == 9`, оба проходят проверку `if (size < 10)`, оба добавляют. В результате — 11. Если добавлять в цикле много раз, гонка может сработать несколько раз, и список вырастет сильнее. Причём `ArrayList` сам по себе не потокобезопасен, так что тут могут возникнуть и другие проблемы — о них в модуле 5. Но главная проблема видна и без них: **проверка и действие не атомарны**.

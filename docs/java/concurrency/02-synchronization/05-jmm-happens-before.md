# 2.5. Модель памяти Java и happens-before

## Где вы это уже видели

**Нотариальное заверение.** Вы подписали договор. Просто подпись — это одно. А подпись, заверенная нотариусом, — совсем другое: она имеет **юридическую силу**. Нотариус гарантирует, что документ подлинный, и эту гарантию признают все. Без нотариуса — «а докажите, что это вы подписали». С нотариусом — «доказано, вопрос закрыт».

**Доставка с уведомлением.** Вы отправили письмо. Обычное письмо — «ну, наверное, дошло». Письмо с уведомлением о вручении — у вас на руках **доказательство**, что получатель его видел. Разница не в самом письме, а в **гарантии**.

**Сохранение в облаке.** Вы нажали «Сохранить» в документе. Если у вас выключена синхронизация — коллега, открывший документ, увидит **старую** версию. А если синхронизация включена — увидит новую. Разница — в наличии **механизма**, который гарантирует видимость.

**Общее во всех случаях** одно: есть действие, а есть **гарантия**, что результат этого действия увидят другие. В программировании такая гарантия называется **happens-before**. И это не абстрактное понятие, а формальное правило, на которое можно ссылаться в спорах о том, «работает ли код».

## Теория

### Что такое модель памяти

До сих пор мы говорили: «поток может не увидеть изменение», «volatile гарантирует видимость», «synchronized тоже гарантирует видимость». Но **откуда** эти гарантии? Кто их даёт?

Их даёт **модель памяти Java** — сокращённо JMM (Java Memory Model). Это часть спецификации языка, которая описывает, **какие значения может увидеть поток** при чтении переменной. Не «как устроен процессор», не «как работает кэш», а именно **что гарантировано** на уровне языка.

JMM — это как правила дорожного движения. Они не описывают, как устроен двигатель, зато точно говорят, кто кому уступает. Соблюдаете правила — все живы. Нарушаете — сами понимаете.

### Формальное определение happens-before

**Happens-before** — это отношение между двумя действиями в программе. Запись `A happens-before B` означает: **все изменения, сделанные до A, гарантированно видны в B**.

То есть если поток сделал что-то, а потом это «что-то» находится в отношении happens-before с действием в другом потоке, то второй поток увидит все изменения первого. Не «может увидеть», не «скорее всего увидит», а **гарантированно**.

Это формальное правило. На него можно ссылаться: «вот здесь happens-before, значит, код корректен». А не «на моей машине работало».

### Основные правила happens-before

Спецификация Java определяет несколько правил, которые создают отношение happens-before. Вот главные.

#### Правило 1: program order (порядок программы)

**Внутри одного потока** действия выполняются в том порядке, в котором они написаны. Если в потоке `A` написано `x = 1; y = 2;`, то `x = 1` happens-before `y = 2`.

Это правило кажется очевидным, но оно важно: оно даёт базу, от которой строятся все остальные.

#### Правило 2: monitor lock (монитор)

**Выход из `synchronized`-блока happens-before вход в `synchronized`-блок с тем же монитором.**

То есть если поток A вышел из `synchronized (lock)`, а поток B потом вошёл в `synchronized (lock)` с тем же `lock`, то все изменения, которые A сделал до выхода, видны в B после входа.

```java
// Поток A
synchronized (lock) {
    data = 42;   // это изменение
}                 // happens-before следующего входа

// Поток B
synchronized (lock) {
    int x = data; // увидит 42
}
```

Вот почему `synchronized` даёт не только взаимное исключение, но и **видимость**.

#### Правило 3: volatile

**Запись в `volatile`-переменную happens-before чтение из неё.**

Если поток A записал значение в `volatile`-переменную, а поток B потом прочитал эту переменную, то все изменения, которые A сделал **до записи**, видны в B после чтения.

```java
// Поток A
data = 42;         // изменение
flag = true;       // volatile-запись

// Поток B
if (flag) {        // volatile-чтение, увидел true
    int x = data;  // увидит 42
}
```

Вот почему `volatile` гарантирует видимость не только самого себя, но и **всего, что было записано до него**.

#### Правило 4: thread start

**`Thread.start()` happens-before любое действие в новом потоке.**

То есть всё, что было сделано до `start()`, видно новому потоку.

```java
data = 42;      // изменение в main
thread.start(); // happens-before всего в новом потоке

// Внутри thread.run():
int x = data;   // увидит 42
```

Это логично: новый поток создаётся **после** того, как вы подготовили данные. Иначе было бы бессмысленно передавать что-то в поток при создании.

#### Правило 5: thread join

**Любое действие в потоке happens-before `join()` на этом потоке.**

То есть после `join()` все изменения, сделанные завершившимся потоком, видны тому, кто ждал.

```java
// Внутри worker:
data = 42;      // изменение

// В main:
worker.join();  // happens-before всех действий после join
int x = data;   // увидит 42
```

Это тоже логично: `join()` означает «дождаться завершения». Если дождались — увидели результат.

#### Правило 6: transitivity (транзитивность)

**Если A happens-before B, а B happens-before C, то A happens-before C.**

Это самое мощное правило. Оно позволяет строить **цепочки** гарантий.

```java
// Поток A
data = 42;          // A
flag = true;        // volatile-запись, A happens-before B

// Поток B
if (flag) {         // B — volatile-чтение
    otherFlag = true; // volatile-запись, B happens-before C
}

// Поток C
if (otherFlag) {    // C — volatile-чтение
    int x = data;   // увидит 42 — через транзитивность
}
```

Поток A записал `data`, потом `flag`. Поток B увидел `flag`, записал `otherFlag`. Поток C увидел `otherFlag` и читает `data`. По транзитивности: A happens-before B, B happens-before C, значит, A happens-before C. Поток C увидит `data = 42`.

  <strong style="color: #B388FF;">Правило:</strong> happens-before — это <em>транзитивное</em> отношение. Если вы можете построить цепочку от записи к чтению, все изменения по цепочке видны. Если не можете — гарантий нет.
</div>

### Что happens-before НЕ гарантирует

Важно понимать, что happens-before — это **не** «всё происходит в порядке, в котором написано». Это отношение между **конкретными** действиями, которые связаны определёнными механизмами (`synchronized`, `volatile`, `start`, `join`).

Если между двумя действиями нет happens-before — у вас **нет гарантий**. Никаких. Может сработать, может не сработать. На вашей машине сработает, на сервере — нет.

```java
// Поток A
data = 42;

// Поток B
int x = data; // НЕТ happens-before между этими действиями
```

Здесь нет ни `synchronized`, ни `volatile`, ни `start`, ни `join` между записью и чтением. Значит, нет гарантии. `x` может быть 42, а может быть 0 — как повезёт. Формально это гонка данных, и поведение программы **не определено**.

### Почему без happens-before поведение не определено

Это важный момент, и он отличается от «программа сломается». В Java, если есть гонка данных, поведение **не определено спецификацией**. Это не значит «программа упадёт» или «программа выдаст неправильный результат». Это значит, что JVM **имеет право** сделать что угодно: увидеть старое значение, увидеть новое, увидеть «полузаписанное» значение (для `long` и `double`), переупорядочить операции.

На практике JVM не делает «чего угодно» — она следует разумным оптимизациям. Но спецификация не гарантирует, что эти оптимизации совпадут на разных JVM, разных процессорах, разных версиях Java. Поэтому полагаться на поведение без happens-before нельзя.

### final-поля и безопасная публикация

Особый случай happens-before — это `final`-поля. Если объект сконструирован корректно, `final`-поля гарантированно видны другим потокам в **правильном** состоянии — то есть после инициализации, а не в промежуточном.

Это называется **безопасной публикацией**. Подробнее — в главе 2.13 про неизменяемость и в модуле 7. Пока достаточно знать: `final`-поля — это способ сделать объект «видимым целиком», без использования `synchronized` или `volatile`.

### Аналогия с нотариусом

Вернёмся к началу главы. `happens-before` — это **нотариальное заверение**. Вы сделали действие, нотариус поставил печать — и теперь это действие имеют право видеть все. Без печати — «а докажите, что это вы».

`synchronized`, `volatile`, `start`, `join` — это **нотариусы**. Каждый из них создаёт happens-before между двумя действиями. Между какими именно — зависит от механизма.

Программа без happens-before — это как договор без нотариуса. Может, всё и хорошо, а может, и нет. Спецификация говорит: «не гарантирую». И если что-то пойдёт не так — это ваша проблема, а не JVM.

### Как использовать это на практике

Практический вывод простой: **если вы работаете с общими данными из разных потоков, между записью и чтением должен быть happens-before**. Создаётся он четырьмя механизмами.

1. **`synchronized`** — через монитор.
2. **`volatile`** — через саму переменную.
3. **`Thread.start()`** — при создании потока.
4. **`Thread.join()`** — при ожидании завершения.

Если ни один из этих механизмов не задействован — у вас гонка данных, и поведение программы не определено. Это не «может сломаться», это «спецификация не гарантирует ничего». Разница тонкая, но важная: гонку нужно **исправлять**, а не «надеяться, что пронесёт».

## Микрозадача 1: построить happens-before через volatile

**Задача:** Создайте два потока. Поток A записывает в обычную переменную `data` значение 42, потом записывает `true` в `volatile`-переменную `ready`. Поток B в цикле читает `ready`, пока не увидит `true`, потом читает `data`. Убедитесь, что `data` всегда равна 42.

**Решение:**

```java
public class Main {
    private static int data = 0;
    private static volatile boolean ready = false;

    public static void main(String[] args) throws InterruptedException {
        Thread producer = new Thread(() -> {
            data = 42;       // изменение
            ready = true;    // volatile-запись, happens-before чтения в consumer
        }, "producer");

        Thread consumer = new Thread(() -> {
            while (!ready) {
                // ждём
            }
            System.out.println("data = " + data);
        }, "consumer");

        consumer.start();
        Thread.sleep(100);
        producer.start();

        producer.join();
        consumer.join();
    }
}
```

**Вывод:**

```text
data = 42
```

Всегда 42, сколько бы раз ни запускали.

**Разбор:** поток `producer` записал `data = 42`, потом `ready = true`. Между `data = 42` и записью в `ready` действует program order (внутри одного потока). Между записью в `ready` и чтением `ready` в `consumer` действует правило volatile. По транзитивности: `data = 42` happens-before `ready = true` happens-before чтения `ready` happens-before `data = 42` (чтение). Значит, `consumer` гарантированно увидит `data = 42`.

Если бы `ready` не был `volatile` — гарантий не было бы. `consumer` мог бы зависнуть в цикле навсегда или прочитать `data = 0`.

## Микрозадача 2: без happens-before — не определено

**Задача:** Уберите `volatile` из предыдущей задачи. Запустите несколько раз. Убедитесь, что поведение нестабильно: иногда программа зависает, иногда `data` равна 0, иногда 42.

**Решение:**

```java
public class Main {
    private static int data = 0;
    private static boolean ready = false; // больше не volatile

    public static void main(String[] args) throws InterruptedException {
        Thread producer = new Thread(() -> {
            data = 42;
            ready = true;
        }, "producer");

        Thread consumer = new Thread(() -> {
            while (!ready) {
                // ждём
            }
            System.out.println("data = " + data);
        }, "consumer");

        consumer.start();
        Thread.sleep(100);
        producer.start();

        producer.join();
        consumer.join();
    }
}
```

**Возможные выводы (разные запуски):**

```text
data = 42
```

Или:

```text
data = 0
```

Или вообще ничего — программа висит, `consumer` не видит `ready = true`.

**Разбор:** без `volatile` между записью `data` и чтением `data` нет happens-before. Поведение не определено. На практике `consumer` читает `ready` из своего кэша и не видит, что `producer` записал `true`. Или видит `true`, но `data` всё ещё 0 — потому что запись `data` тоже не видна. Это **не** «плохо работает» — это «спецификация ничего не гарантирует». Разные машины, разные JVM, разные запуски могут давать разные результаты. И это правильно с точки зрения JMM: вы не создали механизм, который гарантирует видимость.

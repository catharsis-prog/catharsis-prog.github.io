# Практикум по модулю 3. Высокоуровневая координация

## Зачем это

Модуль 1 был про то, как запускать потоки. Модуль 2 — про то, как не дать им испортить данные. Модуль 3 — про то, как **координировать** их действия: ждать, встречаться, ограничивать, обмениваться.

Мы прошли пять глав: `CountDownLatch`, `CyclicBarrier`, `Semaphore`, `Exchanger` и `Phaser`, `Lock` и `Condition`. Пора собрать всё это вместе. Задачи этого практикума требуют **выбирать** подходящий примитив, а не просто применять тот, что «изучали вчера». В реальной работе почти никогда не бывает «вот тебе задача на `Semaphore`» — бывает «вот тебе задача, реши её как знаешь». Этот навык и тренируем.

**Разборы** — на отдельной странице: **[Разборы практикума](/java/concurrency/03-coordination/practice-solutions)**. Сначала попробуйте сами.

## Задача 1. Запуск микросервисов

**Что комбинируется:** 3.1 (`CountDownLatch`), 1.6 (прерывание), 1.8 (демоны).

Сервис `order` не может начать принимать запросы, пока не готовы три зависимости: `db`, `cache`, `queue`. Каждая запускается в своём потоке и инициализируется случайное время от 500 до 3000 мс.

**Требования:**

1. Создайте `CountDownLatch(3)` для трёх зависимостей.
2. Каждая зависимость в своём потоке: спит, потом печатает `[db] готов`, вызывает `countDown()` в `finally`.
3. Главный поток ждёт `latch.await(5, TimeUnit.SECONDS)`.
4. Если дождались — печатает `order: все зависимости готовы, принимаю запросы`.
5. Если таймаут — печатает `order: не все зависимости готовы за 5 секунд` и завершается.

**Дополнительно:** сделайте так, чтобы одна из зависимостей («cache») падала с `RuntimeException` до `countDown()`. Убедитесь, что `finally` спасает программу от вечного ожидания.

2. Что произойдёт без таймаута, если одна зависимость «зависнет» навсегда?
3. Почему `CountDownLatch` здесь лучше, чем `join()` на потоках?

## Задача 2. Многораундовая симуляция

**Что комбинируется:** 3.2 (`CyclicBarrier`), 2.2 (`synchronized`), 2.5 (happens-before).

Симуляция распространения тепла в одномерном стержне. Массив из 20 элементов, начальная температура — 0 везде, кроме центрального элемента (индекс 10) — 100.

Четыре потока-воркера, каждый обрабатывает свою часть массива (5 элементов). На каждом **шаге** (всего 10 шагов) каждый воркер обновляет свои элементы по формуле: `newTemp[i] = (temp[i-1] + temp[i] + temp[i+1]) / 3`. После обновления — `barrier.await()`.

**Требования:**

1. `CyclicBarrier(4, barrierAction)`.
2. `BarrierAction` печатает текущее состояние массива (все 20 чисел) и максимальную температуру.
3. Воркеры обновляют **только свою часть**, но читают соседние элементы (в том числе из чужих частей — это нормально, данные не меняются между шагами).
4. После 10 шагов программа завершается.

**Ключевая тонкость:** воркеры должны читать **старое** состояние массива при обновлении, а писать — в **новый** массив. Иначе получится гонка: один воркер уже обновил, другой ещё читает старое. Используйте два массива и меняйте их местами после каждого шага (double buffering).

**Вопросы в комментарии:**

1. Почему `BarrierAction` безопасно читает массив, хотя воркеры писали в него параллельно?
2. Почему нужен double buffering — почему нельзя обновлять массив «на месте»?
3. Что произойдёт, если один воркер на пятом шаге бросит исключение? Как отреагируют остальные?

## Задача 3. Rate limiting для API

**Что комбинируется:** 3.3 (`Semaphore`), 1.7 (имена), 2.6 (атомарные классы).

Внешнее API выдерживает **не больше пяти** одновременных запросов. Больше — начинает отвечать ошибкой 429. Нужно написать клиент, который делает 50 запросов, но не превышает лимит.

**Требования:**

1. `Semaphore(5, true)` — справедливый, чтобы никто не голодал.
2. 50 потоков, каждый делает один «запрос» (спит 100–500 мс), потом освобождает разрешение.
3. Счётчик `AtomicInteger activeRequests` — увеличивается при входе, уменьшается при выходе.
4. Периодически (каждые 100 мс в отдельном демон-потоке) печатайте `active = N`, где N — текущее число активных запросов.
5. Убедитесь, что `active` **никогда** не превышает 5.

**Дополнительно:** добавьте `tryAcquire(2, TimeUnit.SECONDS)`. Если за 2 секунды разрешение не получено — поток печатает `[worker-N] timeout` и завершается без запроса. Запустите. Сколько потоков получили таймаут? Почему?

2. Что произойдёт, если один поток забудет `release()`?

## Задача 4. Конвейер с обменом

**Что комбинируется:** 3.4 (`Exchanger`), 1.6 (прерывание), 2.5 (happens-before).

Двухэтапный конвейер: поток `reader` читает данные, поток `writer` их записывает. Между ними — `Exchanger<StringBuilder>`.

**Требования:**

1. `reader` генерирует строки `line-1`, `line-2`, ..., `line-10` и складывает их в `StringBuilder`.
2. Когда буфер достигает 5 строк — `reader` обменивается буфером с `writer` через `Exchanger` и продолжает с пустым буфером.
3. `writer` получает буфер, «записывает» его (печатает содержимое), очищает и ждёт следующий.
4. После 10 строк `reader` прекращает генерацию и завершает работу. `writer` должен корректно завершиться — например, получив от `reader` специальный «сигнал» (пустой буфер или `null`).

**Дополнительно:** добавьте `exchange(buffer, 1, TimeUnit.SECONDS)` с таймаутом. Что произойдёт, если одна из сторон «зависнет»?

1. Почему `Exchanger` подходит здесь лучше, чем `BlockingQueue`?
2. Что произойдёт, если `writer` не очистит буфер после получения? Какие строки увидит в следующий раз?

## Задача 5. Динамические фазы

**Что комбинируется:** 3.4 (`Phaser`), 3.2 (`CyclicBarrier`), 2.7 (deadlock).

Задача «параллельная проверка гипотез». Начинают **пять** потоков-исследователей. На первой фазе каждый проверяет свою гипотезу. После первой фазы **два** потока «уходят» (гипотезы опровергнуты), остальные три продолжают на второй фазе. На третьей фазе к ним присоединяется **один новый** поток (новая гипотеза).

**Требования:**

1. `Phaser(5)` — стартуют пять.
2. Каждый поток проходит фазу 0 (проверка), печатает `[worker-N] фаза 0`.
3. Потоки 4 и 5 на переходе в фазу 1 вызывают `arriveAndDeregister()` — уходят.
4. Потоки 1, 2, 3 проходят фазу 1, печатают `[worker-N] фаза 1`.
5. Перед фазой 2 главный поток регистрирует нового участника через `register()` и запускает поток `worker-6`.
6. Все четыре (1, 2, 3, 6) проходят фазу 2.
7. Все завершаются через `arriveAndDeregister()`.

**Подсказка:** главный поток должен быть **зарегистрированным участником** фазера (`new Phaser(1)` + `register()` для остальных), чтобы контролировать переходы. Иначе он не сможет «подождать» нужную фазу.

**Вопросы в комментарии:**

1. Почему `CyclicBarrier` не подошёл бы для этой задачи?
2. Что произойдёт, если `register()` вызвать **после** того, как все остальные уже пришли к барьеру фазы 1?
3. Как убедиться, что `worker-6` присоединился именно к фазе 2, а не к фазе 3?

## Задача 7. Диагноз по симптому

**Что комбинируется:** всё.

Вам даны три программы. Каждая использует примитивы из модуля 3, но **неправильно**. Определите проблему и предложите исправление.

**Программа А (CountDownLatch):**

```java
CountDownLatch latch = new CountDownLatch(3);
for (int i = 0; i < 3; i++) {
    new Thread(() -> {
        try {
            doWork();
        } catch (Exception e) {
            // логируем
        }
        latch.countDown(); // не в finally
    }).start();
}
latch.await();
```

**Программа Б (Semaphore):**

```java
Semaphore sem = new Semaphore(3);
void process() {
    sem.acquire();
    // работа
    sem.release();
    sem.release(); // случайно дважды
}
```

**Программа В (Lock):**

```java
Lock lock = new ReentrantLock();
void doWork() {
    lock.lock();
    // работа
    lock.unlock();
    // ещё работа — но уже без блокировки
}
```

**Вопросы:**

1. Что произойдёт в программе А, если `doWork()` выбросит исключение?
2. Что произойдёт в программе Б после нескольких вызовов `process()`?
3. Что произойдёт в программе В, если «ещё работа» обращается к общим данным?
4. Как исправить каждую?

## Задача 8. Резюме в одном приложении

**Что комбинируется:** всё.

Напишите программу, которая демонстрирует **все** примитивы модуля 3 за один запуск.

**Сценарий:** система обработки заказов.

1. **`Phaser`** — три этапа обработки заказа: `validate`, `payment`, `ship`. На каждом этапе участвуют три потока-воркера.
2. **`CountDownLatch`** — при старте программы `order-service` ждёт, пока все три зависимости (`db`, `cache`, `queue`) инициализируются.
3. **`Semaphore`** — не больше двух одновременных обращений к «внешней платёжной системе».
4. **`CyclicBarrier`** — на каждом этапе все три воркера встречаются, чтобы собрать промежуточный результат.
5. **`Exchanger`** — два «аудитора» обмениваются найденными проблемами после каждого этапа.
6. **`ReentrantLock`** — защита общего счётчика обработанных заказов.

**Требования:**

- Программа проходит 5 заказов через все три этапа.
- На каждом этапе работают три воркера параллельно.
- Платёжная система вызывается не чаще двух раз одновременно.
- В конце — сводка: сколько заказов прошло, сколько ошибок, сколько раз вызывали платёжную систему.

**Что проверяется:** умение собрать **все** примитивы модуля в одной связной программе, не перепутав их назначение.

## 🎯 Проектное задание. Многопоточный веб-сканер

Это задание сложнее предыдущих. Оно не про конкретный примитив, а про **дизайн**: как собрать из примитивов координации реальную программу.

### Постановка

Напишите класс `WebScanner`, который «обходит» список сайтов и собирает статистику.

1. Принимает список URL-адресов (можно фейковых, вместо реального HTTP — `Thread.sleep`).
2. Параллельно обходит сайты, но **не больше N одновременно** (`Semaphore`).
3. Разбивает работу на **этапы**: сначала все скачивают главные страницы, потом все скачивают найденные ссылки, потом все агрегируют результаты (`Phaser` или `CyclicBarrier`).
4. Если один сайт «упал» — это не должно останавливать остальные. Счётчик ошибок — атомарный.
5. Сканер должен корректно завершаться по сигналу (например, по `interrupt` на главном потоке).

### Требования к дизайну

- `Semaphore(N)` для ограничения параллелизма.
- `Phaser` для синхронизации этапов (динамическое число участников: если сайт упал, он выходит из фазы).
- `AtomicInteger` для счётчиков (успешно, ошибок).
- `CountDownLatch` для «дождаться инициализации всех воркеров».
- Демон-поток `monitor`, который раз в 500 мс печатает прогресс.
- Корректное завершение: `monitor` — по `interrupt`, воркеры — по сигналу от `Semaphore`/`Phaser`.

### Тесты для проверки

1. 20 URL, `N = 5`.
2. Три этапа: главные страницы, ссылки, агрегация.
3. С вероятностью 20% сайт «падает» на первом этапе — он выходит из дальнейших фаз.
4. Все потоки завершаются, программа не висит.
5. Сводка корректна: `success + failed == total`.

### Задание со звёздочкой

1. Что произойдёт, если `N = 20` (равно числу URL)? `N = 1`?
2. Как бы вы изменили дизайн, если бы этапов было 10, а не 3?
3. Как бы вы реализовали «отмену» сканера из другого потока (например, по нажатию кнопки)?
4. Что произойдёт с `Phaser`, если один воркер упадёт с `RuntimeException`? Как это исправить?

# 3.3. Semaphore

## Где вы это уже видели

**Парковка с ограниченным числом мест.** Пятьдесят мест. Пятьдесят машин заехали — ворота закрываются, следующая ждёт. Кто-то выехал — место освободилось, ворота открываются, ждущая машина заезжает. Парковка не «ждёт всех», не «собирает группу» — она просто **пропускает не больше пятидесяти** и держит очередь на въезд.

**Бассейн с дорожками.** Восемь дорожек. Восемь пловцов плавают одновременно. Девятый ждёт на бортике. Кто-то вышел — девятый заходит. Никакой синхронизации «все встретились», просто **лимит на одновременное присутствие**.

**Гостиница.** Двести номеров. Двести гостей заселились — новых не селят, пока кто-то не выедет. При этом гости не знают друг друга, не собираются вместе, не синхронизируются. Они просто **занимают ресурс** и **освобождают его**.

**Библиотека.** На полке три экземпляра одной книги. Три читателя взяли — четвёртому говорят: «ждите, пока вернут». Никто не ждёт «всех читателей», никто не собирается в группу. Просто есть **три разрешения**, и они выдаются по одному.

**Общее во всех случаях** одно: есть ресурс, который **не может использоваться больше чем N участниками одновременно**. Не «все вместе», не «по очереди», а именно **не больше N**. Это и есть `Semaphore` — «семафор», то есть буквально «ограничитель».

## Теория

### Что такое Semaphore

`Semaphore` — примитив синхронизации из `java.util.concurrent`. Он работает как **счётчик разрешений**.

- Создаётся с числом разрешений `N`.
- Поток, который хочет получить доступ, вызывает `acquire()` — забирает одно разрешение. Если разрешений нет — **блокируется**, пока кто-то не вернёт.
- Когда поток закончил работу, он вызывает `release()` — возвращает разрешение. Ожидающий поток (если есть) забирает его и продолжает.

Разрешений всего `N`. Значит, одновременно работать могут не больше `N` потоков. Остальные стоят в очереди на `acquire()`.

### Простая схема

```java
import java.util.concurrent.Semaphore;

public class Main {
    public static void main(String[] args) {
        Semaphore semaphore = new Semaphore(3);

        for (int i = 1; i <= 10; i++) {
            int id = i;
            new Thread(() -> {
                try {
                    semaphore.acquire();
                    System.out.println("worker-" + id + " вошёл");
                    Thread.sleep(1000);
                    System.out.println("worker-" + id + " выходит");
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                } finally {
                    semaphore.release();
                }
            }, "worker-" + id).start();
        }
    }
}
```

**Возможный вывод:**

```text
worker-1 вошёл
worker-2 вошёл
worker-3 вошёл
worker-1 выходит
worker-4 вошёл
worker-2 выходит
worker-5 вошёл
...
```

Обратите внимание: **в любой момент времени «внутри» не больше трёх потоков**. Четвёртый ждёт, пока кто-то из первых трёх не выйдет. Это и есть семафор: разрешений три, значит, и «внутри» не больше трёх.

### Ключевая идея: разрешения, а не «все или никто»

`CountDownLatch` и `CyclicBarrier` — про **синхронизацию**: дождаться события, дождаться группы. `Semaphore` — про **ограничение**: пропустить не больше N.

Это разные задачи, и путать их не стоит.

| | CountDownLatch / CyclicBarrier | Semaphore |
|---|---|---|
| Что делает | Ждёт события / группы | Ограничивает число одновременных |
| Участники | Знают друг о друге | Могут не знать |
| Освобождение | `countDown()` / автоматическое | Явный `release()` |
| Основное применение | Координация этапов | Пул ресурсов, throttling |

Потоки, работающие с `Semaphore`, обычно **не знают друг о друге**. Они не «собираются», не «ждут всех». Они просто пытаются войти, и семафор решает, можно ли.

### Semaphore(1) — это мьютекс

Если создать `Semaphore(1)`, то одновременно работать может только один поток. Это по сути **мьютекс** — то же, что `synchronized`, но с явным `acquire()`/`release()`.

```java
Semaphore mutex = new Semaphore(1);

mutex.acquire();
try {
    // критическая секция
} finally {
    mutex.release();
}
```

Зачем это, если есть `synchronized`? Три причины.

**Первая: `tryAcquire()` с таймаутом.** У `synchronized` нет способа «попробовать захватить и не ждать вечно». У `Semaphore` есть.

**Вторая: справедливость.** `synchronized` не гарантирует, что лок получит тот, кто дольше ждёт. `Semaphore` с `fair=true` — гарантирует.

**Третья: `release()` можно вызвать из другого потока.** С `synchronized` монитор захватывает и отпускает один и тот же поток. С `Semaphore` — любой поток может вернуть разрешение. Это иногда нужно (например, при передаче задачи между потоками).

`Semaphore(1)` — это, по сути, «продвинутый `synchronized`» с дополнительными возможностями. Подробнее о `Lock` (ещё более гибком варианте) — в главе 3.5.

### tryAcquire: не ждать вечно

`acquire()` блокируется, пока не получит разрешение. Но иногда лучше не ждать, а попробовать и, если не вышло, — заняться чем-то другим.

**`tryAcquire()`** — пытается захватить разрешение **сразу**. Если получилось — `true`, если нет — `false`. Не блокируется.

```java
if (semaphore.tryAcquire()) {
    try {
        // работаем
    } finally {
        semaphore.release();
    }
} else {
    // разрешений нет, делаем что-то другое
}
```

**`tryAcquire(timeout, unit)`** — пытается захватить **не дольше** указанного времени. Если получилось — `true`, если таймаут — `false`.

```java
if (semaphore.tryAcquire(500, TimeUnit.MILLISECONDS)) {
    try {
        // работаем
    } finally {
        semaphore.release();
    }
} else {
    // не дождались за 500 мс — идём другой дорогой
}
```

Это спасает от зависания, если разрешение так и не вернут (из-за бага в чужом коде, например). В продакшене `tryAcquire` с таймаутом — почти всегда предпочтительнее, чем `acquire()` без таймаута.

### Справедливость: fair vs non-fair

`Semaphore` может быть **справедливым** и **несправедливым**. По умолчанию — несправедливый.

```java
Semaphore unfair = new Semaphore(3);           // по умолчанию
Semaphore fair = new Semaphore(3, true);       // fair mode
```

**Несправедливый (по умолчанию).** Когда разрешение освобождается, его забирает **любой** поток, который в этот момент пытается `acquire()`. Необязательно тот, кто дольше ждёт. Может быть, поток, который только что подошёл.

**Справедливый.** Когда разрешение освобождается, его получает **тот, кто дольше всех ждёт** (FIFO). Это гарантирует отсутствие starvation.

Что выбрать? Как всегда, зависит от задачи.

- **Несправедливый** — быстрее. Потоки не встают в очередь, а «конкурируют» за разрешение. В высоконагруженных системах это даёт лучшую пропускную способность.
- **Справедливый** — предсказуемее. Гарантирует, что никто не будет голодать. Но медленнее из-за управления очередью.

По умолчанию — несправедливый. Если у вас есть подозрение на starvation — переключитесь на справедливый и посмотрите, не улучшится ли ситуация.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> если используете <code>Semaphore</code> для защиты общего ресурса — почти всегда берите <code>fair=true</code>. Если для throttling (ограничения скорости) — можно оставить несправедливым, он быстрее.
</div>

### acquire(n) и release(n): несколько разрешений сразу

`Semaphore` позволяет захватывать и возвращать **несколько** разрешений за раз.

```java
Semaphore semaphore = new Semaphore(10);

semaphore.acquire(3);    // забрать три разрешения
try {
    // работаем
} finally {
    semaphore.release(3); // вернуть три разрешения
}
```

Если разрешений меньше, чем запрошено, — поток ждёт, пока их не станет достаточно. Это атомарная операция: либо забирает все три сразу, либо ни одного.

Зачем это? Для случаев, когда задача требует больше одного «слота». Например, тяжёлая задача, которая занимает три из десяти потоков пула. Или задача, которой нужно два соединения к базе одновременно.

### Частые ошибки

**Ошибка 1: забыть `release()`.** Если поток взял разрешение и не вернул — разрешение потеряно навсегда. Через какое-то время разрешений не останется, и все остальные потоки зависнут в `acquire()`. **Всегда** `release()` в `finally`.

```java
semaphore.acquire();
try {
    // работа
} finally {
    semaphore.release(); // даже при исключении
}
```

**Ошибка 2: `release()` больше, чем `acquire()`.** `Semaphore` не отслеживает, кто сколько взял. Если вы вызвали `release()` без `acquire()`, разрешений станет больше, чем изначально. Это ломает инвариант «не больше N одновременно». Внимательно следите за парностью.

**Ошибка 3: `release()` без `try/finally`.** Если между `acquire()` и `release()` что-то упадёт — разрешение не вернётся. `try/finally` обязателен.

**Ошибка 4: использовать `Semaphore` для защиты данных.** `Semaphore` — это **счётчик разрешений**, а не защита от гонок. Если поток вошёл в «разрешённую зону» — это не значит, что данные защищены от других потоков, которые тоже вошли (если разрешений больше одного). Для защиты данных нужен `synchronized` или `Lock`.

**Ошибка 5: путать `acquire`/`release` с `wait`/`notify`.** Это разные механизмы. `wait`/`notify` — про координацию по условию. `acquire`/`release` — про ограничение числа.

### Где Semaphore реально нужен

Три классических применения.

**Пул ресурсов.** Ограниченное число соединений к базе данных, потоков в пуле, файловых дескрипторов. `Semaphore(N)` гарантирует: не больше N одновременно.

```java
Semaphore connectionPool = new Semaphore(10);

Connection getConnection() throws InterruptedException {
    connectionPool.acquire();
    return createConnection();
}

void releaseConnection(Connection conn) {
    conn.close();
    connectionPool.release();
}
```

**Throttling (ограничение скорости).** Не больше N запросов к внешнему API в секунду. `Semaphore(N)` ограничивает параллелизм, а внешний таймер возвращает разрешения.

**Ограничение параллельных загрузок.** Пользователь нажал «скачать всё» — сто файлов. Но качать сто одновременно — плохо: канал забьётся, сервер ответит ошибкой. `Semaphore(5)` ограничивает пять одновременных загрузок, остальные ждут.

### Semaphore vs ThreadPoolExecutor

Может возникнуть вопрос: «А зачем `Semaphore`, если есть пул потоков с фиксированным размером?»

Ответ: это разные инструменты.

**`ThreadPoolExecutor`** ограничивает **число потоков**. Но задачи могут выполняться в пуле, а ресурс — вне пула. Например, у вас пул из 100 потоков, но база данных выдерживает только 10 соединений. Пул не спасёт — нужно ограничить доступ к базе через `Semaphore(10)`.

**`Semaphore`** ограничивает **доступ к ресурсу**, независимо от того, сколько потоков его пытаются получить.

Обычно их используют **вместе**: пул потоков для управления потоками, `Semaphore` для управления доступом к конкретному ресурсу. Подробнее о пулах — в модуле 4.

### Аналогия с парковкой

Вернёмся к началу. `Semaphore` — это **парковка с ограниченным числом мест**. Пятьдесят мест — пятьдесят разрешений. Машина заезжает — забирает разрешение (`acquire`). Выезжает — возвращает (`release`). Пятидесятая машина заняла последнее место — следующая ждёт у ворот.

`CountDownLatch` — это если бы все пятьдесят машин **договорились встретиться** на парковке и ждали, пока приедут все. Разные задачи: одна про «сколько машин одновременно», другая про «когда все собрались».

`CyclicBarrier` — это если бы пятьдесят машин **собрались и поехали колонной**, потом снова собрались на следующей стоянке. Тоже не про лимит, а про синхронизацию.

`Semaphore` — именно про **лимит**. Про «не больше пятидесяти». Про «кто-то выехал — следующий заехал».

## Микрозадача 1: мьютекс через Semaphore(1)

**Задача:** Создайте `Semaphore(1)` и два потока, каждый увеличивает общий счётчик тысячу раз. Защитите счётчик через `acquire`/`release`. Убедитесь, что результат всегда 2000.

**Решение:**

```java
import java.util.concurrent.Semaphore;

public class Main {
    private static int counter = 0;
    private static final Semaphore mutex = new Semaphore(1);

    public static void main(String[] args) throws InterruptedException {
        Thread t1 = new Thread(Main::incrementMany);
        Thread t2 = new Thread(Main::incrementMany);
        t1.start(); t2.start();
        t1.join(); t2.join();
        System.out.println("Получили: " + counter);
    }

    private static void incrementMany() {
        for (int i = 0; i < 1000; i++) {
            try {
                mutex.acquire();
                try {
                    counter++;
                } finally {
                    mutex.release();
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
        }
    }
}
```

**Вывод** (всегда):

```text
Получили: 2000
```

**Разбор:** `Semaphore(1)` — это мьютекс. Пока один поток внутри `counter++`, второй ждёт на `acquire()`. `try/finally` гарантирует, что `release()` выполнится даже при исключении. Обратите внимание на вложенность: `try` вокруг `acquire` (для обработки `InterruptedException`) и `try/finally` вокруг `counter++` (для гарантированного `release`). Это каноническая структура, которую стоит запомнить.

## Микрозадача 2: ограничение параллелизма

**Задача:** Создайте `Semaphore(3)` и десять потоков. Каждый печатает «вошёл», спит секунду, печатает «вышел». Убедитесь, что одновременно «внутри» не больше трёх потоков.

**Решение:**

```java
import java.util.concurrent.Semaphore;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    private static final Semaphore semaphore = new Semaphore(3);
    private static final AtomicInteger inside = new AtomicInteger(0);
    private static final AtomicInteger maxInside = new AtomicInteger(0);

    public static void main(String[] args) throws InterruptedException {
        Thread[] threads = new Thread[10];
        for (int i = 0; i < 10; i++) {
            int id = i + 1;
            threads[i] = new Thread(() -> {
                try {
                    semaphore.acquire();
                    try {
                        int current = inside.incrementAndGet();
                        maxInside.updateAndGet(m -> Math.max(m, current));
                        System.out.println("worker-" + id + " вошёл (внутри: " + current + ")");
                        Thread.sleep(1000);
                        inside.decrementAndGet();
                        System.out.println("worker-" + id + " выходит");
                    } finally {
                        semaphore.release();
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }, "worker-" + id);
            threads[i].start();
        }

        for (Thread t : threads) t.join();
        System.out.println("Максимум одновременно внутри: " + maxInside.get());
    }
}
```

**Возможный вывод:**

```text
worker-1 вошёл (внутри: 1)
worker-2 вошёл (внутри: 2)
worker-3 вошёл (внутри: 3)
worker-1 выходит
worker-4 вошёл (внутри: 3)
...
Максимум одновременно внутри: 3
```

**Разбор:** `Semaphore(3)` гарантирует, что внутри не больше трёх потоков. Остальные семь ждут на `acquire()`. Как только один выходит и вызывает `release()`, один из ждущих заходит. `maxInside` фиксирует максимум — он всегда будет 3. Если бы разрешений было 5 — было бы 5. Если бы 1 — было бы 1 (мьютекс).

## 📌 Что дальше

В следующей главе — **«Exchanger и Phaser»**. `Exchanger` — простой примитив для обмена данными между **двумя** потоками: один кладёт, другой забирает, встреча происходит в одной точке. `Phaser` — более гибкий вариант `CyclicBarrier`, который позволяет динамически добавлять и убирать участников и работать с несколькими фазами. А то ведь до сих пор у нас были только «все или никто» и «не больше N». Пора поговорить о том, как **обмениваться** и как строить **многофазные** алгоритмы.

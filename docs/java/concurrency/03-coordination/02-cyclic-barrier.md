# 3.2. CyclicBarrier

## Где вы это уже видели

**Утренняя планёрка.** Команда из шести человек. Кто-то пришёл раньше, кто-то задержался с кофе. Начинать без всех — бессмысленно: половина не в курсе. Когда приходит шестой — руководитель говорит: «Ну что, все в сборе, начинаем». А через день — та же история, та же шестёрка, та же планёрка.

**Многопользовательская игра.** Четыре игрока в лобби. Один уже нажал «Готов», второй выбирает персонажа, третий — загружается, четвёртый — отвлёкся. Раунд начинается только когда **все четверо** нажали «Готов». Раунд проходит, все снова в лобби, снова ждут друг друга — и следующий раунд начинается по тому же правилу.

**Групповая экскурсия.** Гид ведёт группу по городу. У каждой остановки он собирает всех, считает по головам: «Раз, два, три... все на месте? Идём к следующей». Не уходит, пока последний не догнал. А у следующей остановки — та же процедура.

**Уборка по субботам.** Четверо соседей по квартире договорились: каждую субботу в 10:00 все собираются на кухне, делят, кто что моет, и расходятся. Через неделю — снова все на кухне. Это не разовое мероприятие, это **цикл**.

**Общее во всех случаях** одно: есть **фиксированная группа** участников, и есть **точка сбора**. Пока не пришли все — никто не идёт дальше. Когда пришли все — все вместе идут дальше. И так **снова и снова**, сколько нужно раз. Это и есть `CyclicBarrier` — «циклический барьер».

## Теория

### Что такое CyclicBarrier

`CyclicBarrier` — примитив синхронизации из `java.util.concurrent`. Он устроен так.

- Создаётся с фиксированным числом участников `N`.
- Каждый поток, дойдя до точки сбора, вызывает `await()` и **блокируется**.
- Когда **все N** потоков вызвали `await()`, барьер «открывается»: **все просыпаются одновременно** и продолжают работу.
- Барьер **сбрасывается** и готов к следующему циклу. Отсюда и слово «cyclic» — циклический.

В отличие от `CountDownLatch`, который «дошёл до нуля и умер», `CyclicBarrier` живёт до тех пор, пока вы его не выбросите. Каждый цикл — это новый «раунд» синхронизации.

### Простая схема

```java
import java.util.concurrent.CyclicBarrier;

public class Main {
    public static void main(String[] args) {
        int N = 3;
        CyclicBarrier barrier = new CyclicBarrier(N);

        for (int i = 1; i <= N; i++) {
            int id = i;
            new Thread(() -> {
                try {
                    System.out.println("Участник " + id + " подошёл к барьеру");
                    barrier.await();
                    System.out.println("Участник " + id + " пошёл дальше");
                } catch (Exception e) {
                    Thread.currentThread().interrupt();
                }
            }, "worker-" + id).start();
        }
    }
}
```

**Возможный вывод:**

```text
Участник 1 подошёл к барьеру
Участник 2 подошёл к барьеру
Участник 3 подошёл к барьеру
Участник 1 пошёл дальше
Участник 2 пошёл дальше
Участник 3 пошёл дальше
```

Все три подошли, никто не пошёл дальше, пока не подошли все. Потом все трое продолжили почти одновременно.

### Отличие от CountDownLatch

Это главное, что нужно понять в этой главе. Два примитива выглядят похоже, но решают разные задачи.

`CountDownLatch` — это «**один (или несколько) ждёт N событий**». Есть те, кто ждёт, и есть те, кто сигнализирует. Сигнализирующие после `countDown()` продолжают свою работу — они не «ждут всех». А те, кто ждёт, дожидаются и идут дальше. Одноразовый.

`CyclicBarrier` — это «**все ждут всех**». Нет отдельной группы «ждущих» и «сигнализирующих». Все участники равны: каждый доходит до барьера, каждый ждёт остальных, все вместе идут дальше. Переиспользуемый.

| | CountDownLatch | CyclicBarrier |
|---|---|---|
| Кто кого ждёт | Один ждёт N событий | Все ждут всех |
| После срабатывания | Один идёт дальше, N уже ушли | Все идут дальше вместе |
| Переиспользование | Нет (одноразовый) | Да (циклический) |
| Роли | Ждущий и сигнализирующие | Все равны |
| Основной метод | `countDown()` + `await()` | `await()` у всех |

Если помните главу 3.1 — там был пример «стартовый пистолет»: N потоков ждут одного сигнала от главного. Это `CountDownLatch`. А если бы **все N** ждали, пока **все N** соберутся, и потом шли дальше — это был бы `CyclicBarrier`. Разница тонкая, но существенная: в latch роли разные, в barrier — все равны.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> если у вас есть «тот, кто ждёт» и «те, кто сигнализирует», — это <code>CountDownLatch</code>. Если у вас есть группа равных участников, которые должны встретиться, — это <code>CyclicBarrier</code>.
</div>

### BarrierAction: действие при сборе

У `CyclicBarrier` есть дополнительная возможность, которой нет у `CountDownLatch`: **действие, выполняемое при сборе**. Это `Runnable`, который выполняется **один раз**, когда все N потоков дошли до барьера, но **до** того, как они продолжат.

```java
CyclicBarrier barrier = new CyclicBarrier(N, () -> {
    System.out.println("Все собрались! Выполняю действие");
});
```

Когда последний поток вызывает `await()`, происходит следующее:

1. Барьер срабатывает.
2. **Один** поток (тот, который пришёл последним) выполняет `BarrierAction`.
3. После завершения `BarrierAction` все N потоков просыпаются и идут дальше.

Зачем это нужно? Для действий, которые имеют смысл только «когда все собрались»: агрегировать результаты раунда, обновить общее состояние, напечатать отчёт, обнулить счётчики. Без `BarrierAction` пришлось бы делать это в одном из потоков с проверкой «я последний?» — а это дополнительная синхронизация. `BarrierAction` делает это за вас.

Пример: каждый поток за раунд накопил какое-то число, и в конце раунда нужно посчитать сумму.

```java
int[] results = new int[N];
CyclicBarrier barrier = new CyclicBarrier(N, () -> {
    int sum = 0;
    for (int r : results) sum += r;
    System.out.println("Сумма за раунд: " + sum);
    // обнулить результаты для следующего раунда
    for (int i = 0; i < results.length; i++) results[i] = 0;
});
```

`BarrierAction` выполняется в потоке, который **последним** пришёл к барьеру. Гарантий, что это всегда один и тот же поток, нет — кто последний, тот и выполняет. Это важно помнить: не полагайтесь на то, что `BarrierAction` всегда выполняется в конкретном потоке.

### Переиспользование: циклы

Главное отличие `CyclicBarrier` от `CountDownLatch` — он сбрасывается и готов к следующему циклу. Это позволяет строить многораундовые алгоритмы: клеточные автоматы, итерационные вычисления, пошаговые симуляции.

```java
int rounds = 5;
CyclicBarrier barrier = new CyclicBarrier(N);

for (int i = 0; i < N; i++) {
    new Thread(() -> {
        for (int round = 1; round <= rounds; round++) {
            // вычисления в текущем раунде
            doWork(round);
            // ждём всех, потом следующий раунд
            barrier.await();
        }
    }).start();
}
```

Каждый поток делает свой кусок работы в раунде, потом ждёт остальных. Все вместе переходят к следующему раунду. И так пять раз. `CyclicBarrier` «сбрасывается» автоматически после каждого срабатывания.

### BrokenBarrierException: когда барьер ломается

У `CyclicBarrier` есть особенность, которой нет у `CountDownLatch`: барьер может **сломаться**. Если это произошло, все потоки, ожидающие на барьере, получают `BrokenBarrierException`.

Когда это случается:

1. **Поток был прерван, пока ждал на барьере.** Если кто-то вызвал `interrupt()` на ждущем потоке — барьер считается сломанным, все остальные получают исключение.
2. **Поток упал с исключением, пока ждал.** Если `await()` бросил исключение — барьер ломается.
3. **Кто-то вызвал `reset()`.** `reset()` принудительно сбрасывает барьер, все ждущие получают `BrokenBarrierException`.
4. **BarrierAction упал с исключением.** Если `BarrierAction` бросил исключение — барьер ломается, все ждущие получают `BrokenBarrierException`.

Почему так? Потому что `CyclicBarrier` — это **все или никто**. Если один участник выбыл, «все собрались» уже не наступит никогда. Ждать дальше бессмысленно. Поэтому барьер ломается, и все получают исключение — чтобы программа не зависла.

Это разумное поведение, но о нём нужно помнить. Если вы ловите `BrokenBarrierException` — значит, кто-то из участников выбыл. Обычно это означает, что нужно либо перезапустить цикл (`reset()`), либо завершить работу.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> <code>BrokenBarrierException</code> — это не «ошибка в коде», а <em>сигнал</em>, что барьер больше не может сработать. Программа должна его обработать: либо сбросить барьер и начать заново, либо корректно завершиться. Молча игнорировать его нельзя.
</div>

### Методы

**`CyclicBarrier(int parties)`** — конструктор, задаёт число участников.

**`CyclicBarrier(int parties, Runnable barrierAction)`** — конструктор с действием при сборе.

**`int await()`** — блокироваться, пока все не соберутся. Возвращает **номер прибытия**: 0 для первого пришедшего, `parties - 1` для последнего. Иногда используется для выбора «главного» потока в раунде.

**`int await(long timeout, TimeUnit unit)`** — то же, но не дольше указанного времени. Если таймаут истёк — барьер ломается, все получают `BrokenBarrierException`, а текущий поток получает `TimeoutException`.

**`int getParties()`** — сколько всего участников.

**`int getNumberWaiting()`** — сколько сейчас ждут.

**`boolean isBroken()`** — сломан ли барьер.

**`void reset()`** — сбросить барьер. Все ждущие получают `BrokenBarrierException`, барьер готов к новому циклу.

### Частые ошибки

**Ошибка 1: неправильное число участников.** Если `CyclicBarrier(3)`, а потоков, которые вызывают `await()`, только два — барьер никогда не сработает. Все будут ждать вечно (или получат `BrokenBarrierException` при таймауте).

**Ошибка 2: не обрабатывать `BrokenBarrierException`.** Если один поток выбыл, все остальные получают это исключение. Если его не обработать — программа упадёт или зависнет.

**Ошибка 3: `BarrierAction` выполняется в неизвестном потоке.** Не полагайтесь на то, что это всегда «главный» поток. Это тот, кто пришёл последним.

**Ошибка 4: использовать `CyclicBarrier` для защиты данных.** Как и `CountDownLatch`, он **не защищает** от гонок. Только координирует.

**Ошибка 5: переиспользовать после `BrokenBarrierException` без `reset()`.** После поломки барьер остаётся сломанным. Чтобы использовать его снова, нужно явно вызвать `reset()`.

### CyclicBarrier vs Phaser

`Phaser` (глава 3.4) — более гибкий вариант `CyclicBarrier`. Он позволяет:

- Динамически добавлять и убирать участников.
- Несколько фаз с разным числом участников.
- Наследование фаз.

`CyclicBarrier` проще, и для фиксированной группы участников его достаточно. `Phaser` нужен, когда число участников меняется или когда фаз много и они разные. Если не уверены, что нужно, — начните с `CyclicBarrier`.

### Аналогия с планёркой

Вернёмся к началу. `CyclicBarrier` — это **планёрка**. Шесть человек, фиксированный состав. Каждый приходит и «отмечается» (`await`). Пока не пришли все — никто не начинает. Когда пришёл шестой — руководитель (это `BarrierAction`, если хотите) говорит «начинаем», и все переходят к обсуждению. Через день — снова планёрка, снова все шестеро, снова барьер.

`CountDownLatch` — это если бы вы ждали **одного** опаздывающего: «пока Петров не придёт — не начинаем». Петров пришёл, все начали. Но Петров — это не «все», это **один человек**, которого ждут. Разница в том, что в `CountDownLatch` есть «тот, кого ждут», а в `CyclicBarrier` — все ждут всех.

## Микрозадача 1: три раунда

**Задача:** Создайте `CyclicBarrier(3)` и три потока. Каждый поток в цикле из трёх раундов: печатает `[имя] раунд N`, спит 100 мс, вызывает `barrier.await()`. Убедитесь, что раунды синхронизированы: все три потока проходят раунд 1, потом все три — раунд 2, и так далее.

**Решение:**

```java
import java.util.concurrent.CyclicBarrier;

public class Main {
    public static void main(String[] args) {
        int N = 3;
        int rounds = 3;
        CyclicBarrier barrier = new CyclicBarrier(N);

        for (int i = 1; i <= N; i++) {
            int id = i;
            new Thread(() -> {
                try {
                    for (int round = 1; round <= rounds; round++) {
                        System.out.println("[worker-" + id + "] раунд " + round);
                        Thread.sleep(100);
                        barrier.await();
                    }
                } catch (Exception e) {
                    Thread.currentThread().interrupt();
                }
            }, "worker-" + id).start();
        }
    }
}
```

**Возможный вывод:**

```text
[worker-1] раунд 1
[worker-2] раунд 1
[worker-3] раунд 1
[worker-1] раунд 2
[worker-2] раунд 2
[worker-3] раунд 2
[worker-1] раунд 3
[worker-2] раунд 3
[worker-3] раунд 3
```

**Разбор:** обратите внимание — раунды идут строго по порядку. Все три потока проходят раунд 1, потом все три — раунд 2, потом раунд 3. Не может быть «worker-1 уже в раунде 2, а worker-2 ещё в раунде 1». Барьер синхронизирует их на каждой итерации. Это и есть цикличность: один и тот же барьер используется три раза.

## Микрозадача 2: BarrierAction для агрегации

**Задача:** Четыре потока, каждый за раунд накапливает случайное число. В конце каждого раунда `BarrierAction` печатает сумму и обнуляет результаты. Три раунда.

**Решение:**

```java
import java.util.concurrent.CyclicBarrier;

public class Main {
    private static final int N = 4;
    private static final int[] results = new int[N];

    public static void main(String[] args) {
        CyclicBarrier barrier = new CyclicBarrier(N, () -> {
            int sum = 0;
            for (int r : results) sum += r;
            System.out.println("Сумма за раунд: " + sum);
            for (int i = 0; i < N; i++) results[i] = 0;
        });

        for (int i = 0; i < N; i++) {
            int id = i;
            new Thread(() -> {
                try {
                    for (int round = 1; round <= 3; round++) {
                        results[id] = (int) (Math.random() * 100);
                        barrier.await();
                    }
                } catch (Exception e) {
                    Thread.currentThread().interrupt();
                }
            }, "worker-" + id).start();
        }
    }
}
```

**Возможный вывод:**

```text
Сумма за раунд: 213
Сумма за раунд: 187
Сумма за раунд: 234
```

**Разбор:** каждый поток записывает своё число в `results[id]` (по индексу — без гонки), потом ждёт на барьере. Когда все четверо дошли — `BarrierAction` (выполняется в потоке, который пришёл последним) считает сумму, печатает и обнуляет массив для следующего раунда. Потом все четверо переходят к следующему раунду. Барьер автоматически сбросился и готов к следующей итерации.

## 🎯 Самостоятельная задача

Реализуйте **параллельную обработку изображения** (симуляцию) через `CyclicBarrier`.

**Постановка:**

1. Есть массив из 16 «пикселей», каждый — целое число. Начальное значение — 0.
2. Четыре потока-воркера, каждый отвечает за свою четверть массива (индексы `0..3`, `4..7`, `8..11`, `12..15`).
3. На каждом **шаге симуляции** (всего 10 шагов) каждый воркер обновляет свои пиксели: например, прибавляет к каждому `шаг * id`.
4. После обновления все воркеры ждут на барьере.
5. `BarrierAction` после каждого шага печатает текущее состояние массива (все 16 значений) и сумму.
6. После 10 шагов программа завершается, выводит финальную сумму.

**Требования:**

- `CyclicBarrier(4, barrierAction)` — четыре участника и действие при сборе.
- `BarrierAction` должен обходить весь массив и печатать его. Это нормально, что он читает данные, которые писали другие потоки — между `await()` и `BarrierAction` действует happens-before.
- Каждый воркер обновляет только свою четверть — гонки нет.
- Обработайте `BrokenBarrierException` — выведите сообщение и завершите поток.

**Дополнительно:** добавьте в один из воркеров на пятом шаге искусственное исключение (`throw new RuntimeException`). Посмотрите, что произойдёт с остальными потоками. Убедитесь, что они получают `BrokenBarrierException` и программа не зависает.

1. Почему `BarrierAction` может безопасно читать весь массив, хотя потоки писали в него параллельно?
2. Почему после исключения в одном воркере остальные получают `BrokenBarrierException`, а не ждут вечно?
3. В чём преимущество `BarrierAction` перед ручной проверкой «я последний?» в каждом воркере?
4. Почему для этой задачи не подошёл бы `CountDownLatch`?

## 📌 Что дальше

В следующей главе — **«Semaphore»**. Это примитив для **ограничения количества одновременных доступов** к ресурсу. `CountDownLatch` и `CyclicBarrier` — про «дождаться всех», а `Semaphore` — про «пустить не больше N». А то ведь до сих пор мы только и делали, что ждали. Пора научиться **ограничивать**.

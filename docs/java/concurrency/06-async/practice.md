## Задача 1. Future vs CompletableFuture

**Что комбинируется:** 6.1 (`Future`), 6.2 (`CompletableFuture`), 4.2 (`ExecutorService`).

Реализуйте одну и ту же задачу **двумя способами** и сравните.

**Постановка:** три «источника данных», каждый возвращает число. Нужно получить все три, сложить, вернуть сумму.

- `sourceA()` — спит 300 мс, возвращает 10.
- `sourceB()` — спит 500 мс, возвращает 20.
- `sourceC()` — спит 200 мс, возвращает 30.

**Версия A: `Future`.**

1. `ExecutorService` на 3 потока.
2. Три `submit`, три `Future<Integer>`.
3. Замер: `get()` на каждом по очереди.
4. Сумма.

**Версия B: `CompletableFuture`.**

1. Три `supplyAsync`, три `CompletableFuture<Integer>`.
2. `CompletableFuture.allOf` + `thenCombine` или `thenApply`.
3. `get()` в конце.
4. Сумма.

**Замеры:**

- Общее время каждой версии.
- Количество блокировок `get()`.

**Вопросы в комментарии:**

1. Почему версия B **не быстрее** версии A, если все источники параллельны в обеих?
2. В чём разница в **коде**, если бы источников было не три, а десять?
3. В чём разница, если бы нужны были **не все**, а «первый успешный»?

## Задача 2. Найди три ошибки

**Что комбинируется:** 6.2, 6.3, 6.4.

Вам дан код. В нём **три ошибки**, из-за которых программа либо падает, либо теряет данные, либо «залипает». Найдите их, объясните и исправьте.

```java
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.CompletableFuture;
import java.util.stream.Collectors;
import java.util.stream.IntStream;

public class Main {
    public static void main(String[] args) throws Exception {
        List<Integer> numbers = IntStream.rangeClosed(1, 100_000)
            .boxed()
            .collect(Collectors.toList());

        List<Integer> result = new ArrayList<>();
        numbers.parallelStream()
            .map(x -> x * 2)
            .forEach(result::add);
        System.out.println("Размер: " + result.size());

        CompletableFuture<String> future = CompletableFuture
            .supplyAsync(() -> {
                throw new RuntimeException("сбой");
            })
            .thenApply(s -> s + "!")
            .exceptionally(ex -> ex.getMessage());

        System.out.println("Future результат: " + future.get());

        CompletableFuture<String> timeout = CompletableFuture
            .supplyAsync(() -> {
                try { Thread.sleep(10000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                return "готово";
            })
            .completeOnTimeout("fallback", 1, java.util.concurrent.TimeUnit.SECONDS);

        System.out.println("Timeout результат: " + timeout.get());
    }
}
```

**Подсказки:**

- Ошибка 1 — `ArrayList` + `parallelStream().forEach` — гонка (глава 5.1, 6.4).
- Ошибка 2 — `exceptionally` после `thenApply` получает **обёрнутое** исключение, но `ex.getMessage()` может вернуть `null` или не то, что ожидали. А ещё — цепочка **восстановлена**, но тип `String` — и это нормально. Ошибка не в этом. Ошибка в том, что `.thenApply(s -> s + "!")` **не выполнится**, потому что `supplyAsync` упал. А `exceptionally` — выполнится. Вопрос: почему `get()` возвращает «сбой» (или что-то другое)? Проверьте, что на самом деле возвращает `ex.getMessage()` — это `CompletionException`, у него нет сообщения.
- Ошибка 3 — `completeOnTimeout` не **отменяет** задачу (глава 6.3). Задача продолжает работать 10 секунд, программа ждёт её завершения. `get()` вернёт «fallback» через 1 секунду, но программа завершится только через 10.

## Задача 3. Цепочка с обработкой ошибок

**Что комбинируется:** 6.2 (`thenCompose`), 6.3 (`exceptionally`, `handle`, `orTimeout`).

Реализуйте **асинхронную загрузку профиля пользователя** с обработкой ошибок.

**Постановка:**

1. `loadUser(id)` — `CompletableFuture<User>`. Спит 200 мс. 20% шанс упасть с `RuntimeException("user not found")`.
2. `loadOrders(User)` — `CompletableFuture<List<Order>>`. Спит 300 мс. 20% шанс упасть.
3. `loadRecommendations(User)` — `CompletableFuture<List<Item>>`. Спит 400 мс. 10% шанс упасть.
4. `combine(User, List<Order>, List<Item>)` — `Profile`. Просто собирает всё вместе.

**Требования:**

1. Постройте цепочку: `loadUser` → параллельно `loadOrders` и `loadRecommendations` → `combine`.
2. **Обработка ошибок:**
   - Если `loadUser` упал — вернуть `null` (без профиля).
   - Если `loadOrders` упал — пустой список.
   - Если `loadRecommendations` упал — пустой список.
3. **Таймаут** на каждый шаг — 1 секунда (`orTimeout`). Таймаут считается ошибкой — обрабатывается как «упал».
4. **Логирование** каждого шага через `whenComplete` — «loadUser: успех/ошибка», «loadOrders: …», и т.д.
5. **Замер** общего времени. Если все успешно — ~400 мс (200 + 300/400 параллельно). Если `loadUser` упал — ~200 мс.

**Дополнительно:**

- Запустите 100 раз. Соберите статистику: сколько раз каждый шаг упал, сколько раз был таймаут.
- Замените `orTimeout` на `completeOnTimeout` с fallback-значением. Сравните: стало ли проще?
- Сделайте так, чтобы при падении `loadUser` вся цепочка **не запускала** `loadOrders` и `loadRecommendations` (экономия ресурсов). Проверьте, что это работает.

**Вопросы в комментарии:**

1. Почему `loadOrders` и `loadRecommendations` должны запускаться **параллельно**, а не последовательно?
2. Почему `exceptionally` лучше `handle` для каждого шага в этой задаче?
3. Почему `whenComplete` не должен бросать исключений?
4. Почему `orTimeout` на каждом шаге — а не один общий таймаут на всю цепочку?

## Задача 4. Первый успешный

**Что комбинируется:** 6.3 (`anyOf`), 6.1 (`Future`), 4.2 (`ExecutorService`).

Реализуйте **hedged request** — отправку запроса в несколько источников, с выбором первого успешного.

**Постановка:**

1. `querySource(name, delay, failProbability)` — `CompletableFuture<String>`. Спит `delay` мс, с вероятностью `failProbability` падает.
2. Три источника:
   - `fast`: 100 мс, 50% падений.
   - `medium`: 300 мс, 20% падений.
   - `slow`: 500 мс, 5% падений.
3. Запустить все три **одновременно**. Взять **первый успешный** результат.
4. Если **все** упали — вернуть `"all failed"`.

**Требования:**

- Использовать `anyOf` для «первого готового», но с обработкой ошибок: если первый готовый — упал, взять следующий.
- Можно реализовать через `CompletableFuture.anyOf` + рекурсию, или через `CompletableFuture` с `handle` на каждом источнике, чтобы «упавший» превращался в `null`, а `anyOf` возвращал первый **не-null**.

**Дополнительно:**

- Запустите 100 раз. Соберите статистику: какой источник выиграл чаще всего, сколько раз все упали.
- Замените `anyOf` на последовательный перебор: сначала `fast`, если упал — `medium`, если упал — `slow`. Сравните время и надёжность.
- Добавьте **общий таймаут** 700 мс. Если ни один не успел — вернуть `"timeout"`.

**Вопросы в комментарии:**

1. Почему `anyOf` **без** `handle` на каждом источнике — плохая идея?
2. В чём преимущество hedged request перед последовательным перебором?
3. В каком случае последовательный перебор лучше?
4. Почему «первый успешный» — это не «первый завершившийся»?

## Задача 6. Асинхронный пайплайн

**Что комбинируется:** 6.2 (`thenCompose`), 6.3 (`exceptionally`), 5.4 (`BlockingQueue`).

Реализуйте **асинхронный конвейер обработки** с очередью.

**Постановка:**

1. `BlockingQueue<String> inputQueue` — входящие «запросы».
2. `BlockingQueue<String> outputQueue` — «результаты».
3. **Producer** кладёт 20 «запросов» с паузой 100 мс.
4. **Async-обработчик** (главный поток):
   - Забирает из `inputQueue` через `poll(timeout)`.
   - Для каждого запроса строит `CompletableFuture`:
     - `step1`: 100 мс, может упасть.
     - `step2`: 200 мс, может упасть.
     - `step3`: 50 мс, может упасть.
   - Все три шага — через `thenCompose`.
   - С `exceptionally` — вернуть `"error: " + причина`.
   - Кладёт результат в `outputQueue`.
5. **Consumer** забирает из `outputQueue` и печатает.

**Требования:**

- Producer и Consumer — обычные потоки.
- Обработчик — использует `CompletableFuture` для каждого запроса, **не блокируется** на них (или блокируется, но асинхронно).
- Не менее 5 запросов должны «упасть» (по 20% на шаг — примерно 12 из 20).
- Корректное завершение: после 20 запросов — «poison pill» для consumer.

**Дополнительно:**

- Замените «один `CompletableFuture` на запрос» на «один `CompletableFuture` на все запросы» (`allOf`). Что изменилось?
- Ограничьте параллелизм через `Semaphore` (глава 3.3). Не более 5 `CompletableFuture` одновременно.
- Добавьте метрики: сколько успешно, сколько упало на каком шаге.

**Вопросы в комментарии:**

1. Почему `CompletableFuture` в этой задаче удобнее, чем «просто `ExecutorService.submit`»?
2. Почему `exceptionally` на каждом шаге — а не один в конце?
3. Почему `thenCompose` нужен на каждом шаге, а не `thenApply`?
4. Как ограничить параллелизм, если `CompletableFuture` «запускает всё сразу»?

## Задача 7. Диагноз по симптому

**Что комбинируется:** всё.

Вам даны три программы. Каждая использует `CompletableFuture` или `parallelStream`, но **неправильно**. Определите проблему и предложите исправление.

**Программа А:**

```java
List<CompletableFuture<String>> futures = urls.stream()
    .map(url -> CompletableFuture.supplyAsync(() -> httpGet(url)))
    .collect(Collectors.toList());

List<String> results = futures.stream()
    .map(CompletableFuture::join)
    .collect(Collectors.toList());
```

**Программа Б:**

```java
CompletableFuture
    .supplyAsync(() -> loadUser(id))
    .thenApply(user -> loadOrders(user))
    .thenApply(orders -> sum(orders))
    .thenAccept(sum -> System.out.println(sum));
```

**Программа В:**

```java
List<Integer> result = numbers.parallelStream()
    .map(x -> {
        try { Thread.sleep(10); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        return x * 2;
    })
    .collect(Collectors.toList());
```

2. Почему Б «неправильно»? Что произойдёт с `orders`? Как это исправить?
3. Почему В может быть **медленнее** последовательного варианта? Какая операция «съедает» всю параллельность?

## Задача 8. Резюме в одном приложении

**Что комбинируется:** всё.

Напишите **асинхронный агрегатор данных** — мини-аналог API-шлюза.

**Сценарий:**

1. **Принимает** «запрос пользователя» через `BlockingQueue<String>` (3 потока кладут 10 запросов).
2. Для каждого запроса **параллельно** обращается к трём источникам:
   - `sourceA` — 200 мс, 20% падений.
   - `sourceB` — 300 мс, 20% падений.
   - `sourceC` — 100 мс, 30% падений.
3. Для каждого источника — `CompletableFuture` с `orTimeout(500ms)` и `exceptionally`.
4. Когда все три готовы (`allOf`) — **комбинирует** результаты.
5. **Результат** — `CompletableFuture<String>`, который складывается в `ConcurrentLinkedQueue`.
6. **Другой поток** забирает результаты из `ConcurrentLinkedQueue` и печатает.
7. **Метрики:** сколько запросов обработано, сколько упало на каждом источнике, сколько таймаутов.

**Требования:**

- Ограничение параллелизма через `Semaphore(5)` — не более 5 запросов одновременно.
- Все шаги — на `CompletableFuture`.
- Корректное завершение.
- Сводка в конце.

**Что проверяется:** умение собрать `CompletableFuture`, `BlockingQueue`, `Semaphore`, `orTimeout`, `exceptionally`, `allOf` в связную систему.

## 🎯 Проектное задание. Асинхронный агрегатор с fallback

Это задание сложнее предыдущих. Оно не про конкретный метод, а про **дизайн**.

### Постановка

Реализуйте `AsyncAggregator`, который собирает данные из **нескольких** источников с fallback-стратегией.

1. Принимает **список** источников (каждый — `Function<String, CompletableFuture<String>>`).
2. Принимает `key` (например, `"user:42"`).
3. Для каждого источника — `CompletableFuture` с `orTimeout(1, TimeUnit.SECONDS)`.
4. **Стратегия fallback:** попробовать источники **по очереди** (не параллельно), пока один не вернёт результат. Если упал или таймаут — перейти к следующему. Если все упали — вернуть `"all failed"`.
5. **Стратегия parallel:** попробовать **все** источники параллельно, взять первый успешный (`anyOf` + `handle`). Если все упали — `"all failed"`.
6. **Стратегия hedged:** сначала `primary`, через 200 мс — `secondary` (если `primary` ещё не ответил), через 400 мс — `tertiary`. Первый успешный — побеждает.

### Требования к реализации

- Каждая стратегия — отдельный метод.
- Логирование через `whenComplete` на каждом шаге.
- Метрики: `hits` (успех с первого источника), `fallbacks` (успех со второго+), `failures` (все упали), `timeouts`.
- Конфигурируемый `Executor` (не `commonPool` для I/O).
- Корректное завершение `Executor` в `finally`.

### Тесты

1. **Все успешны:** все три источника отвечают. `fallback`-версия должна взять **первый**, а не все.
2. **Первый падает:** `primary` падает, `secondary` успешен. `fallback` — берёт `secondary`.
3. **Все падают:** все три падают. `fallback` — `"all failed"`.
4. **Таймаут:** `primary` «висит» 2 секунды. `orTimeout` через 1 секунду → переход к следующему.
5. **Замер:** для каждой стратегии — общее время на 100 запросов. Сравните.

### Задание со звёздочкой

1. Почему `fallback`-стратегия может быть **медленнее** `parallel` в среднем, но **надёжнее**?
2. Как реализовать `hedged`-стратегию, чтобы «вторичный» источник запускался **только если** `primary` ещё не ответил? (Подсказка: `CompletableFuture` + `ScheduledExecutorService`.)
3. Как бы вы реализовали **адаптивный** выбор стратегии: если `primary` отвечает быстро — используем `fallback`; если медленно — `parallel`? (Подсказка: скользящее среднее времени ответа.)
4. Что произойдёт, если все три стратегии использовать **вместе** в одном агрегаторе? Как это повлияет на нагрузку?

Ответьте в комментарии к коду. Однозначно правильных ответов на последние вопросы нет — важно ваше рассуждение.

# 6.1. Future и Callable

## Где вы это уже видели

**Гардероб в театре.** Вы сдаёте пальто, получаете номерок. Пальто висит где-то в недрах гардероба, а у вас на руках — бумажка с номером. Вы можете пойти в буфет, поговорить с приятелем, почитать программку. Когда нужно — возвращаетесь, отдаёте номерок, получаете пальто. Номерок — это не пальто, это **обещание**, что пальто будет выдано по требованию.

**Заказ в бургерной.** Вы оплатили, получили чек с номером 47. Кухня готовит. Вы садитесь за столик, листаете телефон. Через пять минут на табло появляется «47». Вы идёте и забираете свой заказ. Пока номер не появился — вы **не стоите у стойки**, вы занимаетесь своими делами.

**Трек-номер посылки.** Вы оформили доставку в интернет-магазине. У вас есть трек-номер. Вы можете **проверить статус** — «в пути», «на складе», «доставлено». Или можете **дождаться** уведомления. Или **отменить** заказ, пока он не ушёл. Всё это — разные способы работы с одним и тем же «обещанием доставки».

**Билет на поезд.** Купили билет на завтрашний поезд. Поезд ещё не пришёл, но место за вами. Если планы поменялись — можно **сдать билет** (отменить). Если поезд отменили — вам **вернут деньги** (исключение). Пока поезд не пришёл, вы **не сидите на вокзале** — вы занимаетесь своими делами.

**Общее во всех случаях** одно: есть **задача**, которая выполняется где-то в другом месте, и есть **номерок** — способ получить результат, когда он будет готов. Пока результат не готов, вы свободны. Когда готов — забираете. Это и есть `Future` — «обещание результата».

## Теория

### Callable: Runnable с результатом

Вспомним главу 1.2. `Runnable` — это задача без результата: `void run()`. Сделал — и всё, никакого «вернуть».

`Callable<V>` — это задача **с результатом** типа `V`. Один метод: `V call() throws Exception`. Два важных отличия от `Runnable`.

**Первое: возвращает значение.** `call()` возвращает `V`, а не `void`. Можно получить результат.

**Второе: может бросать проверяемые исключения.** `call()` объявляет `throws Exception`. Внутри можно спокойно делать `Thread.sleep`, читать файлы, ходить в сеть — не нужно оборачивать в `try/catch`.

```java
import java.util.concurrent.Callable;

Callable<Integer> task = () -> {
    Thread.sleep(1000); // можно, это checked exception
    return 42;
};
```

Если бы это был `Runnable`, пришлось бы делать `try/catch` вокруг `sleep`. С `Callable` — не нужно.

### Future: обещание результата

`Future<V>` — интерфейс, который **обещает** результат типа `V` когда-нибудь в будущем. Когда именно — неизвестно. Может, через миллисекунду. Может, через час. Может, никогда — если задача упадёт или её отменят.

Основные методы:

**`V get()`** — получить результат. **Блокируется**, пока результат не будет готов. Если задача упала — бросает `ExecutionException` с причиной внутри. Если задача отменена — бросает `CancellationException`. Если текущий поток прервали во время ожидания — бросает `InterruptedException`.

**`V get(long timeout, TimeUnit unit)`** — то же, но **не дольше** указанного времени. Если не дождались — бросает `TimeoutException`.

**`boolean isDone()`** — задача завершилась? Неважно, успешно или с ошибкой — просто «закончилась».

**`boolean isCancelled()`** — задача была отменена?

**`boolean cancel(boolean mayInterruptIfRunning)`** — попытаться отменить. Возвращает `true`, если отмена «принята». Если задача уже завершилась — `false`. Параметр `mayInterruptIfRunning` — прерывать ли выполняющуюся задачу через `interrupt`.

### Как получить Future

Главный способ — через `ExecutorService.submit()` (глава 4.2).

```java
ExecutorService pool = Executors.newFixedThreadPool(4);

Future<Integer> future = pool.submit(() -> {
    Thread.sleep(1000);
    return 42;
});
```

`submit` возвращает `Future<Integer>` — номерок. Задача уже выполняется в пуле. Вы свободны.

```java
// можно заниматься своими делами
System.out.println("Пока задача работает, я делаю что-то ещё");

// а потом — забрать результат
Integer result = future.get(); // блокируется, пока не будет готов
System.out.println("Результат: " + result);
```

**Обратите внимание:** между `submit` и `get` можно делать **что угодно**. Задача работает в фоне. Это и есть асинхронность — в том смысле, в каком её даёт `Future`.

### Future — это «полу-асинхронность»

Важно понимать: `Future` — это **не** полноценная асинхронность. Это способ **запустить в фоне и потом дождаться**. Когда вы вызываете `get()`, вы **блокируетесь**. Если задача займёт час — вы будете ждать час.

Это нормально для многих задач: «запусти параллельно, а потом собери результаты». Но для «настоящей» асинхронности — когда нужно **скомбинировать** несколько `Future` без блокировки, — `Future` не подходит. Для этого есть `CompletableFuture` (глава 6.2). Пока просто запомните: **`Future` умеет ждать, но не умеет комбинировать**.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> <code>Future</code> — для «запустил в фоне, потом дождался». Если нужно «сделай A, потом B, потом C, и всё без блокировки» — это <code>CompletableFuture</code>, глава 6.2.
</div>

### ExecutionException: исключения из задачи

Если задача упала с исключением — `get()` бросит `ExecutionException`. Внутри — причина (`getCause()`).

```java
Future<Integer> future = pool.submit(() -> {
    throw new RuntimeException("что-то пошло не так");
});

try {
    future.get();
} catch (ExecutionException e) {
    System.out.println("Задача упала: " + e.getCause().getMessage());
}
```

**Почему `ExecutionException`, а не `RuntimeException` напрямую?** Потому что `get()` — это метод, который может бросить и другие исключения (`InterruptedException`, `CancellationException`, `TimeoutException`). Разработчики JDK решили «обернуть» исключение задачи в отдельный тип, чтобы не смешивать с другими.

**Важно:** исключение задачи **не пробрасывается само по себе**. Если вы никогда не вызываете `get()`, вы никогда не узнаете, что задача упала. Оно «хранится» в `Future` и ждёт, пока его достанут. Об этом была ошибка в главе 4.2 — «игнорировать Future».

### CancellationException: задача отменена

Если задача была отменена через `cancel(true)`, то `get()` бросит `CancellationException`.

```java
Future<Integer> future = pool.submit(() -> {
    Thread.sleep(10000);
    return 42;
});

future.cancel(true); // отменить
// ...
try {
    future.get(); // бросит CancellationException
} catch (CancellationException e) {
    System.out.println("Задача была отменена");
}
```

`CancellationException` — **не ошибка**. Это нормальный сценарий: «я передумал, не надо». Обрабатывать её нужно спокойно, не как аварию.

### cancel: попытка отмены

`cancel(boolean mayInterruptIfRunning)` — попытка отменить задачу. Три возможных исхода.

**Задача ещё не начала выполняться** — она просто не запустится. `cancel` вернёт `true`.

**Задача выполняется** — если `mayInterruptIfRunning = true`, задача получит `interrupt`. Если `false` — доработает до конца, а её результат будет проигнорирован. `cancel` вернёт `true` в обоих случаях (отмена «принята»).

**Задача уже завершилась** — `cancel` вернёт `false`, ничего не произойдёт.

**Ключевое:** `cancel` — это **просьба**, а не приказ. Если задача игнорирует `interrupt` (например, `while(true)` без проверки флага — глава 1.6), она продолжит работать. `Future.isCancelled()` вернёт `true`, `get()` бросит `CancellationException`, но сама задача всё ещё будет занимать поток. Это ответственность задачи — реагировать на прерывание.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> <code>cancel(true)</code> не гарантирует остановку задачи. Он только посылает <code>interrupt</code>. Если задача не проверяет флаг прерывания — она продолжит работать. <code>Future.isCancelled()</code> вернёт <code>true</code>, но поток будет занят.
</div>

### get(timeout): не ждать вечно

`get()` без таймаута может ждать вечно. Если задача «залипла» — вы «залипли» вместе с ней. В продакшене это плохо.

`get(timeout)` — ждёт **не дольше** указанного времени. Если не дождались — `TimeoutException`.

```java
try {
    Integer result = future.get(5, TimeUnit.SECONDS);
    System.out.println("Результат: " + result);
} catch (TimeoutException e) {
    System.out.println("Не дождались за 5 секунд");
    future.cancel(true); // отменяем — не нужен нам такой результат
}
```

**Важно:** `TimeoutException` **не отменяет** задачу. Задача продолжает выполняться в фоне. Вы просто перестаёте её ждать. Если результат больше не нужен — вызовите `cancel(true)`.

### isDone: проверка без блокировки

`isDone()` — «задача завершилась?». Не блокируется. Возвращает `true`, если задача закончилась — успешно, с ошибкой или была отменена. Всё равно.

```java
if (future.isDone()) {
    Integer result = future.get(); // не блокируется — задача уже готова
} else {
    System.out.println("Ещё работает");
}
```

Это даёт возможность **опрашивать** результат, не блокируясь. Но обычно это плохая идея — busy wait (глава 2.8). Лучше — `get(timeout)` или `CompletableFuture` (глава 6.2).

### FutureTask: редко нужен

`FutureTask<V>` — конкретная реализация `Future`, которая одновременно является `Runnable`. Можно использовать напрямую:

```java
FutureTask<Integer> task = new FutureTask<>(() -> {
    Thread.sleep(1000);
    return 42;
});
new Thread(task).start();
Integer result = task.get();
```

Но обычно не нужно: `ExecutorService.submit()` делает то же самое, проще. `FutureTask` полезен в редких случаях, когда нужен `Future`, который сам является `Runnable` (например, для `execute()` в `ExecutorService`). В обычном коде — не нужен.

### Частые ошибки

**Ошибка 1: `get()` без таймаута в продакшене.** Может ждать вечно. Всегда — с таймаутом, и `cancel(true)` при таймауте.

**Ошибка 2: игнорировать `Future`.** Задача упала с исключением — никто не узнал. Всегда сохраняйте `Future` и проверяйте `get()`.

**Ошибка 3: `cancel(true)` без проверки флага в задаче.** Задача «не заметит» прерывания, продолжит работать. `isCancelled` вернёт `true`, но поток занят.

**Ошибка 4: `get()` без `try/catch`.** `ExecutionException`, `InterruptedException`, `TimeoutException`, `CancellationException` — четыре разных исключения, каждое нужно обработать.

**Ошибка 5: путать `Future` и `CompletableFuture`.** `Future` — «полу-асинхронность» с блокирующим `get`. `CompletableFuture` — полноценная асинхронность с цепочками. Не пытайтесь строить цепочки на `Future` — это будет ад из `get()` в `get()`.

**Ошибка 6: `cancel(false)` для долгой задачи.** `false` — «не прерывай». Задача доработает до конца, просто результат проигнорируется. Если задача спит час — вы ждёте час, хотя результат уже не нужен. Обычно нужен `cancel(true)`.

### Аналогия с номерком из гардероба

Вернёмся к началу. **`Callable`** — это **пальто**, которое вы сдали. Оно есть, оно где-то висит, его можно получить.

**`Future`** — это **номерок**. Бумажка с цифрой. Не само пальто, а обещание его выдать.

**`get()`** — это **подойти к гардеробу и отдать номерок**. Если пальто уже готово — сразу получаете. Если ещё ищут — стоите и ждёте. Это блокировка.

**`get(timeout)`** — «подожду пять минут, потом уйду». Если не выдали — уходите (и, возможно, просите вернуть пальто позже).

**`cancel()`** — «я передумал, заберите номерок». Если пальто ещё не нашли — его не будут искать. Если уже несут — его вернут на место (если задача проверяет прерывание).

**`isDone()`** — «пальто уже готово?». Можно спросить, не вставая в очередь.

**`ExecutionException`** — «извините, пальто испорчено в химчистке». Номерок был, а результата нет — с ошибкой.

## Микрозадача 1: базовый Future

**Задача:** Создайте `ExecutorService` на 2 потока. Отправьте задачу через `submit`, которая спит 1 секунду и возвращает `42`. Между `submit` и `get` выведите «Пока задача работает, я свободен». Потом получите результат через `get()` и выведите его.

**Решение:**

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;
import java.util.concurrent.TimeUnit;

public class Main {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(2);

        Future<Integer> future = pool.submit(() -> {
            Thread.sleep(1000);
            return 42;
        });

        System.out.println("Пока задача работает, я свободен");
        System.out.println("Свободен ещё немного...");
        Thread.sleep(300);
        System.out.println("Всё ещё свободен");

        Integer result = future.get();
        System.out.println("Результат: " + result);

        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
    }
}
```

**Возможный вывод:**

```text
Пока задача работает, я свободен
Свободен ещё немного...
Всё ещё свободен
Результат: 42
```

**Разбор:** задача запущена через `submit` и работает в фоне. Главный поток «свободен» — он спал 300 мс, потом ещё что-то делал. Только когда вызвал `get()` — заблокировался и дождался результата. Это и есть «полу-асинхронность»: задача асинхронна, но получение результата — синхронно.

Если бы задача занимала 10 секунд, а главный поток — 300 мс, он бы «висел» на `get()` ещё 9,7 секунды. Именно поэтому в продакшене — `get(timeout)`.

## Микрозадача 2: get с таймаутом

**Задача:** Отправьте задачу, которая спит 5 секунд. Вызовите `get(1, TimeUnit.SECONDS)`. Убедитесь, что вылетает `TimeoutException`. Отмените задачу через `cancel(true)`. Проверьте `isCancelled`.

**Решение:**

```java
import java.util.concurrent.*;

public class Main {
    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(2);

        Future<Integer> future = pool.submit(() -> {
            System.out.println("Задача начала работу");
            try {
                Thread.sleep(5000);
            } catch (InterruptedException e) {
                System.out.println("Задача прервана");
                Thread.currentThread().interrupt();
                throw e;
            }
            System.out.println("Задача завершилась сама");
            return 42;
        });

        try {
            Integer result = future.get(1, TimeUnit.SECONDS);
            System.out.println("Результат: " + result);
        } catch (TimeoutException e) {
            System.out.println("Не дождались за 1 секунду");
            future.cancel(true);
            System.out.println("isCancelled: " + future.isCancelled());
            System.out.println("isDone: " + future.isDone());
        }

        Thread.sleep(500);
        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
    }
}
```

**Возможный вывод:**

```text
Задача начала работу
Не дождались за 1 секунду
isCancelled: true
isDone: true
Задача прервана
```

**Разбор:** `get(1, TimeUnit.SECONDS)` подождал секунду, не дождался — бросил `TimeoutException`. Мы отменили задачу через `cancel(true)`. `isCancelled` и `isDone` сразу вернули `true` — задача «помечена» как отменённая.

А потом — «Задача прервана». Это уже **сама задача** получила `interrupt`, поймала `InterruptedException` и корректно завершилась. Между `cancel(true)` и фактическим завершением задачи есть задержка: `cancel` только посылает `interrupt`, а задача реагирует, когда дойдёт до точки проверки.

**Важно:** `isCancelled = true` **не значит**, что задача уже остановилась. Она может ещё работать. Это «обещание», что результат будет проигнорирован, а не «факт остановки».

## 🎯 Самостоятельная задача

Реализуйте **параллельный загрузчик с таймаутами и отменой**.

**Постановка:**

1. Есть список из 10 «URL-адресов» (строки).
2. Каждый «файл» загружается 200–2000 мс (случайное время).
3. С вероятностью 20% «загрузка» падает с `RuntimeException`.
4. Нужно загрузить все файлы параллельно через `ExecutorService` (4 потока) + `Future` для каждого.

**Требования:**

1. Сохраняйте `Future<String>` для каждого файла в `List`.
2. Для каждого `Future` вызывайте `get(3, TimeUnit.SECONDS)`.
3. Обработайте:
   - `TimeoutException` — отменить `cancel(true)`, записать «timeout».
   - `ExecutionException` — записать «failed: причина».
   - `CancellationException` — записать «cancelled».
   - `InterruptedException` — восстановить флаг, выйти из цикла.
4. В конце — сводка: сколько успешно, сколько timeout, сколько failed.
5. Корректно завершить пул.

**Дополнительно:**

- Проверьте: после `cancel(true)` задача действительно реагирует на `interrupt`? Добавьте в задачу `try/catch(InterruptedException)`, который логирует «прервана».
- Замените `get(3, TimeUnit.SECONDS)` на `get()` без таймаута. Что произойдёт с задачами, которые «зависают»? (Смоделируйте зависание: задача спит 30 секунд.)
- Добавьте общий таймаут: если суммарно прошло больше 10 секунд — отменить все `Future` и выйти.

**Вопросы в комментарии:**

1. Почему `TimeoutException` не останавливает задачу?
2. Что произойдёт, если `cancel(true)` вызвать на уже завершённой задаче?
3. Почему `isDone()` может вернуть `true` до фактического завершения задачи при `cancel`?
4. В чём разница между «отменить задачу» и «перестать её ждать»?

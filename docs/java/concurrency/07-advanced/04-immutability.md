# 7.4. Неизменяемость как стратегия

## Где вы это уже видели

**Паспорт.** В паспорте написано: фамилия, имя, дата рождения. Вы не можете «исправить» дату рождения в паспорте ручкой. Если что-то поменялось (фамилия после замужества) — выдают **новый** паспорт. Старый сдаётся. Паспорт — это **неизменяемый** документ, который можно только **заменить** целиком.

**Рецепт в кулинарной книге.** Вы прочитали рецепт. Пока вы готовите, рецепт **не меняется**. Если бы кто-то мог поменять его на середине («а теперь добавь ещё соли») — было бы странно. Рецепт — **неизменяемая** инструкция, доступная всем одновременно.

**Координаты на карте.** У ресторана есть адрес: «ул. Ленина, 5». Адрес **не меняется**, пока ресторан не переедет. Если переехал — это уже **другой** адрес (или другой ресторан). Координаты — **неизменяемая** ссылка на место.

**Номинал монеты.** У монеты в 10 рублей — номинал 10 рублей. Нельзя «переделать» её в 50. Можно обменять на другую. Монета — **неизменяемый** объект с фиксированным номиналом.

**Кредитный договор.** В договоре зафиксированы сумма, ставка, срок. Если условия меняются — **подписывают новый** договор (доп. соглашение). Старый остаётся в силе для старых условий. Договор — **неизменяемый** документ.

**Общее во всех случаях** одно: есть **объект**, который нельзя **изменить** после создания. Если нужно другое значение — создаётся **новый** объект. Старый остаётся нетронутым. Это и есть **неизменяемость** (immutability), и это — самая мощная стратегия борьбы с гонками.

## Теория

### Проблема изменяемого состояния

До сих пор мы всё время **защищали** изменяемые данные. `synchronized` (глава 2.2) — чтобы два потока не писали одновременно. `volatile` (глава 2.4) — чтобы один видел изменения другого. `AtomicInteger` (глава 2.6) — чтобы инкремент был атомарным. `Lock` (глава 3.5) — чтобы был таймаут и справедливость. `ConcurrentHashMap` (глава 5.2) — чтобы мапа не ломалась. Везде — **изменяемое** состояние и **защита** от гонок.

А что если **не менять** данные? Тогда **нечего защищать**. Гонка — это когда два потока **пишут** в общую переменную. Если **никто не пишет** — гонки **не существует**. Всё просто: **неизменяемый объект потокобезопасен по определению**.

Это не «ещё один способ», а **смена парадигмы**. Вместо «защитить изменяемое» — «сделать так, чтобы менять было нечего».

### Что делает объект неизменяемым

В Java объект считается **неизменяемым**, если выполнены четыре условия.

**Условие 1: все поля `final`.** После конструктора значение поля нельзя изменить. `final` гарантирует, что ссылка не будет переприсвоена.

**Условие 2: нет сеттеров.** Никаких методов, которые меняют поля. Только геттеры (и то — не всегда).

**Условие 3: класс `final` (или все конструкторы `private`).** Чтобы нельзя было унаследоваться и **добавить** изменяемое поведение. Если класс не `final`, наследник может добавить сеттер — и «неизменяемость» сломается.

**Условие 4: изменяемые поля защищены.** Если поле — ссылка на изменяемый объект (например, `List`), нужна **defensive copying**: при создании — копировать, при чтении — не давать «утечку» ссылки.

```java
public final class Money {
    private final long amount;
    private final String currency;

    public Money(long amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }

    public long getAmount() { return amount; }
    public String getCurrency() { return currency; }
}
```

**Что здесь важно.**

- `final` на классе — нельзя унаследоваться и добавить сеттер.
- `final` на полях — нельзя переприсвоить.
- Нет сеттеров — нельзя изменить.
- `long` и `String` — сами по себе неизменяемые. Defensive copying не нужен.

Такой объект **потокобезопасен по определению**. Не нужен `synchronized`. Не нужен `volatile`. Не нужен `Lock`. Два потока могут читать его одновременно — и никто никому не помешает, потому что **читать** — безопасно, а **писать** нечего.

### record: неизменяемость по умолчанию

В Java 16 появились `record` — специальный тип для «неизменяемых контейнеров данных». `record` **автоматически** удовлетворяет первым трём условиям: все поля `final`, нет сеттеров, класс `final`.

```java
public record Money(long amount, String currency) {}
```

Одна строчка — и у вас:
- конструктор `Money(long amount, String currency)`;
- геттеры `amount()` и `currency()`;
- `equals`, `hashCode`, `toString`;
- все поля `final`;
- класс `final`.

**Это идиоматический способ делать неизменяемые объекты в современной Java.** Если вам нужен «объект-значение» (деньги, координаты, диапазон, имя) — `record`, а не класс с кучей boilerplate.

**Осторожно:** `record` гарантирует неизменяемость **ссылок**, но не **содержимого**. Если поле — `List<String>`, сам список может быть изменяемым. `record` не защищает от `list.add(...)`. Для полной неизменяемости — **defensive copying** или неизменяемые коллекции (ниже).

### Неизменяемые коллекции

`List.of(...)`, `Set.of(...)`, `Map.of(...)` — создают **неизменяемые** коллекции. Любая попытка изменить — `UnsupportedOperationException`.

```java
List<String> list = List.of("a", "b", "c");
list.add("d"); // UnsupportedOperationException
```

**Важно:** `List.of` не делает **копию** переданных элементов. Если вы передали изменяемый объект — он остался изменяемым. Неизменяема **структура** списка (нельзя добавить/удалить элемент), но не **элементы**.

Для **полной** неизменяемости — `List.copyOf(...)`, который **копирует** элементы в новый список и делает его неизменяемым:

```java
List<String> mutable = new ArrayList<>();
mutable.add("a");
List<String> immutable = List.copyOf(mutable);
mutable.add("b"); // на immutable не влияет
System.out.println(immutable); // [a]
```

`Collections.unmodifiableList(...)` — **обёртка** над существующим списком. Не копирует. Если исходный список изменят — изменения **видны** через обёртку. Это **не** полная неизменяемость.

```java
List<String> mutable = new ArrayList<>();
mutable.add("a");
List<String> wrapper = Collections.unmodifiableList(mutable);
mutable.add("b");
System.out.println(wrapper); // [a, b] — обёртка видит изменения
```

**Правило:** для настоящей неизменяемости — `List.copyOf`, `Map.copyOf`, `Set.copyOf` или `List.of`. `Collections.unmodifiable*` — только если вы **уверены**, что исходный объект больше никто не меняет.

### Почему неизменяемость устраняет гонки

Вспомним определение гонки (глава 2.1): «два потока одновременно обращаются к общим данным, и хотя бы один **пишет**». Если **никто не пишет** — гонки **нет**. Не «меньше», не «реже» — **вообще нет**.

Неизменяемый объект:
- создан один раз (в конструкторе);
- после этого **никогда** не меняется;
- все потоки видят **одно и то же** состояние.

Не нужно `synchronized` — нечего защищать. Не нужно `volatile` — нечего «публиковать». Не нужно `Lock` — нечего «захватывать». Не нужно `Atomic` — нечего «атомарно инкрементировать».

**Это и есть главная сила неизменяемости:** она устраняет **причину** гонки, а не борется с **симптомом**.

### Safe publication: почему final-поля безопасны

Есть тонкий момент, связанный с моделью памяти (глава 2.5). Если объект **не** неизменяем, и вы «публикуете» его (передаёте в другой поток) без синхронизации — другой поток может увидеть **недоинициализированный** объект. Поля могут быть `null` или значениями по умолчанию, хотя конструктор уже отработал.

`final`-поля — **исключение**. JMM гарантирует: если объект опубликован корректно, `final`-поля видны в **правильном** состоянии, даже без синхронизации. Это называется **safe publication** через `final`.

**Практический вывод:** неизменяемый объект с `final`-полями можно **безопасно** передавать между потоками без `synchronized` и `volatile`. Это ещё одна причина использовать `final` везде, где возможно.

**Осторожно:** safe publication работает только для `final`-полей **самого объекта**. Если поле — ссылка на изменяемый объект, его **содержимое** может быть не полностью инициализировано. Поэтому для полной безопасности — все поля должны быть либо примитивами, либо ссылками на другие неизменяемые объекты, либо защищены defensive copying.

### Неизменяемость и производительность

Может показаться, что «создавать новый объект на каждое изменение» — расточительно. Это не всегда так.

**Плюсы:**
- **Нет блокировок.** Чтение без синхронизации — быстро.
- **Нет переключений контекста.** Потоки не ждут друг друга.
- **Меньше ошибок.** Нет гонок — нет багов.
- **Легче кешировать.** Неизменяемый объект можно кешировать, шарить, использовать как ключ в мапе без defensive copying.
- **Безопасно передавать между потоками.** Safe publication через `final`.

**Минусы:**
- **Аллокации.** Каждое «изменение» — новый объект. Для маленьких объектов (числа, строки) — дёшево. Для больших (списки на миллион элементов) — дорого.
- **GC-нагрузка.** Больше мусора — чаще сборка.
- **Не для всех задач.** Если нужно часто менять большое состояние (например, `ArrayList` в цикле) — неизменяемость проиграет.

**Когда неизменяемость — правильный выбор:**

- Объекты-значения (деньги, координаты, диапазоны, имена).
- Конфигурации (создаются один раз, читаются много).
- Сообщения, события, DTO.
- Ключи в мапах.
- Результаты вычислений.

**Когда изменяемость лучше:**

- Большие коллекции, которые часто меняются (буферы, кеши).
- Счётчики и аккумуляторы (для них — `Atomic` или `LongAdder`).
- «Рабочие» объекты в цикле (например, `StringBuilder` для конкатенации).

### Функциональный подход: «изменение» как создание нового

Классический пример — `String`. Строки в Java **неизменяемы**. Когда вы пишете:

```java
String s = "hello";
s = s + " world";
```

Вы **не меняете** строку `"hello"`. Вы создаёте **новую** строку `"hello world"` и присваиваете её переменной `s`. Старая `"hello"` остаётся в памяти (пока на неё есть ссылки).

Тот же принцип — для **списков**:

```java
List<String> list1 = List.of("a", "b");
List<String> list2 = new ArrayList<>(list1);
list2.add("c");
List<String> list3 = List.copyOf(list2);
```

`list1`, `list2`, `list3` — **разные** объекты. `list1` не изменился. Это «функциональный» подход: **изменение = создание нового**.

**Плюс:** каждый объект — «снимок» состояния. Можно безопасно шарить между потоками. Можно откатываться к предыдущему состоянию.

**Минус:** больше памяти. Если список на миллион элементов и вы добавляете по одному — миллион копий по миллиону элементов. Катастрофа.

**Решение:** для больших коллекций — **persistent data structures** (структуры, которые «делят» общие части между версиями). В Java стандартной библиотеки их нет, но есть сторонние (например, Vavr). Для обычных задач — `List.copyOf` достаточно.

### Immutable vs unmodifiable

Важно различать два понятия.

**Immutable (неизменяемый)** — объект **не может** быть изменён **никаким** способом. Все поля `final`, нет сеттеров, defensive copying.

**Unmodifiable (нередактируемый)** — **обёртка**, которая **запрещает** изменение через себя, но **исходный** объект может быть изменён **напрямую**.

```java
List<String> mutable = new ArrayList<>();
mutable.add("a");

// Unmodifiable — обёртка
List<String> unmod = Collections.unmodifiableList(mutable);
unmod.add("b"); // UnsupportedOperationException
mutable.add("c"); // OK, исходный список изменился
System.out.println(unmod); // [a, c] — обёртка видит изменение

// Immutable — копия
List<String> immut = List.copyOf(mutable);
mutable.add("d");
System.out.println(immut); // [a, c] — копия не видит изменение
```

**Правило:** если вам нужна **настоящая** неизменяемость — `List.copyOf`, `Map.copyOf`, `Set.copyOf` или `record`. `Collections.unmodifiable*` — только для «запрета записи», но не для защиты от изменений извне.

### Частые ошибки

**Ошибка 1: `final` на ссылке, но не на содержимом.** `final List<String> list = new ArrayList<>();` — ссылка `final`, но `list.add(...)` работает. `final` защищает **ссылку**, не **объект**.

**Ошибка 2: `record` с изменяемым полем.** `record Point(List<Integer> coords) {}` — `coords` можно менять. Для полной неизменяемости — `List.copyOf(coords)` в компактном конструкторе.

**Ошибка 3: `Collections.unmodifiableList` вместо `List.copyOf`.** Обёртка видит изменения извне. Для настоящей неизменяемости — копия.

**Ошибка 4: класс не `final`.** Наследник может добавить сеттер — и «неизменяемость» сломается. Всегда `final` (или `record`).

**Ошибка 5: возврат внутренней коллекции.** Если `getItems()` возвращает **ссылку** на внутренний `List`, вызывающий код может его изменить. Defensive copying при возврате (или неизменяемая коллекция).

**Ошибка 6: изменяемые поля в `record`.** `record` не защищает от изменения **содержимого** изменяемых полей. Для полной неизменяемости — только неизменяемые типы.

**Ошибка 7: неизменяемость для больших часто меняющихся структур.** Копирование миллиона элементов на каждое изменение — катастрофа. Для таких — изменяемые структуры + синхронизация (или `Concurrent*`).

### Аналогия с паспортом и рецептом

Вернёмся к началу. **Неизменяемый объект** — это **паспорт**. Создан один раз, не меняется. Если нужно «изменить» — выдают **новый** паспорт, старый сдают. Все, кто видит паспорт, видят **одно и то же**.

**`record`** — это **бланк паспорта**. Вы заполняете поля один раз, и всё. Никаких «исправлений ручкой».

**`List.of`** — это **опубликованный список**, например, список лауреатов премии. Он **не меняется**. Можно распечатать копию, но оригинал — фиксирован.

**`Collections.unmodifiableList`** — это **стеклянная витрина**. Вы **не можете** достать экспонат, но **куратор** может его заменить. Витрина показывает актуальное состояние.

**`List.copyOf`** — это **фотография витрины**. Вы **не можете** достать, и **куратор** не может повлиять на фотографию. Она зафиксирована на момент съёмки.

**Изменяемый объект** — это **доска в офисе**. Все пишут, стирают, переписывают. Нужна синхронизация: пока один пишет — другой ждёт.

**Неизменяемый объект** — это **напечатанный отчёт**. Напечатали — раздали. Каждый читает свою копию. Никто не может «дописать» в чужую.

## Микрозадача 1: record с валидацией

**Задача:** Создайте `record Range(int from, int to)`, который валидирует, что `from <= to`. Попробуйте создать некорректный диапазон. Убедитесь, что бросается исключение.

**Решение:**

```java
public record Range(int from, int to) {
    public Range {
        if (from > to) {
            throw new IllegalArgumentException(
                "from (" + from + ") > to (" + to + ")");
        }
    }

    public static void main(String[] args) {
        Range ok = new Range(1, 10);
        System.out.println(ok); // Range[from=1, to=10]

        try {
            Range bad = new Range(10, 1);
        } catch (IllegalArgumentException e) {
            System.out.println("Ошибка: " + e.getMessage());
        }
    }
}
```

**Возможный вывод:**

```text
Range[from=1, to=10]
Ошибка: from (10) > to (1)
```

**Разбор:** «компактный конструктор» в `record` (`public Range { ... }`) выполняется **до** присвоения полей. В нём можно валидировать. Если данные некорректны — бросаем `IllegalArgumentException`, и объект **не создаётся**. Это гарантирует, что **любой** созданный `Range` — корректен.

Неизменяемость + валидация в конструкторе = «объект всегда в корректном состоянии». Не нужно проверять «а вдруг кто-то поменял поле?» — поменять нельзя.

## Микрозадача 2: неизменяемая коллекция в record

**Задача:** Создайте `record Team(String name, List<String> members)`. В компактном конструкторе сделайте defensive copy через `List.copyOf`. Убедитесь, что внешний список не влияет на `Team`.

**Решение:**

```java
import java.util.ArrayList;
import java.util.List;

public record Team(String name, List<String> members) {
    public Team {
        members = List.copyOf(members); // defensive copy
    }

    public static void main(String[] args) {
        List<String> mutable = new ArrayList<>();
        mutable.add("Alice");
        mutable.add("Bob");

        Team team = new Team("Alpha", mutable);
        System.out.println("До: " + team.members()); // [Alice, Bob]

        mutable.add("Charlie");
        System.out.println("После изменения исходного: " + team.members()); // [Alice, Bob]

        try {
            team.members().add("Dave");
        } catch (UnsupportedOperationException e) {
            System.out.println("Нельзя изменить members: UnsupportedOperationException");
        }
    }
}
```

**Возможный вывод:**

```text
До: [Alice, Bob]
После изменения исходного: [Alice, Bob]
Нельзя изменить members: UnsupportedOperationException
```

**Разбор:** `List.copyOf(members)` создаёт **новую** неизменяемую копию. Изменение исходного `mutable` на `team` **не влияет**. И `team.members().add(...)` бросает `UnsupportedOperationException` — потому что `List.copyOf` возвращает неизменяемый список.

Без `List.copyOf` было бы две проблемы. Первая: изменение `mutable` после создания `team` — **видно** через `team.members()`. Вторая: `team.members().add(...)` **работает**, потому что `record` не защищает содержимое.

## 🎯 Самостоятельная задача

Реализуйте **неизменяемый value object** `Money` и сравните его с изменяемым.

**Постановка:**

1. **`MutableMoney`** — класс с полями `long amount`, `String currency`, сеттерами.
2. **`ImmutableMoney`** — `record` с теми же полями.
3. **`transfer`** — функция, которая «переводит» деньги: создаёт новый объект с другим amount.

**Тесты:**

1. **Под нагрузкой:** 10 потоков, каждый 1000 раз «переводит» 1 рубль. Используйте `MutableMoney` — нужен `synchronized` на каждом изменении. Замерьте время.
2. **То же с `ImmutableMoney`** — каждый «перевод» создаёт **новый** объект. Замерьте время. Сравните.
3. **Без синхронизации:** `MutableMoney` без `synchronized` — гонка. `ImmutableMoney` без синхронизации — корректно, потому что **менять нечего**.
4. **Проверьте:** при 1000 переводах итоговый баланс — корректен в обоих случаях. Но `MutableMoney` без `synchronized` — нет.

**Дополнительно:**

- Добавьте в `MutableMoney` метод `void add(long delta)` — `synchronized`. И `ImmutableMoney add(long delta)` — возвращает **новый** `ImmutableMoney`.
- Сравните: `synchronized` версия vs immutable версия по производительности на 10 потоках × 10 000 операций.
- Проверьте: immutable версия **никогда** не даёт гонку. Запустите 100 раз, убедитесь, что результат всегда корректен.

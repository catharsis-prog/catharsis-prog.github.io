# 7.1. ThreadLocal

## Где вы это уже видели

**Личный шкафчик в раздевалке.** В спортзале у каждого свой шкафчик с замком. Вы кладёте туда кроссовки, полотенце, бутылку воды. Сосед по раздевалке кладёт своё — в свой шкафчик. Вы не видите, что у него внутри, он не видит, что у вас. И не нужно синхронизироваться: каждый работает со своим. Это `ThreadLocal` — «у каждого потока своя копия».

**Черновик на рабочем столе.** Вы пишете документ. У вас на столе лежит черновик — с пометками, зачёркиваниями, стрелками. Коллега за соседним столом пишет свой. Вы не мешаете друг другу, хотя работаете в одном офисе. Каждый — со своим черновиком. `ThreadLocal` — это «свой черновик для каждого потока».

**Корзина в интернет-магазине.** Вы зашли на сайт — у вас своя корзина. Другой покупатель зашёл — у него своя. Оба «в одном магазине», но корзины **разные**. Сервер не путает: у каждого пользователя свой «контекст». `ThreadLocal` в серверных приложениях часто используется именно для этого — «контекст текущего запроса».

**Дневник.** Вы ведёте дневник. Записываете туда мысли, планы, переживания. Никто другой в него не заглядывает — он **ваш личный**. Если бы дневник был общим, вы бы не стали писать в него всё подряд. `ThreadLocal` даёт каждому потоку «личный дневник» — переменную, которую видит только он.

**Общее во всех случаях** одно: есть **переменная**, но у каждого «участника» — **своя копия**. Не общая, не разделяемая, а именно **личная**. Потоки не мешают друг другу, не синхронизируются, не видят чужих данных. Это и есть `ThreadLocal`.

## Теория

### Что такое ThreadLocal

`ThreadLocal<T>` — класс из `java.lang`, который даёт **каждому потоку свою независимую копию** переменной типа `T`.

```java
ThreadLocal<Integer> counter = new ThreadLocal<>();

// В потоке A
counter.set(1);
System.out.println(counter.get()); // 1

// В потоке B
counter.set(2);
System.out.println(counter.get()); // 2 — своё значение, не видит 1 из потока A
```

**Ключевая идея:** `counter` — один объект. Но `get()` возвращает **разное** значение для разных потоков. Внутри `ThreadLocal` хранит `Map<Thread, T>` — по сути, у каждого потока своя «ячейка» в этой мапе.

**Зачем это нужно.** Обычно, когда две нити обращаются к общей переменной, нужна синхронизация (глава 2.2). `ThreadLocal` **избавляет** от синхронизации: каждый поток работает со своей копией, и гонок нет **по определению**. Не нужно `synchronized`, не нужно `volatile`, не нужно `Atomic`. Просто «своя переменная для каждого».

### Основные методы

**`T get()`** — получить значение для текущего потока. Если значения нет — вызывает `initialValue()` (по умолчанию `null`).

**`void set(T value)`** — установить значение для текущего потока.

**`void remove()`** — удалить значение для текущего потока. **Критически важный метод** — см. ниже.

**`protected T initialValue()`** — можно переопределить, чтобы задать «значение по умолчанию». По умолчанию возвращает `null`.

```java
ThreadLocal<Integer> counter = new ThreadLocal<>() {
    @Override
    protected Integer initialValue() {
        return 0;
    }
};
```

Или через `withInitial`:

```java
ThreadLocal<Integer> counter = ThreadLocal.withInitial(() -> 0);
```

`withInitial` — предпочтительнее: короче и понятнее.

### Простой пример

```java
public class Main {
    private static final ThreadLocal<Integer> counter =
        ThreadLocal.withInitial(() -> 0);

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 5; i++) {
                counter.set(counter.get() + 1);
                System.out.println(Thread.currentThread().getName() + ": " + counter.get());
            }
        };

        Thread t1 = new Thread(task, "t1");
        Thread t2 = new Thread(task, "t2");
        t1.start();
        t2.start();
        t1.join();
        t2.join();
    }
}
```

**Возможный вывод:**

```text
t1: 1
t2: 1
t1: 2
t2: 2
t1: 3
t2: 3
t1: 4
t2: 4
t1: 5
t2: 5
```

**Разбор:** каждый поток **независимо** инкрементирует свой счётчик. `t1` видит `1, 2, 3, 4, 5` — и `t2` видит `1, 2, 3, 4, 5`. Они **не мешают** друг другу, хотя код один и тот же. Это `ThreadLocal` в действии: одна переменная, разные значения для разных потоков.

Если бы `counter` был обычным `int`, мы бы получили гонку (глава 2.1) — значения перемешались бы, и итог был бы непредсказуем.

### Где ThreadLocal реально нужен

`ThreadLocal` — не «модный» инструмент, а специфический. Он нужен там, где **нельзя** передавать параметры явно, или где **не хочется** синхронизировать.

**Сценарий 1: контекст запроса в серверном приложении.** В веб-сервере каждый запрос обрабатывается своим потоком. Нужно «протащить» через всю обработку информацию о пользователе, сессии, языке, trace-id. Передавать это через **все** методы — громоздко. `ThreadLocal` даёт «контекст», доступный из любой точки кода.

```java
public class RequestContext {
    private static final ThreadLocal<User> currentUser = new ThreadLocal<>();

    public static void setUser(User user) { currentUser.set(user); }
    public static User getUser() { return currentUser.get(); }
    public static void clear() { currentUser.remove(); }
}

// В фильтре на входе запроса
RequestContext.setUser(extractUser(request));

// Где-то в глубине бизнес-логики
User user = RequestContext.getUser();
```

**Сценарий 2: `SimpleDateFormat` — не потокобезопасен.** Класс `SimpleDateFormat` **не потокобезопасен**: если использовать один экземпляр из нескольких потоков — получите мусор (гонка). Один из способов — `ThreadLocal`:

```java
private static final ThreadLocal<SimpleDateFormat> formatter =
    ThreadLocal.withInitial(() -> new SimpleDateFormat("yyyy-MM-dd"));
```

Каждый поток получает свой `SimpleDateFormat`. Никакой синхронизации. (Современная альтернатива — `DateTimeFormatter` из `java.time`, который **потокобезопасен**. Но `ThreadLocal` — классическое решение.)

**Сценарий 3: буферы для повторного использования.** Если каждый поток многократно создаёт временный буфер (например, `byte[]`), можно создать его один раз в `ThreadLocal` и переиспользовать. Меньше нагрузки на GC.

```java
private static final ThreadLocal<byte[]> buffer =
    ThreadLocal.withInitial(() -> new byte[8192]);
```

**Сценарий 4: «неявные» параметры в API.** Если у вас библиотека, и вы хотите «протащить» конфигурацию через все вызовы, не меняя сигнатуры методов, — `ThreadLocal`. Правда, это спорная практика: «скрытые» зависимости затрудняют понимание кода. Используйте осторожно.

### Главная опасность: утечки памяти

Вот тут начинается самое коварное. `ThreadLocal` внутри устроен так: у каждого `Thread` есть **`ThreadLocalMap`** — мапа, где ключом служит **сам `ThreadLocal`**, а значением — значение для этого потока.

**Проблема:** если `ThreadLocal` используется в **пуле потоков** (глава 4), а поток **не завершается** (он живёт долго, переиспользуется), — то **значение остаётся в памяти** даже после того, как «логически» работа с ним закончилась.

Пример: веб-сервер с пулом из 100 потоков. Каждый запрос кладёт в `ThreadLocal` данные пользователя. Запрос закончился — но поток **не завершился**, он возвращается в пул для следующего запроса. А `ThreadLocal` всё ещё хранит данные пользователя. Следующий запрос на этом потоке — увидит **чужие** данные, если не перезапишет.

Хуже: если данные большие (например, `byte[]` на мегабайт), — они **копится** в `ThreadLocalMap` каждого потока пула. 100 потоков × 1 МБ = 100 МБ памяти, которые не освобождаются. Это называется **утечка памяти через ThreadLocal**.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> если используете <code>ThreadLocal</code> в пуле потоков — <strong>всегда</strong> вызывайте <code>remove()</code> в <code>finally</code>. Иначе — утечка памяти и «протекание» данных между запросами.
</div>

### Правильный паттерн

```java
try {
    RequestContext.setUser(user);
    // ... обработка запроса
} finally {
    RequestContext.clear(); // remove() в ThreadLocal
}
```

**`remove()` обязателен.** Он удаляет значение из `ThreadLocalMap` для текущего потока. Без него — данные остаются, и следующий запрос на этом потоке их увидит.

**Почему `remove`, а не `set(null)`?** `set(null)` записывает `null` как значение. `remove()` — удаляет **запись** из мапы. С точки зрения памяти — `set(null)` всё равно оставляет запись (с ключом `ThreadLocal` и `null`-значением), что тоже «утечка», хоть и меньше. `remove()` — чистит полностью.

### ThreadLocal в пуле: типичный баг

```java
// НЕПРАВИЛЬНО
public void handleRequest(Request req) {
    RequestContext.setUser(extractUser(req));
    // ... обработка
    // забыли clear() в finally
}
```

С пулом потоков:
1. Запрос 1 (пользователь Alice) на потоке `worker-1`. `ThreadLocal` = Alice.
2. Запрос 1 закончился. `clear()` **не вызван**. Поток `worker-1` возвращается в пул.
3. Запрос 2 (пользователь Bob) на потоке `worker-1`. **До** `setUser(Bob)`, если какой-то код вызовет `getUser()` — увидит **Alice**.
4. Привет, утечка данных между пользователями.

Именно поэтому `remove()` — **в `finally`**, всегда.

### InheritableThreadLocal

`InheritableThreadLocal` — расширение, которое **передаёт** значение от родительского потока к дочернему при создании.

```java
InheritableThreadLocal<String> local = new InheritableThreadLocal<>();
local.set("parent-value");

new Thread(() -> {
    System.out.println(local.get()); // "parent-value" — унаследовано
}).start();
```

**Когда нужно:** когда дочерние потоки должны видеть «контекст» родителя — например, trace-id в асинхронных задачах.

**Когда НЕ нужно:** в пулах потоков. Потоки в пуле создаются **один раз** (при старте пула), а не при каждой задаче. Поэтому «наследование» от задачи-отправителя **не работает**: задача выполняется в потоке, который был создан давно, и его `InheritableThreadLocal` — от «родителя» пула, а не от отправителя задачи.

Для передачи контекста в асинхронных задачах используют **другие** инструменты: `CompletableFuture` с явной передачей, `TransmittableThreadLocal` (библиотека Alibaba), или structured concurrency (глава 7.3). `InheritableThreadLocal` — только для «новых» потоков, не для пулов.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> <code>InheritableThreadLocal</code> работает только для потоков, созданных <em>после</em> установки значения. В пулах потоков это не работает — потоки созданы давно. Не используйте <code>InheritableThreadLocal</code> для «передачи контекста в задачу».
</div>

### ThreadLocal vs synchronized

Сравнение на пальцах.

| | `synchronized` | `ThreadLocal` |
|---|---|---|
| Что делает | Защищает **общую** переменную | Даёт **свою** переменную каждому |
| Синхронизация | Нужна | **Не нужна** |
| Память | Одна переменная | Копия на каждый поток |
| Подходит для | Общих данных | Личных данных потока |
| Опасность | Deadlock, contention | Утечки памяти |

**Правило выбора:**

- Данные **должны быть общими** (например, счётчик запросов) → `synchronized` или `Atomic`.
- Данные **должны быть личными** (например, контекст запроса) → `ThreadLocal`.
- Не знаете → скорее всего, вам не нужен `ThreadLocal`. Он специфичен.

### Частые ошибки

**Ошибка 1: забыть `remove()` в пуле.** Самая частая и самая опасная. Утечка памяти + «протекание» данных между запросами. **Всегда** `remove()` в `finally`.

**Ошибка 2: `ThreadLocal` для «глобального состояния».** `ThreadLocal` — не «глобальная переменная». Он «личный для потока». Если данные нужны **всем** потокам — это не `ThreadLocal`.

**Ошибка 3: `ThreadLocal` как «передача параметров».** «Спрятать» параметр в `ThreadLocal`, чтобы не передавать явно — соблазнительно, но делает код непонятным. «Откуда взялся `user`?» — приходится искать по всему коду. Используйте **явную** передачу параметров. `ThreadLocal` — только для «контекста» (trace-id, user), не для бизнес-данных.

**Ошибка 4: `InheritableThreadLocal` в пуле.** Не работает. Потоки созданы давно, наследование не происходит.

**Ошибка 5: `ThreadLocal` для больших объектов.** Каждый поток держит свою копию. 100 потоков × 10 МБ = 1 ГБ. Если объект большой — используйте пул объектов или `remove()` **сразу** после использования.

**Ошибка 6: `ThreadLocal` с `static` для mutable-объекта.** Если `ThreadLocal<Map>` и вы делаете `map.get().put(...)` — вы меняете **общую** мапу (потому что `ThreadLocal` хранит **ссылку** на мапу, а мапа — одна на поток... нет, стоп. `ThreadLocal` даёт каждому потоку **свою** мапу. Но если мапа создана в `initialValue`, она **одна** для потока — и все задачи в этом потоке видят **одну и ту же** мапу. Если нужно «сбросить» между задачами — `remove()` или `set(new HashMap<>())`).

### Аналогия со шкафчиком

Вернёмся к началу. **`ThreadLocal`** — это **личный шкафчик** в раздевалке. У каждого свой, с замком. Вы кладёте туда кроссовки — сосед не видит. Он кладёт своё — вы не видите. Никакой синхронизации: у каждого свой шкафчик.

**`synchronized`** — это **общий шкафчик**. Один на всех. Нужна очередь: пока один внутри — остальные ждут. Медленно, но данные **общие**.

**`remove()`** — это **забрать вещи из шкафчика, когда уходите**. Если не забрать — следующий, кто займёт шкафчик (в пуле потоков), увидит ваши вещи. Иногда это «протекание данных» (конфиденциальность), иногда — «утечка памяти» (шкафчик занят навсегда).

**`InheritableThreadLocal`** — это **шкафчик с «наследством»**. Когда вы «порождаете» новый шкафчик (создаёте новый поток), в него **копируется** содержимое вашего. Но в пуле потоков «новые шкафчики» создаются **один раз**, а потом переиспользуются. Поэтому «наследство» — только от «создателя пула», не от «текущей задачи».

## Микрозадача 1: счётчик на ThreadLocal

**Задача:** Создайте `ThreadLocal<Integer>` с начальным значением 0. Запустите три потока, каждый 5 раз инкрементирует счётчик и печатает `[имя] значение`. Убедитесь, что каждый поток видит **свою** последовательность 1, 2, 3, 4, 5.

**Решение:**

```java
public class Main {
    private static final ThreadLocal<Integer> counter =
        ThreadLocal.withInitial(() -> 0);

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 5; i++) {
                counter.set(counter.get() + 1);
                System.out.println(Thread.currentThread().getName() + ": " + counter.get());
            }
        };

        Thread t1 = new Thread(task, "t1");
        Thread t2 = new Thread(task, "t2");
        Thread t3 = new Thread(task, "t3");
        t1.start(); t2.start(); t3.start();
        t1.join(); t2.join(); t3.join();
    }
}
```

**Возможный вывод:**

```text
t1: 1
t2: 1
t3: 1
t1: 2
t2: 2
t3: 2
t1: 3
t2: 3
t3: 3
t1: 4
t2: 4
t3: 4
t1: 5
t2: 5
t3: 5
```

**Разбор:** каждый поток видит **свою** последовательность от 1 до 5. Они не мешают друг другу — потому что у каждого **свой** `counter`. Один объект `ThreadLocal`, но три «ячейки» внутри. Это и есть «личная копия для каждого потока».

Если бы `counter` был обычным `int` (или `AtomicInteger`), значения были бы **общими**: `t1` мог бы увидеть `1, 4, 7...` — в зависимости от того, как потоки чередуются. `ThreadLocal` этого не допускает **по определению**.

## Микрозадача 2: утечка в пуле

**Задача:** Создайте `ThreadLocal<String>`, пул на 2 потока, отправьте 4 задачи. Каждая задача **не вызывает** `remove()` в `finally`. Задача 1 и 3 — устанавливают `"Alice"`, задачи 2 и 4 — **проверяют** `get()` **до** `set`. Убедитесь, что задача 4 (на том же потоке, что и задача 1) видит `"Alice"` — утечка.

**Решение:**

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class Main {
    private static final ThreadLocal<String> context = new ThreadLocal<>();

    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(2);

        // Задача 1: устанавливает Alice
        pool.execute(() -> {
            context.set("Alice");
            System.out.println("[task1] set Alice на " + Thread.currentThread().getName());
        });

        // Задача 2: проверяет — на другом потоке (пул на 2)
        pool.execute(() -> {
            System.out.println("[task2] видит: " + context.get() + " на " + Thread.currentThread().getName());
            context.set("Bob");
        });

        // Задача 3: снова устанавливает
        pool.execute(() -> {
            context.set("Charlie");
            System.out.println("[task3] set Charlie на " + Thread.currentThread().getName());
        });

        // Задача 4: проверяет — может попасть на поток с Alice
        pool.execute(() -> {
            System.out.println("[task4] видит: " + context.get() + " на " + Thread.currentThread().getName());
        });

        pool.shutdown();
        pool.awaitTermination(5, TimeUnit.SECONDS);
    }
}
```

**Возможный вывод:**

```text
[task1] set Alice на pool-1-thread-1
[task2] видит: null на pool-1-thread-2
[task3] set Charlie на pool-1-thread-1
[task4] видит: Charlie на pool-1-thread-1
```

**Разбор:** обратите внимание на задачу 4. Она выполнилась на `pool-1-thread-1` — том же потоке, что и задача 1 и 3. Задача 4 **не устанавливала** `context`, но `get()` вернул `"Charlie"` — значение, установленное задачей 3. Это **утечка** между задачами.

Если бы задача 4 обрабатывала запрос **другого** пользователя, она бы увидела данные **предыдущего** — потенциальная проблема безопасности. И память: `"Charlie"` (и `"Alice"`, и `"Bob"`) остаются в `ThreadLocalMap` потоков, пока поток жив. В пуле — вечно.

**Исправление:** `remove()` в `finally` в каждой задаче. Тогда задача 4 увидела бы `null` — чистое состояние.

## 🎯 Самостоятельная задача

Реализуйте **контекст запроса** на `ThreadLocal` с корректной очисткой.

**Постановка:**

1. Класс `RequestContext`:
   - `ThreadLocal<String> userId`, `ThreadLocal<String> traceId`, `ThreadLocal<Long> startTime`.
   - Метод `init(String userId, String traceId)` — устанавливает всё, включая `startTime`.
   - Метод `getUserId()`, `getTraceId()`, `getElapsed()` — читают.
   - Метод `clear()` — `remove()` на всех трёх.
2. Класс `RequestProcessor`:
   - Метод `process(String requestId)` — «обрабатывает запрос».
   - Имитация: спит 100 мс, печатает `[traceId] [userId] requestId (elapsed=100ms)`.
   - `init` в начале, `clear` в `finally`.

**Тесты:**

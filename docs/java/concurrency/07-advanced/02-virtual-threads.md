# 7.2. Виртуальные потоки

## Где вы это уже видели

**Официант и кухня.** В ресторане работает один официант. Он принимает заказ у столика, относит его на кухню и... **не стоит над поваром**, ожидая, пока блюдо приготовится. Он идёт к следующему столику. Когда блюдо готово — повар зовёт, официант забирает и несёт. Один официант обслуживает двадцать столов, потому что **не ждёт** впустую. Платформенный поток — это официант, который стоит у кухни, пока не приготовят. Виртуальный поток — это официант, который обслуживает другие столики, пока кухня работает.

**Диспетчерская.** Один диспетчер принимает заявки. Принял — передал бригаде, сам взял следующую. Бригад много, диспетчер один. Диспетчер — это **носитель** (carrier). Бригады — это **виртуальные потоки**. Бригада работает, диспетчер ждёт от неё результата, потом берёт следующую заявку. Если бригада застряла, диспетчер не ждёт — он берёт другую заявку, а к застрявшей вернётся, когда та освободится.

**Библиотека с одним библиотекарем.** Один библиотекарь. Читатель просит книгу — библиотекарь идёт в хранилище, ищет. Пока ищет — другой читатель ждёт. Плохо. А в хорошей библиотеке: библиотекарь принял заявку, передал в хранилище, вернулся к следующему читателю. Хранилище ищет книги параллельно. Один библиотекарь обслуживает сотню читателей, потому что **не ждёт** в хранилище.

**Очередь в поликлинике.** В регистратуре один человек. Пришёл пациент — завели карточку, отправили к врачу. Врач занят — пациент ждёт в коридоре. Регистратор **не идёт** с пациентом к врачу и не стоит под дверью. Он обслуживает следующего. Врачи — это «носители». Пациенты — «виртуальные потоки». Регистратор — «планировщик».

**Общее во всех случаях** одно: есть **дорогой ресурс** (официант, диспетчер, библиотекарь, регистратор), и есть **много дешёвых задач**, которые большую часть времени **ждут**. Дорогой ресурс **переключается** между задачами, не тратя время на ожидание. Это и есть идея виртуальных потоков: **дешёвые потоки, которые ждут, не занимая дорогой поток ОС**.

## Теория

### Проблема платформенных потоков

До сих пор мы работали с **платформенными потоками** — теми, что создаются через `new Thread()`. Каждый такой поток — это **поток операционной системы**. А ОС-потоки дорогие.

**Память:** по умолчанию 1 МБ стека на поток. 10 000 потоков — 10 ГБ. Не влезает.

**Создание:** системный вызов, сотни микросекунд. 10 000 потоков — секунды на создание.

**Переключение:** десятки микросекунд. Если потоков больше, чем ядер, — процессор тратит время на переключения, а не на работу.

**Главная проблема:** если поток **ждёт** (сеть, диск, база) — он **занимает** дорогой ресурс ОС, ничего не делая. Поток «спит», но ОС-поток «занят». 10 000 одновременных HTTP-запросов — 10 000 ОС-потоков, каждый ждёт ответа. Память кончилась, процессор переключается, а полезной работы — ноль.

Именно поэтому мы строили пулы (глава 4): **ограничивали** число потоков, чтобы не утонуть. Но пул — это компромисс: задач больше, чем потоков, задачи ждут в очереди. Для I/O-bound задач это означает: «пока 10 потоков ждут сеть, остальные 990 задач стоят в очереди».

Виртуальные потоки решают эту проблему **иначе**.

### Идея виртуальных потоков

Виртуальный поток — это поток, которым управляет **JVM**, а не операционная система. Он **не привязан** к ОС-потоку на всё время жизни. Когда виртуальный поток блокируется (ждёт сеть), JVM **снимает** его с ОС-потока («размонтирует») и **освобождает** ОС-поток для других виртуальных потоков.

**Ключевая схема:**

1. Есть **пул носителей** (carrier threads) — обычные ОС-потоки, обычно по одному на ядро.
2. Виртуальные потоки **выполняются на носителях**.
3. Когда виртуальный поток блокируется — он **размонтируется** с носителя. Носитель свободен, может взять другой виртуальный поток.
4. Когда блокировка завершается — виртуальный поток **монтируется** на любой свободный носитель и продолжает.

Это как **один официант на двадцать столов**: пока кухня готовит, официант обслуживает другие столы. Один ОС-поток обслуживает тысячи виртуальных.

### Создание виртуальных потоков

Три основных способа.

**Способ 1: `Thread.ofVirtual()`** — прямой, как `new Thread()`.

```java
Thread virtual = Thread.ofVirtual().start(() -> {
    System.out.println("Я в виртуальном потоке");
});
virtual.join();
```

**Способ 2: `Thread.ofVirtual().name(...)`** — с именем.

```java
Thread virtual = Thread.ofVirtual()
    .name("my-virtual")
    .start(() -> System.out.println("Работаю"));
```

**Способ 3: `Executors.newVirtualThreadPerTaskExecutor()`** — «пул», который создаёт **новый виртуальный поток на каждую задачу**.

```java
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    Future<?> future = executor.submit(() -> System.out.println("Задача"));
    future.get();
}
```

**Важно:** `newVirtualThreadPerTaskExecutor()` — это **не** пул с фиксированным числом потоков. Это «исполнитель», который на каждую задачу создаёт **новый** виртуальный поток. Это **нормально** и **правильно**: виртуальные потоки дешёвые, их можно создавать миллионами.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> для виртуальных потоков <em>не нужен</em> пул фиксированного размера. Создавайте новый поток на каждую задачу. Это и есть правильный паттерн. Пул с ограничением — для платформенных потоков, где потоки дорогие.
</div>

### Где виртуальные потоки дают выигрыш

Главное правило: **I/O-bound задачи — да, CPU-bound — нет**.

**I/O-bound:** задача большую часть времени **ждёт** (сеть, диск, база). Виртуальный поток размонтируется на время ожидания, носитель свободен. Можно запустить миллион виртуальных потоков, и все будут «ждать» одновременно, занимая лишь несколько носителей.

**CPU-bound:** задача **считает** (сложные вычисления, шифрование). Виртуальный поток не размонтируется, пока считает, — он занимает носитель. Если запустить миллион CPU-bound виртуальных потоков на 8 носителях — они будут конкурировать за 8 носителей, как обычные потоки. Выигрыша нет, только накладные расходы на планирование.

**Правило простое:**

- Сервер, обрабатывающий тысячи HTTP-запросов → виртуальные потоки.
- Обработка изображений, шифрование, научные вычисления → платформенные потоки (пул на число ядер).

### Проблема pinning: «пришпиливание»

Вот тут начинается самое коварное. Виртуальный поток **не всегда** может размонтироваться. Есть две ситуации, когда он **пришпиливается** к носителю и **не отпускает** его, даже когда блокируется.

**Причина 1: `synchronized` (JDK 21–23).** До JDK 24, если виртуальный поток блокировался внутри `synchronized`-блока или метода — он **не мог** размонтироваться. Монитор `synchronized` привязан к носителю, и JVM не могла «перенести» владение. Виртуальный поток оставался на носителе, носитель был занят, хотя поток «спал».

**Причина 2: native-методы.** Если виртуальный поток выполняет native-метод (JNI) или foreign function, и внутри этого метода блокируется — он тоже пришпиливается. JVM не контролирует native-код и не может размонтировать поток.

**Что это значит на практике:** если в горячем пути есть `synchronized` вокруг блокирующей операции — виртуальные потоки **теряют** своё преимущество. Носители «залипают», throughput падает до уровня платформенных потоков.

**Пример катастрофы:**

```java
// ПЛОХО: synchronized вокруг блокирующей операции
public synchronized String fetchData(String url) {
    return httpClient.get(url); // блокируется на время запроса
}
```

Если тысяча виртуальных потоков вызовут `fetchData` — каждый **пришпилится** к носителю на время HTTP-запроса. Носителей всего 8 (по числу ядер). Значит, одновременно выполняются только 8 запросов, остальные 992 — ждут. Виртуальные потоки стали **пулом на 8 потоков**.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> в JDK 21–23 <code>synchronized</code> вокруг блокирующей операции <strong>убивает</strong> преимущество виртуальных потоков. В JDK 24+ (JEP 491) эта проблема <strong>решена</strong>: <code>synchronized</code> больше не пришпиливает. Но если вы на JDK 21–23 — проверяйте код на <code>synchronized</code> вокруг I/O.
</div>

### Как избежать pinning (JDK 21–23)

**Способ 1: `ReentrantLock` вместо `synchronized`.** `ReentrantLock` (глава 3.5) реализован через `AbstractQueuedSynchronizer` (AQS), который **умеет** размонтировать виртуальный поток. Замена `synchronized` на `ReentrantLock` вокруг блокирующих операций решает проблему.

```java
// ХОРОШО: ReentrantLock не пришпиливает
private final ReentrantLock lock = new ReentrantLock();

public String fetchData(String url) {
    lock.lock();
    try {
        return httpClient.get(url);
    } finally {
        lock.unlock();
    }
}
```

**Способ 2: вынести блокировку за пределы критической секции.** Если возможно, не держите блокировку во время блокирующей операции. Сначала захватите данные, отпустите блокировку, потом делайте I/O.

**Способ 3: JDK 24+.** В JDK 24 (JEP 491) `synchronized` больше не пришпиливает виртуальные потоки. Если у вас есть возможность обновиться — это лучшее решение.

### Виртуальные потоки и ThreadLocal

`ThreadLocal` (глава 7.1) работает с виртуальными потоками, но есть нюанс: **каждый виртуальный поток имеет свой `ThreadLocal`**. Если создать миллион виртуальных потоков, каждый с большим `ThreadLocal` — получите миллион копий. Память.

**Правило:** в виртуальных потоках `ThreadLocal` используйте **осторожно**, с небольшими значениями, и **всегда** `remove()`. Для больших данных — передавайте явно.

### Виртуальные потоки и пулы

Ключевое: **виртуальные потоки не нужно пулить**. Пул — это механизм **переиспользования** дорогих ресурсов. Виртуальные потоки дешёвые, их не нужно переиспользовать — создавайте новые.

**Не делайте так:**

```java
// ПЛОХО: пул виртуальных потоков с ограничением
ExecutorService pool = Executors.newFixedThreadPool(100, 
    Thread.ofVirtual().factory()); // бессмысленно
```

**Делайте так:**

```java
// ХОРОШО: новый виртуальный поток на каждую задачу
try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        executor.submit(task);
    }
}
```

### Ограничение параллелизма

Если виртуальные потоки не пулить, как ограничить число одновременных операций? Например, чтобы не завалить базу данных тысячей соединений.

**Способ 1: `Semaphore` (глава 3.3).**

```java
Semaphore dbConnections = new Semaphore(10);

public void query() throws InterruptedException {
    dbConnections.acquire();
    try {
        // запрос к базе
    } finally {
        dbConnections.release();
    }
}
```

**Способ 2: пул соединений.** Ограничивает соединения, а не потоки. Виртуальные потоки могут быть миллионами, но соединений — 10.

**Важно:** ограничение **параллелизма** и ограничение **потоков** — разные вещи. Виртуальные потоки решают проблему «дорогих потоков», но не решают проблему «дорогих ресурсов» (база, API). Для ресурсов — `Semaphore` или пул соединений.

### Аналогия с официантом и диспетчером

Вернёмся к началу. **Платформенный поток** — это **официант, который стоит у кухни** и ждёт, пока приготовят. Пока ждёт — не обслуживает другие столы. Двадцать столов — двадцать официантов. Дорого, но просто.

**Виртуальный поток** — это **официант, который принял заказ, отнёс на кухню и пошёл к следующему столу**. Когда блюдо готово — повар зовёт, официант забирает. Один официант обслуживает двадцать столов. Это и есть «размонтирование»: официант не ждёт, а переключается.

**Носитель (carrier)** — это **сам официант**, физический человек. Он один, но «обслуживает» много столов, потому что не стоит без дела.

**Pinning** — это когда официант **не может уйти** от столика. Например, гость сказал: «стой здесь, пока я не доем» — и официант стоит. Другие столы ждут. В программе — `synchronized` вокруг блокирующей операции: поток «пришпилен» к носителю.

**JDK 24+** — это когда официант **всё равно может уйти**, даже если гость сказал «стой». JVM научилась размонтировать `synchronized`.

## Микрозадача 1: создать виртуальный поток

**Задача:** Создайте виртуальный поток через `Thread.ofVirtual()`, который печатает имя и признак «виртуальный». Дождитесь завершения через `join()`.

**Решение:**

```java
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Thread virtual = Thread.ofVirtual()
            .name("my-virtual")
            .start(() -> {
                System.out.println("Имя: " + Thread.currentThread().getName());
                System.out.println("Виртуальный: " + Thread.currentThread().isVirtual());
            });
        virtual.join();
    }
}
```

**Возможный вывод:**

```text
Имя: my-virtual
Виртуальный: true
```

**Разбор:** `Thread.ofVirtual()` возвращает `Thread.Builder.OfVirtual`. `name(...)` задаёт имя. `start(...)` создаёт и запускает виртуальный поток. `isVirtual()` возвращает `true` — это признак, что поток виртуальный. `join()` ждёт завершения, как с обычным потоком.

Обратите внимание: код **почти такой же**, как с платформенным потоком. Это сделано намеренно: виртуальные потоки — это «те же потоки», только дешёвые. Переход с `new Thread()` на `Thread.ofVirtual()` — минимальный.

## Микрозадача 2: миллион виртуальных потоков

**Задача:** Создайте 1 000 000 виртуальных потоков через `Executors.newVirtualThreadPerTaskExecutor()`, каждый спит 1 секунду. Замерьте время и память. Сравните с попыткой создать 1 000 000 платформенных потоков (скорее всего, упадёт с `OutOfMemoryError`).

**Решение:**

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        long start = System.currentTimeMillis();
        try (ExecutorService executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < 1_000_000; i++) {
                executor.submit(() -> {
                    try {
                        Thread.sleep(1000);
                    } catch (InterruptedException e) {
                        Thread.currentThread().interrupt();
                    }
                });
            }
        }
        long elapsed = System.currentTimeMillis() - start;
        System.out.println("1M виртуальных потоков за " + elapsed + " мс");
    }
}
```

**Возможный вывод:**

```text
1M виртуальных потоков за ~1500 мс
```

**Разбор:** миллион виртуальных потоков, каждый спит секунду. Все «спят» одновременно, но занимают лишь несколько носителей (по числу ядер). Память — не гигабайты, а десятки мегабайт (стек виртуального потока хранится в куче и растёт по мере необходимости).

С платформенными потоками это бы не сработало: 1 000 000 × 1 МБ = 1 ТБ памяти. `OutOfMemoryError` задолго до миллиона. Виртуальные потоки **меняют правила игры** для I/O-bound задач.

3. Каждый «запрос» обрабатывается 100 мс (имитация I/O).
4. Сервер должен обработать 10 000 запросов.

**Требования:**

- Виртуальные потоки создаются на каждый запрос, **не** пулятся.
- Ограничение параллелизма через `Semaphore(200)` — не более 200 одновременных «соединений».

## Задача 1. Сравнить четыре списка

**Что комбинируется:** 5.1 (гонки), 5.3 (`CopyOnWriteArrayList`), 2.2 (`synchronized`).

Есть задача: 10 потоков-читателей итерируются по списку из 1000 элементов, 1 поток-писатель добавляет элементы. Замерьте время и поведение для четырёх вариантов:

1. **`ArrayList` без синхронизации.** Что произойдёт?
2. **`ArrayList` с `synchronized` на каждой операции** (включая итерацию — `synchronized(list) { for ... }`).
3. **`Collections.synchronizedList`** (с `synchronized` вокруг итерации).
4. **`CopyOnWriteArrayList`** (без `synchronized` вообще).

**Требования:**

- Каждый вариант запускается отдельно, в одинаковых условиях.
- Замеряйте: общее время, количество `ConcurrentModificationException` (если есть), корректность результата.
- Запустите по 5 раз, возьмите среднее.

1. Почему вариант 1 либо падает, либо даёт неверный результат?
2. Почему вариант 4 быстрее вариантов 2 и 3 на чтениях?
3. Как изменится картина, если писатель добавляет не 10 элементов, а 10000? Почему `CopyOnWriteArrayList` станет худшим выбором?

## Задача 2. Найди три ошибки

**Что комбинируется:** 5.1, 5.2, 5.4.

Вам дан код. В нём **три ошибки**, из-за которых программа либо теряет данные, либо падает, либо ведёт себя непредсказуемо. Найдите их, объясните и исправьте.

```java
import java.util.HashMap;
import java.util.Map;

public class Main {
    private static final Map<String, Integer> counters = new HashMap<>();
    private static int failed = 0;

    public static void main(String[] args) throws InterruptedException {
        Thread[] threads = new Thread[10];
        for (int i = 0; i < 10; i++) {
            int id = i;
            threads[i] = new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    String key = "key-" + (j % 100);
                    Integer current = counters.get(key);
                    if (current == null) {
                        counters.put(key, 1);
                    } else {
                        counters.put(key, current + 1);
                    }
                    if (j % 500 == 0) {
                        try {
                            throw new RuntimeException("симуляция");
                        } catch (RuntimeException e) {
                            failed++;
                        }
                    }
                }
            });
            threads[i].start();
        }
        for (Thread t : threads) t.join();
        System.out.println("Уникальных ключей: " + counters.size());
        System.out.println("Сумма значений: " + counters.values().stream().mapToInt(Integer::intValue).sum());
        System.out.println("Сбоев: " + failed);
    }
}
```

**Задумано:** 10 потоков, каждый делает 1000 инкрементов, распределённых по 100 ключам. Ожидается: сумма значений по всем ключам = 10000, сбоев — 20.

**Подсказки:**

- Одна ошибка — `HashMap` не потокобезопасна. `get` + `put` — не атомарно. Даже в одном ключе будут потери.
- Вторая — `failed` не защищён. `failed++` — не атомарно, часть инкрементов потеряется.
- Третья — размер `HashMap` под нагрузкой может стать некорректным (или даже «зациклиться» в старых версиях Java, но в Java 8+ — просто потеря данных).

## Задача 3. Кеш с ленивой загрузкой

**Что комбинируется:** 5.2 (`ConcurrentHashMap`, `computeIfAbsent`), 2.6 (атомарные классы).

Реализуйте **кеш пользователей** с ленивой загрузкой из «базы».

**Постановка:**

1. Класс `UserRepository`:
   - `ConcurrentHashMap<String, User>` внутри.
   - Метод `User getUser(String id)` — использует `computeIfAbsent` с функцией `loadFromDb(id)`.
   - `loadFromDb(id)` — спит 200 мс (имитация) и возвращает `new User(id, "User-" + id)`.
   - Ведёт счётчик **фактических** загрузок (не попаданий) через `AtomicInteger`.
2. Метод `invalidate(String id)` — удаляет пользователя из кеша.
3. Метод `size()` — сколько сейчас в кеше.

**Тесты:**

1. **Один поток:** 1000 раз запрашивает `"user:1"`. Должна быть **одна** загрузка.
2. **10 потоков:** все одновременно запрашивают `"user:1"`. Тоже **одна** загрузка (благодаря `computeIfAbsent`).
3. **10 потоков:** каждый запрашивает свой ключ (`"user:1"` ... `"user:10"`). Должно быть 10 загрузок, и все — параллельно (общее время ~200 мс, а не 2000).
4. **`invalidate`:** загрузили, инвалидировали, загрузили снова — две загрузки.

**Дополнительно:** что произойдёт, если внутри `computeIfAbsent` бросить `RuntimeException`? Кеш останется консистентным? Проверьте.

## Задача 4. Producer-consumer с завершением

**Что комбинируется:** 5.4 (`BlockingQueue`), 3.1 (`CountDownLatch`), 1.6 (прерывания).

Реализуйте **конвейер обработки заказов** с корректным завершением.

**Постановка:**

1. `ArrayBlockingQueue<Order>(10)`.
2. **Три producer-потока:** каждый кладёт 20 заказов с паузой 50 мс, потом **завершается**. Кладёт `put`.
3. **Два consumer-потока:** каждый забирает заказы через `take`, обрабатывает 100 мс, логирует. **Не знают заранее**, сколько заказов всего — должны завершиться, когда производители закончили.
4. Использовать `CountDownLatch(3)` для производителей — сигнал «все положили».
5. После `latch.await()` главный поток ждёт, пока очередь **опустеет**, потом посылает **poison pill** (специальный заказ-маркер) — по одному на каждого consumer.
6. Consumers, увидев poison pill, завершаются.

**Требования:**

- Каждый consumer обрабатывает ровно столько, сколько всего было (60 / 2 = 30, но фактически может быть неравномерно).
- Суммарно: обработано = 60, потеряно = 0, зависаний = 0.

**Дополнительно:** замените poison pill на `volatile boolean stopped` + `poll(100ms)` с проверкой флага. Сравните поведение.

**Вопросы в комментарии:**

1. Почему нельзя просто закрыть очередь (`BlockingQueue` не имеет `close`)?
2. Почему `CountDownLatch` даёт «правильную» точку для сигнала завершения?
3. Почему poison pill на **каждого** consumer — а не один общий?

## Задача 8. Резюме в одном приложении

**Что комбинируется:** всё.

Напишите **систему логирования с буферизацией**, которая демонстрирует все структуры модуля.

**Сценарий:**

1. **`ConcurrentLinkedQueue<String>`** — «горячий буфер» для быстрых логов. Приложения пишут сюда через `offer` без блокировки.
2. **`ArrayBlockingQueue<String>(100)`** — «медленный буфер» для записи на диск.
3. **`ConcurrentHashMap<String, Integer>`** — счётчики по уровню (`INFO`, `WARN`, `ERROR`).
4. **`CopyOnWriteArrayList<LogListener>`** — список слушателей, которым нужно дублировать `ERROR`-логи.
5. **`LinkedBlockingDeque<String>(50)`** — очередь для `ERROR`-логов с приоритетом (высокий в голову).

**Архитектура:**

- 3 приложения-генератора пишут логи в «горячий буфер».
- 1 поток-переносчик: `poll` из горячего, `put` в медленный (с обработкой переполнения).
- 1 поток-писатель: `take` из медленного, «пишет на диск» (спит 10 мс).
- 1 поток-алертер: забирает `ERROR`-логи из deque и уведомляет слушателей.
- Периодически (раз в секунду) — печать статистики: сколько логов каждого уровня, сколько в каждом буфере.

**Требования:**

- Никто не блокируется на «горячем» пути.
- `ERROR`-логи обрабатываются приоритетно (через deque).
- Корректное завершение всех потоков.
- В конце — сводка: всего логов, по уровням, потеряно (если переполнялись буферы).

**Что проверяется:** умение собрать несколько коллекций в связную систему, не перепутать семантику.

## 🎯 Проектное задание. Потокобезопасный кеш с TTL и приоритетами

Это задание сложнее предыдущих. Оно не про конкретную структуру, а про **дизайн**.

### Постановка

Реализуйте `SmartCache<K, V>`, который сочетает все структуры модуля.

1. **Основное хранилище** — `ConcurrentHashMap<K, CacheEntry<V>>`.
   - `CacheEntry` содержит `value`, `createdAt`, `lastAccess`, `priority` (`LOW`, `NORMAL`, `HIGH`).
2. **TTL:** записи старше `ttlMillis` считаются устаревшими.
3. **LRU-вытеснение** при переполнении: если размер > `capacity`, вытесняется запись с самым старым `lastAccess` — но только среди `LOW`-приоритетных. Записи `HIGH` не вытесняются никогда.
4. **Метрики:** `hits`, `misses`, `evictions`, `expirations` — через `AtomicLong`.
5. **Фоновый `cleaner`** — `ScheduledExecutorService`, раз в 100 мс удаляет истёкшие записи.
6. **Метод `get(K)`:** атомарный `computeIfAbsent` с проверкой TTL. Если запись истекла — удаляется и загружается заново.
7. **Метод `put(K, V, Priority)`:** если размер превышен — вытеснение по LRU среди `LOW`.
8. **Метод `snapshot()`:** возвращает `ConcurrentSkipListMap<Long, List<K>>` — снимок по `createdAt` для дебага.
9. **Метод `invalidate(K)`**, **`invalidateAll()`**.

### Требования к реализации

- Все операции — потокобезопасны.
- `get` использует `computeIfAbsent` — одна загрузка на ключ.
- Вытеснение — под блокировкой (только для `LOW`-приоритетных), чтобы не вытеснить «половину» и не оставить кеш в неконсистентном состоянии.
- `cleaner` — демон, корректно завершается по `interrupt`.

### Тесты

1. **Базовые:** 1000 `put`, 1000 `get` — все значения корректны, метрики сходятся.
2. **TTL:** положили, подождали `ttl * 2`, `get` — должен вернуть `null` или загрузить заново.
3. **LRU:** `capacity = 10`, положили 15 `LOW`-записей. Три самые старые по `lastAccess` вытеснены. `HIGH`-записи не тронуты.
4. **Под нагрузкой:** 10 потоков делают случайные `get`/`put` в течение 5 секунд. Никаких `ConcurrentModificationException`, кеш консистентен, метрики корректны.

### Задание со звёздочкой

1. Как реализовать LRU **эффективно** без обхода всей мапы на каждое вытеснение? (Подсказка: `ConcurrentLinkedDeque` с `lastAccess`, но нужна аккуратность — стандартные структуры не дают «LRU из коробки».)
2. Как бы вы реализовали **приоритетное вытеснение** — сначала вытеснять `LOW`, потом `NORMAL`, а `HIGH` — только в крайнем случае?
3. Что произойдёт, если `cleaner` не успевает за частотой истечения записей? Как это отследить?
4. Зачем нужен `snapshot()` через `ConcurrentSkipListMap`? Почему не хватает просто `entrySet()`?

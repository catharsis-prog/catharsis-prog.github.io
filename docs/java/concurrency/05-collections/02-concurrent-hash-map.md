# 5.2. ConcurrentHashMap

## Где вы это уже видели

**Библиотечный каталог.** В большой библиотеке — тысячи книг, и каталог, где они записаны. Читатели приходят постоянно: одни ищут книги, другие возвращают, третьи — новые поступления. Если бы каталог был один на всех и обновлялся целиком — у стойки стояла бы очередь. А в хорошей библиотеке каталог разбит на разделы: пока библиотекарь обновляет раздел «История», вы можете искать в разделе «Физика», и никто никому не мешает.

**Википедия.** Тысячи редакторов одновременно правят статьи. Если бы каждая правка блокировала всю Википедию — она бы не работала. Но правки в разные статьи не мешают друг другу, а в одну и ту же — обрабатываются по очереди. Именно так устроен `ConcurrentHashMap`: разные ключи — параллельно, один ключ — последовательно.

**База данных с блокировками по строкам.** В хорошей СУБД, когда вы обновляете запись клиента №42, блокируется не вся таблица «клиенты», а только строка №42. Остальные сто тысяч клиентов продолжают работать. Это называется **fine-grained locking** — «мелкозернистая блокировка». `ConcurrentHashMap` делает то же самое: блокирует не всю мапу, а отдельные бакеты.

**Многополосная касса.** В супермаркете пять касс. Покупатели распределяются по кассам. Пока на одной кассе пробивают товары — на других тоже идёт работа. Не нужно ждать одну общую. Только когда надо «посчитать общую выручку», кассиры синхронизируются — но это редкая операция.

**Общее во всех случаях** одно: **разделение на независимые части** позволяет работать параллельно. `HashMap` — это один каталог, одна касса, одна таблица. `ConcurrentHashMap` — это много каталогов, много касс, много строк. Отсюда и производительность, и безопасность.

## Теория

### Зачем нужна отдельная мапа

В главе 5.1 мы говорили: `HashMap` не потокобезопасен. `Collections.synchronizedMap` — заплатка: синхронизирует каждый метод, но составные операции не атомарны, а чтения сериализуются.

`ConcurrentHashMap` решает обе проблемы. И делает это не «обёрткой», а **другой структурой данных**. Внутри она устроена так, чтобы:

1. **Чтения не блокировались вообще.** `get()` работает без всяких блокировок. Это достигается за счёт того, что внутренние структуры устроены так, что читатель всегда видит консистентное состояние (или, по крайней мере, не падает).
2. **Записи блокировали только свою часть.** Два потока, пишущие в разные ключи, не мешают друг другу.
3. **Составные операции были атомарны.** `putIfAbsent`, `compute`, `merge` — гарантированно атомарны, даже если внутри них несколько шагов.

### Как она устроена

В Java 8+ `ConcurrentHashMap` внутри — это массив бакетов (как у `HashMap`), но с двумя важными отличиями.

**Первое: вместо `null`-ов в пустых бакетах — CAS-операции.** Когда поток хочет положить первый элемент в пустой бакет, он использует **compare-and-swap** (из главы 2.6). Если бакет всё ещё пуст — кладёт. Если кто-то уже положил — повторяет попытку. Никаких блокировок на этом этапе.

**Второе: когда бакет уже не пуст, используется `synchronized` на первой ноде бакета.** Это **мелкозернистая блокировка**: блокируется только этот бакет, остальные доступны. Потоки, работающие с другими бакетами, не мешают.

Визуально:

```text
ConcurrentHashMap
┌─────┬─────┬─────┬─────┬─────┬─────┬─────┬─────┐
│ [0] │ [1] │ [2] │ [3] │ [4] │ [5] │ [6] │ [7] │
└──┬──┴──┬──┴──┬──┴──┬──┴──┬──┴──┬──┴──┬──┴──┬──┘
   │     │     │     │     │     │     │     │
   ▼     ▼     ▼     ▼     ▼     ▼     ▼     ▼
  ...   ...   ...   ...   ...   ...   ...   ...

Поток A пишет в бакет 2 — блокирует только бакет 2.
Поток B пишет в бакет 5 — блокирует только бакет 5.
Поток C читает бакет 7 — вообще без блокировки.

Потоки A и B не мешают друг другу.
```

Это и есть **fine-grained locking**: блокировки на уровне бакетов, а не на уровне всей мапы.

### Атомарные операции

Вот главное, что даёт `ConcurrentHashMap` помимо потокобезопасности. Пять операций, которые **гарантированно атомарны** — то есть между «прочитать» и «записать» никто не вклинится.

**`putIfAbsent(key, value)`** — «положи, если ключа нет». Атомарно. Возвращает предыдущее значение (или `null`, если ключа не было).

```java
map.putIfAbsent("user:42", new User("Alice"));
```

Классическое применение — «инициализировать, если ещё не инициализировано». Без `ConcurrentHashMap` пришлось бы делать `if (!map.containsKey(key)) map.put(key, value)` — а это **не атомарно**, и два потока могли бы оба пройти проверку и оба положить.

**`computeIfAbsent(key, mappingFunction)`** — «вычисли и положи, если ключа нет». Атомарно. Функция вызывается **один раз** для данного ключа (если ключ не появится).

```java
map.computeIfAbsent("user:42", k -> loadUserFromDb(k));
```

Классическое применение — **ленивая инициализация**. Дорогая операция (например, запрос в базу) выполняется только один раз, даже если десять потоков одновременно попросили этот ключ.

**`compute(key, remappingFunction)`** — «вычисли новое значение на основе старого (или `null`), атомарно». Функция получает `(key, oldValue)`, возвращает новое значение. Если вернёт `null` — ключ удаляется.

```java
map.compute("counter", (k, v) -> v == null ? 1 : v + 1);
```

Классическое применение — **атомарный инкремент** значения в мапе.

**`merge(key, value, remappingFunction)`** — «если ключа нет — положи `value`; если есть — примени функцию к старому и новому». Атомарно.

```java
map.merge("counter", 1, Integer::sum);
```

Это короче, чем `compute`, и семантически понятнее: «добавь 1 к значению по ключу».

**`replace(key, oldValue, newValue)`** — «замени, если текущее значение равно `oldValue`». Атомарно.

```java
map.replace("status", "PENDING", "DONE");
```

Классическое применение — **оптимистичная блокировка**: меняем только если состояние не изменилось.

### Почему computeIfAbsent — это важно

Покажем на примере. Классическая задача: кеш, который загружает значение из базы при первом обращении.

**Наивный вариант (с гонкой):**

```java
public User getUser(String id) {
    User user = cache.get(id);
    if (user == null) {
        user = loadFromDb(id); // может выполниться несколько раз
        cache.put(id, user);
    }
    return user;
}
```

Если десять потоков одновременно запросят `user:42`, все десять увидят `null`, все десять пойдут в базу, все десять положат в кеш. База получит **десять запросов** вместо одного. Для дорогого запроса — катастрофа.

**С `computeIfAbsent`:**

```java
public User getUser(String id) {
    return cache.computeIfAbsent(id, this::loadFromDb);
}
```

`computeIfAbsent` гарантирует: **для данного ключа функция выполнится ровно один раз**, даже если десять потоков пришли одновременно. Остальные девять подождут, пока первый не закончит, и получат его результат. База получит **один запрос**.

Это **огромное** преимущество. Именно из-за него `ConcurrentHashMap` — стандарт для кешей.

**Осторожно:** функция внутри `computeIfAbsent` не должна делать **долгих** операций, которые могут занять много времени. Пока она выполняется, другие потоки, работающие с **тем же ключом** (но не с другими ключами!), ждут. Если функция полезет в сеть с таймаутом в 30 секунд — все, кто ждёт этот ключ, будут ждать 30 секунд. Для ленивой инициализации это нормально, для регулярных операций — плохо.

### Чем ConcurrentHashMap отличается от synchronizedMap

Сравнение в таблице.

| | `Collections.synchronizedMap` | `ConcurrentHashMap` |
|---|---|---|
| Чтения | Блокируются | Без блокировок |
| Записи в разные ключи | Сериализуются | Параллельны |
| Составные операции | Не атомарны | Атомарны (`compute`, `merge`, ...) |
| Итерация | Требует внешнего `synchronized` | Слабо консистентна, работает без `synchronized` |
| `null` ключи и значения | Разрешены | **Запрещены** |
| Производительность под нагрузкой | Низкая | Высокая |

Обратите внимание на две вещи.

**Первое: `null` не разрешён.** Ни ключи, ни значения. Причина — в том, что `null` используется внутри как маркер «ключа нет». Если бы пользователь мог положить `null`, это сломало бы внутреннюю логику.

**Второе: итерация — слабо консистентна.** Это значит, что итератор видит **некоторое** состояние мапы, но не обязан видеть «моментальный снимок». Если во время итерации кто-то добавит элемент — итератор **может** его увидеть, а может и не увидеть. Но `ConcurrentModificationException` **не бросит**. Это компромисс: итерация работает без блокировок и без исключений, но не даёт гарантии «замороженного» состояния.

Это **правильный** компромисс для многопоточного кода: вы обычно хотите «пройти по тому, что есть сейчас», а не «заморозить всё и пройти».

### Когда ConcurrentHashMap НЕ подходит

**Задача 1: атомарная операция над несколькими ключами.** Если нужно «перевести с баланса A на баланс B атомарно» — `ConcurrentHashMap` не поможет. Каждая операция атомарна **для одного ключа**. Между двумя операциями (списать с A, зачислить на B) может вклиниться другой поток. Для таких случаев — `synchronized` или `Lock` (глава 2.2, 3.5).

**Задача 2: сложные инварианты.** Если есть инвариант вида «сумма всех значений равна 1000» — `ConcurrentHashMap` его не защищает. Каждая `put` атомарна, но между ними инвариант может нарушаться. Нужна внешняя синхронизация.

**Задача 3: `null`-значения.** Если логика требует `null` — `ConcurrentHashMap` не подойдёт. Придётся использовать `Collections.synchronizedMap` или обёртку (`Optional`, специальный маркер).

**Задача 4: очень маленькая мапа.** Для 10 элементов и низкой конкуренции разница в производительности ничтожна, а `ConcurrentHashMap` требует больше памяти. Не «на всякий случай» — только когда есть реальная конкуренция.

### Производительность: немного чисел

Не буду приводить точные цифры — они зависят от машины и нагрузки. Но порядок такой.

- **Чтения.** `ConcurrentHashMap.get()` — практически такая же скорость, как `HashMap.get()`. Никаких блокировок.
- **Записи в разные ключи.** Линейно масштабируется с числом потоков (до определённого предела).
- **Записи в один ключ.** Сериализуются, как и ожидалось.
- **`computeIfAbsent`.** Немного медленнее `get`, но атомарно. Обычно окупается.
- **Итерация.** Быстрая, без блокировок, но «слабо консистентная».

`Collections.synchronizedMap` под нагрузкой — **в разы** медленнее. Особенно на чтениях: каждый `get` берёт монитор, даже если мапа не меняется.

### Аналогия с библиотечным каталогом

Вернёмся к началу. **`HashMap`** — это **один общий каталог**. Один библиотекарь, одна очередь. Медленно, но в маленькой библиотеке — работает.

**`Collections.synchronizedMap`** — это **каталог с замком на всю комнату**. Пока один библиотекарь внутри — никто не войдёт. Даже если он просто читает и ничего не меняет. Очередь растёт.

**`ConcurrentHashMap`** — это **каталог, разбитый на разделы**. Каждый раздел — со своим замком. Пока библиотекарь обновляет «Историю», вы ищете в «Физике». Читатели вообще не берут замок — они просто смотрят в открытые ящики. А для «посчитать общее количество книг» есть отдельный атомарный механизм (`size()`, `mappingCount()`).

Именно так и должна работать хорошая библиотека. И именно так работает `ConcurrentHashMap`.

## Микрозадача 1: атомарный счётчик

**Задача:** Создайте `ConcurrentHashMap<String, Integer>` и десять потоков, каждый 1000 раз инкрементирует значение по ключу `"counter"`. Используйте `merge`. Убедитесь, что итоговое значение — ровно 10000.

**Решение:**

```java
import java.util.concurrent.ConcurrentHashMap;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ConcurrentHashMap<String, Integer> map = new ConcurrentHashMap<>();

        Thread[] threads = new Thread[10];
        for (int i = 0; i < 10; i++) {
            threads[i] = new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    map.merge("counter", 1, Integer::sum);
                }
            });
            threads[i].start();
        }
        for (Thread t : threads) t.join();

        System.out.println("Counter: " + map.get("counter"));
    }
}
```

**Вывод:**

```text
Counter: 10000
```

**Разбор:** `merge` атомарен. Каждый вызов «прочитать текущее, прибавить 1, записать» выполняется как единая операция. Даже если десять потоков одновременно делают `merge` по одному ключу, итог — 10000. Никаких потерь.

Если бы вы написали `map.put("counter", map.getOrDefault("counter", 0) + 1)` — это была бы **гонка**, как в главе 2.1. `getOrDefault` и `put` — две операции, между ними может вклиниться другой поток, и один инкремент потеряется.

## Микрозадача 2: ленивая инициализация через computeIfAbsent

**Задача:** Создайте `ConcurrentHashMap<String, String>` — кеш. Пять потоков одновременно запрашивают ключ `"user:42"`, каждый вызывает `computeIfAbsent` с функцией, которая спит 500 мс (имитация запроса в базу) и возвращает строку. Убедитесь, что функция выполнилась **ровно один раз**.

**Решение:**

```java
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ConcurrentHashMap<String, String> cache = new ConcurrentHashMap<>();
        AtomicInteger loadCount = new AtomicInteger(0);

        Thread[] threads = new Thread[5];
        for (int i = 0; i < 5; i++) {
            int id = i;
            threads[i] = new Thread(() -> {
                String value = cache.computeIfAbsent("user:42", k -> {
                    loadCount.incrementAndGet();
                    System.out.println("Поток " + id + " грузит из базы");
                    try { Thread.sleep(500); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                    return "Alice";
                });
                System.out.println("Поток " + id + " получил: " + value);
            });
            threads[i].start();
        }
        for (Thread t : threads) t.join();

        System.out.println("Функция выполнилась " + loadCount.get() + " раз");
    }
}
```

**Возможный вывод:**

```text
Поток 2 грузит из базы
Поток 2 получил: Alice
Поток 0 получил: Alice
Поток 1 получил: Alice
Поток 3 получил: Alice
Поток 4 получил: Alice
Функция выполнилась 1 раз
```

**Разбор:** пять потоков одновременно запросили `"user:42"`. `computeIfAbsent` гарантирует: функция выполнится **один раз**, остальные четыре потока **подождут**, пока первый закончит, и получат его результат. База получит **один** запрос, а не пять. Это и есть основное преимущество `computeIfAbsent` над наивным `get` + `put`.

Обратите внимание: `Поток 2` — это тот, кто первым успел. Не всегда нулевой. Остальные ждут. Это нормально: гарантируется «ровно один», а не «какой именно».

## 🎯 Самостоятельная задача

Реализуйте **потокобезопасный кеш пользователей** на `ConcurrentHashMap`.

**Постановка:**

1. Класс `UserCache` с `ConcurrentHashMap<String, User>` внутри.
2. Метод `getUser(String id)`:
   - Использует `computeIfAbsent` для загрузки из «базы» (имитация — `Thread.sleep(200)` + строка `"User-" + id`).
   - Логирует каждую фактическую загрузку (не попадание в кеш).
3. Метод `invalidate(String id)` — удаляет пользователя из кеша.
4. Метод `invalidateAll()` — очищает кеш.

**Тесты:**

1. Пять потоков одновременно запрашивают `"user:1"`. Убедитесь, что загрузка была **один раз**.
2. Пять потоков одновременно запрашивают **разные** ключи (`"user:1"` ... `"user:5"`). Убедитесь, что все пять загрузок идут **параллельно** (общее время ≈ 200 мс, а не 1000).
3. После загрузки `"user:1"` вызовите `invalidate("user:1")` и снова запросите — должна быть повторная загрузка.

**Дополнительно:**

- Добавьте `getUserCount()` — сколько уникальных пользователей в кеше. Используйте `mappingCount()` вместо `size()` (он возвращает `long` и лучше работает на больших мапах).
- Добавьте `getTotalLoads()` — сколько раз всего загружали. Через `AtomicInteger`.
- Сделайте так, чтобы `getUser` для несуществующего пользователя возвращал `"Unknown"`. Обработайте `null` от `computeIfAbsent` — помните, `ConcurrentHashMap` не разрешает `null`-значения.

## 📌 Что дальше

В следующей главе — **«CopyOnWriteArrayList»**. Разберём коллекцию, которая при каждой записи создаёт **новую копию** массива. Это звучит расточительно, но для определённого класса задач — «много чтений, мало записей» — даёт огромный выигрыш. А то ведь `ConcurrentHashMap` — это мапа, а нужны и списки. И для них есть свой потокобезопасный инструмент.

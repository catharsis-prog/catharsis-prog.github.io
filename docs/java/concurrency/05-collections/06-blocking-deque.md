# 5.6. BlockingDeque и SynchronousQueue

## Где вы это уже видели

**Двусторонняя очередь в столовой.** Лотки ставят с одной стороны, забирают с другой. Но в хорошей столовой — не так: повар может поставить лоток **и спереди, и сзади**. Если смена заканчивается — оставшиеся лотки забирают с того конца, где удобнее. А ещё — если один лоток «застрял», его можно вынуть с любой стороны. Это `BlockingDeque` — очередь с двумя концами.

**Передача эстафетной палочки.** Два бегуна. Один передаёт, другой принимает. **Оба должны быть готовы одновременно**. Если первый ещё не добежал — второй ждёт. Если второй ещё не подошёл — первый ждёт. Передача происходит «из рук в руки», без буфера. Это `SynchronousQueue`.

**Обмен вещами на барахолке.** Вы принесли вещь, хотите обменять. Продавец принёс свою. Вы оба должны встретиться **в одной точке**, обменяться и разойтись. Если один не пришёл — второй стоит и ждёт. Это уже `Exchanger` из главы 3.4, но идея та же: **прямая передача без буфера**.

**Почта с уведомлением.** Вы отправляете письмо, а курьер **лично** вручает его получателю. Если получателя нет дома — курьер ждёт или возвращает письмо. Никакого «почтового ящика» посередине. `SynchronousQueue` работает именно так: `put` не завершится, пока кто-то не сделает `take`.

**Общее во всех случаях** одно: либо есть **два конца**, с которых можно класть и брать, либо **нет буфера** — передача происходит напрямую, «из рук в руки». Это две разные структуры: `BlockingDeque` (два конца) и `SynchronousQueue` (без буфера). Обе — из семейства `BlockingQueue`, но с необычной семантикой.

## Теория

### BlockingDeque: очередь с двумя концами

`BlockingDeque<E>` — интерфейс, расширяющий `BlockingQueue<E>` и `Deque<E>`. Это **двусторонняя блокирующая очередь**. Можно класть и брать **с обоих концов**, и все операции могут блокироваться.

**Основные методы** (помимо унаследованных от `BlockingQueue`):

- **`putFirst(E)`** — кладёт в голову. Блокируется, если очередь полна.
- **`putLast(E)`** — кладёт в хвост. Блокируется, если полна.
- **`takeFirst()`** — берёт из головы. Блокируется, если пусто.
- **`takeLast()`** — берёт из хвоста. Блокируется, если пусто.
- **`offerFirst(E)`**, **`offerLast(E)`**, **`pollFirst()`**, **`pollLast()`** — неблокирующиеся версии.
- **`offerFirst(E, timeout, unit)`** — с таймаутом.

Также есть **`getFirst()`**, **`getLast()`** — но они не блокируются, а бросают `NoSuchElementException`, если пусто. Обычно не используются — лучше `takeFirst`/`takeLast`.

### LinkedBlockingDeque

Единственная стандартная реализация — `LinkedBlockingDeque<E>`. Внутри — **связный список** с головой и хвостом.

```java
BlockingDeque<Integer> deque = new LinkedBlockingDeque<>(100);
deque.putFirst(1);   // в голову
deque.putLast(2);    // в хвост
deque.takeFirst();   // 1
deque.takeLast();    // 2
```

**Особенности.**

**Опциональная ёмкость.** Может быть ограниченной или неограниченной (`Integer.MAX_VALUE`). Как обычно — в продакшене **всегда** ограничивайте.

**Один лок для обоих концов.** В отличие от `LinkedBlockingQueue` (два лока — для `put` и `take`), `LinkedBlockingDeque` использует **один** лок на всю очередь. Это значит, что `putFirst` и `takeLast` **не могут работать одновременно** — они сериализуются. Это цена за гибкость двух концов.

**Почему один лок?** Потому что операции с разных концов могут «пересечься»: например, `takeFirst` и `putFirst` работают с одной головой. Разделить локи на «голову» и «хвост» можно, но это сложно и не всегда даёт выигрыш. Разработчики JDK выбрали простоту.

### Зачем два конца

Может показаться, что два конца — избыточность. Зачем класть в голову, если можно в хвост? Причины две.

**Первая: work-stealing.** Классический паттерн: поток работает с **хвостом** своей очереди (кладёт и берёт), а «воры» берут с **головы**. Так «владелец» и «воры» не мешают друг другу. Именно так устроен `ForkJoinPool` (глава 4.6), хотя внутри у него своя структура — но идея та же.

**Вторая: приоритеты.** Если есть «срочные» и «обычные» задачи, срочные можно класть в голову (`putFirst`), а обычные — в хвост (`putLast`). Тогда `takeFirst` сначала заберёт срочные, а потом обычные. Без двух концов пришлось бы использовать `PriorityBlockingQueue` (глава 5.4), что сложнее и медленнее.

**Третья: LIFO-обработка.** Иногда нужно обрабатывать **последние** задачи первыми (стек). `putLast` + `takeLast` даёт стек. `putFirst` + `takeFirst` — тоже стек, но с другого конца.

### Пример: приоритетная очередь без PriorityBlockingQueue

```java
import java.util.concurrent.BlockingDeque;
import java.util.concurrent.LinkedBlockingDeque;
import java.util.concurrent.TimeUnit;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        BlockingDeque<String> queue = new LinkedBlockingDeque<>(10);

        Thread producer = new Thread(() -> {
            try {
                for (int i = 0; i < 5; i++) {
                    queue.putLast("обычная-" + i); // обычные — в хвост
                    Thread.sleep(100);
                }
                queue.putFirst("СРОЧНАЯ"); // срочная — в голову
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread consumer = new Thread(() -> {
            try {
                while (true) {
                    String item = queue.pollFirst(1, TimeUnit.SECONDS);
                    if (item == null) break;
                    System.out.println("Обрабатываю: " + item);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        producer.start();
        consumer.start();
        producer.join();
        consumer.interrupt();
        consumer.join();
    }
}
```

**Возможный вывод:**

```text
Обрабатываю: обычная-0
Обрабатываю: обычная-1
Обрабатываю: обычная-2
Обрабатываю: обычная-3
Обрабатываю: обычная-4
Обрабатываю: СРОЧНАЯ
```

Или (если срочная успела попасть в голову раньше, чем потребитель забрал очередную обычную):

```text
Обрабатываю: обычная-0
Обрабатываю: обычная-1
Обрабатываю: обычная-2
Обрабатываю: СРОЧНАЯ
Обрабатываю: обычная-3
Обрабатываю: обычная-4
```

**Разбор:** потребитель всегда берёт с головы (`pollFirst`). Обычные задачи кладутся в хвост — они обрабатываются в порядке поступления. Срочная кладётся в голову — она «перепрыгивает» очередь. Это простой способ приоритизации без `PriorityBlockingQueue`.

### SynchronousQueue: очередь без буфера

`SynchronousQueue<E>` — **очередь нулевой ёмкости**. Это звучит странно, но работает так: **каждый `put` ждёт `take`, и наоборот**. Прямая передача «из рук в руки». Без буфера.

```java
import java.util.concurrent.SynchronousQueue;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        SynchronousQueue<String> queue = new SynchronousQueue<>();

        Thread producer = new Thread(() -> {
            try {
                System.out.println("Производитель: кладу 'hello'");
                queue.put("hello"); // ждёт, пока кто-то заберёт
                System.out.println("Производитель: 'hello' передан");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread consumer = new Thread(() -> {
            try {
                Thread.sleep(1000); // подождём, чтобы показать блокировку
                System.out.println("Потребитель: забираю");
                String value = queue.take(); // ждёт, пока кто-то положит
                System.out.println("Потребитель: получил '" + value + "'");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        producer.start();
        consumer.start();
        producer.join();
        consumer.join();
    }
}
```

**Возможный вывод:**

```text
Производитель: кладу 'hello'
Потребитель: забираю
Потребитель: получил 'hello'
Производитель: 'hello' передан
```

**Разбор:** производитель вызвал `put` — и **заблокировался**. Потребитель через секунду вызвал `take` — и они «встретились». Значение передано напрямую. Оба разблокировались одновременно.

**Ключевая идея:** `SynchronousQueue` **не хранит элементы**. Она только «сводит» производителя и потребителя. Каждый `put` «встречается» с `take`. Если пары нет — `put` или `take` ждут.

### Свойства SynchronousQueue

**Ёмкость — ноль.** `size()` всегда `0` (или около того). `isEmpty()` всегда `true`. Это не баг — это семантика.

**Нет `peek`.** Смотреть нечего — элемента нет, пока кто-то не передаёт. `peek()` возвращает `null` всегда.

**`offer` и `poll` не блокируются.** `offer(e)` вернёт `true`, если **сразу** нашёлся потребитель, `false` — если нет. `poll()` вернёт элемент, если **сразу** нашёлся производитель, `null` — если нет.

**Справедливость.** Конструктор `new SynchronousQueue<>(true)` — справедливый режим, FIFO для ждущих. По умолчанию — несправедливый.

**Производительность.** Очень быстрая для «прямой передачи», потому что нет буфера и, следовательно, нет копирования.

### Где SynchronousQueue используется

**`newCachedThreadPool`.** Из главы 4.2: пул неограниченного размера с `SynchronousQueue`. Каждая задача либо сразу передаётся свободному потоку, либо под неё создаётся новый. Буфера нет — задачи не копятся.

**Handoff-паттерн.** Когда один поток передаёт работу другому и **ждёт**, пока тот её примет. Например, «поток-производитель» и «поток-потребитель», где производитель не должен «убегать вперёд» — он ждёт, пока потребитель не заберёт.

**Синхронизация двух потоков.** Иногда нужно, чтобы два потока «встретились» в одной точке, обменялись данными и разошлись. Это можно сделать через `SynchronousQueue`, но проще через `Exchanger` (глава 3.4).

### SynchronousQueue vs Exchanger

Обе «встречают» два потока, но есть различия.

| | `SynchronousQueue` | `Exchanger` |
|---|---|---|
| Потоков | Много (любые пары) | Ровно 2 |
| Что передаётся | Только от `put` к `take` (односторонне) | Оба обмениваются (двусторонне) |
| Возврат значения | `take` возвращает, `put` — нет | Оба возвращают |
| Применение | Handoff, пул потоков | Обмен буферами, crossover |

`SynchronousQueue` — **односторонняя** передача: производитель кладёт, потребитель берёт. `Exchanger` — **двусторонний** обмен: оба отдают и получают.

### Ограничения SynchronousQueue

**Ограничение 1: нет буфера.** Если производитель быстрее потребителя — он **блокируется** на каждом `put`. Это может быть преимуществом (обратное давление), а может — проблемой (производитель простаивает).

**Ограничение 2: `size()` бесполезен.** Всегда `0`. Нельзя «посмотреть, сколько в очереди».

**Ограничение 3: `peek()` бесполезен.** Всегда `null`.

**Ограничение 4: нет итерации.** Нечего итерировать.

**Ограничение 5: только для «прямых» сценариев.** Если нужна буферизация — `SynchronousQueue` не подойдёт.

### Сравнение всех очередей

| Очередь | Ёмкость | Блокировки | Концы | Применение |
|---|---|---|---|---|
| `ArrayBlockingQueue` | Фикс. | Да | 1 | Обычный producer-consumer |
| `LinkedBlockingQueue` | Огранич. | Да (2 лока) | 1 | Высокая конкуренция |
| `PriorityBlockingQueue` | Неогр. | Да | 1 | По приоритету |
| `LinkedBlockingDeque` | Огранич. | Да (1 лок) | 2 | Приоритеты, work-stealing |
| `SynchronousQueue` | 0 | Да | — | Прямая передача |
| `DelayQueue` | Неогр. | Да | 1 | Отложенные задачи |
| `ConcurrentLinkedQueue` | Неогр. | Нет | 1 | «Положил и забыл» |
| `ConcurrentLinkedDeque` | Неогр. | Нет | 2 | Work-stealing без блокировок |

### Частые ошибки

**Ошибка 1: `SynchronousQueue` для producer-consumer с буфером.** Если производитель и потребитель работают с разной скоростью — `SynchronousQueue` заставит их **синхронизироваться на каждой передаче**. Медленно. Для буфера — `ArrayBlockingQueue` или `LinkedBlockingQueue`.

**Ошибка 2: `LinkedBlockingDeque` для «обычной очереди».** Если нужен только один конец — `LinkedBlockingQueue` быстрее (два лока). `LinkedBlockingDeque` — только когда действительно нужны оба конца.

**Ошибка 3: `putFirst` для срочных задач без проверки порядка.** Если потребитель берёт через `takeLast` (а не `takeFirst`), срочная задача окажется **последней**. Убедитесь, что концы согласованы.

**Ошибка 4: неограниченная `LinkedBlockingDeque`.** Та же мина, что и везде. Всегда ограничивайте.

**Ошибка 5: `SynchronousQueue.size()` для логики.** Всегда `0`. Не используйте для «сколько ждёт» — там всегда ноль.

**Ошибка 6: `SynchronousQueue` в `newCachedThreadPool` под нагрузкой.** Пул создаёт поток под каждую задачу, если нет свободных. Под пиковой нагрузкой — тысячи потоков. Это известная проблема (глава 4.2), и `SynchronousQueue` — её часть.

### Аналогия с лотками и палочкой

Вернёмся к началу. **`BlockingDeque`** — это **двусторонняя лента в столовой**. Повар кладёт лотки с одного конца, забирают с другого. Но может и «подложить срочный заказ спереди», чтобы его взяли первым. Или взять «сзади», если там что-то залежалось.

**`SynchronousQueue`** — это **передача эстафетной палочки**. Первый бегун не может «положить палочку на землю и убежать». Он должен **дождаться**, пока второй не схватит. Второй не может «взять палочку из воздуха» — он должен дождаться, пока первый не передаст. Они встречаются, передают, расходятся. Никакого «буфера» между ними.

`BlockingQueue` (обычная) — это **лента с буфером**. Первый положил и убежал. Второй пришёл и забрал. Между ними может быть задержка. `SynchronousQueue` этой задержки **не допускает**.

`Exchanger` — это **обмен подарками**. Оба приносят, оба получают. Не «один отдал, другой взял», а «оба обменялись».

## Микрозадача 1: приоритеты через BlockingDeque

**Задача:** Создайте `LinkedBlockingDeque<String>(10)`. Один поток кладёт обычные задачи (`putLast`), один — срочные (`putFirst`). Потребитель берёт через `takeFirst`. Убедитесь, что срочные обрабатываются раньше обычных, которые ещё в очереди.

**Решение:**

```java
import java.util.concurrent.BlockingDeque;
import java.util.concurrent.LinkedBlockingDeque;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        BlockingDeque<String> queue = new LinkedBlockingDeque<>(10);

        Thread normal = new Thread(() -> {
            try {
                for (int i = 0; i < 5; i++) {
                    queue.putLast("обычная-" + i);
                    Thread.sleep(50);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread urgent = new Thread(() -> {
            try {
                Thread.sleep(75); // подождать, чтобы обычные накопились
                queue.putFirst("СРОЧНАЯ-1");
                Thread.sleep(75);
                queue.putFirst("СРОЧНАЯ-2");
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread consumer = new Thread(() -> {
            try {
                while (true) {
                    String item = queue.pollFirst(500, java.util.concurrent.TimeUnit.MILLISECONDS);
                    if (item == null) break;
                    System.out.println("Обрабатываю: " + item);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        normal.start();
        urgent.start();
        consumer.start();
        normal.join();
        urgent.join();
        consumer.join();
    }
}
```

**Возможный вывод:**

```text
Обрабатываю: обычная-0
Обрабатываю: обычная-1
Обрабатываю: СРОЧНАЯ-1
Обрабатываю: обычная-2
Обрабатываю: СРОЧНАЯ-2
Обрабатываю: обычная-3
Обрабатываю: обычная-4
```

**Разбор:** обычные задачи кладутся в хвост, обрабатываются по порядку. Срочные кладутся в голову — потребитель, берущий с головы (`takeFirst`), забирает их **первыми**, даже если обычные ещё в очереди. Это простой способ приоритизации без `PriorityBlockingQueue`.

## Микрозадача 2: handoff через SynchronousQueue

**Задача:** Создайте `SynchronousQueue<String>`. Производитель кладёт 3 строки с паузой 500 мс. Потребитель забирает с паузой 200 мс. Убедитесь, что производитель **блокируется** на каждом `put`, пока потребитель не заберёт.

**Решение:**

```java
import java.util.concurrent.SynchronousQueue;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        SynchronousQueue<String> queue = new SynchronousQueue<>();
        long start = System.currentTimeMillis();

        Thread producer = new Thread(() -> {
            try {
                for (int i = 1; i <= 3; i++) {
                    System.out.println("[" + (System.currentTimeMillis() - start) + "] Кладу: " + i);
                    queue.put("item-" + i);
                    System.out.println("[" + (System.currentTimeMillis() - start) + "] Передал: " + i);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread consumer = new Thread(() -> {
            try {
                for (int i = 1; i <= 3; i++) {
                    Thread.sleep(200);
                    System.out.println("[" + (System.currentTimeMillis() - start) + "] Забираю");
                    String value = queue.take();
                    System.out.println("[" + (System.currentTimeMillis() - start) + "] Получил: " + value);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        producer.start();
        consumer.start();
        producer.join();
        consumer.join();
    }
}
```

**Возможный вывод:**

```text
[5] Кладу: 1
[210] Забираю
[210] Получил: item-1
[210] Передал: 1
[210] Кладу: 2
[410] Забираю
[410] Получил: item-2
[410] Передал: 2
[410] Кладу: 3
[610] Забираю
[610] Получил: item-3
[610] Передал: 3
```

**Разбор:** обратите внимание на временные метки. Производитель положил первый элемент в 5 мс и **заблокировался**. Потребитель забрал через 205 мс (в 210). В этот момент производитель разблокировался и только тогда «передал». Потом сразу положил второй — снова заблокировался до 410 мс. И так далее.

Производитель **не может убежать вперёд**. Каждый `put` ждёт `take`. Это и есть **прямая передача**: буфера нет, элементы не копятся.

# 5.1. Почему ArrayList и HashMap не потокобезопасны

## Где вы это уже видели

**Общая тетрадь на совещании.** Секретарь ведёт протокол. А если двое начнут писать одновременно — один пишет в середину страницы, другой в конец, и когда один перевернёт страницу, второй продолжит писать на той, которую уже перевернули. Записи перепутаются, часть потеряется, а конец протокола окажется в начале. Никто не виноват — просто тетрадь не рассчитана на двоих.

**Список покупок в общем чате.** Двое пишут одновременно: «молоко», «хлеб». Оба сообщения уходят, но порядок в чате — случайный. А если один редактирует сообщение, пока другой его читает, — второй может увидеть «полуотредактированное»: половину старого, половину нового.

**Доска объявлений в подъезде.** Один вешает объявление, другой в это время пытается снять старое. Кто-то дёрнет кнопку, кто-то — лист. В итоге на доске может оказаться объявление, которое уже никто не вешал, или не оказаться того, что вешали.

**Касса супермаркета.** Одна лента, один кассир. Если двое покупателей начнут выкладывать товары одновременно — один положит свой хлеб, другой свой, а кассир посчитает что-то одно и дважды. Очередь — это механизм, который делает процесс **последовательным**. Без очереди — хаос.

**Общее во всех случаях** одно: **структура данных**, рассчитанная на одного пользователя, ломается, когда пользователей становится двое. Не потому, что она «плохая», — а потому, что её так спроектировали. `ArrayList`, `HashMap`, `HashSet` — именно такие структуры. Они прекрасны в однопоточной программе и опасны в многопоточной. Разберёмся, почему.

## Теория

### Обещание, которого нет

Когда вы пишете `list.add(x)`, вы ожидаете, что элемент добавится, размер увеличится на 1, а все предыдущие элементы останутся на месте. В однопоточной программе так и происходит.

Документация `ArrayList` этого **не обещает** для многопоточной среды. Формулировка в Javadoc примерно такая: «Если несколько потоков обращаются к `ArrayList` одновременно, и хотя бы один из них структурно модифицирует список, список должен быть синхронизирован извне».

То есть: **`ArrayList` не потокобезопасен**. Это не баг, это осознанное решение. Потокобезопасность стоит денег (блокировки, проверки), а в однопоточном коде она не нужна. Поэтому стандартные коллекции сделали быстрыми, но не защищёнными.

### Что именно ломается

Проблем несколько, и они разные.

**Проблема 1: `ConcurrentModificationException`.** Самая заметная. Один поток итерируется по списку, другой в это время добавляет элемент. Итератор видит, что структура изменилась, и бросает исключение.

```java
List<Integer> list = new ArrayList<>();
for (int i = 0; i < 1000; i++) list.add(i);

Thread reader = new Thread(() -> {
    for (Integer x : list) {
        // просто читаем
    }
});
Thread writer = new Thread(() -> {
    for (int i = 1000; i < 2000; i++) list.add(i);
});
```

Через какое-то время `reader` упадёт с `ConcurrentModificationException`. Формально это «fail-fast» поведение: лучше упасть, чем тихо прочитать мусор.

**Проблема 2: потерянные обновления.** Два потока одновременно вызывают `add()`. Внутри `add()` есть `size++` и запись в массив. Между этими операциями может вклиниться второй поток. В итоге один элемент «затрёт» другой, размер списка окажется меньше, чем должен.

**Проблема 3: порча внутренней структуры.** `ArrayList` внутри — это массив `Object[]` и поле `size`. При расширении (когда массив полон) создаётся новый массив большего размера, элементы копируются, ссылка заменяется. Если во время этого процесса другой поток читает или пишет — он может увидеть «полускопированный» массив, старую ссылку, неверный размер. В лучшем случае — исключение, в худшем — данные потеряны или прочитан мусор.

**Проблема 4: бесконечный цикл (в старых версиях HashMap).** До Java 8 `HashMap` при ресайзе мог «зациклиться»: два потока одновременно вызывали `resize()`, и один из них мог создать циклическую ссылку в связном списке бакета. После этого любое чтение ключа из этого бакета уходило в бесконечный цикл. В Java 8+ механизм изменился, и такой «зацикливания» уже нет, но другие проблемы остались.

### Почему нельзя просто «обернуть в synchronized»

Первая идея: «Давайте просто обернём все вызовы в `synchronized` — и дело с концом».

```java
synchronized (list) {
    list.add(x);
}
```

Это **работает** — в смысле, что гонок не будет, если **все** обращения к списку идут через этот монитор. Но у этого подхода три проблемы.

**Первая: легко забыть.** Один вызов без `synchronized` — и вся защита рушится. А обращений к коллекции в коде может быть много, и не все из них очевидны (например, `for (x : list)` — это тоже обращение).

**Вторая: медленно.** Блокировка на **каждое** обращение — это дорого. Даже на чтение. А читают коллекции гораздо чаще, чем пишут. Синхронизировать чтения, которые не мешают друг другу, — расточительство.

**Третья: не работает для итерации.** Даже если вы синхронизируете `add`, итерация через `for (x : list)` **не держит монитор** на всё время цикла. `ConcurrentModificationException` всё равно может возникнуть.

### Обёртки: Collections.synchronizedList и компания

В JDK есть готовые обёртки: `Collections.synchronizedList`, `synchronizedMap`, `synchronizedSet`. Они создают «декоратор», который синхронизирует каждый метод.

```java
List<Integer> syncList = Collections.synchronizedList(new ArrayList<>());
syncList.add(1); // синхронизировано
int size = syncList.size(); // тоже синхронизировано
```

Это **лучше**, чем вручную. Но у этого подхода есть ограничения.

**Ограничение 1: итерация всё равно требует внешней синхронизации.**

```java
synchronized (syncList) {
    for (Integer x : syncList) {
        // ...
    }
}
```

Без этого блока итерация может упасть с `ConcurrentModificationException`, потому что `synchronizedList` синхронизирует **отдельные методы**, а не «весь цикл».

**Ограничение 2: составные операции не атомарны.**

```java
if (!syncList.contains(x)) {
    syncList.add(x); // между contains и add может вклиниться другой поток
}
```

`contains` синхронизирован, `add` синхронизирован, но **вместе они не атомарны**. Между ними список может измениться. Это классическая «check-then-act» гонка из главы 2.1.

**Ограничение 3: медленно.** Каждый метод берёт один и тот же монитор. Даже два потока, которые только читают, — сериализуются. Для read-heavy нагрузки это плохо.

**Вывод:** `synchronizedList` и компания — это «заплатка», а не решение. Для простых случаев — сойдёт. Для реальной нагрузки — нужны специальные коллекции из `java.util.concurrent`.

### ConcurrentHashMap, CopyOnWriteArrayList, BlockingQueue

В пакете `java.util.concurrent` есть коллекции, **спроектированные** для многопоточной среды. Они не просто «обёрнуты в synchronized» — они устроены иначе, чтобы обеспечить потокобезопасность **и** производительность.

Три главных семейства.

**`ConcurrentHashMap`** — потокобезопасная замена `HashMap`. Внутри — «сегментирование» (в Java 8+ — CAS-операции на бакетах), которое позволяет разным потокам писать в разные части мапы **одновременно**. Читает — вообще без блокировок. Подробно — в главе 5.2.

**`CopyOnWriteArrayList`** — потокобезопасная замена `ArrayList` для случаев «много чтений, мало записей». При каждой записи создаёт **новую копию** массива. Читатели работают со старой копией, не блокируются. Подробно — в главе 5.3.

**`BlockingQueue`** — интерфейс для очередей, которые **блокируются**, когда пусты или полны. `ArrayBlockingQueue`, `LinkedBlockingQueue`, `PriorityBlockingQueue`, `SynchronousQueue`. Основа producer-consumer. Подробно — в главах 5.4–5.6.

### Что выбрать

Краткая шпаргалка, подробности — в следующих главах.

| Задача | Инструмент |
|---|---|
| Много чтений, редкие записи в список | `CopyOnWriteArrayList` |
| Обычная мапа под нагрузкой | `ConcurrentHashMap` |
| Очередь producer-consumer | `BlockingQueue` (любая) |
| Очередь без блокировок, но с порядком | `ConcurrentLinkedQueue` |
| Отсортированная мапа под нагрузкой | `ConcurrentSkipListMap` |
| Множество с частыми изменениями | `ConcurrentHashMap.newKeySet()` |
| Множество с редкими изменениями | `CopyOnWriteArraySet` |

### Атомарные операции в ConcurrentHashMap

Важно понимать: `ConcurrentHashMap` даёт не только «потокобезопасность» в смысле «не падает», но и **атомарные составные операции**. Об этом подробно в главе 5.2, но одну вещь стоит запомнить сейчас.

```java
map.putIfAbsent(key, value);           // атомарно: положить, если нет
map.computeIfAbsent(key, k -> f(k));   // атомарно: вычислить и положить, если нет
map.merge(key, 1, Integer::sum);       // атомарно: объединить
map.compute(key, (k, v) -> ...);       // атомарно: вычислить новое значение
```

Это **не** «синхронизированные отдельные методы». Это **истинно атомарные операции**: между «проверить» и «положить» никто не вклинится. Именно этого не хватает `Collections.synchronizedMap`.

### Аналогия с тетрадью и кассой

Вернёмся к началу. **`ArrayList` и `HashMap`** — это **общая тетрадь**. Один пишет — всё хорошо. Двое пишут — записи путаются, страницы переворачиваются не вовремя, часть теряется.

**`Collections.synchronizedList`** — это **тетрадь с замком на обложке**. Открыть может только один. Но: чтобы прочитать всю тетрадь, нужно держать замок всё время чтения (иначе кто-то перевернёт страницу). И если один читает, а второй хочет писать — второй ждёт. Даже если первый читает долго и ничего не меняет.

**`CopyOnWriteArrayList`** — это **тетрадь, которую при каждой записи перепечатывают целиком**. Дорого, но читатели работают со своей копией и не мешают. Подходит, когда читают часто, а пишут редко.

**`ConcurrentHashMap`** — это **тетрадь с отдельным замком на каждой странице**. Писать в разные страницы можно одновременно. Читать — вообще без замка. Вот это уже похоже на нормальное решение.

**`BlockingQueue`** — это **касса с лентой**. Товары (задачи) едут по ленте. Если лента пуста — кассир ждёт. Если полна — покупатель ждёт. Всё честно и упорядоченно.

## Микрозадача 1: поймать ConcurrentModificationException

**Задача:** Создайте `ArrayList`, заполните его числами от 0 до 999. Запустите два потока: один итерируется по списку, другой добавляет элементы. Убедитесь, что итерация падает с `ConcurrentModificationException`.

**Решение:**

```java
import java.util.ArrayList;
import java.util.List;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        List<Integer> list = new ArrayList<>();
        for (int i = 0; i < 1000; i++) list.add(i);

        Thread reader = new Thread(() -> {
            try {
                long sum = 0;
                for (Integer x : list) {
                    sum += x;
                    Thread.sleep(1); // замедляем, чтобы успеть поймать
                }
                System.out.println("Сумма: " + sum);
            } catch (Exception e) {
                System.out.println("reader упал: " + e.getClass().getSimpleName());
            }
        });

        Thread writer = new Thread(() -> {
            try {
                Thread.sleep(100);
                for (int i = 1000; i < 2000; i++) {
                    list.add(i);
                    Thread.sleep(1);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        reader.start();
        writer.start();
        reader.join();
        writer.join();
    }
}
```

**Возможный вывод:**

```text
reader упал: ConcurrentModificationException
```

**Разбор:** итератор `ArrayList` запоминает «версию» списка (`modCount`) при создании. При каждом `next()` он проверяет: если `modCount` изменился — значит, список модифицировали, и итератор больше не может гарантировать корректность. Бросает `ConcurrentModificationException`. Это не «ошибка», а **защитный механизм**: лучше упасть, чем тихо прочитать мусор.

Обратите внимание: `reader` не обязан упасть **каждый** раз. Если `writer` не успеет добавить элемент за время итерации — исключения не будет. Но в многопоточной среде «иногда работает» — это баг, а не «работает».

## Микрозадача 2: показать, что synchronizedList не решает всё

**Задача:** Замените `ArrayList` на `Collections.synchronizedList`. Убедитесь, что:
1. Одиночные `add` и `size` — потокобезопасны.
2. Итерация **без** внешнего `synchronized` всё равно падает.
3. Составная операция `if (!list.contains(x)) list.add(x)` — не атомарна.

**Решение:**

```java
import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        List<Integer> list = Collections.synchronizedList(new ArrayList<>());
        for (int i = 0; i < 1000; i++) list.add(i);

        // 1. Одиночные операции — потокобезопасны
        // 2. Итерация без synchronized — падает
        Thread reader = new Thread(() -> {
            try {
                for (Integer x : list) {
                    Thread.sleep(1);
                }
                System.out.println("reader: OK");
            } catch (Exception e) {
                System.out.println("reader упал: " + e.getClass().getSimpleName());
            }
        });

        Thread writer = new Thread(() -> {
            try {
                Thread.sleep(100);
                for (int i = 1000; i < 2000; i++) {
                    list.add(i);
                    Thread.sleep(1);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        reader.start();
        writer.start();
        reader.join();
        writer.join();

        // 3. Составная операция — не атомарна
        List<Integer> syncList = Collections.synchronizedList(new ArrayList<>());
        syncList.add(1);
        syncList.add(2);

        Thread t1 = new Thread(() -> {
            if (!syncList.contains(3)) {
                try { Thread.sleep(50); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                syncList.add(3);
            }
        });
        Thread t2 = new Thread(() -> {
            if (!syncList.contains(3)) {
                try { Thread.sleep(50); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                syncList.add(3);
            }
        });

        t1.start(); t2.start();
        t1.join(); t2.join();
        System.out.println("Список: " + syncList + ", размер: " + syncList.size());
    }
}
```

**Возможный вывод:**

```text
reader упал: ConcurrentModificationException
Список: [1, 2, 3, 3], размер: 4
```

**Разбор:** три вещи видны.

1. `add` и `size` действительно потокобезопасны — размер в конце корректный (4).
2. Итерация **всё равно упала** — `synchronizedList` синхронизирует отдельные методы, но не блокирует список на всё время `for`. Итератор видит изменение `modCount` и падает.
3. Оба потока проверили `contains(3)` — оба увидели `false`, оба добавили. В списке две тройки. `contains` и `add` синхронизированы, но **вместе** — нет. Между ними вклинился другой поток.

Вот почему `Collections.synchronizedList` — «заплатка». Для простых случаев хватает, для реальной нагрузки — нужны коллекции из `java.util.concurrent`.

В следующей главе — **«ConcurrentHashMap»**. Разберём главную потокобезопасную мапу: как она устроена внутри, почему читает без блокировок, какие атомарные операции даёт (`putIfAbsent`, `compute`, `merge`), и где её использовать вместо `Collections.synchronizedMap`.

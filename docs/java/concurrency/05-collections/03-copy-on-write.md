# 5.3. CopyOnWriteArrayList

## Где вы это уже видели

**Список гостей на свадьбе.** Организатор распечатал список и раздал копии всем, кто встречает гостей. Каждый встречающий сверяется со **своей** копией. Когда кто-то опаздывает и звонит «я буду», организатор **печатает новый список** и раздаёт его заново. Старые копии никуда не деваются — по ним продолжают работать те, у кого они на руках. В итоге никто не ждёт, пока «список обновится», — просто у кого-то копия чуть старее.

**Расписание электричек на вокзале.** Висит огромное табло. Раз в сутки его **перепечатывают целиком**, если что-то поменялось. Всё это время пассажиры смотрят на старую версию и не замечают, что где-то в подсобке готовят новую. Когда новую вывешивают — она появляется целиком, сразу, не «по кусочкам».

**Список задач в проекте.** У тимлида есть список активных задач. Он редко его меняет — раз в день добавит задачу, раз в день закроет. А читают его все: разработчики смотрят «что мне делать», менеджер проверяет статус, тестировщики смотрят «что тестировать». Читают постоянно, меняют редко.

**Доска почёта в школе.** Раз в месяц обновляют — снимают старые фотографии, вешают новые. Всё остальное время — на неё смотрят. Никто не пытается «вставить фотографию в середину», пока другой читает — проще **переделать всю доску целиком** за одну ночь.

**Общее во всех случаях** одно: **читают часто и многие**, а **меняют редко и понемногу**. И когда меняют — проще **сделать копию целиком**, чем возиться с блокировками на каждое чтение. Это и есть `CopyOnWriteArrayList`.

## Теория

### Идея: копирование при записи

`CopyOnWriteArrayList` — потокобезопасный список из `java.util.concurrent`. Идея простая и на первый взгляд расточительная.

**Чтения** — работают с текущим внутренним массивом **без всяких блокировок**. Просто читают. Быстро.

**Записи** (`add`, `remove`, `set`) — делают следующее:

1. Захватывают блокировку (чтобы только один поток писал одновременно).
2. Создают **новый массив** — копию старого, с учётом изменения.
3. Заменяют ссылку на внутренний массив.
4. Отпускают блокировку.

Ключевой момент: **старый массив остаётся целым**. Читатели, которые начали итерацию до замены, продолжают видеть старый массив. Читатели, которые начнут после — увидят новый. Никто никого не блокирует. Никто не видит «полуизменённое» состояние.

### Схема

```text
До записи:
   list ──▶ [A, B, C, D]    ← читатели смотрят сюда, без блокировок

Поток-писатель начинает add("E"):
   list ──▶ [A, B, C, D]    ← читатели всё ещё смотрят сюда
              │
              ▼ копирование
            [A, B, C, D, E]  ← новый массив, ещё не виден

После записи:
   list ──▶ [A, B, C, D, E] ← новые читатели видят это
            [A, B, C, D]    ← старые итераторы ещё могут по нему ходить
```

Старый массив **не удаляется**, пока на него есть ссылки из активных итераторов. Когда последний итератор завершится — сборщик мусора его уберёт.

### Когда это выгодно

`CopyOnWriteArrayList` — это **компромисс**, и он выгоден в определённых условиях.

**Выгодно, когда:**

- **Чтений в десятки и сотни раз больше, чем записей.** Читатели вообще не блокируются — это огромное преимущество.
- **Итерация — частая операция.** Итератор `CopyOnWriteArrayList` работает с **снимком** массива: во время итерации список может меняться, но итератор этого не увидит и не упадёт с `ConcurrentModificationException`.
- **Список небольшой.** Копирование массива из 10 элементов — мгновенно. Из 10 миллионов — уже заметно.
- **Список стабилен.** Например, список слушателей событий, который меняется раз в час, а события обрабатываются тысячи раз в секунду.

**Невыгодно, когда:**

- **Записей много.** Каждая запись — это копия всего массива. Тысяча записей в список из 10000 элементов — это 10 миллионов операций копирования. Катастрофа.
- **Список большой.** Копирование 100000 элементов на каждую запись — дорого.
- **Нужны атомарные составные операции.** `CopyOnWriteArrayList` даёт атомарность только для **отдельных** операций. «Проверить, что элемента нет, и добавить» — не атомарно.
- **Нужен доступ по индексу с частой модификацией.** `get(i)` работает быстро, `add(i, x)` (вставка в середину) — копирует весь массив.

### Потокобезопасные итераторы

Главное практическое преимущество — **итераторы не падают**. Сравните с `ArrayList`.

**`ArrayList`:**

```java
for (Integer x : list) {
    // если другой поток делает add — ConcurrentModificationException
}
```

**`CopyOnWriteArrayList`:**

```java
for (Integer x : list) {
    // другой поток может делать add — итерация продолжается по старому снимку
}
```

Итератор `CopyOnWriteArrayList` запоминает ссылку на массив **в момент создания** и работает с ней. Изменения списка во время итерации он **не видит**. Это называется **snapshot iterator**.

**Важно:** вы можете увидеть **устаревшие** данные. Если во время итерации кто-то добавил элемент, вы его **не увидите**. Это не баг, это семантика: «итерация по состоянию на момент начала». Если нужно видеть изменения — начинайте новую итерацию.

### Методы

`CopyOnWriteArrayList` реализует `List`, поэтому методы знакомые.

- **`add(E)`** — копирует массив, добавляет в конец, заменяет ссылку.
- **`add(int index, E)`** — копирует массив, вставляет в позицию.
- **`remove(Object)`**, **`remove(int)`** — копирует массив без элемента.
- **`set(int, E)`** — копирует массив с заменой.
- **`get(int)`** — **без блокировки**, просто читает из массива.
- **`size()`** — **без блокировки**, возвращает длину текущего массива.
- **`iterator()`** — возвращает **snapshot iterator**, работает без блокировки.

Плюс несколько специфических:

- **`addIfAbsent(E)`** — атомарно добавляет, только если элемента нет. Копирует массив, проверяет наличие, добавляет. Атомарно — то есть два потока, одновременно вызывающие `addIfAbsent(x)`, добавят `x` **ровно один раз**.
- **`addAllAbsent(Collection)`** — добавляет все элементы, которых нет в списке. Атомарно.

`addIfAbsent` — единственная «составная» атомарная операция. Остальные составные операции (`if (!list.contains(x)) list.add(x)`) **не атомарны** — как и везде.

### CopyOnWriteArraySet

Есть и `CopyOnWriteArraySet` — множество на основе `CopyOnWriteArrayList`. Внутри — список, а `add` проверяет, нет ли уже такого элемента (через `addIfAbsent`). Работает так же: много чтений, мало записей, итератор-снимок.

Применение: список слушателей событий, список подписчиков, набор констант, который редко меняется.

### Где реально используется

Классические сценарии — из реальных фреймворков и приложений.

**Список слушателей (listeners).** В UI-фреймворках, в event-bus, в системах плагинов. Слушатели добавляются редко (при старте приложения), а событий — тысячи в секунду. Каждое событие итерирует по списку слушателей. `CopyOnWriteArrayList` — идеально.

**Список подписчиков.** В системах pub-sub: подписчики добавляются/удаляются при подключении/отключении клиента (нечасто), а сообщения публикуются постоянно (часто).

**Конфигурационные списки.** Список разрешённых хостов, список доступных языков, список стран. Меняется редко, читается постоянно.

**Кеш «последних N» значений.** Если нужно хранить «историю», которую читают часто, а добавляют раз в минуту, — сойдёт.

**Внутри JDK.** Например, `javax.swing.event.EventListenerList` — по сути `CopyOnWriteArrayList`. Spring и другие фреймворки тоже используют его для списков слушателей.

### Когда не подходит

Повторю подробнее, потому что ошибка здесь обходится дорого.

**Сценарий: очередь задач.** Producer кладёт задачи, consumer забирает. Записей столько же, сколько чтений. `CopyOnWriteArrayList` **не подойдёт** — каждая `add` копирует массив. Нужна `BlockingQueue` (глава 5.4).

**Сценарий: кеш с частыми обновлениями.** Каждое обновление — копия. Если кеш на 10000 элементов обновляется 100 раз в секунду — это миллион копирований элементов в секунду. Нужен `ConcurrentHashMap` (глава 5.2).

**Сценарий: список на миллион элементов с редкими добавлениями.** Даже одно добавление в час копирует миллион элементов. Для такой структуры лучше `ConcurrentLinkedQueue` или `ConcurrentSkipListMap`, если нужен доступ по ключу.

**Сценарий: нужны атомарные составные операции.** «Найти и обновить» — не атомарно. Нужны `Lock` или специализированные структуры.

### Сравнение с другими списками

| | `ArrayList` | `synchronizedList` | `CopyOnWriteArrayList` |
|---|---|---|---|
| Чтения | Быстро, но небезопасно | Медленно (блокировка) | Быстро, без блокировки |
| Записи | Быстро, но небезопасно | Медленно (блокировка) | Медленно (копия) |
| Итерация | Может упасть | Может упасть (без внешнего synchronized) | Никогда не падает, работает со снимком |
| Много чтений, мало записей | Плохо | Плохо | **Отлично** |
| Много записей | Отлично (в одном потоке) | Плохо | **Катастрофа** |
| Память | Экономно | Экономно | Копия на каждую запись |

### Аналогия с доской почёта

Вернёмся к началу. **`ArrayList`** — это **доска, на которую все смотрят и все могут что-то прикрепить**. Пока один смотрит, другой снимает фотографию. Смотрящий может увидеть «полудоску» — половину старой, половину новой. Или вообще упасть с «ConcurrentModificationException».

**`synchronizedList`** — это **доска с верёвкой вокруг**. Чтобы посмотреть — надо зайти за верёвку. Чтобы поменять — тоже. Один вошёл — остальные ждут снаружи. Даже если он просто смотрит и ничего не трогает.

**`CopyOnWriteArrayList`** — это **доска, которую обновляют целиком**. Раз в месяц снимают все фотографии, вешают новые, вывешивают новую доску. Смотрят все одновременно, каждый видит **свою** версию — ту, что висела, когда он подошёл. Меняется доска целиком, не «по одной фотографии». Никто не ждёт, никто не падает. Просто если кто-то смотрит на старую доску — он увидит старое состояние, пока не подойдёт к новой.

## Микрозадача 1: итератор не падает

**Задача:** Создайте `CopyOnWriteArrayList`, заполните 1000 элементами. Запустите поток-читатель, который итерируется по списку с паузой 1 мс, и поток-писатель, который добавляет элементы с паузой 1 мс. Убедитесь, что читатель **не падает** с `ConcurrentModificationException`.

**Решение:**

```java
import java.util.concurrent.CopyOnWriteArrayList;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        CopyOnWriteArrayList<Integer> list = new CopyOnWriteArrayList<>();
        for (int i = 0; i < 1000; i++) list.add(i);

        Thread reader = new Thread(() -> {
            long sum = 0;
            int count = 0;
            for (Integer x : list) {
                sum += x;
                count++;
                try { Thread.sleep(1); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            }
            System.out.println("Прочитано: " + count + " элементов, сумма: " + sum);
        });

        Thread writer = new Thread(() -> {
            try {
                Thread.sleep(100);
                for (int i = 1000; i < 2000; i++) {
                    list.add(i);
                    Thread.sleep(1);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        reader.start();
        writer.start();
        reader.join();
        writer.join();
        System.out.println("Итоговый размер: " + list.size());
    }
}
```

**Возможный вывод:**

```text
Прочитано: 1000 элементов, сумма: 499500
Итоговый размер: ~1500
```

**Разбор:** `reader` начал итерацию, когда в списке было 1000 элементов. Итератор запомнил снимок массива на этот момент. `writer` добавил ещё 1000 элементов за время итерации. `reader` **не увидел** их — он работал со своим снимком. И **не упал** — `ConcurrentModificationException` здесь не бывает.

Обратите внимание на размер: около 1500, не 2000. Потому что 1000 добавил `reader` (начальные), и `writer` успел добавить сколько-то за время, пока `reader` работал. `reader` закончил примерно через секунду (1000 итераций по 1 мс), `writer` за эту секунду добавил около 900. Отсюда 1900 в списке и 1000 в снимке `reader`.

## Микрозадача 2: addIfAbsent

**Задача:** Создайте `CopyOnWriteArrayList<Integer>` с начальными элементами `[1, 2, 3]`. Запустите 10 потоков, каждый пытается добавить `3`. Через `addIfAbsent` — атомарно. Убедитесь, что `3` добавляется **ровно один раз** (и не добавляется, потому что уже есть).

**Решение:**

```java
import java.util.concurrent.CopyOnWriteArrayList;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        CopyOnWriteArrayList<Integer> list = new CopyOnWriteArrayList<>();
        list.add(1);
        list.add(2);
        list.add(3);

        Thread[] threads = new Thread[10];
        for (int i = 0; i < 10; i++) {
            threads[i] = new Thread(() -> {
                list.addIfAbsent(3);
            });
            threads[i].start();
        }
        for (Thread t : threads) t.join();

        System.out.println("Список: " + list + ", размер: " + list.size());
    }
}
```

**Вывод:**

```text
Список: [1, 2, 3], размер: 3
```

**Разбор:** `addIfAbsent` атомарен. Он захватывает блокировку, копирует массив, проверяет наличие, при необходимости добавляет и заменяет ссылку — всё под одной блокировкой. Даже если десять потоков одновременно вызывают `addIfAbsent(3)`, элемент **уже есть** в списке (начальные данные), и ни один его не добавит. Размер остаётся 3.

Если бы вы написали `if (!list.contains(3)) list.add(3)` — это была бы гонка. `contains` и `add` — две отдельные операции, между ними мог бы вклиниться другой поток. `addIfAbsent` такого не позволяет.

## 🎯 Самостоятельная задача

Реализуйте **event bus** (шину событий) на `CopyOnWriteArrayList`.

**Постановка:**

1. Класс `EventBus` с `CopyOnWriteArrayList<Listener>` внутри.
2. Интерфейс `Listener` с методом `void onEvent(Event event)`. `Event` — любой класс (например, `String`).
3. Метод `subscribe(Listener)` — подписывает.
4. Метод `unsubscribe(Listener)` — отписывает.
5. Метод `publish(Event)` — публикует событие всем подписчикам.
6. Метод `listenerCount()` — сколько сейчас подписчиков.

**Тесты:**

1. Подпишите 5 слушателей. Опубликуйте 100 событий. Каждый слушатель должен получить все 100.
2. Отпишите двух слушателей. Опубликуйте ещё 100. Оставшиеся три получают ещё 100, а отписанные — нет.
3. Параллельно: три потока публикуют события, один поток подписывает/отписывает слушателей. Убедитесь, что **никто не падает** с `ConcurrentModificationException`.

- Замерьте: 10000 `subscribe` в список из 10000 элементов. Убедитесь, что это **медленно** (потому что каждая подписка копирует массив). Сравните с `ConcurrentLinkedQueue`.

## 📌 Что дальше

В следующей главе — **«BlockingQueue и producer-consumer»**. Разберём очередь, которая умеет **блокироваться**, когда пуста или полна. Это основа паттерна producer-consumer — «один кладёт, другой забирает, никто не теряет». Познакомимся с `ArrayBlockingQueue`, `LinkedBlockingQueue`, и увидим, почему `CopyOnWriteArrayList` для очередей **не подходит**. А то ведь до сих пор у нас были коллекции для «случайного доступа», а для потоковой обработки нужен свой инструмент.

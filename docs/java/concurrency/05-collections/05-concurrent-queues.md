# 5.5. Неблокирующие очереди

## Где вы это уже видели

**Билетная касса без очереди.** В аэропорту стоят автоматы самообслуживания. Подошёл — нажал кнопку — получил талон. Никакой очереди, никакого кассира, который «сейчас занят». Если автомат занят, подходишь к следующему. А если все заняты — ждёшь, но не в общей очереди, а просто «смотришь, какой освободится». Это `ConcurrentLinkedQueue`: не блокируется, а «пробует и получает результат».

**Лента новостей.** Вы листаете Twitter. Новые посты приходят постоянно, а вы читаете с той скоростью, с какой успеваете. Лента не блокируется, когда появляется новый пост — она просто растёт. Вы берёте из неё, сколько успели. Никто не ждёт.

**База данных с MVCC.** В хорошей СУБД читатель видит «снимок» данных на момент начала транзакции. Пока он читает, писатель может добавлять новые записи — читатель их не видит и **не блокируется**. Никто никого не ждёт.

**Журнал событий.** В системе мониторинга события сыплются постоянно: запросы, ошибки, метрики. Их складывают в очередь, а обработчик забирает с той скоростью, с какой успевает. Если событий больше, чем обработчик успевает — очередь растёт, но **никто не блокируется**. Просто очередь длиннее.

**Общее во всех случаях** одно: **никто не ждёт**. Не «производитель ждёт, пока потребитель заберёт», а «производитель положил и пошёл дальше». Если очередь пуста — потребитель не ждёт, а получает `null` и **сам решает**, что делать: повторить попытку, пойти по другому пути или завершиться. Это и есть **неблокирующие** структуры.

## Теория

### Чем неблокирующая очередь отличается от BlockingQueue

`BlockingQueue` (глава 5.4) — это **сотрудничество**. Производитель и потребитель договариваются: «я подожду, пока ты не заберёшь». Это удобно, но означает блокировки: `take()` может ждать секунды, `put()` может ждать секунды. Поток в это время «спит», но занимает ресурс.

**Неблокирующая очередь** — это **отсутствие ожидания**. `offer()` всегда возвращает `true` или `false` сразу. `poll()` всегда возвращает элемент или `null` сразу. **Никогда не блокируется**. И это даёт несколько преимуществ, но и накладывает несколько ограничений.

Сравнение:

| | `BlockingQueue` | Неблокирующая очередь |
|---|---|---|
| `put` при полной | Блокируется | Возвращает `false` (или бросает) |
| `take` при пустой | Блокируется | Возвращает `null` |
| Ёмкость | Обычно ограничена | Не ограничена |
| Ожидание | Встроено | Реализуется снаружи (цикл + sleep) |
| Производительность | Хорошая | Очень хорошая под нагрузкой |
| Использование | Producer-consumer | «Положил и забыл» |

**Ключевое отличие:** `BlockingQueue` «умеет ждать», неблокирующая — «не умеет». Если вам нужно ждать (потребитель должен получить элемент, даже если очередь пуста) — это `BlockingQueue`. Если не нужно (потребитель может обработать `null` — «сейчас ничего нет, попробую позже») — неблокирующая.

### ConcurrentLinkedQueue

`ConcurrentLinkedQueue<E>` — основная неблокирующая очередь в JDK. Внутри — **связный список**, где операции `offer` и `poll` реализованы через **CAS** (compare-and-swap, глава 2.6). Никаких блокировок — только атомарные операции.

```java
import java.util.concurrent.ConcurrentLinkedQueue;

ConcurrentLinkedQueue<Integer> queue = new ConcurrentLinkedQueue<>();

queue.offer(1);           // всегда true (очередь не ограничена)
queue.offer(2);
queue.offer(3);

Integer first = queue.poll(); // 1 или null, если пусто
Integer second = queue.poll(); // 2
Integer third = queue.poll(); // 3
Integer empty = queue.poll(); // null — очередь пуста
```

**Ключевые методы:**

- **`offer(E)`** — кладёт элемент в конец. **Всегда возвращает `true`** (очередь не ограничена). Не блокируется.
- **`poll()`** — забирает элемент из головы. Возвращает `null`, если очередь пуста. Не блокируется.
- **`peek()`** — смотрит голову, не забирая. Возвращает `null`, если пусто.
- **`size()`** — **не атомарен** и **дорогой** (обходит весь список). Не используйте для синхронизации.
- **`isEmpty()`** — тоже обходит список (в старых версиях), не атомарен.

**Важно:** `size()` у `ConcurrentLinkedQueue` — **O(n)**. Это не баг, а следствие того, что внутри связный список без счётчика. Если вам нужен размер — используйте `LongAdder` или `AtomicInteger` **отдельно**, а не `size()`.

### Слабая консистентность

`ConcurrentLinkedQueue` — как и `ConcurrentHashMap` — даёт **слабую консистентность** (weakly consistent) итераторов. Это значит:

- Итератор видит **некоторое** состояние очереди, но не обязан видеть «снимок на момент создания».
- Элементы, добавленные во время итерации, **могут** быть увидены, а могут и нет.
- `ConcurrentModificationException` **не бросается**.

Для большинства задач это правильно: вы хотите «пройти по тому, что есть», а не «заморозить всё и пройти».

### ConcurrentLinkedDeque

`ConcurrentLinkedDeque<E>` — двусторонняя неблокирующая очередь. Можно класть и брать с **обоих концов**.

```java
ConcurrentLinkedDeque<Integer> deque = new ConcurrentLinkedDeque<>();

deque.offerFirst(1);  // в голову
deque.offerLast(2);   // в хвост
deque.pollFirst();    // из головы
deque.pollLast();     // из хвоста
```

Полезно для **work-stealing**: каждый поток работает со своим концом, а «воры» забирают с другого. `ForkJoinPool` (глава 4.6) использует именно такую структуру.

### ConcurrentSkipListMap и Set

`ConcurrentSkipListMap<K, V>` — **отсортированная** потокобезопасная мапа. В отличие от `ConcurrentHashMap`, которая не гарантирует порядок, `ConcurrentSkipListMap` **сортирует** элементы по ключу (через `Comparable` или `Comparator`).

```java
import java.util.concurrent.ConcurrentSkipListMap;

ConcurrentSkipListMap<Integer, String> map = new ConcurrentSkipListMap<>();
map.put(3, "three");
map.put(1, "one");
map.put(2, "two");

// Итерация — в порядке возрастания ключей
for (var entry : map.entrySet()) {
    System.out.println(entry.getKey() + " = " + entry.getValue());
}
// 1 = one
// 2 = two
// 3 = three
```

Внутри — **скип-лист** (skip list): многоуровневый связный список, который позволяет искать, вставлять и удалять за **O(log n)** без блокировок. `ConcurrentHashMap` — это **хэш-таблица**, где порядок не гарантирован, но операции **O(1)** (амортизированно).

**Ключевые методы** (помимо обычных `put`/`get`):

- **`firstKey()`**, **`lastKey()`** — минимальный/максимальный ключ.
- **`ceilingKey(k)`** — минимальный ключ, ≥ `k`.
- **`floorKey(k)`** — максимальный ключ, ≤ `k`.
- **`headMap(k)`**, **`tailMap(k)`**, **`subMap(k1, k2)`** — подмапы.
- **`compute`**, **`merge`**, **`putIfAbsent`** — атомарные, как у `ConcurrentHashMap`.

`ConcurrentSkipListSet<E>` — множество на основе `ConcurrentSkipListMap`. Отсортированное, потокобезопасное.

### Когда ConcurrentSkipListMap вместо ConcurrentHashMap

**ConcurrentSkipListMap** — когда:

- Нужна **сортировка по ключу**.
- Нужны операции «найти ближайший ключ» (`ceiling`, `floor`).
- Нужен **диапазонный поиск** (`headMap`, `tailMap`).
- Ключи **сравнимы** (реализуют `Comparable` или передан `Comparator`).

**ConcurrentHashMap** — когда:

- Сортировка не нужна.
- Нужна **максимальная скорость** доступа по ключу.
- Ключи — хэшируемые (не обязательно сравнимые).
- Размер мапы большой и важна производительность.

На практике `ConcurrentHashMap` используется чаще, потому что сортировка нужна редко. `ConcurrentSkipListMap` — для специфических задач: тайм-серии, диапазонные запросы, «ближайший сосед».

### Ограничения неблокирующих очередей

Неблокирующие очереди — не «лучше» блокирующих. У них есть свои ограничения.

**Ограничение 1: нет «ждать, пока появится».** Если очередь пуста, `poll()` возвращает `null`. Чтобы «подождать», нужно **самому** крутить цикл с `poll()` + `sleep()`. Это **busy wait** (глава 2.8) — плохо, если не с `sleep`.

```java
// Плохо — busy wait, жрёт CPU
while (queue.poll() == null) {
    // ничего
}

// Лучше — с паузой
Integer value;
while ((value = queue.poll()) == null) {
    Thread.sleep(10);
}
```

Но и это не идеально: `sleep(10)` даёт задержку до 10 мс, `sleep(1)` — грузит CPU. Для «ждать по-настоящему» нужна `BlockingQueue`.

**Ограничение 2: неограниченный размер.** `ConcurrentLinkedQueue` растёт, пока есть память. Под нагрузкой, где производитель быстрее потребителя, — очередь растёт и может кончиться память. `BlockingQueue` с ограничением даёт **обратное давление**, неблокирующая — нет.

**Ограничение 3: `size()` дорогой.** O(n) у `ConcurrentLinkedQueue`. Нельзя использовать для «сколько сейчас в очереди» — обойдёте весь список на каждой проверке.

**Ограничение 4: слабая консистентность.** Итератор видит «примерно то, что есть». Для многих задач это ок, но если нужна «замороженная картина» — `ConcurrentLinkedQueue` не подойдёт.

### Где реально используется

**Сбор событий в системе мониторинга.** События сыплются постоянно, обработчик забирает с той скоростью, с какой успевает. Если очередь растёт — это сигнал, что обработчик не справляется, но никто не блокируется.

**Очередь задач с «положил и забыл».** Если задача не критична (например, отправить метрику) — `ConcurrentLinkedQueue` подойдёт лучше `BlockingQueue`, потому что не задерживает вызывающий поток.

**Внутренние структуры фреймворков.** `ForkJoinPool` использует `ConcurrentLinkedDeque` для work-stealing (глава 4.6). Spring и другие фреймворки — для асинхронных событий.

**Кеш с TTL.** Если нужно «удалять старые записи», можно использовать `ConcurrentSkipListMap` с ключом = timestamp. Записи хранятся в порядке времени, и `headMap(now - ttl)` даёт все устаревшие.

**Тайм-серии.** Для хранения метрик с временными метками: `ConcurrentSkipListMap<Instant, Value>`. Диапазонные запросы (`subMap`) — быстрые.

### Частые ошибки

**Ошибка 1: `ConcurrentLinkedQueue` для producer-consumer с ожиданием.** Потребитель крутится в `while (queue.poll() == null) sleep(10)` — это busy wait с задержкой. Правильно — `BlockingQueue`.

**Ошибка 2: неограниченная очередь под нагрузкой.** Растёт, пока не кончится память. Если нужна ёмкость — `BlockingQueue` с ограничением (или своя обёртка с `AtomicInteger`).

**Ошибка 3: использование `size()` для логики.** Дорого и не атомарно. Если нужно «примерно» — `LongAdder` отдельно. Если точно — синхронизация.

**Ошибка 4: `ConcurrentSkipListMap` с несравнимыми ключами.** Упадёт с `ClassCastException` при вставке второго элемента (сравнение через `Comparable`). Убедитесь, что ключи сравнимы, или передайте `Comparator`.

**Ошибка 5: `ConcurrentSkipListMap` для «обычной мапы».** Если сортировка не нужна — `ConcurrentHashMap` быстрее. `SkipListMap` — специфический инструмент, не «мапа по умолчанию».

**Ошибка 6: путать `ConcurrentLinkedQueue` с `ConcurrentLinkedDeque`.** Обычная очередь — только с одного конца, deque — с двух. Если нужен `pollLast` — берите deque.

### Аналогия с автоматами самообслуживания

Вернёмся к началу. **`BlockingQueue`** — это **касса с кассиром**. Пока кассир занят — стоишь в очереди и ждёшь. `take` и `put` блокируются.

**`ConcurrentLinkedQueue`** — это **автомат самообслуживания**. Подошёл — нажал — получил. Если занят, подошёл к другому. Если все заняты — **сам решаешь**, что делать: подождать, пойти в другой зал, уйти. Автомат не блокирует.

**`ConcurrentSkipListMap`** — это **библиотечный каталог, где книги стоят по алфавиту**. Можно быстро найти «все книги от A до M» (`subMap`), «ближайшую книгу после Иванова» (`ceilingKey`). Порядок — встроенный.

**`ConcurrentHashMap`** — это **тот же каталог, но без алфавита**. Найти книгу по названию — быстро, а «все от A до M» — нет, потому что порядка нет.

## Микрозадача 1: ConcurrentLinkedQueue

**Задача:** Создайте `ConcurrentLinkedQueue<Integer>`. Три потока кладут по 1000 элементов, один поток забирает всё, что есть, в цикле. Убедитесь, что ни один элемент не потерян и не задублирован.

**Решение:**

```java
import java.util.concurrent.ConcurrentLinkedQueue;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ConcurrentLinkedQueue<Integer> queue = new ConcurrentLinkedQueue<>();
        AtomicInteger consumed = new AtomicInteger(0);
        AtomicInteger sum = new AtomicInteger(0);

        Thread[] producers = new Thread[3];
        for (int i = 0; i < 3; i++) {
            int id = i;
            producers[i] = new Thread(() -> {
                for (int j = 0; j < 1000; j++) {
                    queue.offer(id * 10000 + j);
                }
            });
        }

        Thread consumer = new Thread(() -> {
            int emptyPolls = 0;
            while (emptyPolls < 100) {
                Integer value = queue.poll();
                if (value == null) {
                    emptyPolls++;
                    try { Thread.sleep(1); } catch (InterruptedException e) { Thread.currentThread().interrupt(); return; }
                } else {
                    emptyPolls = 0;
                    consumed.incrementAndGet();
                    sum.addAndGet(value);
                }
            }
        });

        for (Thread p : producers) p.start();
        consumer.start();
        for (Thread p : producers) p.join();
        consumer.join();

        System.out.println("Забрано: " + consumed.get());
        System.out.println("Осталось в очереди: " + queue.size());
    }
}
```

**Возможный вывод:**

```text
Забрано: 3000
Осталось в очереди: 0
```

**Разбор:** три производителя кладут по 1000 — всего 3000. Потребитель забирает в цикле. Если очередь пуста — `poll()` возвращает `null`, потребитель увеличивает `emptyPolls`, спит 1 мс. Если 100 раз подряд пусто — считает, что производители закончили, и выходит. В итоге забрано ровно 3000, ничего не потеряно.

**Важно:** условие завершения `emptyPolls < 100` — эвристика. В реальном коде нужно **точное** условие: например, «все производители завершились и очередь пуста» — через `CountDownLatch` (глава 3.1) или `AtomicInteger` активных производителей.

## Микрозадача 2: ConcurrentSkipListMap

**Задача:** Создайте `ConcurrentSkipListMap<Integer, String>`, положите 10 элементов с ключами 1, 5, 10, 15, 20, 25, 30, 35, 40, 45. Убедитесь, что итерация идёт по возрастанию. Найдите `ceilingKey(12)` и `floorKey(12)`. Получите `subMap(10, 30)`.

**Решение:**

```java
import java.util.concurrent.ConcurrentSkipListMap;

public class Main {
    public static void main(String[] args) {
        ConcurrentSkipListMap<Integer, String> map = new ConcurrentSkipListMap<>();
        int[] keys = {1, 5, 10, 15, 20, 25, 30, 35, 40, 45};
        for (int k : keys) map.put(k, "value-" + k);

        System.out.println("Итерация (по возрастанию): " + map.keySet());
        System.out.println("ceilingKey(12): " + map.ceilingKey(12));
        System.out.println("floorKey(12): " + map.floorKey(12));
        System.out.println("subMap(10, 30): " + map.subMap(10, 30));
    }
}
```

**Вывод:**

```text
Итерация (по возрастанию): [1, 5, 10, 15, 20, 25, 30, 35, 40, 45]
ceilingKey(12): 15
floorKey(12): 10
subMap(10, 30): {10=value-10, 15=value-15, 20=value-20, 25=value-25}
```

**Разбор:** итерация по возрастанию — встроена. `ceilingKey(12)` — минимальный ключ ≥ 12, это 15. `floorKey(12)` — максимальный ≤ 12, это 10. `subMap(10, 30)` — все ключи от 10 (включительно) до 30 (исключительно). Для хэш-мапы это было бы невозможно — порядка нет.

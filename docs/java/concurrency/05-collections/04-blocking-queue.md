# 5.4. BlockingQueue и producer-consumer

## Где вы это уже видели

**Конвейер на заводе.** Детали едут по ленте. Рабочий на входе кладёт детали на ленту, рабочий на выходе их снимает и обрабатывает. Если лента пуста — второй рабочий ждёт. Если лента переполнена — первый рабочий ждёт. Никто не кладёт детали на пол и не хватает их из воздуха. Лента — это **буфер** между двумя работниками, и у неё есть **предел**.

**Касса в Макдональдсе.** Приняли заказ — положили в очередь на кухню. Повар берёт заказ из очереди, готовит, отдаёт на выдачу. Если очередь заказов пуста — повар ждёт. Если очередь забита (много клиентов) — приём заказов приостанавливается. Никто не готовит бургер «в воздух» и никто не ждёт свой заказ вечно — очередь регулирует поток.

**Приёмная у врача.** Пациенты приходят, регистрируются, садятся в очередь. Врач вызывает следующего. Если пациентов нет — врач отдыхает. Если пациентов слишком много — регистратура перестаёт принимать новых (перенаправляет в другой кабинет). Очередь — буфер между «приходом» и «обслуживанием».

**Сортировочный центр Почты.** Посылки приезжают фурами — их выгружают в накопитель. Сортировщики берут по одной, сортируют, отправляют дальше. Накопитель имеет **предел ёмкости**. Если он полон — фуры ждут снаружи. Если пуст — сортировщики ждут. Идеальный буфер.

**Общее во всех случаях** одно: есть **производитель** (тот, кто кладёт), есть **потребитель** (тот, кто берёт), и есть **буфер ограниченной ёмкости** между ними. Если буфер пуст — потребитель ждёт. Если полон — производитель ждёт. Никто не теряет, никто не переполняет. Это и есть паттерн **producer-consumer**, а `BlockingQueue` — его готовая реализация.

## Теория

### Зачем нужен отдельный примитив

В главе 2.9 мы вручную реализовали producer-consumer на `wait`/`notify` с двумя `Condition`. Это работало, но заняло страницу кода, и в нём легко ошибиться: забыть `while`, перепутать `signal` и `signalAll`, забыть восстановить флаг при прерывании. И таких «ручных» реализаций в реальных проектах — десятки.

`BlockingQueue` — это **готовая реализация** паттерна. Один интерфейс, несколько реализаций на разные случаи. Внутри — уже правильная синхронизация, `wait`/`notify`, `Condition`, обработка прерываний. Вам остаётся только класть и брать.

### Что такое BlockingQueue

`BlockingQueue<E>` — интерфейс из `java.util.concurrent`. Он расширяет `Queue<E>` и добавляет методы, которые **блокируются**, когда очередь пуста (для `take`) или полна (для `put`).

Основные методы.

**`put(E e)`** — кладёт элемент. Если очередь **полна** — блокируется, пока не появится место. Бросает `InterruptedException`, если поток прервут.

**`take()`** — берёт элемент и удаляет из очереди. Если очередь **пуста** — блокируется, пока не появится элемент. Бросает `InterruptedException`.

**`offer(E e)`** — пытается положить элемент. Если очередь полна — возвращает `false` сразу, не блокируется.

**`offer(E e, long timeout, TimeUnit unit)`** — пытается положить, но не дольше таймаута. Если за это время места не появилось — возвращает `false`.

**`poll()`** — пытается взять элемент. Если очередь пуста — возвращает `null` сразу.

**`poll(long timeout, TimeUnit unit)`** — пытается взять, но не дольше таймаута. Если не появилось — возвращает `null`.

**`peek()`** — смотрит первый элемент, не забирая. Может вернуть `null`, если пусто.

**`size()`** — текущий размер.

**`remainingCapacity()`** — сколько ещё влезет.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> <code>put</code>/<code>take</code> — блокирующиеся, для producer-consumer. <code>offer</code>/<code>poll</code> — неблокирующиеся, для случаев «попробовать и, если не вышло, идти дальше». <code>offer</code>/<code>poll</code> с таймаутом — компромисс: «подожди разумное время».
</div>

### Реализации

В JDK несколько готовых реализаций. Каждая — для своего сценария.

**`ArrayBlockingQueue<E>`** — ограниченная очередь на массиве. Ёмкость **фиксирована** при создании и не может быть изменена. Внутри — массив и два индекса (голова и хвост). Самая простая, самая предсказуемая по памяти.

```java
BlockingQueue<String> queue = new ArrayBlockingQueue<>(100);
```

Опционально поддерживает **справедливость** (FIFO для ожидающих потоков):

```java
BlockingQueue<String> fair = new ArrayBlockingQueue<>(100, true);
```

`fair = true` гарантирует, что производитель, дольше всех ждущий места, получит его первым. Это защита от starvation (глава 2.8), но медленнее — как и любая справедливость.

**`LinkedBlockingQueue<E>`** — очередь на связном списке. Может быть **ограниченной** или **неограниченной** (точнее, `Integer.MAX_VALUE`, что на практике неограниченно).

```java
BlockingQueue<String> bounded = new LinkedBlockingQueue<>(1000);
BlockingQueue<String> unbounded = new LinkedBlockingQueue<>();
```

Быстрее `ArrayBlockingQueue` при высокой конкуренции, потому что использует **два разных лока** — один для `put`, другой для `take`. Производители и потребители не мешают друг другу.

**Осторожно:** неограниченная `LinkedBlockingQueue` — та же мина, что и `newFixedThreadPool` с неограниченной очередью (глава 4.3). Под нагрузкой она растёт, пока не кончится память. В продакшене — **всегда** указывайте ёмкость.

**`PriorityBlockingQueue<E>`** — очередь с приоритетами. Извлекается не «первый пришедший», а **самый приоритетный**. Элементы должны реализовывать `Comparable` или передавать `Comparator`.

```java
BlockingQueue<Task> queue = new PriorityBlockingQueue<>();
```

**Неограниченная.** Осторожно с памятью. Хороша для случаев, когда есть «важные» и «неважные» задачи, и важные должны обрабатываться первыми.

**`SynchronousQueue<E>`** — очередь **нулевой ёмкости**. Каждый `put` должен ждать `take`, и наоборот. `put` блокируется, пока кто-то не заберёт, `take` блокируется, пока кто-то не положит. Никакого буфера — прямая передача из рук в руки.

```java
BlockingQueue<String> queue = new SynchronousQueue<>();
```

Именно её использует `newCachedThreadPool()` (глава 4.2): если есть свободный поток — задача сразу передаётся ему, иначе — создаётся новый поток.

**`DelayQueue<E>`** — очередь, где элементы становятся доступны только через указанное время. Каждый элемент реализует `Delayed` с методом `getDelay()`. `take` возвращает элемент, только когда его время пришло; иначе ждёт.

```java
BlockingQueue<DelayedTask> queue = new DelayQueue<>();
```

Применение: отложенные задачи, таймауты, ретраи.

**`LinkedTransferQueue<E>`** — гибрид. Работает как `SynchronousQueue` (прямая передача), но умеет и буферизовать. Обычно быстрее `LinkedBlockingQueue` в сценариях «производитель ждёт потребителя». Обычно не нужна в учебных задачах, но полезна в высоконагруженных системах.

### Сводная таблица

| Реализация | Ёмкость | Особенность | Когда использовать |
|---|---|---|---|
| `ArrayBlockingQueue` | Фиксированная | Массив, предсказуема | Обычный producer-consumer |
| `LinkedBlockingQueue` | Ограниченная или «безграничная» | Два лока | Высокая конкуренция |
| `PriorityBlockingQueue` | Неограниченная | По приоритету | Важные задачи вперёд |
| `SynchronousQueue` | 0 | Прямая передача | `newCachedThreadPool` |
| `DelayQueue` | Неограниченная | По времени | Отложенные задачи |
| `LinkedTransferQueue` | Ограниченная или нет | Гибрид | Высокие нагрузки |

### Паттерн producer-consumer

Producer-consumer — это **архитектурный паттерн**, а не просто «два потока с очередью». Суть в том, что **производитель и потребитель не знают друг о друге**. Они общаются только через очередь. Это даёт три преимущества.

**Первое: развязка (decoupling).** Производитель не знает, кто и как обрабатывает его данные. Потребитель не знает, откуда они пришли. Можно менять одну сторону, не трогая другую.

**Второе: сглаживание нагрузки (load leveling).** Если производитель быстрый, а потребитель медленный — очередь накапливает данные. Потребитель разгребает по мере сил. Если наоборот — потребитель ждёт. Очередь — это **буфер**, который гасит неравномерность.

**Третье: ограничение памяти.** Ограниченная очередь не даёт производителю «убежать вперёд» и забить память. Когда очередь полна — производитель ждёт. Это **обратное давление** (backpressure).

### Канонический код

Вот как выглядит producer-consumer на `BlockingQueue`.

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(10);

        Thread producer = new Thread(() -> {
            try {
                for (int i = 0; i < 100; i++) {
                    queue.put(i); // блокируется, если очередь полна
                    System.out.println("Положил: " + i);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread consumer = new Thread(() -> {
            try {
                for (int i = 0; i < 100; i++) {
                    Integer value = queue.take(); // блокируется, если пуста
                    System.out.println("Забрал: " + value);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        producer.start();
        consumer.start();
        producer.join();
        consumer.join();
    }
}
```

**Что здесь важно.**

**Производитель и потребитель не знают друг о друге.** Они оба знают только про `queue`. Можно добавить второго производителя — код потребителя не изменится.

**`put` блокируется, когда очередь полна.** Если производитель бежит быстрее, чем потребитель забирает, он упрётся в лимит и будет ждать. Это **обратное давление**: производитель замедляется автоматически.

**`take` блокируется, когда очередь пуста.** Если потребитель быстрее — он ждёт.

**`InterruptedException`.** Оба метода могут быть прерваны — важно обработать (глава 1.6).

### Завершение producer-consumer

Классическая проблема: **как сказать потребителю, что данных больше не будет?** Ведь `take` ждёт вечно, если очередь пуста. Если производитель закончил и больше ничего не положит — потребитель будет ждать вечно.

Есть несколько паттернов.

**Паттерн 1: «известное количество».** Если производитель знает, сколько элементов положит, — потребитель тоже знает и просто берёт ровно N раз. Это пример выше. Но подходит не всегда.

**Паттерн 2: «отравленная пилюля» (poison pill).** Производитель кладёт специальное «стоп-значение», и потребитель, увидев его, завершается. Если производителей несколько — каждый кладёт свою пилюлю.

```java
// producer
for (int i = 0; i < 100; i++) queue.put(i);
queue.put(-1); // poison pill

// consumer
while (true) {
    Integer value = queue.take();
    if (value == -1) break;
    // обрабатываем
}
```

**Паттерн 3: `volatile` флаг остановки.** Дополнительно к очереди — `volatile boolean stopped`. Производитель выставляет `false` и прерывает потребителя через `interrupt`. Потребитель ловит `InterruptedException` и завершается.

```java
// producer
stopped = true;
consumer.interrupt();

// consumer
try {
    while (!stopped) {
        Integer value = queue.poll(100, TimeUnit.MILLISECONDS); // с таймаутом
        if (value != null) { /* обрабатываем */ }
    }
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

**Паттерн 4: `shutdown()` пула.** Если потребители — это пул потоков, то `shutdown()` + `awaitTermination()` сам разберётся. Подробно — в главе 4.5.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> если производитель может закончиться — обязательно сообщите потребителю. Иначе потребитель будет ждать вечно. Poison pill, флаг или таймаут в <code>poll</code> — на выбор.
</div>

### BlockingQueue vs wait/notify

Мы уже делали producer-consumer на `wait`/`notify` (глава 2.9). Зачем `BlockingQueue`?

**Первое: безопасность.** `BlockingQueue` не даёт ошибиться. Нет `while`, нет `notifyAll`, нет `Condition`. Просто `put` и `take`.

**Второе: производительность.** `LinkedBlockingQueue` использует **два лока** — один для производителей, другой для потребителей. На `wait`/`notify` приходилось бы использовать один монитор для обоих. Это даёт заметный выигрыш под нагрузкой.

**Третье: гибкость.** Разные реализации — под разные сценарии. `Array` — фиксированная память, `Linked` — высокая конкуренция, `Priority` — порядок по приоритету, `Delay` — отложенные. На `wait`/`notify` всё пришлось бы реализовывать вручную.

**Четвёртое: обработка прерываний.** `put`/`take` корректно бросают `InterruptedException`. На `wait`/`notify` можно случайно «проглотить» прерывание.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> для producer-consumer всегда используйте <code>BlockingQueue</code>, а не ручной <code>wait</code>/<code>notify</code>. Ручная реализация — только для обучения, не для продакшена.
</div>

### Частые ошибки

**Ошибка 1: неограниченная `LinkedBlockingQueue`.** Та же мина, что и с пулами. Под нагрузкой очередь растёт, пока не кончится память. В продакшене — только с ёмкостью.

**Ошибка 2: нет сигнала завершения.** Потребитель ждёт вечно, если производитель закончил. Poison pill, флаг, таймаут — что-то должно быть.

**Ошибка 3: `put`/`take` без обработки `InterruptedException`.** Поток прервут — программа продолжит работать «как ни в чём не бывало», но фактически задача остановки проигнорирована. Всегда восстанавливайте флаг (глава 1.6).

**Ошибка 4: блокировка внутри задачи, которая сама в очереди.** Если задача в пуле потоков кладёт в `BlockingQueue` **того же** пула — возможен deadlock. Пул ждёт, пока задача закончится, а задача ждёт, пока освободится поток пула.

**Ошибка 5: один производитель — один потребитель, но `put` из нескольких потоков.** `BlockingQueue` потокобезопасна, но если производителей несколько — убедитесь, что их `put` не конфликтуют логически. Например, два производителя могут «перепутать» порядок элементов, если порядок важен.

**Ошибка 6: `size()` для синхронизации.** `size()` — приблизительный. Между `size()` и следующим действием очередь может измениться. Для синхронизации используйте `put`/`take` с их блокирующей семантикой, а не «проверил размер — сделал».

### Аналогия с конвейером

Вернёмся к началу. **`BlockingQueue`** — это **лента конвейера** между двумя рабочими. У ленты есть **ёмкость**: скажем, помещается 10 деталей. Первый рабочий кладёт на ленту — если она полна, ждёт. Второй снимает — если пуста, ждёт.

**`ArrayBlockingQueue`** — это **лента фиксированной длины**. Заранее известна, сколько поместится. Предсказуемо.

**`LinkedBlockingQueue`** — это **лента, которая может растягиваться** (если не задать ёмкость). Гибко, но если рабочий на выходе медленный — лента растянется до бесконечности и упрётся в стену цеха.

**`SynchronousQueue`** — это **прямая передача из рук в руки**. Ленты нет. Один рабочий передаёт деталь другому. Без буфера. Быстро, но требует, чтобы оба были готовы одновременно.

**`PriorityBlockingQueue`** — это **лента, на которой детали выстраиваются по важности**. Не «первая пришла — первая ушла», а «самая важная — первой». Удобно, если детали неравноценны.

А ручной `wait`/`notify` — это **сделать ленту самому из подручных материалов**. Можно, но зачем, если есть готовая?

## Микрозадача 1: простой producer-consumer

**Задача:** Создайте `ArrayBlockingQueue<Integer>(5)`. Один производитель кладёт 20 чисел, один потребитель забирает 20. Убедитесь, что программа корректно завершается, и все 20 элементов проходят через очередь.

**Решение:**

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.BlockingQueue;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<Integer> queue = new ArrayBlockingQueue<>(5);

        Thread producer = new Thread(() -> {
            try {
                for (int i = 1; i <= 20; i++) {
                    queue.put(i);
                    System.out.println("Положил: " + i);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        Thread consumer = new Thread(() -> {
            try {
                for (int i = 1; i <= 20; i++) {
                    Integer value = queue.take();
                    System.out.println("Забрал: " + value);
                }
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        producer.start();
        consumer.start();
        producer.join();
        consumer.join();
        System.out.println("Очередь пуста: " + queue.isEmpty());
    }
}
```

**Возможный вывод:**

```text
Положил: 1
Положил: 2
Положил: 3
Положил: 4
Положил: 5
Забрал: 1
Положил: 6
Забрал: 2
...
Забрал: 20
Очередь пуста: true
```

**Разбор:** очередь ёмкостью 5. Производитель кладёт элементы, но когда очередь заполнена (5 штук), `put` блокируется — ждёт, пока потребитель заберёт. Потребитель забирает — производитель продолжает. В итоге все 20 элементов проходят, очередь пуста. Никто не потерял, никто не переполнил.

## Микрозадача 2: несколько производителей и потребителей

**Задача:** Три производителя, три потребителя, `LinkedBlockingQueue` на 10 элементов. Каждый производитель кладёт 30 элементов, каждый потребитель забирает 30. Убедитесь, что всего обработано 90 элементов, и никто не завис.

**Решение:**

```java
import java.util.concurrent.BlockingQueue;
import java.util.concurrent.LinkedBlockingQueue;
import java.util.concurrent.atomic.AtomicInteger;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        BlockingQueue<Integer> queue = new LinkedBlockingQueue<>(10);
        AtomicInteger consumed = new AtomicInteger(0);

        Thread[] producers = new Thread[3];
        for (int i = 0; i < 3; i++) {
            int id = i;
            producers[i] = new Thread(() -> {
                try {
                    for (int j = 0; j < 30; j++) {
                        queue.put(id * 1000 + j);
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }, "producer-" + id);
        }

        Thread[] consumers = new Thread[3];
        for (int i = 0; i < 3; i++) {
            int id = i;
            consumers[i] = new Thread(() -> {
                try {
                    for (int j = 0; j < 30; j++) {
                        queue.take();
                        consumed.incrementAndGet();
                    }
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }, "consumer-" + id);
        }

        for (Thread p : producers) p.start();
        for (Thread c : consumers) c.start();
        for (Thread p : producers) p.join();
        for (Thread c : consumers) c.join();

        System.out.println("Всего обработано: " + consumed.get() + " (ожидалось 90)");
        System.out.println("Очередь пуста: " + queue.isEmpty());
    }
}
```

**Вывод:**

```text
Всего обработано: 90 (ожидалось 90)
Очередь пуста: true
```

**Разбор:** три производителя кладут по 30 элементов — всего 90. Три потребителя забирают по 30 — тоже 90. Очередь ёмкостью 10, поэтому производители иногда ждут, потребители иногда ждут. В итоге всё сходится: 90 элементов обработано, очередь пуста.

Обратите внимание: **порядок обработки не гарантирован** между разными производителями. Первый производитель мог положить `1, 2, 3`, второй — `1001, 1002, 1003`, и потребитель видит их вперемешку. `BlockingQueue` гарантирует **FIFO** для элементов (кто первый положил — тот первым и заберут), но не «сначала все от первого производителя».

## 📌 Что дальше

В следующей главе — **«Неблокирующие очереди»**. Разберём `ConcurrentLinkedQueue` — очередь без блокировок на CAS-операциях. Она быстрее `BlockingQueue`, но не умеет блокироваться. А также `ConcurrentSkipListMap` — отсортированную мапу под нагрузкой. А то ведь `BlockingQueue` блокируется — это хорошо для producer-consumer, но не всегда. Иногда нужно «положить и не ждать».

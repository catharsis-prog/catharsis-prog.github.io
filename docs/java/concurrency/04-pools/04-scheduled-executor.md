# 4.4. ScheduledExecutorService

## Где вы это уже видели

**Будильник.** Вы ставите его на 7:00 — и он звонит один раз. Не «через час», не «как получится», а ровно в 7:00. Если опоздал на минуту — это уже не будильник, а недоразумение.

**Метро.** Поезда идут каждые две минуты. Не «через две минуты после предыдущего», а **по расписанию**: 7:00, 7:02, 7:04. Если поезд задержался на минуту — следующий всё равно выходит в 7:04, и интервал сокращается. Это `scheduleAtFixedRate`.

**Кормление кота.** Вы кормите кота в 8:00. Кот ест двадцать минут, потом вы моете миску, потом занимаетесь своими делами. И только **после всего этого** начинаете отсчёт до следующего кормления. Следующее — через двадцать четыре часа **после** окончания уборки, а не «ровно в 8:00 завтра». Это `scheduleWithFixedDelay`.

**Проверка почты.** Вы настроили приложение проверять почту «каждые пять минут». Но если проверка заняла десять секунд — следующая начнётся через пять минут **после** завершения предыдущей, а не «ровно через пять минут от начала». Иначе при медленной сети проверки начали бы наслаиваться друг на друга.

**Полив цветов.** Раз в день, утром. Если вы в отъезде — полив пропускается, но на следующий день система снова попробует полить. Одна неудача не отменяет расписание навсегда — хотя в Java, к сожалению, отменяет, и об этом ниже.

**Общее во всех случаях** одно: есть **действие**, есть **расписание**, и действие нужно выполнить либо **один раз с задержкой**, либо **повторять** по определённому правилу. Это и есть `ScheduledExecutorService`.

## Теория

### Чем плох Timer

До Java 5 для отложенных задач использовали класс `Timer`. Он до сих пор есть в JDK, но пользоваться им **не надо**. Причины три, и все три серьёзные.

**Первое: Timer — однопоточный.** Все задачи в одном `Timer` выполняются в **одном потоке**, последовательно. Если одна задача задержится на минуту — все остальные опоздают на минуту. Для будильника это может быть некритично, для сервера — катастрофа.

**Второе: исключение убивает весь Timer.** Если задача бросит `RuntimeException`, `Timer` **прекратит работу полностью**. Остальные запланированные задачи не выполнятся никогда. Никакого уведомления, никакого лога — просто тишина. Ищите потом, почему рассылка не уходит третий день.

**Третье: нет нормального API.** Ни `scheduleAtFixedRate` с ясной семантикой, ни `scheduleWithFixedDelay`. Всё делается через флаги, и легко перепутать.

`ScheduledExecutorService` решает все три проблемы: работает на пуле потоков, изолирует исключения, имеет ясное API. Переходите на него.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> <code>java.util.Timer</code> — устаревший инструмент. Не используйте его в новом коде. Если встретили в старом — замените на <code>ScheduledExecutorService</code>.
</div>

### Как получить ScheduledExecutorService

`ScheduledExecutorService` — это **интерфейс**, наследник `ExecutorService`. Получить его можно через `Executors`:

```java
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2);
```

Число в конструкторе — это `corePoolSize`. Практически всегда достаточно **одного** потока, если задачи короткие. Два-три — если задачи могут подолгу работать и не должны мешать друг другу.

Можно собрать и вручную через `ScheduledThreadPoolExecutor`, но это нужно редко. `Executors.newScheduledThreadPool` покрывает почти все сценарии.

### Три метода — три разных поведения

У `ScheduledExecutorService` есть три основных метода. Они выглядят похоже, но ведут себя **по-разному**, и путать их — классическая ошибка.

**`schedule(Runnable task, long delay, TimeUnit unit)`** — выполнить **один раз** через `delay`.

**`scheduleAtFixedRate(Runnable task, long initialDelay, long period, TimeUnit unit)`** — выполнять периодически с **фиксированным интервалом** между **началами**.

**`scheduleWithFixedDelay(Runnable task, long initialDelay, long delay, TimeUnit unit)`** — выполнять периодически с **фиксированной задержкой** между **окончанием предыдущего и началом следующего**.

Разница между двумя последними — важнее, чем кажется. Разберём её подробно.

### schedule: один раз с задержкой

Самый простой случай.

```java
ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);

scheduler.schedule(
    () -> System.out.println("Прошло 5 секунд"),
    5, TimeUnit.SECONDS
);
```

Задача выполнится один раз, через пять секунд, в потоке пула. `schedule` возвращает `ScheduledFuture<?>`, через который можно отменить задачу до её выполнения.

```java
ScheduledFuture<?> future = scheduler.schedule(() -> System.out.println("Привет"), 5, TimeUnit.SECONDS);
// передумали
future.cancel(false);
```

Это удобно: например, для задачи «если пользователь не подтвердил в течение минуты — отменить заказ».

### scheduleAtFixedRate: фиксированные интервалы между стартами

```java
scheduler.scheduleAtFixedRate(
    () -> System.out.println("Тик: " + System.currentTimeMillis()),
    0, 1, TimeUnit.SECONDS
);
```

Задача запускается с `initialDelay = 0` (сразу), потом **каждую секунду от начала предыдущего запуска**. Не от конца — от начала.

Это и есть «расписание метро». Если задача выполняется 200 мс — следующий запуск через 800 мс. Если задача выполняется 1,5 секунды — следующий запуск **уже должен был начаться** 500 мс назад. Что делать в этом случае — отдельный вопрос, об этом ниже.

**Типичное применение:** задачи, которые должны идти «по часам» — обновление кеша каждые 5 секунд, отправка метрик каждую минуту, тик игрового мира.

### scheduleWithFixedDelay: фиксированная пауза после завершения

```java
scheduler.scheduleWithFixedDelay(
    () -> {
        System.out.println("Начинаю работу");
        try { Thread.sleep(300); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        System.out.println("Закончил работу");
    },
    0, 1, TimeUnit.SECONDS
);
```

Задача запускается, работает сколько нужно (скажем, 300 мс), **завершается**, потом **ждёт одну секунду**, потом запускается снова. Итого между стартами — 1,3 секунды, но между **концом** и **следующим стартом** — ровно одна секунда.

**Типичное применение:** задачи, где важен «отдых» между итерациями — периодический опрос внешнего API (не хотим его заваливать), проверка обновлений, периодическая очистка ресурсов.

### Главное различие

Сравним на примере. Задача выполняется **300 мс**, интервал — **1000 мс**.

**`scheduleAtFixedRate(period = 1000)`:**

```text
t=0    : начало
t=300  : конец
t=1000 : начало (следующий тик по расписанию)
t=1300 : конец
t=2000 : начало
...
```

Между стартами — ровно 1000 мс, всегда.

**`scheduleWithFixedDelay(delay = 1000)`:**

```text
t=0    : начало
t=300  : конец
t=1300 : начало (через 1000 мс после окончания)
t=1600 : конец
t=2600 : начало
...
```

Между стартами — 1300 мс (300 мс работы + 1000 мс паузы).

**Формула:**

- `fixedRate`: интервал = `period` (фиксированный, независимо от времени работы).
- `fixedDelay`: интервал = `время_работы + delay` (зависит от времени работы).

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> <code>scheduleAtFixedRate</code> — когда важно «раз в секунду, несмотря ни на что». <code>scheduleWithFixedDelay</code> — когда важно «отдохнуть секунду после работы». Не путайте.
</div>

### Что происходит, если задача не успевает

При `scheduleAtFixedRate` возможна ситуация: задача выполняется дольше, чем `period`. Что тогда?

**Поведение по умолчанию:** следующий запуск начнётся **сразу после завершения** текущего. Задача не запустится «внахлёст» сама с собой — `ScheduledThreadPoolExecutor` **не запускает одну и ту же задачу параллельно**. Это важно: даже если по расписанию уже три запуска «просрочены», выполнится один за другим, а не три одновременно.

**Результат:** «пропущенные» тики накапливаются как долг, и задача начинает догонять сама себя. Если задача стабильно медленнее `period`, она будет работать **непрерывно**, без пауз. Это может быть нормально (если вы правда хотите «как можно чаще»), а может быть проблемой (если задача жрёт процессор).

**Решение:** если задача может выполняться дольше `period`, используйте `scheduleWithFixedDelay`. Он гарантирует паузу между итерациями, и задача не будет «догонять» сама себя.

### Исключения в периодических задачах

Вот тут кроется самая коварная ловушка `ScheduledExecutorService`.

**Если периодическая задача бросит исключение — она больше не выполнится.** Никогда. Тишина. Без уведомления.

Пример:

```java
scheduler.scheduleAtFixedRate(() -> {
    System.out.println("Тик");
    if (Math.random() < 0.1) {
        throw new RuntimeException("Что-то сломалось");
    }
}, 0, 1, TimeUnit.SECONDS);
```

С вероятностью 10% на каждом тике задача бросит исключение. После этого — **никаких тиков**. Задача «умерла», а вы даже не узнаете, если не смотрите в логи пула.

**Почему так.** `ScheduledThreadPoolExecutor` считает, что если задача бросила исключение — она «не может продолжаться». Поэтому он её отменяет. Логика разумная, но неочевидная.

**Решение:** оборачивайте тело периодической задачи в `try/catch`. Ловите все исключения и логируйте.

```java
scheduler.scheduleAtFixedRate(() -> {
    try {
        System.out.println("Тик");
        if (Math.random() < 0.1) {
            throw new RuntimeException("Что-то сломалось");
        }
    } catch (Throwable t) {
        System.err.println("Ошибка в тике: " + t.getMessage());
        // задача продолжит выполняться
    }
}, 0, 1, TimeUnit.SECONDS);
```

Ловите именно `Throwable`, а не `Exception`: `Error` (например, `OutOfMemoryError`) тоже «убьёт» задачу, а иногда его нужно хотя бы залогировать.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> любая периодическая задача должна иметь <code>try/catch</code> вокруг всего тела. Иначе одно исключение — и задача тихо умрёт. Это самая частая причина «почему у меня перестала работать рассылка через месяц после запуска».
</div>

### Отмена задач

`scheduleAtFixedRate` и `scheduleWithFixedDelay` возвращают `ScheduledFuture<?>`. Через него можно **отменить** периодическую задачу:

```java
ScheduledFuture<?> future = scheduler.scheduleAtFixedRate(task, 0, 1, TimeUnit.SECONDS);

// через какое-то время
future.cancel(false); // false — не прерывать выполняющуюся задачу
                      // true  — прервать через interrupt
```

После `cancel` задача больше не запускается. Если в этот момент она выполняется — при `cancel(true)` получит `interrupt`, при `cancel(false)` — доработает до конца.

**Важно:** `cancel` не освобождает поток пула. Он просто «вычёркивает» задачу из расписания. Поток остаётся в пуле и готов к другим задачам.

### Завершение пула

Как и любой `ExecutorService`, `ScheduledExecutorService` нужно завершать.

```java
scheduler.shutdown(); // перестать принимать новые задачи, дать доработать текущие
scheduler.awaitTermination(10, TimeUnit.SECONDS);
```

**Важно:** `shutdown()` **не отменяет** периодические задачи. Он перестаёт принимать **новые** задачи, но уже запланированные периодические — продолжают работать. Если хотите их остановить — сначала `cancel` на их `ScheduledFuture`, потом `shutdown`.

```java
future.cancel(false);
scheduler.shutdown();
```

`shutdownNow()` — прерывает выполняющиеся задачи и отменяет все запланированные. Возвращает список задач, которые не успели начаться.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> <code>shutdown()</code> не отменяет периодические задачи. Чтобы остановить их, вызовите <code>cancel</code> на каждой <code>ScheduledFuture</code>. Или используйте <code>shutdownNow()</code>, который отменяет всё разом.
</div>

### Сколько потоков в пуле

Обычно **одного** потока достаточно. Периодические задачи обычно короткие: проверить статус, обновить кеш, отправить метрику. Они не конкурируют друг с другом.

Два-три потока нужны, если:

- Какая-то задача может выполняться долго — и вы не хотите, чтобы она задерживала остальные.
- Задачи «тяжёлые» и должны работать параллельно (например, несколько независимых мониторингов).

Слишком много потоков — тоже плохо: задачи будут конкурировать за процессор, а толку не прибавится.

### Частые ошибки

**Ошибка 1: `Timer` вместо `ScheduledExecutorService`.** Об этом уже было, но повторю: `Timer` — устаревший, однопоточный, умирает от первого исключения.

**Ошибка 2: нет `try/catch` в периодической задаче.** Задача умрёт после первого исключения. Самая частая причина «у меня всё работало, а потом перестало».

**Ошибка 3: путать `fixedRate` и `fixedDelay`.** Если задача выполняется дольше `period`, `fixedRate` начнёт «догонять» сам себя и работать без пауз. `fixedDelay` — нет.

**Ошибка 4: `shutdown()` без `cancel`.** Периодические задачи продолжат работать после `shutdown()`. Если хотите их остановить — сначала `cancel`.

**Ошибка 5: `initialDelay = 0` для задач, которые сразу лезут в сеть.** Задача запустится в момент старта приложения, когда окружение ещё не готово (база не подключилась, конфиг не прочитан). Используйте небольшую начальную задержку.

**Ошибка 6: слишком частые тики.** `scheduleAtFixedRate(task, 0, 1, TimeUnit.MILLISECONDS)` — это 1000 запусков в секунду. Если задача хоть что-то делает, вы загрузите процессор на 100%. Периодичность должна соответствовать реальной потребности.

**Ошибка 7: задача с побочными эффектами под `fixedRate` при перекрытии.** Если задача выполняется дольше `period`, следующий запуск начнётся сразу после завершения. Если задача меняет общее состояние, могут возникнуть гонки с другими запусками (хотя сама с собой она не пересекается). Продумайте, безопасно ли это.

### Аналогия с метро и кормлением кота

Вернёмся к началу. **`scheduleAtFixedRate`** — это **метро**. Поезда выходят по расписанию. Если один поезд задержался — следующий всё равно выходит в своё время. Интервал между отправлениями фиксирован, независимо от того, сколько ехал предыдущий.

**`scheduleWithFixedDelay`** — это **кормление кота**. Вы кормите, кот ест, вы моете миску, и только **потом** начинаете отсчёт. Следующее кормление — через сутки **после** окончания уборки, а не «ровно в 8:00». Если кот ел дольше обычного — следующее кормление сдвигается.

**`schedule`** — это **будильник**. Один раз, в назначенное время, и всё. Никаких повторов.

А `Timer`, если хотите знать, — это **один будильник на все случаи жизни**, который звонит всем членам семьи одновременно, и если кто-то не проснулся с первого раза — больше не звонит никогда. Не берите его.

## Микрозадача 1: schedule с задержкой

**Задача:** Создайте `ScheduledExecutorService`, запланируйте задачу через `schedule` с задержкой 2 секунды. Задача печатает время начала и время выполнения. Замерьте, действительно ли прошло две секунды.

**Решение:**

```java
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.TimeUnit;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);
        long start = System.currentTimeMillis();

        System.out.println("Запланировали задачу через 2 секунды");
        scheduler.schedule(() -> {
            long elapsed = System.currentTimeMillis() - start;
            System.out.println("Задача выполнилась через " + elapsed + " мс");
        }, 2, TimeUnit.SECONDS);

        scheduler.shutdown();
        scheduler.awaitTermination(5, TimeUnit.SECONDS);
    }
}
```

**Возможный вывод:**

```text
Запланировали задачу через 2 секунды
Задача выполнилась через 2005 мс
```

**Разбор:** задача действительно выполнилась через две секунды, плюс-минус накладные расходы планировщика (5 мс — это нормально). `schedule` — одноразовый: после выполнения задача больше не повторится. `shutdown()` после выполнения — обязательный, иначе пул будет держать программу.

## Микрозадача 2: fixedRate vs fixedDelay

**Задача:** Запланируйте две периодические задачи: одну через `scheduleAtFixedRate` с `period = 1s`, другую через `scheduleWithFixedDelay` с `delay = 1s`. Обе работают по 300 мс. Запустите на 5 секунд, потом отмените. Сравните метки времени между запусками.

**Решение:**

```java
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.ScheduledFuture;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicLong;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(2);
        AtomicLong lastFixedRate = new AtomicLong(0);
        AtomicLong lastFixedDelay = new AtomicLong(0);

        Runnable fixedRateTask = () -> {
            long now = System.currentTimeMillis();
            long delta = lastFixedRate.get() == 0 ? 0 : now - lastFixedRate.get();
            lastFixedRate.set(now);
            System.out.println("[fixedRate]  дельта: " + delta + " мс");
            try { Thread.sleep(300); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        };

        Runnable fixedDelayTask = () -> {
            long now = System.currentTimeMillis();
            long delta = lastFixedDelay.get() == 0 ? 0 : now - lastFixedDelay.get();
            lastFixedDelay.set(now);
            System.out.println("[fixedDelay] дельта: " + delta + " мс");
            try { Thread.sleep(300); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        };

        ScheduledFuture<?> fr = scheduler.scheduleAtFixedRate(fixedRateTask, 0, 1, TimeUnit.SECONDS);
        ScheduledFuture<?> fd = scheduler.scheduleWithFixedDelay(fixedDelayTask, 0, 1, TimeUnit.SECONDS);

        Thread.sleep(5000);
        fr.cancel(false);
        fd.cancel(false);
        scheduler.shutdown();
        scheduler.awaitTermination(5, TimeUnit.SECONDS);
    }
}
```

**Возможный вывод:**

```text
[fixedRate]  дельта: 0 мс
[fixedDelay] дельта: 0 мс
[fixedRate]  дельта: 1000 мс
[fixedDelay] дельта: 1300 мс
[fixedRate]  дельта: 1000 мс
[fixedDelay] дельта: 1300 мс
[fixedRate]  дельта: 1000 мс
[fixedDelay] дельта: 1300 мс
```

**Разбор:** вот наглядное различие. `fixedRate` запускает задачу каждые 1000 мс **от начала** предыдущей. `fixedDelay` запускает через 1000 мс **после окончания** предыдущей — а так как задача работает 300 мс, между стартами получается 1300 мс. Если задача станет медленнее (например, 1500 мс), `fixedRate` начнёт запускать без пауз (следующий сразу после предыдущего), а `fixedDelay` всегда будет держать паузу в 1000 мс.

## 🎯 Самостоятельная задача

Напишите **планировщик периодических задач** — мини-аналог `cron`, но попроще.

**Требования:**

1. Класс `TaskScheduler` с `ScheduledExecutorService(2)` внутри.
2. Метод `schedule(String name, Runnable task, long periodMillis)` — регистрирует задачу под именем, запускает с `scheduleAtFixedRate`.
3. Метод `cancel(String name)` — отменяет задачу по имени.
4. Метод `listActive()` — возвращает список активных имён.
5. Метод `shutdown()` — отменяет все задачи и завершает пул.
6. **Каждая задача** обёрнута в `try/catch(Throwable)` и логирует ошибки — задача не должна «умирать» от исключения.
7. **Демонстрация:** зарегистрируйте три задачи — `heartbeat` (каждую секунду, печатает «жив»), `cleanup` (каждые 2 секунды, «уборка»), `failing` (каждые 500 мс, с вероятностью 30% бросает `RuntimeException`). Запустите на 5 секунд, потом отмените `cleanup`, потом дождитесь завершения.

**Что проверить:**

- `failing` продолжает работать после исключений — благодаря `try/catch`.
- `cleanup` перестаёт печатать после `cancel`.
- После `shutdown` программа корректно завершается.

**Дополнительно:**

- Добавьте метод `scheduleOnce(String name, Runnable task, long delayMillis)` через `schedule`.
- Сделайте так, чтобы `cancel` возвращал `boolean`: `true`, если задача была, `false`, если нет.
- Попробуйте **убрать** `try/catch` из `failing`. Убедитесь, что она тихо умирает после первого исключения, а `heartbeat` и `cleanup` продолжают работать.

## 📌 Что дальше

В следующей главе — **«Корректное завершение пула»**. Разберём подробно, чем `shutdown()` отличается от `shutdownNow()`, как дождаться завершения через `awaitTermination`, что делать с задачами, которые не успели выполниться, и почему `shutdown` без `awaitTermination` — почти всегда ошибка. А то ведь до сих пор мы вскользь упоминали `shutdown()` в каждой главе. Пора разобраться с ним как следует — тема скучная, но без неё любое приложение, использующее пулы, будет висеть или терять задачи.

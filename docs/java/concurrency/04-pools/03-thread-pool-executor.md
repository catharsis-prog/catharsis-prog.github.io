# 4.3. ThreadPoolExecutor изнутри

## Где вы это уже видели

**Кафе на вокзале.** У стойки стоят три постоянных бариста — они работают всегда, даже когда посетителей нет: это их смена. Если посетители повалили валом и трое не справляются, администратор зовёт подработчиков — но не больше пяти сверху, иначе на кухне станет тесно. Когда вал спадает, подработчики через пятнадцать минут уходят домой, а трое постоянных остаются.

**Скорая помощь.** В смене четыре бригады. Если вызовов больше — подключают резервные, но не больше восьми бригад одновременно: больше не поместится в диспетчерскую и не проедет по дворам. Если и этого не хватает — вызовы кладут в очередь. А если и очередь переполнена — вызывают соседнюю станцию, отдают вызов им.

**Библиотека с читальным залом.** В читальном зале двенадцать столов. Это core — они есть всегда. В коридоре можно поставить дополнительные стулья — до двадцати всего. Если читателей больше двадцати — они ждут в очереди у входа. Если и очередь длиннее, чем помещение позволяет, — администратор вежливо говорит «приходите завтра».

**Общее во всех случаях** одно: есть **базовый штат** (не уходит), есть **предел расширения** (сколько можно добавить), есть **очередь** (где ждут), и есть **правило, что делать, когда всё переполнено**. Именно эти четыре вещи и настраивает `ThreadPoolExecutor`.

## Теория

### Зачем лезть внутрь

`Executors.newFixedThreadPool(4)` — это удобно. Но за удобством спрятаны решения, которые принимали **не вы**. Пул сам решил: очередь у него неограниченная, размер фиксированный, политика отказа — «бросай исключение». В девяноста процентах случаев это разумно. В оставшихся десяти — приводит к тому, что приложение падает с `OutOfMemoryError` из-за очереди в миллион задач, или висит, потому что задачи копятся быстрее, чем обрабатываются.

`ThreadPoolExecutor` — это тот же пул, но с открытой панелью управления. Вы сами выбираете размеры, очередь, поведение при переполнении, время жизни лишних потоков. Это сложнее, но честнее.

### Четыре параметра

Главный конструктор `ThreadPoolExecutor` выглядит так:

```java
public ThreadPoolExecutor(
    int corePoolSize,                  // базовый штат
    int maximumPoolSize,               // предел расширения
    long keepAliveTime,                // сколько живёт лишний поток
    TimeUnit unit,                     // единица времени для keepAlive
    BlockingQueue<Runnable> workQueue, // очередь задач
    ThreadFactory threadFactory,       // фабрика потоков
    RejectedExecutionHandler handler   // политика отказа
)
```

Четыре из них — основные. Разберём каждый.

### corePoolSize: базовый штат

Это **минимальное** число потоков, которые пул держит постоянно. Они создаются по мере прихода задач (если только вы не вызвали `prestartAllCoreThreads()`), но **не уничтожаются**, даже если простаивают. Даже если `keepAliveTime` давно истёк.

Базовый штат — это ваши постоянные сотрудники. Они на смене всегда.

### maximumPoolSize: предел расширения

Это **максимальное** число потоков, которые пул может создать. Когда задач больше, чем базовый штат может обработать, и очередь переполнена — пул создаёт **дополнительные** потоки, вплоть до этого предела.

Это ваши подработчики. Их зовут, только когда совсем прижало.

### keepAliveTime: сколько живёт лишний поток

Дополнительные потоки (те, что сверх `corePoolSize`) после `keepAliveTime` простоя **уничтожаются**. Базовые — нет.

По умолчанию `keepAliveTime` применяется только к потокам сверх `corePoolSize`. Если хотите, чтобы и базовые умирали от простоя, — вызовите `allowCoreThreadTimeOut(true)`.

### workQueue: очередь задач

Тип очереди определяет **поведение пула под нагрузкой**. Это самый важный параметр для понимания того, что произойдёт, когда задач больше, чем потоков.

Вот основные варианты.

**`LinkedBlockingQueue` без размера** — неограниченная очередь. Задачи копятся в памяти. Пул никогда не создаст больше `corePoolSize` потоков (потому что очередь «никогда не полна»), и `maximumPoolSize` фактически игнорируется. Если задачи приходят быстрее, чем выполняются, — очередь растёт, память кончается, `OutOfMemoryError`.

**`LinkedBlockingQueue` с размером** — ограниченная очередь. Когда она заполняется, пул создаёт новые потоки до `maximumPoolSize`. Когда и они заняты, и очередь полна — срабатывает `RejectedExecutionHandler`.

**`ArrayBlockingQueue`** — тоже ограниченная, но на массиве фиксированного размера. Быстрее `LinkedBlockingQueue` по памяти, но требует заранее знать ёмкость.

**`SynchronousQueue`** — очередь «нулевой длины». Каждая задача либо сразу передаётся свободному потоку, либо под неё создаётся новый. Если свободных потоков нет и создавать новый нельзя (упёрлись в `maximumPoolSize`) — срабатывает `RejectedExecutionHandler`. Это очередь `newCachedThreadPool`.

**`PriorityBlockingQueue`** — очередь с приоритетами. Задачи извлекаются в порядке приоритета, а не в порядке прихода. Полезно, когда есть важные и не очень важные задачи.

**`DelayQueue`** — задачи становятся доступны только через указанное время. Используется в `ScheduledThreadPoolExecutor`.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> в продакшене используйте <em>ограниченную</em> очередь. Неограниченная очередь — это мина замедленного действия: под нагрузкой она съест всю память. Размер очереди — это ваш «буфер», и у него должен быть предел.
</div>

### RejectedExecutionHandler: что делать при переполнении

Когда и `maximumPoolSize` достигнут, и очередь полна — новая задача **отвергается**. Что именно произойдёт, определяет `RejectedExecutionHandler`. Есть четыре стандартные политики.

**`AbortPolicy`** (по умолчанию) — бросает `RejectedExecutionException`. Вызывающий код должен её поймать и решить, что делать.

```java
new ThreadPoolExecutor.AbortPolicy()
```

**`CallerRunsPolicy`** — задача выполняется **в вызывающем потоке**. Тот, кто вызвал `execute()`, сам её и выполнит. Это создаёт «обратное давление»: если пул перегружен, вызывающий поток тоже начинает работать, и новые задачи он подаёт медленнее. Часто это самый разумный выбор для серверных приложений.

```java
new ThreadPoolExecutor.CallerRunsPolicy()
```

**`DiscardPolicy`** — задача **молча отбрасывается**. Ни исключения, ни уведомления. Опасно: задачи теряются без следа. Используйте, только если точно знаете, что потеря задач допустима.

```java
new ThreadPoolExecutor.DiscardPolicy()
```

**`DiscardOldestPolicy`** — отбрасывается **самая старая** задача в очереди, а новая ставится на её место. Имеет смысл, когда важны свежие данные, а старые можно потерять (например, обновление котировок).

```java
new ThreadPoolExecutor.DiscardOldestPolicy()
```

Можно написать и свою политику — реализовать интерфейс `RejectedExecutionHandler`. Например, логировать отказы и слать метрику.

### Порядок принятия решений

Вот как `ThreadPoolExecutor` решает, что делать с новой задачей. Порядок строгий, и его полезно запомнить.

1. **Если потоков меньше, чем `corePoolSize`** — создать новый поток и дать ему задачу.
2. **Иначе — попытаться положить задачу в очередь.** Если очередь приняла — готово.
3. **Если очередь полна, а потоков меньше, чем `maximumPoolSize`** — создать новый поток и дать ему задачу.
4. **Иначе** — применить `RejectedExecutionHandler`.

Обратите внимание на второй шаг: **сначала очередь, потом новые потоки**. Это значит, что при использовании неограниченной очереди шаг 3 **никогда не наступает** — очередь «никогда не полна», и пул не растёт выше `corePoolSize`. Это классическая ловушка, из-за которой `newFixedThreadPool` ведёт себя не так, как ожидают.

### Визуально

```text
Задача пришла
     │
     ▼
┌──────────────────────────────────────┐
│ Потоков < corePoolSize?              │
│   да → создать поток, дать задачу    │
│   нет → ▼                            │
└──────────────────────────────────────┘
     │
     ▼
┌──────────────────────────────────────┐
│ Очередь приняла задачу?              │
│   да → готово                        │
│   нет → ▼                            │
└──────────────────────────────────────┘
     │
     ▼
┌──────────────────────────────────────┐
│ Потоков < maximumPoolSize?           │
│   да → создать поток, дать задачу    │
│   нет → ▼                            │
└──────────────────────────────────────┘
     │
     ▼
   RejectedExecutionHandler
```

### Пример: свой пул

Соберём пул под конкретную задачу: не больше четырёх потоков, очередь на двадцать задач, при переполнении — выполняем в вызывающем потоке.

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

public class Main {
    public static void main(String[] args) {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
            2,                                  // corePoolSize
            4,                                  // maximumPoolSize
            60, TimeUnit.SECONDS,               // keepAliveTime
            new ArrayBlockingQueue<>(20),       // очередь на 20 задач
            new ThreadPoolExecutor.CallerRunsPolicy()
        );

        for (int i = 0; i < 30; i++) {
            int id = i;
            pool.execute(() -> {
                System.out.println("Задача " + id + " в " + Thread.currentThread().getName());
                try { Thread.sleep(100); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            });
        }

        pool.shutdown();
    }
}
```

**Что здесь важно.** База — два потока. Под нагрузкой пул вырастет до четырёх. Очередь — двадцать задач. Если придут ещё — `CallerRunsPolicy` заставит `main` сам выполнить задачу, что замедлит подачу новых и даст пулу разгрестись. Ни одна задача не потеряется, ни одна не бросит исключения.

### Параметры через Executors

Полезно знать, какие параметры стоят за готовыми фабриками.

**`newFixedThreadPool(n)`** — это:

```java
new ThreadPoolExecutor(n, n, 0L, TimeUnit.MILLISECONDS,
    new LinkedBlockingQueue<Runnable>())
```

`core = max = n`, очередь неограниченная. Пул не растёт и не сжимается. Задачи копятся в очереди бесконечно.

**`newCachedThreadPool()`** — это:

```java
new ThreadPoolExecutor(0, Integer.MAX_VALUE, 60L, TimeUnit.SECONDS,
    new SynchronousQueue<Runnable>())
```

`core = 0`, `max = Integer.MAX_VALUE`, очередь нулевая. Каждая задача — либо свободному потоку, либо новый поток. Простаивающие потоки умирают через 60 секунд.

**`newSingleThreadExecutor()`** — это:

```java
new ThreadPoolExecutor(1, 1, 0L, TimeUnit.MILLISECONDS,
    new LinkedBlockingQueue<Runnable>())
```

Один поток, очередь неограниченная. Последовательная обработка.

Теперь вы видите, **почему** они ведут себя так, как ведут. И можете решить, подходит вам это или нужен свой пул.

### Метрики и мониторинг

`ThreadPoolExecutor` умеет рассказывать о себе. Полезные методы:

- **`getPoolSize()`** — сколько потоков сейчас в пуле.
- **`getActiveCount()`** — сколько выполняют задачи.
- **`getQueue().size()`** — сколько задач в очереди.
- **`getCompletedTaskCount()`** — сколько задач выполнено.
- **`getLargestPoolSize()`** — максимум, до которого пул когда-либо разрастался.

Эти метрики стоит отдавать в систему мониторинга. Если очередь растёт — пора увеличивать пул или добавлять мощности. Если `getActiveCount()` всегда равен `corePoolSize`, а очередь пуста — пул переразмерен, можно уменьшить.

### Частые ошибки

**Ошибка 1: неограниченная очередь.** Самая частая и самая опасная. Задачи копятся, память кончается. В продакшене — только ограниченная очередь.

**Ошибка 2: `maximumPoolSize` меньше `corePoolSize`.** Конструктор бросит `IllegalArgumentException`. Проверяйте.

**Ошибка 3: `corePoolSize = maximumPoolSize` с ограниченной очередью.** Тогда пул никогда не создаст дополнительных потоков: очередь заполнится, а `maximum` уже равен `core`. Пул начнёт отвергать задачи раньше, чем вы ожидаете.

**Ошибка 4: забыть `shutdown()`.** Как и с `Executors` — программа не завершится.

**Ошибка 5: использовать `DiscardPolicy` без метрик.** Задачи молча теряются. Если это допустимо — убедитесь, что вы хотя бы считаете, сколько потеряно.

**Ошибка 6: один пул для CPU-bound и I/O-bound.** Первые занимают потоки, вторые ждут. В итоге оба типа мешают друг другу. Лучше — два пула.

### Аналогия с кафе

Вернёмся к началу. **`corePoolSize`** — три постоянных бариста. **`maximumPoolSize`** — три плюс пять подработчиков, всего восемь. **`keepAliveTime`** — пятнадцать минут: если подработчик не нужен пятнадцать минут, он уходит. **`workQueue`** — очередь заказов: двадцать чеков на держателе. **`RejectedExecutionHandler`** — что делает администратор, когда и очередь полна, и все восемь заняты: `AbortPolicy` — говорит «извините, заказы не принимаем»; `CallerRunsPolicy` — сам встаёт за стойку и делает кофе; `DiscardPolicy` — молча выкидывает чек; `DiscardOldestPolicy` — выкидывает самый старый чек и принимает новый.

Хороший управляющий подбирает эти параметры под поток посетителей. Плохой — оставляет «по умолчанию» и удивляется, почему в час пик всё встало.

## Микрозадача 1: показать, что max не работает с неограниченной очередью

**Задача:** Создайте `ThreadPoolExecutor` с `core=2`, `max=4`, `keepAlive=1s` и **неограниченной** `LinkedBlockingQueue`. Отправьте 10 задач, каждая спит 500 мс и печатает имя потока. Убедитесь, что работают только два потока — `max` не задействован.

**Решение:**

```java
import java.util.concurrent.LinkedBlockingQueue;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
            2, 4, 1, TimeUnit.SECONDS,
            new LinkedBlockingQueue<>()  // неограниченная
        );

        for (int i = 0; i < 10; i++) {
            int id = i;
            pool.execute(() -> {
                System.out.println("Задача " + id + " в " + Thread.currentThread().getName());
                try { Thread.sleep(500); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            });
        }

        pool.shutdown();
        pool.awaitTermination(10, TimeUnit.SECONDS);
    }
}
```

**Возможный вывод:**

```text
Задача 0 в pool-1-thread-1
Задача 1 в pool-1-thread-2
Задача 2 в pool-1-thread-1
Задача 3 в pool-1-thread-2
...
```

Только `thread-1` и `thread-2`. `thread-3` и `thread-4` не появляются.

**Разбор:** очередь неограниченная, значит, она всегда принимает задачу. Пул доходит до шага 2 («попытаться положить в очередь») и на нём останавливается — шаг 3 («создать дополнительный поток») недостижим. `maximumPoolSize = 4` оказывается мёртвой настройкой. Именно так работает `newFixedThreadPool` — и именно поэтому его `max` (равный `core`) ни на что не влияет, кроме как на ваши ожидания.

## Микрозадача 2: ограниченная очередь оживляет max

**Задача:** Повторите предыдущую задачу, но замените очередь на `ArrayBlockingQueue<>(2)`. Отправьте 10 задач. Убедитесь, что теперь работают **четыре** потока, а часть задач отвергается по `AbortPolicy`.

**Решение:**

```java
import java.util.concurrent.ArrayBlockingQueue;
import java.util.concurrent.ThreadPoolExecutor;
import java.util.concurrent.TimeUnit;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
            2, 4, 1, TimeUnit.SECONDS,
            new ArrayBlockingQueue<>(2)
        );

        for (int i = 0; i < 10; i++) {
            int id = i;
            try {
                pool.execute(() -> {
                    System.out.println("Задача " + id + " в " + Thread.currentThread().getName());
                    try { Thread.sleep(500); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
                });
            } catch (java.util.concurrent.RejectedExecutionException e) {
                System.out.println("Задача " + id + " отвергнута");
            }
        }

        pool.shutdown();
        pool.awaitTermination(10, TimeUnit.SECONDS);
    }
}
```

**Возможный вывод:**

```text
Задача 0 в pool-1-thread-1
Задача 1 в pool-1-thread-2
Задача 2 в pool-1-thread-3
Задача 3 в pool-1-thread-4
Задача 4 отвергнута
...
```

**Разбор:** теперь очередь может принять только две задачи. Когда приходит третья и очередь полна, пул создаёт третий поток (потому что `max = 4`), потом четвёртый. Когда и они заняты, и очередь полна — `AbortPolicy` бросает `RejectedExecutionException`. Первые четыре задачи выполняются, две ждут в очереди, остальные отвергаются. Совсем другая картина, чем в предыдущей задаче, — при тех же `core` и `max`.

Разберём отложенные и периодические задачи: `schedule`, `scheduleAtFixedRate`, `scheduleWithFixedDelay`, и почему `Timer` — устаревший инструмент, которым пользоваться не стоит. А то ведь таймеры — это то, с чего начинается любой фоновый процесс: «подожди минуту и сделай», «каждые пять секунд проверь». Дело нехитрое, но с массой тонкостей.

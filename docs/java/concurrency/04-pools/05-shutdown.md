# 4.5. Корректное завершение пула

## Где вы это уже видели

**Закрытие ресторана.** Повара уже не принимают новые заказы, но те, что на плите, — доводят до конца. Гости доедают, официанты убирают со столов. Через полчаса двери запираются, свет гаснет. Никто не вышвыривает посетителей с недоеденным ужином.

**Увольнение сотрудника.** Есть два способа. Первый: «доработай текущий проект, сдай дела, и мы расстанемся». Второй: «сдай пропуск, охрана, выведи». Первый — `shutdown()`. Второй — `shutdownNow()`.

**Остановка конвейера на заводе.** Сначала перестают подавать новые детали, потом дают доехать тем, что уже на ленте, и только когда лента пуста — выключают. Иначе детали застрянут в механизмах, и придётся разбирать.

**Выключение компьютера.** Обычное «Завершение работы» — программа ждёт, пока приложения сохранят данные, закроют файлы и выключатся сами. «Принудительное завершение» (долгое нажатие кнопки питания) — просто рубит питание, и вы теряете несохранённое. Разница та же.

**Общее во всех случаях** одно: завершение — это **процесс**, а не одномоментный акт. Его можно провести вежливо и грубо. Вежливо — дольше, но безопаснее. Грубо — быстрее, но с потерями. И почти всегда — вежливо предпочтительнее, если только вы не в чрезвычайной ситуации.

## Теория

### Почему это важно

В предыдущих главах мы упоминали `shutdown()` вскользь: «вызовите — и программа завершится». Пора разобраться детально, потому что **неправильное завершение пула** — источник трёх типов проблем, каждая из которых встречается в реальном коде постоянно.

**Проблема первая: программа не завершается.** Забыли `shutdown()` — потоки пула продолжают работать, JVM не может выйти. Пользователь закрывает окно — оно не закрывается. Админ нажимает «остановить сервис» — процесс висит. Приходится убивать через `kill -9`.

**Проблема вторая: задачи теряются.** Вызвали `shutdownNow()` — все задачи, которые не успели начаться, отброшены. Все задачи, которые выполнялись, — прерваны на середине. Если это была отправка писем или запись в базу — часть писем не ушла, часть транзакций не завершилась.

**Проблема третья: задачи не доработали.** Вызвали `shutdown()` — пул перестал принимать новые задачи, но продолжает выполнять текущие. А вы сразу вышли из `main`. Пока пул что-то делает, JVM уже хочет завершиться. Получается либо зависание, либо потеря задач.

Правильное завершение решает все три. Правил немного, но их нужно соблюдать.

### Два метода: shutdown и shutdownNow

Разница между ними — принципиальная.

**`shutdown()`** — **вежливое** завершение:

1. Пул перестаёт принимать **новые** задачи. Попытка вызвать `execute()` после `shutdown()` бросает `RejectedExecutionException`.
2. Задачи, которые **уже** в очереди, — выполняются до конца.
3. Задачи, которые **уже** выполняются, — дорабатывают.
4. После завершения всех задач потоки пула уничтожаются.
5. Метод `shutdown()` **не блокируется** — он возвращает управление сразу, а пул продолжает работу в фоне.

**`shutdownNow()`** — **грубое** завершение:

1. Пул перестаёт принимать новые задачи.
2. Задачи из очереди **извлекаются** и возвращаются в виде `List<Runnable>` — они **не будут** выполнены.
3. Выполняющиеся задачи **прерываются** через `interrupt()`.
4. Потоки пула завершаются, как только задачи отреагируют на прерывание (или доработают, если игнорируют прерывание).
5. Возвращает список задач, которые не успели начаться.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> <code>shutdown()</code> — по умолчанию. <code>shutdownNow()</code> — только когда действительно нужно немедленно (завершение процесса, аварийная остановка). И даже тогда — подумайте, не жалко ли задач.
</div>

### awaitTermination: дождаться завершения

`shutdown()` **не блокируется**. Это значит, что после вызова `shutdown()` пул ещё работает — дорабатывает задачи. Если вы сразу выходите из `main`, JVM будет ждать, пока все потоки пула не завершатся, но вы не будете знать, когда это произойдёт, и не сможете что-то сделать после.

`awaitTermination` — метод, который **блокируется**, пока пул не завершится или не истечёт таймаут.

```java
scheduler.shutdown();
if (scheduler.awaitTermination(10, TimeUnit.SECONDS)) {
    System.out.println("Пул завершился корректно");
} else {
    System.out.println("Пул не завершился за 10 секунд");
}
```

Возвращает `true`, если дождались, `false` — если таймаут истёк. Таймаут **обязателен**: без него `awaitTermination` может ждать вечно, если задача «залипла».

### Канонический паттерн завершения

Вот правильная последовательность. Запомните её, она пригодится в любом проекте.

```java
ExecutorService pool = Executors.newFixedThreadPool(4);
try {
    // отправляем задачи, работаем
    for (int i = 0; i < 10; i++) {
        pool.execute(task);
    }
} finally {
    pool.shutdown();
    try {
        if (!pool.awaitTermination(10, TimeUnit.SECONDS)) {
            // не дождались — идём на грубую силу
            pool.shutdownNow();
            // и ещё раз ждём, уже недолго
            if (!pool.awaitTermination(5, TimeUnit.SECONDS)) {
                System.err.println("Пул не завершился даже после shutdownNow");
            }
        }
    } catch (InterruptedException e) {
        // нас самих прервали во время ожидания — прерываем пул и выходим
        pool.shutdownNow();
        Thread.currentThread().interrupt();
    }
}
```

**Что тут важно.**

**Первое:** `shutdown()` в `finally` — чтобы выполнился даже при исключении.

**Второе:** `awaitTermination` с таймаутом. Если пул завершился сам — идём дальше. Если нет — эскалируем.

**Третье:** `shutdownNow()` как эскалация. Если `shutdown()` + 10 секунд не помогли — значит, какая-то задача «залипла». Прерываем её. Это лучше, чем ждать вечно.

**Четвёртое:** обработка `InterruptedException` от `awaitTermination` — если нас самих прерывают, мы тоже прерываем пул и восстанавливаем флаг. Вежливое поведение.

**Пятое:** второй `awaitTermination` после `shutdownNow` — потому что `shutdownNow` тоже не мгновенный. Задачи могут проигнорировать прерывание (например, если у них `while(true)` без проверки флага), и пул всё равно будет ждать. Если и это не помогло — логируем, но не блокируемся навсегда.

Этот паттерн часто называют «shutdown hook» пула. В библиотеках и фреймворках он реализован именно так.

### try-with-resources: короткий путь

Если вы на Java 19+, `ExecutorService` реализует `AutoCloseable`. Тогда всё упрощается.

```java
try (ExecutorService pool = Executors.newFixedThreadPool(4)) {
    for (int i = 0; i < 10; i++) {
        pool.execute(task);
    }
}
// здесь автоматически вызван shutdown + awaitTermination
```

**Что важно знать:** try-with-resources для `ExecutorService` вызывает **`shutdown()` + `awaitTermination`** с разумным таймаутом. Если задачи не завершаются — он вызовет `shutdownNow()`. То есть работает как канонический паттерн выше, но за вас.

Минус: вы не контролируете таймаут. По умолчанию — довольно большой (порядка суток в некоторых версиях, но это деталь реализации). Если задачи могут «залипнуть» — лучше использовать ручной паттерн с явным таймаутом.

Для учебных задач и небольших программ — try-with-resources отлично.

### Что происходит с задачами в очереди при shutdownNow

Это тонкий момент. `shutdownNow()` возвращает `List<Runnable>` — задачи, которые **были в очереди** и не успели начаться. С ними нужно что-то делать.

```java
List<Runnable> notStarted = pool.shutdownNow();
System.out.println("Не выполнено задач: " + notStarted.size());
```

**Варианты:**

1. **Ничего не делать.** Если задачи идемпотентны и повторятся позже — окей.
2. **Сохранить в лог или файл.** Чтобы потом разобраться, что потеряли.
3. **Выполнить синхронно.** Если потеря недопустима — выполните их сами, в текущем потоке. Медленно, но ничего не теряется.
4. **Отправить в другой пул.** Если у вас есть резервный — отправьте туда.

Выбор зависит от бизнес-логики. Главное — **помнить, что задачи могут потеряться**, и решать, что с этим делать.

**Задачи, которые уже выполнялись**, в список **не попадают**. Они получили `interrupt` и должны сами решить, что делать. Если задача проигнорировала прерывание — она доработает до конца, и `shutdownNow` фактически станет `shutdown`.

### Прерывание и shutdownNow

`shutdownNow()` прерывает выполняющиеся задачи через `Thread.currentThread().interrupt()`. Это значит:

- Если задача спит в `Thread.sleep` — получит `InterruptedException`, проснётся.
- Если задача ждёт в `wait`, `join`, `Condition.await`, `Lock.lockInterruptibly` — получит `InterruptedException`.
- Если задача крутится в `while(true)` без проверки флага — **не узнает** о прерывании, будет работать вечно.

Поэтому в задачах, которые живут долго, важно **проверять флаг прерывания**. Об этом была глава 1.6. Здесь это знание применяется на практике.

```java
pool.execute(() -> {
    while (!Thread.currentThread().isInterrupted()) {
        // работа
    }
    System.out.println("Задача завершилась по прерыванию");
});
```

Так задача корректно отреагирует на `shutdownNow`. Без проверки флага — она просто «не заметит» вежливой просьбы остановиться, и `shutdownNow` придётся ещё долго ждать.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> <code>shutdownNow()</code> — это не «мгновенное убийство». Он <em>прерывает</em> задачи, но задачи могут прерывание проигнорировать. Если задача не проверяет флаг прерывания — она продолжит работу, и пул не завершится.
</div>

### Сравнение: что когда

| | `shutdown()` | `shutdownNow()` |
|---|---|---|
| Новые задачи | Отвергаются | Отвергаются |
| Очередь | Дорабатывается | Возвращается, не выполняется |
| Выполняющиеся | Дорабатывают | Прерываются |
| Блокируется | Нет | Нет |
| Возвращает | `void` | `List<Runnable>` |
| Когда использовать | Обычное завершение | Аварийная остановка |

### Периодические задачи и shutdown

Помните из главы 4.4: `shutdown()` **не отменяет** периодические задачи. Они продолжают выполняться, и пул не завершится, пока они не будут отменены.

```java
ScheduledFuture<?> periodic = scheduler.scheduleAtFixedRate(task, 0, 1, TimeUnit.SECONDS);

// при завершении
periodic.cancel(false);
scheduler.shutdown();
scheduler.awaitTermination(10, TimeUnit.SECONDS);
```

Если забыть `cancel` — `shutdown()` не завершит пул, потому что периодическая задача всё ещё «активна». `awaitTermination` вернёт `false`. Придётся `shutdownNow()`.

`shutdownNow()` периодические задачи **отменяет** — они попадают в «отменённые» и не возвращаются. Это одна из причин, почему `shutdownNow` в этом случае может быть предпочтительнее.

### Хуки завершения JVM

Есть ещё один вариант — **shutdown hook**. Это код, который выполняется при завершении JVM (например, по Ctrl+C или `System.exit()`).

```java
Runtime.getRuntime().addShutdownHook(new Thread(() -> {
    System.out.println("Завершаю пул...");
    pool.shutdown();
    try {
        if (!pool.awaitTermination(10, TimeUnit.SECONDS)) {
            pool.shutdownNow();
        }
    } catch (InterruptedException e) {
        pool.shutdownNow();
        Thread.currentThread().interrupt();
    }
}));
```

Это полезно для **серверных приложений**: когда приходит сигнал остановки (например, от Kubernetes), JVM запускает хук, и пул корректно завершается.

**Осторожно:**

- Хук не сработает при `kill -9` (SIGKILL) — процесс убивается без возможности что-то сделать.
- Хук не должен работать долго — есть таймаут (обычно 30 секунд), после которого JVM убьёт его.
- В хуке нельзя **создавать новые задачи** в пуле — пул уже в процессе завершения.
- Хук не должен бросать исключения — это может помешать другим хукам.

Хук — не замена нормальному `shutdown()`. Это **дополнительная** страховка для случаев, когда приложение завершается извне.

### Антипаттерны

Несколько вещей, которые делать **не надо**.

**Антипаттерн 1: `System.exit()` для «завершения».** `System.exit()` останавливает JVM, не давая пулу доработать. Задачи теряются. Хуки сработают, но это уже аварийное завершение.

**Антипаттерн 2: `shutdownNow()` без сохранения задач.** Задачи из очереди пропали, вы даже не посмотрели, сколько их было. Если это были оплаты — клиенты недовольны.

**Антипаттерн 3: `awaitTermination` без таймаута.** Может ждать вечно. В продакшене — только с таймаутом.

**Антипаттерн 4: `shutdown()` без `awaitTermination` и выход.** Программа «завершилась», а задачи ещё выполняются в фоне. При следующем запуске — неконсистентное состояние.

**Антипаттерн 5: `shutdown()` внутри задачи пула.** Задача, которая вызывает `shutdown()` на своём же пуле. Пул ждёт завершения этой задачи, а задача ждёт завершения пула. Взаимная блокировка — вариант deadlock.

### Аналогия с рестораном

Вернёмся к началу. **`shutdown()`** — это **вежливое закрытие**. Повара не принимают новые заказы, но те, что на плите, — дорабатывают. Гости доедают. Через полчаса двери запираются, свет гаснет.

**`shutdownNow()`** — это **эвакуация**. «Всем выйти, оставить всё как есть!». Повара бросают заказы, гости выбегают с недоеденным. Кто-то остался в туалете — его выводят. Быстро, но неаккуратно.

**`awaitTermination`** — это **ожидание у двери**. Вы стоите и смотрите, как последний гость выходит. С таймаутом — «жду полчаса, потом ухожу». Без таймаута — «жду, пока все не выйдут, даже если это займёт всю ночь».

**Shutdown hook** — это **пожарная тревога**. Срабатывает автоматически при внештатном завершении, и все бегут к выходу по плану эвакуации. Не заменяет нормального закрытия, но страхует на случай, если что-то пошло не так.

## Микрозадача 1: показать разницу shutdown и shutdownNow

**Задача:** Создайте пул на 2 потока. Отправьте 10 задач, каждая спит 1 секунду. Через 500 мс вызовите `shutdownNow()`. Убедитесь, что часть задач не выполнилась — и получите их список.

**Решение:**

```java
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(2);

        for (int i = 0; i < 10; i++) {
            int id = i;
            pool.execute(() -> {
                try {
                    System.out.println("Задача " + id + " начала работу");
                    Thread.sleep(1000);
                    System.out.println("Задача " + id + " завершилась");
                } catch (InterruptedException e) {
                    System.out.println("Задача " + id + " прервана");
                    Thread.currentThread().interrupt();
                }
            });
        }

        Thread.sleep(500);
        List<Runnable> notStarted = pool.shutdownNow();
        System.out.println("Не выполнено задач: " + notStarted.size());

        pool.awaitTermination(5, TimeUnit.SECONDS);
    }
}
```

**Возможный вывод:**

```text
Задача 0 начала работу
Задача 1 начала работу
Задача 0 прервана
Задача 1 прервана
Не выполнено задач: 8
```

**Разбор:** в начале работали только две задачи (пул на два потока). Остальные восемь ждали в очереди. Через 500 мс `shutdownNow` прервал выполняющиеся (0 и 1) и вернул восемь, которые не успели начаться. Все восемь задач **потеряны** — если бы это были письма, они бы не ушли.

## Микрозадача 2: вежливый shutdown

**Задача:** То же самое, но через `shutdown()` вместо `shutdownNow()`. Убедитесь, что **все 10 задач** выполнились до конца.

**Решение:**

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        ExecutorService pool = Executors.newFixedThreadPool(2);

        for (int i = 0; i < 10; i++) {
            int id = i;
            pool.execute(() -> {
                try {
                    System.out.println("Задача " + id + " начала работу");
                    Thread.sleep(1000);
                    System.out.println("Задача " + id + " завершилась");
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            });
        }

        Thread.sleep(500);
        pool.shutdown(); // вежливо

        if (pool.awaitTermination(20, TimeUnit.SECONDS)) {
            System.out.println("Пул завершился корректно, все задачи выполнены");
        } else {
            System.out.println("Пул не завершился за 20 секунд");
        }
    }
}
```

**Возможный вывод:**

```text
Задача 0 начала работу
Задача 1 начала работу
Задача 0 завершилась
Задача 2 начала работу
...
Задача 9 завершилась
Пул завершился корректно, все задачи выполнены
```

**Разбор:** `shutdown()` не тронул ни одну задачу. Все 10 выполнились до конца. Программа подождала 20 секунд — хватило с запасом (10 задач × 1 секунда / 2 потока = около 5 секунд). Вот что такое вежливость на практике.

## 🎯 Самостоятельная задача

Напишите **менеджер пула с корректным завершением и логированием**.

**Постановка:**

1. Класс `ManagedPool` с `ExecutorService` на 4 потока.
2. Метод `submit(Runnable task)` — отправляет задачу.
3. Метод `shutdown()` — выполняет канонический паттерн:
   - `shutdown()`;
   - `awaitTermination(5, TimeUnit.SECONDS)`;
   - если не дождались — `shutdownNow()`, логирует, сколько задач не началось;
   - ещё раз `awaitTermination(5, TimeUnit.SECONDS)`;
   - если всё ещё не завершился — логирует «часть задач проигнорировала прерывание».
4. Метод `getStats()` — возвращает `Map<String, Long>` с полями: `completed`, `rejected`, `notStarted` (из `shutdownNow`), `shutdownTimeMillis`.

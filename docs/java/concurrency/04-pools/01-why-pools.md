# 4.1. Зачем нужны пулы потоков

## Где вы это уже видели

**Ресторан.** В хорошем ресторане официанты работают в штате. Их пятеро, они обслуживают все столики. Когда приходит новый гость — не нанимают нового официанта, а просто говорят: «Столик номер семь». Один из пятерых освободится и обслужит. А если бы на каждого гостя нанимали нового человека — ресторан разорился бы через неделю.

**Колл-центр.** В банке сидят двадцать операторов. Приходит звонок — он попадает в очередь. Свободный оператор берёт трубку, решает вопрос, кладёт трубку, берёт следующий звонок. Операторы не «создаются» под каждый звонок. Они **переиспользуются**.

**Такси-парк.** У компании пятьдесят машин. Заказ приходит — диспетчер назначает свободную. Когда заказ выполнен — машина возвращается в парк и берёт следующий. Никто не покупает новую машину на каждый заказ.

**Доставка.** У службы доставки десять курьеров. Приходит сто заказов — они ложатся в очередь. Курьеры разбирают их по одному: взял заказ, отвёз, взял следующий. Если бы на каждый заказ нанимали нового курьера — через день в городе было бы десять тысяч курьеров, из которых девять тысяч девятьсот стояли бы без дела.

**Общее во всех случаях** одно: есть **фиксированный штат исполнителей** и есть **поток задач**, который через них проходит. Исполнители переиспользуются. Задачи ждут в очереди. Это и есть **пул потоков** — «thread pool».

## Теория

### Цена создания потока

До сих пор мы создавали потоки вручную: `new Thread(...)`, `start()`, `join()`. Для учебных примеров это прекрасно работает. Для реальных программ — не очень. И вот почему.

**Каждый поток занимает память.** У каждого потока есть свой стек. По умолчанию в HotSpot JVM на Linux x64 размер стека — около **1 мегабайта**. Можно изменить через флаг `-Xss`, но по умолчанию — так. Тысяча потоков — примерно гигабайт памяти только под стеки. Десять тысяч потоков — десять гигабайт. На обычной машине это уже не влезет.

**Создание потока — это системный вызов.** Когда вы вызываете `start()`, JVM обращается к операционной системе: «создай мне поток». Операционная система выделяет ресурсы, регистрирует поток в планировщике, настраивает его состояние. Это не мгновенно — это **сотни микросекунд**, а иногда и миллисекунды.

**Переключение контекста — дорого.** Когда потоков много, а ядер мало, планировщик постоянно переключается между ними. Каждое переключение — это сохранение состояния одного потока и восстановление другого. Тысячи инструкций процессора. Если у вас 800 потоков на 8 ядрах — процессор большую часть времени тратит на переключение, а не на полезную работу.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> поток — дорогой ресурс. Создавать его под каждую мелкую задачу — расточительство. Для большого числа задач нужен пул.
</div>

### Что происходит, когда потоков слишком много

Есть наивная идея: «раз потоки полезны — создадим их побольше». Идея плохая. Вот что происходит.

**Первое: конкуренция за процессор.** Если у вас 8 ядер, а потоков 800, — одновременно всё равно работают 8. Остальные 792 стоят в очереди планировщика. Они не ускоряют программу — они **мешают** друг другу. Каждому нужно процессорное время, каждый требует переключения контекста. В итоге программа работает **медленнее**, чем с восемью потоками.

**Второе: конкуренция за память.** 800 потоков × 1 МБ стека = 800 МБ памяти. Плюс накладные расходы на структуры планировщика. На сервере с ограниченной памятью это может закончиться `OutOfMemoryError`.

**Третье: накладные расходы на создание.** Создание 800 потоков занимает время. Если задачи мелкие — например, обработать один запрос, — накладные расходы на создание потока могут превысить время выполнения самой задачи. Получается абсурд: программа тратит больше времени на «нанять работника», чем на «сделать работу».

### Идея пула

Пул потоков решает все три проблемы сразу.

**Идея простая:**

1. Создать **N потоков заранее**, при старте программы. Один раз. Это дорого, но один раз.
2. Создать **очередь задач** — структуру, куда складываются задачи.
3. Каждый поток в цикле: **взять задачу из очереди → выполнить → взять следующую**.
4. Если очередь пуста — поток **ждёт**, пока появится задача.
5. Если очередь полна — новая задача **ждёт**, пока освободится место.

Всё. Никакой магии. Потоки не создаются под каждую задачу — они **переиспользуются**. А задачи проходят через фиксированный «штат исполнителей».

### Как это работает внутри

Концептуально пул выглядит так.

```text
       ┌─────────────────────────────────┐
       │    Очередь задач (BlockingQueue)│
       │  [T1] [T2] [T3] [T4] [T5] ...   │
       └──────────────┬──────────────────┘
                      │
        ┌─────────────┼─────────────┐
        │             │             │
        ▼             ▼             ▼
   ┌─────────┐   ┌─────────┐   ┌─────────┐
   │ Воркер 1│   │ Воркер 2│   │ Воркер N│
   └─────────┘   └─────────┘   └─────────┘
        │             │             │
        └─────┬───────┴───────┬─────┘
              │               │
              ▼               ▼
        (выполняют задачи по одной)
```

Что делает каждый воркер:

```text
пока не сказано «завершайся»:
    задача = очередь.взять()   // ждёт, если пусто
    задача.выполнить()
```

И всё. Воркер не знает, откуда пришла задача и что она делает. Он просто берёт и выполняет. Задачи ничего не знают о воркерах — они просто лежат в очереди и ждут.

Это и есть **разделение ответственности**: задачи описывают «что делать», воркеры — «кто делает», очередь — «когда». Об этом мы говорили в главе 1.2, когда обсуждали разницу между `Thread` и `Runnable`. Только теперь это разделение доведено до полноценной архитектуры.

### Преимущества пула

Четыре главных.

**Первое: переиспользование потоков.** Потоки создаются один раз при старте пула. Дальше — только берут задачи из очереди. Стоимость создания платится один раз, а не на каждую задачу.

**Второе: ограничение параллелизма.** В любой момент времени работают **не больше N** потоков. Это защищает от «слишком много потоков» — и от конкуренции за CPU, и от избытка памяти. N вы выбираете сами, исходя из числа ядер и характера задач.

**Третье: управление очередью.** Задачи не теряются. Если все воркеры заняты — новые задачи ждут в очереди. Если очередь переполнена — можно применить политику отказа (об этом в главе 4.3). Всё под контролем.

**Четвёртое: единая точка управления.** Пул можно остановить, изменить его размер, собрать статистику, дождаться завершения всех задач. С отдельными потоками это пришлось бы делать вручную.

### Когда пул не нужен

Пул — не универсальное решение. Иногда он **не нужен** или даже **вреден**.

**Одна-две задачи.** Если у вас две задачи — проще создать два потока и не заводить пул. Пул — для **многих** задач.

**Очень короткие задачи с высокой частотой.** Если задача выполняется микросекунды, а накладные расходы на очередь — тоже микросекунды, пул может не дать выигрыша. Скорее даже проиграть прямому выполнению в вызывающем потоке. Тут надо мерить.

**CPU-bound задачи с числом потоков больше числа ядер.** Если задача упирается в процессор, а у вас 8 ядер — пул больше 8 потоков только навредит. Каждый лишний поток — это лишнее переключение контекста.

**Задачи, которые сами управляют потоками.** Если задача создаёт свои потоки (например, `ForkJoinPool` — глава 4.6), пул может конфликтовать с этим. Об этом — в следующих главах.

**Виртуальные потоки (Java 21+).** Если у вас I/O-bound задачи, современные виртуальные потоки (глава 7.2) могут заменить пул: они дёшевы и не требуют переиспользования. Об этом — в модуле 7.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> пул — это инструмент для <em>многих мелких задач</em>. Если у вас одна большая задача или задач совсем немного — пул не нужен, хватит обычных потоков.
</div>

### Сколько потоков в пуле

Классический вопрос, на который нет универсального ответа. Но есть эмпирические правила.

**Для CPU-bound задач** — примерно **число ядер**. Восемь ядер — восемь потоков. Больше не даст ускорения, потому что все потоки всё равно конкурируют за те же ядра. Можно чуть больше (на 1–2), чтобы компенсировать моменты, когда поток делает что-то не процессорное, но сильно больше — вредно.

**Для I/O-bound задач** — **больше, чем число ядер**. Поток большую часть времени ждёт (сеть, диск, база данных). Пока один ждёт, другой может работать. Оптимальное число зависит от соотношения «время ожидания / время работы». Если поток 90% времени ждёт — потоков можно иметь в 10 раз больше, чем ядер.

**Смешанные задачи** — тут сложнее. Обычно делают **два пула**: один для CPU-bound, другой для I/O-bound. Или используют отдельные пулы для разных типов задач, чтобы они не мешали друг другу.

Точное число — вопрос измерений. Начните с эмпирических правил и замерьте, что получается на вашей нагрузке.

### Аналогия с рестораном

Вернёмся к началу. **Пул потоков** — это **штат официантов**. Пять человек, работают постоянно, обслуживают все столики. Заказы — это **очередь задач**. Гость сел — заказ в очередь. Свободный официант берёт заказ, обслуживает, возвращается за следующим.

**Создание потока под каждую задачу** — это **нанимать нового официанта на каждый столик**. Только что наняли — он взял заказ, обслужил, ушёл. Пришёл новый гость — нанимаем нового официанта. Абсурд, но именно это мы делали до сих пор в учебных примерах.

**Слишком большой пул** — это **тысяча официантов на двадцать столиков**. Все бегают, толкаются, мешают друг другу, а полезной работы делает столько же, сколько делали бы пятеро. Только зарплату платить надо всем.

**Правильный пул** — это **пять официантов на тридцать столиков**. В пик — все пятеро работают, заказы в очереди. В затишье — сидят, ждут, пьют чай. Спокойно и эффективно.

## Микрозадача 1: измерить цену создания потока

**Задача:** Замерьте время создания и завершения 1000 потоков, каждый из которых ничего не делает (просто пустой `run`). Сравните с временем выполнения 1000 задач в пуле из 10 потоков.

**Решение:**

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        // Вариант 1: 1000 отдельных потоков
        long start = System.currentTimeMillis();
        Thread[] threads = new Thread[1000];
        for (int i = 0; i < 1000; i++) {
            threads[i] = new Thread(() -> {});
            threads[i].start();
        }
        for (Thread t : threads) t.join();
        long directTime = System.currentTimeMillis() - start;
        System.out.println("1000 отдельных потоков: " + directTime + " мс");

        // Вариант 2: пул из 10 потоков, 1000 задач
        ExecutorService pool = Executors.newFixedThreadPool(10);
        start = System.currentTimeMillis();
        for (int i = 0; i < 1000; i++) {
            pool.execute(() -> {});
        }
        pool.shutdown();
        pool.awaitTermination(10, TimeUnit.SECONDS);
        long poolTime = System.currentTimeMillis() - start;
        System.out.println("1000 задач в пуле из 10 потоков: " + poolTime + " мс");
    }
}
```

**Возможный вывод:**

```text
1000 отдельных потоков: 78 мс
1000 задач в пуле из 10 потоков: 12 мс
```

**Разбор:** в первом варианте мы создали 1000 реальных потоков — с системными вызовами, стеком, регистрацией в планировщике. Во втором — создали только 10 потоков и 1000 раз положили задачу в очередь. Разница в **шесть раз**, и это на пустых задачах. Если бы задачи делали хоть что-то полезное, разница в накладных расходах была бы ещё заметнее.

Обратите внимание: на самом деле не 1000 потоков работали одновременно — у вас, скорее всего, 4–16 ядер, и планировщик переключал потоки. Но даже на пустых задачах создание 1000 потоков заняло заметно больше времени, чем 1000 задач в пуле.

## Микрозадача 2: показать проблему «слишком много потоков»

**Задача:** Создайте 5000 потоков, каждый спит 1 секунду. Замерьте, сколько времени займёт выполнение всех. Затем сделайте то же самое через пул из 10 потоков. Сравните.

**Решение:**

```java
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;

public class Main {
    public static void main(String[] args) throws InterruptedException {
        // Вариант 1: 5000 потоков, каждый спит 1 секунду
        long start = System.currentTimeMillis();
        Thread[] threads = new Thread[5000];
        for (int i = 0; i < 5000; i++) {
            threads[i] = new Thread(() -> {
                try { Thread.sleep(1000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            });
            threads[i].start();
        }
        for (Thread t : threads) t.join();
        long directTime = System.currentTimeMillis() - start;
        System.out.println("5000 потоков: " + directTime + " мс");

        // Вариант 2: пул из 10 потоков, 5000 задач
        ExecutorService pool = Executors.newFixedThreadPool(10);
        start = System.currentTimeMillis();
        for (int i = 0; i < 5000; i++) {
            pool.execute(() -> {
                try { Thread.sleep(1000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            });
        }
        pool.shutdown();
        pool.awaitTermination(30, TimeUnit.MINUTES);
        long poolTime = System.currentTimeMillis() - start;
        System.out.println("5000 задач в пуле из 10 потоков: " + poolTime + " мс");
    }
}
```

**Возможный вывод:**

```text
5000 потоков: 1123 мс
5000 задач в пуле из 10 потоков: 500327 мс
```

**Разбор:** вот тут интересный результат, который многих удивляет. Пять тысяч потоков справились за **секунду с небольшим** — потому что все они спали одновременно. А пул из 10 потоков работал **больше восьми минут**, потому что задачи выполнялись по 10 одновременно.

**В чём мораль?** Пул ограничивает параллелизм. Это **преимущество** для CPU-bound задач (не мешаем друг другу), но **проблема** для I/O-bound задач (не используем возможность ждать параллельно). Если задача — «ждать секунду», то 5000 потоков справятся за секунду, а пул из 10 — за 500 секунд. Выбор зависит от задачи.

**Про 5000 потоков и память.** 5000 потоков × ~1 МБ стека = ~5 ГБ памяти. Если у вас меньше — получите `OutOfMemoryError` раньше, чем дождётесь результата. Это ещё одна причина не создавать потоки без ограничений.

# 4.6. ForkJoinPool и RecursiveTask

## Где вы это уже видели

**Разбор большого документа.** Вам дали триста страниц, и нужно найти все упоминания слова «судьба». Что делает разумный человек? Не читает всё подряд. Делит документ на три части, отдаёт трём коллегам. Каждый делит свою часть ещё на три — и так, пока куски не станут совсем маленькими. Каждый быстро просматривает свой кусок, отмечает найденное, возвращает результат. Потом результаты складываются в один список.

**Уборка большого дома.** Вы не начинаете с одной комнаты и не идёте по кругу. Вы делите дом: я — верхний этаж, ты — нижний. Каждый делит свой этаж на комнаты. Если кто-то закончил раньше — идёт помогать другому. В конце всё убрано, и никто не простаивал.

**Параллельная сортировка.** Вам нужно отсортировать миллион чисел. Вместо того чтобы сортировать всё в одном потоке, вы делите массив пополам, каждую половину — ещё пополам, и так до маленьких кусочков, которые сортируются мгновенно. Потом кусочки сливаются обратно в отсортированное целое.

**Помощь коллеге.** В офисе четыре программиста. У одного задача застряла — он ждёт ответа от сервера. Остальные трое заняты своими делами. Но вот второй закончил свою задачу и видит, что у первого ещё висит работа. Он не сидит без дела — берёт часть задач первого и делает их. Потом возвращает результат. Это и есть «кража работы».

**Общее во всех случаях** одно: **большая задача дробится на маленькие**, маленькие решаются параллельно, результаты складываются обратно. И потоки, которые закончили свою работу раньше, — **не простаивают**, а помогают другим. Это и есть `ForkJoinPool` — пул, который умеет дробить и воровать.

## Теория

### Чем ForkJoinPool отличается от ThreadPoolExecutor

До сих пор мы работали с `ThreadPoolExecutor` — плоским пулом. Задача пришла — взяли поток — выполнили — вернули поток в пул. Каждая задача независима, и поток не может «помочь» другой задаче.

`ForkJoinPool` устроен иначе. Он рассчитан на задачи, которые **можно рекурсивно разбить на подзадачи**. И у него есть механизм **work-stealing** — «кража работы»: если поток закончил свои задачи и видит, что у другого потока очередь не пуста, он **забирает** оттуда задачи и выполняет их.

Это даёт два преимущества.

**Первое: эффективное использование ядер.** Если одна ветка рекурсии оказалась «тяжёлой», а другая — «лёгкой», свободные потоки не простаивают, а помогают. В плоском пуле такое невозможно: каждый поток привязан к своей задаче.

**Второе: меньше переключений.** Задачи, которые порождает `fork()`, остаются в **локальной очереди** потока, а не в общей. Поток выполняет их сам, без переключения контекста. Только когда локальная очередь пуста — он идёт «воровать» к другим.

### RecursiveTask и RecursiveAction

`ForkJoinPool` работает с задачами двух типов.

**`RecursiveTask<V>`** — задача, возвращающая результат типа `V`. Наследник `ForkJoinTask<V>`.

**`RecursiveAction`** — задача без результата. Наследник `ForkJoinTask<Void>`.

Оба требуют реализовать метод `compute()` — в нём описывается логика: либо разбить задачу на подзадачи, либо решить её напрямую.

### Структура RecursiveTask

Канонический паттерн выглядит так.

```java
class MyTask extends RecursiveTask<Long> {
    private final long[] data;
    private final int from, to;

    MyTask(long[] data, int from, int to) {
        this.data = data;
        this.from = from;
        this.to = to;
    }

    @Override
    protected Long compute() {
        // база рекурсии: задача достаточно мала — решаем сами
        if (to - from <= THRESHOLD) {
            long sum = 0;
            for (int i = from; i < to; i++) sum += data[i];
            return sum;
        }

        // рекурсивный случай: делим пополам
        int mid = (from + to) / 2;
        MyTask left = new MyTask(data, from, mid);
        MyTask right = new MyTask(data, mid, to);

        left.fork();                // левая — в очередь пула (асинхронно)
        long rightResult = right.compute(); // правая — считаем сами
        long leftResult = left.join();      // ждём левую

        return leftResult + rightResult;
    }
}
```

**Что здесь важно.**

**База рекурсии.** Когда задача достаточно мала (`to - from <= THRESHOLD`), она решается **напрямую**, без дробления. Порог выбирается эмпирически: слишком маленький — много накладных расходов на создание задач, слишком большой — плохо используем параллелизм.

**`fork()`** — отправляет задачу в очередь пула. Асинхронно, сразу возвращает управление.

**`compute()`** — выполняет задачу в текущем потоке. Не асинхронно.

**`join()`** — ждёт завершения задачи и возвращает результат. Если задача уже выполнена — сразу возвращает. Если ещё нет — текущий поток **может помочь** выполнить её (work-stealing в действии).

**Почему `left.fork()` + `right.compute()` + `left.join()`, а не `left.fork(); right.fork(); join(); join();`?** Потому что `fork` + `compute` использует текущий поток для правой задачи, и это эффективнее — не нужно ждать. Если бы вы сделали `fork(); fork();`, обе задачи ушли бы в очередь, а текущий поток сразу встал бы в `join` — простаивал бы.

### Порог: главный параметр

`THRESHOLD` — это число, меньше которого задача решается напрямую. От него зависит производительность.

**Слишком маленький** — например, `THRESHOLD = 1`. Получим миллион задач по одному элементу. Накладные расходы на создание, `fork`, `join` съедят всё преимущество параллелизма. Может оказаться медленнее, чем последовательный алгоритм.

**Слишком большой** — например, `THRESHOLD = 1_000_000`. Получим несколько задач, которые не загружают все ядра. Параллелизма почти нет.

**Как выбрать.** Эмпирически. Начните с `THRESHOLD ≈ 1000–10000` для простых операций (сложение, поиск минимума) и `THRESHOLD ≈ 100–1000` для более сложных (сортировка, сравнение объектов). Замерьте. Если задача «тяжёлая» — порог можно уменьшить, если «лёгкая» — увеличить.

Хорошее эмпирическое правило: **подзадача должна занимать не меньше 1 микросекунды**. Если меньше — накладные расходы на `fork`/`join` превысят выигрыш.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Правило:</strong> <code>ForkJoinPool</code> выгоден, когда задача <em>действительно</em> разбивается на независимые подзадачи и когда подзадачи достаточно крупные. Для мелких задач он проиграет обычному циклу.
</div>

### Work-stealing: как это работает внутри

У каждого потока в `ForkJoinPool` есть **своя двусторонняя очередь** (deque) задач. Когда поток делает `fork()`, задача кладётся **в свой** deque. Когда поток ищет работу — берёт **из своего** deque. Это быстро, без синхронизации.

Если свой deque пуст — поток идёт **воровать** у других. Забирает с **другого конца** чужого deque. Так делается специально: поток-владелец берёт с одного конца, вор — с другого. Они не мешают друг другу, и синхронизация минимальна.

Визуально:

```text
Поток 1: [T1] [T2] [T3] ←── свой конец (берёт отсюда)
         │
         └── воровской конец ←── воры берут отсюда

Поток 2: [T4] [T5] [T6]
Поток 3: пусто → идёт воровать у Потока 1 или 2
```

Это даёт высокую производительность при минимальных блокировках. Именно поэтому `ForkJoinPool` быстрее обычного `ThreadPoolExecutor` для задач типа «разделяй и властвуй».

### Пример: сумма массива

```java
import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.RecursiveTask;
import java.util.Random;

public class Main {
    public static void main(String[] args) {
        long[] data = new long[10_000_000];
        Random random = new Random(42);
        for (int i = 0; i < data.length; i++) data[i] = random.nextInt(100);

        // Последовательная сумма — для сравнения
        long start = System.currentTimeMillis();
        long sequentialSum = 0;
        for (long v : data) sequentialSum += v;
        long sequentialTime = System.currentTimeMillis() - start;

        // Параллельная сумма через ForkJoinPool
        ForkJoinPool pool = new ForkJoinPool();
        start = System.currentTimeMillis();
        long parallelSum = pool.invoke(new SumTask(data, 0, data.length));
        long parallelTime = System.currentTimeMillis() - start;

        System.out.println("Последовательно: " + sequentialSum + " за " + sequentialTime + " мс");
        System.out.println("Параллельно:    " + parallelSum + " за " + parallelTime + " мс");
    }

    static class SumTask extends RecursiveTask<Long> {
        private static final int THRESHOLD = 10_000;
        private final long[] data;
        private final int from, to;

        SumTask(long[] data, int from, int to) {
            this.data = data;
            this.from = from;
            this.to = to;
        }

        @Override
        protected Long compute() {
            if (to - from <= THRESHOLD) {
                long sum = 0;
                for (int i = from; i < to; i++) sum += data[i];
                return sum;
            }
            int mid = (from + to) / 2;
            SumTask left = new SumTask(data, from, mid);
            SumTask right = new SumTask(data, mid, to);
            left.fork();
            long rightResult = right.compute();
            long leftResult = left.join();
            return leftResult + rightResult;
        }
    }
}
```

**Возможный вывод** на машине с 8 ядрами:

```text
Последовательно: 495000213 за 45 мс
Параллельно:    495000213 за 12 мс
```

Параллельная версия в 3–4 раза быстрее. Не в 8 раз — потому что накладные расходы на `fork`/`join` и на синхронизацию всё равно есть, и не все восемь ядер заняты на 100% (сумма массива — операция очень быстрая, память — узкое место).

**Замечание.** На такой простой операции, как сумма, выигрыш невелик. `ForkJoinPool` раскрывается на **более тяжёлых** задачах: сортировка больших массивов, обход деревьев, сложные вычисления.

### RecursiveAction: без результата

Если задача не возвращает результат — используйте `RecursiveAction`.

```java
class IncrementTask extends RecursiveAction {
    private final long[] data;
    private final int from, to;

    IncrementTask(long[] data, int from, int to) {
        this.data = data;
        this.from = from;
        this.to = to;
    }

    @Override
    protected void compute() {
        if (to - from <= THRESHOLD) {
            for (int i = from; i < to; i++) data[i]++;
            return;
        }
        int mid = (from + to) / 2;
        invokeAll(
            new IncrementTask(data, from, mid),
            new IncrementTask(data, mid, to)
        );
    }
}
```

**`invokeAll(task1, task2, ...)`** — удобный метод: делает `fork` для всех, потом `join` для всех. Эквивалентно `fork` + `fork` + `join` + `join`, но короче. Для двух задач — норм. Для многих — может проиграть, потому что все уходят в очередь, а текущий поток сразу ждёт.

### Как получить доступ к ForkJoinPool

**Способ первый: свой пул.**

```java
ForkJoinPool pool = new ForkJoinPool();
Long result = pool.invoke(task);
```

Создаёт пул с числом потоков, равным числу ядер. Можно указать явно:

```java
ForkJoinPool pool = new ForkJoinPool(4);
```

**Способ второй: общий пул.**

```java
ForkJoinPool.commonPool().invoke(task);
```

`ForkJoinPool.commonPool()` — глобальный пул, который используется по умолчанию. Именно в нём работают `parallelStream()` и `CompletableFuture` без явного пула. Число потоков в нём — на один меньше числа ядер (потому что одно ядро «оставляют» основному потоку).

Использовать общий пул удобно, но **осторожно**: если одна задача в нём «залипнет», она повлияет на все остальные, которые используют тот же пул. Для изолированных задач лучше создавать свой пул.

**Способ третий: через `Executors.newWorkStealingPool()`.**

```java
ExecutorService pool = Executors.newWorkStealingPool();
```

Фабричный метод из главы 4.2. По сути — `ForkJoinPool`, но с интерфейсом `ExecutorService`. Удобно, если вы хотите единый интерфейс для разных пулов.

### Где ForkJoinPool реально полезен

**Разделяй и властвуй** — главный сценарий.

- **Сортировка.** `Arrays.parallelSort()` внутри использует `ForkJoinPool`.
- **Свёртка больших массивов.** Сумма, минимум, максимум, среднее.
- **Обход деревьев.** Параллельный обход большой структуры.
- **Параллельные стримы.** `parallelStream()` работает на `ForkJoinPool.commonPool()`.
- **Рекурсивные алгоритмы.** Быстрая сортировка, сортировка слиянием, обход графа.

### Где ForkJoinPool НЕ нужен

**Задачи без рекурсивной структуры.** Если задача не дробится — обычный `ThreadPoolExecutor` проще и быстрее. Не пихайте `ForkJoinPool` туда, где он не нужен.

**Очень короткие задачи.** Накладные расходы на `fork`/`join` съедят весь выигрыш.

**Задачи с общими блокировками.** Если подзадачи конкурируют за один монитор — `ForkJoinPool` не поможет, только навредит: потоки будут простаивать в ожидании.

**I/O-bound задачи.** `ForkJoinPool` рассчитан на CPU-bound. Если задача большую часть времени ждёт сеть или диск — потоки простаивают, и никакая «кража работы» не поможет. Для I/O-bound — обычный `ThreadPoolExecutor` с большим числом потоков, или (Java 21+) виртуальные потоки.

**Задачи, которые сами используют `ForkJoinPool`.** Рекурсия может привести к переполнению очереди и падению. Если задача внутри уже вызывает `ForkJoinPool` — либо используйте общий пул, либо создавайте новый.

### Проблема: commonPool и параллельные стримы

`parallelStream()` использует `ForkJoinPool.commonPool()`. Это значит, что все параллельные стримы в программе делят один пул. Если один стрим «залип» — он блокирует другие.

Кроме того, размер `commonPool` — `Runtime.getRuntime().availableProcessors() - 1`. На машине с 4 ядрами — 3 потока. На сервере с 64 ядрами — 63. Не всегда этого достаточно.

Если нужен изолированный пул для стримов — можно «подсунуть» свой:

```java
ForkJoinPool customPool = new ForkJoinPool(16);
List<Integer> result = customPool.submit(
    () -> list.parallelStream().map(...).collect(toList())
).get();
```

Подробно про `parallelStream` — в главе 6.4. Пока просто помните: **общий пул — общий на всю программу**, и это может быть проблемой.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> <code>ForkJoinPool.commonPool()</code> используется всеми <code>parallelStream()</code> и <code>CompletableFuture</code> без явного пула. Если хотите изоляции — создавайте свой пул и передавайте его явно.
</div>

### Частые ошибки

**Ошибка 1: неверный THRESHOLD.** Слишком маленький — много накладных расходов. Слишком большой — нет параллелизма. Замеряйте.

**Ошибка 2: `fork(); fork(); join(); join();`.** Обе задачи ушли в очередь, текущий поток сразу встал в `join` — простаивает. Лучше: `fork(); compute(); join();`.

**Ошибка 3: блокирующие операции внутри задачи.** `sleep`, `wait`, ввод-вывод — всё это блокирует поток. `ForkJoinPool` не рассчитан на блокировки: он ждёт, что потоки постоянно работают. Блокировка уменьшает эффективный параллелизм.

**Ошибка 4: использовать общий пул для долгих задач.** Задача в `commonPool` может блокировать другие, которые тоже используют `commonPool` (например, `parallelStream` в другом месте программы). Для изоляции — свой пул.

**Ошибка 5: слишком большие подзадачи с общими данными.** Если подзадачи читают-пишут общий массив **без синхронизации**, будут гонки. `ForkJoinPool` не защищает от гонок — он только распределяет работу. Убедитесь, что подзадачи работают с независимыми участками данных.

**Ошибка 6: рекурсия без базы.** Если `compute()` всегда делит задачу и никогда не решает напрямую — бесконечная рекурсия, `StackOverflowError` или зависание.

### Аналогия с разбором документа

Вернёмся к началу. **`ForkJoinPool`** — это **команда из четырёх коллег**, разбирающих большой документ. Большой документ делится на части, части — на ещё меньшие, пока куски не станут совсем маленькими (это `THRESHOLD`). Каждый коллега берёт свою часть.

**`fork()`** — «возьми эту часть и разберись с ней». Коллега берёт и уходит.

**`compute()`** — «я сам разберусь с этой частью прямо сейчас». Коллега не уходит, а делает.

**`join()`** — «покажи, что нашёл». Коллега возвращается и отдаёт результат.

**Work-stealing** — это **помощь коллеге**. Если один закончил свою часть, а у другого ещё много — первый идёт и берёт часть его работы. Не сидит без дела. Именно это делает `ForkJoinPool` особенным: в обычном пуле потоки не могут «помочь» друг другу.

А `commonPool` — это **один общий офис на всю компанию**. Все документы разбираются там. Если один отдел загрузил офис — другим не останется места. Поэтому для больших проектов — свой отдельный офис.

## Микрозадача 1: параллельная сумма

**Задача:** Реализуйте `RecursiveTask<Long>` для суммы массива `long[]` через `ForkJoinPool`. Замерьте время последовательной суммы и параллельной на массиве из 10 миллионов элементов. Сравните.

**Решение:**

```java
import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.RecursiveTask;
import java.util.Random;

public class Main {
    public static void main(String[] args) {
        long[] data = new long[10_000_000];
        Random random = new Random(42);
        for (int i = 0; i < data.length; i++) data[i] = random.nextInt(100);

        long start = System.currentTimeMillis();
        long seq = 0;
        for (long v : data) seq += v;
        long seqTime = System.currentTimeMillis() - start;

        ForkJoinPool pool = new ForkJoinPool();
        start = System.currentTimeMillis();
        long par = pool.invoke(new SumTask(data, 0, data.length));
        long parTime = System.currentTimeMillis() - start;

        System.out.println("Последовательно: " + seq + " за " + seqTime + " мс");
        System.out.println("Параллельно:    " + par + " за " + parTime + " мс");
        System.out.println("Совпадает: " + (seq == par));
        System.out.println("Ускорение: " + (double) seqTime / parTime + "x");
    }

    static class SumTask extends RecursiveTask<Long> {
        private static final int THRESHOLD = 10_000;
        private final long[] data;
        private final int from, to;

        SumTask(long[] data, int from, int to) {
            this.data = data; this.from = from; this.to = to;
        }

        @Override
        protected Long compute() {
            if (to - from <= THRESHOLD) {
                long sum = 0;
                for (int i = from; i < to; i++) sum += data[i];
                return sum;
            }
            int mid = (from + to) / 2;
            SumTask left = new SumTask(data, from, mid);
            SumTask right = new SumTask(data, mid, to);
            left.fork();
            long rightResult = right.compute();
            long leftResult = left.join();
            return leftResult + rightResult;
        }
    }
}
```

**Возможный вывод:**

```text
Последовательно: 495000213 за 42 мс
Параллельно:    495000213 за 11 мс
Совпадает: true
Ускорение: 3.8x
```

**Разбор:** параллельная версия быстрее в 3–4 раза на восьми ядрах. Не в 8 раз — потому что есть накладные расходы на `fork`/`join`, и не все ядра заняты на 100% (память, кэш). Для простой суммы это типично. Для более тяжёлых алгоритмов (сортировка) ускорение будет ближе к числу ядер.

Обратите внимание на `THRESHOLD = 10_000`. Если уменьшить до 100 — получим сто тысяч задач, и накладные расходы могут съесть выигрыш. Если увеличить до 1_000_000 — получим всего десять задач, и параллелизма почти не будет. Правильный порог — на границе, где накладные расходы малы, а параллелизм есть.

## Микрозадача 2: параллельный поиск максимума

**Задача:** Реализуйте `RecursiveTask<Long>` для поиска максимума в массиве. Сравните с последовательным поиском. Убедитесь, что результаты совпадают.

**Решение:**

```java
import java.util.concurrent.ForkJoinPool;
import java.util.concurrent.RecursiveTask;
import java.util.Random;

public class Main {
    public static void main(String[] args) {
        long[] data = new long[10_000_000];
        Random random = new Random(42);
        for (int i = 0; i < data.length; i++) data[i] = random.nextInt(1_000_000);

        long seq = Long.MIN_VALUE;
        for (long v : data) if (v > seq) seq = v;

        ForkJoinPool pool = new ForkJoinPool();
        long par = pool.invoke(new MaxTask(data, 0, data.length));

        System.out.println("Максимум послед.: " + seq);
        System.out.println("Максимум паралл.: " + par);
        System.out.println("Совпадает: " + (seq == par));
    }

    static class MaxTask extends RecursiveTask<Long> {
        private static final int THRESHOLD = 10_000;
        private final long[] data;
        private final int from, to;

        MaxTask(long[] data, int from, int to) {
            this.data = data; this.from = from; this.to = to;
        }

        @Override
        protected Long compute() {
            if (to - from <= THRESHOLD) {
                long max = Long.MIN_VALUE;
                for (int i = from; i < to; i++) if (data[i] > max) max = data[i];
                return max;
            }
            int mid = (from + to) / 2;
            MaxTask left = new MaxTask(data, from, mid);
            MaxTask right = new MaxTask(data, mid, to);
            left.fork();
            long rightMax = right.compute();
            long leftMax = left.join();
            return Math.max(leftMax, rightMax);
        }
    }
}
```

**Возможный вывод:**

```text
Максимум послед.: 999999
Максимум паралл.: 999999
Совпадает: true
```

**Разбор:** структура та же, что и с суммой, но операция объединения — `Math.max`, а не `+`. `ForkJoinPool` не зависит от того, **что** именно вы делаете — он только распределяет работу. Любая ассоциативная операция подойдёт: сумма, минимум, максимум, произведение, конкатенация.

Если хотите проверить, что `THRESHOLD` действительно влияет, запустите с разными значениями и замерьте. На этой задаче разница будет заметна: маленький порог — много задач, большой — мало параллелизма.

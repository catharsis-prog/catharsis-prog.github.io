# 1.2. Создание потока: Thread vs Runnable

## Где вы это уже видели

Всякий раз, когда вы просите кого-то что-то сделать, вы невольно разделяете две вещи: **что делать** и **кто делает**. Разделение это настолько привычное, что вы его не замечаете. А между тем в нём вся суть этой главы.

**Письмо.** Вы пишете письмо, но несёт его почтальон. Письмо — это работа, почтальон — исполнитель. Письмо можно отдать и этому почтальону, и другому, и третьему — лишь бы дошёл. Если бы письмо было частью вас, пришлось бы нести самому. Хорошо ли это? Смотря куда.

**Резолюция.** Начальник пишет на бумаге: «выдать Иванову сто рублей». Это резолюция, то есть задача. Кому её поручить — вопрос отдельный: Иванову, Петрову, Сидорову. Резолюция не прирастает к конкретному чиновнику, и правильно: иначе на каждое новое дело пришлось бы нанимать нового человека.

**Заказ в трактире.** «Принесите мне щи». Щи — заказ, половой — исполнитель. Один и тот же заказ можно отдать любому половому.

**Загрузка файла.** Пользователь нажал «Скачать», а вы не хотите, чтобы интерфейс замёрз на минуту. Значит, загрузку надо оформить как отдельную задачу и отдать потоку.

**Сервер.** Пришёл запрос — его надо обработать в своём потоке, чтобы не задерживать остальные.

**Общий знаменатель** у всех пяти случаев один: есть задача — что нужно сделать, и есть исполнитель — кто это делает. В Java задача и исполнитель — разные объекты, и вся эта глава о том, как их правильно разделять. А те, кто не разделяет, — сами знаете, что с ними бывает.

## Теория

### Два способа создать поток

В Java есть два канонических способа запустить свой поток.

1. **Унаследоваться от класса `Thread`** и переопределить метод `run()`.
2. **Реализовать интерфейс `Runnable`** и передать его в конструктор `Thread`.

Оба рабочие. Но один считается правильным, а второй — устаревшим стилем, который оставили в языке ради обратной совместимости, как оставляют в конторе старого писца: и жалко, и жалованье платить надо. Разберём оба, чтобы понять, почему так.

### Способ первый: наследование от Thread

Класс `Thread` — это обёртка над системным потоком. У него есть метод `run()`, в котором описано, что поток должен делать. По умолчанию он пустой. Значит, если хотите свою работу — переопределите.

```java
public class MyThread extends Thread {
    @Override
    public void run() {
        System.out.println("Работаю в потоке: " + Thread.currentThread().getName());
    }
}
```

Запуск:

```java
public class Main {
    public static void main(String[] args) {
        MyThread thread = new MyThread();
        thread.start();
    }
}
```

Здесь `MyThread` — это одновременно и **задача**, и **исполнитель**. Класс сам себе и работа, и поток. На первый взгляд удобно: создали объект — он же и поток, два дела в одном. В реальности это переплетение и создаёт те самые хлопоты, о которых ниже.

### Способ второй: реализация Runnable

`Runnable` — интерфейс с единственным методом `run()`. Он описывает **задачу** и только её. Никакого отношения к потоку, его жизненному циклу и системным ресурсам.

```java
public class MyTask implements Runnable {
    @Override
    public void run() {
        System.out.println("Работаю в потоке: " + Thread.currentThread().getName());
    }
}
```

Чтобы эта задача выполнилась, её надо передать исполнителю:

```java
public class Main {
    public static void main(String[] args) {
        Runnable task = new MyTask();
        Thread thread = new Thread(task);
        thread.start();
    }
}
```

Теперь роли разделены: `MyTask` — это **что делать**, а `Thread` — это **кто делает**. Задачу можно отдать другому потоку, положить в очередь, передать пулу. Об этом — в модуле 4, но запомните уже сейчас: разделение это не случайное, а намеренное.

### Почему Runnable предпочтительнее

Причин несколько, и все они практические.

**Первая: в Java у класса только один родитель.** Как у человека — только одна мать. Унаследовались от `Thread` — и всё, другого родителя уже не будет, как бы он вам ни понадобился. А интерфейсов можно реализовать сколько угодно — как, впрочем, и бумаг можно подписать несколько. `Runnable` — интерфейс, а значит, места у вас не занимает. Пустяк, а на практике решает многое.

**Вторая: разделение задачи и механизма запуска.** Задача — это «посчитать сумму массива». Механизм — «в каком потоке это выполнить». Это две разные вещи, и смешивать их в одном классе — всё равно что требовать, чтобы писарь умел писать только одну бумагу. Сегодня задача в одном потоке, завтра в пуле из десяти, послезавтра асинхронно. Если задача прибита гвоздями к `Thread`, каждый раз её переписывать. Если это `Runnable` — просто передают другому исполнителю, и дело с концом.

**Третья: переиспользование.** Один и тот же `Runnable` можно запустить в разных потоках, положить в очередь, передать в `ExecutorService`. С наследником `Thread` так не получится: объект одноразовый. Повторный запуск того же объекта бросит исключение, о чём мы подробно поговорим в следующей главе. Как билет на один сеанс: во второй раз контролёр его порвёт.

**Четвёртая: `Thread` сам реализует `Runnable`.** Это значит, что любой `Thread` можно передать туда, где ожидается `Runnable`. Обратное неверно. Выбирая `Runnable`, вы получаете более гибкий тип и, если угодно, более широкие возможности.

Наследование от <code>Thread</code> оставьте для редких случаев, когда действительно нужно расширить поведение самого потока, а не описать работу. ### Лямбда-выражения: короткая форма Runnable

`Runnable` — функциональный интерфейс, у него один абстрактный метод. Значит, вместо анонимного класса можно написать лямбду:

```java
public class Main {
    public static void main(String[] args) {
        Runnable task = () -> System.out.println("Работаю в потоке: " + Thread.currentThread().getName());
        new Thread(task).start();
    }
}
```

Или ещё короче, без промежуточной переменной:

```java
new Thread(() -> System.out.println("Работаю")).start();
```

Для коротких задач это самый читаемый вариант. Если логика большая — лучше вынести её в отдельный класс или метод, иначе `main` превратится в кашу, а каша, как известно, никого ещё до добра не доводила.

### Что происходит при запуске

Метод `start()` — это не «вызвать `run()`». Это команда: создай новый поток и начни в нём выполнять `run()`. Разница между `start()` и `run()` настолько важна, что ей посвящена целая следующая глава. Пока просто запомните: **запускают поток через `start()`, а не через `run()`**. Впрочем, если запустить через `run()`, ничего не сломается. Просто никакого потока не будет. Бумага написана, а писца не позвали.

### Итог: что выбрать

- **Задача** — почти всегда `Runnable`, часто в виде лямбды.
- **Наследование от `Thread`** — только если вам действительно нужно расширить поведение самого потока, а не описать работу. На практике это нужно крайне редко.

Так что если вам случится выбирать — выбирайте `Runnable`. Не потому, что `Thread` плох, а потому, что `Runnable` честнее: он делает только то, что обещает, и не притязает на большее. А в нашем деле скромность — качество не лишнее.

## Микрозадача 1: поток через наследование

**Задача:** Создайте класс, унаследованный от `Thread`, который печатает «Привет из потока» три раза. Запустите его из `main`.

**Решение:**

```java
public class GreetingThread extends Thread {
    @Override
    public void run() {
        for (int i = 0; i < 3; i++) {
            System.out.println("Привет из потока " + getName());
        }
    }

    public static void main(String[] args) {
        GreetingThread thread = new GreetingThread();
        thread.start();
    }
}
```

**Разбор:** внутри `run()` мы вызываем `getName()` без `Thread.currentThread()` — потому что `this` и есть поток, унаследованный от `Thread`, а `getName()` унаследован. Удобно? Да. Но именно эта «удобность» и есть ловушка: класс `GreetingThread` теперь навсегда привязан к `Thread`. Если завтра эту же задачу захочется выполнить в пуле потоков — придётся переписывать. А переписывать, как вы, вероятно, уже заметили, никто не любит.

## Микрозадача 2: та же задача через Runnable

**Задача:** Сделайте то же самое, но через `Runnable`. Сравните объём кода и гибкость.

**Решение:**

```java
public class GreetingTask implements Runnable {
    @Override
    public void run() {
        for (int i = 0; i < 3; i++) {
            System.out.println("Привет из потока " + Thread.currentThread().getName());
        }
    }

    public static void main(String[] args) {
        Thread thread = new Thread(new GreetingTask());
        thread.start();
    }
}
```

**Разбор:** в `run()` теперь нужно явно писать `Thread.currentThread().getName()`, потому что `GreetingTask` — не поток, у него нет своего имени. Зато `GreetingTask` — обычный класс, который можно передать куда угодно: в `Thread`, в пул потоков, в очередь. Одна и та же задача — разные способы исполнения. Разница, на первый взгляд, косметическая, а на поверку — принципиальная.

## 🎯 Самостоятельная задача

Напишите программу с двумя потоками. Один печатает чётные числа от 0 до 20, другой — нечётные от 1 до 19. Каждый поток перед завершением выводит «Поток X закончил».

Оформите задачи через `Runnable`, а не через наследование от `Thread`. В комментарии к коду ответьте: почему вы выбрали `Runnable`, и что пришлось бы изменить в программе, если бы задачи нужно было выполнять не в отдельных потоках, а последовательно.

## 📌 Что дальше

В следующей главе — **«`start()` vs `run()`»**. Разберёмся, почему вызов `run()` напрямую не создаёт поток, что будет при повторном `start()`, и какие ошибки здесь встречаются чаще всего. Ошибки эти, надо сказать, коварные: программа не падает, результат выдаёт, — а результата-то и нет.

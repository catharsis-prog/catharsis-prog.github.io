# 1.5. sleep(), join(), yield()

## Где вы это уже видели

Три положения, каждому знакомые. И во всех трёх — одно и то же недоумение: метод вроде бы простой, а ведёт себя не так, как написано в учебнике.

**Положение первое.** Позвали `sleep()` — поток спит, а остальные, глядишь, стоят. Смотрят, в чём дело: оказалось, во сне он чернильницу не отпустил. Спит, а место занято.

**Положение второе.** Не дождались потока через `join()` — `main` напечатал «конец» раньше, чем рабочий поток начал. Или наоборот: `main` ждёт, а поток всё не заканчивается, и сколько ещё ждать — неизвестно. Тут бы `join()` с таймаутом.

**Положение третье.** Написали `yield()` — и ничего не произошло. Уступил место, а его никто не занял. Или занял, а он и не заметил. В учебниках пишут, что метод полезный, а на практике — как вежливость в пустой приёмной: все довольны, а дела нет.

**Общий знаменатель** у всех трёх случаев один: методы эти не делают того, что подсказывает их название. `sleep` не отпускает чернильницу, `join` не гарантирует, что дождёшься, а `yield` не гарантирует, что уступишь. Разберём каждый как следует, чтобы не ждать от них лишнего.

## Теория

### sleep(): писец дремлет

`Thread.sleep(millis)` приостанавливает текущий поток на указанное число миллисекунд. Поток при этом переходит в состояние `TIMED_WAITING` — то самое, о котором говорили в прошлой главе. По истечении срока он возвращается в `RUNNABLE` и продолжает с того места, где остановился.

```java
try {
    Thread.sleep(1000); // спать одну секунду
} catch (InterruptedException e) {
    Thread.currentThread().interrupt();
}
```

У метода есть две вещи, которые надо запомнить крепко.

**Первая: `sleep()` не отпускает монитор.** Если поток спит внутри `synchronized`-блока — монитор остаётся при нём. Другие потоки, которым этот монитор нужен, будут стоять в `BLOCKED`, пока он не проснётся и не выйдет из блока. Как писец, который уснул над бумагой: спит, а чернильница при нём, и никто другой ею не воспользуется. Это одна из самых частых причин «зависаний», которые на поверку оказываются просто чьим-то долгим сном.

**Вторая: `sleep()` не точен.** Вы просите сто миллисекунд — поток может проспать сто десять, сто пятьдесят, а при невезении и секунду. Планировщик операционной системы не обязан будить поток ровно в назначенный момент. `sleep(100)` означает «не раньше чем через сто миллисекунд», а не «ровно через сто». Это важно, если вы меряете время или строите на `sleep` какую-нибудь точную периодичность — не стройте.

<div style="background-color: #1E0F33; border-left: 4px solid #B388FF; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #B388FF;">Замечание:</strong> <code>Thread.sleep</code> — статический метод. Он усыпляет <em>тот поток, который его вызвал</em>, а не тот, у которого вы его «вызвали» через ссылку. <code>thread.sleep(1000)</code> усыпит текущий поток, а не <code>thread</code>. Это одна из классических ловушек: код выглядит так, будто вы усыпляете <code>thread</code>, а на деле спите сами.
</div>

Ещё одна деталь: `sleep()` может быть прерван. Если кто-то вызовет `interrupt()` на спящем потоке — тот проснётся раньше срока и получит `InterruptedException`. Об этом — в следующей главе, но знать заранее полезно.

### join(): писец ждёт соседа

`thread.join()` — это команда «подожди, пока `thread` не завершится». Вызывается он на объекте другого потока, а действует на текущий: текущий поток останавливается и ждёт, пока указанный поток не закончит работу.

```java
Thread worker = new Thread(() -> {
    try {
        Thread.sleep(2000);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
    System.out.println("Рабочий закончил");
});

worker.start();
worker.join(); // main ждёт, пока worker не завершится
System.out.println("main дождался");
```

**Вывод:**

```text
Рабочий закончил
main дождался
```

Без `join()` порядок был бы обратным — мы это видели в главе 1.3. `start()` возвращает управление сразу, `main` бежит вперёд и печатает свою строку, не дожидаясь рабочего. `join()` этот бег останавливает. Как если бы вы не просто поручили писцу бумагу, а встали у его стола и ждали, пока он не кончит: без этого — уйдёте, а бумага останется недописанной.

**Ключевая тонкость: без таймаута `join()` ждёт вечно.** Если поток, которого вы ждёте, никогда не завершится — вы будете ждать ровно столько же. Это одна из причин, по которой `join()` без таймаута считается опасным. Поток может попасть в дедлок, зациклиться, ждать чего-то, чего никогда не произойдёт, — а вы всё стоите и стоите.

Поэтому у `join()` есть перегрузка с таймаутом:

```java
worker.join(1000); // ждать не дольше одной секунды
```

Он ждёт указанное время и возвращает управление — дождался или нет. Проверить, дождались ли, можно через `worker.isAlive()`:

```java
worker.join(1000);
if (worker.isAlive()) {
    System.out.println("Не дождались, работаем дальше");
}
```

В состоянии потока `join()` отражается так: без таймаута — `WAITING` (ждём сигнала «поток завершился»), с таймаутом — `TIMED_WAITING`.

**Ещё одна тонкость: `join()` реагирует на `interrupt()`.** Если во время ожидания кто-то прервёт текущий поток — он выйдет из `join()` с `InterruptedException`. Это правильное поведение: вечное ожидание в `join()` — как раз та ситуация, которую `interrupt()` и призван прерывать.

### yield(): писец уступает место

`Thread.yield()` — самая странная из трёх методов. Формально она означает: «я не против уступить процессор, если кому-то ещё нужно». На практике это **всего лишь подсказка планировщику**, и планировщик вправе её проигнорировать.

```java
for (int i = 0; i < 1000; i++) {
    System.out.println(i);
    Thread.yield(); // «уступи, если есть кому»
}
```

Что при этом происходит на самом деле — зависит от операционной системы, версии JVM, загрузки машины и фазы луны. Поток остаётся в состоянии `RUNNABLE`: он не «ждёт», не «спит» и не «блокируется». Он просто сообщает: «если есть другие желающие — я не против». Других желающих может не быть. Или они могут быть, а планировщик всё равно решит оставить процессор за вами.

<div style="background-color: #251445; border-left: 4px solid #00E5D1; padding: 1rem; margin: 1.5rem 0;">
  <strong style="color: #00E5D1;">Важно:</strong> <code>yield()</code> в реальном коде практически не используется. Он остался в языке с ранних версий, когда планировщики были примитивнее, и в учебниках кочует из книги в книгу как «метод для уступки процессора». Полагаться на него нельзя: ни порядка выполнения, ни гарантированной паузы, ни fairness он не обеспечивает. Если вам нужно, чтобы поток уступил — используйте <code>sleep(0)</code> или, что чаще правильнее, пересмотрите архитектуру: если потоки «мешают» друг другу, дело обычно не в <code>yield</code>, а в том, что их слишком много.
</div>

В конторе это выглядит так: писец привстал и объявил: «я не против уступить место, если кому нужно». Все кивнули. Никто не встал. Писец сел обратно и продолжил. Или, что хуже: вся контора начала привставать и садиться — вежливость соблюдена, а бумаги не двигаются.

### Сравнение: что делает каждый метод

Чтобы не путаться, вот короткая сводка.

| Метод | Что делает | Состояние потока | Гарантии |
|---|---|---|---|
| `sleep(ms)` | Приостанавливает текущий поток на `ms` | `TIMED_WAITING` | Не раньше `ms`; монитор не отпускает |
| `join()` | Ждёт завершения указанного потока | `WAITING` | Дождётся, если поток завершится; может ждать вечно |
| `join(ms)` | Ждёт завершения не дольше `ms` | `TIMED_WAITING` | Вернётся через `ms`, дождался или нет |
| `yield()` | Подсказывает планировщику «можно уступить» | `RUNNABLE` | Никаких |

Заметьте: только `sleep` и `join` имеют хоть какие-то гарантии, и обе они — «не раньше» или «не дольше», а не «ровно». `yield` не гарантирует ничего. Запомните это хорошенько.

### Как это связано с состояниями

Мы уже говорили об этом в прошлой главе, но повторим, чтобы закрепилось.

`sleep()` переводит поток в `TIMED_WAITING`. `join()` без таймаута — в `WAITING`, с таймаутом — в `TIMED_WAITING`. `yield()` оставляет поток в `RUNNABLE` — потому что поток и не ждёт ничего, и не спит; он просто готов, как и был. Разница между этими состояниями и есть разница между тремя методами: один усыпляет, другой заставляет ждать чужого завершения, третий вежливо намекает. Только и всего.

## Микрозадача 1: join() без таймаута

**Задача:** Покажите, что `main` без `join()` завершается раньше рабочего потока, а с `join()` — после.

**Решение:**

```java
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            try {
                Thread.sleep(1000);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
                return;
            }
            System.out.println("Рабочий закончил");
        });

        System.out.println("--- Без join ---");
        Thread first = new Thread(worker::run);
        first.start();
        System.out.println("main закончил");

        Thread.sleep(1500); // дать первому отработать и не смешать вывод

        System.out.println("--- С join ---");
        Thread second = new Thread(worker::run);
        second.start();
        second.join();
        System.out.println("main закончил");
    }
}
```

**Возможный вывод:**

```text
--- Без join ---
main закончил
Рабочий закончил
--- С join ---
Рабочий закончил
main закончил
```

**Разбор:** в первом случае мы запустили поток через `start()` и сразу пошли дальше. `main` напечатал свою строку и завершился, а рабочий поток ещё спал. Во втором — после `start()` вызвали `join()` и `main` встал, пока рабочий не закончит. Обратите внимание на промежуточный `Thread.sleep(1500)` — он нужен, чтобы вывод первой части не смешался со второй, а не потому, что так надо делать в жизни. В реальном коде так не пишут: если нужно дождаться потока — вызывают `join()`, а не `sleep()`. `sleep()` не гарантирует, что другой поток успел; `join()` гарантирует. Разница та же, что между «подождать, пока часы пробьют» и «дождаться, пока часы пробьют»: первое — надежда, второе — метод.

## Микрозадача 2: join() с таймаутом

**Задача:** Покажите, что `join(timeout)` возвращает управление через указанное время, даже если поток ещё не завершился. Проверьте через `isAlive()`.

**Решение:**

```java
public class Main {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            try {
                Thread.sleep(3000);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });

        worker.start();

        System.out.println("Ждём не больше секунды...");
        worker.join(1000);

        if (worker.isAlive()) {
            System.out.println("Не дождались, работаем дальше");
        } else {
            System.out.println("Дождались, всё хорошо");
        }

        worker.join(); // на всякий случай — дождаться и не оставить висящий поток
        System.out.println("main закончил");
    }
}
```

**Возможный вывод:**

```text
Ждём не больше секунды...
Не дождались, работаем дальше
main закончил
```

**Разбор:** рабочий поток спит три секунды, а `join(1000)` ждёт только одну. Через секунду `main` просыпается, проверяет `isAlive()` — поток ещё жив, значит, не дождались. `main` идёт дальше, а потом вызывает `join()` без таймаута, чтобы не оставить рабочий поток висеть: к этому моменту осталось ещё две секунды, и `main` их честно ждёт. Обратите внимание, что без второго `join()` программа всё равно завершилась бы корректно, но main закончил бы свою работу, а рабочий поток ещё спал бы — и в некоторых сценариях это может привести к неожиданностям. Привычка дожидаться своих потоков, если они запущены вручную, — хорошая.

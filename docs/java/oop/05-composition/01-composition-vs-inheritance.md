# 1. Композиция vs наследование

## Где вы это уже видели

Четыре модуля мы учились пользоваться наследованием: разбирались, когда оно уместно, как его писать, какие у него тонкости, и в уроке 7 модуля 3 честно признали — иногда оно вредит. Пора поговорить о том, что делать **вместо** него, когда оно вредит.

Речь пойдёт о **композиции** — о том, чтобы не наследоваться, а **содержать**. Слово страшное, идея простая: вместо «моя машина **является** транспортным средством» — «в моей машине **есть** двигатель». И это «есть» часто оказывается и гибче, и надёжнее, и просто понятнее.

**Ситуация первая.** Вы собираете компьютер. У вас есть материнская плата, процессор, оперативная память, видеокарта, жёсткий диск. Вы не «наследуете» компьютер от процессора и не «делаете» процессор частью компьютера через `extends`. Вы **вставляете** процессор в сокет — и компьютер работает, пока процессор на месте. Захотите поменять процессор — достанете один, вставите другой. Система при этом не меняется.

**Ситуация вторая.** Вы готовите кофе. У вас есть кофемашина, и в неё вставляется капсула. Вы не «делаете» кофемашину разновидностью капсулы — вы **используете** капсулу. Захотите другой вкус — достанете одну капсулу, вставите другую. Кофемашина одна, капсул много. И если завтра появится новый вкус — вы просто купите новые капсулы, а машину менять не нужно.

**Ситуация третья.** Вы работаете в компании, и у вас есть начальник. Вы не «являетесь» начальником — вы **имеете** начальника. Начальник может смениться — вы останетесь собой. В компаниях, где «начальник — это часть тебя» (как наследование), смена начальника ломала бы всю вашу работу. А в компаниях, где «у тебя есть начальник» (как композиция), — просто приходит новый, и вы продолжаете работать.

**Ситуация четвёртая.** Вы пишете отчёт и вставляете в него таблицу из Excel. Вы не «делаете» отчёт разновидностью таблицы — вы **содержите** её внутри. Таблицу можно заменить, обновить, удалить — отчёт останется отчётом. А если бы отчёт был унаследован от таблицы, — любое изменение в таблице ломало бы отчёт.

**Ситуация пятая.** Вы играете в игру, и у персонажа есть инвентарь: меч, щит, зелья. Инвентарь — это **список предметов**, которые персонаж **содержит**. Он не «является» мечом и не «является» зельем. Захотите поменять меч — выкинете старый, возьмёте новый. Персонаж при этом не меняется.

**Ситуация шестая.** Вы видите код, в котором `class Stack extends ArrayList`, и понимаете, что это плохо. Или `class Order extends Customer`, и понимаете, что это бессмысленно. Или `class StringUtils extends String` — и понимаете, что это невозможно (String — final). Но что делать вместо? Как правильно? Именно об этом урок.

Если хотя бы одна из этих ситуаций вам знакома — урок для вас.

## Два отношения: «is-a» и «has-a»

Мы уже говорили об этом в уроке 1 модуля 3, но повторим, потому что это фундамент.

**«Is-a»** (является) — это отношение **наследования**. Кошка **является** животным. Сотрудник **является** человеком. Круг **является** фигурой. Наследование выражает именно это: «мой класс — частный случай другого класса».

**«Has-a»** (имеет) — это отношение **композиции**. У машины **есть** двигатель. У заказа **есть** список товаров. У пользователя **есть** адрес. Композиция выражает: «мой класс **содержит** другой объект и использует его».

Это не «взаимоисключающие» отношения. Часто у класса есть и то, и другое: у `Manager` есть родитель (`Employee`) и есть поле (`List<Employee> subordinates`). Но важно понимать, **какое отношение** вы выражаете — от этого зависит, использовать `extends` или поле.

**Главное правило:** **если можно сказать «X является Y» без всяких «но» — это наследование. Если «у X есть Y» — это композиция.** И большая часть связей в реальном коде — это «has-a», а не «is-a». Поэтому композиция используется чаще, чем кажется на первый взгляд.

## Что такое композиция

**Композиция** — это когда класс **содержит** другой объект в качестве поля и **делегирует** ему часть работы.

Вот как это выглядит:

```java
class Engine {
    void start() {
        System.out.println("Двигатель запущен");
    }

    void stop() {
        System.out.println("Двигатель остановлен");
    }
}

class Car {
    private final Engine engine;

    Car(Engine engine) {
        this.engine = engine;
    }

    void start() {
        engine.start();
    }

    void stop() {
        engine.stop();
    }
}
```

Здесь `Car` **содержит** `Engine`. `Car.start()` **делегирует** вызов `engine.start()`. `Car` не наследует `Engine` — он его использует.

Что это даёт:

- **Гибкость.** Двигатель можно поменять — `car` получит новый `Engine` и будет работать с ним. Без перекомпиляции `Car`.
- **Изоляция.** Изменения в `Engine` затрагивают `Car` только через его публичный интерфейс. Внутренности `Engine` можно менять — `Car` не заметит.
- **Тестируемость.** В тестах `Car` можно подставить «заглушку» `FakeEngine`, которая ничего не делает, но записывает вызовы. `Car` этого не заметит.
- **Комбинируемость.** Из `Engine`, `Wheel`, `Transmission` и других компонентов можно собрать **разные** машины: легковую, грузовую, спортивную. Наследование такой гибкости не даёт.

## Композиция vs наследование: сравнение

Сравним на конкретном примере. Задача: сделать `Stack` (стек — структура «последним пришёл, первым вышел»).

**Через наследование:**

```java
class Stack extends ArrayList<Object> {
    void push(Object item) {
        add(item);
    }

    Object pop() {
        return remove(size() - 1);
    }

    Object peek() {
        return get(size() - 1);
    }
}
```

Работает. Стек «является» списком, у него есть все методы списка, плюс свои. Но есть проблемы:

- **`Stack` имеет лишние методы.** `add(int, Object)`, `remove(int)`, `set`, `sort` и ещё десятки — все доступны, хотя для стека они бессмысленны. Кто-то может вызвать `stack.add(0, "элемент")` и «вставить» элемент в середину — с точки зрения `Stack` это катастрофа.
- **`Stack` наследует `equals`, `hashCode`, `toString` от `ArrayList`.** Это может быть нежелательно: у стека и списка может быть разная семантика равенства.
- **Изменения в `ArrayList` ломают `Stack`.** Если `ArrayList` добавит новый метод, — `Stack` его тоже получит. Если `ArrayList` изменит реализацию — поведение `Stack` может измениться неожиданно.

**Через композицию:**

```java
class Stack {
    private final List<Object> items = new ArrayList<>();

    void push(Object item) {
        items.add(item);
    }

    Object pop() {
        if (items.isEmpty()) {
            throw new IllegalStateException("Стек пуст");
        }
        return items.remove(items.size() - 1);
    }

    Object peek() {
        if (items.isEmpty()) {
            throw new IllegalStateException("Стек пуст");
        }
        return items.get(items.size() - 1);
    }

    boolean isEmpty() {
        return items.isEmpty();
    }

    int size() {
        return items.size();
    }
}
```

Теперь `Stack` **содержит** список, но не «является» им. У него только те методы, которые нужны: `push`, `pop`, `peek`, `isEmpty`, `size`. Никаких `add(int, Object)` и `sort`. Никто не может «влезть» в середину.

Что мы потеряли? Возможность передать `Stack` туда, где ожидается `List`. Но это, скорее всего, **не нужно**: `Stack` — не `List`, и если функции нужен `List`, — ей и надо передавать `List`, а не `Stack`.

Что мы получили? **Честную семантику.** `Stack` — это стек. Он не притворяется списком. Его интерфейс — это его интерфейс, а не «всё, что есть у `ArrayList`».

**Это и есть тот самый случай, о котором мы говорили в уроке 7 модуля 3:** «Stack extends ArrayList» — это «наследование, которое врёт». Композиция — лекарство от этой лжи.

## Когда композиция лучше

Композиция почти всегда лучше, кроме тех случаев, когда она **хуже**. Серьёзно: «предпочитайте композицию наследованию» — это не догма, а **правило большого пальца**. Оно работает в 90% случаев. В 10% — наследование уместно, и его надо использовать.

Вот когда композиция **точно** лучше.

**Когда «is-a» не выполняется.** Если `Stack` — не `ArrayList`, если `Order` — не `Customer`, если `UserService` — не `Validator`, — наследование формально работает, но врёт. Композиция — честна.

**Когда нужна гибкость.** Если компонент может меняться (двигатель, капсула, стратегия оплаты), — композиция позволяет заменить его без изменения «главного» класса. Наследование такой гибкости не даёт: наследник фиксируется при компиляции.

**Когда наследник не использует всё, что даёт родитель.** Если у `Stack` есть 40 методов `ArrayList`, из которых используются 3, — это «раздутый интерфейс». Композиция даёт только то, что нужно.

**Когда наследование нарушает инкапсуляцию.** Когда `Square` «переопределяет» `setWidth` в `Rectangle`, чтобы сохранить инвариант, — это нарушение. Композиция может выразить то же самое без нарушения.

**Когда иерархия становится глубокой.** Пять уровней наследования — это уже проблема (мы говорили в уроке 7 модуля 3). Композиция позволяет строить **плоские** структуры: `Order` содержит `Customer`, `List<Item>`, `PaymentMethod` — но не наследует ни от чего из них.

**Когда нужно комбинировать несколько «способностей».** Класс может содержать **несколько** компонентов. Наследоваться от нескольких классов нельзя — а «содержать» можно.

## Когда наследование всё-таки лучше

Не всё так однозначно. Наследование **уместно**, когда:

**«Is-a» выполняется и стабильно.** Если `Cat` **действительно** `Animal` и это не изменится, — наследование нормально. Если `Money` — это `Value` и это не изменится, — тоже.

**Есть общая реализация, которую наследники используют.** Если у `Animal` есть `eat()` и `sleep()`, и все наследники используют их, — наследование экономит код. Без него пришлось бы либо дублировать, либо выносить в утилитный класс.

**Иерархия закрыта.** Если вы **точно знаете**, что подтипов ровно N, и они не изменятся, — наследование может быть уместно. В Java 17 для этого есть `sealed`, но и без него — если иерархия стабильна, наследование работает.

**Абстрактный класс как «каркас».** Если вы хотите дать наследникам «каркас» с абстрактными методами для переопределения, — наследование уместно. Это «шаблонный метод», о котором будем говорить в уроке 4.

**Главное — не смешивать мотивации.** Если вы наследуетесь, потому что «это **является** тем» — нормально. Если потому что «хочу использовать код родителя» — плохо, используйте композицию.

## Аналогия, которая помогает

Хорошая аналогия — **конструктор LEGO vs готовые модели**.

**Наследование** — это как **готовая модель**. Вы покупаете собранный самолёт. Он красивый, летает, всё работает. Но если вы захотите поменять крылья, — придётся разбирать и собирать заново. И если производитель поменяет конструкцию модели, — ваша перестанет подходить к новым деталям.

**Композиция** — это как **конструктор LEGO**. У вас есть кубики, из которых можно собрать что угодно. Захотите поменять крылья — отцепите одни, прицепите другие. Захотите сделать из самолёта машину — разберите, соберите заново. Гибко, но нужно больше «деталей».

И вот важная деталь: **в реальной жизни почти всё — это конструктор**. Самолёт — это двигатели, крылья, шасси, система управления. Кофемашина — это нагреватель, помпа, отсек для капсул. Компьютер — это процессор, память, диски. Редко что-то «является» чем-то одним — обычно это **набор** компонентов.

Наследование — это как «готовая модель»: работает, пока не понадобится менять. Композиция — «конструктор»: гибче, но требует понимания, из чего что собирается.

**Правило хорошего тона:** **начинайте с конструктора**. Если окажется, что модель стабильна и менять её не нужно, — можно «склеить» её в готовую. Не наоборот: если начать с готовой модели и захотеть её разобрать, — будет больно.

## Микрозадача 1

Вот три пары классов. Для каждой определите: это «is-a» (можно наследовать) или «has-a» (нужна композиция)?

1. `Car` и `Engine`
2. `Cat` и `Animal`
3. `Order` и `List<Item>`

### Разбор

**1. `Car` и `Engine` — «has-a».** У машины есть двигатель. Машина не «является» двигателем. Композиция:

```java
class Car {
    private final Engine engine;
    // ...
}
```

**2. `Cat` и `Animal` — «is-a».** Кошка является животным. Наследование уместно (если `Animal` не слишком широкое):

```java
class Cat extends Animal {
    // ...
}
```

**3. `Order` и `List<Item>` — «has-a».** У заказа есть список товаров. Заказ не «является» списком товаров. Композиция:

```java
class Order {
    private final List<Item> items;
    // ...
}
```

**Мораль.** Из трёх пар только одна — наследование. Это типичное соотношение: большая часть связей в реальном коде — композиция.

## Микрозадача 2

Вот класс. Определите, что в нём не так с точки зрения наследования, и перепишите его через композицию.

```java
class Order extends ArrayList<Item> {
    private String customerName;

    Order(String customerName) {
        this.customerName = customerName;
    }

    double total() {
        double sum = 0;
        for (Item item : this) {
            sum += item.getPrice();
        }
        return sum;
    }

    String getCustomerName() {
        return customerName;
    }
}
```

### Разбор

**Что не так.** `Order` наследует `ArrayList<Item>`. То есть «заказ **является** списком товаров». Это неправда: заказ — это **документ**, у которого **есть** список товаров, плюс имя клиента, плюс, возможно, адрес, дата, статус.

Что это значит на практике:

- **`Order` имеет все методы `ArrayList`.** `add`, `remove`, `set`, `sort`, `clear`, `subList` — всё доступно. Хотя «заказу» они не нужны и могут сломать инварианты.
- **`Order` не может наследоваться от чего-то ещё.** Если завтра понадобится, чтобы `Order` был, например, `Document` — нельзя (Java не даёт множественного наследования).
- **`Order` наследует `equals`, `hashCode`, `toString` от `ArrayList`.** Это некорректно: у заказа и списка может быть разная семантика.
- **Любой код может «испортить» `Order`**, добавив товар в середину или удалив не тот. Стек и заказ — структуры с инвариантами, которые наследование не защищает.

**Как переписать через композицию:**

```java
class Order {
    private final String customerName;
    private final List<Item> items;

    Order(String customerName) {
        if (customerName == null || customerName.isEmpty()) {
            throw new IllegalArgumentException("Имя клиента обязательно");
        }
        this.customerName = customerName;
        this.items = new ArrayList<>();
    }

    void addItem(Item item) {
        if (item == null) {
            throw new IllegalArgumentException("Товар не может быть null");
        }
        items.add(item);
    }

    void removeItem(Item item) {
        items.remove(item);
    }

    double total() {
        double sum = 0;
        for (Item item : items) {
            sum += item.getPrice();
        }
        return sum;
    }

    String getCustomerName() {
        return customerName;
    }

    List<Item> getItems() {
        return Collections.unmodifiableList(items);
    }
}
```

Теперь `Order` **содержит** список — но не «является» им. У него только те методы, которые нужны: `addItem`, `removeItem`, `total`, `getItems`. Никаких `sort`, `clear`, `subList`. И `getItems` возвращает **неизменяемое представление**, чтобы снаружи не меняли список в обход `Order`.

**Что мы потеряли?** Возможность передать `Order` туда, где ожидается `List<Item>`. Но это, скорее всего, не нужно: если функции нужен список товаров — ей и надо передавать `List<Item>`, а не `Order`.

**Мораль.** «Order extends ArrayList» — это классический пример «наследования, которое врёт». Композиция — правильное решение.

## Самостоятельная задача

- как выразить «у пользователя есть список ролей» — через поле или через наследование?

Затем ответьте на вопрос: если завтра понадобится, чтобы у пользователя был **не один** адрес (например, домашний и рабочий), — что придётся менять в вашей структуре? Это проще, чем если бы `User` **наследовался** от `Address`? Почему?

## Что дальше

Мы разобрались, что такое композиция и почему «предпочитайте композицию наследованию» — это не просто лозунг. В следующем уроке — **«Агрегация и композиция»** — мы поговорим о **видах** композиции. Оказывается, «содержать» можно по-разному: одно дело — «у меня есть список друзей» (агрегация, объекты живут отдельно), другое — «у меня есть сердце» (композиция, объекты создаются и умирают вместе). И это различие важно для того, как проектировать классы и их жизненный цикл.

А пока — маленькое упражнение на наблюдательность. Откройте любой свой проект (или открытый проект на Java) и найдите все `extends`. Для каждого задайте вопрос: **это «is-a» или «has-a»?** Если «has-a» (то есть класс наследуется от чего-то, что логичнее было бы содержать), — это кандидат на рефакторинг. Просто найдите. Не переделывайте (пока). Понимание того, где `extends` — это «правильно», а где — «долг», — уже большой шаг к более чистому коду.

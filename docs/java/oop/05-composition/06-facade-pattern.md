# 6. Паттерн «Фасад»

## Где вы это уже видели

Пять уроков мы говорили о композиции: как класс содержит другие классы, как делегирует им работу, как зависит от интерфейсов и получает зависимости снаружи. Всё это — про **внутреннее устройство**. Пора поговорить о том, как **показать** это устройство наружу — или, наоборот, **спрятать**.

Фасад — это паттерн о том, как **упростить** работу со сложной подсистемой. У вас есть десять классов, которые работают вместе, — и вы даёте клиенту **один** класс, который умеет «включить всё сразу». Клиент не знает про десять классов, он знает только про один. Это и есть фасад.

**Ситуация первая.** Вы уходите из дома. Вам нужно: выключить свет, выключить газ, выключить воду, закрыть окна, поставить сигнализацию, выключить кондиционер. Шесть действий. Но в **умном доме** есть **одна кнопка** «Я ушёл» — и она делает всё это разом. Вы нажимаете одну кнопку, а «под капотом» — шесть действий. Это и есть фасад: одна кнопка вместо шести.

**Ситуация вторая.** Вы заказываете в интернет-магазине. Вам нужно: выбрать товар, добавить в корзину, оформить заказ, оплатить, выбрать доставку, отследить. Шесть шагов. Но в приложении есть **одна кнопка** «Купить в один клик» — и она делает всё это разом (если у вас сохранены адрес и карта). Это фасад: одна кнопка вместо шести.

**Ситуация третья.** Вы включаете компьютер. Вам нужно: подать питание, запустить BIOS, загрузить ОС, запустить службы, войти в систему. Пять шагов. Но вы нажимаете **одну** кнопку «Power» — и всё это происходит. Вы не думаете про BIOS и службы, вы просто включаете компьютер. Это фасад: одна кнопка вместо пяти.

**Ситуация четвёртая.** Вы в отеле. Вам нужно: забронировать номер, оплатить, заселиться, получить ключ, узнать про завтрак. Пять шагов. Но ресепшн делает всё это **за вас**: вы общаетесь с одним человеком, а он «дёргает» нужные службы. Это фасад: одна точка контакта вместо пяти.

**Ситуация пятая.** Вы в ресторане. Вы говорите официанту: «Борщ и салат». Официант передаёт заказ на кухню, кухня — повару, повар — на раздачу. Вы не общаетесь с поваром, не ищете, где взять хлеб, не оплачиваете отдельно каждое блюдо. Вы работаете с **официантом**, а он — с подсистемой. Это фасад: одна точка контакта, за которой — сложная подсистема.

**Ситуация шестая.** Вы смотрите на код и видите:

```java
class SmartHome {
    void leaveHome() {
        lightController.turnOffAll();
        gasController.shutOff();
        waterController.shutOff();
        windowController.closeAll();
        securitySystem.arm();
        airConditioner.turnOff();
    }
}
```

— и понимаете, что `leaveHome()` **собрал** шесть вызовов в один. Клиенту не нужно помнить про шесть контроллеров — он вызывает один метод. Знакомо? Тогда этот урок для вас.

## Что такое фасад

**Фасад** — это класс, который **предоставляет простой интерфейс** к сложной подсистеме. Клиент работает с фасадом, а фасад — с подсистемой. Клиент не знает про внутреннее устройство, он знает только про фасад.

Формально у фасада три части.

**Подсистема.** Набор классов, которые работают вместе. Они сложные, у них много методов, они знают друг о друге.

**Фасад.** Один класс, который «собирает» типичные сценарии работы с подсистемой. У него несколько **простых** методов, которые вызывают **много** методов подсистемы.

**Клиент.** Работает с фасадом, а не с подсистемой напрямую.

Вот как это выглядит:

```java
// Подсистема
class LightController {
    void turnOn() { System.out.println("Свет включён"); }
    void turnOff() { System.out.println("Свет выключен"); }
    void turnOffAll() { System.out.println("Свет выключен везде"); }
}

class GasController {
    void shutOff() { System.out.println("Газ перекрыт"); }
}

class WaterController {
    void shutOff() { System.out.println("Вода перекрыта"); }
}

class WindowController {
    void closeAll() { System.out.println("Окна закрыты"); }
}

class SecuritySystem {
    void arm() { System.out.println("Сигнализация включена"); }
}

class AirConditioner {
    void turnOff() { System.out.println("Кондиционер выключен"); }
}

// Фасад
class SmartHomeFacade {
    private final LightController light = new LightController();
    private final GasController gas = new GasController();
    private final WaterController water = new WaterController();
    private final WindowController windows = new WindowController();
    private final SecuritySystem security = new SecuritySystem();
    private final AirConditioner airConditioner = new AirConditioner();

    void leaveHome() {
        light.turnOffAll();
        gas.shutOff();
        water.shutOff();
        windows.closeAll();
        security.arm();
        airConditioner.turnOff();
    }

    void arriveHome() {
        security.disarm();
        light.turnOn();
        // ...
    }
}
```

Клиент:

```java
SmartHomeFacade home = new SmartHomeFacade();
home.leaveHome();   // одна строчка вместо шести
```

Клиент **не знает** про `LightController`, `GasController`, `SecuritySystem`. Он знает только про `SmartHomeFacade` и его методы `leaveHome` / `arriveHome`. Всё остальное — «под капотом».

**Ключевая идея:** фасад **не заменяет** подсистему. Подсистема остаётся сложной, у неё остаются все методы. Фасад — это **дополнительный** слой, который **упрощает** типичные сценарии.

## Фасад vs просто «метод, который вызывает много методов»

Может показаться, что фасад — это «просто метод, который вызывает другие методы». И это правда — но не вся.

**Простой метод** — это когда **один класс** вызывает методы **нескольких** других классов. Он может быть в любом месте, у него может не быть «официального» статуса фасада.

**Фасад** — это **осознанный** дизайн-паттерн. У него есть **намерение**: «я хочу упростить работу с подсистемой». И у него есть **структура**:

- фасад **содержит** подсистему (через поля);
- фасад **делегирует** ей работу (через методы);
- клиент **работает только** с фасадом, не с подсистемой напрямую;
- фасад **не добавляет** новой логики — он только **собирает** вызовы.

Если вы просто написали метод `doEverything()`, который вызывает пять методов, — это может быть фасадом, а может — «методом, который делает слишком много». Разница в **намерении** и **структуре**.

Фасад — это **соглашение**: «этот класс — точка входа в подсистему». Клиент знает, что если ему нужно что-то от подсистемы — он идёт в фасад. А если он идёт в подсистему напрямую — он **нарушает** это соглашение.

## Зачем нужен фасад

Фасад решает несколько задач, и все они — про **упрощение**.

**Скрыть сложность.** Подсистема может состоять из десяти классов с сотней методов. Клиенту не нужно про них знать — ему нужен **один** метод «сделать типичное». Фасад это обеспечивает.

**Уменьшить связанность.** Клиент **не зависит** от подсистемы. Он зависит только от фасада. Если подсистема изменится (например, `LightController` переименует метод `turnOffAll` в `switchOffEverything`) — клиент не пострадает: фасад адаптируется, клиент — нет.

**Дать «правильный» вход.** Подсистема может быть «универсальной» — у неё много методов, и не все они нужны клиенту. Фасад даёт **правильный** вход: только те операции, которые нужны.

**Упростить тестирование.** Если клиент работает с фасадом, — в тестах можно подменить фасад заглушкой. Не нужно «мокать» всю подсистему.

**Сделать код читаемым.** `home.leaveHome()` читается лучше, чем шесть вызовов подряд. И намерение («я ухожу») видно сразу.

## Фасад в реальном коде

Фасад используется повсюду, часто — не называясь «фасадом». Несколько примеров.

**`javax.faces` (JSF).** `FacesContext` — это фасад над множеством подсистем: жизненный цикл, компоненты, валидация, рендеринг. Клиент работает с `FacesContext`, а он «дёргает» нужные подсистемы.

**`java.sql.DriverManager`.** `getConnection(url)` — фасад над пулом соединений, драйверами, конфигурацией. Клиент не знает про `Driver`, `Connection`, `DataSource` — он просто получает `Connection` по URL.

**Spring `JdbcTemplate`.** Фасад над JDBC: `query`, `update`, `execute` — и «под капотом» работа с `Connection`, `Statement`, `ResultSet`, обработка исключений, закрытие ресурсов. Клиент пишет одну строчку — а Spring делает двадцать.

**SLF4J.** `LoggerFactory.getLogger(...)` — фасад над логгерами (Logback, Log4j, JUL). Клиент работает с `Logger`, а **какой** логгер за ним — не важно.

**`Files`.** `Files.readAllLines(path)` — фасад над `FileInputStream`, `BufferedReader`, `InputStreamReader`, обработкой исключений, закрытием ресурсов. Клиент — одна строчка.

**`HttpClient` (Java 11+).** `HttpClient.send(request, ...)` — фасад над сокетами, TLS, HTTP/2, пулом соединений. Клиент — один вызов.

Во всех примерах — одна и та же идея: **клиент работает с простым интерфейсом, а сложность — «под капотом»**.

## Фасад vs другие паттерны

Фасад легко спутать с другими паттернами. Полезно различать.

**Фасад vs Адаптер.** Адаптер **преобразует** интерфейс (чтобы несовместимые классы могли работать вместе). Фасад **упрощает** интерфейс (чтобы клиенту было легче). Адаптер — «переводчик», фасад — «швейцар».

**Фасад vs Декоратор.** Декоратор **добавляет** поведение (оборачивает объект). Фасад **упрощает** интерфейс (собирает много вызовов в один). Декоратор — «дополнение», фасад — «сокращение».

**Фасад vs Медиатор.** Медиатор **координирует** взаимодействие между объектами (они общаются через медиатора, а не напрямую). Фасад **упрощает** работу с подсистемой (клиент общается с фасадом, а не с подсистемой). Медиатор — «посредник», фасад — «точка входа».

**Фасад vs Singleton.** Singleton — про **один экземпляр**. Фасад — про **упрощение интерфейса**. Часто фасад делают Singleton'ом (один фасад на подсистему), но это не обязательно.

**Фасад vs Strategy.** Strategy — про **взаимозаменяемые алгоритмы**. Фасад — про **упрощение**. Strategy — «выбор», фасад — «сокращение».

Общее правило: **фасад — это про «упростить», а не про «преобразовать», «дополнить» или «координировать»**.

## Аналогия, которая помогает

Хорошая аналогия — **швейцар в отеле**.

Представьте, что вы в отеле. У вас есть десять потребностей: заказать такси, забронировать столик в ресторане, купить билеты в театр, заказать еду в номер, постирать одежду, вызвать врача, купить цветы, заказать экскурсию, обменять валюту, распечатать документы.

**Без швейцара** вы бы обзванивали десять разных служб, искали номера, объясняли, что вам нужно, договаривались о времени. Это **сложно**.

**С швейцаром** вы просто говорите: «Мне нужно такси в аэропорт и столик в ресторане на 8». Швейцар **сам** звонит в такси, **сам** бронирует столик, **сам** согласовывает время. Вы получаете результат, но не участвуете в процессе.

**Швейцар** — это фасад. Он **не делает** работу сам (не водит такси, не готовит еду) — он **делегирует** нужным службам. Но **для вас** он — одна точка входа, и это удобно.

**`leaveHome()`** — это как «швейцар, который знает, что нужно сделать, когда гость уходит». Вы говорите «я ухожу», а он «дёргает» нужные службы.

**Ключевая мысль:** **швейцар не заменяет службы** — он **координирует** их для вас. Так же и фасад: он **не заменяет** подсистему — он **упрощает** работу с ней.

И ещё одна деталь: **вы можете пойти в службу напрямую**, если хотите. Например, позвонить в ресторан сами. Швейцар не **запрещает** это — он просто **упрощает**. Фасад — то же самое: подсистема **доступна**, но **фасад** — удобнее.

## Микрозадача 1

Вот код. Определите, что в нём «подсистема», что «фасад» и что «клиент». Есть ли здесь проблемы?

```java
class Order {
    // ...
}

class OrderRepository {
    void save(Order order) { /* ... */ }
}

class PaymentProcessor {
    boolean pay(Order order) { /* ... */ return true; }
}

class EmailService {
    void sendConfirmation(Order order) { /* ... */ }
}

class InventoryService {
    boolean reserve(Order order) { /* ... */ return true; }
}

class OrderFacade {
    private final OrderRepository repo;
    private final PaymentProcessor payment;
    private final EmailService email;
    private final InventoryService inventory;

    OrderFacade(OrderRepository repo, PaymentProcessor payment,
                EmailService email, InventoryService inventory) {
        this.repo = repo;
        this.payment = payment;
        this.email = email;
        this.inventory = inventory;
    }

    boolean placeOrder(Order order) {
        if (!inventory.reserve(order)) {
            return false;
        }
        if (!payment.pay(order)) {
            return false;
        }
        repo.save(order);
        email.sendConfirmation(order);
        return true;
    }
}
```

### Разбор

**Подсистема** — `OrderRepository`, `PaymentProcessor`, `EmailService`, `InventoryService`. Четыре класса, которые работают вместе, чтобы «оформить заказ».

**Фасад** — `OrderFacade`. Один класс, который «собирает» типичный сценарий: зарезервировать, оплатить, сохранить, отправить подтверждение.

**Клиент** — тот, кто вызывает `new OrderFacade(...).placeOrder(order)`. Одна строчка вместо четырёх.

**Что хорошо:**
- `OrderFacade` **принимает** зависимости через конструктор (DI из прошлого урока) — значит, тестируется.
- `OrderFacade` **не создаёт** зависимости — он их получает.
- Клиент работает с **одним** методом `placeOrder` — не думает про четыре подсистемы.

**Что не так.**

**Первая проблема: `OrderFacade` содержит бизнес-логику.** Порядок шагов (reserve → pay → save → email), обработка ошибок — это **не «упрощение интерфейса»**, это **бизнес-логика**. Фасад должен **собирать** вызовы, а не **решать**, в каком порядке их делать. Возможно, `OrderFacade` — это не «фасад», а «сервис».

**Как отличить.** Если класс делает **только** `delegate.method()` (без проверок и условий) — это **фасад**. Если добавляет логику — это **сервис** (или «application service» в терминах DDD). Оба — нормальные паттерны, но **разные**. Их не надо путать.

**Вторая проблема: `OrderFacade` — не «фасад» в чистом виде.** В классическом фасаде **нет** бизнес-логики. Он **просто** собирает вызовы. Если вам нужна бизнес-логика — это **сервис**, а не фасад. Это не «плохо», это «другое».

**Как переписать (если хотим чистый фасад):**

```java
class OrderFacade {
    private final OrderRepository repo;
    private final PaymentProcessor payment;
    private final EmailService email;
    private final InventoryService inventory;

    // ... конструктор ...

    void reserve(Order order) { inventory.reserve(order); }
    void pay(Order order) { payment.pay(order); }
    void save(Order order) { repo.save(order); }
    void notify(Order order) { email.sendConfirmation(order); }
}
```

Теперь `OrderFacade` — это **точка входа** в подсистему. Клиент может **сам** решить, в каком порядке вызывать. Но **и** может использовать «сложный» сценарий:

```java
class OrderService {
    private final OrderFacade facade;

    boolean placeOrder(Order order) {
        facade.reserve(order);
        facade.pay(order);
        facade.save(order);
        facade.notify(order);
        return true;
    }
}
```

Теперь **два** класса: `OrderFacade` — «простой доступ», `OrderService` — «бизнес-логика». Каждый занимается своим.

**Мораль.** Фасад — это **упрощение интерфейса**, а не **бизнес-логика**. Если вы добавляете проверки, условия, порядок шагов — это уже **сервис**, а не фасад. Оба — нормальные, но **разные**. И путать их — плохо: если «фасад» обрастает логикой, он перестаёт быть «простым интерфейсом» и становится «боттлнеком», в котором сосредоточена вся бизнес-логика.

## Микрозадача 2

Вот код. Определите, что не так с точки зрения фасада, и исправьте.

```java
class Kitchen {
    void cook(String dish) { System.out.println("Готовим: " + dish); }
}

class Bar {
    void makeDrink(String drink) { System.out.println("Готовим напиток: " + drink); }
}

class Cashier {
    void takeOrder(String dish, String drink) {
        Kitchen kitchen = new Kitchen();
        Bar bar = new Bar();
        kitchen.cook(dish);
        bar.makeDrink(drink);
    }
}

class RestaurantFacade {
    void order(String dish, String drink) {
        Cashier cashier = new Cashier();
        cashier.takeOrder(dish, drink);
    }
}
```

### Разбор

**Что не так.** `RestaurantFacade` — это **фасад**, но он **создаёт** `Cashier` внутри метода. И `Cashier` **создаёт** `Kitchen` и `Bar` внутри метода. Это **привязка к реализации**, о которой мы говорили в уроке 4 и 5.

Проблемы:

- **В тестах нельзя подставить заглушки.** Каждый тест создаёт реальные `Cashier`, `Kitchen`, `Bar`.
- **Нельзя поменять реализацию.** Захотите заменить `Cashier` на «самообслуживание» — придётся менять `RestaurantFacade`.
- **Фасад «знает» про `Cashier`, `Kitchen`, `Bar`.** Он не должен — он должен «знать» только про **подсистему** в целом.

**Как исправить.** Внедрить зависимости через конструктор:

```java
class RestaurantFacade {
    private final Kitchen kitchen;
    private final Bar bar;
    private final Cashier cashier;

    RestaurantFacade(Kitchen kitchen, Bar bar, Cashier cashier) {
        this.kitchen = kitchen;
        this.bar = bar;
        this.cashier = cashier;
    }

    void order(String dish, String drink) {
        kitchen.cook(dish);
        bar.makeDrink(drink);
    }
}
```

Теперь фасад **принимает** зависимости. В тестах можно подставить заглушки. В `main` — реальные объекты.

**Что ещё можно улучшить.**

**Первое.** `Cashier` в фасаде — это «пятое колесо». Если фасад **сам** вызывает `kitchen.cook` и `bar.makeDrink`, — `Cashier` не нужен. Уберите его из конструктора.

**Второе.** `RestaurantFacade` **знает** про `Kitchen` и `Bar` — конкретные классы. Лучше — через интерфейсы:

```java
interface Kitchen {
    void cook(String dish);
}

interface Bar {
    void makeDrink(String drink);
}

class RestaurantFacade {
    private final Kitchen kitchen;
    private final Bar bar;

    RestaurantFacade(Kitchen kitchen, Bar bar) {
        this.kitchen = kitchen;
        this.bar = bar;
    }

    void order(String dish, String drink) {
        kitchen.cook(dish);
        bar.makeDrink(drink);
    }
}
```

Теперь фасад **не знает** про конкретные реализации. Можно подставить `VegetarianKitchen` или `MockBar` для тестов.

**Третье.** В **реальном** ресторане `Cashier` **не готовит** — он **передаёт** заказ на кухню и в бар. Если у вас есть `Cashier`, — он должен **делегировать**, а не **создавать**. И фасад должен **работать с `Cashier`**, а `Cashier` — с `Kitchen` и `Bar`:

```java
class Cashier {
    private final Kitchen kitchen;
    private final Bar bar;

    Cashier(Kitchen kitchen, Bar bar) {
        this.kitchen = kitchen;
        this.bar = bar;
    }

    void takeOrder(String dish, String drink) {
        kitchen.cook(dish);
        bar.makeDrink(drink);
    }
}

class RestaurantFacade {
    private final Cashier cashier;

    RestaurantFacade(Cashier cashier) {
        this.cashier = cashier;
    }

    void order(String dish, String drink) {
        cashier.takeOrder(dish, drink);
    }
}
```

Теперь фасад **тонкий** — он просто вызывает `cashier.takeOrder`. Это **чистый фасад**: он **не знает** про `Kitchen` и `Bar`, он знает только про `Cashier`. А `Cashier` **сам** работает с подсистемой.

**Мораль.** Фасад — это «один класс, который знает про подсистему». Но **что именно** считать «подсистемой» — вопрос дизайна. Если подсистема — это `Kitchen + Bar`, — фасад работает с ними напрямую. Если подсистема — это `Cashier + Kitchen + Bar`, — фасад работает с `Cashier`, а `Cashier` — с остальными. Выбор зависит от того, **что** вы хотите спрятать.

**И ещё.** Фасад **не должен создавать** зависимости. Он их **принимает** (через конструктор). Это DI из прошлого урока. Фасад без DI — это «god object», который создаёт и управляет всем. Фасад с DI — это «тонкая обёртка», которую легко тестировать и менять.

## Что дальше

Мы закончили модуль про композицию. Разобрались, что такое композиция, чем она отличается от наследования, как работают делегирование, интерфейсы, Dependency Injection и паттерн «Фасад». Всё это — про то, как **строить гибкие системы**, в которых каждый класс делает **только то, что умеет**.

В следующем модуле — **«Проектирование и SOLID»** — мы поговорим о принципах, которые лежат в основе всего, что мы прошли. SOLID — это пять принципов: единственная ответственность, открытость/закрытость, подстановка Лисков, разделение интерфейсов, инверсия зависимостей. Каждый из них мы уже видели на практике (в наследовании, в полиморфизме, в композиции), но теперь увидим их **вместе** — как единую систему.

А пока — маленькое упражнение на наблюдательность. Откройте любой свой проект (или открытый проект на Java) и найдите классы, у которых **много** методов. Для каждого задайте вопрос: **это фасад или «god object»?** Если методы — это `delegate.someMethod()` (без логики) — фасад, это нормально. Если методы **содержат** бизнес-логику — это «сервис», а не фасад. Если методов много и они **разные** — возможно, это «god object», и его стоит разбить. Просто найдите. Не переделывайте (пока). Понимание того, **где** фасад, а **где** — «боттлнек», — уже большой шаг к более чистой архитектуре.

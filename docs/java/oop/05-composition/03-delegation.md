# 3. Делегирование

## Где вы это уже видели

В прошлых уроках мы разобрались, что класс может **содержать** другой объект (композиция) и что это часто лучше, чем наследоваться. Но что делать с этим содержанием? Просто «держать» — мало. Обычно класс **делегирует** содержимому часть своей работы: вызывает его методы, передаёт ему управление, использует его как «помощника».

Делегирование — это третий кит композиции (после «has-a» и различия агрегации/композиции). И он, пожалуй, самый практичный: именно делегирование позволяет строить гибкие системы, где каждый объект занимается своим делом.

**Ситуация первая.** Вы работаете в компании, и у вас есть ассистент. Вы не делаете всё сами — вы **поручаете** ему часть задач: «созвонись с клиентом», «подготовь отчёт», «забронируй билеты». Вы остаётесь «главным», но часть работы **делегируете**. Если ассистент сменится — вы продолжите работать, просто с новым человеком.

**Ситуация вторая.** Вы в ресторане. Вы не идёте на кухню и не готовите сами — вы **делегируете** это повару. Официант **делегирует** заказ на кухню, кухня **делегирует** приготовление повару, повар **делегирует** нарезку овощей своему помощнику. Каждый занимается своим делом, и никто не делает всё сразу.

**Ситуация третья.** Вы в банке. Вы не «делаете перевод» сами — вы **делегируете** это банку. Банк **делегирует** проверку счёта системе безопасности, **делегирует** списание бухгалтерской системе, **делегирует** уведомление клиенту SMS-сервису. Вы получаете результат, но не участвуете в каждой операции.

**Ситуация четвёртая.** Вы нажимаете «Отправить» в почте. Почтовый клиент **делегирует** отправку SMTP-серверу, тот **делегирует** доставку серверу получателя, тот **делегирует** уведомление почтовому клиенту получателя. Одна кнопка — целая цепочка делегатов, и каждый знает только про следующий шаг.

**Ситуация пятая.** Вы нажимаете «Оплатить» в интернет-магазине. Магазин **делегирует** оплату платёжной системе (Stripe, ЮKassa, СБП), та **делегирует** списание банку, банк **делегирует** подтверждение клиенту. Вы видите только «оплата прошла» — а за этим стоит цепочка делегатов.

**Ситуация шестая.** Вы смотрите на код и видите:

```java
class Order {
    private final List<Item> items;

    double total() {
        double sum = 0;
        for (Item item : items) {
            sum += item.getPrice();
        }
        return sum;
    }
}
```

— и понимаете, что `Order` **сам** считает сумму. А можно было бы **делегировать** это отдельному `PriceCalculator` — и тогда `Order` не знал бы, как считать, а `PriceCalculator` не знал бы, что такое `Order`. Оба стали бы проще. Знакомо? Тогда этот урок для вас.

## Что такое делегирование

**Делегирование** — это когда объект **не выполняет** работу сам, а **перепоручает** её другому объекту. В коде это выглядит как вызов метода «помощника»:

```java
class Engine {
    void start() {
        System.out.println("Двигатель запущен");
    }
}

class Car {
    private final Engine engine;

    Car(Engine engine) {
        this.engine = engine;
    }

    void start() {
        engine.start();   // делегируем запуск двигателю
    }
}
```

Здесь `Car.start()` **не запускает** двигатель сам — он **делегирует** это `Engine.start()`. `Car` знает только, что «нужно запустить двигатель», и что «двигатель умеет запускаться». Как именно он запускается — не забота `Car`.

**Ключевая идея:** делегирование — это **разделение ответственности**. Каждый объект делает **только то, что умеет**. `Car` знает, как «запустить машину» — повернуть ключ, подать сигнал двигателю. `Engine` знает, как «запустить двигатель» — подать топливо, поджечь, раскрутить. Никто не знает «всего».

Это отличается от наследования. При наследовании `Car extends Engine` — `Car` **унаследовал бы** `start()` и делал бы всё сам (или переопределял бы). При делегировании — `Car` **вызывает** `Engine.start()`, но не «является» двигателем. Ответственность разделена, роли разделены.

## Как это работает: три шага

Делегирование всегда состоит из трёх шагов.

**Шаг 1: класс содержит «помощника».** Поле типа другого класса (или интерфейса).

```java
class Car {
    private final Engine engine;
    // ...
}
```

**Шаг 2: класс получает «помощника» — либо создаёт сам, либо принимает снаружи.** Это то самое различие композиции/агрегации из прошлого урока.

```java
Car(Engine engine) {   // принимаем снаружи — агрегация
    this.engine = engine;
}

// или

Car() {                // создаём внутри — композиция
    this.engine = new Engine();
}
```

**Шаг 3: класс вызывает методы «помощника» в своих методах.** Это и есть делегирование.

```java
void start() {
    engine.start();
}
```

Часто **все три шага** не видны сразу — класс просто «вызывает» помощника, а «содержит» и «получает» его где-то в другом месте. Но эти три шага — всегда.

## Делегирование vs наследование

Сравним на примере. Задача: класс `Stack`, который умеет `push`, `pop`, `peek`.

**Через наследование:**

```java
class Stack extends ArrayList<Object> {
    void push(Object item) {
        add(item);
    }

    Object pop() {
        return remove(size() - 1);
    }

    Object peek() {
        return get(size() - 1);
    }
}
```

`Stack` **является** `ArrayList`. Имеет все его методы. И все его проблемы (мы обсуждали в уроке 1).

**Через делегирование:**

```java
class Stack {
    private final List<Object> items = new ArrayList<>();

    void push(Object item) {
        items.add(item);
    }

    Object pop() {
        if (items.isEmpty()) {
            throw new IllegalStateException("Стек пуст");
        }
        return items.remove(items.size() - 1);
    }

    Object peek() {
        if (items.isEmpty()) {
            throw new IllegalStateException("Стек пуст");
        }
        return items.get(items.size() - 1);
    }

    boolean isEmpty() {
        return items.isEmpty();
    }

    int size() {
        return items.size();
    }
}
```

`Stack` **содержит** `List` и **делегирует** ему `add`, `remove`, `get`, `isEmpty`, `size`. У `Stack` **нет** методов `sort`, `subList`, `clear` — потому что он их не делегирует. Только те, что нужны.

**Что мы получили:**
- **Чистый интерфейс.** У `Stack` только методы, которые имеют смысл. Никаких `add(int, Object)`.
- **Контроль над жизненным циклом.** Если `items` — `ArrayList` внутри `Stack`, — никто снаружи не может его изменить. `Stack` полностью контролирует содержимое.
- **Изоляция от изменений.** Если завтра `ArrayList` добавит новый метод, — `Stack` его не получит. `Stack` «изолирован» от `ArrayList`.

**Что потеряли:**
- **`Stack` не «является» `List`.** Если функции нужен `List`, — `Stack` не подойдёт. Но это, скорее всего, **не проблема**: `Stack` — это стек, а не список.

## Делегирование vs композиция

В прошлом уроке мы говорили о композиции как о «содержании». Чем делегирование отличается?

На самом деле, **делегирование — это способ использования композиции**. Когда вы **содержите** объект (композиция), — вы можете:
- **не использовать** его (просто хранить);
- **использовать** его (делегировать ему работу).

Делегирование — это **активное** использование. Композиция — это **структура**. Делегирование — это **поведение**.

На практике, когда говорят «композиция», — почти всегда имеют в виду «композиция + делегирование». Потому что содержать объект и не использовать его — бессмысленно. Так что эти два понятия тесно связаны: композиция — это «как устроено», делегирование — это «как работает».

## Виды делегирования

Делегирование бывает **полным** и **частичным**.

**Полное делегирование** — когда класс **целиком** передаёт работу помощнику. Например, `Stack` для `push`/`pop`/`peek` целиком делегирует `List`. Никакой «своей» логики нет, кроме проверки на пустоту.

**Частичное делегирование** — когда класс **дополняет** работу помощника своей логикой. Например, `Stack` **добавляет** проверку «не пуст ли» перед вызовом `items.remove`. Это уже не «чистое» делегирование — это «делегирование с проверкой».

Оба вида уместны. Полное — когда помощник делает всю работу, и классу добавить нечего. Частичное — когда класс хочет **контролировать** условия или **добавлять** побочные эффекты.

Пример частичного делегирования:

```java
class LoggingStack {
    private final Stack delegate;

    LoggingStack(Stack delegate) {
        this.delegate = delegate;
    }

    void push(Object item) {
        System.out.println("push: " + item);
        delegate.push(item);
    }

    Object pop() {
        Object result = delegate.pop();
        System.out.println("pop: " + result);
        return result;
    }
}
```

Здесь `LoggingStack` **делегирует** `Stack`, но **добавляет** логирование. Это «частичное» делегирование — с дополнением.

## Делегирование в реальном коде

Делегирование используется повсюду. Несколько примеров.

**`Collections.unmodifiableList(list)`.** Возвращает **обёртку**, которая делегирует все **читающие** методы настоящему списку, а **изменяющие** — бросают `UnsupportedOperationException`. Это «частичное» делегирование: часть методов делегируется, часть — нет.

**`Collections.synchronizedList(list)`.** Возвращает обёртку, которая **делегирует** все методы настоящему списку, но **оборачивает** их в `synchronized`. Тоже частичное делегирование.

**`HttpServletRequest` в сервлетах.** Обёртка, которая делегирует методы настоящему запросу. Позволяет добавлять свою логику (например, логирование или проверку прав) без изменения оригинального класса.

**`InputStream` и его обёртки.** `BufferedInputStream` **делегирует** чтение настоящему `InputStream`, но **добавляет** буферизацию. `GZIPInputStream` делегирует, но **добавляет** распаковку. `CipherInputStream` делегирует, но **добавляет** расшифровку.

**`Comparators`.** `Comparator.comparing(...).reversed()` — это делегирование. `reversed()` возвращает новый компаратор, который **делегирует** вызов настоящему и **инвертирует** результат. `thenComparing(...)` — тоже делегирование.

**Фасады.** Класс `SmartHomeFacade`, который **делегирует** методы умному дому, освещению, климату, безопасности. Об этом будем говорить в уроке 6.

Во всех этих примерах — одна и та же идея: **класс не делает работу сам, а перепоручает её другому объекту**.

## Делегирование и тестирование

Одно из главных преимуществ делегирования — **тестируемость**. Если класс делегирует работу помощнику, — в тестах можно подменить помощника на «заглушку».

Пример. `OrderService`, который создаёт заказ и отправляет уведомление:

```java
class OrderService {
    private final NotificationSender notifier;

    OrderService(NotificationSender notifier) {
        this.notifier = notifier;
    }

    void placeOrder(Order order) {
        // ... сохранение заказа ...
        notifier.send(order.getCustomerEmail(), "Заказ оформлен");
    }
}
```

В тестах:

```java
class FakeNotifier implements NotificationSender {
    List<String> sent = new ArrayList<>();

    @Override
    public void send(String to, String message) {
        sent.add(to + ": " + message);
    }
}

@Test
void testPlaceOrder() {
    FakeNotifier fake = new FakeNotifier();
    OrderService service = new OrderService(fake);

    service.placeOrder(new Order("alice@example.com"));

    assertEquals(1, fake.sent.size());
    assertEquals("alice@example.com: Заказ оформлен", fake.sent.get(0));
}
```

Мы **не отправляем** настоящее письмо — мы **делегируем** `FakeNotifier`, который просто записывает вызовы. Тест быстрый, детерминированный, не требует SMTP-сервера. Это стало возможным благодаря делегированию.

Если бы `OrderService` **сам** отправлял письма (через `new SmtpClient()`), — тестировать было бы гораздо сложнее: пришлось бы либо поднимать SMTP-сервер, либо «мокать» статический метод. Делегирование решает эту проблему elegantly.

## Аналогия, которая помогает

Хорошая аналогия — **менеджер и его команда**.

**Менеджер** не делает всю работу сам. Он **делегирует** задачи команде: разработчику — написать код, дизайнеру — нарисовать макет, тестировщику — проверить. Менеджер **остаётся ответственным** за результат, но **не делает** каждую задачу сам.

**Менеджер знает**, кого за что «дёрнуть» — то есть у него есть «карта делегатов». В коде это поля-помощники.

**Если разработчик заболел** — менеджер может **заменить** его другим. В коде это означает, что помощника можно заменить (композиция-агрегация).

**Если менеджер уволился** — команда остаётся, работу продолжает новый менеджер. В коде это означает, что помощники живут своей жизнью.

**Если менеджер делает всё сам** — он становится «бутылочным горлышком». В коде это «god object» — класс, который знает и делает всё. Его тяжело поддерживать, тестировать, менять.

**Если менеджер только делегирует и ничего не делает сам** — это уже не менеджер, а «обёртка». В коде это тоже бывает (декораторы, прокси), но это уже особый случай.

**Идеальный менеджер** — тот, кто **знает, кому делегировать**, **контролирует результат**, но **не делает работу сам**. Это и есть правильное делегирование в коде.

## Микрозадача 1

Вот класс. Определите, что в нём «делегируется» и что «делается самим». Есть ли здесь проблемы?

```java
class EmailService {
    private final SmtpClient smtp;
    private final String fromAddress;

    EmailService(SmtpClient smtp, String fromAddress) {
        this.smtp = smtp;
        this.fromAddress = fromAddress;
    }

    void sendWelcome(String to) {
        String body = "Добро пожаловать!";
        smtp.send(fromAddress, to, "Привет", body);
    }

    void sendPasswordReset(String to, String token) {
        String body = "Ваш токен: " + token;
        smtp.send(fromAddress, to, "Сброс пароля", body);
    }
}
```

### Разбор

**Что делегируется.** `EmailService` **делегирует** `SmtpClient` фактическую отправку (`smtp.send(...)`). `EmailService` не знает, **как** отправляется письмо — только **что** нужно отправить.

**Что делается самим.** `EmailService` **формирует** тело письма (`body`), **выбирает** тему (`"Привет"`, `"Сброс пароля"`) и **передаёт** адрес отправителя. Это его работа — не `SmtpClient`.

**Проблемы.**

**Первая.** `SmtpClient` — конкретный класс. Если в тестах понадобится подменить его, — не получится, если он `final` или создаёт реальное соединение. Лучше — интерфейс `EmailSender`, а `SmtpClient` — его реализация. Тогда в тестах можно подставить `FakeEmailSender`.

**Вторая.** `EmailService` отвечает **и** за формирование писем, **и** за их отправку. Если писем станет десять (welcome, password reset, order confirmation, ...), — `EmailService` разрастётся. Логичнее разделить: `EmailContentBuilder` формирует, `EmailSender` отправляет.

**Третья.** Тема письма — «Привет» — написана в коде. Если нужно локализовать (i18n) или сделать настраиваемой, — придётся менять `EmailService`. Лучше — вынести в шаблоны или ресурсы.

**Как улучшить:**

```java
interface EmailSender {
    void send(String from, String to, String subject, String body);
}

class EmailService {
    private final EmailSender sender;
    private final EmailContentBuilder builder;
    private final String fromAddress;

    EmailService(EmailSender sender, EmailContentBuilder builder, String fromAddress) {
        this.sender = sender;
        this.builder = builder;
        this.fromAddress = fromAddress;
    }

    void sendWelcome(String to) {
        Email email = builder.welcome();
        sender.send(fromAddress, to, email.subject(), email.body());
    }

    void sendPasswordReset(String to, String token) {
        Email email = builder.passwordReset(token);
        sender.send(fromAddress, to, email.subject(), email.body());
    }
}
```

Теперь `EmailService` **делегирует** формирование `EmailContentBuilder` и отправку `EmailSender`. Каждый занимается своим. И в тестах можно подменить и то, и другое.

**Мораль.** Делегирование — не «всё отдать помощнику», а «разделить ответственность». Каждый класс делает **только то, что умеет**. Если класс делает слишком много, — это сигнал, что часть работы стоит делегировать.

## Микрозадача 2

Вот класс. Определите, что в нём не так с точки зрения делегирования, и исправьте.

```java
class Report {
    private String title;
    private String content;

    void generate() {
        // ... формирование content ...
        System.out.println("=== " + title + " ===");
        System.out.println(content);
        // ... сохранение в файл ...
        // ... отправка по email ...
    }
}
```

### Разбор

**Проблема.** `generate` делает **всё**: формирует контент, печатает, сохраняет в файл, отправляет email. Это «god method» — метод, который знает и делает слишком много. Если что-то из этого изменится (например, формат печати или способ отправки), — придётся менять `Report`.

Кроме того, нарушается **единственная ответственность** (SRP, о которой будем говорить в модуле 6). `Report` должен **представлять** отчёт, а не **печатать**, **сохранять** и **отправлять**.

**Как исправить.** Разделить на части и делегировать:

```java
class Report {
    private final String title;
    private final String content;

    Report(String title, String content) {
        this.title = title;
        this.content = content;
    }

    String getTitle() { return title; }
    String getContent() { return content; }
}

class ReportPrinter {
    void print(Report report) {
        System.out.println("=== " + report.getTitle() + " ===");
        System.out.println(report.getContent());
    }
}

class ReportSaver {
    void save(Report report, String path) {
        // ... сохранение в файл ...
    }
}

class ReportMailer {
    void mail(Report report, String to) {
        // ... отправка по email ...
    }
}
```

Теперь `Report` **только** представляет отчёт. `ReportPrinter` **только** печатает. `ReportSaver` **только** сохраняет. `ReportMailer` **только** отправляет.

Использование:

```java
Report report = new Report("Итоги года", "...");
ReportPrinter printer = new ReportPrinter();
printer.print(report);

ReportSaver saver = new ReportSaver();
saver.save(report, "report.txt");

ReportMailer mailer = new ReportMailer();
mailer.mail(report, "boss@example.com");
```

Теперь каждый класс можно **тестировать отдельно**. И если изменится формат печати, — `Report`, `ReportSaver`, `ReportMailer` не тронуты.

**Что мы потеряли?** Один вызов `report.generate()` превратился в три вызова. Но это **правильно**: явное лучше неявного. И если нужно «сделать всё сразу», — можно добавить фасад (об этом в уроке 6):

```java
class ReportFacade {
    void generateAndSend(Report report, String path, String to) {
        new ReportPrinter().print(report);
        new ReportSaver().save(report, path);
        new ReportMailer().mail(report, to);
    }
}
```

`ReportFacade` **делегирует** всем трём. Клиенту не надо знать про `ReportPrinter`, `ReportSaver`, `ReportMailer` — он работает с `ReportFacade`. Это **фасад** — обёртка над подсистемой, которая скрывает её сложность.

**Мораль.** Делегирование — это не «добавить побольше классов», а **разделить ответственность**. Если класс делает **одну вещь** — он простой, тестируемый, понятный. Если делает пять — он «божественный объект», и его тяжело поддерживать.

## Самостоятельная задача

Спроектируйте класс `OrderService` для интернет-магазина.

Поля:

- `OrderRepository` — для сохранения заказов;
- `PaymentProcessor` — для проведения оплаты;
- `NotificationSender` — для отправки уведомлений клиенту;
- `InventoryService` — для проверки и резервирования товаров.

Метод `placeOrder(Order)` должен:

1. Проверить наличие товаров через `InventoryService`.
2. Провести оплату через `PaymentProcessor`.
3. Сохранить заказ через `OrderRepository`.
4. Отправить уведомление клиенту через `NotificationSender`.

Подумайте:

- какие из этих действий — «делегирование», а какие — «своя логика» `OrderService`? (Подсказка: почти всё делегирование, «своей» логики мало — только порядок шагов и обработка ошибок.)
- что должен делать `OrderService`, если оплата не прошла? (Скорее всего — вернуть ошибку, отменить резервирование через `InventoryService`, **не** сохранять заказ.)
- что должен делать `OrderService`, если товара нет? (Вернуть ошибку, **не** проводить оплату.)
- что должен делать `OrderService`, если после оплаты не удалось сохранить заказ? (Скорее всего — вернуть деньги через `PaymentProcessor.refund`, если такой метод есть.)
- что должен делать `OrderService`, если после сохранения заказа не удалось отправить уведомление? (Скорее всего — залогировать ошибку, но **не** возвращать деньги: заказ-то создан.)
- какие из этих действий — «транзакционные» (должны быть выполнены или все вместе, или ни одного), а какие — «нетранзакционные»?

Затем ответьте на вопрос: если завтра понадобится добавить «сохранение в Elasticsearch» или «уведомление по SMS», — что придётся менять в `OrderService`? Это проще, чем если бы `OrderService` **сам** делал всё это (через `new ElasticClient()`, `new SmsClient()`)?

Готового ответа не будет. Если хотите свериться — загляните в следующий урок про Dependency Injection: там мы разберём, как «правильно» получать зависимости (как в этой задаче — через конструктор), и вы увидите, насколько ваша интуиция про «передать снаружи» совпала с тем, как это устроено в реальном коде.

## Что дальше

Мы разобрались, что такое делегирование, зачем оно нужно и как с ним работать. В следующем уроке — **«Интерфейсы как способ развязать руки»** — мы поговорим о том, как программировать «под интерфейс, а не под реализацию». Это естественное продолжение делегирования: делегировать можно не только конкретному классу, но и **интерфейсу** — и тогда можно подменить любую реализацию, включая заглушку в тестах.

А пока — маленькое упражнение на наблюдательность. Откройте любой свой проект (или открытый проект на Java) и найдите классы, у которых есть поля типа других классов. Для каждого задайте вопрос: **что этот класс делегирует?** И **что делает сам?** Если класс **только** делегирует (все методы — это `delegate.someMethod()`) — возможно, это обёртка или декоратор, и это нормально. Если класс делегирует **и** делает много своего — нормально тоже, но проверьте, не пытается ли он «быть всем сразу». Если класс **не делегирует** никому, хотя мог бы — возможно, он «божественный объект». Просто найдите. Не переделывайте (пока). Понимание того, **как** устроено делегирование в вашем коде, — уже большой шаг к более чистой архитектуре.

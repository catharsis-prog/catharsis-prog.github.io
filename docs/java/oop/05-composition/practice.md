# Практикум — Композиция и интерфейсы

## Как это работает

Здесь семь задач. Первые три — на технику: замена наследования композицией, агрегация vs композиция, делегирование. Следующие три — на понимание: интерфейсы как decoupling, Dependency Injection, фасад. Последняя — проектное задание: собрать «умный дом» из компонентов.

Решения лежат на [отдельной странице](./practice-solutions). Сначала попробуйте сами, потом сверяйтесь. Если ваше решение отличается от моего, но работает и обосновано — оно тоже правильное. В композиции многое зависит от контекста: агрегация или композиция, DI через конструктор или через сеттер, фасад или сервис — всё это «уместно или неуместно здесь», а не «правильно или неправильно».

Код пишите в файлах `.java`, запускайте. Особенно полезно **ломать** свои иерархии: попробуйте добавить новую зависимость и посмотрите, сколько файлов придётся тронуть. Если много — возможно, DI не хватает.

## Задача 1. Замена наследования композицией

Вот класс, который наследуется от `ArrayList`:

```java
class Playlist extends ArrayList<Song> {
    private String name;

    Playlist(String name) {
        this.name = name;
    }

    String getName() {
        return name;
    }
}
```

Переделайте его через **композицию**:

- `Playlist` **содержит** `List<Song>`, а не наследует его;
- конструктор принимает `name` и создаёт пустой список;
- методы: `addSong(Song)`, `removeSong(Song)`, `getSongCount()`, `getSongs()` (возвращает **неизменяемое представление** или копию);
- добавьте проверки: `name` не пустой, `song` не `null`.

В `main`:

1. Создайте плейлист.
2. Добавьте три песни.
3. Выведите количество.
4. Попробуйте изменить список через `getSongs()` — убедитесь, что не получится.
5. Удалите одну песню.

Ответьте на вопрос: **что мы потеряли**, отказавшись от наследования? И **что приобрели**?

**Что проверяется:** понимаете ли вы, как заменить наследование композицией и почему это часто лучше.

## Задача 2. Агрегация vs композиция

Создайте систему из трёх классов:

- `Department` (отдел) с полями `name` и `List<Employee> employees`;
- `Employee` (сотрудник) с полями `name` и `salary`;
- `Company` (компания) с полями `name` и `List<Department> departments`.

Для каждой связи определите: это **агрегация** или **композиция**? Реализуйте:

- `Company` **создаёт** свои отделы (композиция) — метод `createDepartment(String name)`;
- `Department` **принимает** сотрудников снаружи (агрегация) — метод `hire(Employee)`;
- `Employee` может быть **переведён** из одного отдела в другой — метод `transfer(Employee, Department from, Department to)` в `Company`.

В `main`:

1. Создайте компанию.
2. Создайте два отдела.
3. Наймите трёх сотрудников: двух в первый отдел, одного во второй.
4. Переведите одного сотрудника из первого отдела во второй.
5. Выведите список отделов и сотрудников в каждом.

Ответьте на вопросы:

- почему `Company → Department` — композиция, а `Department → Employee` — агрегация?
- что произойдёт с сотрудниками, если отдел будет «удалён»? А если компания?
- может ли сотрудник быть в двух отделах одновременно? Если да — как это выразить?

**Что проверяется:** понимаете ли вы разницу между агрегацией и композицией и умеете ли выражать её в коде.

## Задача 3. Делегирование вместо копирования

Вот код с дублированием:

```java
class FileLogger {
    void log(String message) {
        System.out.println("[FILE] " + message);
    }
}

class ConsoleLogger {
    void log(String message) {
        System.out.println("[CONSOLE] " + message);
    }
}

class FilteringFileLogger {
    void log(String message) {
        if (message.contains("ERROR")) {
            System.out.println("[FILE] " + message);
        }
    }
}

class FilteringConsoleLogger {
    void log(String message) {
        if (message.contains("ERROR")) {
            System.out.println("[CONSOLE] " + message);
        }
    }
}
```

Переделайте через **делегирование**:

- создайте интерфейс `Logger` с методом `log(String)`;
- `FileLogger` и `ConsoleLogger` реализуют его;
- создайте `FilteringLogger` — обёртку над **любым** `Logger`, которая делегирует `log` только если сообщение содержит `"ERROR"`.

В `main`:

1. Создайте `FilteringLogger` над `FileLogger` — залогируйте `"ERROR: что-то сломалось"` и `"INFO: всё хорошо"`. Убедитесь, что первое прошло, а второе — нет.
2. Создайте `FilteringLogger` над `ConsoleLogger` — то же самое.
3. Создайте «двойную» фильтрацию: `FilteringLogger` над `FilteringLogger` над `FileLogger` — убедитесь, что работает.

Ответьте на вопрос: **что мы выиграли**, заменив четыре класса на три (интерфейс + два логгера + обёртка)? Что было бы, если бы мы захотели добавить `EmailLogger` и `FilteringEmailLogger`? Сколько классов было бы в «старом» варианте и сколько — в «новом»?

**Что проверяется:** понимаете ли вы, как делегирование заменяет дублирование и позволяет комбинировать поведение.

## Задача 4. Программирование под интерфейс

Вот класс, привязанный к конкретной реализации:

```java
class ReportService {
    private final MySQLDatabase database = new MySQLDatabase("localhost:3306");

    List<String> loadReport() {
        return database.query("SELECT * FROM reports");
    }
}
```

Переделайте так, чтобы `ReportService` **не зависел** от MySQL:

- создайте интерфейс `Database` с методом `List<String> query(String sql)`;
- `MySQLDatabase` реализует `Database`;
- создайте альтернативную реализацию `InMemoryDatabase`, которая хранит данные в `List<String>` и «выполняет» запросы (просто возвращает всё, что есть — для простоты);
- `ReportService` принимает `Database` через конструктор.

В `main`:

1. Создайте `ReportService` с `MySQLDatabase` — выведите результат.
2. Создайте `ReportService` с `InMemoryDatabase`, наполните его данными — выведите результат.
3. Убедитесь, что `ReportService` **не меняется** при смене базы.

Ответьте на вопрос: **что** делает `ReportService` **простым и тестируемым** в новой версии? И **что** потерялось по сравнению со старой?

**Что проверяется:** понимаете ли вы, как «программировать под интерфейс» и почему это основа decoupling.

## Задача 5. Dependency Injection через конструктор

Вот класс с самосозданием зависимостей:

```java
class AuthService {
    private final UserRepository repository = new JpaUserRepository();
    private final PasswordHasher hasher = new BcryptHasher(12);
    private final TokenGenerator tokenGenerator = new JwtTokenGenerator("secret");

    String login(String email, String password) {
        User user = repository.findByEmail(email);
        if (user == null || !hasher.matches(password, user.getPasswordHash())) {
            throw new IllegalArgumentException("Неверный логин или пароль");
        }
        return tokenGenerator.generate(user.getId());
    }
}
```

Переделайте через **DI через конструктор**:

- создайте интерфейсы `UserRepository`, `PasswordHasher`, `TokenGenerator`;
- `AuthService` принимает все три через конструктор;
- все поля `final`;
- в конструкторе проверяйте, что зависимости не `null`.

Затем создайте «заглушки»:

- `FakeUserRepository` — возвращает заранее заданного пользователя по email;
- `FakePasswordHasher` — возвращает `true`, если пароль `"correct"`, и `false` иначе;
- `FakeTokenGenerator` — возвращает фиксированный токен `"fake-token"`.

В `main`:

1. Соберите `AuthService` с настоящими (или фиктивными) реализациями.
2. Попробуйте залогиниться с правильным и неправильным паролем.
3. Убедитесь, что `AuthService` **не знает**, какие реализации за интерфейсами.

Ответьте на вопрос: **что** изменилось в **тестируемости** `AuthService`? Какие тесты теперь можно написать, которые были невозможны раньше?

**Что проверяется:** понимаете ли вы DI через конструктор и умеете ли применять его на практике.

## Задача 6. Фасад для подсистемы

Создайте подсистему «домашний кинотеатр»:

- `Projector` — `on()`, `off()`, `setInput(String)`;
- `SoundSystem` — `on()`, `off()`, `setVolume(int)`;
- `DvdPlayer` — `on()`, `off()`, `play(String)`;
- `Lights` — `dim()`, `on()`;
- `Screen` — `down()`, `up()`.

Создайте `HomeTheaterFacade` с двумя методами:

- `watchMovie(String movie)` — включить проектор (вход `"DVD"`), включить звук (громкость 10), включить DVD, опустить экран, приглушить свет, запустить фильм;
- `endMovie()` — выключить DVD, поднять экран, включить свет, выключить звук, выключить проектор.

В `main`:

1. Создайте фасад.
2. Вызовите `watchMovie("Интерстеллар")` — убедитесь, что все действия выполнились в правильном порядке.
3. Вызовите `endMovie()` — убедитесь, что всё выключилось.

Ответьте на вопросы:

- должен ли `HomeTheaterFacade` **принимать** зависимости через конструктор или **создавать** их сам? Почему?
- что должен делать фасад, если `projector.on()` бросил исключение? Прервать сценарий? Продолжить?
- если завтра понадобится третий сценарий (например, «играть в игру»), — сколько файлов придётся менять?

**Что проверяется:** понимаете ли вы, что такое фасад и как он упрощает работу с подсистемой.

## Задача 7. Проект — «умный дом»

Это большое задание. Его можно решать несколько вечеров. Здесь нужно применить **всё**, что мы прошли в модуле: композицию, делегирование, интерфейсы, DI и фасад.

Спроектируйте систему «умный дом».

### Компоненты

Каждый компонент — отдельный класс с методами:

- `Light` — `on()`, `off()`, `dim()`, `isOn()`;
- `Thermostat` — `setTemperature(int)`, `turnOff()`, `getTemperature()`;
- `SecuritySystem` — `arm()`, `disarm()`, `isArmed()`;
- `MusicSystem` — `play(String track)`, `stop()`, `setVolume(int)`;
- `Window` — `open()`, `close()`, `isOpen()`;
- `CoffeeMachine` — `brew()`, `turnOff()`, `isReady()`.

Реализации могут просто печатать, что происходит, и хранить состояние в полях.

### Интерфейсы для DI

Определите интерфейсы, если это уместно:

- `Switchable` (вкл/выкл) — для `Light`, `Thermostat`, `MusicSystem`, `CoffeeMachine`;
- `Securable` — для `SecuritySystem`;
- `Openable` — для `Window`.

Подумайте: **какие** методы в **каких** интерфейсах. Один большой интерфейс на всё — плохо (это принцип ISP, о котором будем говорить в модуле 6). Несколько маленьких — хорошо.

### Фасад

`SmartHomeFacade` с методами:

- `arriveHome()` — снять с охраны, включить свет, включить отопление на 22, открыть окна;
- `leaveHome()` — выключить весь свет, выключить отопление, поставить на охрану, закрыть окна, выключить кофемашину;
- `movieMode()` — приглушить свет, закрыть окна, включить музыку `"Soundtrack"` на громкости 5, установить температуру 20;
- `morningRoutine()` — снять с охраны, включить свет, сварить кофе, включить музыку `"Morning"`;
- `goodNight()` — выключить свет, выключить отопление, поставить на охрану, закрыть окна, остановить музыку.

Фасад **принимает** все компоненты через конструктор (DI). Внутри — только вызовы компонентов, никакой бизнес-логики.

### Сценарий проверки

Напишите `main`:

1. Создайте все компоненты (каждый — отдельный объект).
2. Соберите `SmartHomeFacade` из них.
3. Вызовите `arriveHome()` — проверьте, что состояние компонентов изменилось.
4. Вызовите `movieMode()` — проверьте, что состояние изменилось соответствующим образом.
5. Вызовите `goodNight()` — проверьте, что всё «уснуло».
6. Вызовите `leaveHome()` дважды подряд — убедитесь, что второй вызов не ломается.

### Дополнительные требования

- Фасад — `final`? Обоснуйте.
- Все компоненты — `final`? Обоснуйте.
- Используйте интерфейсы везде, где это уместно (для DI).
- Обрабатывайте `null`: если в конструктор фасада передали `null` — бросайте `IllegalArgumentException`.
- `SmartHomeFacade` **не должен** создавать компоненты сам — только принимать через конструктор.
- Где-то в `main` создайте **второй** набор компонентов (например, `MockLight`, который записывает вызовы в список) и соберите **второй** фасад. Убедитесь, что фасад работает с любыми реализациями.

### Вопросы на подумать

1. Что произойдёт, если завтра появится новый компонент — `SmartLock` (умный замок)? Сколько файлов придётся менять?
2. Что произойдёт, если завтра понадобится **второй** сценарий «гости»? Куда его добавить?
3. Если бы вы хотели, чтобы **каждый** вызов компонента логировался, — как это сделать, не меняя ни один компонент? (Подсказка: декоратор.)
4. Что произойдёт, если один и тот же `Light` передать в **два** фасада? Это нормально? Как это связано с агрегацией/композицией?
5. Нужно ли делать `SmartHomeFacade` Singleton'ом? Почему?

**Что проверяется:** всё сразу. Умение проектировать систему из компонентов, применять композицию, делегирование, интерфейсы, DI и фасад — и обосновывать каждое решение.

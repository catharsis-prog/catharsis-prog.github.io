# 5. Dependency Injection на пальцах

## Где вы это уже видели

В прошлом уроке мы разобрались, что «программировать под интерфейс» — это хорошо, и что зависимость должна приходить снаружи. Но мы не обсудили **как** именно она приходит. А способов много, и они не равнозначны.

Этот урок — про **Dependency Injection** (DI). Название звучит как что-то из мира Spring и «взрослой» разработки, но идея за ним очень простая и очень старая. Она не требует фреймворка. Она не требует аннотаций. Она требует только одного: **объект не создаёт свои зависимости сам, а получает их извне**.

**Ситуация первая.** Вы собираете компьютер. Вы не «выращиваете» процессор из материнской платы — вы **вставляете** его в сокет. Материнская плата не создаёт процессор, она **принимает** его. И если захотите поменять процессор, — достанете один, вставите другой. Плата при этом не меняется. Это и есть DI: компонент **получает** зависимость, а не создаёт её.

**Ситуация вторая.** Вы готовите кофе в кофемашине. Кофемашина не «выращивает» капсулы внутри себя — вы **вставляете** капсулу снаружи. Кофемашина **принимает** капсулу и работает с ней. Захотите другой вкус — вставите другую капсулу. Машина не меняется.

**Ситуация третья.** Вы работаете в компании, и у вас есть начальник. Вас **назначили** на эту должность, а не «вырастили» начальника из вас. Начальник приходит снаружи. И если он сменится — вы продолжите работать, просто с другим человеком.

**Ситуация четвёртая.** Вы в ресторане. Вы **заказываете** блюдо, а не готовите его сами. Повар **получает** ингредиенты со склада, а не выращивает их на кухне. Склад **получает** продукты от поставщика, а не производит их сам. Каждый уровень **принимает** зависимость снаружи.

**Ситуация пятая.** Вы в больнице. Врач **получает** инструменты от медсестры, а не ищет их сам. Медсестра **получает** их со склада. Склад **получает** их от поставщика. Врач не знает, **откуда** инструменты, — он знает, что они **есть**.

**Ситуация шестая.** Вы смотрите на код и видите:

```java
class OrderService {
    private final PaymentProcessor processor = new StripePaymentProcessor("api_key_12345");
    // ...
}
```

— и понимаете, что `OrderService` **сам создаёт** `StripePaymentProcessor`. В тестах нельзя подставить заглушку, в коде нельзя заменить на СБП, ключ «вшит» в класс. Знакомо? Тогда этот урок для вас.

## Что такое Dependency Injection

**Dependency Injection** (внедрение зависимостей) — это когда объект **не создаёт** свои зависимости сам, а **получает** их извне: через конструктор, через сеттер или через параметр метода.

Три способа инжекции — три подхода, которые отличаются тем, **когда** и **как** зависимость попадает в объект.

### Через конструктор

Самый частый и самый «правильный» способ. Зависимость передаётся в конструкторе, и объект **не может** существовать без неё.

```java
class OrderService {
    private final PaymentProcessor processor;

    OrderService(PaymentProcessor processor) {
        if (processor == null) {
            throw new IllegalArgumentException("PaymentProcessor обязателен");
        }
        this.processor = processor;
    }

    void process(Order order) {
        processor.pay(order.getTotal());
    }
}
```

Создание:

```java
OrderService service = new OrderService(new StripePaymentProcessor("api_key"));
```

**Плюсы:**
- **Объект не может существовать в «недоделанном» виде.** Если зависимость не передана, — конструктор не сработает. Нельзя «забыть» её установить.
- **Поле можно сделать `final`.** После создания объекта зависимость не изменится — а это хорошо для потокобезопасности и предсказуемости.
- **Все зависимости видны сразу.** По сигнатуре конструктора понятно, **что** нужно объекту для работы.
- **Легко тестировать.** В тестах просто передаём заглушку в конструктор.

**Минусы:**
- **Много зависимостей — длинный конструктор.** Если у класса пять зависимостей, — конструктор из пяти аргументов. Читать неудобно, но это **честно**: если у класса пять зависимостей, — может, он делает слишком много.
- **Циклические зависимости невозможны.** Если `A` зависит от `B`, а `B` от `A`, — нельзя передать их друг другу в конструкторе. Это **плюс**, а не минус: циклы в зависимостях — признак плохого дизайна.

### Через сеттер

Зависимость передаётся через отдельный метод после создания.

```java
class OrderService {
    private PaymentProcessor processor;

    void setProcessor(PaymentProcessor processor) {
        this.processor = processor;
    }

    void process(Order order) {
        if (processor == null) {
            throw new IllegalStateException("PaymentProcessor не установлен");
        }
        processor.pay(order.getTotal());
    }
}
```

Создание:

```java
OrderService service = new OrderService();
service.setProcessor(new StripePaymentProcessor("api_key"));
```

**Плюсы:**
- **Можно менять зависимость «на лету».** Полезно, если зависимость действительно должна меняться (например, выбор платёжной системы пользователем).
- **Позволяет обойти циклы.** Если у `A` и `B` циклическая зависимость (что редко бывает нужно), — можно установить их друг другу через сеттеры.

**Минусы:**
- **Объект может быть в «недоделанном» виде.** Между `new OrderService()` и `setProcessor(...)` объект не готов к использованию. Если кто-то вызовет `process` — упадёт.
- **Поле нельзя сделать `final`.** Зависимость может измениться в любой момент — сложнее рассуждать о поведении.
- **Не все зависимости видны сразу.** По сигнатуре класса непонятно, что ему нужен `PaymentProcessor` — это видно только по коду.

**Когда использовать:** **редко**. В основном — когда зависимость действительно опциональна или должна меняться.

### Через параметр метода

Зависимость передаётся прямо в метод, который её использует.

```java
class OrderService {
    void process(Order order, PaymentProcessor processor) {
        processor.pay(order.getTotal());
    }
}
```

**Плюсы:**
- **Максимальная гибкость.** Каждый вызов может использовать **свою** зависимость.
- **Нет состояния.** `OrderService` не хранит `processor` — он «одноразовый».

**Минусы:**
- **Каждый вызов должен передавать зависимость.** Неудобно, если `OrderService` вызывается из десяти мест.
- **Зависимость «размазывается» по вызовам.** Её нельзя «настроить один раз» — приходится передавать каждый раз.
- **Не подходит для зависимостей, которые «живут» дольше одного вызова** (например, `Database`, `Logger`).

**Когда использовать:** **редко**. В основном — когда зависимость действительно «на один вызов» (например, стратегия сортировки в `list.sort(comparator)`).

## Почему через конструктор — «правильно»

Из трёх способов **конструктор** — самый частый и самый рекомендуемый. Причин несколько.

**Первая: объект всегда в валидном состоянии.** После `new OrderService(processor)` объект **готов к работе**. Нет «промежуточного» состояния, в котором он не готов. Это важно для многопоточности: объект, созданный в одном потоке, можно безопасно передать в другой — он уже полностью инициализирован.

**Вторая: зависимости неизменяемы.** Поле `final` — после создания объекта оно не изменится. Это делает поведение предсказуемым: `OrderService` всегда работает с **тем** `processor`, который был передан. Не «иногда этим, иногда тем».

**Третья: зависимости явные.** По сигнатуре конструктора сразу видно, что нужно объекту. Не надо читать весь класс, чтобы понять, что он использует. Это важно при чтении кода: `new OrderService(processor, notifier, repository)` — и вы сразу понимаете, **что** делает `OrderService` (оплата, уведомления, сохранение).

**Четвёртая: тестировать легко.** В тестах просто передаём заглушки. Не нужно «настраивать» объект после создания или использовать рефлексию.

**Пятая: циклические зависимости видны сразу.** Если `A` зависит от `B`, а `B` от `A`, — конструкторы не сработают. Это **хорошо**: циклы в зависимостях — признак плохого дизайна, и лучше узнать о них **на этапе компиляции**, чем ловить `StackOverflowError` в runtime.

**Правило:** **если зависимость обязательна — через конструктор. Если опциональна — через сеттер. Если на один вызов — через параметр.** В 90% случаев — конструктор.

## Что даёт DI

Мы уже говорили об этом в прошлом уроке, но повторим с акцентом на DI.

**Гибкость.** Замена реализации — одна строчка в `main` или в конфигурации. Код, который использует зависимость, не меняется.

**Тестируемость.** В тестах — заглушки. Никакого реального Stripe, PostgreSQL, SMTP. Тесты быстрые, детерминированные, не требуют инфраструктуры.

**Изоляция.** Каждый класс тестируется **отдельно**. `OrderService` — с заглушкой `PaymentProcessor`. `PaymentProcessor` — с заглушкой `HttpClient`. Каждый тест проверяет **только свой** класс.

**Прозрачность.** По сигнатуре конструктора видно, что нужно классу. Это документация, которая не устаревает.

**Слабая связанность.** Классы зависят от **интерфейсов**, а не от реализаций. Это и есть decoupling из прошлого урока.

## DI без фреймворка

Многие думают, что DI — это Spring. Это не так. DI — это **принцип**, а Spring — это **фреймворк**, который его реализует. Принцип можно применять где угодно.

Вот пример DI **без** Spring:

```java
public class Main {
    public static void main(String[] args) {
        // Создаём зависимости
        PaymentProcessor processor = new StripePaymentProcessor(
            System.getenv("STRIPE_KEY")
        );
        NotificationSender notifier = new SmtpNotificationSender(
            "smtp.example.com", 587
        );
        OrderRepository repository = new JpaOrderRepository();

        // Внедряем их в сервис
        OrderService service = new OrderService(processor, notifier, repository);

        // Работаем
        service.placeOrder(new Order(...));
    }
}
```

Здесь DI есть, а Spring — нет. Мы **вручную** создали зависимости и **вручную** передали их в конструктор. Это и есть DI в чистом виде.

Что даёт Spring? Он **автоматизирует** этот процесс: вместо ручного `new` и ручной передачи — аннотации и автоматическое связывание. Но **принцип** — тот же.

**Когда Spring полезен.** Когда зависимостей много (десятки, сотни), когда они создаются в разных местах, когда нужны «жизненные циклы» (singleton, prototype) — тогда ручное управление становится утомительным, и фреймворк помогает.

**Когда Spring НЕ нужен.** Когда приложение маленькое, зависимостей мало, и `main` с десятком `new` — это нормально. Не тащите Spring в проект, где его не требуется. DI работает и без него.

## «Ручной» DI vs DI-контейнер

Когда говорят «DI», часто имеют в виду **DI-контейнер** — фреймворк, который **сам** создаёт зависимости и **сам** их связывает. Например, Spring:

```java
@Service
class OrderService {
    private final PaymentProcessor processor;

    @Autowired
    OrderService(PaymentProcessor processor) {
        this.processor = processor;
    }
}

@Component
class StripePaymentProcessor implements PaymentProcessor {
    // ...
}
```

Spring **сам** находит `StripePaymentProcessor` (потому что он `@Component`), **сам** создаёт его и **сам** передаёт в `OrderService`. Вам не нужно писать `new`.

**Плюсы DI-контейнера:**
- **Меньше boilerplate.** Не нужно писать `new` и связывать всё вручную.
- **Управление жизненным циклом.** Контейнер сам решает, когда создавать объект (singleton, prototype) и когда уничтожать.
- **Единая конфигурация.** Все зависимости — в одном месте (в аннотациях или XML).

**Минусы DI-контейнера:**
- **Магия.** Не всегда понятно, **откуда** взялась зависимость. `@Autowired` — и всё работает, но **как** — не видно.
- **Сложность.** Контейнер сам по себе — большая система. Для маленького проекта это overkill.
- **Сложность тестирования.** Иногда нужно поднимать контейнер целиком, чтобы протестировать один класс.
- **Привязка к фреймворку.** Если используете Spring — вы «в нём». Заменить на что-то другое потом сложно.

**Когда что выбрать.** Для маленьких проектов — **ручной DI** (как в примере выше). Для больших — **DI-контейнер** (Spring, Guice, Dagger). Но принцип — один: **объект не создаёт зависимости сам, а получает их извне**.

## Аналогия, которая помогает

Хорошая аналогия — **конструктор LEGO и готовый набор**.

**Готовый набор** — это класс, который **сам создаёт** свои зависимости. Все детали «вшиты» внутрь. Работает, но если захотите поменять одну деталь — придётся разбирать весь набор.

**Конструктор LEGO** — это класс с DI. Вы **сами** выбираете детали (в `main` или в конфигурации) и **сами** их вставляете. Набор «оживает», когда вы его собрали. И вы можете собрать **разные** вещи из одних и тех же деталей.

**`main`** — это «стол, на котором вы собираете». Вы кладёте детали (создаёте зависимости), собираете из них что-то (передаёте в конструкторы) и запускаете (вызываете методы).

**DI-контейнер** — это «автоматическая сборка». Вы даёте ему коробку с деталями (аннотации) и говорите «собери мне вот это» (запросите бин). Он сам находит нужные детали и собирает. Удобно, но менее прозрачно: не всегда видно, **как** он это сделал.

**Идея DI** в том, что **класс — это не «готовый набор», а «инструкция по сборке»**. Он говорит: «мне нужны такие-то детали», а **какие именно** — решает тот, кто собирает.

## Микрозадача 1

Вот класс. Определите, что в нём не так с точки зрения DI, и перепишите его.

```java
class UserService {
    private final UserRepository repository = new JpaUserRepository();
    private final EmailSender emailer = new SmtpEmailSender("smtp.example.com");
    private final PasswordHasher hasher = new BcryptPasswordHasher(12);

    void register(String email, String password) {
        String hash = hasher.hash(password);
        User user = new User(email, hash);
        repository.save(user);
        emailer.send(email, "Добро пожаловать!");
    }
}
```

### Разбор

**Что не так.** `UserService` **сам создаёт** три зависимости:

- `new JpaUserRepository()` — привязан к JPA;
- `new SmtpEmailSender("smtp.example.com")` — привязан к SMTP и к конкретному хосту;
- `new BcryptPasswordHasher(12)` — привязан к bcrypt и к конкретной «стоимости».

**Проблемы:**
- **В тестах нельзя подставить заглушки.** Каждый тест создаёт реальные `JpaUserRepository`, `SmtpEmailSender`, `BcryptPasswordHasher`. Тесты будут медленными, будут требовать БД и SMTP, будут «мигать».
- **Нельзя поменять реализацию.** Захотите перейти на `MongoUserRepository` — придётся менять `UserService`. Захотите `ArgonPasswordHasher` вместо bcrypt — тоже.
- **`smtp.example.com` «вшит» в код.** Для тестов и для продакшена хост должен быть разным — а он один.
- **`12` «вшито» в код.** Стоимость bcrypt — параметр, который должен быть настраиваемым.
- **`UserService` знает слишком много.** Он знает, что `JpaUserRepository` — это репозиторий, что `SmtpEmailSender` требует хост, что `BcryptPasswordHasher` требует стоимость. Это не его забота.

**Как переписать:**

```java
interface UserRepository {
    void save(User user);
}

interface EmailSender {
    void send(String to, String message);
}

interface PasswordHasher {
    String hash(String password);
}

class UserService {
    private final UserRepository repository;
    private final EmailSender emailer;
    private final PasswordHasher hasher;

    UserService(UserRepository repository, EmailSender emailer, PasswordHasher hasher) {
        this.repository = repository;
        this.emailer = emailer;
        this.hasher = hasher;
    }

    void register(String email, String password) {
        String hash = hasher.hash(password);
        User user = new User(email, hash);
        repository.save(user);
        emailer.send(email, "Добро пожаловать!");
    }
}
```

Создание — в `main`:

```java
UserRepository repository = new JpaUserRepository();
EmailSender emailer = new SmtpEmailSender(System.getenv("SMTP_HOST"));
PasswordHasher hasher = new BcryptPasswordHasher(12);

UserService service = new UserService(repository, emailer, hasher);
```

Теперь:

- **Тестируется** — с заглушками `FakeRepository`, `FakeEmailSender`, `FakeHasher`.
- **Меняется** — замена `JpaUserRepository` на `MongoUserRepository` не трогает `UserService`.
- **Настраивается** — хост SMTP и стоимость bcrypt — в `main` (или в конфиге), а не в классе.

**Что мы получили:**
- `UserService` **не знает**, какая реализация за интерфейсами.
- **Все зависимости явно видны** в конструкторе.
- **Все поля `final`** — после создания не меняются.

**Мораль.** «Объект сам создаёт зависимости» — это антипаттерн, который называется «control freak» (или «скрытые зависимости»). Он привязывает класс к инфраструктуре и делает его нетестируемым. DI — лекарство от этого.

## Микрозадача 2

Вот два варианта `OrderService`. Определите, какой лучше с точки зрения DI, и объясните, почему.

```java
// Вариант A: конструктор
class OrderService {
    private final PaymentProcessor processor;
    private final NotificationSender notifier;

    OrderService(PaymentProcessor processor, NotificationSender notifier) {
        this.processor = processor;
        this.notifier = notifier;
    }

    void placeOrder(Order order) {
        processor.pay(order.getTotal());
        notifier.send(order.getCustomerEmail(), "Заказ оформлен");
    }
}

// Вариант B: сеттеры
class OrderService {
    private PaymentProcessor processor;
    private NotificationSender notifier;

    void setProcessor(PaymentProcessor processor) {
        this.processor = processor;
    }

    void setNotifier(NotificationSender notifier) {
        this.notifier = notifier;
    }

    void placeOrder(Order order) {
        processor.pay(order.getTotal());
        notifier.send(order.getCustomerEmail(), "Заказ оформлен");
    }
}
```

### Разбор

**Вариант A (конструктор) — лучше.** Причин несколько.

**Первая: объект всегда готов.** После `new OrderService(processor, notifier)` — `placeOrder` работает. В варианте B между `new OrderService()` и `setProcessor(...)` объект **не готов**: `placeOrder` упадёт с `NullPointerException`, если его вызовут до установки зависимостей.

**Вторая: зависимости обязательны.** Сигнатура конструктора **требует** две зависимости. Нельзя «забыть» установить. В варианте B можно забыть `setProcessor` и не заметить, пока не вызовешь `placeOrder`.

**Третья: поля `final`.** В варианте A — `final`, значит, после создания не меняются. Это предсказуемо: `OrderService` всегда работает с **теми** зависимостями, что передали. В варианте B — не `final`, значит, могут измениться в любой момент. Это сложнее для рассуждения и для многопоточности.

**Четвёртая: читаемость.** По сигнатуре `new OrderService(processor, notifier)` сразу видно, **что** нужно. В варианте B нужно читать весь класс, чтобы понять, какие зависимости есть.

**Когда вариант B оправдан.**

- **Зависимость действительно опциональна** — например, «если `notifier` не установлен, — уведомления не отправляются». Но это можно выразить и через конструктор: `new OrderService(processor, NullNotifier.INSTANCE)` — с явным «пустым» notifier'ом.
- **Циклическая зависимость** — если `A` и `B` зависят друг от друга. Но это **признак плохого дизайна**: скорее всего, стоит вынести общую часть в третий класс.
- **Фреймворк требует** — некоторые старые фреймворки (например, сервлеты) требуют setter-инъекции. Но это не «хорошо», а «так получилось».

**Мораль.** **Конструктор — почти всегда лучше.** Если сомневаетесь — используйте конструктор. Исключения редки и обычно означают, что с дизайном что-то не так.

А пока — маленькое упражнение на наблюдательность. Откройте любой свой проект (или открытый проект на Java) и найдите все `new` внутри классов (не в `main`, не в фабриках — а в обычных методах и полях). Для каждого задайте вопрос: **а не должен ли этот `new` быть снаружи?** Если класс создаёт зависимость сам, — он привязан к ней. Если зависимость передаётся снаружи — он свободен. И проверьте: можно ли протестировать этот класс, подставив заглушку? Если нет — DI не хватает. Просто найдите. Не переделывайте (пока). Понимание того, **где** создаются зависимости, — уже большой шаг к более гибкому коду.

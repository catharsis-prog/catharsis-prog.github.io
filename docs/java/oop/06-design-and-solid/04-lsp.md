# 4. LSP: подстановка без сюрпризов

## Где вы это уже видели

В прошлых уроках мы дважды подходили к одной и той же проблеме: «наследование, которое врёт». В модуле 3, в уроке 7, мы говорили о «квадрате и прямоугольнике», а в практикуме разбирали `Square extends Rectangle` как классический пример неправильного наследования. Пора дать этой проблеме имя. Оно есть — **принцип подстановки Барбары Лисков**, или сокращённо **LSP**.

Принцип звучит просто: **объект подкласса должен быть подставляем вместо объекта суперкласса без нарушения корректности программы**. Но за этой простотой скрывается целая философия, и понять её — значит **перестать** использовать наследование там, где оно **формально работает, но по сути врёт**.

**Ситуация первая.** Вы покупаете чехол для телефона. На коробке написано: «Подходит для iPhone 13, 14, 15». Вы покупаете, приходите домой, — и чехол **не подходит** для вашего iPhone 13. Хотя на коробке написано «подходит». Продавец нарушил контракт: он **обещал** совместимость, а её **нет**. Это нарушение LSP: «новый чехол» **не подставляется** вместо «старого чехла».

**Ситуация вторая.** Вы заказываете в ресторане «стейк». В меню написано: «стейк из говядины, прожарка medium». Вам приносят **куриную грудку**. Формально «это тоже стейк» (в каком-то смысле), но **не в том**, что обещано в меню. Вы **не можете** использовать куриную грудку там, где ожидали стейк из говядины. Нарушение LSP.

**Ситуация третья.** Вы нанимаете водителя с правами категории B. Он показывает права — всё в порядке. Но когда вы сажаете его за руль **грузовика** (категория C), — он **не справляется**. Формально «он водитель», но **не в том смысле**, который нужен для грузовика. Нарушение LSP.

**Ситуация четвёртая.** Вы работаете с банковской картой. Она обещает: «можно платить в любом магазине». Вы приходите в магазин, — и карта **не принимается**. Формально «это карта», но **не в том смысле**, в котором вы ожидали. Нарушение LSP.

**Ситуация пятая.** Вы работаете с API. Документация обещает: «метод `getUser(id)` возвращает пользователя или `null`, если не найден». Вы вызываете — и **падает** с исключением, если пользователь не найден. Формально «метод тот же», но **ведёт себя иначе**, чем обещано. Нарушение LSP.

**Ситуация шестая.** Вы видите код:

```java
class Rectangle {
    protected int width;
    protected int height;

    void setWidth(int w) { width = w; }
    void setHeight(int h) { height = h; }
    int area() { return width * height; }
}

class Square extends Rectangle {
    @Override
    void setWidth(int w) {
        super.setWidth(w);
        super.setHeight(w);
    }

    @Override
    void setHeight(int h) {
        super.setWidth(h);
        super.setHeight(h);
    }
}
```

— и понимаете, что если передать `Square` туда, где ожидается `Rectangle`, и вызвать `setWidth(5); setHeight(4);` — площадь будет **не 20**, а 16. Потому что `Square` **нарушает** контракт `Rectangle`. Знакомо? Тогда этот урок для вас.

## Что такое LSP

**Liskov Substitution Principle** (принцип подстановки Барбары Лисков) — сформулирован **Барбарой Лисков** в 1987 году в докладе «Data Abstraction and Hierarchy».

Формулировка: **«Если для каждого объекта `o1` типа `S` существует объект `o2` типа `T`, такой что для всех программ `P`, определённых в терминах `T`, поведение `P` не меняется при замене `o2` на `o1`, то `S` является подтипом `T`».**

Если перевести на человеческий: **«Объект подкласса должен вести себя как объект суперкласса во всех отношениях».**

Или ещё короче: **«Подкласс не должен удивлять»**.

**Ключевая идея:** **наследование — это не только «унаследовать поля и методы», но и «унаследовать контракт»**. Если родитель **обещает** определённое поведение, — наследник **обязан** его **выполнять**. Не «выполнять как-то», а **именно так**, как **обещано**.

**Что такое «контракт».** Это набор **утверждений** о том, что метод делает:

- **предусловия** — что должно быть **верно до** вызова (например, «параметр не `null`»);
- **постусловия** — что будет **верно после** вызова (например, «результат — не `null`»);
- **инварианты** — что **всегда верно** для объекта (например, «ширина и высота — не отрицательные»).

**Подкласс обязан соблюдать контракт родителя.** Не может **ослаблять** предусловия (требовать **меньше**), не может **усиливать** постусловия (обещать **больше**), не может **нарушать** инварианты. Может **усиливать** предусловия (требовать **больше** — но тогда он **не подставляем**) и **ослаблять** постусловия (обещать **меньше** — но тогда он **не подставляем**). То есть — **строго** соблюдать **или** усиливать гарантии (требовать меньше, обещать больше), но **не ослаблять** их.

## Классический пример: квадрат и прямоугольник

Разберём подробно, потому что это **самый частый** пример нарушения LSP.

**С точки зрения математики:** квадрат — **частный случай** прямоугольника. У квадрата все углы прямые, все стороны равны. «Квадрат является прямоугольником» — **верно**.

**С точки зрения кода:**

```java
class Rectangle {
    protected int width;
    protected int height;

    void setWidth(int w) { width = w; }
    void setHeight(int h) { height = h; }

    int area() { return width * height; }
}

class Square extends Rectangle {
    @Override
    void setWidth(int w) {
        super.setWidth(w);
        super.setHeight(w);
    }

    @Override
    void setHeight(int h) {
        super.setWidth(h);
        super.setHeight(h);
    }
}
```

**Контракт `Rectangle`:**
- «можно установить ширину **независимо** от высоты» (`setWidth`);
- «можно установить высоту **независимо** от ширины» (`setHeight`);
- «площадь = ширина × высота» (`area`).

**Что делает `Square`:**
- `setWidth(5)` устанавливает **и** ширину, **и** высоту в 5. Это **нарушает** контракт «независимо».
- `setHeight(4)` устанавливает **и** ширину, **и** высоту в 4. Опять нарушает.

**Что происходит, если использовать `Square` вместо `Rectangle`:**

```java
void test(Rectangle r) {
    r.setWidth(5);
    r.setHeight(4);
    assert r.area() == 20;   // ожидание от Rectangle
}

test(new Rectangle());   // ✅ area = 20
test(new Square());      // ❌ area = 16, assertion fails
```

Функция `test` **написана** для `Rectangle` и **ожидает** его контракт. `Square` **не выполняет** контракт. Значит, `Square` **не является** `Rectangle` **в том смысле**, в котором определён `Rectangle`. LSP **нарушен**.

**Что не так с «математической» логикой.** «Квадрат — это прямоугольник» — верно **для математических объектов** (неизменяемых, без сеттеров). Но `Rectangle` **в коде** — это **изменяемый** объект с **сеттерами**. Математический прямоугольник **не имеет** операции «изменить ширину» — он **фиксирован**. Как только вы добавляете **изменяемость**, — контракт **меняется**, и математическая аналогия **перестаёт работать**.

**Как исправить.**

**Вариант 1: не наследовать.** `Square` — **отдельный** класс, не связанный с `Rectangle`:

```java
class Rectangle {
    private final int width, height;

    Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }

    int area() { return width * height; }
}

class Square {
    private final int side;

    Square(int side) {
        this.side = side;
    }

    int area() { return side * side; }
}
```

**Вариант 2: сделать `Rectangle` неизменяемым.** Если `Rectangle` **не имеет** сеттеров, — `Square` **может** наследоваться:

```java
class Rectangle {
    private final int width, height;

    Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }

    int area() { return width * height; }
}

class Square extends Rectangle {
    Square(int side) {
        super(side, side);
    }
}
```

Теперь `Square` **не нарушает** контракт: у `Rectangle` **нет** `setWidth`/`setHeight`, которые можно было бы «сломать». `Square` **просто** создаёт прямоугольник с равными сторонами. LSP **соблюдается**.

**Вариант 3: общий интерфейс.** `Shape` с методом `area()`, `Rectangle` и `Square` — **независимые** реализации:

```java
interface Shape {
    int area();
}

class Rectangle implements Shape {
    private final int width, height;

    Rectangle(int width, int height) {
        this.width = width;
        this.height = height;
    }

    public int area() { return width * height; }
}

class Square implements Shape {
    private final int side;

    Square(int side) {
        this.side = side;
    }

    public int area() { return side * side; }
}
```

Теперь нет «родителя-наследника», есть «общий контракт». LSP **соблюдается** (никто никого не подменяет).

**Мораль.** «Квадрат — это прямоугольник» **математически** — верно. **Программно** — **зависит** от контракта. Если контракт **изменяемый** — не наследовать. Если **неизменяемый** — можно. Если **общий интерфейс** — лучше.

## Другие классические примеры

**Пингвин и птица.** «Птица умеет летать» — `Bird` с `fly()`. `Penguin extends Bird` — но `fly()` бросает `UnsupportedOperationException`. Нарушение LSP: `Penguin` **не является** `Bird` в том смысле, в котором определён `Bird`. **Решение:** `Bird` без `fly()`, `FlyingBird extends Bird` с `fly()`. `Penguin extends Bird`, `Sparrow extends FlyingBird`.

**Страус и птица.** То же самое.

**`Stack extends Vector` (Java 1.0).** `Stack` наследует `Vector` и получает все его методы: `add(int, E)`, `remove(int)`, `set(int, E)`. Но стек **не позволяет** вставку в середину. Нарушение LSP: если функция ожидает `Vector` и вставляет в середину, — со `Stack` она сломается. **Решение:** `Stack` **содержит** `Vector` (композиция), а не наследует. Так в современной Java и сделано: `Stack` наследует `Vector` (для обратной совместимости), но **рекомендуется** использовать `Deque`.

**Иммутабельный `List` и `ArrayList`.** `List` обещает `add`. `Collections.unmodifiableList` возвращает `List`, который **бросает** `UnsupportedOperationException` при `add`. Формально — `List`, по факту — **не выполняет** контракт. Нарушение LSP. **Решение:** в Java **нет** отдельного интерфейса «изменяемый список»; это **известная проблема**, и с ней живут, **документируя** поведение.

**`FileInputStream` и `ByteArrayInputStream`.** Оба — `InputStream`. `FileInputStream` **может** бросить `IOException`, `ByteArrayInputStream` — **нет**. Формально — оба `InputStream`, по факту — **разные** контракты. Это **допустимое** нарушение: `IOException` — это **checked exception**, и код, работающий с `InputStream`, **обязан** его обрабатывать. Так что `ByteArrayInputStream` **не нарушает** контракт — он **просто** не бросает (а мог бы). LSP **соблюдается** (постусловие «может быть IOException» **ослаблено** до «не будет IOException» — это **допустимо**).

**Мораль.** LSP — это **про контракт**, а не про «формальное наследование». `class B extends A` **не гарантирует** LSP. LSP **гарантируется** только тогда, когда `B` **соблюдает** **все** обязательства `A`.

## LSP и контракты: предусловия, постусловия, инварианты

Формально LSP формулируется через **контракты**. Три части: **предусловия**, **постусловия**, **инварианты**. Разберём подробно.

### Предусловия

**Предусловие** — это **требование** к вызывающему коду: «перед вызовом должно быть верно X». Например, «параметр не `null`», «сумма положительная», «файл существует».

**Правило LSP:** **подкласс не может усиливать предусловия**. Если родитель **принимает** любое значение, — наследник **не может** требовать «только положительное». Иначе код, работающий с родителем, **сломается** с наследником.

**Пример нарушения.** `Rectangle.setWidth(int w)` **принимает** любое `int`. `Square.setWidth(int w)` **тоже** принимает любое `int` (не усиливает). Но **семантически** — `Square` **требует**, чтобы `width == height`. Формально **не нарушает** (по сигнатуре), но **фактически** — нарушает (по **ожидаемому** поведению).

**Пример соблюдения.** Родитель: «принимает строку любой длины». Наследник: «принимает строку **непустую**». **Нарушение** (усилил предусловие). Наследник: «принимает строку **любой длины, включая пустую**». **Соблюдение** (не усилил).

### Постусловия

**Постусловие** — это **гарантия** вызывающему коду: «после вызова будет верно Y». Например, «результат не `null`», «файл создан», «список отсортирован».

**Правило LSP:** **подкласс не может ослаблять постусловия**. Если родитель **гарантирует** «результат не `null`», — наследник **не может** возвращать `null`. Иначе код, работающий с родителем, **сломается** с наследником.

**Пример нарушения.** `Repository.findById` **обещает** «возвращает пользователя или `null`, если не найден». `CachingRepository.findById` **бросает** `NoSuchElementException`, если не найден. **Нарушение** (ослабил постусловие: вместо «`null`» — исключение).

**Пример соблюдения.** `Repository.findById` **обещает** «может вернуть `null`». `CachingRepository.findById` **всегда** возвращает **непустой** объект (потому что кэш). **Соблюдение** (усилил постусловие: вместо «может быть `null`» — «не будет `null`»).

### Инварианты

**Инвариант** — это **свойство**, которое **всегда** верно для объекта. Например, «ширина и высота не отрицательные», «баланс не отрицательный», «список не `null`».

**Правило LSP:** **подкласс не может нарушать инварианты родителя**. Если родитель **гарантирует** «ширина не отрицательная», — наследник **тоже** должен это гарантировать.

**Пример нарушения.** `Rectangle` **гарантирует** «width >= 0 и height >= 0». `Square` **гарантирует** «width == height». Формально **не нарушает** инвариант `Rectangle` (0 == 0, 5 == 5, ...). Но **добавляет** свой инвариант, который **конфликтует** с **операциями** `Rectangle` (`setWidth`). Это **тонкий** случай: инвариант **не нарушен**, но **операции** нарушают. LSP **нарушен** через операции, а не через инварианты.

**Пример соблюдения.** `Rectangle` **гарантирует** «width >= 0». `Square` **гарантирует** «width >= 0 и width == height». **Соблюдение**: `Square` **усиливает** инвариант, не нарушая.

## Как проверить LSP

Есть несколько **практических** способов **проверить**, соблюдается ли LSP в вашей иерархии.

**Способ 1: тесты.** Напишите тесты для **родителя**. Прогоните их для **всех** наследников. Если какой-то наследник **не проходит** — LSP нарушен.

**Пример.** Тест для `Rectangle`: `setWidth(5); setHeight(4); assert area == 20;`. Прогон для `Square` — **падает**. LSP нарушен.

**Способ 2: типичные сценарии.** Представьте **типичные** операции над родителем (из документации, из тестов, из реального кода). Для **каждой** проверьте: «работает ли она с наследником?».

**Способ 3: вопросы.** Задайте вопросы:

- «Может ли наследник **отказаться** от операции родителя?» Если да — LSP нарушен.
- «Может ли наследник **требовать больше** от вызывающего кода?» Если да — LSP нарушен.
- «Может ли наследник **обещать меньше** вызывающему коду?» Если да — LSP нарушен.
- «Может ли наследник **нарушить инвариант** родителя?» Если да — LSP нарушен.

**Способ 4: «запах».** Если в наследнике вы **вынуждены** бросать `UnsupportedOperationException`, **проверять** `if (this instanceof ...)`, **обходить** логику родителя, — это **признак** нарушения LSP.

## Аналогия, которая помогает

Хорошая аналогия — **подмена в футбольной команде**.

**Тренер** выпускает на поле **нападающего**. Нападающий **обещает**: «буду забивать голы, открываться, прессинговать». Это **контракт** нападающего.

**Замена** — другой нападающий. Он **тоже** нападающий, **тоже** обещает «забивать, открываться, прессинговать». Тренер **уверен**, что замена **усилит** игру (или хотя бы **не испортит**). LSP **соблюдён**: новый нападающий **подставляется** вместо старого **без сюрпризов**.

**Плохая замена** — защитник, который «вроде бы футболист». Формально «он игрок», но **не нападающий**. Если тренер **ожидает** «забивать», а защитник **не забивает**, — игра **ломается**. LSP **нарушен**: защитник **не подставляется** вместо нападающего **без сюрпризов**.

**Ещё хуже** — нападающий, который **отказывается** бегать. «Я нападающий, но бегать не буду». Формально «нападающий», но **не выполняет** контракт. LSP **нарушен**.

**Что важно:** LSP — это **не про «формальную должность»**, а про **«выполнение обещаний»**. Нападающий **обещает** одно, защитник — **другое**. Если вы **меняете** одного на другого, — **меняется** игра. Если вы **оставляете** нападающего нападающим — игра **не меняется**. LSP **соблюдён**.

**И ещё.** Тренер **не знает**, **какой именно** нападающий выйдет на поле. Он **знает** только, что тот **умеет** забивать. Это **полиморфизм** (модуль 4) **и** LSP **вместе**: код работает с **контрактом** (`Striker`), а **конкретная** реализация (`Messi`, `Ronaldo`) **подставляется** без сюрпризов.

## Микрозадача 1

Вот иерархия. Определите, **нарушается** ли LSP, и если да — как исправить.

```java
class Bird {
    void fly() {
        System.out.println("Лечу!");
    }
}

class Penguin extends Bird {
    @Override
    void fly() {
        throw new UnsupportedOperationException("Пингвины не летают");
    }
}
```

### Разбор

**LSP нарушен.** `Bird` **обещает** «умеет летать» (`fly` **работает**). `Penguin` **не выполняет** это обещание: `fly` **бросает** исключение. Код, который **ожидает** `Bird` и вызывает `fly`, — **сломается** с `Penguin`. Формально «пингвин — птица», но **не в том смысле**, в котором определён `Bird`.

**Как исправить.** Есть несколько вариантов.

**Вариант 1: разделить на два класса.**

```java
class Bird {
    void eat() { System.out.println("Ем"); }
    void sleep() { System.out.println("Сплю"); }
}

class FlyingBird extends Bird {
    void fly() { System.out.println("Лечу!"); }
}

class Penguin extends Bird {
    // не реализует fly — и не обещает
}

class Sparrow extends FlyingBird {
    // реализует fly
}
```

Теперь `Bird` **не обещает** `fly`. `Penguin` **не нарушает** контракт. `Sparrow` **обещает** и **выполняет**. LSP **соблюдён**.

**Вариант 2: интерфейс `Flying`.**

```java
class Bird { /* ... */ }

interface Flying {
    void fly();
}

class Sparrow extends Bird implements Flying {
    public void fly() { System.out.println("Лечу!"); }
}

class Penguin extends Bird {
    // не реализует Flying
}
```

Теперь `fly` — это **отдельный** контракт. `Sparrow` **подписывается** под ним. `Penguin` — **нет**. LSP **соблюдён**.

**Вариант 3: сделать `fly` пустым.** **Плохой** вариант, но иногда используется:

```java
class Bird {
    void fly() {
        // ничего не делает
    }
}
```

**Почему плохо:** `fly` **не бросает** исключение, но и **не летит**. Это **тихий отказ**: код ожидает «лечу», а получает «ничего». LSP **формально** соблюдён (нет `UnsupportedOperationException`), но **по смыслу** — нарушен: `Penguin` **не выполняет** контракт «лечу», а **делает вид**, что выполняет. **Хуже**, чем явное исключение.

**Мораль.** LSP — это **про контракт**, а не про «формальное наследование». Если наследник **не может** выполнить контракт — **не наследуй**. Раздели на **отдельные** типы или **интерфейсы**.

## Микрозадача 2

Вот иерархия. Определите, **нарушается** ли LSP, и если да — как исправить.

```java
interface Repository<T> {
    T findById(long id);
    void save(T entity);
    void delete(long id);
    List<T> findAll();
}

class ReadOnlyRepository<T> implements Repository<T> {
    @Override
    public T findById(long id) { /* ... */ return null; }

    @Override
    public void save(T entity) {
        throw new UnsupportedOperationException("Только чтение");
    }

    @Override
    public void delete(long id) {
        throw new UnsupportedOperationException("Только чтение");
    }

    @Override
    public List<T> findAll() { /* ... */ return List.of(); }
}
```

### Разбор

**LSP нарушен.** `Repository` **обещает**: «можно сохранить (`save`), удалить (`delete`), найти (`findById`), получить все (`findAll`)». `ReadOnlyRepository` **не выполняет** `save` и `delete` — **бросает** `UnsupportedOperationException`. Код, который **ожидает** `Repository` и вызывает `save`, — **сломается** с `ReadOnlyRepository`.

**Как исправить.** Разделить интерфейсы.

**Вариант 1: `ReadableRepository` и `WritableRepository`.**

```java
interface ReadableRepository<T> {
    T findById(long id);
    List<T> findAll();
}

interface WritableRepository<T> {
    void save(T entity);
    void delete(long id);
}

interface Repository<T> extends ReadableRepository<T>, WritableRepository<T> {
    // объединяет оба
}

class ReadOnlyRepository<T> implements ReadableRepository<T> {
    public T findById(long id) { /* ... */ return null; }
    public List<T> findAll() { /* ... */ return List.of(); }
}

class FullRepository<T> implements Repository<T> {
    // реализует всё
}
```

Теперь `ReadOnlyRepository` **не обещает** `save` и `delete`. LSP **соблюдён**.

**Вариант 2: `ReadOnlyRepository` не реализует `Repository` вообще.**

```java
class ReadOnlyRepository<T> {
    public T findById(long id) { /* ... */ return null; }
    public List<T> findAll() { /* ... */ return List.of(); }
}
```

Проще, но теряется **общий контракт** (если кому-то нужно «любой репозиторий, у которого есть `findById`»).

**Мораль.** LSP — это **про контракт**, и если реализация **не может** выполнить часть контракта — **не реализуй** этот интерфейс. Разделяй на **маленькие** интерфейсы (**это ISP, о котором будем говорить в следующем уроке**). LSP и ISP **связаны**: ISP помогает **соблюдать** LSP, разделяя «толстые» интерфейсы на «тонкие».

## Самостоятельная задача

Возьмите **любую** иерархию из вашего проекта (или из открытого проекта на Java), в которой есть **наследование** (`extends`) или **реализация интерфейса** (`implements`).

Подумайте:

- **какой контракт** у родителя? Что он **обещает** (предусловия, постусловия, инварианты)?
- **выполняет** ли наследник этот контракт **полностью**? Или есть **случаи**, когда он **не выполняет**?
- есть ли в наследнике **`UnsupportedOperationException`**, **пустые методы**, **проверки типа** (`instanceof`), **обходы** логики родителя? Если да — это **признаки** нарушения LSP.
- **можно** ли переписать иерархию так, чтобы LSP **соблюдался**? Через **разделение** интерфейсов? Через **композицию**? Через **изменение контракта** родителя?
- **стоит** ли это делать? (Если наследник **используется** только в одном месте и «работает» — может, и не стоит. Если это **публичный** API или **много** использований — скорее стоит.)

Затем ответьте на вопрос: **почему** LSP — это **не «всегда»**, а **«когда подставляют»**? Приведите пример, где нарушение LSP **допустимо** (например, `UnsupportedOperationException` в `Collections.unmodifiableList`).

Готового ответа не будет. Это ваша честная проверка на понимание: **видите** ли вы LSP в реальном коде, **считаете** ли «стоит ли переписывать», и **принимаете** ли осознанные решения.

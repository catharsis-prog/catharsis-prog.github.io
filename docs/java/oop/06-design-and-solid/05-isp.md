# 5. ISP: интерфейсы по потребностям

## Где вы это уже видели

В прошлом уроке мы разбирали LSP и в микрозадаче наткнулись на `ReadOnlyRepository`, который реализует «толстый» `Repository`, но вынужден бросать `UnsupportedOperationException` в `save` и `delete`. Тогда мы сказали: «разделите интерфейс». Пора объяснить, **почему** и **как** — и дать этому принципу имя. Оно есть: **Interface Segregation Principle**, или **ISP**.

Идея простая: **клиент не должен зависеть от интерфейса, который он не использует**. Если у вас есть интерфейс с десятью методами, а клиенту нужен **один**, — интерфейс **слишком толстый**. Лучше — **много маленьких** интерфейсов, каждый под свою задачу.

**Ситуация первая.** Вы покупаете универсальный пульт. На нём **пятьдесят** кнопок: включение, громкость, каналы, меню, субтитры, телетекст, запись, перемотка, стоп, пауза, выбор источника, настройки изображения, настройки звука... Вы дома пользуетесь **пятью**: включить, громче, тише, канал плюс, канал минус. Остальные сорок пять — **не нужны**. Вы **зависите** от пульта с пятьюдесятью кнопками, хотя вам нужен пульт с пятью. Это **толстый** интерфейс.

**Ситуация вторая.** Вы приходите в ресторан на завтрак. Вам приносят **меню на двадцать страниц**: завтраки, обеды, ужины, детское меню, вегетарианское, безглютеновое, барная карта, вина, десерты. Вы хотите **яичницу и кофе**. Вы **зависите** от меню на двадцать страниц, хотя вам нужна **одна** страница «завтраки». Это **толстое** меню.

**Ситуация третья.** Вы заполняете анкету при регистрации. В ней **тридцать** полей: имя, email, телефон, адрес, дата рождения, семейное положение, образование, опыт работы, хобби, любимый цвет, размер обуви... Из них **обязательных** — **пять**. Остальные двадцать пять — «на всякий случай». Вы **зависите** от анкеты с тридцатью полями, хотя вам нужны **пять**. Это **толстая** анкета.

**Ситуация четвёртая.** Вы подписываете договор аренды. В нём **сорок** пунктов: аренда, оплата, срок, ремонт, животные, шум, гости, парковка, вывоз мусора, страхование... Вам как арендатору **важны** пункты про срок, оплату и ремонт. Остальные тридцать семь — **не ваша** забота. Вы **зависите** от договора с сорока пунктами, хотя вам нужны **три**. Это **толстый** договор.

**Ситуация пятая.** Вы ищете работу. Видите вакансию: «Требуется разработчик со знанием Java, Spring, Hibernate, SQL, NoSQL, Docker, Kubernetes, AWS, Azure, GCP, React, Angular, Vue, Python, Go, Rust, машинного обучения, блокчейна, квантовых вычислений, умения летать». Из этого списка **в реальной работе** понадобится **пять** пунктов. Остальные — «для галочки». Вы **зависите** от вакансии с двадцатью требованиями, хотя реально нужно **пять**. Это **толстая** вакансия.

**Ситуация шестая.** Вы смотрите на код и видите:

```java
interface Worker {
    void work();
    void eat();
    void sleep();
    void takeVacation();
    void report();
    void attendMeeting();
    void fillTimesheet();
}

class Robot implements Worker {
    public void work() { /* ... */ }
    public void eat() { throw new UnsupportedOperationException(); }
    public void sleep() { throw new UnsupportedOperationException(); }
    public void takeVacation() { throw new UnsupportedOperationException(); }
    public void report() { /* ... */ }
    public void attendMeeting() { /* ... */ }
    public void fillTimesheet() { /* ... */ }
}
```

— и понимаете: робот **не ест**, **не спит**, **не берёт отпуск**, но **вынужден** реализовывать эти методы. Знакомо? Тогда этот урок для вас.

## Что такое ISP

**Interface Segregation Principle** (принцип разделения интерфейсов) — сформулирован **Робертом Мартином** в середине 1990-х, когда он консультировал **Xerox** по поводу их системы для принтеров.

**Формулировка:** **«Клиенты не должны зависеть от интерфейсов, которые они не используют».**

Или по-другому: **«Много маленьких интерфейсов лучше, чем один большой»**.

**Ключевая идея:** **интерфейс должен содержать только те методы, которые нужны клиенту**. Если у интерфейса есть методы, которые клиент **не использует**, — интерфейс **слишком толстый**, и его стоит **разделить**.

**Почему это важно.** Потому что **толстый интерфейс** заставляет реализации **врать**:

- если реализация **не может** выполнить метод — она **бросает** `UnsupportedOperationException` (это нарушение LSP, как мы видели в прошлом уроке);
- если реализация **не хочет** выполнять метод — она **делает пустоту** (это «тихий отказ», который **хуже** исключения);
- если реализация **выполняет**, но **бессмысленно** — это **обман** клиента.

**Мораль:** **толстый интерфейс** — это **плохой контракт**. Он обещает **больше**, чем могут выполнить реализации. И клиент, который **зависит** от него, — **вынужден** иметь дело с методами, которые **не работают**.

## История: Xerox и принтеры

История, из которой родился ISP, **показательна**. Расскажу её — она объясняет, **почему** принцип вообще появился.

Xerox разрабатывала систему управления **принтерами**. У них был **единый** интерфейс `Job`, который умел: `print`, `staple` (сшивать), `fax` (отправлять факс). Логика: «это же работа с документом, пусть всё будет в одном».

Проблема: **не все принтеры** умели **всё**. Один принтер **печатал**, но **не сшивал**. Другой **сшивал**, но **не отправлял факс**. Третий **отправлял факс**, но **не печатал**. И каждый раз, когда клиент работал с `Job`, — приходилось **проверять**, **какой** принтер за ним стоит, и **какие** методы **можно** вызывать.

Решение: **разделить** `Job` на **три** интерфейса: `Printer`, `Stapler`, `Fax`. Принтер реализует **только** `Printer`. Сшиватель — **только** `Stapler`. Многофункциональное устройство — **все три**. Клиент работает с **тем** интерфейсом, который ему нужен, и **не зависит** от методов, которых у него нет.

**Мораль.** **Один большой интерфейс** — это «универсальное устройство», которое **на самом деле** не универсально. **Много маленьких** — это «специализированные устройства», каждое из которых **делает своё** и **не обещает** лишнего.

## Толстые интерфейсы: примеры

Разберём несколько **типичных** случаев, где толстый интерфейс **создаёт проблемы**.

### Пример 1: `Worker` с `eat` и `work`

```java
interface Worker {
    void work();
    void eat();
    void sleep();
    void takeVacation();
}
```

**Проблема.** `Robot` **не ест**, `Human` **не может работать 24/7**, `Contractor` **не берёт отпуск** (он не сотрудник). Каждая реализация **вынуждена** либо бросать исключение, либо делать пустоту.

**Как разделить.**

```java
interface Workable {
    void work();
}

interface Feedable {
    void eat();
}

interface Restable {
    void sleep();
}

interface Vacationable {
    void takeVacation();
}

class Human implements Workable, Feedable, Restable, Vacationable {
    // реализует всё
}

class Robot implements Workable {
    // только work
}
```

Теперь `Robot` **не зависит** от `eat`, `sleep`, `takeVacation` — их **нет** в его контракте. Клиент, работающий с роботом, **не сможет** случайно вызвать `eat` — компилятор не даст.

**Что можно улучшить.** Некоторые интерфейсы можно **объединить**, если они **всегда** идут вместе. Например, `Feedable` и `Restable` — у людей **всегда** есть оба (человек и ест, и спит). Можно сделать `LivingCreature` с двумя методами:

```java
interface LivingCreature {
    void eat();
    void sleep();
}

class Human implements Workable, LivingCreature, Vacationable {
    // ...
}
```

Это **не** нарушает ISP: `LivingCreature` — **один** контракт «живое существо», и клиенту, которому нужно «живое существо», — нужны **оба** метода. ISP — **не «один метод на интерфейс»**, а «только те методы, которые нужны **клиенту**».

### Пример 2: `Connection` с `read`, `write`, `close`

```java
interface Connection {
    byte[] read();
    void write(byte[] data);
    void close();
    void beginTransaction();
    void commit();
    void rollback();
}
```

**Проблема.** `HttpConnection` **не поддерживает** транзакции. `FileConnection` **не поддерживает** транзакции. `DatabaseConnection` — **поддерживает**. `HttpConnection` **вынужден** бросать `UnsupportedOperationException` в `beginTransaction`/`commit`/`rollback`.

**Как разделить.**

```java
interface Readable {
    byte[] read();
}

interface Writable {
    void write(byte[] data);
}

interface Closeable {
    void close();
}

interface Transactional {
    void beginTransaction();
    void commit();
    void rollback();
}

interface Connection extends Readable, Writable, Closeable {
    // общий контракт соединения
}

interface DatabaseConnection extends Connection, Transactional {
    // соединение с транзакциями
}
```

Теперь `HttpConnection` реализует `Connection` (три метода). `DatabaseConnection` — `Connection` + `Transactional` (шесть). Клиент, работающий с `HttpConnection`, **не зависит** от транзакций.

**Что можно улучшить.** `Closeable` уже есть в Java (`java.io.Closeable`). Можно **использовать** его, а не создавать свой. Это **хорошая практика**: не дублировать стандартные интерфейсы.

### Пример 3: `ReportGenerator` с `generate`, `format`, `save`, `send`

```java
interface ReportGenerator {
    String generate(Report report);
    String formatAsHtml(String content);
    String formatAsPdf(String content);
    String formatAsCsv(String content);
    void saveToFile(String content, String path);
    void sendByEmail(String content, String to);
}
```

**Проблема.** Если клиенту нужно **только** «сгенерировать HTML», — он **зависит** от пяти методов, которые **не будет** использовать. И если `ReportGenerator` **реализуется** классом, которому нужно **только** `generate`, — он **вынужден** бросать `UnsupportedOperationException` в остальных.

**Как разделить.**

```java
interface ReportGenerator {
    String generate(Report report);
}

interface HtmlFormatter {
    String formatAsHtml(String content);
}

interface PdfFormatter {
    String formatAsPdf(String content);
}

interface CsvFormatter {
    String formatAsCsv(String content);
}

interface FileSaver {
    void saveToFile(String content, String path);
}

interface EmailSender {
    void sendByEmail(String content, String to);
}
```

Теперь клиент **выбирает**, от чего **зависеть**. Если нужно **только** «сгенерировать», — `ReportGenerator`. Если нужно **и** «сгенерировать», **и** «отформатировать» — `ReportGenerator` + `HtmlFormatter`.

**Что можно улучшить.** `HtmlFormatter`, `PdfFormatter`, `CsvFormatter` — это **похожие** интерфейсы. Можно **объединить** их в один `Formatter` с методом `format(content)`:

```java
interface Formatter {
    String format(String content);
}

class HtmlFormatter implements Formatter { /* ... */ }
class PdfFormatter implements Formatter { /* ... */ }
class CsvFormatter implements Formatter { /* ... */ }
```

Это **не нарушает** ISP: `Formatter` — **один** контракт «форматировать», и клиенту, которому нужно «форматировать», — нужен **один** метод. Конкретный формат — **реализация** (выбор через стратегию, модуль 4).

**Мораль ISP.** Разделяйте **по потребностям клиента**, а не по «количеству методов». Если у клиента одна потребность — один метод. Если несколько связанных — несколько методов в **одном** интерфейсе. Если несколько **несвязанных** — **разные** интерфейсы.

## ISP и LSP

В прошлом уроке мы разбирали LSP. ISP и LSP **связаны**: ISP **помогает** соблюдать LSP.

**Как именно.** LSP требует, чтобы **подкласс выполнял контракт родителя**. Если контракт **толстый** (много методов), — наследнику **сложнее** его выполнить: он **вынужден** реализовывать методы, которые **не имеют смысла**, — и **либо** бросает исключение (нарушение LSP), **либо** делает пустоту (тоже нарушение).

**ISP решает эту проблему**: разделяя интерфейс на **маленькие**, — вы даёте наследнику **выбирать**, какие контракты он **действительно** выполняет. `Robot` **реализует** `Workable` и **не реализует** `Feedable`. Он **не нарушает** контракт `Feedable`, потому что **не подписывался** под ним.

**Пример.** `ReadOnlyRepository` из прошлого урока. Если `Repository` **толстый** (findById, save, delete, findAll), — `ReadOnlyRepository` **вынужден** бросать `UnsupportedOperationException` в save/delete. Нарушение LSP.

Если `Repository` **разделён** на `ReadableRepository` (findById, findAll) и `WritableRepository` (save, delete), — `ReadOnlyRepository` **реализует** только `ReadableRepository` и **не нарушает** контракт (потому что не подписывался под `WritableRepository`). LSP **соблюдён**.

**Мораль.** **ISP — это «профилактика» LSP**. Разделяя интерфейсы, вы **уменьшаете** вероятность, что наследник **не сможет** выполнить контракт. И **увеличиваете** вероятность, что он **выполнит** те контракты, под которыми **действительно** подписался.

## ISP и SRP

ISP и SRP **тоже** связаны, но **по-другому**.

**SRP** — про **классы**: «одна причина для изменения».

**ISP** — про **интерфейсы**: «клиент не зависит от того, что не использует».

**Как они связаны.** Если класс **следует SRP** — у него **одна** ответственность. Если интерфейс **следует ISP** — у него **один** «набор потребностей клиента». Часто это **одно и то же**: класс с одной ответственностью **естественно** реализует интерфейс с одним «набором потребностей».

**Но не всегда.** Класс **может** реализовывать **несколько** интерфейсов (каждый — свой «набор потребностей»), и это **не нарушает** SRP. Например, `Human` реализует `Workable`, `Feedable`, `Restable`, `Vacationable` — **четыре** интерфейса, но **один** класс с **одной** ответственностью: «человек». Это **нормально**: класс **может** реализовывать **много** маленьких интерфейсов.

**Мораль.** ISP — **про клиентов**, SRP — **про классы**. Оба — про «не делай слишком много», но на **разных** уровнях.

## ISP в реальном коде

ISP используется **повсюду**. Несколько примеров.

**`java.util.Collection` и `java.util.List` и `java.util.Set`.** `Collection` — общий интерфейс (add, remove, size, contains). `List` — добавляет «доступ по индексу» (get, set, indexOf). `Set` — добавляет «множество» (без дубликатов). Клиент **выбирает**, что ему нужно. Если нужно **только** «перебрать», — `Iterable`. Если нужен **индекс**, — `List`. Если нужно **множество**, — `Set`.

**`java.io.InputStream` и `java.io.Reader`.** `InputStream` — для **байтов**. `Reader` — для **символов**. Клиент **выбирает**, что ему нужно. Не «один большой интерфейс» для всего.

**`java.sql.Connection` и `java.sql.Statement` и `java.sql.ResultSet`.** Connection — «соединение». Statement — «запрос». ResultSet — «результат». Клиент **выбирает**, что ему нужно. Не «один большой интерфейс» для всего.

**Spring `ApplicationContext`.** `ApplicationContext` — «толстый» интерфейс (много методов). Но он **разделён** на `BeanFactory`, `ListableBeanFactory`, `HierarchicalBeanFactory`, `ResourceLoader`, `ApplicationEventPublisher` и т. д. Клиент **выбирает**, что ему нужно. `ApplicationContext` — **композиция** всех этих интерфейсов.

**Servlet `HttpServletRequest`.** Он **толстый** (много методов: getParameter, getHeader, getSession, getCookies, getInputStream...). Но он **не разделён** — и это **критика** ISP в адрес Servlet API. Клиент, которому нужен **только** `getParameter`, — **зависит** от **всего** интерфейса.

**Мораль.** ISP **работает** в стандартных библиотеках, но **не всегда**. Иногда «толстый» интерфейс **оправдан** (например, `HttpServletRequest` — потому что «запрос» — это **единый** объект с **многими** свойствами). ISP — **эвристика**, а не **закон**.

## Когда ISP вредит

ISP — **эвристика**. Бывают случаи, когда **следовать ISP буквально** — **плохо**.

### Случай 1: слишком много интерфейсов

Если у вас **двадцать** интерфейсов по **одному** методу, и клиент **вынужден** реализовывать **все двадцать**, — это **хуже**, чем один «толстый» интерфейс. Клиент **запутается** в `import` и **не увидит** общей картины.

**Правило.** **ISP — не «один метод на интерфейс»**. Если методы **логически связаны** и **всегда** используются вместе, — **один** интерфейс **нормально**.

### Случай 2: `default`-методы

С появлением `default`-методов (модуль 4) **толстые** интерфейсы **стали менее** проблемными. Можно **добавить** метод с реализацией, и **никто** не сломается. Клиент, которому метод **не нужен**, — **не переопределяет** его.

**Пример.** `List` с `forEach` (default) — клиенты, которым `forEach` **не нужен**, — **не реализуют** его. Толстый интерфейс **стал терпимее**.

**Но.** `default`-методы **не отменяют** ISP. Если метод **не имеет смысла** для реализации, — она **вынуждена** либо **переопределить** (чтобы бросить исключение), либо **оставить** `default` (который может **делать не то**). Это **всё ещё** проблема.

### Случай 3: «толстый» интерфейс как фасад

Иногда «толстый» интерфейс — это **фасад** (модуль 5) над **подсистемой**. Он **намеренно** объединяет **много** методов, чтобы **упростить** работу клиента. `ApplicationContext` — **толстый**, но это **фасад**: клиенту **удобнее** работать с **одним** интерфейсом, чем с **десятью**.

**Мораль.** **ISP — для случаев, где клиенты разные**. Если клиент **один** (или их **мало** и у них **одни** потребности) — «толстый» интерфейс **нормально**.

### Случай 4: overengineering

«Сделать **пять** интерфейсов на **два** метода» — **overengineering**. Если у вас **два** метода, которые **всегда** используются вместе, — **не надо** их разделять. Это **усложнит** код, а не **упростит**.

**Правило.** **ISP — реакция на реальную потребность**, а не «на всякий случай». Если клиенту **нужны** все методы — «толстый» интерфейс **нормально**.

### Случай 5: производительность

Иногда «толстый» интерфейс **проще** с точки зрения **производительности**: меньше **виртуальных** вызовов, меньше **объектов**. Если это **критично** — «толстый» интерфейс **оправдан**.

**Мораль.** **ISP — не «единственный» критерий**. Если «толстый» интерфейс **быстрее** и **проще** — используйте его.

## Аналогия, которая помогает

Хорошая аналогия — **швейцарский нож vs набор инструментов**.

**Швейцарский нож** — это «толстый» интерфейс. У него **двадцать** инструментов: нож, ножницы, штопор, открывашка, пила, отвёртка, шило, зубочистка, пинцет... Вы **пользуетесь** **двумя-тремя** (нож, штопор, открывашка). Остальные **семнадцать** — «на всякий случай». И если один инструмент **сломается** — вы **не можете** его заменить: нож **один**, и он **встроен** в корпус.

**Набор инструментов** — это «много маленьких интерфейсов». У вас **отдельно** нож, **отдельно** штопор, **отдельно** открывашка. Вы **берёте** только то, что **нужно**. Если нож **сломался** — вы **меняете** нож, а не весь набор. Если нужен **новый** инструмент — **докупаете** его **отдельно**.

**ISP** — это «набор инструментов». Вы **не зависите** от двадцати инструментов, которые **не используете**. Вы **берёте** тот, который **нужен**.

**Но.** Швейцарский нож **удобнее** в походе: **один** предмет, **всё** под рукой. Если вы **точно знаете**, что вам нужны **все двадцать** инструментов, — швейцарский нож **лучше**. ISP **не «всегда»**, а **«когда клиенты разные»**.

**И ещё.** В **наборе инструментов** каждый **инструмент** — **свой** контракт. Нож **обещает** «резать». Штопор — «открывать вино». Открывашка — «открывать банки». Клиент **выбирает** нужный. В **швейцарском ноже** — **один** контракт «делать всё», и клиент **вынужден** разбираться, **какой** инструмент **за что** отвечает.

**Мораль.** ISP — это «набор инструментов»: **много маленьких** интерфейсов, **каждый** — под свою задачу. Клиент **берёт** нужный. Но **если** клиенту **нужны все** — «швейцарский нож» (толстый интерфейс) **может** быть **удобнее**.

## Микрозадача 1

Вот интерфейс. Определите, **нарушается** ли ISP, и если да — как разделить.

```java
interface SmartDevice {
    void turnOn();
    void turnOff();
    void setVolume(int volume);
    void setChannel(int channel);
    void setBrightness(int brightness);
    void setTemperature(int temperature);
    void play(String media);
    void pause();
    void stop();
}
```

### Разбор

**ISP нарушен.** Интерфейс **объединяет** **разные** «навыки»:

- **включение/выключение** — общее для всех устройств;
- **громкость** и **каналы** — для **телевизора** (и, может быть, **колонок**);
- **яркость** — для **лампы** (и, может быть, **экрана**);
- **температура** — для **термостата** (и, может быть, **кондиционера**);
- **воспроизведение** — для **медиаплеера** (и, может быть, **телевизора**).

`Lamp` **не имеет** `setChannel` и `setVolume`. `Thermostat` **не имеет** `setBrightness` и `play`. Каждое устройство **вынуждено** реализовывать **все** методы — и **либо** бросать `UnsupportedOperationException`, **либо** делать пустоту.

**Как разделить.**

```java
interface Switchable {
    void turnOn();
    void turnOff();
}

interface VolumeControllable {
    void setVolume(int volume);
}

interface ChannelControllable {
    void setChannel(int channel);
}

interface BrightnessControllable {
    void setBrightness(int brightness);
}

interface TemperatureControllable {
    void setTemperature(int temperature);
}

interface MediaPlayer {
    void play(String media);
    void pause();
    void stop();
}
```

Теперь:

- `Lamp implements Switchable, BrightnessControllable` — **только** то, что нужно;
- `TV implements Switchable, VolumeControllable, ChannelControllable, MediaPlayer` — **всё** нужное;
- `Thermostat implements Switchable, TemperatureControllable` — **только** то, что нужно.

**Что можно улучшить.** `Switchable` **уже есть** в примере из теории (`Light`, `Thermostat`, `MusicSystem`, `CoffeeMachine` из модуля 5). Можно **использовать** его же. `ChannelControllable` можно **объединить** с `VolumeControllable` в `TVControllable` — если **все** устройства с каналами **имеют** и громкость (обычно так). Но это уже **решение по контексту**, а не **жёсткое** требование ISP.

**Мораль.** ISP — **не «один метод на интерфейс»**, а «только те методы, которые **нужны клиенту»**. Если **все** устройства с каналами **имеют** громкость — можно **объединить**. Если **некоторые** — **разделить**. Решение — **по контексту**.

## Микрозадача 2

Вот интерфейс. Определите, **нарушается** ли ISP, и если да — как разделить.

```java
interface UserRepository {
    User findById(long id);
    User findByEmail(String email);
    List<User> findAll();
    List<User> findByRole(Role role);
    void save(User user);
    void delete(long id);
    void update(User user);
}
```

### Разбор

**ISP нарушен.** Интерфейс **объединяет** **два** «набора потребностей»:

- **чтение** (`findById`, `findByEmail`, `findAll`, `findByRole`);
- **запись** (`save`, `delete`, `update`).

Клиент, которому нужно **только чтение** (например, `UserReportService`), — **зависит** от методов записи. Клиент, которому нужна **только запись** (например, `UserImportService`), — **зависит** от методов чтения.

**Как разделить.**

```java
interface ReadableUserRepository {
    User findById(long id);
    User findByEmail(String email);
    List<User> findAll();
    List<User> findByRole(Role role);
}

interface WritableUserRepository {
    void save(User user);
    void delete(long id);
    void update(User user);
}

interface UserRepository extends ReadableUserRepository, WritableUserRepository {
    // общий контракт — для тех, кому нужно всё
}
```

Теперь:

- `UserReportService` **зависит** от `ReadableUserRepository` — **только** чтение;
- `UserImportService` **зависит** от `WritableUserRepository` — **только** запись;
- `UserAdminService` **зависит** от `UserRepository` — **всё**.

**Что можно улучшить.** `ReadableUserRepository` **можно разделить** дальше: `findById` и `findAll` — **«базовое»** чтение; `findByEmail`, `findByRole` — **«поиск»**. Если клиенту нужен **только** `findById`, — он **не зависит** от поиска.

Но **стоит ли** — **зависит от контекста**. Если **все** клиенты используют **все** методы чтения — **не стоит** разделять. Если **некоторые** — **стоит**. ISP — **эвристика**, а не **жёсткое** правило.

**Мораль.** ISP **не «всегда»**, а «когда клиенты разные». `UserRepository` **избыточен** для `UserReportService`, но **достаточен** для `UserAdminService`. Разделение — **по потребностям** клиентов.

## Самостоятельная задача

Возьмите **любой** интерфейс из вашего проекта (или из открытого проекта на Java), у которого **больше пяти** методов.

Подумайте:

- **сколько** у него «наборов потребностей»? То есть **сколько** разных **типов клиентов** его используют, и **какие** методы **каждому** нужны?
- **все ли** реализации используют **все** методы? Или есть методы, которые **бросают** исключение, **делают пустоту** или **не имеют смысла** для какой-то реализации?
- **можно** ли разделить интерфейс на **два-три** маленьких, чтобы каждый «набор потребностей» был **отдельно**?
- **что** изменится в коде, который **использует** интерфейс? (Сколько `import` придётся добавить? Сколько `implements` изменить?)
- **стоит** ли это делать? (Если у интерфейса **один** клиент и он **использует** все методы — **не стоит**. Если **разные** клиенты и **разные** методы — **стоит**.)

Затем ответьте на вопрос: **почему** ISP — это **не «всегда»**, а **«когда клиенты разные»**? Приведите пример, где **толстый** интерфейс **оправдан** (например, `HttpServletRequest`, `ApplicationContext`).

Готового ответа не будет. Это ваша честная проверка на понимание: **видите** ли вы ISP в реальном коде, **считаете** ли «стоит ли разделять», и **принимаете** ли осознанные решения.

# 3. OCP: открыт для расширения, закрыт для изменения

## Где вы это уже видели

В прошлом уроке мы разобрались с SRP — «одна причина для изменения». Пора поговорить о втором принципе SOLID, который звучит как парадокс: **класс должен быть открыт для расширения, но закрыт для изменения**. Как это вообще возможно — быть «открытым» и «закрытым» одновременно?

Ответ прост: **открыт для расширения** — значит, что **новое поведение** можно добавить, не меняя существующий код. **Закрыт для изменения** — значит, что **существующий код** не нужно трогать при добавлении нового поведения. И это не противоречие, а конкретный приём, который мы уже не раз видели в предыдущих модулях. Просто теперь у него есть имя.

**Ситуация первая.** У вас есть система скидок. Сейчас их три: обычная, VIP, чёрная пятница. Завтра маркетинг хочет **четвёртую** — «студенческая». Вы открываете код и видите `if (тип == REGULAR) ... else if (тип == VIP) ... else if (тип == BLACK_FRIDAY)`. Чтобы добавить студенческую, — нужно **изменить** этот код. А это значит, что вы трогаете **работающий** код, который сейчас **проходит тесты**. Риск сломать что-то — **ненулевой**. Даже если вы просто добавите ещё одну ветку `else if`, — вы **изменили** класс, который до этого **работал**. Это и есть нарушение OCP.

**Ситуация вторая.** У вас есть система уведомлений. Сейчас — email и SMS. Завтра хотят push. Вы смотрите на код: `class Notifier { void send(String type, ...) { if (type.equals("email")) ... else if (type.equals("sms")) ... } }`. Чтобы добавить push, — **меняете** `Notifier`. Опять нарушение OCP.

**Ситуация третья.** У вас есть парсер файлов. Сейчас — CSV и JSON. Завтра — XML. Парсер — это `if (format == CSV) ... else if (format == JSON) ...`. Чтобы добавить XML, — **меняете** парсер. Нарушение OCP.

**Ситуация четвёртая.** У вас есть игра. Сейчас — три типа оружия: меч, лук, посох. Завтра — копьё. Класс `Weapon` с методом `attack()`, который использует `if (type == SWORD) ...`. Чтобы добавить копьё, — **меняете** `Weapon`. Нарушение OCP.

**Ситуация пятая.** Вы читаете книгу, там написано: «Класс должен быть открыт для расширения, но закрыт для изменения». Вы думаете: «Как это? Либо открыт, либо закрыт». И не понимаете, что имеется в виду. А имеется в виду **очень конкретная вещь**: новый код можно добавить **снаружи** класса, не трогая **внутри**.

**Ситуация шестая.** Вы смотрите на код и видите:

```java
class DiscountCalculator {
    double calculate(Order order) {
        if (order.getType() == REGULAR) return order.getTotal() * 0.05;
        if (order.getType() == VIP) return order.getTotal() * 0.15;
        if (order.getType() == BLACK_FRIDAY) return order.getTotal() * 0.5;
        throw new IllegalArgumentException("Неизвестный тип");
    }
}
```

— и понимаете: чтобы добавить четвёртый тип, — придётся **изменить** `calculate`. А можно ли сделать так, чтобы **новый тип** добавлялся **без изменения** `calculate`? Да. И это — OCP.

## Что такое OCP

**Open/Closed Principle** (принцип открытости/закрытости) — сформулирован **Бертраном Мейером** в 1988 году в книге «Object-Oriented Software Construction».

Формулировка: **«Программные сущности (классы, модули, функции) должны быть открыты для расширения, но закрыты для изменения».**

Что это значит:

- **Открыт для расширения** — можно добавить новое поведение. Не «когда-нибудь», а **легко**: без переписывания, без риска сломать существующее.
- **Закрыт для изменения** — существующий код **не трогается** при добавлении нового поведения. Ну, или трогается **минимально** (например, добавление строчки в конфигурацию).

**Ключевая идея:** **новое поведение — это добавление нового кода, а не изменение старого**. В идеале — **никаких** `if/else` по типу, **никаких** `switch` по типу. Просто новый класс — и всё работает.

**Почему это важно.** Потому что **изменение** работающего кода — это **риск**. Риск сломать то, что работало. Риск пропустить тест-кейс. Риск, что кто-то в другом месте рассчитывал на **старое** поведение. **Добавление** нового кода — тоже риск, но **меньший**: старый код **не тронут**, он **уже** работает, он **уже** протестирован.

**Мораль:** **OCP — это про минимизацию изменений**. Не «никогда не меняй код», а «сделай так, чтобы при добавлении нового поведения **старого** кода касались **как можно меньше**».

## Как это выглядит: до и после

Разберём на примере. Задача: система скидок.

**Без OCP:**

```java
enum CustomerType { REGULAR, VIP, BLACK_FRIDAY }

class DiscountCalculator {
    double calculate(Order order) {
        switch (order.getCustomerType()) {
            case REGULAR:      return order.getTotal() * 0.05;
            case VIP:          return order.getTotal() * 0.15;
            case BLACK_FRIDAY: return order.getTotal() * 0.50;
            default: throw new IllegalArgumentException("Неизвестный тип: " + order.getCustomerType());
        }
    }
}
```

**Что здесь плохо:**

- **При добавлении нового типа** (`STUDENT`) — нужно **изменить** `DiscountCalculator`. Добавить ещё один `case`. Изменение работающего кода.
- **При добавлении нового типа** — компилятор **не подскажет**, что что-то не так. `default` сработает только в runtime.
- **Тесты** для старых типов **не проверяют** новый тип. Если вы добавили `STUDENT` и ошиблись в формуле, — тесты не заметят (они тестируют `REGULAR`, `VIP`, `BLACK_FRIDAY`).

**С OCP:**

```java
interface DiscountStrategy {
    double apply(Order order);
}

class RegularDiscount implements DiscountStrategy {
    public double apply(Order order) { return order.getTotal() * 0.05; }
}

class VipDiscount implements DiscountStrategy {
    public double apply(Order order) { return order.getTotal() * 0.15; }
}

class BlackFridayDiscount implements DiscountStrategy {
    public double apply(Order order) { return order.getTotal() * 0.50; }
}

class DiscountCalculator {
    private final Map<CustomerType, DiscountStrategy> strategies;

    DiscountCalculator(Map<CustomerType, DiscountStrategy> strategies) {
        this.strategies = strategies;
    }

    double calculate(Order order) {
        DiscountStrategy strategy = strategies.get(order.getCustomerType());
        if (strategy == null) {
            throw new IllegalArgumentException("Нет скидки для типа: " + order.getCustomerType());
        }
        return strategy.apply(order);
    }
}
```

**Что изменилось:**

- **При добавлении нового типа** (`STUDENT`) — создаём **новый класс** `StudentDiscount`, регистрируем его в `Map` (в `main` или в конфигурации). `DiscountCalculator` **не меняется**.
- **`DiscountCalculator` закрыт для изменения** — его код не трогается при добавлении новых типов.
- **`DiscountCalculator` открыт для расширения** — новые типы добавляются через новые реализации `DiscountStrategy`.

**Это и есть OCP.** Класс `DiscountCalculator` **никогда** не меняется. Новые типы — **снаружи**. И `DiscountCalculator` **не знает**, какие типы существуют. Он просто берёт из `Map` и применяет.

## Механизмы OCP

OCP достигается **разными механизмами**. Мы уже видели их в предыдущих модулях. Перечислим основные.

### Полиморфизм и стратегия

**Самый частый механизм.** Интерфейс + реализации. `DiscountStrategy` + `RegularDiscount`, `VipDiscount`, `BlackFridayDiscount`. Контекст работает с интерфейсом, реализации добавляются снаружи.

**Это то, что мы видели в модуле 4** — паттерн «Стратегия». И это **прямое применение OCP**.

### Наследование с абстрактным методом

**Тоже работает.** Абстрактный класс `Shape` с абстрактным `area()`. Новые фигуры — `Circle`, `Rectangle`, `Triangle` — наследуются и реализуют `area()`. `Shape.area()` **не меняется** при добавлении фигуры.

**Но.** Наследование **жёстче**: наследник фиксируется при компиляции. И «is-a» должно выполняться (модуль 3). Поэтому **стратегия** (интерфейс + композиция) часто **гибче**, чем наследование.

### Композиция

**Стратегия — это частный случай композиции.** Класс `DiscountCalculator` **содержит** `Map<CustomerType, DiscountStrategy>` и **делегирует** ему работу. Новые типы — **новые элементы** в `Map`.

**Мы это видели в модуле 5.** Композиция — **естественный** механизм OCP.

### Фабрики

**Иногда** для OCP нужна **фабрика** — класс, который создаёт объекты по какому-то ключу. Фабрика **скрывает** конкретные классы и позволяет добавлять новые через **регистрацию**.

**Пример.** `DiscountCalculatorFactory` с методом `create(CustomerType)` возвращает нужную стратегию. Внутри — `Map` или `switch` (да, `switch`, но **один раз**, в **одном** месте). Добавление нового типа — добавление в фабрику, **одно место**.

**Фабрика — не «серебряная пуля».** Если у вас **есть** DI (модуль 5), — фабрика часто **не нужна**: `Map` в `main` — то же самое, но проще.

## OCP в реальном коде

OCP используется **повсюду**. Несколько примеров.

**`Comparator` в Java.** `list.sort(comparator)` — это OCP. `sort` **не меняется** при добавлении новых способов сортировки. Новый способ — **новый** `Comparator`.

**`Runnable`, `Callable`.** `ExecutorService.submit(runnable)` — OCP. `submit` **не меняется**. Новые задачи — **новые** `Runnable`.

**`Iterator`.** `for (Item i : collection)` — OCP. `for` **не меняется**. Новые коллекции — **новые** `Iterator`.

**`Strategy` в Spring.** `@Autowired List<MyStrategy>` — Spring **сам** собирает все реализации. Добавление новой — **одна** аннотация, и она **в списке**. `MyService` **не меняется**.

**`Plugin`-архитектуры.** Плагины — **новые** модули, которые **не меняют** ядро. Ядро **знает** только интерфейс плагина. Плагин — **снаружи**.

**`Filter` в Servlet API.** `Filter` — интерфейс. `FilterChain` — цепочка. Добавление нового фильтра — **новый** класс, **регистрация** в `web.xml` или в аннотации. `FilterChain` **не меняется**.

**`Interceptor` в Spring MVC.** `HandlerInterceptor` — интерфейс. Добавление нового — **новый** класс. `DispatcherServlet` **не меняется**.

**`Handler` в Netty.** `ChannelHandler` — интерфейс. Добавление нового — **новый** класс. `Pipeline` **не меняется**.

Во всех примерах — **одна идея**: **новое поведение — новый класс**, а не изменение существующего.

## OCP и SRP

Два принципа **связаны**. SRP говорит: «одна причина для изменения». OCP говорит: «при добавлении нового поведения — существующий код не меняется».

**Как они связаны.** Если класс **следует SRP** — у него **одна** причина для изменения. Если вы добавляете **новое поведение** — это **новая** причина. Значит, **нарушение SRP** часто ведёт к **нарушению OCP**: класс «делает несколько вещей», и добавление новой — **меняет** его.

**Обратное тоже верно.** Если класс **следует OCP** — он **не меняется** при расширениях. Значит, **причина** для изменения — только **одна** (например, «изменилось внутреннее представление»). Это **помогает** SRP.

**Пример.** `DiscountCalculator` **следует SRP** (одна ответственность: «применять скидку»). И **следует OCP** (новые скидки — новые классы). **Оба** выполняются, потому что класс **маленький** и **делает одно**.

**Пример.** `DiscountCalculator` **с if/else** — **нарушает OCP** (нужно менять при добавлении). И **нарушает SRP** (причины для изменения: «изменилась формула обычной скидки», «изменилась формула VIP», ..., **пять** причин). **Оба** нарушены, потому что класс **делает много** (пять формул).

**Мораль.** SRP и OCP — **два взгляда** на **одну проблему**. SRP смотрит **внутрь** («сколько причин для изменения?»). OCP смотрит **наружу** («сколько кода нужно тронуть при расширении?»). Часто они **согласованы**.

## Когда OCP вредит

OCP — **эвристика**, не «закон». Бывают случаи, когда **следовать OCP буквально** — плохо.

### Случай 1: два варианта, которые не изменятся

Если у вас **два** варианта поведения, и **точно** известно, что **третьего** не будет, — `if/else` **проще** и **понятнее**, чем стратегия.

**Пример.** `boolean isAdult(int age) { return age >= 18; }` — **не надо** делать `interface AgeValidator` с реализациями. Два варианта («взрослый» / «не взрослый») — `if` **нормально**.

**Пример.** `if (user.isAdmin()) ... else ...` — **не надо** делать `interface PermissionStrategy`. Два варианта — `if` **нормально**.

**Правило:** **OCP для случаев, где расширение — реально**. Если «расширений» **не будет** — `if` **лучше**.

### Случай 2: расширение — «внутри», а не «снаружи»

Иногда **новое поведение** — это **внутреннее** изменение (например, «формула скидки стала другой»). Не «новый тип», а «новые правила для того же типа». Это **изменение**, а не **расширение**.

**Пример.** Была скидка 5%, стала 7%. Это **не** «новый тип», это **изменение** существующего. OCP **не применяется** — вы **меняете** `RegularDiscount`.

**Мораль:** **OCP для добавления нового**, а не для **изменения** старого. Старое **должно** меняться, если **требования** изменились. OCP **не** защищает от этого.

### Случай 3: расширение редко

Если «новый тип» добавляется **раз в год** — **стоит ли** делать стратегию? Может, `if/else` **проще**: одна строка, **изменить** раз в год — не проблема.

**Пример.** У вас три **фиксированных** тарифа на подписку, и «новых» **не будет** (это решено на уровне бизнеса). `if/else` — **нормально**.

**Мораль:** **OCP для случаев, где расширение — часто**. Если раз в год — `if/else` **достаточно**.

### Случай 4: overengineering

«Сделать стратегию **на всякий случай**» — **плохо**. Если у вас **один** тип сейчас, и «неизвестно, будет ли второй», — **не надо** делать `interface` + **одну** реализацию + `Map` + регистрацию. Это **overengineering**, о котором мы говорили в модуле 5.

**Правило:** **OCP — реакция на реальное расширение**, а не «на всякий случай».

### Случай 5: слишком много абстракций

Если у вас **десять** интерфейсов, **каждый** с **одной** реализацией, и **все** «на всякий случай» — вы **усложнили** код, а не **упростили**. Каждый интерфейс — **дополнительный** уровень абстракции, **дополнительный** файл, **дополнительная** точка изменения.

**Мораль:** **абстракция — это цена**. Применяйте **только** там, где расширение **действительно** нужно.

## Аналогия, которая помогает

Хорошая аналогия — **розетки и вилки** (мы её уже использовали в модуле 5, но она **идеально** подходит к OCP).

**Розетка** — это «закрыта для изменения». Её **конструкция** не меняется. Она **одна** и та же.

**Вилки** — это «открыто для расширения». Вы можете **добавить** новую вилку (утюг, лампа, компьютер) — **не меняя** розетку.

**OCP** — это **розетка**. Она **закрыта** (не меняется при добавлении новых приборов) и **открыта** (любой прибор с вилкой может быть подключён).

**Что было бы без OCP.** У каждого прибора — **своя** розетка. Утюг — с одной, лампа — с другой. Замена утюга — замена розетки. **Кошмар**.

**Что было бы, если OCP «слишком».** У вас **десять** розеток «на всякий случай», хотя приборов — **два**. Или **сто** типов розеток, хотя приборов — **три**. **Overengineering**.

**Идеал.** Одна **стандартная** розетка, много **стандартных** вилок. OCP **работает**, когда **абстракция** («вилка») **стабильна**, а **реализации** («приборы») — **добавляются**.

**И ещё.** Розетка **не знает**, **что** в неё включено. Она **просто проводит** электричество. Так же и `DiscountCalculator` **не знает**, какие стратегии есть. Он **просто применяет** ту, что в `Map`.

## Микрозадача 1

Вот класс. Определите, **соблюдается** ли в нём OCP, и если нет — перепишите так, чтобы соблюдался.

```java
enum ShapeType { CIRCLE, RECTANGLE, TRIANGLE }

class AreaCalculator {
    double calculate(Shape shape) {
        switch (shape.getType()) {
            case CIRCLE:
                return Math.PI * shape.getRadius() * shape.getRadius();
            case RECTANGLE:
                return shape.getWidth() * shape.getHeight();
            case TRIANGLE:
                double p = (shape.getA() + shape.getB() + shape.getC()) / 2;
                return Math.sqrt(p * (p - shape.getA()) * (p - shape.getB()) * (p - shape.getC()));
            default:
                throw new IllegalArgumentException("Неизвестная фигура");
        }
    }
}
```

### Разбор

**OCP нарушается.** При добавлении нового типа фигуры (например, `SQUARE` или `ELLIPSE`) — придётся **менять** `AreaCalculator`. Добавлять `case`. Это изменение работающего кода.

**Как переписать с OCP:**

```java
interface Shape {
    double area();
}

class Circle implements Shape {
    private final double radius;

    Circle(double radius) { this.radius = radius; }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}

class Rectangle implements Shape {
    private final double width;
    private final double height;

    Rectangle(double width, double height) {
        this.width = width;
        this.height = height;
    }

    @Override
    public double area() {
        return width * height;
    }
}

class Triangle implements Shape {
    private final double a, b, c;

    Triangle(double a, double b, double c) {
        this.a = a; this.b = b; this.c = c;
    }

    @Override
    public double area() {
        double p = (a + b + c) / 2;
        return Math.sqrt(p * (p - a) * (p - b) * (p - c));
    }
}
```

**Что изменилось:**

- **`AreaCalculator` исчез.** Каждая фигура **сама** знает свою площадь. `shape.area()` — полиморфизм (модуль 4).
- **При добавлении новой фигуры** — новый класс, реализующий `Shape`. `Shape` (и все существующие фигуры) **не меняются**.
- **OCP соблюдается.** Новое поведение — **новый класс**, а не **изменение** `AreaCalculator`.

**Что мы получили:**

- **Расширяемость.** Новая фигура — новый класс. Никаких `switch`.
- **Закрытость.** `Shape` (и `Circle`, `Rectangle`, `Triangle`) **не меняются** при добавлении `Square`.
- **Читаемость.** Каждый класс — свой `area()`. Не нужно смотреть на «общий» `AreaCalculator` со `switch`.

**Что потеряли:**

- **`AreaCalculator` как «единая точка»** для площади. Раньше был один класс, теперь — метод в каждом. Но это **не потеря**: каждая фигура **сама** знает свою площадь, и это **правильно** (SRP).
- **Возможность «внешней» логики** площади. Если вы **не хотите**, чтобы фигура знала свою площадь (например, «площадь вычисляется внешним сервисом»), — `AreaCalculator` **уместен**. Но это **редкий** случай.

**Мораль.** OCP **достигается** через полиморфизм. `switch` по типу — **нарушение** OCP. `interface` + реализации — **соблюдение**.

## Микрозадача 2

Вот два класса. Определите, в каком из них **соблюдается** OCP, а в каком — **нет**.

**Класс A:**

```java
class ReportGenerator {
    void generate(Report report, String format) {
        if (format.equals("pdf")) {
            // ... генерация PDF
        } else if (format.equals("html")) {
            // ... генерация HTML
        } else if (format.equals("csv")) {
            // ... генерация CSV
        } else {
            throw new IllegalArgumentException("Неизвестный формат: " + format);
        }
    }
}
```

**Класс B:**

```java
interface ReportFormatter {
    String format(Report report);
}

class PdfFormatter implements ReportFormatter {
    public String format(Report report) { /* ... */ return ""; }
}

class HtmlFormatter implements ReportFormatter {
    public String format(Report report) { /* ... */ return ""; }
}

class CsvFormatter implements ReportFormatter {
    public String format(Report report) { /* ... */ return ""; }
}

class ReportGenerator {
    private final Map<String, ReportFormatter> formatters;

    ReportGenerator(Map<String, ReportFormatter> formatters) {
        this.formatters = formatters;
    }

    String generate(Report report, String format) {
        ReportFormatter formatter = formatters.get(format);
        if (formatter == null) {
            throw new IllegalArgumentException("Неизвестный формат: " + format);
        }
        return formatter.format(report);
    }
}
```

### Разбор

**Класс A (`ReportGenerator` с `if/else`)** — **нарушает OCP**. При добавлении нового формата (например, `XML` или `Markdown`) — придётся **менять** `generate`. Добавлять `else if`. Это изменение работающего кода.

**Класс B (`ReportGenerator` с `Map`)** — **соблюдает OCP**. При добавлении нового формата — **новый класс** `XmlFormatter`, **регистрация** в `Map`. `generate` **не меняется**.

**Что мы получили в классе B:**

- **Расширяемость.** Новый формат — новый класс + одна строчка в `main` (регистрация). `ReportGenerator` **не меняется**.
- **Закрытость.** `generate` **никогда** не меняется.
- **Читаемость.** Каждый формат — свой класс. Не нужно читать «общий» `if/else` с десятью ветками.

**Что потеряли:**

- **`ReportGenerator` знает о `Map`.** Раньше он **сам** знал о `pdf`/`html`/`csv`. Теперь — **не знает**, но **зависит** от `Map`. Это **нормально**: `Map` — это **конфигурация**, а не «знание о конкретных форматах».
- **Нужна регистрация в `main`.** Раньше `ReportGenerator` **сам** «знал» все форматы. Теперь — **кто-то** должен их зарегистрировать. Это **одна строчка** в `main` на каждый формат. **Приемлемо**.

**Что можно улучшить.** `ReportGenerator` **принимает** `Map` через конструктор (DI из модуля 5). В тестах можно подставить **заглушку** `FakeFormatter`. Хорошо.

**Мораль.** OCP — это **`Map` + интерфейс + DI**. Всё, что мы прошли в модулях 4 и 5, **собирается** в OCP.

## Самостоятельная задача

Возьмите **любой** класс из вашего проекта (или из открытого проекта на Java), который использует `if/else` или `switch` **по типу**.

Подумайте:

- **нарушает** ли он OCP? (Подсказка: если при добавлении нового типа придётся **менять** этот класс — да.)
- **как часто** добавляются новые типы? (Раз в месяц? Раз в год? Никогда?)
- **стоит** ли переписывать по OCP? (Если «никогда» — может, `if/else` **достаточно**. Если «часто» — **стоит**.)
- **если стоит** — как бы вы переписали? Интерфейс + реализации + `Map`? Или `interface` + `switch` в **одном** месте (фабрика)?
- **что** вы потеряете при переписывании? (Меньше кода — **больше файлов**. `if/else` — **проще** читать. `interface` + `Map` — **проще** расширять, но **сложнее** понять «что где».)
- **что** вы получите? (При добавлении нового типа — **только** новый класс. Не нужно трогать старое. Меньше риска.)

Затем ответьте на вопрос: **почему** OCP — это **не «всегда»**, а **«когда расширение реально»**? Приведите пример, где `if/else` **лучше**, чем `interface` + `Map`.

Готового ответа не будет. Это ваша честная проверка на понимание: **видите** ли вы OCP в реальном коде, **считаете** ли «стоит ли переписывать», и **принимаете** ли осознанные решения.

Если нет (например, «типов ровно два, и третьего не будет») — `if/else` **достаточно**. Просто найдите. Не переделывайте (пока).

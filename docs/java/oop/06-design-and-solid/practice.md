# Практикум — Проектирование и SOLID

## Как это работает

Здесь семь задач. Первые три — на диагностику: находить нарушения SRP, OCP, LSP в готовом коде и объяснять, почему это нарушения. Следующие три — на рефакторинг: переписать код так, чтобы принципы соблюдались. Последняя — проектное задание: спроектировать платёжный сервис с нуля.

Решения лежат на [отдельной странице](./practice-solutions). Сначала попробуйте сами, потом сверяйтесь. В SOLID особенно много «зависит от контекста»: иногда нарушение оправдано, иногда нет. Я показываю один из разумных вариантов и объясняю, почему он устроен именно так. Если ваше решение отличается, но работает и обосновано — оно тоже правильное.

Код пишите в файлах `.java`, запускайте. Особенно полезно **ломать** свои решения: добавьте новый тип в иерархию и посмотрите, сколько файлов придётся тронуть. Если много — возможно, OCP не хватает. Попробуйте подставить «неправильную» реализацию туда, где ожидается родитель — если ломается, LSP нарушен.

## Задача 1. Диагностика SRP

Вот класс. Определите, сколько у него причин для изменения, и обоснуйте, нарушает ли он SRP.

```java
class OrderManager {
    private final List<Order> orders = new ArrayList<>();

    void addOrder(Order order) {
        orders.add(order);
    }

    Order findById(String id) {
        return orders.stream().filter(o -> o.getId().equals(id)).findFirst().orElse(null);
    }

    double calculateTotal(Order order) {
        return order.getItems().stream().mapToDouble(Item::getPrice).sum();
    }

    void applyDiscount(Order order, double percent) {
        // ... применяет скидку к заказу ...
    }

    void saveToDatabase() {
        // ... сохраняет все заказы в БД ...
    }

    String toJson(Order order) {
        return "{\"id\":\"" + order.getId() + "\"}";
    }

    void sendConfirmationEmail(Order order) {
        // ... отправляет email клиенту ...
    }
}
```

Подумайте: какие из этих методов относятся к «модели заказа», какие — к «хранению», какие — к «форматированию», какие — к «уведомлениям»? Сколько разных «акторов» потребуют изменений в этом классе?

**Что проверяется:** умеете ли вы находить причины для изменения и связывать их с акторами.

## Задача 2. Диагностика OCP

Вот код. Определите, что здесь нарушает OCP, и объясните, почему.

```java
class FileExporter {
    void export(Report report, String format) {
        if (format.equals("csv")) {
            // ... запись CSV ...
        } else if (format.equals("pdf")) {
            // ... запись PDF ...
        } else if (format.equals("html")) {
            // ... запись HTML ...
        } else if (format.equals("xlsx")) {
            // ... запись XLSX ...
        } else {
            throw new IllegalArgumentException("Неизвестный формат: " + format);
        }
    }
}
```

Ответьте на вопросы:

- сколько файлов придётся изменить, чтобы добавить формат `xml`?
- сколько файлов придётся изменить, чтобы добавить формат `markdown`?
- что произойдёт, если кто-то забудет обновить `FileExporter` при добавлении нового формата в другом месте?
- какое **минимальное** изменение сделает класс открытым для расширения?

**Что проверяется:** понимаете ли вы, что OCP — это про «новое поведение через новый код», а не про «переписать старый код».

## Задача 3. Диагностика LSP

Вот иерархия. Определите, нарушается ли LSP, и если да — как переписать, чтобы не нарушался.

```java
class Account {
    protected double balance;

    void deposit(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Сумма должна быть положительной");
        balance += amount;
    }

    void withdraw(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Сумма должна быть положительной");
        if (amount > balance) throw new IllegalStateException("Недостаточно средств");
        balance -= amount;
    }

    double getBalance() {
        return balance;
    }
}

class SavingsAccount extends Account {
    private static final double MIN_BALANCE = 1000;

    @Override
    void withdraw(double amount) {
        if (amount <= 0) throw new IllegalArgumentException("Сумма должна быть положительной");
        if (balance - amount < MIN_BALANCE) {
            throw new IllegalStateException("Нельзя опустить баланс ниже " + MIN_BALANCE);
        }
        balance -= amount;
    }
}
```

Подумайте:

- что обещает `Account.withdraw`? Может ли клиент `Account` ожидать, что `withdraw` сработает, если `amount <= balance`?
- выполняет ли `SavingsAccount.withdraw` это обещание? В каких случаях — нет?
- нарушает ли `SavingsAccount` принцип подстановки? Почему?
- как переписать иерархию, чтобы LSP соблюдался?

**Что проверяется:** понимаете ли вы, что LSP — про контракт, а не про формальное наследование.

## Задача 4. Рефакторинг SRP и ISP

Вот интерфейс и класс, который его реализует.

```java
interface UserOperations {
    User findById(long id);
    User findByEmail(String email);
    List<User> findAll();
    void save(User user);
    void delete(long id);
    void update(User user);
    void sendWelcomeEmail(User user);
    void sendPasswordResetEmail(User user, String token);
    void exportToCsv(List<User> users, String path);
}
```

Класс `UserService` реализует все методы. Некоторые методы ему «не идут»: `exportToCsv` — это про экспорт, `sendWelcomeEmail` — про email. Клиенты, которым нужен только `findById`, зависят от всех десяти методов.

Разделите интерфейс на несколько маленьких, следуя SRP и ISP. Перепишите `UserService` так, чтобы он реализовывал только те интерфейсы, которые имеют смысл. Остальные методы вынесите в отдельные классы.

В `main` покажите, как клиент, которому нужен только `findById`, зависит только от `ReadableUserRepository` (или как вы назовёте), а не от всего.

Подумайте:

- сколько интерфейсов получилось?
- какие методы в каком интерфейсе?
- какие методы стоит вынести в **отдельные классы**, а не в интерфейсы `UserService`?
- что делать, если клиенту нужен и `findById`, и `save` одновременно? (Подсказка: он может зависеть от двух интерфейсов сразу.)

**Что проверяется:** понимаете ли вы, как разделять «толстые» интерфейсы и почему.

## Задача 5. Рефакторинг OCP и DIP

Вот код, который нарушает и OCP, и DIP одновременно.

```java
class NotificationService {
    void send(String type, String to, String message) {
        if (type.equals("email")) {
            SmtpClient smtp = new SmtpClient("smtp.example.com");
            smtp.send(to, message);
        } else if (type.equals("sms")) {
            SmsGateway gateway = new SmsGateway("api-key");
            gateway.sendSms(to, message);
        } else if (type.equals("push")) {
            FirebaseClient firebase = new FirebaseClient();
            firebase.push(to, message);
        } else {
            throw new IllegalArgumentException("Неизвестный тип: " + type);
        }
    }
}
```

Перепишите так, чтобы:

- не было `if/else` по типу (OCP);
- не было `new` внутри метода (DIP);
- добавление нового канала требовало **только** нового класса и одной строчки в `main`.

Подумайте:

- какой интерфейс вы вводите?
- сколько реализаций?
- как `NotificationService` выбирает нужную реализацию — через поле, через `Map`, через что-то ещё?
- что выиграли, что потеряли?
- что произойдёт, если в `main` зарегистрированы не все реализации — как клиент об этом узнает?

**Что проверяется:** понимаете ли вы, как OCP и DIP работают вместе.

## Задача 6. Рефакторинг LSP

Вернитесь к задаче 3 с `Account` и `SavingsAccount`. Перепишите иерархию так, чтобы LSP соблюдался.

Подумайте:

- должно ли `SavingsAccount` вообще наследоваться от `Account`?
- если да — что нужно изменить в контракте `Account` (или `SavingsAccount`), чтобы LSP соблюдался?
- если нет — как связать `SavingsAccount` и `Account` через интерфейс или композицию?
- нужно ли добавить в `Account` метод, которого сейчас нет? Например, `canWithdraw(double amount)` или `getMinimumBalance()`?
- что произойдёт, если завтра появится `PremiumAccount` с овердрафтом (баланс может быть отрицательным)? Как это выразить в новой иерархии?

Напишите тест, который доказывает, что LSP **соблюдается** (или, если не соблюдается, — что нарушается).

**Что проверяется:** понимаете ли вы, как исправлять нарушения LSP и как проверять, что исправление работает.

## Задача 7. Проект — Платёжный сервис

Это большое задание. Его можно решать несколько вечеров. Здесь нужно применить **всё**, что мы прошли в модуле: и SRP, и OCP, и LSP, и ISP, и DIP, и всё, что было в предыдущих модулях — инкапсуляцию, полиморфизм, композицию, DI.

Спроектируйте платёжный сервис интернет-магазина с нуля.

### Требования

**Поддерживаемые способы оплаты:**

- карта (комиссия 2%);
- СБП (комиссия 0.5%);
- ЮMoney (комиссия 1%);
- криптовалюта (комиссия 5%, лимит на одну транзакцию — 100 000);
- бонусные баллы (комиссия 0%, лимит — 5000 баллов на одну транзакцию).

**Жизненный цикл платежа:**

1. Создать платёж (зафиксировать сумму, способ оплаты, заказ).
2. Проверить допустимость (лимиты, доступность способа).
3. Провести оплату.
4. Зафиксировать результат (успех или ошибка).
5. Отправить уведомление клиенту (email) — при успехе или при ошибке.

**Дополнительные требования:**

- Возможность **повторной попытки**: если платёж не прошёл, — можно попробовать ещё раз, но не больше трёх раз.
- Возможность **возврата** (refund) — но **не для всех** способов оплаты: для бонусов возврат невозможен.
- **Логирование** всех попыток (успешных и неуспешных) — в файл или консоль. Способ логирования должен быть заменяемым.
- Все денежные суммы — через класс `Money` (из урока 7), не через `double`.

### Что спроектировать

Разбейте систему на классы. Минимум — следующие:

- `PaymentMethod` — интерфейс или абстрактный класс для способов оплаты;
- конкретные реализации (`CardPayment`, `SbpPayment`, `YooMoneyPayment`, `CryptoPayment`, `BonusPayment`);
- `Payment` — модель платежа (заказ, сумма, способ, статус, попытки);
- `PaymentService` — сервис, который проводит платёж;
- `NotificationSender` — интерфейс для уведомлений;
- `Logger` — интерфейс для логирования;
- `Refundable` — интерфейс или отдельный сервис для возврата (только для тех способов, где он возможен).

Подумайте, где применить каждый принцип:

- **SRP:** какие классы имеют одну причину для изменения? Где вы провели границы?
- **OCP:** что произойдёт при добавлении нового способа оплаты (например, `SberPay`)? Сколько файлов придётся изменить?
- **LSP:** все ли реализации `PaymentMethod` ведут себя одинаково? Если есть `BonusPayment`, который «не поддерживает возврат», — не нарушает ли это LSP? Как избежать нарушения?
- **ISP:** какие интерфейсы получились? Не «толстые» ли они? Если `PaymentMethod` имеет метод `refund`, а бонусы его не поддерживают — это нарушение ISP (и LSP). Как разделить?
- **DIP:** от чего зависит `PaymentService`? От абстракций или от реализаций?

### Сценарий проверки

Напишите `main`, который:

1. Собирает `PaymentService` с картой, СБП, криптой и бонусами.
2. Проводит успешный платёж картой на 1000.
3. Проводит успешный платёж СБП на 5000.
4. Пытается провести платёж криптой на 150 000 — получает ошибку «превышен лимит».
5. Пытается провести платёж бонусами на 10 000 — получает ошибку «превышен лимит бонусов».
6. Проводит повторную попытку для неуспешного платежа — тоже неуспешно, но количество попыток увеличилось.
7. Пытается сделать возврат для успешного платежа картой — успех.
8. Пытается сделать возврат для успешного платежа бонусами — узнаёт, что возврат невозможен.
9. Проверяет, что в логе есть записи обо всех попытках.

### Дополнительные вопросы

1. Если бы завтра понадобилось отправлять уведомления не только по email, но и по SMS, — сколько файлов придётся изменить?
2. Если бы понадобилось ограничить количество попыток **по-разному** для разных способов оплаты (например, для карты — 3, для крипты — 1), — где бы вы это выразили?
3. Если бы понадобилось логировать не только попытки, но и **все** операции с платежом (создание, проверка, оплата, возврат), — как бы вы это сделали, не меняя `PaymentService`? (Подсказка: декоратор или аспект.)
4. Если бы понадобилось добавить **частичный возврат** (например, вернуть 500 из 1000), — как бы вы расширили интерфейс `Refundable`?
5. Что произойдёт, если в `main` зарегистрировать **два** способа оплаты с одинаковым именем (например, две реализации `CardPayment`)? Как это обработать?

**Что проверяется:** всё сразу. Умение проектировать систему с нуля, применять все принципы осознанно, обосновывать каждое решение и расширять систему без боли.

# 2. SRP: одна причина для изменения

## Где вы это уже видели

В прошлом уроке мы говорили, зачем нужны принципы, и упомянули, что SRP — это не «класс должен делать что-то одно», а «у класса должна быть одна причина для изменения». Пора разобраться, что это значит на практике. Потому что формулировка «одно» — самая коварная из всех принципов SOLID: она выглядит простой, но за ней стоит целая философия.

**Ситуация первая.** Вы приходите на ревью, и коллега говорит: «Этот класс нарушает SRP». Вы смотрите: класс `UserService` с методами `register`, `login`, `logout`, `updateProfile`, `changePassword`, `sendWelcomeEmail`. Вроде бы «всё про пользователя» — одна ответственность? Или шесть? Где граница?

**Ситуация вторая.** Вы читаете книгу, там написано: «Класс должен делать **одно**». Вы пишете класс `Point` с полями `x` и `y`. Он «делает два» — хранит `x` и хранит `y`? Или «делает одно» — представляет точку? Ответа в книге нет, и вы закрываете её с раздражением.

**Ситуация третья.** У вас есть класс `Report` с методами `generateContent`, `formatAsHtml`, `formatAsPdf`, `saveToFile`, `sendByEmail`. Пять методов — пять ответственностей? Или один «отчёт»? И как **отличить** одно от другого?

**Ситуация четвёртая.** Вы разделили класс на пять маленьких — и теперь у вас **пять** классов, которые **всегда** используются вместе. Раньше был один большой, теперь пять маленьких, и чтобы понять, что происходит, — нужно прочитать все пять. Стало ли лучше? Или вы просто разменяли одну проблему на другую?

**Ситуация пятая.** Вы читаете код коллеги: `OrderManager` с двадцатью методами, который делает всё — от создания заказа до отправки email. Вы говорите: «Это нарушает SRP». Коллега отвечает: «Покажи, **где** написано, что именно я нарушил». И вы понимаете, что **не можете** — у вас нет **критерия**, только «мне кажется, это слишком много».

**Ситуация шестая.** Вы видите класс `Calculator` с одним методом `calculate`. Один метод — одна ответственность? Но метод делает **двадцать** разных вычислений в зависимости от типа входных данных. Один метод — но двадцать ответственностей? Где правда?

Если хотя бы одна из этих ситуаций вам знакома — урок для вас.

## Что такое «ответственность»

**Ответственность** (responsibility) — это **причина для изменения**. Если у класса одна ответственность, — у него одна причина для изменения. Если две — две причины. И так далее.

Это определение — от Роберта Мартина, и оно **ключевое**. Обратите внимание: не «одно действие», не «один метод», не «одно поле». А **причина для изменения**.

**Что это значит на практике.** Причина для изменения — это **«если изменится X — нужно будет поменять этот класс»**. Причём X — это **внешнее** по отношению к классу: изменение требований, изменение формата, изменение инфраструктуры. Не «изменение самого класса» (это очевидно), а **изменение мира**, которое **требует** изменения класса.

Пример. `Order` хранит номер заказа, дату, список товаров и статус. Причина для изменения: **«изменилась модель заказа»**. Одна причина — одна ответственность. Хорошо.

Пример. `OrderService` умеет создавать заказ, оплачивать, отправлять уведомление, сохранять в базу и формировать PDF. Причины для изменения:

- **«изменилось бизнес-правило создания заказа»** — меняется `OrderService`;
- **«изменилась платёжная система»** — меняется `OrderService`;
- **«изменился формат уведомления»** — меняется `OrderService`;
- **«изменилась схема БД»** — меняется `OrderService`;
- **«изменился формат PDF»** — меняется `OrderService`.

**Пять причин** — **пять ответственностей**. Плохо.

**Ключевая идея:** ответственность — это **не «что класс делает»**, а **«почему класс меняется»**. Два класса могут «делать одно и то же» (например, оба возвращают строку), но иметь **разные** причины для изменения. И наоборот: один класс может «делать одно» (например, «обрабатывать заказ»), но иметь **несколько** причин для изменения (бизнес-правила, инфраструктура, форматирование).

## Пример: как отличить одну ответственность от нескольких

Разберём на примере. Вот класс:

```java
class UserService {
    void register(String email, String password) {
        // 1. Проверить, что email не занят
        // 2. Захешировать пароль
        // 3. Сохранить пользователя в БД
        // 4. Отправить приветственное письмо
    }
}
```

Сколько здесь ответственностей? Смотрим на **причины для изменения**.

**Причина 1: «изменились правила регистрации».** Например, добавили обязательное подтверждение email, или изменили минимальную длину пароля. — **меняется `register`**.

**Причина 2: «изменилась схема БД».** Например, добавили поле `created_at`, или перешли с PostgreSQL на MongoDB. — **меняется `register`**.

**Причина 3: «изменился формат приветственного письма».** Например, поменяли шаблон, добавили ссылку на акцию. — **меняется `register`**.

**Три причины** — **три ответственности**. Класс нарушает SRP.

**Как разделить.**

```java
class UserRegistrationService {
    private final UserRepository repository;
    private final PasswordHasher hasher;
    private final EmailSender emailer;

    void register(String email, String password) {
        if (repository.existsByEmail(email)) {
            throw new IllegalStateException("Email уже занят");
        }
        String hash = hasher.hash(password);
        User user = new User(email, hash);
        repository.save(user);
        emailer.sendWelcome(email);
    }
}
```

Теперь:

- **`UserRegistrationService`** — «бизнес-правила регистрации». Причина для изменения: «изменились правила регистрации». Одна ответственность.
- **`UserRepository`** — «сохранение пользователя». Причина: «изменилась схема БД». Одна ответственность.
- **`PasswordHasher`** — «хеширование пароля». Причина: «изменился алгоритм хеширования». Одна ответственность.
- **`EmailSender`** — «отправка email». Причина: «изменился формат письма». Одна ответственность.

Каждый класс — **одна** причина для изменения. Хорошо.

**Обратите внимание.** `UserRegistrationService` **всё ещё** делает несколько вещей: проверяет email, хеширует пароль, сохраняет пользователя, отправляет письмо. С точки зрения «что делает» — это «много». Но с точки зрения **«почему меняется»** — одна причина: **правила регистрации**. Всё, что связано с «как регистрировать пользователя», — в одном месте. Всё, что связано с «как хранить», — в репозитории. Всё, что связано с «как отправлять письмо», — в `EmailSender`.

## Ответственность — это «актор»

В 2014 году Роберт Мартин **уточнил** SRP. Он сказал: ответственность — это **«актор»** (actor), то есть **человек или группа людей**, которые **требуют** изменений в классе. Если изменения в классе требуются **разными** акторами — у класса **несколько** ответственностей.

Пример. `OrderService` с методами «создание заказа», «оплата», «уведомление», «сохранение», «PDF»:

- «создание заказа» — требует **бизнес-аналитик** (меняются правила продаж);
- «оплата» — требует **бухгалтер** (меняются правила оплаты);
- «уведомление» — требует **маркетолог** (меняются тексты);
- «сохранение» — требует **DBA** (меняется схема БД);
- «PDF» — требует **юрист** (меняется формат документа).

**Пять разных акторов** — **пять ответственностей**. Класс нарушает SRP.

А вот `Order` (модель) — его причины для изменения:

- «изменились поля заказа» — требует бизнес-аналитик;
- «изменилась структура» — тоже бизнес-аналитик.

**Один актор** — **одна ответственность**. Класс следует SRP.

**Это уточнение помогает в спорных случаях.** Если не получается определить «одну ответственность» — задайте вопрос: **«кто** потребует изменений в этом классе?». Если **один** человек (или одна роль) — одна ответственность. Если **разные** — несколько.

## Примеры: SRP в реальном коде

Разберём несколько типичных случаев, где легко ошибиться.

### Случай 1: `Point` с `x` и `y`

**Кажется:** класс делает «два» — хранит `x` и хранит `y`. Нарушает SRP?

**На самом деле:** класс представляет **одну** точку. Причина для изменения: **«изменилось представление точки»**. Одна причина — одна ответственность. **Не нарушает SRP.**

**Мораль.** «Одно» — это не «одно поле». Это «одна причина».

### Случай 2: `UserService` с `register`, `login`, `logout`, `changePassword`

**Кажется:** класс «про пользователя», одна ответственность.

**На самом деле:** причин для изменения **несколько**:

- «изменились правила регистрации» — одна;
- «изменились правила аутентификации» — другая;
- «изменились правила смены пароля» — третья.

**Три причины** — **три ответственности**. Класс нарушает SRP.

**Как разделить.** `UserRegistrationService`, `AuthenticationService`, `PasswordChangeService`. Каждый — своя ответственность. **Общий** `UserRepository` (или `UserFinder`), который они используют.

**Мораль.** «Одна тема» — это не «одна ответственность». Тема может быть одна («пользователи»), а ответственностей — несколько (регистрация, аутентификация, смена пароля).

### Случай 3: `Calculator` с одним методом `calculate`, который делает двадцать разных вычислений

**Кажется:** один метод — одна ответственность.

**На самом деле:** причин для изменения **двадцать** (каждое вычисление может измениться отдельно). **Двадцать ответственностей.** Класс нарушает SRP.

**Как разделить.** Каждое вычисление — отдельный метод (или отдельный класс), каждый со своей ответственностью. Или паттерн «Стратегия» (модуль 4): каждое вычисление — своя `CalculationStrategy`.

**Мораль.** «Один метод» — это не «одна ответственность». Метод может делать много всего.

### Случай 4: `EmailSender` с методами `sendWelcome`, `sendPasswordReset`, `sendOrderConfirmation`

**Кажется:** класс «отправляет email», одна ответственность.

**На самом деле:** причин для изменения **несколько**:

- «изменился формат welcome-письма» — одна;
- «изменился формат password reset» — другая;
- «изменился формат order confirmation» — третья.

**Три причины** — **три ответственности**. Класс нарушает SRP.

**Как разделить.** `EmailSender` (только отправка — «взять письмо и отправить»), `WelcomeEmailBuilder`, `PasswordResetEmailBuilder`, `OrderConfirmationEmailBuilder` (формирование писем). Каждый — своя ответственность.

**Мораль.** «Одна операция» (отправка email) — это не «одна ответственность». Отправка — одна, а формирование разных писем — разное.

## Как найти ответственности в классе

Есть несколько практических приёмов, которые помогают **увидеть**, сколько ответственностей у класса.

**Приём 1: причины для изменения.** Перечислите все **внешние** изменения, которые потребуют правки класса. Если их **больше одной** и они **не связаны** — несколько ответственностей.

**Приём 2: акторы.** Кто (какая роль) потребует каждого из изменений? Если **разные** роли — несколько ответственностей. Если **одна** — одна.

**Приём 3: группы методов.** Посмотрите на методы и сгруппируйте их по **темам**. Если группы **не пересекаются** и **не используют** общие поля — возможно, это разные ответственности.

**Приём 4: слово «и» в описании.** Опишите класс одним предложением. Если в предложении есть «и» — возможно, ответственностей несколько. «Класс создаёт заказ **и** оплачивает его **и** отправляет уведомление» — три «и» — три ответственности.

**Приём 5: количество `import`.** Посмотрите на `import` в начале файла. Если там **много** разных пакетов (`java.sql`, `javax.mail`, `java.io`, `java.net`) — возможно, класс общается с **разными** подсистемами, и это **разные** ответственности.

**Приём 6: тесты.** Если для тестирования класса нужны **разные** инфраструктуры (БД, SMTP, файловая система) — возможно, у класса **несколько** ответственностей.

## Когда SRP не работает

SRP — это эвристика, а не закон. Бывают случаи, когда **следовать SRP буквально** — плохо.

**Случай 1: слишком мелкие классы.** Если у вас **двадцать** классов по **пять** строк, и чтобы понять «как работает регистрация», — нужно прочитать **все двадцать**, — это **хуже**, чем один класс на 200 строк. SRP **не требует** «дробить всё на мельчайшие классы». Он требует **одну причину для изменения**, а не «один метод».

**Случай 2: классы, которые всегда используются вместе.** Если `Order` **всегда** используется вместе с `OrderItem`, и они **не имеют смысла** друг без друга, — может быть, это **один** класс? SRP не требует **разделять** то, что **логически едино**. `Order` с `List<OrderItem>` — нормально. `Order` и `OrderItem` как отдельные классы — тоже нормально. Оба варианта — «одна ответственность» на **своём** уровне.

**Случай 3: маленькие скрипты.** Если у вас **скрипт на 50 строк**, который делает одно действие раз в день, — не надо его дробить на десять классов. SRP для **больших** систем, где изменения **регулярны** и **разными** людьми. Для маленьких — «работает» достаточно.

**Случай 4: производительность.** Иногда дробление на классы **ухудшает** производительность: вместо одного вызова — цепочка из десяти. Обычно это **незначительно**, но в **горячих** местах может быть важно. В таких случаях — либо **мириться** с дублированием, либо **объединять** классы. SRP — не **единственный** критерий.

**Случай 5: «god object» как фасад.** Иногда **большой** класс — это **фасад** над подсистемой (модуль 5). Он «делает много», но **делегирует** подсистеме. С точки зрения SRP — у него **одна** ответственность: «предоставлять простой интерфейс к подсистеме». Внутри — десять классов, но **снаружи** — один. Это нормально.

**Правило:** **SRP — про «причины для изменения», а не про «количество методов»**. Если у класса **одна** причина меняться — он следует SRP, даже если у него **двадцать** методов. Если **несколько** — нарушает, даже если у него **один** метод.

## Аналогия, которая помогает

Хорошая аналогия — **больница**.

В больнице есть **врачи**, **медсёстры**, **администраторы**, **уборщики**. Каждый делает **своё дело**. Врач лечит, медсестра ухаживает, администратор ведёт документацию, уборщик убирает.

**Если бы один человек делал всё** — это был бы «божественный объект». Врач, который **и** лечит, **и** убирает, **и** ведёт документацию, **и** ухаживает, — **не мог бы** быть специалистом во всём. И **изменения** в одной области (например, новые правила уборки) требовали бы **переобучения** этого «универсала».

**SRP** — это «разделение ролей». Врач — **одна** ответственность. Медсестра — **другая**. Администратор — **третья**. Уборщик — **четвёртая**. Каждый делает **своё дело** и **меняется** по **своим** причинам.

**Но!** В маленькой **поликлинике** на 10 человек — **врач** может **и** лечить, **и** вести документацию, **и** иногда **убирать**. Это **не нарушает** SRP, потому что **причины для изменения** — **одни и те же** (изменения в медицине, изменения в документообороте — редко, и оба «про поликлинику»). Разделение на десять человек было бы **избыточным**.

**SRP — это про «разделение ролей»**, а не про «разделение на мельчайшие единицы». В больнице — много ролей, в поликлинике — меньше, в кабинете одного врача — одна. И это **нормально**.

**И ещё.** Даже в большой больнице есть **главврач** — который **координирует** всех. Он «делает много», но **делегирует**. Это **фасад** (модуль 5), и он **не нарушает** SRP, потому что его **ответственность** — «координация», одна.

## Микрозадача 1

Вот класс. Определите, сколько у него **причин для изменения** и есть ли нарушение SRP.

```java
class ShoppingCart {
    private final List<Item> items = new ArrayList<>();

    void addItem(Item item) {
        items.add(item);
    }

    void removeItem(Item item) {
        items.remove(item);
    }

    double getTotal() {
        return items.stream().mapToDouble(Item::getPrice).sum();
    }

    void applyDiscount(double percent) {
        // ... применить скидку к items
    }

    void saveToDatabase() {
        // ... сохранить корзину в БД
    }

    void sendReceipt(String email) {
        // ... отправить чек на email
    }
}
```

### Разбор

**Причины для изменения.**

**Причина 1: «изменились правила работы с корзиной».** Например, добавили максимальное количество товаров, или изменили правила применения скидки. — **меняется `ShoppingCart`**.

**Причина 2: «изменилась схема БД».** Например, добавили поле `updated_at`, или перешли на другую БД. — **меняется `saveToDatabase`**.

**Причина 3: «изменился формат чека».** Например, добавили логотип, или изменили шаблон. — **меняется `sendReceipt`**.

**Три причины** — **три ответственности**. Класс нарушает SRP.

Причём **акторы** разные:
- «правила корзины» — бизнес-аналитик;
- «схема БД» — DBA;
- «формат чека» — маркетолог или бухгалтер.

**Как разделить.**

```java
class ShoppingCart {
    private final List<Item> items = new ArrayList<>();

    void addItem(Item item) { items.add(item); }
    void removeItem(Item item) { items.remove(item); }
    double getTotal() { /* ... */ }
    void applyDiscount(double percent) { /* ... */ }
}

class CartRepository {
    void save(ShoppingCart cart) { /* ... */ }
}

class ReceiptSender {
    void send(ShoppingCart cart, String email) { /* ... */ }
}
```

Теперь:

- `ShoppingCart` — только «правила корзины». Одна причина: «изменились правила корзины».
- `CartRepository` — только «сохранение». Одна причина: «изменилась БД».
- `ReceiptSender` — только «отправка чека». Одна причина: «изменился формат».

**Три класса** — **три ответственности**. Хорошо.

**Что можно улучшить.** `getTotal` и `applyDiscount` — это **две** разные вещи? `getTotal` — «посчитать сумму», `applyDiscount` — «применить скидку». Может быть, это **две** ответственности? Зависит от того, **как часто** они меняются. Если скидки — это отдельная фича, которая часто меняется, — возможно, стоит вынести `applyDiscount` в отдельный `DiscountService`. Если скидки — простая часть корзины — можно оставить.

**Мораль.** SRP — это «причины для изменения», а не «методы». В `ShoppingCart` **три** ответственности, потому что **три** разных причины для изменения. Разделение — очевидно.

## Микрозадача 2

Вот два класса. Определите, в каком из них **нарушение SRP**, а в каком — **нет**.

```java
class A {
    private double x;
    private double y;

    double getX() { return x; }
    double getY() { return y; }
    void setX(double x) { this.x = x; }
    void setY(double y) { this.y = y; }

    double distanceTo(A other) {
        return Math.sqrt(Math.pow(x - other.x, 2) + Math.pow(y - other.y, 2));
    }
}

class B {
    private String name;

    String getName() { return name; }
    void setName(String name) { this.name = name; }

    void save() {
        // ... сохранение в БД
    }

    String toJson() {
        return "{\"name\":\"" + name + "\"}";
    }
}
```

### Разбор

**Класс A (`Point`)** — **следует SRP**. У него **одна** причина для изменения: **«изменилось представление точки»**. Всё — координаты, геттеры, сеттеры, расстояние — **связано** с этим. Одна ответственность. Хорошо.

**Класс B (`User`)** — **нарушает SRP**. У него **три** причины для изменения:

- **«изменилась модель пользователя»** (например, добавилось поле `email`) — меняется `name`, `getName`, `setName`;
- **«изменилась схема БД»** — меняется `save`;
- **«изменился формат JSON»** — меняется `toJson`.

Три причины — три ответственности.

Причём **акторы** разные:
- «модель» — бизнес-аналитик;
- «БД» — DBA;
- «JSON» — разработчик API.

**Как разделить.**

```java
class User {
    private String name;
    String getName() { return name; }
    void setName(String name) { this.name = name; }
}

class UserRepository {
    void save(User user) { /* ... */ }
}

class UserJsonSerializer {
    String toJson(User user) { return "{\"name\":\"" + user.getName() + "\"}"; }
}
```

Теперь:

- `User` — «модель». Одна причина: «изменилась модель».
- `UserRepository` — «сохранение». Одна причина: «изменилась БД».
- `UserJsonSerializer` — «сериализация в JSON». Одна причина: «изменился формат JSON».

**Мораль.** Класс с **одним** методом может **нарушать** SRP (если метод делает **много**). Класс с **десятью** методами может **следовать** SRP (если все методы — **про одно и то же**). «Одно» — это **причина для изменения**, а не **количество методов**.

## Самостоятельная задача

Возьмите класс из вашего проекта (или из открытого проекта на Java), который **больше 100 строк**. Проанализируйте его по SRP.

Подумайте:

- **сколько** у него «причин для изменения»? Перечислите все.
- **какие** акторы стоят за этими причинами? (Роли: бизнес-аналитик, DBA, маркетолог, тестировщик, разработчик API...)
- **связаны** ли причины между собой? (Например, «модель» и «валидация модели» — близкие; «модель» и «формат JSON» — далёкие.)
- **можно** ли разделить класс на несколько, чтобы у каждого была **одна** причина? Как бы вы назвали эти классы?
- **что** изменится в коде, который **использует** этот класс? (Сколько мест придётся обновить?)
- **стоит** ли это делать? (Подсказка: если класс 100 строк и «работает» — может, не стоит. Если 300 — скорее стоит. Если 500 — точно стоит.)

Затем ответьте на вопрос: **почему** «класс делает много» — это **не всегда** проблема? Приведите пример, где **большой** класс **оправдан** (подсказка: фасад, god object, скрипт).

Готового ответа не будет. Это ваша честная проверка на понимание: **видите** ли вы «причины для изменения» в реальном коде, **считаете** ли вы их, и **принимаете** ли осознанные решения.

## Что дальше

Мы разобрались, что такое SRP, как найти ответственности в классе, как их разделить и когда SRP **не** работает. В следующем уроке — **«OCP: открыт для расширения, закрыт для изменения»** — мы разберём второй принцип. Что значит «открыт **и** закрыт одновременно», как это выражается в коде, и когда OCP **вредит** (да, и такое бывает).

А пока — маленькое упражнение на наблюдательность. Откройте любой свой проект (или открытый проект на Java) и найдите класс, который **больше 100 строк**. Прочитайте его и попробуйте ответить на вопрос: **«сколько у этого класса причин для изменения?»** Если одна — хорошо. Если несколько — возможно, это кандидат на рефакторинг. Просто найдите. Не переделывайте (пока). Понимание того, **где** у класса «несколько причин», — уже большой шаг к более чистому коду.

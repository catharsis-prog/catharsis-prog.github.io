# 3. super

## Где вы это уже видели

В прошлом уроке мы несколько раз натыкались на `super(...)` и откладывали разговор на потом. Пришло время разобраться. Ключевое слово `super` — это то, через что наследник обращается к своему родителю. И у него есть три разных применения, которые легко перепутать.

**Ситуация первая.** Вы работаете в компании, и у вас есть начальник. Вы можете сделать что-то сами, а можете пойти к начальнику и сказать: «Я сделал свою часть, но вот это решение — за вами». Вы не «перепоручаете всё», вы только **делегируете** то, что относится к его зоне ответственности. `super` — это и есть такое обращение к «начальнику»: «сделай свою часть».

**Ситуация вторая.** Вы делаете ремонт в квартире. Есть базовый проект от застройщика: стены, пол, потолок, проводка. Вы делаете свой проект: добавляете мебель, меняете обои, но **базовые стены и проводку оставляете как есть**. Если вы хотите поменять что-то в проводке, — вы вызываете электрика из управляющей компании, который работает по базовому проекту. `super` — это обращение к «базовому проекту»: «сделай так, как было задумано изначально».

**Ситуация третья.** Вы готовите по рецепту. В рецепте написано: «Возьмите тесто, приготовьте по базовому рецепту, потом добавьте начинку». «Базовый рецепт» — это `super`. Вы не готовите тесто с нуля каждый раз, вы **переиспользуете** базовый рецепт и добавляете к нему что-то своё.

**Ситуация четвёртая.** Вы пишете письмо. Есть шаблон: «Уважаемый [имя], [текст], с уважением, [подпись]». Вы берёте шаблон и заполняете его: «Уважаемый Иван Иванович, ...». Вы не пишете «Уважаемый» и «с уважением» каждый раз заново — вы **переиспользуете** шаблон. `super` — это обращение к шаблону: «сделай свою часть, а я добавлю свою».

**Ситуация пятая.** Вы в иерархии должностей. У вас есть «сотрудник» (базовая должность) и «менеджер» (расширенная). Когда менеджер делает отчёт, — он делает всё, что делает обычный сотрудник, плюс добавляет раздел про свою команду. В коде это выглядит как «вызови `super.makeReport()`, потом добавь свой раздел». Не «перепиши отчёт с нуля», а «переиспользуй базовый и расширь».

**Ситуация шестая.** Вы смотрите на код и видите:

```java
class Dog extends Animal {
    @Override
    void speak() {
        super.speak();
        System.out.println("Гав!");
    }
}
```

— и понимаете, что `super.speak()` вызывает `Animal.speak()`. Но **зачем**? Почему не написать то же самое в `Dog.speak()`? И что произойдёт, если `Animal.speak()` изменится завтра? И можно ли вызвать `super.speak()` где-то не в первой строке? На эти вопросы мы и ответим в этом уроке.

Если последняя ситуация вам знакома — урок для вас. Если остальные тоже — интуиция про «обращение к базовому» у вас уже есть.

## Три применения super

В Java у `super` есть три разных применения, и их полезно различать.

### 1. Вызов конструктора родителя: super(...)

Это самое частое применение. Мы уже говорили о нём в прошлом уроке, но повторим и углубим.

```java
class Animal {
    private String name;

    Animal(String name) {
        this.name = name;
    }
}

class Dog extends Animal {
    Dog(String name) {
        super(name);   // вызываем конструктор Animal(String)
    }
}
```

`super(name)` вызывает конструктор родителя с параметром `name`. Это **единственный способ** передать данные в приватные поля родителя — потому что напрямую к ним наследник не имеет доступа.

**Правила, которые нужно помнить.**

**Первое.** `super(...)` должен быть **первой строкой** в конструкторе. Нельзя написать:

```java
Dog(String name) {
    System.out.println("Создаём собаку");
    super(name);   // ошибка компиляции
}
```

Это то же самое ограничение, что и с `this(...)`: конструктор родителя должен быть выполнен **до** того, как начнёт выполняться тело наследника. Иначе получится, что наследник работает с «недоделанным» родителем.

**Второе.** Нельзя вызвать и `this(...)`, и `super(...)` одновременно. Оба должны быть первыми, а первым может быть только одно. Логика простая: `this(...)` сам внутри себя вызовет `super(...)` (явно или невидимо), и делать это дважды не нужно.

**Третье.** Если `super(...)` не написан явно, — Java подставляет `super()` (без параметров). Если такого конструктора у родителя нет, — ошибка компиляции. Это мы разбирали в прошлом уроке, но напомним: как только в родителе появляется конструктор с параметрами, — конструктор без параметров исчезает, и наследник обязан вызывать `super(...)` с параметрами.

**Четвёртое.** `super(...)` можно вызывать только в конструкторе. Нельзя вызвать его из обычного метода. Это логично: «создать родителя» имеет смысл только в момент создания объекта.

### 2. Вызов метода родителя: super.method(...)

Это второе по частоте применение. `super.someMethod()` вызывает **реализацию метода из родителя**, даже если в наследнике этот метод переопределён.

```java
class Animal {
    void speak() {
        System.out.println("Какое-то животное издаёт звук");
    }
}

class Dog extends Animal {
    @Override
    void speak() {
        super.speak();   // вызываем реализацию Animal
        System.out.println("Гав!");
    }
}

new Dog().speak();
// Какое-то животное издаёт звук
// Гав!
```

**Зачем это нужно.** Иногда наследник хочет **расширить** поведение родителя, а не **заменить** его. «Сделай то же, что родитель, плюс ещё что-то». Это именно тот случай: `Dog.speak()` делает то, что делает `Animal.speak()`, и добавляет «Гав!».

Если бы мы не вызывали `super.speak()`, а просто написали `System.out.println("Гав!")`, — мы бы **потеряли** поведение родителя. Если завтра `Animal.speak()` изменится (например, начнёт печатать что-то более осмысленное), — `Dog.speak()` этого не заметит. С `super.speak()` — заметит.

**Важная тонкость.** `super.method()` можно вызывать **в любом месте** метода, не только в первой строке. Это отличается от `super(...)`, который должен быть первым. Логика такая: «вызвать метод родителя» — это обычная операция, которая может быть в любом месте. «Вызвать конструктор родителя» — это часть инициализации, и она должна быть первой.

**Ещё одна тонкость.** `super.method()` вызывает **ближайшую** реализацию в иерархии. Если у вас `A → B → C` и вы в `C` вызываете `super.method()`, — вызовется `B.method()`, а не `A.method()`. Если `B.method()` вызывает `super.method()`, — вызовется `A.method()`. Это называется «цепочка вызовов» и работает как матрёшка.

### 3. Доступ к полю родителя: super.field

Это самое редкое применение, потому что **переопределять поля не рекомендуется** (мы говорили об этом в прошлом уроке). Но технически `super.field` обращается к полю родителя, если в наследнике есть поле с тем же именем.

```java
class Animal {
    String name = "Животное";
}

class Dog extends Animal {
    String name = "Собака";

    void print() {
        System.out.println(super.name);   // Животное (поле Animal)
        System.out.println(this.name);    // Собака (поле Dog)
    }
}
```

Здесь `super.name` — это `Animal.name`, а `this.name` — это `Dog.name`. Два разных поля, и `super` позволяет обратиться к «скрытому» полю родителя.

**Но зачем?** Почти никогда не нужно. Если вы обнаружили, что вам нужно `super.field`, — это, скорее всего, признак того, что иерархия спроектирована неправильно. Правильно — иметь **одно** поле `name` в `Animal`, а в `Dog` его не переопределять. Тогда `super.name` и `this.name` — это одно и то же, и путаницы не возникает.

Я привожу это применение для полноты, но в реальном коде его стоит избегать.

## Порядок инициализации

Тонкость, которую полезно понимать, потому что она объясняет много «странного» поведения.

Когда вы создаёте объект, — инициализация идёт **сверху вниз** по иерархии. Сначала выполняется всё для `Object`, потом для `Animal`, потом для `Dog`. Внутри каждого класса порядок такой:

1. **Поля получают значения по умолчанию** (`null`, `0`, `false`).
2. **Выполняются инициализаторы полей** (те присваивания, которые написаны прямо в объявлении).
3. **Выполняется тело конструктора.**

Это то же самое, что мы разбирали в уроке 4 модуля 1, но теперь — в применении к цепочке классов. Вот пример:

```java
class Animal {
    String name = "Животное";   // инициализатор поля

    Animal() {
        System.out.println("Animal: name = " + name);
    }
}

class Dog extends Animal {
    String name = "Собака";     // инициализатор поля

    Dog() {
        super();                // невидимо
        System.out.println("Dog: name = " + name);
    }
}

new Dog();
```

Порядок выполнения будет такой:

1. Поля `Animal.name` = `null` (по умолчанию).
2. Поля `Dog.name` = `null` (по умолчанию).
3. Инициализатор `Animal.name` = `"Животное"`.
4. Конструктор `Animal()`: печатает `Animal: name = Животное`.
5. Инициализатор `Dog.name` = `"Собака"`.
6. Конструктор `Dog()`: печатает `Dog: name = Собака`.

Вывод:

```
Animal: name = Животное
Dog: name = Собака
```

Обратите внимание: **в момент выполнения `Animal()` поле `Dog.name` ещё не инициализировано**. Если бы `Animal()` обращался к методу, который переопределён в `Dog` и читает `Dog.name`, — он бы увидел `null`. Это классическая ловушка: **вызов переопределённого метода из конструктора родителя** может привести к работе с неинициализированными полями наследника.

Правило, которое стоит запомнить: **не вызывайте из конструктора методы, которые могут быть переопределены**. Если очень нужно — делайте их `final` или `private` (тогда они не переопределяются). Это правило не всегда удобно соблюдать, но оно спасает от очень странных багов.

## super в цепочке вызовов

Полезно понимать, как `super` работает в глубокой иерархии. Вот пример:

```java
class A {
    void greet() {
        System.out.println("A");
    }
}

class B extends A {
    @Override
    void greet() {
        System.out.println("B до");
        super.greet();       // вызывает A.greet()
        System.out.println("B после");
    }
}

class C extends B {
    @Override
    void greet() {
        System.out.println("C до");
        super.greet();       // вызывает B.greet()
        System.out.println("C после");
    }
}

new C().greet();
```

Вывод:

```
C до
B до
A
B после
C после
```

Это и есть «цепочка вызовов»: `C.greet()` вызывает `super.greet()`, который попадает в `B.greet()`. Тот вызывает `super.greet()`, который попадает в `A.greet()`. Тот печатает «A» и возвращается. `B.greet()` продолжает после `super.greet()` и печатает «B после». `C.greet()` продолжает и печатает «C после».

Такая схема работает как **расширение** поведения: каждый уровень делает что-то своё **до** и **после** родительской реализации. Это мощный приём, но им легко злоупотребить: если каждый уровень добавляет по строчке, — через несколько уровней становится непонятно, что вообще происходит. Глубокие иерархии с `super` в каждом методе — это код, который трудно читать и отлаживать.

**Правило:** если вы пишете `super.someMethod()` в **каждом** переопределённом методе наследника, — это сигнал, что иерархия слишком глубокая или спроектирована неправильно. Скорее всего, стоит подумать о композиции, о которой мы будем говорить в модуле 5.

## Когда super — плохая идея

`super` полезен, но у него есть тёмная сторона.

**`super` создаёт жёсткую связь с родителем.** Когда вы вызываете `super.someMethod()`, — вы зависите от того, что этот метод существует и ведёт себя определённым образом. Если завтра родитель изменит свою реализацию, — ваш наследник может сломаться. Это называется «проблема хрупкого базового класса», и о ней мы поговорим в уроке 7.

**`super` затрудняет понимание кода.** Когда вы видите метод в наследнике, который вызывает `super.method()`, — вам нужно **знать**, что делает `method()` в родителе. А это значит, что для понимания одной строки приходится смотреть в другой класс. В глубокой иерархии таких переходов может быть много, и понимание становится сложным.

**`super` — это признак «переиспользования кода, а не «выражения отношения».** Помните, в прошлом уроке мы говорили, что наследование — это не «способ переиспользовать код». `super` — это именно инструмент для переиспользования кода. Если вы используете `super` часто, — возможно, вы используете наследование не по назначению. Композиция часто решает ту же задачу лучше.

**`super` может нарушить инкапсуляцию.** Если родитель вызывает `super.someMethod()` в своём конструкторе, — это может привести к работе с неинициализированными полями наследника (мы говорили об этом выше). Если вы пишете родителя с расчётом на наследников, — вы должны быть осторожны с такими вызовами.

Общее правило: **`super` уместен, когда наследник действительно «расширяет» поведение родителя, а не «обходит» его**. Если вы чувствуете, что используете `super` только потому, что «так принято», — возможно, стоит пересмотреть иерархию.

## Аналогия, которая помогает

Хорошая аналогия — **рецепт и его вариация**.

Представьте, что у вас есть **базовый рецепт борща**: возьмите свёклу, капусту, картошку, морковь, лук, мясо, варите час. Это `Animal`. Теперь у вас есть **вариация «постный борщ»**: всё то же самое, но без мяса, с грибами. Это `Dog`. Чтобы приготовить постный борщ, — вы **не пишете рецепт с нуля**, а берёте базовый и «вызываете» его с модификацией: «сделай как в базовом, но вместо мяса добавь грибы».

**`super()` в конструкторе** — это как «возьми базовый рецепт за основу». Вы «передаёте» в базовый рецепт параметры: «свёкла — 2 штуки, мясо — не нужно». И базовый рецепт готовит свою часть с этими параметрами.

**`super.method()`** — это как «сделай ту часть, что в базовом рецепте, и потом добавь свою». Например: «свари бульон как в базовом рецепте, потом добавь лапшу». Вы вызываете базовое действие, а потом делаете что-то своё.

**`super.field`** — это как «используй базовый ингредиент». Например, в базовом рецепте есть «специя» (соль), а в вариации — своя «специя» (перец). Если вы хотите использовать соль из базового рецепта, — скажете `super.специя`. Но чаще всего это признак путаницы: у вас две «специи», и непонятно, какая где. Лучше — одна «специя», и не надо `super`.

И ещё одна мысль из этой аналогии: **если вы каждый раз готовите по базовому рецепту и добавляете что-то своё, — это «расширение»**. Если вы каждый раз **переписываете** базовый рецепт с нуля, — `super` не нужен, но и наследование, возможно, тоже.

## Микрозадача 1

Вот код. Что выведется? Объясните порядок.

```java
class A {
    A() {
        System.out.println("A()");
        method();
    }

    void method() {
        System.out.println("A.method()");
    }
}

class B extends A {
    int value = 42;

    B() {
        super();   // невидимо
        System.out.println("B()");
    }

    @Override
    void method() {
        System.out.println("B.method(), value = " + value);
    }
}

new B();
```

### Разбор

Выведется:

```
A()
B.method(), value = 0
B()
```

Разберём по шагам.

`new B()` — начинается создание объекта `B`.

Сначала выполняется конструктор `A()` (невидимо вызванный из `B()`):

- Печатает «A()».
- Вызывает `method()`. Здесь важный момент: **`method()` — это метод, переопределённый в `B`**, и вызывается именно `B.method()`, даже хотя мы всё ещё «внутри» конструктора `A`. Это полиморфизм в действии: метод выбирается по **фактическому типу объекта** (`B`), а не по типу класса, в котором находится вызов.
- `B.method()` печатает «B.method(), value = …». Но `value` в этот момент **ещё не инициализировано** — инициализаторы полей `B` выполняются **после** конструктора `A`. Поэтому `value = 0` (значение по умолчанию для `int`).

Потом выполняется инициализатор поля `B.value = 42`.

Потом выполняется тело конструктора `B()`: печатает «B()».

Итог: `value` выводится как `0`, хотя в объявлении написано `42`. Это и есть та самая ловушка «вызов переопределённого метода из конструктора родителя», о которой мы говорили.

**Как избежать.** Не вызывайте из конструктора методы, которые могут быть переопределены. Если нужно — сделайте метод `final` или `private`. В нашем случае — можно сделать `A.method()` `final`:

```java
class A {
    A() {
        System.out.println("A()");
        method();
    }

    final void method() {
        System.out.println("A.method()");
    }
}
```

Тогда `B` не сможет его переопределить, и вызовется `A.method()`. Проблема исчезнет.

**Мораль.** Порядок инициализации в иерархии — сверху вниз, но с тонкостями. Конструктор родителя выполняется **до** инициализации полей наследника, и если он вызывает переопределённый метод, — наследник работает с «полуинициализированными» полями. Это редко бывает нужно и почти всегда — ошибка.

## Микрозадача 2

Вот код. Он не компилируется. Найдите ошибку и объясните, почему.

```java
class A {
    void method() {
        System.out.println("A.method()");
    }
}

class B extends A {
    void method() {
        System.out.println("B.method()");
    }

    void test() {
        super.method();   // вызов A.method()
        super.method();   // ещё раз
        super.method();   // и ещё
    }
}
```

### Разбор

Хитрость в том, что этот код **компилируется** и работает. В нём **нет ошибки**. Три вызова `super.method()` подряд — это нормально, и каждый раз будет вызываться `A.method()`.

А вот если бы код был таким:

```java
class A {
    A() {
        super();   // ошибка: у Object нет super() в этом смысле
    }
}
```

— вот это не скомпилировалось бы. Или:

```java
class A {
    A() {
        this();   // ошибка: рекурсивный вызов
    }
}
```

— это тоже не скомпилировалось бы. Но наш код — в порядке.

Так что это **не задача на поиск ошибки**, а задача на понимание. Что здесь важно понять?

**Первое.** `super.method()` можно вызывать **сколько угодно раз** и **в любом месте метода**. Нет ограничения «только в первой строке», как у `super(...)`. Это обычный вызов, и его можно повторять.

**Второе.** Каждый вызов `super.method()` — это **отдельный** вызов `A.method()`. Если бы `A.method()` имел побочные эффекты (например, увеличивал счётчик), — они бы произошли трижды.

**Третье.** Это **не то же самое**, что `this.method()`. `this.method()` вызвал бы `B.method()` (потому что `this` — это `B`), а `super.method()` — `A.method()`. Это два разных метода, и `super` позволяет обойти переопределение.

Так что в этом коде нет ошибки, но есть **странность**: зачем вызывать `super.method()` три раза подряд? Это либо бессмысленно (если метод идемпотентный), либо не то, что хотел автор. Скорее всего, автор хотел вызвать `A.method()` один раз, а потом сделать что-то ещё.

**Мораль.** Задача была с подвохом: не всё, что выглядит странно, — ошибка. Но странный код — это повод задуматься, а не повод «оставить как есть». Если вы видите три `super.method()` подряд, — спросите себя: «А точно ли нужно три раза? Может, один?». И если ответ «три» — добавьте комментарий, объясняющий, почему именно три. Через полгода вы (или ваш коллега) скажете спасибо.

## Самостоятельная задача

Спроектируйте иерархию для системы «документы».

Базовый класс `Document` с полями `title`, `createdAt`, `author`. У него есть метод `render()`, который печатает что-то вроде «Документ: [title]».

Наследники:

- `Report extends Document` — с полем `period` (за какой период). Метод `render()` печатает «Отчёт: [title] за [period]» — то есть **расширяет** поведение родителя.
- `Invoice extends Document` — с полем `amount` (сумма). Метод `render()` печатает «Счёт: [title] на сумму [amount]» — тоже расширяет.
- `Memo extends Document` — с полем `recipient` (получатель). Метод `render()` печатает «Служебная записка: [title] для [recipient]» — тоже расширяет.

Подумайте:

- какие конструкторы нужны в каждом классе;
- как `Report.render()` может **переиспользовать** `Document.render()`, а не переписывать его с нуля;
- нужно ли вызывать `super.render()` в каждом наследнике, или где-то можно обойтись без него;
- что произойдёт, если завтра `Document.render()` начнёт печатать ещё и дату создания;
- где `super` полезен, а где — избыточен.

Затем ответьте на вопрос: если завтра появится `UrgentReport extends Report`, который добавляет к отчёту пометку «СРОЧНО», — как он должен переопределить `render()`? Должен ли он вызывать `super.render()` (то есть `Report.render()`)? А тот — `Document.render()`? Сколько раз в итоге вызовется `Document.render()`, если все три уровня вызывают `super.render()`?

Готового ответа не будет. Если хотите свериться — загляните в следующий урок про переопределение методов: там мы разберём `@Override`, ковариантные возвращаемые типы и другие тонкости, и вы увидите, насколько ваша интуиция про «расширение поведения» совпала с тем, как это устроено в Java.

## Что дальше

Мы разобрались с тремя применениями `super` и с порядком инициализации в иерархии. В следующем уроке — **«Переопределение методов»** — мы поговорим о том, что происходит, когда наследник «переписывает» метод родителя. `@Override`, ковариантные возвращаемые типы, вызов `super` — всё это будет в фокусе. И — что важнее — мы разберёмся, когда переопределение уместно, а когда — нет.

А пока — маленькое упражнение на наблюдательность. Посмотрите на любую иерархию классов в своём проекте (или в открытом проекте на Java). Найдите в наследниках вызовы `super`. Для каждого задайте вопрос: **а зачем он здесь?** Это «расширение» (наследник делает что-то своё **до** или **после** родительского вызова)? Или «обход» (наследник пытается обойти родительское поведение)? Если «обход» — возможно, иерархия спроектирована неправильно. Просто найдите. Не чините (пока). Понимание того, зачем нужен `super`, — уже большой шаг к более чистому коду.

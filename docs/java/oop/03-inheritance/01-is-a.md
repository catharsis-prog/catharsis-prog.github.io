# 1. «Is-a» — когда наследование уместно

## Где вы это уже видели

Два модуля мы говорили о том, как устроен один класс: из чего он состоит, как защищает своё состояние, как не даёт испортить данные. Пора поговорить о том, как классы соотносятся друг с другом. И начнём мы не с синтаксиса, а с вопроса, который задают реже, чем стоило бы: **а нужно ли вообще это наследование в данном случае?**

Потому что наследование — это самый соблазнительный и самый опасный инструмент ООП. Соблазнительный — потому что позволяет писать меньше кода. Опасный — потому что неправильное наследование ломает программу тихо, и вы замечаете это через полгода, когда уже не помните, почему сделали именно так. Об этом мы будем говорить весь модуль, но начнём с первого вопроса: **когда вообще «это является тем» — правда?**

**Ситуация первая.** Вы говорите: «Кошка — это животное». Звучит разумно: у кошки есть всё, что есть у животного (голова, лапы, способность двигаться), плюс кое-что своё (мяукает, ловит мышей). Наследование здесь естественно: `Cat extends Animal` — «кошка является животным», и всё, что умеет животное, умеет и кошка.

**Ситуация вторая.** Вы говорите: «Машина — это средство передвижения». Тоже звучит разумно. А теперь: «Самолёт — это средство передвижения». Тоже верно. А «лодка»? «Велосипед»? «Самокат»? «Лифт»? С каждым шагом «средство передвижения» становится всё более размытым понятием. И вот уже оказывается, что у «средства передвижения» есть метод `drive()`, который для лифта не имеет смысла, и метод `fillFuel()`, который не нужен велосипеду. Наследование формально работает, но по смыслу — врёт.

**Ситуация третья.** Вы говорите: «Квадрат — это прямоугольник». С точки зрения геометрии — да, квадрат является частным случаем прямоугольника (у него все углы прямые). А с точки зрения кода — не всегда: если у прямоугольника есть сеттеры `setWidth` и `setHeight`, которые можно менять независимо, — то квадрат, у которого стороны всегда равны, эти сеттеры нарушит. Наследование формально работает, но ломает инвариант. Классическая ловушка, о которой мы поговорим подробнее в модуле 6 (принцип подстановки Лисков), но намекнуть на неё стоит уже сейчас.

**Ситуация четвёртая.** Вы говорите: «Сотрудник — это человек». Верно. «Менеджер — это сотрудник». Тоже верно. «Стажёр — это сотрудник». Верно. А теперь: «Стажёр — это менеджер»? Нет. «Менеджер — это стажёр»? Тоже нет. Наследование позволяет построить иерархию `Person → Employee → Manager`, и это будет правильно. А вот `Person → Employee → Intern → Manager` — уже нет: стажёр и менеджер — это разные ветви, а не одна в другой.

**Ситуация пятая.** Вы говорите: «Заказ — это документ». Может быть, если у вас в системе все документы имеют номер, дату и статус. А может быть, и нет: если «документ» — это что-то с полями «автор», «подпись», «версия», — то заказ туда не очень вписывается. Наследование позволяет сделать `Order extends Document`, но «заказ — это документ» — не универсальная истина, а решение, зависящее от того, что у вас в системе считается документом.

**Ситуация шестая.** Вы пишете код и видите:

```java
class Animal { /* общее */ }
class Cat extends Animal { /* кошка */ }
class Dog extends Animal { /* собака */ }
```

— и всё выглядит логично. А потом видите:

```java
class Stack extends ArrayList { /* стек */ }
```

— и не понимаете: `Stack` — это `ArrayList`? Стек является списком? Вроде бы нет — стек это структура «последним пришёл, первым вышел», а список — это упорядоченная коллекция. Но код работает, потому что «стек — это коллекция», и у `ArrayList` есть всё нужное. И вот тут возникает вопрос: это наследование уместно или нет? И как это понять?

Если последняя ситуация вам знакома — этот урок для вас. Если остальные тоже — отлично, интуиция про «является» у вас уже есть, осталось научиться её проверять.

## Что такое «is-a»

**«Is-a»** (произносится «из-эй») — это отношение «является». Оно означает, что объект одного класса **является** объектом другого класса в том смысле, что может использоваться везде, где ожидается второй.

Кошка **является** животным: если функция ожидает животное, — кошка подойдёт. Собака **является** животным: тоже подойдёт. А вот машина **не является** животным: если функция ожидает животное, — машину туда не передашь.

В коде это выражается через `extends`:

```java
class Animal {
    void eat() {
        System.out.println("Животное ест");
    }
}

class Cat extends Animal {
    void meow() {
        System.out.println("Мяу");
    }
}
```

Теперь `Cat` **является** `Animal`: всё, что умеет `Animal` (`eat()`), умеет и `Cat`. Плюс `Cat` умеет что-то своё (`meow()`).

И вот ключевая проверка, которую стоит делать **перед тем**, как писать `extends`: **можно ли сказать, что объект подкласса — это объект суперкласса, без всяких «но»?**

«Кошка — это животное, **но** она не умеет летать» — это нормально: `Animal` и не обещает, что все животные умеют летать. «Кошка — это животное» — без «но». А вот:

«Квадрат — это прямоугольник, **но** его нельзя растянуть» — это уже плохо: `Rectangle` обещает, что его можно растянуть (есть `setWidth`/`setHeight`), а `Square` не может. Наследование формально работает, но по смыслу — врёт.

**Главное правило:** если вы не можете сказать «объект подкласса — это объект суперкласса, и он ведёт себя как суперкласс во всех отношениях», — наследование, скорее всего, не подходит. Есть и другие инструменты (композиция, интерфейсы), о которых мы будем говорить в этом и следующих модулях.

## Проверка «is-a» в жизни

Давайте потренируемся. Возьмём несколько пар и проверим, «is-a» это или нет.

**Кошка и животное.** Да. Кошка — это животное. Везде, где нужно животное, — кошка подойдёт.

**Машина и транспорт.** Да, но с оговоркой: «транспорт» — очень широкое понятие. Если у «транспорта» есть метод `refuel()`, то для велосипеда это не сработает. Значит, наследование от «транспорта» к «велосипеду» — плохо, а от «транспорта» к «машине» — нормально (если у «транспорта» нет методов, которые машине не подходят).

**Квадрат и прямоугольник.** С точки зрения геометрии — да. С точки зрения кода — зависит от того, что умеет прямоугольник. Если прямоугольник **неизменяемый** (нет сеттеров), — квадрат можно наследовать от него, и всё будет хорошо. Если прямоугольник **изменяемый** (есть `setWidth`/`setHeight`), — квадрат нарушит его инвариант, и наследование — плохо.

**Стек и список.** С формальной точки зрения — нет. Стек — это структура с ограниченным доступом (только с одного конца). Список — с доступом с любого места. Стек **не является** списком; он **содержит** список внутри (или массив, или что-то ещё). Наследование `Stack extends ArrayList` — плохо, и об этом мы поговорим подробнее в модуле 5.

**Сотрудник и человек.** Да. Сотрудник — это человек (у него есть имя, возраст, паспорт — всё, что у человека). Плюс у него есть зарплата, должность и т. д.

**Заказ и документ.** Зависит от того, что такое «документ» в вашей системе. Если документ — это «что-то с номером и датой», то да, заказ подойдёт. Если документ — это «что-то с автором и подписью», — заказ не подойдёт. Нет универсального ответа; ответ зависит от контекста.

**Пользователь и администратор.** Да. Администратор — это пользователь (у него есть логин, пароль, имя). Плюс он умеет что-то, чего не умеет обычный пользователь (например, банить других). Это классический пример наследования.

**Пользователь и заказ.** Нет. Пользователь — не заказ, и заказ — не пользователь. Это два разных понятия, и связь между ними — «пользователь делает заказ» — это не «is-a», а «has-a» (у пользователя есть заказы) или «uses-a» (пользователь использует заказ).

**Круг и эллипс.** С точки зрения математики — круг это эллипс с равными осями. С точки зрения кода — та же проблема, что с квадратом и прямоугольником: если у эллипса можно менять оси независимо, — круг не сможет. Если эллипс неизменяемый — можно.

**Кот и кошка.** В русском языке «кошка» может означать «кошка вообще» (как вид). В таком случае «кот — это кошка». Но если «кошка» — это самка кота, — то нет, это не «is-a», это «пол». Наследование `Cat extends Animal` — нормально, а `MaleCat extends Cat` — уже сомнительно: пол — это не подтип, это атрибут.

## Когда «is-a» — плохая идея

Даже если формально «is-a» выполняется, наследование может быть плохой идеей. Вот несколько признаков, что вы идёте не туда.

**Подкласс не использует всё, что даёт суперкласс.** Если у `Animal` есть метод `fly()`, а у `Cat` он не нужен, — либо `Animal` слишком общий, либо `Cat` — не совсем `Animal`. Это называется «нарушение принципа разделения интерфейсов», и мы поговорим об этом в модуле 6 (принцип ISP).

**Подкласс хочет «отменить» поведение суперкласса.** Если у `Rectangle` есть `setWidth`, а `Square` хочет его «запретить» (бросать исключение), — это признак того, что наследование не работает. Подкласс должен **расширять** поведение, а не **сужать** его.

**Подкласс зависит от деталей реализации суперкласса.** Если `Square` знает, что `Rectangle` хранит ширину и высоту в двух полях, — он привязан к реализации. Если завтра `Rectangle` поменяет представление (например, будет хранить площадь и соотношение сторон), — `Square` сломается. Это называется «проблема хрупкого базового класса», и о ней мы поговорим в уроке 7.

**Иерархия становится глубокой.** `A → B → C → D → E` — это уже подозрительно. Чем глубже иерархия, тем сложнее понять, что где определено, и тем больше шансов, что изменение в `A` сломает `E`. Часто плоскую структуру с композицией проще поддерживать, чем глубокую иерархию.

**Наследование используется для переиспользования кода.** Это самая частая ошибка. Наследование — это **не** «способ переиспользовать код», это **способ выразить отношение «is-a»**. Если вам просто нужно переиспользовать код, — есть композиция. Об этом мы будем говорить в модуле 5, но запомните главное: **«я хочу использовать код из класса X» — это не повод писать `extends X`**.

## Аналогия, которая помогает

Хорошая аналогия — **родословная и медицинская карта**.

Представьте, что наследование — это родословная. У вас есть «прабабушка», «бабушка», «мама», «вы». Каждый следующий **является** потомком предыдущего, и наследует какие-то черты. Но не все: у прабабушки был музыкальный слух, у вас — нет. У бабушки была склонность к математике, у вас — тоже. Это не «наследование кода», это «наследование черт», и не все черты передаются.

**«Is-a» в родословной:** «Я — потомок прабабушки». Это правда, и это выражается через наследование. «Я — человек». Тоже правда, но это не про родословную, это про вид. Наследование в коде может выражать и то, и другое, но важно понимать, что именно вы выражаете.

**«Has-a» в родословной:** у вас есть медицинская карта. Карта — не вы, и вы — не карта. Но она у вас есть. Это отношение «has-a», и оно выражается через **композицию**, а не через наследование.

И вот ключевая мысль этой аналогии: **не всё, что «ваше», — это «вы»**. У вас есть дом, но вы — не дом. У вас есть имя, и имя — это часть вас (можно сказать «вы — это человек с таким именем»), но имя — это атрибут, а не подтип. Наследование нужно только там, где «это является тем» — без всяких «но».

И ещё: **глубокая родословная не всегда полезна**. Вы можете проследить своих предков до XV века, но знание того, что ваш прапрапрапрадед был кузнецом, вряд ли поможет вам в программировании. Так же и с наследованием: чем глубже иерархия, тем меньше пользы от верхних уровней и тем сложнее разобраться, что где.

## Микрозадача 1

Вот несколько пар классов. Для каждой пары определите: это «is-a» (можно наследовать), «has-a» (нужна композиция), или «ни то, ни другое» (это разные понятия, связь через что-то третье).

1. `Dog` и `Animal`
2. `Engine` и `Car`
3. `Manager` и `Employee`
4. `Order` и `Customer`
5. `Circle` и `Shape`
6. `String` и `User`

### Разбор

**1. `Dog` и `Animal`** — «is-a». Собака — это животное. Наследование уместно, если у `Animal` нет методов, которые собаке не подходят.

**2. `Engine` и `Car`** — «has-a». Двигатель — это не машина; у машины есть двигатель. Композиция: `class Car { private Engine engine; ... }`. Наследование `Engine extends Car` было бы абсурдом.

**3. `Manager` и `Employee`** — «is-a». Менеджер — это сотрудник (у него есть имя, зарплата, должность). Плюс он умеет что-то своё (например, проводить совещания). Наследование уместно.

**4. `Order` и `Customer`** — «ни то, ни другое». Заказ — не клиент, и клиент — не заказ. Связь такая: «у клиента есть заказы» (или «заказ принадлежит клиенту»). Это отношение «has-a» в обратную сторону, и выражается через поле `Customer customer` в `Order` или `List<Order> orders` в `Customer`.

**5. `Circle` и `Shape`** — «is-a». Круг — это фигура (у неё есть площадь, периметр). Наследование уместно, если у `Shape` нет методов, которые кругу не подходят (например, если у `Shape` есть `setWidth`/`setHeight`, — круг их нарушит).

**6. `String` и `User`** — «ни то, ни другое». Строка — не пользователь, и пользователь — не строка. Связь такая: «у пользователя есть имя (строка)». Выражается через поле `String name` в `User`. Наследование `User extends String` было бы абсурдом (и к тому же `String` — `final`, так что технически невозможно).

**Мораль.** «Is-a» — это отношение «является», «has-a» — «содержит», «ни то, ни другое» — «связаны, но не через наследование». И большая часть связей в реальном коде — это не «is-a», а «has-a» или «ни то, ни другое». Поэтому наследование используется реже, чем кажется на первый взгляд.

## Микрозадача 2

Вот код. Определите, уместно ли здесь наследование, и если нет — почему.

```java
class Bird {
    void fly() {
        System.out.println("Лечу!");
    }
}

class Penguin extends Bird {
    @Override
    void fly() {
        throw new UnsupportedOperationException("Пингвины не летают");
    }
}
```

### Разбор

Наследование **неуместно**, и вот почему.

Формально «пингвин — это птица» — правда. Но `Bird` обещает, что умеет `fly()`. А `Penguin` это обещание нарушает: он бросает исключение. Это значит, что если функция ожидает `Bird` и вызывает `fly()`, — с `Penguin` она упадёт. То есть `Penguin` **не является** `Bird` в том смысле, в котором `Bird` определён в этом коде. Он «птица» биологически, но не «`Bird`» программно.

Это называется **нарушением принципа подстановки Лисков** (LSP). Мы поговорим о нём подробно в модуле 6, но суть такая: **подкласс должен вести себя как суперкласс во всех отношениях**. Если он «ломает» поведение (бросает исключение вместо работы), — он не подкласс, а что-то другое.

**Как исправить.** Есть несколько вариантов.

**Первый — разнести на разные иерархии.** Не все птицы летают. Значит, «летающая птица» — это отдельный подтип:

```java
class Bird {
    void eat() { ... }
}

class FlyingBird extends Bird {
    void fly() { ... }
}

class Penguin extends Bird {   // пингвин — птица, но не летающая
}

class Sparrow extends FlyingBird {   // воробей — летающая птица
}
```

Теперь `Bird` не обещает `fly()`, и `Penguin` ничего не нарушает. А `FlyingBird` обещает, и `Sparrow` выполняет.

**Второй — вынести `fly()` в интерфейс.** Об этом мы будем говорить в модуле 4, но идея такая:

```java
class Bird { ... }

interface Flying {
    void fly();
}

class Sparrow extends Bird implements Flying { ... }
class Penguin extends Bird { /* не реализует Flying */ }
```

Тогда «умеет летать» — это не свойство всех птиц, а отдельный контракт, который можно «прикрепить» к любому классу.

**Третий — сделать `fly()` по умолчанию «пустым».** Плохой вариант, но иногда используется:

```java
class Bird {
    void fly() {
        // ничего не делает по умолчанию
    }
}
```

Тогда `Penguin` не переопределяет `fly()`, и всё «работает». Но это обман: `fly()` у пингвина ничего не делает, хотя метод называется «летать». Это **тихий отказ**, о котором мы говорили в уроке 4 модуля про инкапсуляцию. Пользователь думает, что пингвин летит, а он просто молчит. Плохо.

**Мораль.** «Is-a» — это не только про биологию или формальную логику, но и про **контракт класса**. Если класс обещает какое-то поведение, — подкласс должен его выполнять. Если не может, — это не подкласс, а что-то другое. И лучше спроектировать иерархию так, чтобы таких «неудобных» подклассов не было.

## Самостоятельная задача

Придумайте иерархию для системы «фигуры на плоскости». В ней должны быть:

- круг;
- прямоугольник;
- квадрат;
- треугольник;
- эллипс.

Подумайте:

- какие отношения между этими фигурами — «is-a», «has-a» или «ни то, ни другое»;
- стоит ли делать общий базовый класс `Shape`, и если да — что в нём будет (какие методы);
- уместно ли наследование `Square extends Rectangle` (помните о проблеме с сеттерами);

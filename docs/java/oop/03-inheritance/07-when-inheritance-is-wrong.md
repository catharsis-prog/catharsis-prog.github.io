# 7. Когда наследование — плохая идея

## Где вы это уже видели

Шесть уроков мы говорили о наследовании как о полезном инструменте: как его писать, как переопределять методы, как делать абстрактные классы. Пора поговорить о том, где оно **вредит**. Потому что наследование — это такой инструмент, который легко переусердствовать: соблазн «сделать иерархию» велик, а расплата приходит потом, когда иерархия разрастается и начинает трещать по швам.

**Ситуация первая.** Вы купили дом у застройщика. Прошло пять лет, застройщик решил «улучшить» фундамент — и у вас в подвале треснула стена. Вы ничего не делали, но что-то сломалось. Это и есть «хрупкий базовый класс»: изменение в фундаменте (родителе) ломает то, что на нём стоит (наследников).

**Ситуация вторая.** Вы работаете в компании, и у вас есть «общий регламент для всех сотрудников». Он занимает триста страниц. И в нём есть правило, которое относится только к бухгалтерам, но написано так, что все остальные тоже должны его соблюдать. Например: «каждый сотрудник обязан ежедневно закрывать отчётный период». Бухгалтеры кивают, а программисты в недоумении: какой отчётный период? Это «раздутый базовый класс»: он пытается быть общим для всех, но на самом деле описывает частные случаи.

**Ситуация третья.** Вы смотрите на родословную. Прапрадед был купцом, прадед — инженером, дед — врачом, отец — юристом, вы — программистом. Никакой «общей профессии» у семьи нет, но формально вы все «потомки прапрадеда». Если бы кто-то попытался «унаследовать» профессию прапрадеда, — ничего хорошего бы не вышло: вы не купец, и никогда им не были. Это «наследование ради родства»: формально связь есть, но по сути — она ничего не даёт.

**Ситуация четвёртая.** Вы работаете с API. У вас есть базовый класс `BaseController` с двадцатью методами: `handleRequest`, `validateInput`, `logRequest`, `checkAuth`, `formatResponse` и так далее. Вы хотите написать контроллер для новой страницы — и вы **обязаны** унаследоваться от `BaseController`, потому что «так принято». В итоге ваш контроллер тащит за собой двадцать методов, из которых использует три. Остальные семнадцать — «на всякий случай», и они мешают: при чтении кода непонятно, что действительно используется, а что нет.

**Ситуация пятая.** Вы расширяете класс `ArrayList`, чтобы сделать `Stack`. Вроде бы всё работает: `push` — это `add`, `pop` — это `remove(size - 1)`. Но потом кто-то вызывает у вашего стека `add(0, element)` — и добавляет элемент в **начало**. С точки зрения `ArrayList` это нормально, а с точки зрения стека — это катастрофа: стек так не работает. Наследование формально работает, но по смыслу — врёт: `Stack` не «является» `ArrayList`, потому что у `ArrayList` больше возможностей, чем у стека.

**Ситуация шестая.** Вы видите иерархию из семи уровней: `Object → Component → UIComponent → Panel → ScrollablePanel → ScrollableListPanel → MessagesPanel`. И понимаете, что изменение в `Component` (верхний уровень) может сломать `MessagesPanel` (нижний уровень), но вы даже не знаете, каким образом. Потому что чтобы это понять, нужно прочитать семь классов и понять, как они взаимодействуют.

Если последняя ситуация вам знакома — урок для вас. Если остальные тоже — интуиция про «наследование может вредить» у вас уже есть.

## Проблема хрупкого базового класса

Это, пожалуй, главная проблема наследования, и у неё даже есть специальное название — **fragile base class problem**. Суть в одном предложении: **изменение в базовом классе может сломать наследников, даже если вы не знали, что они есть**.

Вот пример. Есть базовый класс:

```java
class Base {
    void doSomething() {
        System.out.println("Base");
    }
}

class Derived extends Base {
    @Override
    void doSomething() {
        System.out.println("Derived");
    }

    void doSomethingTwice() {
        doSomething();   // Derived.doSomething()
        doSomething();   // Derived.doSomething()
    }
}
```

Всё работает: `doSomethingTwice()` вызывает `Derived.doSomething()` дважды, как и задумано.

Теперь автор `Base` решает **улучшить** метод — добавить в него какой-то полезный «общий» эффект. Например, логирование:

```java
class Base {
    void doSomething() {
        System.out.println("Начинаем doSomething");
        System.out.println("Base");
    }
}
```

Казалось бы, изменение в `Base` не должно затронуть `Derived`, ведь `Derived` переопределяет `doSomething()`. Но! Смотрите:

- `Derived.doSomethingTwice()` вызывает `Derived.doSomething()` дважды.
- `Derived.doSomething()` **не вызывает `super.doSomething()`** — в нём просто `System.out.println("Derived")`.

Значит, добавленное логирование в `Base` **не появится** при вызове `Derived.doSomething()`. И если автор `Base` надеялся, что теперь все наследники будут логировать, — он ошибся. А если наоборот — наследник был бы зависим от `Base`, и добавление логирования в `Base` могло бы что-то сломать.

Это простой пример, но проблема глубже. В реальном коде автор `Base` может:

- **вызвать** из нового метода `doSomething()`, и это «дёрнет» наследника в неожиданном месте;
- **добавить** в `doSomething()` вызов какого-то другого метода, который наследник переопределил, — и снова «дёрнуть» неожиданно;
- **изменить** порядок вызовов внутри `doSomething()`, и это сломает наследников, которые рассчитывали на старый порядок;
- **добавить** проверку, которая бросает исключение, — и наследник, который не ожидал, начнёт падать.

Самое неприятное: **автор `Base` может даже не знать, что у него есть наследники**. В большой компании `Base` мог быть написан три года назад, наследники — год назад, а автор — уволился. И никто не знает, что где зависит.

## Глубокие иерархии

Вторая большая проблема — **глубина**. Чем длиннее цепочка наследования, тем сложнее понять, что происходит.

Вот пример: `A → B → C → D → E`. Чтобы понять, что делает метод `foo()` в `E`, вам нужно:

1. Посмотреть, определён ли `foo()` в `E`. Если да — посмотреть, не вызывает ли он `super.foo()`.
2. Если вызывает (или не определён в `E`), — посмотреть `D`. И так далее.
3. Учтите, что в каждом классе `foo()` мог быть переопределён, и в каждом мог быть `super.foo()`.
4. Учтите, что `A` мог быть изменён вчера, и `E` теперь работает не так, как вы думали.

Это **очень сложно**. В каждом классе иерархии нужно понять, что происходит, и как это связано с соседями. Читать пять классов, чтобы понять одну строку, — это тяжело, и это приводит к ошибкам.

Есть эмпирическое правило (не строгое, но полезное): **если иерархия глубже трёх уровней, — это сигнал, что что-то не так**. Три уровня — это обычно «интерфейс → абстрактный класс → конкретный класс» или что-то подобное, и это ещё обозримо. Пять, шесть, семь — уже почти наверняка проблема. Скорее всего, стоит подумать о композиции.

## Наследование ради переиспользования кода

Третья проблема — **самая частая**. Наследование используется не для того, чтобы выразить «is-a», а для того, чтобы **переиспользовать код**. Мол, «я хочу использовать `doSomething()` из `Base`, поэтому сделаю `extends Base`». Это неправильная мотивация.

Вот пример. Вы хотите использовать метод `validate()` из класса `Validator` в своём классе `UserService`. И вы пишете:

```java
class UserService extends Validator {
    // ...
}
```

Формально «`UserService` — это `Validator`» — **неправда**. `UserService` — это не валидатор, это сервис, который **использует** валидатор для проверки данных. Наследование здесь — попытка «переиспользовать код», но не «выразить отношение». И это приводит к проблемам:

- **Вы тащите за собой всё**, что есть в `Validator` (все его методы, поля, поведение), хотя вам нужен только `validate()`.
- **`UserService` теперь «является» `Validator`**, и его можно передать туда, где ожидается `Validator`. Но там его будут использовать как валидатор, что не то, что нужно.
- **Изменения в `Validator`** могут сломать `UserService`, даже если они не имеют отношения к `validate()`.
- **Тестировать `UserService`** сложнее: чтобы понять, что он делает, нужно помнить, что он ещё и `Validator`.

Правильное решение — **композиция**:

```java
class UserService {
    private final Validator validator = new Validator();

    void register(String email) {
        if (!validator.validate(email)) {
            throw new IllegalArgumentException("Некорректный email");
        }
        // ...
    }
}
```

Теперь `UserService` **использует** `Validator`, но не «является» им. Он не тащит за собой лишние методы, его не могут использовать как валидатор, изменения в `Validator` затрагивают только `validate()`, а тестировать проще.

**Правило простое:** если вы пишете `extends`, потому что «хочу использовать код из родителя», — это, скорее всего, ошибка. Правильная мотивация для `extends` — «это **является** тем, и я хочу выразить это отношение». Если мотивация другая, — используйте композицию.

## Наследование, которое врёт

Четвёртая проблема — **нарушение контракта**. Наследник формально «является» родителем, но ведёт себя не так, как родитель обещает. Это называется **нарушением принципа подстановки Лисков** (LSP), и мы подробно разберём его в модуле 6, но упомянуть стоит уже сейчас.

Пример: `Stack extends ArrayList`. Стек — не список, потому что у списка можно добавлять элементы в любое место, а у стека — только в конец (и только «сверху»). Формально `Stack` наследует `add(int, E)`, но использовать этот метод у стека — **семантическая ошибка**. Если функция ожидает `List` и добавляет элемент в середину, — со стеком она сломается (ну, или сломает стек).

Или `Square extends Rectangle`. Квадрат — прямоугольник по геометрии, но не по поведению: у прямоугольника можно независимо менять ширину и высоту, а у квадрата — нельзя (иначе он перестанет быть квадратом). Формально `Square` наследует `setWidth`/`setHeight`, но использование их независимо нарушает инвариант квадрата.

В обоих случаях наследование **формально работает, но врёт**. И это опасно, потому что ошибка невидима: код компилируется, тесты проходят, а баг вылезает в самый неподходящий момент.

**Как проверить, что наследование не врёт.** Представьте, что у вас есть функция, которая принимает родителя и делает с ним что-то разумное. Подставьте туда наследника. Работает? Если да — наследование «честное». Если функция начинает вести себя странно — наследование врёт.

Например: «функция, которая принимает `Rectangle` и увеличивает ширину в два раза». Если подставить `Square`, — он перестанет быть квадратом (ширина и высота станут разными). Значит, `Square extends Rectangle` — врёт.

## Признаки того, что наследование — плохая идея

Соберём всё вместе. Вот несколько признаков, что в вашем коде наследование используется неправильно.

**Признак 1: вы переопределяете метод, чтобы «запретить» его.** Например, `Square.setWidth` бросает `UnsupportedOperationException`. Или `Penguin.fly` бросает исключение. Это значит, что наследник не может выполнить контракт родителя, — а значит, он не «является» родителем в том смысле, в котором родитель определён.

**Признак 2: у наследника много методов, которые он «не использует».** Например, `UserService extends Validator` использует только один метод из двадцати. Это признак того, что наследование используется «ради кода», а не «ради отношения».

**Признак 3: вы наследуетесь от класса, чтобы «получить доступ» к его полям или методам.** Например, «наследуюсь от `BaseController`, чтобы иметь `logRequest()`». Это неправильно: если нужен доступ — используйте композицию и вызывайте методы через неё.

**Признак 4: иерархия глубже трёх уровней.** Обычно это уже проблема. Каждый уровень добавляет сложности, и рано или поздно она становится невыносимой.

**Признак 5: изменения в базовом классе ломают наследников.** Если вы боитесь менять базовый класс, потому что «что-то сломается», — это уже «хрупкий базовый класс». И это сигнал, что иерархия спроектирована неправильно.

**Признак 6: вы не можете сказать «это является тем» без «но».** «Кошка — это животное, но она не умеет летать» — нормально (животное и не обещает летать). А «квадрат — это прямоугольник, но его нельзя растянуть» — уже проблема.

**Признак 7: наследник знает о деталях реализации родителя.** Например, `Derived` знает, что `Base` хранит данные в массиве, и использует это. Если `Base` поменяет представление — `Derived` сломается. Это признак того, что наследование «привязывает» к реализации, а не к контракту.

Если вы обнаружили хотя бы два-три признака из этого списка, — стоит задуматься о композиции.

## Что делать вместо наследования

Хорошая новость: у наследования есть альтернативы, и часто они **лучше**. Мы будем говорить о них в модуле 5, но кратко упомянем сейчас.

**Композиция.** Вместо `class A extends B` — `class A { private B b; }`. Класс `A` **содержит** `B` и **делегирует** ему работу. Это гибче: `B` можно заменить (например, на другую реализацию или на мок в тестах), и изменения в `B` затрагивают только те методы, которые `A` действительно использует.

**Интерфейсы.** Вместо `abstract class B` — `interface B`. Интерфейс задаёт контракт, но не реализацию. Класс может реализовать **несколько** интерфейсов (в отличие от `extends`, который только один). И интерфейс не «привязывает» к иерархии.

**Стратегия.** Вместо `class A extends B` с переопределением метода — вынести поведение в отдельный объект (`Strategy`) и подставлять его. Например, `Sorter` с полем `Comparator` — вместо того чтобы наследоваться от `Sorter` для каждой сортировки.

**Делегирование.** Если класс `A` хочет использовать методы `B`, — не наследоваться, а **делегировать** им: `A.doSomething()` вызывает `b.doSomething()`. Это то же «переиспользование кода», но без наследования.

Все эти приёмы мы разберём в модуле 5. Пока что запомните главное: **у наследования есть альтернативы, и часто они лучше**. Наследование — это не «единственный способ», а «один из инструментов», и пользоваться им стоит осознанно.

## Аналогия, которая помогает

Хорошая аналогия — **карточный домик**.

**Наследование — это карточный домик.** Каждый уровень опирается на предыдущий. Пока всё стоит — красиво и работает. Но если выдернуть одну карту снизу — рухнет всё, что на ней стоит. И чем выше домик, тем страшнее его трогать: одно неверное движение, и всё развалится.

**Композиция — это кирпичная стена.** Каждый кирпич — самостоятельный. Если один кирпич выпал — стена стоит, просто с дыркой. И можно заменить один кирпич, не трогая остальные.

**Интерфейс — это чертёж стены.** Он говорит, какой должна быть стена, но не говорит, из чего её строить. Можно построить кирпичную, бетонную, деревянную — главное, чтобы соответствовала чертежу.

**Хрупкий базовый класс — это когда карточный домик строит кто-то другой, а вы живёте на верхнем этаже.** Однажды он решит «улучшить» нижний этаж, а у вас всё рухнет. И вы даже не будете знать, почему.

И ещё одна мысль: **карточный домик красив, но недолговечен**. Он впечатляет на фотографии, но в реальной жизни мало кто строит дома из карт. Так же и с наследованием: красивая иерархия впечатляет на диаграмме, но в реальной поддержке часто оказывается, что плоская структура с композицией — надёжнее.

## Микрозадача 1

Вот иерархия. Найдите в ней три проблемы и объясните, почему они проблемы.

```java
class Vehicle {
    void startEngine() { /* ... */ }
    void fillFuel() { /* ... */ }
    void fly() { /* ... */ }
}

class Car extends Vehicle {
    @Override
    void fly() {
        throw new UnsupportedOperationException("Машины не летают");
    }
}

class Bicycle extends Vehicle {
    @Override
    void startEngine() {
        throw new UnsupportedOperationException("У велосипеда нет двигателя");
    }

    @Override
    void fillFuel() {
        throw new UnsupportedOperationException("Велосипед не заправляется");
    }

    @Override
    void fly() {
        throw new UnsupportedOperationException("Велосипеды не летают");
    }
}
```

### Разбор

Проблем три, и они типичные.

**Проблема 1: базовый класс слишком широкий.** `Vehicle` обещает, что **у любого** транспорта есть двигатель, топливо и способность летать. Но это не так: у велосипеда нет двигателя, а летают вообще не все. `Vehicle` пытается быть «общим для всех», но на самом деле описывает **частные случаи** (машины и самолёты), а не общее.

Это та самая «раздутый базовый класс», о которой мы говорили в начале урока. Он вроде бы «общий», но на самом деле — «сборная солянка» из разных иерархий.

**Проблема 2: наследники нарушают контракт.** `Car.fly()`, `Bicycle.startEngine()`, `Bicycle.fillFuel()`, `Bicycle.fly()` — все бросают `UnsupportedOperationException`. Это нарушение принципа подстановки Лисков: если функция ожидает `Vehicle` и вызывает `fly()`, — с `Car` она упадёт. Значит, `Car` не «является» `Vehicle` в том смысле, в котором определён `Vehicle`.

**Проблема 3: иерархия не отражает реальность.** Велосипед — это транспорт, но не «то же самое, что машина». Он не должен наследовать `startEngine()` и `fillFuel()`. Иерархия «`Vehicle` → `Car`, `Bicycle`» — это не «общее → частное», а «сборная солянка → конкретные случаи».

**Как исправить.** Есть несколько подходов.

**Первый — разнести на разные интерфейсы:**

```java
interface Vehicle { }

interface EnginePowered {
    void startEngine();
    void fillFuel();
}

interface Flying {
    void fly();
}

class Car implements Vehicle, EnginePowered { /* ... */ }
class Bicycle implements Vehicle { /* ... */ }
class Airplane implements Vehicle, EnginePowered, Flying { /* ... */ }
```

Теперь «умеет летать» — это отдельный контракт, «имеет двигатель» — отдельный. Машина реализует `EnginePowered`, но не `Flying`. Велосипед не реализует ни то, ни другое. Всё логично.

**Второй — композиция.** Вместо наследования — `Vehicle` содержит `Engine`:

```java
class Vehicle {
    private Engine engine;   // может быть null, если двигателя нет
}

class Engine {
    void start() { /* ... */ }
    void fillFuel() { /* ... */ }
}
```

Тогда «есть двигатель» — это «поле `engine` не `null`», а не «метод, который бросает исключение».

**Третий — не делать общий базовый класс вообще.** Если у машины, велосипеда и самолёта нет **общего** поведения, — может быть, не нужен и общий базовый класс. Пусть будут отдельные классы, а «транспорт» — это просто понятие в документации, а не в коде.

**Мораль.** Базовый класс должен описывать **общее**, а не «всё, что бывает». Если метод не имеет смысла для всех наследников, — его не должно быть в базовом классе. И «бросать `UnsupportedOperationException`» — это не «правильное поведение по умолчанию», а «признак того, что метод здесь не должен быть».

## Микрозадача 2

Вот иерархия. Она длинная и «красивая». Найдите в ней проблему, которую мы обсуждали в этом уроке.

```java
class Object { /* ... */ }
class Component extends Object { /* ... */ }
class UIComponent extends Component { /* ... */ }
class Panel extends UIComponent { /* ... */ }
class ScrollablePanel extends Panel { /* ... */ }
class ScrollableListPanel extends ScrollablePanel { /* ... */ }
class MessagesPanel extends ScrollableListPanel { /* ... */ }
```

### Разбор

Проблема — **глубина**. Семь уровней наследования — это очень много. Чтобы понять, что делает `MessagesPanel`, вам нужно прочитать все шесть классов выше. И если что-то в `Component` изменится, — `MessagesPanel` может сломаться, и вы даже не сразу поймёте, почему.

Это «проблема глубокой иерархии», о которой мы говорили. Её симптомы:

- **Сложно читать.** Чтобы понять один класс, нужно прочитать шесть.
- **Хрупко.** Изменение в любом из шести предков может сломать `MessagesPanel`.
- **Трудно тестировать.** Тестировать `MessagesPanel` в изоляции сложно: он тащит за собой поведение всех шести предков.
- **Трудно расширять.** Если нужно добавить новое поведение (например, «`MessagesPanel` с анимацией»), — придётся либо наследоваться ещё раз (восьмой уровень), либо лезть в середину иерархии.

**Как исправить.** Скорее всего, стоит разбить иерархию на **несколько независимых частей** и связать их **композицией**:

```java
class MessagesPanel {
    private final ScrollableList list;
    private final PanelStyle style;
    // ...
}
```

Здесь `MessagesPanel` — **самостоятельный** класс, который **содержит** `ScrollableList` и `PanelStyle`. Каждый компонент можно менять и тестировать отдельно. И «MessagesPanel — это ScrollableList» — уже не утверждается; вместо этого «MessagesPanel **содержит** список». Это честнее и гибче.

Возможно, некоторые промежуточные классы вообще не нужны: `ScrollablePanel` — это `Panel` + `Scrollable`, и это можно выразить через интерфейсы (`Panel implements Scrollable`), а не через наследование.

**Мораль.** Глубокая иерархия — это **долг**, который вы откладываете. Чем длиннее цепочка, тем больше проблем будет потом. Если иерархия глубже трёх уровней, — это сигнал, что стоит подумать о композиции. Не всегда нужно её менять, но **подумать** — стоит.

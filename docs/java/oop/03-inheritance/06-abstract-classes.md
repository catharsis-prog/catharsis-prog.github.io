# 6. Абстрактные классы

## Где вы это уже видели

До сих пор все классы, которые мы писали, можно было создать через `new`. `User`, `Account`, `Shape`, `Animal` — каждый из них был полноценным типом, экземпляр которого имел смысл. Но иногда бывает иначе: есть понятие, которое **существует только как обобщение**, и создать «просто его» — бессмысленно.

**Ситуация первая.** Вы говорите: «Покажи мне животное». И собеседник спрашивает: «Какое? Кошку? Собаку? Корову?» — «Просто животное». — «Такого не бывает. Животное — это общее понятие, а конкретное — это всегда кто-то». В программе это естественно выражается через абстрактный класс: `Animal` существует как **понятие**, но объект `new Animal()` создать нельзя — потому что «просто животное» не существует.

**Ситуация вторая.** Вы работаете с фигурами. У вас есть `Shape` — общее понятие фигуры. У неё есть площадь, периметр, цвет. Но «просто фигура» — это что? Квадрат? Круг? Треугольник? Нет «просто фигуры»; есть **конкретные** фигуры, и каждая из них — частный случай. `new Shape()` был бы бессмыслицей: какую площадь возвращать? Какой периметр? Абстрактный класс говорит: «фигура — это понятие, но конкретную фигуру задаёт наследник».

**Ситуация третья.** Вы читаете вакансию: «Требуется сотрудник». Не «менеджер», не «разработчик», не «бухгалтер» — просто «сотрудник». Формально это возможно (есть же общие требования), но на практике «просто сотрудник» не работает: у любого реального сотрудника есть **конкретная роль**, и от неё зависят обязанности. Абстрактный класс `Employee` выражает общее, но конкретную роль задают наследники — `Manager`, `Developer`, `Accountant`.

**Ситуация четвёртая.** Вы смотрите на меню в ресторане. Есть раздел «Напитки»: чай, кофе, сок, вода. «Напиток» — это общее понятие. Вы не можете заказать «просто напиток» — официант спросит: «Какой?» И это нормально: «напиток» существует только как **категория**, а заказать можно только конкретный напиток.

**Ситуация пятая.** Вы работаете с документами. У вас есть `Document` — общее понятие. У него есть заголовок, дата создания, автор. Но «просто документ» — это что? Отчёт? Счёт? Служебная записка? `new Document()` имел бы смысл только если у документа есть какая-то конкретная логика (например, «печатать текст»), но если её нет — это «пустой» объект, от которого мало пользы.

**Ситуация шестая.** Вы видите код:

```java
abstract class Shape {
    abstract double area();
}
```

— и не понимаете: почему `abstract`? Почему метод `area()` без тела? Как это вообще работает, если тело не написано? И кто его реализует? И зачем это нужно, если можно просто написать `double area() { return 0; }` в обычном классе?

Если последняя ситуация вам знакома — урок для вас. Если остальные тоже — интуиция про «общее понятие без конкретики» у вас уже есть.

## Что такое абстрактный класс

**Абстрактный класс** — это класс, который **нельзя создать напрямую** через `new`. Он существует только для того, чтобы от него наследовались.

Объявляется он с ключевым словом `abstract`:

```java
abstract class Shape {
    abstract double area();
}
```

Здесь два `abstract`: один на классе, другой на методе. И у каждого своё значение.

**`abstract class Shape`** — нельзя написать `new Shape()`. Компилятор не даст. Это класс, который существует только как «заготовка» для наследников.

**`abstract double area()`** — это **абстрактный метод**: у него нет тела. Точка с запятой вместо фигурных скобок. Это значит: «у всех фигур есть площадь, но как именно её считать — каждая фигура решает сама».

Наследник **обязан** реализовать все абстрактные методы, если только он сам не `abstract`:

```java
class Circle extends Shape {
    private double radius;

    Circle(double radius) {
        this.radius = radius;
    }

    @Override
    double area() {
        return Math.PI * radius * radius;
    }
}
```

Теперь `new Circle(5)` работает, потому что `Circle` реализовал `area()`. А `new Shape()` — не работает, потому что `Shape` абстрактный.

**Важная деталь.** Абстрактный класс **может** содержать обычные (неабстрактные) методы и поля. Он не обязан быть «только абстрактным». Вот пример:

```java
abstract class Shape {
    private String color;

    Shape(String color) {
        this.color = color;
    }

    String getColor() {
        return color;
    }

    abstract double area();

    abstract double perimeter();

    void printInfo() {
        System.out.println("Фигура: " + getClass().getSimpleName()
            + ", цвет: " + color
            + ", площадь: " + area()
            + ", периметр: " + perimeter());
    }
}
```

Здесь `color`, `getColor()` и `printInfo()` — обычные, с реализацией. `area()` и `perimeter()` — абстрактные, без реализации. И это нормально: у всех фигур есть цвет (общее), но площадь и периметр каждая фигура считает по-своему (разное).

## Абстрактные методы

**Абстрактный метод** — это метод **без тела**. Он объявляет «что», но не «как». Реализацию предоставляют наследники.

```java
abstract double area();
```

Обратите внимание: **нет фигурных скобок**, только точка с запятой. Это не «пустое тело», это именно «нет тела». Разница важная: пустое тело (`{ }`) — это реализация, которая ничего не делает. Отсутствие тела — это «реализации нет, наследник обязан её дать».

**Правила.**

**Первое: абстрактный метод может быть только в абстрактном классе.** Нельзя написать `abstract`-метод в обычном классе. Логика простая: если у класса есть метод без реализации, — объект этого класса был бы «недоделанным», и его нельзя было бы создать. Значит, класс тоже должен быть абстрактным.

**Второе: наследник обязан реализовать все абстрактные методы.** Если не реализовал — он тоже должен быть `abstract`:

```java
abstract class Shape {
    abstract double area();
}

abstract class AbstractCircle extends Shape {
    // не реализует area() — поэтому тоже abstract
    protected double radius;
}

class Circle extends AbstractCircle {
    @Override
    double area() {
        return Math.PI * radius * radius;
    }
}
```

Здесь `AbstractCircle` не реализует `area()`, поэтому и сам должен быть `abstract`. А `Circle` реализует — и может быть обычным.

**Третье: абстрактный метод не может быть `private` или `final`.** `private` — потому что его не видно в наследниках, значит, они не смогут его реализовать. `final` — потому что его нельзя переопределить, значит, реализовать. Оба запрета логичны: абстрактный метод существует **только** для того, чтобы его реализовали, — а `private` и `final` мешают этому.

**Четвёртое: абстрактный метод не может быть `static`.** `static`-методы принадлежат классу, а не объекту, и не наследуются в обычном смысле. Абстрактный `static` не имеет смысла: его не нужно реализовывать в наследниках.

## Зачем нужны абстрактные классы

Абстрактные классы решают несколько задач, и все они — про **выражение намерения**.

### Выразить «это понятие, а не вещь»

Главная задача — сказать: «Это абстракция, конкретные реализации — в наследниках». `Shape` — это не «фигура вообще», это «понятие фигуры», и конкретная фигура — это всегда `Circle`, `Rectangle` или `Triangle`. Создавать `new Shape()` бессмысленно, и абстрактный класс это запрещает.

Это не просто синтаксическое удобство, это **коммуникация с читателем**. Когда вы видите `abstract class Shape`, — вы сразу понимаете: «Ага, это базовое понятие, работают с конкретными наследниками». Когда вы видите `class Shape` — вы не знаете, можно ли его создавать, и надо смотреть конструкторы и методы.

### Заставить наследников реализовать нужное

Абстрактный метод — это **обязательство**, которое родитель накладывает на наследников. «У тебя **должна** быть площадь, и ты **должен** уметь её считать». Если наследник забыл — компилятор не даст скомпилировать.

Это очень полезно: вы как автор базового класса гарантируете, что все наследники будут иметь нужный набор методов. И можете **использовать** эти методы в коде базового класса — как в `printInfo()` выше, где вызывается `area()`.

### Дать общую реализацию, но оставить место для своей

Абстрактный класс может содержать **и** общую реализацию (для всех), **и** абстрактные методы (для конкретных наследников). Это позволяет избежать дублирования кода: общее пишется один раз в базовом классе, специфичное — в каждом наследнике.

Например, `printInfo()` пишется один раз в `Shape` и работает для всех фигур, потому что вызывает абстрактные `area()` и `perimeter()`. Если бы не было абстрактного класса, — `printInfo()` пришлось бы дублировать в каждой фигуре (или выносить в утилитный класс).

### Обеспечить частичную реализацию

Иногда базовый класс знает, **что** делать, но не знает **как** в деталях. Абстрактный класс позволяет «заполнить» то, что известно, и оставить «дырки» для наследников. Это называется **шаблонный метод** (template method) — мы поговорим о нём в модуле 5, но идея уже видна: `printInfo()` — это шаблон, а `area()`/`perimeter()` — «дырки», которые заполняют наследники.

## Абстрактный класс vs обычный

Может возникнуть вопрос: зачем вообще абстрактный класс, если можно сделать обычный и просто не создавать его объекты? Например, написать `class Shape` с методом `area()`, который возвращает `0`, и никогда не делать `new Shape()`.

Причин, почему абстрактный класс лучше, несколько.

**Первая: компилятор проверяет.** Если вы сделали `Shape` обычным и забыли, что не надо создавать его объекты, — `new Shape()` скомпилируется, и вы получите бессмысленный объект. С `abstract` — не скомпилируется, и ошибка будет видна сразу.

**Вторая: намерение явное.** `abstract` говорит: «это не для создания, это для наследования». Без `abstract` приходится догадываться: а можно ли создавать `Shape`? А зачем он тогда нужен? `abstract` снимает эти вопросы.

**Третья: наследники обязаны.** Если `area()` в обычном `Shape` возвращает `0`, — наследник **может** его не переопределять, и тогда площадь будет `0`, что, скорее всего, не то, что нужно. С `abstract` — наследник **обязан** переопределить, иначе не скомпилируется. Ошибка ловится на этапе компиляции, а не в момент выполнения.

**Четвёртая: смысл.** «Фигура без площади» — это бессмыслица. `abstract` выражает это напрямую: «площадь есть у всех, но у каждой своя, и общей формулы нет».

Так что **абстрактный класс — это не «обычный класс с ограничениями», это другой инструмент**. Он говорит: «это понятие, а не вещь», и компилятор это проверяет.

## Когда абстрактный класс — плохая идея

Абстрактные классы полезны, но и у них есть тёмная сторона.

**Когда абстрактный класс «слишком умный».** Если в абстрактном классе много общей логики, — наследники оказываются жёстко привязаны к ней. Если завтра вы захотите поменять общую логику, — придётся менять базовый класс, и это может сломать всех наследников. Это «проблема хрупкого базового класса», о которой мы будем говорить в следующем уроке.

**Когда наследников слишком много.** Если у `Shape` десять наследников, и каждый переопределяет `area()` по-своему, — это нормально. А если у `Employee` пятьдесят наследников с разной логикой, — базовый класс становится «свалкой» общих методов, и разобраться в нём сложно.

**Когда абстрактный класс используется там, где хватило бы интерфейса.** В Java есть и абстрактные классы, и интерфейсы. У них разные роли, и мы будем говорить об этом в модуле 4. Пока что запомните: **абстрактный класс — для «общего понятия с общей реализацией», интерфейс — для «контракта без реализации»**. Если у вас нет общей реализации, — возможно, лучше интерфейс.

**Когда абстрактный класс «протекает».** Если абстрактный класс содержит конкретную логику, которая зависит от деталей наследников, — это признак того, что иерархия спроектирована неправильно. Например, если `printInfo()` в `Shape` знает, что у `Circle` есть радиус, и печатает его, — это уже не «общая логика», а «логика, которая знает про наследника». Абстрактный класс должен знать только про **свой** контракт, не про наследников.

Общее правило: **абстрактный класс — для случаев, когда есть общее понятие и общая реализация, которую наследники дополняют**. Если общей реализации нет, — это интерфейс. Если реализация есть, но она не должна быть общей, — это композиция. Мы будем говорить об этом подробнее в модуле 4 и 5.

## Аналогия, которая помогает

Хорошая аналогия — **шаблон резюме**.

Представьте, что у вас есть **шаблон резюме**: в нём есть разделы «О себе», «Опыт работы», «Образование», «Навыки». Шаблон задаёт **структуру**, но не содержание. Вы не можете «отправить шаблон» работодателю — это бессмысленно, там нет вашей информации. Вы **заполняете** шаблон своими данными и отправляете **заполненное** резюме.

**Абстрактный класс — это шаблон.** Он задаёт структуру: «в резюме должны быть такие-то разделы». Он не задаёт содержание — это делают наследники (ваши конкретные резюме).

**Абстрактные методы — это разделы, которые нужно заполнить.** «О себе» — это абстрактный метод: у каждого своё. «Опыт работы» — тоже. А вот «Формат» (например, «резюме должно быть в PDF») — это уже общая реализация, её не надо переопределять.

**Наследники — это конкретные резюме.** «Резюме Иванова», «Резюме Петрова». Каждое заполняет разделы по-своему. Но структура у всех одна — потому что она задана шаблоном.

**`new Shape()` — это как «отправить пустой шаблон».** Формально можно, но бессмысленно: работодатель не поймёт, что вы хотели сказать. Абстрактный класс это запрещает: «нельзя отправить пустой шаблон, заполните его».

И ещё одна мысль: **шаблон не обязан быть полным**. В нём могут быть разделы «обязательные» (абстрактные методы) и «опциональные» (обычные методы с реализацией по умолчанию). Наследник может переопределить опциональные, если хочет, но не обязан. Это гибкость, которую даёт абстрактный класс.

## Микрозадача 1

Вот код. Что произойдёт при компиляции? Объясните.

```java
abstract class Shape {
    abstract double area();
}

class Circle extends Shape {
    private double radius;

    Circle(double radius) {
        this.radius = radius;
    }
}
```

### Разбор

Код **не скомпилируется**. Компилятор скажет: «`Circle` не является абстрактным и не переопределяет абстрактный метод `area()` в `Shape`».

Причина: `Shape` объявляет `area()` как абстрактный. Значит, **любой** неабстрактный наследник обязан его реализовать. `Circle` этого не делает — значит, он тоже должен быть `abstract`. А он не `abstract` — значит, ошибка.

**Как исправить.** Вариантов два.

**Первый — реализовать `area()` в `Circle`:**

```java
class Circle extends Shape {
    private double radius;

    Circle(double radius) {
        this.radius = radius;
    }

    @Override
    double area() {
        return Math.PI * radius * radius;
    }
}
```

Это самый естественный вариант: `Circle` знает, как считать площадь, и делает это.

**Второй — сделать `Circle` абстрактным:**

```java
abstract class Circle extends Shape {
    protected double radius;

    Circle(double radius) {
        this.radius = radius;
    }
}
```

Тогда `Circle` — тоже «заготовка», и `area()` реализуют его наследники. Но это странно: `Circle` — это уже конкретная фигура, у неё есть конкретная формула площади. Скорее всего, второй вариант — не то, что нужно.

**Мораль.** Абстрактный метод — это **обязательство**, которое родитель накладывает на наследников. Если наследник не хочет (или не может) его выполнить, — он тоже должен быть абстрактным. Это гарантирует, что **любой** конкретный объект имеет все нужные методы, — и вызывающий код может на них рассчитывать.

## Микрозадача 2

Вот код. Он компилируется, но работает не так, как задумано. Найдите проблему.

```java
abstract class Animal {
    private String name;

    Animal(String name) {
        this.name = name;
        System.out.println("Создаём " + describe());
    }

    abstract String describe();
}

class Dog extends Animal {
    private String breed;

    Dog(String name, String breed) {
        super(name);
        this.breed = breed;
    }

    @Override
    String describe() {
        return "собаку породы " + breed;
    }
}

new Dog("Рекс", "овчарка");
```

### Разбор

Проблема — классическая ловушка, которую мы разбирали в уроке 3 модуля (про `super`): **вызов переопределённого метода из конструктора родителя**.

Смотрите, что происходит.

`new Dog("Рекс", "овчарка")` — начинается создание `Dog`. Java вызывает `super("Рекс")` — конструктор `Animal`.

В конструкторе `Animal` печатается `"Создаём " + describe()`. Здесь `describe()` — это **абстрактный метод**, который переопределён в `Dog`. Полиморфизм работает: вызывается `Dog.describe()`, а не какой-то «абстрактный» вариант (его и нет).

Но! В этот момент **конструктор `Dog` ещё не выполнился** — мы всё ещё «внутри» `Animal`. Поле `breed` у `Dog` ещё не инициализировано (оно получает значение по умолчанию `null`). Поэтому `Dog.describe()` возвращает `"собаку породы null"`.

Вывод:

```
Создаём собаку породы null
```

Хотя задумано было `"Создаём собаку породы овчарка"`.

**Как избежать.** Вариантов несколько, но все они — про то, чтобы **не вызывать переопределённые методы из конструктора**.

**Первый — сделать метод `final`:** если `describe()` нельзя переопределить, — вызов из конструктора безопасен (вызывается версия родителя). Но тогда `Dog` не сможет задать своё описание.

**Второй — передать описание в конструктор явно:**

```java
abstract class Animal {
    private String name;
    private String description;

    Animal(String name, String description) {
        this.name = name;
        this.description = description;
        System.out.println("Создаём " + description);
    }
}

class Dog extends Animal {
    private String breed;

    Dog(String name, String breed) {
        super(name, "собаку породы " + breed);
        this.breed = breed;
    }
}
```

Теперь описание передаётся явно, и конструктор `Animal` не вызывает `describe()`. Проблема исчезла.

**Третий — не печатать в конструкторе.** Пусть `printInfo()` будет отдельным методом, который вызывается **после** создания объекта:

```java
Dog dog = new Dog("Рекс", "овчарка");
dog.printInfo();   // здесь всё инициализировано
```

Тогда порядок инициализации не важен.

**Четвёртый — сделать поле `breed` инициализируемым в конструкторе родителя.** Но это уже не про `Dog`, а про `Animal`, и, возможно, неправильно с точки зрения дизайна.

**Мораль.** Вызов переопределённого метода из конструктора — **опасен**, потому что наследник может быть ещё не инициализирован. Это правило мы уже упоминали в уроке 3 (модуль про `super`) и в уроке 4 (модуль про переопределение), но здесь оно особенно наглядно: абстрактный метод в конструкторе — это именно вызов переопределённого метода, и он может привести к работе с `null`-полями. **Не вызывайте переопределяемые методы из конструктора** — это правило номер один для любого класса, который может быть расширен.

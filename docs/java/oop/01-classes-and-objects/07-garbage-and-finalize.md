# 7. Мусор и finalize

## Где вы это уже видели

В прошлых уроках мы много раз создавали объекты через `new`. Создавали пользователей, счета, корзины, термостаты. И почти никогда не задумывались: а что с ними происходит потом? Куда они деваются, когда программа про них забывает?

В языках вроде C или C++ этот вопрос стоит очень остро: каждый `malloc` требует `free`, каждый `new` — `delete`. Забыли освободить — утечка памяти. Освободили дважды — программа падает. Освободили слишком рано — данные испорчены. В Java этот груз с вас сняли. Но не полностью — есть нюансы, и о них стоит знать.

**Ситуация первая.** Вы выкидываете мусор из квартиры. Вы не следите за каждым фантиком: завели пакет, накопили — вынесли. Пока пакет не вынесли, мусор лежит в углу и занимает место. А как только вынесли — место освободилось. И вы не думаете о судьбе каждого конкретного фантика: он либо в пакете, либо уже на свалке.

**Ситуация вторая.** Вы удаляете приложение с телефона. Иконка исчезает, приложение больше не запускается, а через какое-то время система сама подчищает его данные. Вы не удаляете каждый файл по отдельности — вы просто говорите «этого больше нет», и система разбирается.

**Ситуация в третьей.** Вы работаете с гуглодоком и удаляете документ. Он попадает в корзину. Через тридцать дней Google сам его удалит — без вашего участия. А если вы захотите удалить сразу — есть кнопка «Удалить навсегда». Но чаще всего вы просто забываете про документ, и через месяц его нет. Система сама разобралась.

**Ситуация четвёртая.** Вы снимаете квартиру. Когда вы съезжаете — хозяин проверяет, не оставили ли вы после себя мусор. Это и есть аналог `finalize`: «сделай что-нибудь перед тем, как объект уйдёт». Только в Java это работает плохо — и в этом уроке мы поймём почему.

**Ситуация пятая.** Вы забыли закрыть кран. Вода льётся, счётчик крутится. С точки зрения «водопровод работает» — всё в порядке, вода идёт. Но с точки зрения вашего кошелька — это утечка. В программах так же: память вроде бы есть, но что-то её занимает и не отдаёт.

**Ситуация шестая.** Вы вызываете `System.gc()` в коде и надеетесь, что теперь память освободится. А программа продолжает падать с `OutOfMemoryError`. Вы не понимаете: я же попросил! Я же вызвал! Почему не работает?

Если последняя ситуация вам знакома — этот урок для вас. Если остальные тоже — отлично, интуиция про «само разберётся» у вас уже есть, осталось разобраться с деталями.

## Зачем вообще нужен сборщик мусора

Вспомним из урока про ссылки: объект живёт в куче, а переменная хранит ссылку на него. Пока на объект есть хотя бы одна ссылка — объект «жив»: к нему можно обратиться, что-то с ним сделать. Как только ссылок не осталось — объект становится недостижимым. К нему больше нельзя обратиться, потому что вы не знаете, где он, и никто не знает.

Такой объект — это и есть мусор. Он занимает память, но никому не нужен. И если его не убрать, память будет заполняться, пока программа не упадёт с `OutOfMemoryError`.

**Сборщик мусора** (garbage collector, GC) — это часть JVM, которая время от времени проходит по куче и удаляет объекты, на которые больше нет ссылок. Вы этого не видите: это происходит в фоне, автоматически, без вашего участия.

Ключевая идея: **вы не управляете памятью напрямую**. Вы не говорите «удали этот объект». Вы просто перестаёте на него ссылаться — и рано или поздно сборщик мусора заметит это и освободит память.

Вот простой пример:

```java
User alice = new User("Алиса", "alice@example.com");
alice = null;
```

После `alice = null` в переменной больше нет ссылки на объект. Если на этот объект никто другой не ссылается, он стал мусором. Через какое-то время (не сразу!) сборщик мусора его удалит.

Другой пример:

```java
void doSomething() {
    User bob = new User("Боб", "bob@example.com");
    // ... что-то делаем с bob ...
}
// после выхода из метода локальная переменная bob исчезает,
// и если на объект больше никто не ссылается — он становится мусором
```

Здесь `bob` — локальная переменная. После выхода из метода она исчезает (стек очищается), и ссылка на объект теряется. Объект становится мусором.

И ещё пример:

```java
User alice = new User("Алиса", "alice@example.com");
alice = new User("Другая Алиса", "other@example.com");
```

Здесь произошло то же самое: `alice` сначала указывала на первый объект, потом — на второй. Первый объект больше никому не нужен (на него нет ссылок) и становится мусором.

## Когда объект становится мусором

Точного момента, когда объект «превращается» в мусор, не существует. Есть момент, когда на объект больше нет ссылок — с этого момента он **достижим только через мусор**, если так можно выразиться. И есть момент, когда сборщик мусора его реально удаляет — это может произойти через миллисекунду, а может через час, в зависимости от того, когда GC решит пройтись.

Важно понять одну вещь: **«нет ссылок» и «удалён» — это разные вещи**. Между ними может пройти много времени, и в течение этого времени объект занимает память. Это нормально, и в большинстве случаев не является проблемой.

Есть исключения, о которых стоит знать.

**`static`-поля.** Помните из прошлого урока, что `static`-поле живёт всё время работы программы? Так вот: если `static`-поле хранит ссылку на объект, этот объект **никогда не станет мусором**. Пока класс загружен (а он загружен всегда), ссылка из `static`-поля считается «живой». Это одна из самых частых причин утечек памяти в Java: разработчик хранит что-то в `static`-коллекции, забывает удалять, и память постепенно забивается.

```java
class Cache {
    static Map<String, User> users = new HashMap<>();

    static void remember(User user) {
        users.put(user.email, user);
    }
}
```

Каждый вызов `remember` добавляет пользователя в `static`-коллекцию. И этот пользователь уже никогда не станет мусором — даже если весь остальной код про него забыл. Потому что `Cache.users` на него ссылается.

**Долгоживущие коллекции.** Та же проблема, но не через `static`, а через объекты, которые живут долго. Например, у вас есть объект `Application`, который живёт всю программу, и в нём есть `Map<String, Session>` — все сессии пользователей. Если вы не удаляете сессии из этой коллекции, они накапливаются. Это тоже утечка.

**Забытые слушатели (listeners).** Классика: объект подписался на события другого объекта, но забыл отписаться. Первый объект живёт долго, второй — уже нет, но первый продолжает держать ссылку на второго. Второй не становится мусором. Утечка.

Общий принцип такой: **объект становится мусором, когда на него нет ссылок**. Если ссылка есть, но вы про неё забыли (например, она лежит в `static`-коллекции), объект остаётся в памяти. Это и есть утечка — не в смысле «сборщик мусора не работает», а в смысле «вы сами держите ссылку, о которой не помните».

## Почему System.gc() — плохая идея

Иногда хочется «помочь» сборщику мусора: вызвать `System.gc()` и заставить его убраться прямо сейчас. Не делайте так.

Во-первых, `System.gc()` — это **всего лишь просьба**. JVM может её проигнорировать, если считает, что сейчас не время. В некоторых конфигурациях (например, с флагом `-XX:+DisableExplicitGC`) она игнорируется полностью.

Во-вторых, даже если JVM согласится, полный проход сборщика — это **дорогая операция**. Она останавливает часть программы (в некоторых сборщиках — вообще всю программу на время прохода). Вызов `System.gc()` в неподходящий момент может вызвать заметные паузы и ухудшить производительность.

В-третьих, **вы почти никогда не знаете лучше**. Современные сборщики мусора (G1, ZGC, Shenandoah) очень умные. Они сами решают, когда и что убирать, основываясь на статистике и профиле нагрузки. Ваш «помощь» скорее помешает, чем поможет.

Правило простое: **не вызывайте `System.gc()`**. Если вам кажется, что нужен явный вызов, — скорее всего, проблема в другом (утечка, или вы держите много объектов одновременно). Ищите причину, а не лечите симптом.

## finalize — почему он плохой

Теперь про `finalize`. Это метод, который **когда-то** (в старых версиях Java) вызывался сборщиком мусора **перед удалением объекта**. Идея была такая: «вот тебе шанс сделать что-то перед уходом». Закрыть файл, освободить ресурс, попрощаться.

Звучит разумно. На практике оказалось, что `finalize` — почти всегда плохая идея, и вот почему.

**Он может не вызваться.** Совершенно не гарантируется, что `finalize` будет вызван до завершения программы. Если программа завершается, а объект ещё не успел стать мусором — `finalize` не вызовется вообще. Если JVM решит, что не будет вызывать `finalize`, — он не вызовется. Гарантий ноль.

**Он может вызваться в любой момент.** Между моментом, когда объект стал недостижим, и моментом, когда `finalize` вызвался, может пройти произвольное время. Объект уже мусор, но ресурсы, которые он держит (например, файл), ещё не освобождены. Это может привести к исчерпанию файловых дескрипторов, соединений с базой и других ресурсов.

**Он может «воскресить» объект.** Внутри `finalize` можно сохранить `this` куда-нибудь в статическое поле — и объект снова станет достижимым. Сборщик мусора это увидит и не удалит объект. Такое «воскрешение» формально разрешено, но почти всегда означает баг.

**Он плохо работает с наследованием.** `finalize` в подклассе должен вызывать `super.finalize()`. Если забыть — ресурсы родителя не освободятся. Легко забыть, легко ошибиться.

**Он создаёт проблемы с производительностью.** Объекты, у которых есть `finalize`, требуют дополнительной обработки. Сборщик мусора должен их отслеживать, откладывать удаление, вызывать `finalize` — это дорого.

**Он устарел.** Начиная с Java 9 метод `finalize` помечен как `deprecated`. В Java 18 он помечен `forRemoval` — то есть его **планируют удалить** в будущих версиях языка. Использовать его сегодня — значит писать код, который сломается завтра.

Короткий вывод: **не используйте `finalize`**. Никогда. Если вы видите его в чужом коде — это повод переписать.

## Как освобождать ресурсы правильно

Тогда как же быть с ресурсами? Ведь если объект держит файл или соединение с базой, нужно же их закрыть?

Нужно. Но не через `finalize`, а через **явное закрытие**. В Java для этого есть два механизма, и они оба гораздо надёжнее.

**Способ первый — `try-with-resources`.** Если объект реализует интерфейс `AutoCloseable` (или его подинтерфейс `Closeable`), его можно использовать в `try-with-resources`, и Java сама вызовет `close()` в конце блока — даже если было исключение:

```java
try (FileInputStream file = new FileInputStream("data.txt")) {
    // читаем файл
} // здесь file.close() вызовется автоматически
```

Это самый надёжный и самый рекомендуемый способ. Он гарантирует закрытие, не требует от вас помнить о `finally`, и хорошо читается.

**Способ второй — явный `close()`.** Если `try-with-resources` по каким-то причинам не подходит (например, ресурс живёт дольше одного метода), закрывайте его явно:

```java
FileInputStream file = new FileInputStream("data.txt");
try {
    // читаем файл
} finally {
    file.close();
}
```

Или, если ресурс живёт долго и вы точно знаете, когда он должен быть закрыт:

```java
class FileReader {
    private FileInputStream file;

    FileReader(String path) throws IOException {
        this.file = new FileInputStream(path);
    }

    void close() throws IOException {
        if (file != null) {
            file.close();
            file = null;
        }
    }
}
```

Клиент такого класса должен сам вызвать `close()`. И это нормально: **ответственность за ресурсы лежит на том, кто их создал или получил**. Если объект держит файл — тот, кто создал объект, должен позаботиться о закрытии. Не `finalize`, не сборщик мусора, а вы.

Кстати, тот же принцип работает и для других ресурсов: соединений с базой, сетевых сокетов, потоков. Везде, где есть «открыть» — должно быть «закрыть», и делать это нужно явно.

## Аналогия, которая помогает

Хорошая аналогия — **гостиница и горничная**.

Представьте, что программа — это гостиница. Объекты — это номера. Вы (программа) время от времени заселяетесь в номера и выселяетесь из них.

**Сборщик мусора — это горничная.** Она ходит по этажам и смотрит: в каких номерах никого нет, но вещи остались. Такие номера она убирает: выбрасывает забытые вещи, проветривает, готовит номер для следующего гостя. Вы не зовёте горничную каждый раз, когда выезжаете: она приходит по расписанию, когда накопится работа.

**Вы не управляете горничной.** Вы не можете сказать «приди прямо сейчас и убери номер 305». Точнее, можете попросить (`System.gc()`), но она может ответить «у меня сейчас другие дела» или «я приду, когда сочтёт нужным». И это нормально: вы всё равно не знаете, в каком номере сейчас кто-то есть.

**`finalize` — это гость, который оставил записку: «если я вдруг уйду и забуду вещи, позвоните мне, я вернусь и заберу».** Красиво звучит, но работает плохо: горничная может не заметить записку, может позвонить через неделю, а может — вообще не позвонить. И тогда вещи гостя остаются в номере, занимают место, и никто не может их убрать.

**Правильный способ — это когда гость сам забирает вещи перед выездом.** Платит по счёту, забирает чемодан, оставляет ключи. Тогда горничной не нужно ничего решать: номер пустой, можно убирать. Это и есть `try-with-resources` или явный `close()`.

И ещё одна параллель: **гостиница не бесконечна**. Если номера не освобождаются, рано или поздно новых гостей некуда будет селить. Так и с памятью: если объекты накапливаются, программа падает с `OutOfMemoryError`. Сборщик мусора помогает, но только если вы сами не держите номера занятыми «на всякий случай» — через `static`-коллекции и забытые ссылки.

## Микрозадача 1

Вот код. Сколько объектов станут мусором после его выполнения? Для каждого объекта объясните, почему.

```java
class Item {
    String name;
    Item(String name) { this.name = name; }
}

Item a = new Item("Первый");
Item b = new Item("Второй");
Item c = a;
a = new Item("Третий");
b = c;
c = null;
```

### Разбор

Пройдёмся по шагам.

`Item a = new Item("Первый");` — создан объект №1 («Первый»). `a` ссылается на него.

`Item b = new Item("Второй");` — создан объект №2 («Второй»). `b` ссылается на него.

`Item c = a;` — `c` теперь ссылается на объект №1. `a` и `c` указывают на один объект.

`a = new Item("Третий");` — создан объект №3 («Третий»). `a` теперь ссылается на него. На объект №1 всё ещё ссылается `c`, так что он пока жив.

`b = c;` — `b` теперь ссылается на объект №1 (как и `c`). Объект №2 («Второй») больше никому не нужен — на него нет ссылок. **Объект №2 становится мусором.**

`c = null;` — `c` никуда не ссылается. Но объект №1 всё ещё доступен через `b`.

Итог: **мусором стал один объект — «Второй»**. Объекты «Первый» и «Третий» живы: «Первый» доступен через `b`, «Третий» — через `a`. Ссылка `c` больше ни на что не указывает, но это не делает объект «Первый» мусором, потому что на него всё ещё смотрит `b`.

Обратите внимание, как легко ошибиться в такой задаче, если не проследить все ссылки. И как это, кстати, показывает, почему утечки памяти — не такая уж редкая штука: одна забытая ссылка — и объект остаётся в памяти, хотя вы про него уже не помните.

## Микрозадача 2

Вот класс, который якобы «умеет» закрывать файл при удалении. Найдите в нём три проблемы.

```java
class FileWrapper {
    private FileInputStream file;

    FileWrapper(String path) throws IOException {
        this.file = new FileInputStream(path);
    }

    @Override
    protected void finalize() throws Throwable {
        file.close();
        super.finalize();
    }
}
```

### Разбор

Три проблемы, все — классические.

**Первая: `finalize` вообще может не вызваться.** Как мы обсуждали, гарантий ноль. Если программа завершится до того, как объект станет мусором, — `close` не будет вызван. А если программа работает долго и объектов таких много — файлы могут остаться открытыми дольше, чем нужно.

**Вторая: `finalize` может вызваться с задержкой.** Между моментом, когда объект стал недостижим, и вызовом `finalize` может пройти много времени. Всё это время файл открыт. Если файлов много — можно исчерпать лимит на количество открытых файлов в системе (обычно 1024 или 4096 на процесс), и программа начнёт падать с ошибкой «too many open files».

**Третья: `file.close()` может бросить исключение, и это исключение потеряется.** Если `close` выбросит `IOException` (а он может — например, если файл уже закрыт или диск отвалился), это исключение никто не перехватит. Оно будет проигнорировано сборщиком мусора, и вы даже не узнаете, что что-то пошло не так.

Правильный вариант — реализовать `AutoCloseable`:

```java
class FileWrapper implements AutoCloseable {
    private FileInputStream file;

    FileWrapper(String path) throws IOException {
        this.file = new FileInputStream(path);
    }

    @Override
    public void close() throws IOException {
        if (file != null) {
            file.close();
            file = null;
        }
    }
}
```

И использовать через `try-with-resources`:

```java
try (FileWrapper wrapper = new FileWrapper("data.txt")) {
    // работаем с wrapper
} // close() вызовется автоматически, даже при исключении
```

Или, если ресурс живёт дольше одного метода, — вызывать `close()` явно. В любом случае это будет **гарантированно**, а не «когда-нибудь, может быть».

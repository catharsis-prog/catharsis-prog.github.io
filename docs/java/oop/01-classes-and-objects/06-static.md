# 6. static

## Где вы это уже видели

До сих пор всё, о чём мы говорили, принадлежало объектам. У Алисы своё имя, у Боба своё. У одной корзины три товара, у другой — пять. Это естественно: объект — это конкретная вещь, и у каждой вещи свои свойства.

Но иногда нужно, чтобы что-то было **одно на всех**. Одна константа, общая для всех объектов класса. Один счётчик, который считает всех созданных пользователей. Один метод, который не зависит ни от какого конкретного объекта. Для этого в Java есть ключевое слово `static`.

Прежде чем идти в код, посмотрим, где эта идея встречается в жизни.

**Ситуация первая.** Вы работаете в компании, и у неё есть юридический адрес. Он один на всех сотрудников — не у каждого свой. У Иванова может быть свой домашний адрес, у Петрова свой, а юридический адрес компании — общий. Если компания переедет, это затронет всех сразу. Это `static`-поле: одно значение, общее для всех объектов класса «Компания».

**Ситуация вторая.** Вы считаете, сколько людей вошло в комнату. Каждый человек — отдельный, со своим именем и своей историей. Но счётчик «сколько вошло» — один. Он не принадлежит ни одному конкретному человеку, он принадлежит самой комнате. И увеличивается при входе каждого. Это `static`-поле: счётчик, общий для всех экземпляров класса.

**Ситуация третья.** Вы пользуетесь калькулятором. У калькулятора нет «своего» числа — числа вы вводите сами. Операция «сложить два числа» не зависит от того, какой у вас калькулятор: если у вас и у друга одинаковые калькуляторы, `2 + 3` даст `5` в обоих. Функция сложения — общая для всех калькуляторов. Это `static`-метод: действие, не привязанное к конкретному объекту.

**Ситуация четвёртая.** Вы смотрите на курс валют. Он один на всю страну — не у каждого человека свой. У вас может быть свой кошелёк, свои накопления, свои расходы — но курс доллара к рублю один. Если он изменится, это затронет всех. Это `static`-поле: глобальная константа, общая для всех.

**Ситуация пятая.** Вы видите на двери офиса табличку «Компания "Ромашка", ИНН такой-то». На табличке — информация, которая относится ко всей компании, а не к конкретному сотруднику. Внутри офиса у каждого сотрудника свой стол, свой компьютер, свои бумаги. Но ИНН на входе — один на всех. Это `static`-поле: атрибут класса, а не экземпляра.

**Ситуация шестая.** Вы пишете код и видите `Math.PI` или `Integer.parseInt("42")`. И не понимаете: почему у `Math` и `Integer` нет объектов, но методы вызываются? Почему `Math.PI` работает, хотя `Math` — это класс, а не объект? Это `static` в действии: `Math` — это класс, у которого все методы и константы статические, и объект `Math` вам вообще не нужен.

Если последняя ситуация вам знакома — этот урок для вас. Если остальные тоже — отлично, интуиция про «общее для всех» у вас уже есть, осталось связать её с синтаксисом.

## Что значит static

**`static` — это ключевое слово, которое говорит: «этот член принадлежит классу, а не объекту»**. То есть он существует **один на весь класс**, а не по одному на каждый объект.

Сравните два поля:

```java
class User {
    static int totalCount;   // одно на всех
    String name;             // своё у каждого
}
```

`name` — это поле объекта. У каждого пользователя своё имя. Если у вас три пользователя — три разных `name`.

`totalCount` — это поле класса. Оно одно на весь класс `User`. Если у вас три пользователя, `totalCount` всё равно один. Его значение общее.

Вот как это выглядит в коде:

```java
class User {
    static int totalCount = 0;
    String name;

    User(String name) {
        this.name = name;
        totalCount++;
    }
}

User alice = new User("Алиса");
User bob = new User("Боб");
User carol = new User("Кэрол");

System.out.println(User.totalCount);   // 3
```

Обратите внимание: `totalCount` увеличивается в конструкторе каждого объекта — но хранится в одном месте. Все три конструктора писали в **одну и ту же** переменную, а не в три разных. Это и есть смысл `static`: одно значение, доступное всем объектам класса, и не привязанное ни к одному конкретному.

Кстати, обратите внимание на способ доступа: `User.totalCount`, а не `alice.totalCount`. Хотя технически можно написать и `alice.totalCount` — Java не запретит, — правильнее обращаться через имя класса. Потому что `totalCount` не принадлежит Алисе, он принадлежит классу `User`, и обращаться к нему логичнее через класс.

## Как static устроен в памяти

Полезно понимать, где именно живёт `static`-поле. Помните из прошлого урока, что объекты живут в куче, а локальные переменные — в стеке? Так вот, **`static`-поля живут в отдельной области памяти**, которая называется «metaspace» (в современных версиях Java; раньше это была «область методов»). Она не привязана ни к стеку, ни к конкретному объекту в куче.

У этого есть несколько последствий, которые полезно держать в голове.

**`static`-поле существует, даже если объектов нет.** Даже если вы не создали ни одного `User`, `User.totalCount` существует и равен `0`. Поле класса существует всё время, пока загружен класс, а не только пока есть объекты.

**`static`-поле живёт всё время работы программы.** Объект можно собрать сборщиком мусора, когда на него больше нет ссылок. А `static`-поле не собирается: оно живёт, пока загружен класс, то есть практически всю программу. Это одна из причин, почему `static`-поля надо использовать с осторожностью: они не освобождаются.

**`static`-поле общее для всех.** Если один объект изменил `totalCount`, это изменение видно всем. Это и хорошо (счётчик работает как надо), и потенциально плохо (можно случайно испортить общее состояние).

## static-методы

Методы тоже могут быть `static`. И правила у них похожие: **`static`-метод принадлежит классу, а не объекту**. Чтобы его вызвать, не нужен объект — достаточно имени класса.

```java
class MathUtils {
    static int max(int a, int b) {
        return a > b ? a : b;
    }
}

int result = MathUtils.max(5, 10);   // 10
```

Здесь `MathUtils.max(5, 10)` — вызов `static`-метода. Объект `MathUtils` не создаётся, он и не нужен. Метод — это просто функция, привязанная к классу для порядка.

У `static`-методов есть важное ограничение, о котором нужно помнить: **внутри `static`-метода нельзя обращаться к нестатическим полям и методам**. Почему — сейчас объясню, но сначала пример.

```java
class User {
    static int totalCount = 0;
    String name;

    static void printTotal() {
        System.out.println(totalCount);    // можно — totalCount статическое
        // System.out.println(name);       // нельзя — name нестатическое
    }
}
```

Строка `System.out.println(name)` не скомпилируется. Компилятор скажет что-то вроде «нестатическая переменная `name` не может быть использована из статического контекста». И это логично: `name` — это поле **конкретного объекта**. У какого именно объекта `printTotal` должен взять `name`, если `printTotal` — метод класса, и объекта у него нет? Непонятно. Поэтому и нельзя.

Если нужно, чтобы `static`-метод работал с полем объекта, этот объект нужно передать ему явно:

```java
static void printName(User user) {
    System.out.println(user.name);
}
```

— вот теперь всё честно: метод принимает объект как параметр и работает с его полем. Никакой магии.

## Обратная сторона: static-метод не видит this

Собственно, вот и объяснение, почему из `static`-метода нельзя обратиться к полям объекта. Помните, в прошлых уроках мы говорили, что внутри каждого нестатического метода невидимо передаётся `this` — ссылка на текущий объект? Так вот: **в `static`-методе `this` нет**. У него нет «текущего объекта», потому что он вызывается через класс, а не через объект.

Поэтому в `static`-методе нельзя написать `this.name` — компилятор не поймёт, о каком объекте речь. И нельзя вызвать нестатический метод — потому что и он неявно работает с `this`.

Это, кстати, полезный маркер: **если вы пишете метод и не используете `this` ни в явном, ни в неявном виде (то есть не обращаетесь к полям и нестатическим методам), — возможно, этот метод стоит сделать статическим**. Он не зависит от объекта, и незачем делать вид, что зависит.

## Константы и static final

Самое частое применение `static` — это **константы**. Константа — это значение, которое не меняется и общее для всех.

```java
class Circle {
    static final double PI = 3.141592653589793;

    double radius;

    double area() {
        return PI * radius * radius;
    }
}
```

Здесь `PI` — это `static final`: одно значение, общее для всех кругов, и его нельзя изменить. `final` говорит «не присваивать повторно», `static` — «одно на класс». Вместе получается то, что в других языках называют просто «константа».

Константы обычно пишут заглавными буквами — это соглашение, которого придерживается вся Java. Если вы видите `MAX_SIZE`, `DEFAULT_TIMEOUT`, `PI` — это почти наверняка `static final`-поле.

И ещё одна деталь: **`static final` для примитивов и `String` — это настоящие константы**, известные компилятору. Для объектов — уже не совсем. `static final List<String> EMPTY_LIST = new ArrayList<>();` — это `static final`-ссылка, но содержимое списка можно менять (`EMPTY_LIST.add(...)` скомпилируется и сработает). Так что `final` защищает только саму ссылку, а не объект, на который она указывает. Об этом мы будем говорить в модуле про неизменяемость, а пока просто запомните: **`final` не делает объект неизменяемым, он делает неизменяемой переменную**.

## Когда static — плохая идея

Теперь важная часть, которую часто пропускают в учебниках. `static` удобен, но у него есть **тёмная сторона**, и она проявляется в больших программах.

**Проблема первая: это глобальное состояние.** `static`-поле — это, по сути, глобальная переменная с приятным синтаксисом. Все проблемы, о которых мы говорили в первом уроке (процедурный подход и его пределы), возвращаются: любая часть программы может изменить `static`-поле, и проследить, кто и когда это сделал, становится трудно.

Вот пример, который встречается чаще, чем хотелось бы:

```java
class Config {
    static String apiUrl = "https://api.example.com";
}

class SomeService {
    void doSomething() {
        Config.apiUrl = "https://staging.example.com";   // поменяли для теста
    }
}

class AnotherService {
    void doSomethingElse() {
        HttpClient.get(Config.apiUrl);   // а тут уже staging, и никто не понял почему
    }
}
```

Один класс поменял глобальную настройку — и это повлияло на другой класс, который вообще не подозревал. Точно та же проблема, что с глобальными переменными в процедурном коде. `static` её не решает, он её маскирует.

**Проблема вторая: трудно тестировать.** Если `static`-поле используется в нескольких местах, то для теста нужно аккуратно выставить его в нужное состояние и потом сбросить. Иначе тесты начнут влиять друг на друга. Это неудобно и чревато «мигающими» тестами — которые иногда проходят, иногда нет, в зависимости от порядка запуска.

**Проблема третья: трудно менять.** Если код везде обращается к `User.totalCount` напрямую, то заменить это на что-то более гибкое (например, на счётчик, который передаётся в конструктор) — большая работа. `static` создаёт жёсткие связи между классами.

Из этого следует простое правило, которое стоит запомнить: **`static` уместен для констант, для утилитных функций (которые не зависят от состояния) и для счётчиков создания объектов**. Во всех остальных случаях — подумайте дважды. Скорее всего, вы хотите не `static`, а что-то другое.

## Утилитные классы

Отдельно стоит поговорить про **утилитные классы** — классы, которые целиком состоят из `static`-методов и не предполагают создания объектов. Классический пример — `java.lang.Math`:

```java
int max = Math.max(5, 10);
double pi = Math.PI;
double sqrt = Math.sqrt(2);
```

Объект `Math` никогда не создаётся. Все методы и константы — статические. Это удобно: у нас есть набор математических функций, и незачем каждый раз создавать объект, чтобы их вызвать.

Ещё примеры из стандартной библиотеки: `Integer.parseInt`, `String.valueOf`, `Arrays.sort`, `Collections.emptyList`. Все они — `static`-методы утилитных классов.

Есть два подхода к тому, как писать утилитные классы. Первый — просто класс со `static`-методами, как `Math`. Второй — класс со `static`-методами и **приватным конструктором**, чтобы никто случайно не создал объект:

```java
class StringUtils {
    private StringUtils() {
        // чтобы никто не создал new StringUtils()
    }

    static boolean isBlank(String s) {
        return s == null || s.trim().isEmpty();
    }
}
```

Приватный конструктор здесь — это вежливое «пожалуйста, не создавайте меня». Он не обязателен, но делает намерение явным. Если кто-то напишет `new StringUtils()`, компилятор сразу скажет: «нельзя». И это лучше, чем через полгода объяснять коллеге, почему `new StringUtils()` бессмысленно.

## Аналогия, которая помогает

Хорошая аналогия — **доска объявлений в офисе**.

Представьте офис. У каждого сотрудника есть свой стол, свой компьютер, свои бумаги. Это объекты и их поля. Всё это личное, у каждого своё.

А ещё в офисе есть **доска объявлений**. Она одна на весь офис. На ней висит информация, которая касается всех: график работы, правила, объявления. Каждый сотрудник может подойти и прочитать. И если кто-то поменяет объявление — увидят все.

**`static`-поле — это то, что висит на доске.** Одно на всех, не принадлежит ни одному сотруднику.

**`static`-метод — это действие, которое не привязано к конкретному столу.** Например, «прочитать объявление» — вы можете это сделать, не подходя к своему столу. «Написать объявление» — тоже. А вот «взять свою ручку» — уже нет, ручка у вас на столе, и без стола её не взять.

И вот важная деталь: **если на доске кто-то поменял объявление, это может сбить с толку всех остальных**. Сотрудник Иванов поменял «обед с 13:00» на «обед с 12:00», потому что у него встреча, — а Петров и Сидоров пришли в 13:00, и обед уже прошёл. Это та самая проблема глобального состояния, о которой мы говорили.

Поэтому доска — удобна, но с ней нужно обращаться аккуратно. **На доску вешают то, что действительно общее и меняется редко** (правила, константы), а не то, что у каждого своё (личные дела, текущие задачи). Аналогично, `static` — для констант и утилит, а не для того, что по сути своей принадлежит объектам.

## Микрозадача 1

Вот класс. Ответьте: сколько `static`-полей в нём, и что будет выведено в конце?

```java
class Counter {
    static int total = 0;
    int value = 0;

    Counter() {
        total++;
        value++;
    }
}

Counter a = new Counter();
Counter b = new Counter();
Counter c = new Counter();

System.out.println(Counter.total);
System.out.println(a.value);
System.out.println(b.value);
System.out.println(c.value);
```

### Разбор

**`static`-поле здесь одно** — `total`. Поле `value` — нестатическое, оно своё у каждого объекта.

Что происходит по шагам.

`Counter a = new Counter();` — создан объект №1. Конструктор: `total++` (общий счётчик стал 1), `value++` (у объекта №1 `value = 1`).

`Counter b = new Counter();` — создан объект №2. Конструктор: `total++` (общий счётчик стал 2), `value++` (у объекта №2 `value = 1`).

`Counter c = new Counter();` — создан объект №3. Конструктор: `total++` (общий счётчик стал 3), `value++` (у объекта №3 `value = 1`).

Итого:

```
3
1
1
1
```

Три объекта — три разных `value`, каждая равна 1. Плюс одно общее `total`, равное 3. Классическая пара «статический счётчик + личное значение».

## Микрозадача 2

Вот код с ошибкой компиляции. Найдите её и объясните, почему она возникает.

```java
class Greeter {
    String greeting = "Привет";

    static void sayHello() {
        System.out.println(greeting + ", мир!");
    }
}
```

### Разбор

Ошибка в том, что `sayHello` — `static`-метод, а обращается к `greeting` — нестатическому полю. Это запрещено, и вот почему.

`static`-метод не имеет доступа к `this`. У него нет «текущего объекта». А `greeting` — это поле конкретного объекта. У какого именно объекта `sayHello` должен взять `greeting`, если `sayHello` — метод класса, и объекта у него нет?

Компилятор это ловит и не даёт скомпилировать программу. Хорошо, что так: если бы он пропустил, что было бы? Пришлось бы гадать, чей `greeting` использовать. Неопределённость, которую лучше не допускать.

Есть три способа исправить.

**Способ первый — сделать `greeting` статическим:**

```java
class Greeter {
    static String greeting = "Привет";

    static void sayHello() {
        System.out.println(greeting + ", мир!");
    }
}
```

Тогда `greeting` — общее для всех, и `sayHello` может его использовать. Минус: теперь `greeting` один для всех объектов класса, и если вы захотите разные приветствия — не получится.

**Способ второй — сделать `sayHello` нестатическим:**

```java
class Greeter {
    String greeting = "Привет";

    void sayHello() {
        System.out.println(greeting + ", мир!");
    }
}
```

Тогда `sayHello` работает с `greeting` того объекта, через который его вызвали. Минус: чтобы сказать «привет», нужно создать объект. Для чего-то простого это лишнее.

**Способ третий — передать объект параметром:**

```java
class Greeter {
    String greeting = "Привет";

    static void sayHello(Greeter greeter) {
        System.out.println(greeter.greeting + ", мир!");
    }
}
```

Тогда метод остаётся статическим, но работает с явно переданным объектом. Минус: вызывающему коду нужно передавать объект, что не всегда удобно.

Какой способ выбрать — зависит от задачи. Если приветствие должно быть одинаковым для всех — первый. Если у каждого объекта своё — второй (или третий, если по каким-то причинам нужен именно `static`). В 90% случаев правильный ответ — **второй**: сделать метод нестатическим. Потому что «приветствие» — это характеристика объекта, а не класса, и логично, чтобы метод, использующий его, тоже был методом объекта.

## Самостоятельная задача

Спроектируйте класс `Product` для интернет-магазина, в котором есть счётчик созданных товаров.

Подумайте:

- какие поля будут статическими, а какие — нет;
- как увеличивать счётчик при создании товара;
- нужен ли метод для получения значения счётчика — и если да, статический он или нет;
- что должно происходить, если товар удаляется (счётчик уменьшается или нет?);
- как бы вы протестировали, что счётчик работает правильно, если тестов много и они запускаются подряд.

Затем ответьте на вопрос: если два разных теста создают товары, и оба проверяют значение `Product.getCounter()`, — будут ли они влиять друг на друга? И если да, как этого избежать?

Готового ответа не будет. Если хотите свериться — загляните в следующий урок про мусор и `finalize`: там мы поговорим о том, что происходит с объектом, когда на него больше нет ссылок, и вы увидите, насколько ваша интуиция про жизненный цикл совпала с тем, как это устроено на самом деле.

## Что дальше

Мы разобрались, что такое `static` и когда он полезен, а когда — вреден. В следующем уроке — **«Мусор и `finalize`»** — мы поговорим о том, что происходит с объектом в конце его жизни. Java не требует от вас явно освобождать память — за это отвечает сборщик мусора. Но это не значит, что можно вообще не думать о жизненном цикле объектов: есть нюансы, и о них стоит знать.

А пока — маленькое упражнение на наблюдательность. Найдите в своём проекте (или в стандартной библиотеке) класс, у которого есть `static`-поле. Посмотрите, что это за поле: константа? счётчик? кэш? настройка? Подумайте: а можно ли было обойтись без `static`? Если да — почему выбрали именно его? Если нет — что именно в этом поле «общее для всех»? Это упражнение хорошо проясняет, где `static` действительно нужен, а где — просто привычка.

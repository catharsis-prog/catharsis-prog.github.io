# 4. Конструкторы

## Где вы это уже видели

В прошлых уроках мы создавали объекты так: сначала `new User()`, а потом отдельными строчками заполняли поля — `alice.name = "Алиса"` и так далее. Это работает, но есть одна неловкость: между моментом, когда объект создан, и моментом, когда в него вписали все нужные значения, объект находится в странном состоянии. Он уже существует, но ещё не имеет смысла. Как анкета, на которую положили, но пока не заполнили: бумага есть, а человека в ней нет.

Конструкторы решают именно эту проблему. Но прежде чем идти в код, давайте посмотрим, где эта идея встречается в жизни.

**Ситуация первая.** Вы заказываете кофе в кофейне. Бариста не подаёт вам пустой стакан и не говорит: «Молоко добавьте сами, сахар вон там, эспрессо варите в углу». Он спрашивает: «Какой? С молоком? Сахар?» — и выдаёт готовый напиток. Всё, что нужно для кофе, определяется в момент заказа. Пока вы не назвали параметры, кофе не существует; как только назвали — он сразу такой, каким должен быть.

**Ситуация вторая.** Вы регистрируетесь на сайте. Форма требует имя, почту и пароль. Вы не можете создать аккаунт «пустым» и потом донастроить его — сайт не даст зарегистрироваться без этих полей. Аккаунт появляется сразу в рабочем состоянии: с именем, с почтой, с паролем. Всё, что нужно для входа, уже есть в момент создания.

**Ситуация третья.** Вы покупаете автомобиль в салоне. У машины есть цвет, комплектация, VIN-номер. VIN присваивается один раз и навсегда — в момент сборки. Вы не можете купить машину без VIN и «дописать» его потом. Цвет и комплектация тоже определяются до того, как машина станет вашей.

**Ситуация четвёртая.** Вы открываете новый документ в текстовом редакторе. Он создаётся сразу с настройками по умолчанию: шрифт Times New Roman или Calibri, поля стандартные, ориентация книжная. Вы не создаёте «никакой» документ и не настраиваете всё с нуля — редактор сам подставляет разумные значения. Но при желании вы можете создать документ с другими настройками — сразу, при создании: «новый документ в формате А4, альбомная ориентация».

**Ситуация пятая.** Вы регистрируете сим-карту. У неё есть номер, тариф, владелец. Пока сим-карта не активирована, у неё нет номера, и позвонить с неё нельзя. Активация — это и есть «момент рождения» сим-карты как Working Thing: после неё у неё есть всё нужное, до неё — ничего.

**Ситуация шестая.** Вы смотрите на код, где написано `new User()`, и не понимаете, откуда берутся значения полей. В прошлом уроке мы писали `alice.name = "Алиса"` вручную. А что, если бы мы этого не написали? Что было бы в `alice.name`? Пустая строка? `null`? Что-то ещё? И почему `new User()` вообще работает, если в классе `User` нет ни одного метода, который называется `User`?

Если последняя ситуация вам знакома — этот урок для вас. Если остальные тоже — отлично, значит, интуиция про «рождение с параметрами» у вас уже есть, и осталось связать её с синтаксисом.

## Что такое конструктор

**Конструктор** — это особый метод, который вызывается автоматически в момент создания объекта через `new`. Его задача — привести объект в рабочее состояние: заполнить поля начальными значениями, проверить, что переданные параметры корректны, подготовить всё, что нужно для дальнейшей работы.

Выглядит конструктор почти как обычный метод, но с двумя отличиями:

- **имя совпадает с именем класса** (с точностью до регистра);
- **у него нет возвращаемого типа** — даже `void` не пишется.

Вот пример:

```java
class User {
    String name;
    String email;
    int age;

    User(String name, String email, int age) {
        this.name = name;
        this.email = email;
        this.age = age;
    }
}
```

Здесь `User(...)` — конструктор. Он принимает три параметра и раскладывает их по полям. Теперь создать пользователя можно так:

```java
User alice = new User("Алиса", "alice@example.com", 30);
```

Обратите внимание: **объект создаётся сразу с нужными значениями**. Нет промежуточного состояния, в котором пользователь существует, но ещё не имеет имени. Как только `new User(...)` отработал — объект готов к использованию.

Вот в чём главная идея: конструктор — это **точка входа объекта в мир**. Всё, что объекту нужно для жизни, передаётся ему здесь. После этого объект живёт своей жизнью, но начало у него всегда одно — конструктор.

## Конструктор по умолчанию

Тут начинается то, что сбивает с толку почти всех. В прошлом уроке мы писали:

```java
class User {
    String name;
    String email;
    int age;
}
```

— и создавали объекты через `new User()` без параметров. Как это работало, если в классе не было никакого конструктора?

Ответ такой: **если вы не написали ни одного конструктора, Java добавляет конструктор по умолчанию — без параметров, который ничего не делает**. Он буквально выглядит так:

```java
User() {
    // ничего
}
```

Точнее, он не «ничего не делает», а заполняет поля значениями по умолчанию: `null` для объектов, `0` для чисел, `false` для `boolean`. Но с точки зрения кода, который мы пишем, он «пустой».

И вот ключевой момент: **этот конструктор существует ровно до тех пор, пока вы не написали свой**. Как только в классе появляется хоть один явный конструктор, конструктор по умолчанию исчезает. Компилятор считает, что вы теперь сами отвечаете за инициализацию объекта, и не подсовывает вам свою версию.

Это легко увидеть на примере. Вот класс с конструктором:

```java
class User {
    String name;
    String email;

    User(String name, String email) {
        this.name = name;
        this.email = email;
    }
}
```

Теперь `new User()` **не скомпилируется**. Компилятор скажет: «Конструктор `User()` не найден». Потому что конструктор по умолчанию больше не существует — его заменил ваш.

Это не баг и не странность, а сознательное решение: если вы написали конструктор с параметрами, значит, вы считаете, что пользователя нельзя создать без имени и почты. Java уважает это решение и не даёт обойти его.

Если вам **нужны оба** — конструктор с параметрами и без — их можно написать рядом:

```java
class User {
    String name;
    String email;

    User(String name, String email) {
        this.name = name;
        this.email = email;
    }

    User() {
        this.name = "Безымянный";
        this.email = "unknown@example.com";
    }
}
```

Теперь `new User("Алиса", "alice@example.com")` и `new User()` оба работают. Какой из них выбирать — зависит от задачи. Обычно лучше ограничить набор конструкторов разумным минимумом: если пользователя без имени не бывает, не надо и делать конструктор, который позволяет его создать.

## Ключевое слово this

В примере выше вы видели `this.name = name;`. Пора разобраться, что это такое и зачем.

Проблема в том, что параметр конструктора и поле класса могут называться одинаково. В нашем случае так и есть: есть поле `name` и есть параметр `name`. Если написать просто:

```java
User(String name, String email) {
    name = name;    // так писать нельзя
}
```

— то `name = name` присвоит параметр самому себе. Поле останется со значением по умолчанию (`null`), а параметр никуда не денется. Это классическая ошибка, и компилятор её не поймает: с его точки зрения, код корректен, просто бесполезен.

Ключевое слово `this` разрешает неоднозначность. **`this` — это ссылка на текущий объект**. Тот самый невидимый параметр, о котором мы говорили в прошлом уроке. Когда вы пишете `this.name`, вы говорите: «поле `name` **этого** объекта», а не параметр с тем же именем.

```java
User(String name, String email) {
    this.name = name;      // полю this.name присвоить значение параметра name
    this.email = email;
}
```

Читается как «у этого объекта поле `name` равно параметру `name`». Понятно и однозначно.

Есть ещё одна тонкость: иногда `this` используется для **вызова другого конструктора** того же класса. Это бывает удобно, когда несколько конструкторов должны делать почти одно и то же:

```java
class User {
    String name;
    String email;
    int age;

    User(String name, String email, int age) {
        this.name = name;
        this.email = email;
        this.age = age;
    }

    User(String name, String email) {
        this(name, email, 18);   // вызвать первый конструктор с возрастом по умолчанию
    }
}
```

Строка `this(name, email, 18)` вызывает другой конструктор этого же класса. Важное правило: **вызов `this(...)` должен быть первой строкой в конструкторе**. Почему — чуть ниже, когда будем говорить о порядке инициализации.

## Порядок инициализации

Есть вопрос, который почти никогда не задают вслух, но который рано или поздно возникает: а что происходит **между** вызовом `new` и выполнением тела конструктора? В каком порядке всё инициализируется?

Порядок такой:

1. **Выделяется память под объект.** Все поля получают значения по умолчанию: `null`, `0`, `false`.
2. **Выполняются инициализаторы полей** — те присваивания, которые написаны прямо в объявлении поля (о них ниже).
3. **Выполняется тело конструктора.**

Вот простой пример:

```java
class Counter {
    int value = 5;      // инициализатор поля
    int limit = 100;    // ещё один

    Counter(int value) {
        this.value = value;
    }
}
```

Что произойдёт при `new Counter(10)`?

- Память выделена, `value = 0`, `limit = 0`.
- Выполняются инициализаторы: `value = 5`, `limit = 100`.
- Выполняется тело конструктора: `this.value = 10`.

Итог: `value = 10`, `limit = 100`. Значение из инициализатора `value = 5` было перезаписано конструктором — это нормально, если задумано, и странно, если нет.

Отсюда, кстати, растёт правило про `this(...)` в первой строке. Если бы `this(...)` стоял где-то в середине конструктора, возник бы вопрос: а что делать с инициализаторами полей — выполнять их до или после вызова другого конструктора? Java решает этот вопрос жёстко: **вызов другого конструктора должен быть первым**, и тогда все инициализаторы и тела выполняются ровно один раз в понятном порядке.

А что если конструктор вызывает **родительский** конструктор через `super(...)` — о котором мы будем говорить в модуле про наследование? То же самое: `super(...)` должен быть первой строкой. И если вы не напишете `super(...)` явно, Java автоматически подставит вызов `super()` — конструктора родителя без параметров. Мы вернёмся к этому в уроке про `super`, а пока просто знайте, что за кулисами всегда есть «невидимая цепочка» вызовов конструкторов вверх по иерархии.

## Инициализаторы полей

Иногда в конструкторе нужно не просто присвоить параметр, а вычислить значение. Например:

```java
class Account {
    String number;
    double balance;
    double minBalance;

    Account(String number, double initialBalance) {
        this.number = number;
        this.balance = initialBalance;
        this.minBalance = initialBalance * 0.1;
    }
}
```

Тут `minBalance` — это не отдельный параметр, а вычисляемое значение. Его можно посчитать в конструкторе, как выше. А можно — прямо в объявлении поля:

```java
class Account {
    String number;
    double balance;
    double minBalance = balance * 0.1;   // так не сработает!
}
```

— и вот тут возникает тонкость: **инициализаторы полей выполняются в порядке объявления, и на момент выполнения `minBalance = balance * 0.1` поле `balance` ещё равно 0**. Результат — `minBalance = 0`, что вряд ли то, чего вы хотели.

Поэтому правило такое: **если значение поля зависит от параметров конструктора или от других полей, инициализируйте его в конструкторе, а не в объявлении**. Инициализаторы удобны только для простых констант, которые не зависят ни от чего:

```java
class Account {
    String number;
    double balance;
    double minBalance;
    String currency = "RUB";              // константа, всегда одинаковая
    int transactionCount = 0;             // просто ноль

    Account(String number, double initialBalance) {
        this.number = number;
        this.balance = initialBalance;
        this.minBalance = initialBalance * 0.1;
    }
}
```

## Перегрузка конструкторов

Как вы уже видели, в классе может быть **несколько конструкторов с разными параметрами**. Это называется перегрузкой (overloading), и это нормальная практика. Вот пример:

```java
class User {
    String name;
    String email;
    int age;

    User(String name, String email, int age) {
        this.name = name;
        this.email = email;
        this.age = age;
    }

    User(String name, String email) {
        this(name, email, 18);
    }

    User(String name) {
        this(name, "unknown@example.com", 18);
    }
}
```

Три конструктора. Первый — полный. Второй — без возраста. Третий — только с именем. Каждый следующий использует `this(...)` для вызова более полного, чтобы не дублировать логику. Это стандартный приём, и он удобен: вы предлагаете пользователю класса выбор из нескольких «способов родить» объект, но реализация у всех способов одна.

Есть одно важное ограничение: **перегруженные конструкторы должны различаться параметрами** — их количеством, типами или порядком. Два конструктора с одинаковым набором параметров, но разными именами полей, невозможны — компилятор не поймёт, какой из них вызывать.

```java
User(String name, String email) { ... }
User(String email, String name) { ... }   // это не перегрузка, это ошибка
```

Второй конструктор отличается от первого только порядком параметров, но для компилятора это одно и то же: две строки. Так нельзя. А вот так — можно:

```java
User(String name, String email) { ... }
User(String name) { ... }                 // разное количество
User(User other) { ... }                  // другой тип параметра
```

## Приватные конструкторы

Есть ещё одна возможность, о которой стоит упомянуть, хотя она понадобится нам позже. **Конструктор может быть `private`** — то есть недоступным снаружи класса. Звучит странно: как же тогда создать объект? А иногда и не надо.

Например, класс, который содержит только статические методы (вроде `Math` в стандартной библиотеке Java), не предполагает создания объектов вообще. Тогда пишут приватный конструктор, чтобы никто случайно не создал `new Math()`, и всё.

Или другой случай: класс хочет сам контролировать, как создаются его объекты. Например, `Integer.valueOf(42)` возвращает один и тот же объект для маленьких чисел — это оптимизация, которая возможна только если конструктор закрыт и создание идёт через фабричный метод. Подробнее — в модуле про инкапсуляцию, когда будем говорить о том, что бывает полезно спрятать.

Пока что просто запомните: `private`-конструктор — это способ сказать «не создавайте меня снаружи, я сам решу, как появляться». Иногда это имеет смысл.

## Аналогия, которая помогает

Хорошая аналогия — **заводская упаковка**.

Представьте, что объект — это товар на полке. У товара есть коробка, на коробке написан артикул, внутри — сам товар. И есть **процесс упаковки на заводе**: детали собирают, проверяют, кладут в коробку, заклеивают, наклеивают этикетку. Всё это происходит до того, как товар попадёт на полку.

**Конструктор — это и есть процесс упаковки.** Он определяет, как товар рождается. Если вы пропустите какую-то деталь (например, не положите инструкцию), товар будет неполным — но вы об этом узнаете только когда откроете коробку. Если вы перепутаете детали (например, положите инструкцию от другого товара), будет ещё хуже.

И вот важная деталь: **на полке не бывает «недоделанных» товаров**. Нельзя купить коробку без товара внутри — точнее, можно, но это брак, и он не должен доходить до покупателя. Аналогично, объект, созданный через конструктор, должен быть сразу готов к использованию. Если между `new` и первым осмысленным действием с объектом нужно ещё что-то дописать — это признак того, что конструктор не доделал свою работу.

Ещё одна параллель: **у завода могут быть разные линии упаковки** для одного и того же товара. Одна упаковывает полный набор, другая — облегчённый, третья — премиум с бантиком. Все они делают «тот же товар», но с разной комплектацией. Это и есть перегрузка конструкторов: разные линии упаковки для одного класса.

## Микрозадача 1

Посмотрите на класс и ответьте: сколько у него конструкторов? Какие из них можно вызвать, а какие нет? И что произойдёт, если написать `new Book()`?

```java
class Book {
    String title;
    String author;
    int year;

    Book(String title, String author, int year) {
        this.title = title;
        this.author = author;
        this.year = year;
    }

    Book(String title, String author) {
        this(title, author, 2024);
    }
}
```

### Разбор

**Конструкторов два:** `Book(String, String, int)` и `Book(String, String)`. Оба публичные (по умолчанию), оба доступны снаружи.

**`new Book()` не скомпилируется.** Конструктора без параметров в классе нет, и Java его не подставит, потому что есть явные конструкторы. Компилятор сообщит, что не может найти подходящий конструктор.

Чтобы `new Book()` работал, нужно добавить третий конструктор:

```java
Book() {
    this("Без названия", "Неизвестен", 2024);
}
```

— или явно, без `this(...)`:

```java
Book() {
    this.title = "Без названия";
    this.author = "Неизвестен";
    this.year = 2024;
}
```

Оба варианта рабочие. Первый короче, второй нагляднее. В данном случае я бы выбрал первый — он использует уже существующий конструктор и не дублирует логику.

Обратите внимание на ещё одну деталь. Конструктор `Book(String, String)` вызывает `this(title, author, 2024)`. Это означает, что при создании книги с названием и автором год автоматически ставится в 2024. Если пользователь класса потом захочет поменять год — он сможет это сделать через сеттер (когда мы их добавим). Но при создании — по умолчанию текущий.

## Микрозадача 2

Вот класс. В нём есть ошибка — код не скомпилируется. Найдите её и объясните, что не так.

```java
class Point {
    int x;
    int y;

    Point(int x, int y) {
        x = x;
        y = y;
    }

    Point() {
        this(0, 0);
        x = 10;
    }
}
```

### Разбор

Здесь две ошибки, и обе поучительные.

**Первая ошибка — в первом конструкторе.** Строки `x = x;` и `y = y;` присваивают параметр самому себе. Поле остаётся со значением по умолчанию (`0`), а параметр никуда не девается. Скомпилируется — но не сделает того, что задумано. Правильно:

```java
Point(int x, int y) {
    this.x = x;
    this.y = y;
}
```

Это та самая ловушка, про которую мы говорили: без `this` компилятор не понимает, что вы имеете в виду поле, а не параметр. Точнее, понимает — но не так, как вам бы хотелось: он считает, что вы работаете с параметром.

**Вторая ошибка — во втором конструкторе.** Вызов `this(0, 0)` должен быть **первой строкой**. А у вас после него идёт `x = 10;`. Java это не пропустит: правило про «`this(...)` — только первым» жёсткое, и обойти его нельзя.

Правильно — либо перенести присваивание до вызова `this(...)` (но это невозможно, потому что `this(...)` должен быть первым), либо перенести логику внутрь того конструктора, который вызывается:

```java
Point(int x, int y) {
    this.x = x;
    this.y = y;
}

Point() {
    this(10, 0);   // x = 10, y = 0
}
```

Или, если хочется более явно:

```java
Point() {
    this(0, 0);
}
// и потом уже сеттером менять x, если нужно
```

Но самый чистый вариант — когда все «магические» значения определяются в одном месте, а остальные конструкторы просто делегируют ему. Иначе через полгода вы забудете, почему `Point()` даёт `(10, 0)`, а `Point(0, 0)` — `(0, 0)`, и будете долго искать причину.

## Самостоятельная задача

Спроектируйте класс `Coffee` для кофейни.

Подумайте:

- какие у него будут поля (например, название, объём, цена, количество сахара — но можно и свои);
- сколько конструкторов имеет смысл сделать и какие параметры они принимают;
- какой конструктор будет «основным» (тем, куда делегируют остальные);
- какие значения по умолчанию разумны для параметров, которые можно не указывать;
- что должен делать конструктор, если передали отрицательный объём или отрицательную цену.

Затем ответьте на вопрос: если у класса три конструктора, и один из них вызывает другой через `this(...)`, — сколько раз выполнится тело «главного» конструктора при создании объекта? Один или несколько?

Готового ответа не будет. Если хотите свериться — загляните в следующий урок про ссылки и `null`: там мы начнём разбираться, где именно в памяти живут объекты и как они умудряются ссылаться друг на друга, — и вы увидите, насколько ваша интуиция совпала с тем, как это устроено на самом деле.

Мы разобрались, как объект появляется на свет и почему конструктор — это не «ещё один метод», а точка входа, через которую объект попадает в мир. В следующем уроке — **«Ссылки и `null`»** — мы поговорим о том, что происходит после создания. Где объект живёт, что хранит переменная, и почему `null` — это не «ничего», а «пока никуда не указывает», и чем это оборачивается на практике.

А пока — маленькое упражнение на наблюдательность. Посмотрите на любой класс, который вы писали раньше (или который есть в вашем рабочем проекте). Найдите в нём конструкторы. Если их несколько — посмотрите, есть ли между ними `this(...)`. Если есть — проследите, какой из них «главный». А если конструктор один и он без параметров — подумайте: а какие поля объект получает в этот момент, и всегда ли эти значения осмысленны для дальнейшей работы?

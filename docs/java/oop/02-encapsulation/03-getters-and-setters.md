# 3. Геттеры и сеттеры

## Где вы это уже видели

В прошлых уроках мы несколько раз писали `getBalance()`, `setEmail()`, `getName()`. Это самая частая пара методов в Java — настолько частая, что многие думают, будто в ней и состоит вся инкапсуляция. «Поле сделал `private`, написал геттер и сеттер — всё, инкапсуляция готова». Это не так, и в этом уроке мы разберёмся почему.

**Ситуация первая.** Вы в банке хотите узнать баланс. Вы не лезете в базу данных банка и не читаете внутренние таблицы. Вы спрашиваете у операциониста: «Сколько у меня на счёте?» — и он отвечает. Операционист — это геттер. Он не отдаёт вам всю базу, он отвечает на конкретный вопрос.

**Ситуация вторая.** Вы хотите перевести деньги. Вы не пишете новое значение баланса в базу — вы даёте распоряжение: «Переведите 5000 рублей вот на этот счёт». Банк сам решает, достаточно ли средств, не заблокирован ли счёт, не превышен ли лимит. Вы не «устанавливаете баланс», вы **совершаете действие**. Это важно: сеттер — это не «записать значение», это «выполнить операцию, которая может изменить состояние».

**Ситуация третья.** Вы в гостинице. Вы можете спросить у администратора: «На каком этаже мой номер?» — и он ответит. Вы не можете сказать: «Сделайте мой номер на пятнадцатом этаже». Максимум — попросить поменять номер, и администратор решит, возможно ли это. Геттер работает, сеттер — нет: не всё, что можно прочитать, можно изменить.

**Ситуация четвёртая.** Вы в ресторане. В меню написано «Стейк — 1500 рублей». Вы можете прочитать цену. Вы не можете зачеркнуть её и написать «100 рублей». Цена — это то, что читается, но не меняется клиентом. Сеттера на цену нет (точнее, он есть у менеджера ресторана, но не у вас).

**Ситуация пятая.** Вы работаете с банковской картой. У неё есть PIN-код. Вы можете его поменять — но только через банкомат, зная старый PIN. Вы не можете «установить PIN» напрямую: банк требует подтверждения, что это действительно вы. Сеттер `setPin` есть, но он не просто записывает значение — он **проверяет условия**.

**Ситуация шестая.** Вы смотрите на код и видите:

```java
class User {
    private String email;

    public String getEmail() { return email; }
    public void setEmail(String email) { this.email = email; }
}
```

— и думаете: «Это же инкапсуляция, поле `private`, доступ через методы». А потом кто-то пишет `user.setEmail("не-почта")`, и класс это спокойно принимает. И вы понимаете, что `private` сам по себе ничего не защитил — он просто переименовал прямой доступ в вызов метода.

Если последняя ситуация вам знакома — этот урок для вас. Если остальные тоже — отлично, у вас уже есть интуиция про «читать можно, менять — только через операцию», осталось связать её с кодом.

## Что такое геттер и сеттер

**Геттер** (getter) — метод, который возвращает значение поля. Обычно называется `getXxx()` для полей с именем `xxx` (или `isXxx()` для `boolean`).

**Сеттер** (setter) — метод, который устанавливает значение поля. Обычно называется `setXxx(value)`.

Вот классическая пара:

```java
class User {
    private String name;

    public String getName() {
        return name;
    }

    public void setName(String name) {
        this.name = name;
    }
}
```

На первый взгляд, это просто «обёртка» вокруг поля. И если это **всё**, что делает пара, — то это и есть просто обёртка. Никакой инкапсуляции здесь нет: снаружи можно прочитать и записать любое значение, как если бы поле было `public`.

**Настоящая инкапсуляция** начинается, когда геттер и сеттер **что-то делают**, кроме чтения и записи. Проверяют, преобразуют, защищают, логируют. Вот пример:

```java
class User {
    private String email;

    public String getEmail() {
        return email;
    }

    public void setEmail(String email) {
        if (email == null || !email.contains("@")) {
            throw new IllegalArgumentException("Некорректный email: " + email);
        }
        this.email = email.toLowerCase().trim();
    }
}
```

Теперь `setEmail` не просто записывает — он проверяет, что email содержит `@`, и нормализует его (приводит к нижнему регистру, обрезает пробелы). Класс **гарантирует**, что `email` всегда валиден и всегда в одном формате. Это уже инкапсуляция.

Разница принципиальная. «Голый» сеттер — это переименование `public`-поля. Сеттер с проверкой — это точка контроля, через которую нельзя протащить мусор.

## Почему «голые» геттеры-сеттеры — плохо

Многие начинающие (и, к сожалению, некоторые опытные) пишут для каждого поля пару «голых» геттера и сеттера и считают, что инкапсуляция сделана. Это не так, и вот почему.

**Первое: это не защищает.** Если `setEmail` просто пишет в поле, то снаружи можно записать что угодно. `private` не помогает: он только меняет синтаксис вызова, но не ограничивает значения. Класс не контролирует своё состояние — он просто позволяет делать с ним что угодно через метод.

**Второе: это создаёт ложное чувство защищённости.** Когда вы видите `private`-поле с геттером и сеттером, вы думаете: «Ага, поле защищено». А на самом деле — нет. И вы пишете код, который полагается на «защиту», которой нет.

**Третье: это раздувает публичный интерфейс.** Каждое поле даёт два публичных метода. Если у класса десять полей — двадцать методов. И все они `public`. А значит, все они — обязательства, которые класс берёт на себя перед внешним миром. Завтра вы захотите поменять тип поля — придётся менять и методы, и всех, кто их использует.

**Четвёртое: это не выражает намерения.** `setBalance(100)` — что это значит? Положить сто рублей? Установить баланс в сто рублей (то есть стереть предыдущий)? Списать сто рублей? Из кода непонятно. А `deposit(100)` или `withdraw(100)` — понятно сразу.

**Пятое: это провоцирует анемичную модель.** «Анемичная модель» — это когда классы — просто мешки с данными, а вся логика — в отдельных функциях, которые эти данные дёргают. По сути, это процедурный подход, замаскированный под ООП. И все проблемы процедурного подхода (о которых мы говорили в первом уроке) возвращаются: данные меняются где попало, инварианты не соблюдаются, изменения расползаются.

Проще говоря: **«голый» сеттер — это `public`-поле, только с более длинным именем**. Если вы всё равно разрешаете менять значение когда угодно и на что угодно, — зачем вообще `private`? Только для вида?

## Когда сеттер — это зло

Есть несколько ситуаций, когда сеттер (даже не «голый») — плохая идея.

**Поле не должно меняться после создания.** Например, `id` заказа, `createdAt` пользователя, `isbn` книги, номер банковского счёта. Эти поля определяются при создании объекта и дальше не меняются. Сеттер на них — это разрешение нарушить инвариант «это поле неизменно».

```java
class Order {
    private final String id;
    private final long createdAt;

    public Order(String id) {
        this.id = id;
        this.createdAt = System.currentTimeMillis();
    }

    public String getId() { return id; }
    public long getCreatedAt() { return createdAt; }

    // сеттеров на id и createdAt нет — и не должно быть
}
```

Здесь поля `final` — их нельзя изменить даже изнутри класса после конструктора. И сеттеров нет. Если кто-то захочет поменять `id` — он не сможет, и это правильно.

**Сеттер позволяет объекту попасть в невалидное состояние.** Например, у счёта есть баланс, и он не может быть отрицательным. Если есть `setBalance`, кто-то может выставить `-1000`. Если сеттера нет, а есть только `deposit` и `withdraw`, которые проверяют, — такого не случится.

**Сеттер ломает инварианты между полями.** У `Order` есть `quantity` (количество) и `totalPrice` (общая стоимость). Если менять их по отдельности, можно получить ситуацию «10 штук на 100 рублей», хотя цена одной штуки — 50 рублей. Значит, сеттеров на оба поля быть не должно; вместо них — метод `changeQuantity`, который пересчитывает `totalPrice`.

**Сеттер мешает неизменяемости.** Если все поля можно поменять через сеттеры, объект изменяем. А изменяемые объекты сложнее в использовании: их нельзя безопасно передавать между потоками, нельзя кэшировать, нельзя использовать как ключи в `Map`. Мы поговорим об этом в уроке про неизменяемые объекты, но подумать полезно уже сейчас.

Общее правило: **сеттер нужен только тогда, когда изменение поля — это осмысленная операция с точки зрения предметной области**. Если поле можно менять «просто так» — возможно, его не должно быть в публичном интерфейсе вообще.

## Когда без сеттера не обойтись

Справедливости ради, бывают ситуации, когда сеттер нужен.

**Простой класс данных.** Иногда класс — это действительно просто набор полей (например, DTO для передачи данных между слоями). В таком случае сеттеры допустимы, потому что у класса нет инвариантов, которые нужно защищать. Но даже здесь стоит подумать: а не подойдёт ли `record` (мы будем говорить о нём в уроке 13)?

**Поле с независимой валидацией.** Если поле можно менять, и его значение не связано с другими полями, — сеттер с проверкой будет нормальным решением. Например, `User.email` — почту можно менять, она не влияет на другие поля, и единственное требование — чтобы она содержала `@`.

**Фреймворки.** Некоторые фреймворки (например, Hibernate, Jackson) требуют, чтобы у класса были геттеры и сеттеры для всех полей — они через них «заполняют» объекты при десериализации. Это техническое требование, и с ним приходится мириться. Но это не значит, что классы должны быть такими всегда — только когда они используются с этими фреймворками.

**Гибкое конфигурирование.** Если у объекта много параметров, и все они опциональны, — иногда удобно иметь сеттеры, чтобы настраивать объект после создания. Но это часто признак того, что стоило бы использовать паттерн «строитель» (Builder), о котором мы поговорим в модуле 5.

В остальных случаях — думайте дважды. Сеттер — это разрешение менять объект, и каждое такое разрешение должно быть обосновано.

## А как же геттеры?

С геттерами история мягче, но не сильно. Геттер кажется безобидным: он только читает, ничего не меняет. Что в нём может быть плохого?

**Геттер может вернуть изменяемый объект.** Помните микрозадачу из урока 8 про `getRoles()`, который возвращал сам список? Вот это — типичная проблема. Геттер возвращает внутреннее состояние, и через возвращённый объект это состояние можно изменить.

```java
class User {
    private java.util.List<String> roles = new java.util.ArrayList<>();

    public java.util.List<String> getRoles() {
        return roles;   // плохо: можно менять снаружи
    }
}
```

**Геттер может раскрывать внутреннее представление.** Если у класса `Stack` есть геттер на внутренний массив — кто угодно может в него залезть и сломать инварианты стека.

**Геттер может быть дорогим.** Иногда геттер не просто читает поле, а что-то вычисляет. Например, `getTotal()` у корзины считает сумму всех товаров. Это нормально, но вызывающий код должен понимать, что метод может быть небыстрым. Обычно это решается соглашением: методы, которые что-то вычисляют, называют `calculateXxx()` или `computeXxx()`, а не `getXxx()`.

**Геттер может возвращать `null`.** Если поле может быть `null`, геттер вернёт `null`, и вызывающий код должен это обработать. Об этом мы говорили в уроке 5.

Общее правило: **геттер должен возвращать либо неизменяемое значение (примитив, `String`, `record`), либо копию, либо неизменяемое представление**. Если поле изменяемое — не отдавайте его напрямую.

## Аналогия, которая помогает

Хорошая аналогия — **окно и дверь в доме**.

Представьте, что объект — это дом. В доме есть **внутренние комнаты** (поля) и **стены** (модификаторы доступа). А ещё есть **окна** и **двери**.

**`private` без геттеров и сеттеров** — это дом без окон и дверей. Внутрь никак не попасть. Иногда это правильно (например, для синглтона), но обычно — нет: с домом нельзя взаимодействовать.

**`private` + геттер** — это дом с окном. Вы можете посмотреть внутрь, но не можете войти. И вот важный момент: **что именно вы видите через окно, зависит от того, насколько большое окно**. Если окно размером со стену — вы видите всё. Если маленькое — только то, что показывает хозяин. Хороший геттер — это маленькое окно: вы видите ровно то, что нужно, и не больше.

**`private` + геттер и сеттер** — это дом с окном и дверью. Через дверь можно войти и что-то поменять. И вот тут важно, **что это за дверь**. Если дверь — это просто проём без замка, то кто угодно может зайти и вынести всё. А если это дверь с домофоном и охраной — то зайти можно только тем, кому разрешено, и только с определёнными намерениями.

**«Голый» сеттер — это проём без замка.** Формально «дверь есть», но она ничего не защищает. «Сеттер с проверкой» — это дверь с охраной. «Отсутствие сеттера, но метод `deposit`» — это вообще не дверь, а окошко кассы, через которое можно только положить деньги, но не залезть внутрь.

И ещё одна мысль: **не обязательно делать на каждое поле окно**. Иногда достаточно одного маленького окошка, через которое видно всё, что нужно. И не обязательно делать дверь на каждое поле — иногда хватает одной двери в подъезд, через которую и заходят, и выходят.

## Микрозадача 1

Вот класс. Определите, какие из геттеров и сеттеров «голые» (не защищают ничего), а какие — настоящие точки контроля.

```java
class Product {
    private String name;
    private double price;
    private int quantity;
    private java.util.List<String> tags;

    public Product() {
        this.tags = new java.util.ArrayList<>();
    }

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }

    public double getPrice() { return price; }
    public void setPrice(double price) {
        if (price < 0) {
            throw new IllegalArgumentException("Цена не может быть отрицательной");
        }
        this.price = price;
    }

    public int getQuantity() { return quantity; }
    public void setQuantity(int quantity) { this.quantity = quantity; }

    public java.util.List<String> getTags() { return tags; }
}
```

### Разбор

**`getName` / `setName`** — голые. `setName` просто пишет в поле. Можно передать `null` или пустую строку — класс не заметит.

**`getPrice` / `setPrice`** — настоящая точка контроля. `setPrice` проверяет, что цена не отрицательна. Если передать `-100`, будет `IllegalArgumentException`. Класс гарантирует инвариант «цена всегда неотрицательна».

**`getQuantity` / `setQuantity`** — голые. Можно поставить `-5`, и класс это примет. А ещё можно установить `quantity = 10` без учёта того, что цена, возможно, должна пересчитаться (если бы она зависела от количества).

**`getTags`** — проблема. Возвращает сам список, а не копию. Значит, `product.getTags().add("...")` добавит тег в обход любых проверок. Это та самая «утечка изменяемого состояния», о которой мы говорили в уроке 8.

**Как улучшить.**

`setName` — добавить проверку на `null` и пустоту:

```java
public void setName(String name) {
    if (name == null || name.isEmpty()) {
        throw new IllegalArgumentException("Имя не может быть пустым");
    }
    this.name = name;
}
```

`setQuantity` — добавить проверку на неотрицательность. А если бы количество влияло на другие поля — заменить на метод `changeQuantity(int delta)`, который пересчитывает всё, что нужно.

`getTags` — вернуть копию или неизменяемое представление:

```java
public java.util.List<String> getTags() {
    return java.util.Collections.unmodifiableList(tags);
}
```

Или вообще не отдавать список, а давать методы `hasTag(String)`, `getTagCount()`, `addTag(String)` с проверками.

**Мораль.** Из четырёх пар «геттер + сеттер» только одна (`price`) делает что-то полезное. Остальные — просто переименованный `public`. Если бы мы сделали все поля `public`, было бы то же самое, только короче.

## Микрозадача 2

Вот класс. Он выглядит защищённым, но на самом деле у него есть проблема. Найдите её.

```java
class DateRange {
    private java.util.Date start;
    private java.util.Date end;

    public DateRange(java.util.Date start, java.util.Date end) {
        this.start = start;
        this.end = end;
    }

    public java.util.Date getStart() { return start; }
    public java.util.Date getEnd() { return end; }

    public boolean contains(java.util.Date date) {
        return !date.before(start) && !date.after(end);
    }
}
```

### Разбор

Проблема в том, что `Date` — **изменяемый** класс. У него есть метод `setTime(long)`, и его можно вызвать у объекта, который мы получили из геттера. Кроме того, объект `Date`, который передали в конструктор, тоже можно менять снаружи — и класс `DateRange` об этом не узнает.

Вот как можно сломать `DateRange`:

```java
java.util.Date start = new java.util.Date(2024, 0, 1);
java.util.Date end = new java.util.Date(2024, 11, 31);

DateRange range = new DateRange(start, end);
System.out.println(range.contains(new java.util.Date(2024, 5, 1)));  // true

// а теперь меняем start снаружи
start.setYear(2025);
System.out.println(range.contains(new java.util.Date(2024, 5, 1)));  // false — почему?
```

— потому что `range.start` и `start` — это один и тот же объект. Мы поменяли его через переменную `start`, и `DateRange` даже не заметил, что его инвариант («`start` раньше `end`») нарушился.

То же самое через геттер:

```java
range.getStart().setYear(2025);
```

— и `DateRange` снова в невалидном состоянии.

**Как исправить.** Два варианта.

**Первый — использовать неизменяемый тип.** `java.time.LocalDate`, `java.time.Instant` — неизменяемые классы. Их нельзя поменять после создания. Если передать их в конструктор и вернуть из геттера, — никто не сможет изменить внутреннее состояние `DateRange` снаружи.

```java
class DateRange {
    private final java.time.LocalDate start;
    private final java.time.LocalDate end;

    public DateRange(java.time.LocalDate start, java.time.LocalDate end) {
        if (start.isAfter(end)) {
            throw new IllegalArgumentException("Начало позже конца");
        }
        this.start = start;
        this.end = end;
    }

    public java.time.LocalDate getStart() { return start; }
    public java.time.LocalDate getEnd() { return end; }

    public boolean contains(java.time.LocalDate date) {
        return !date.isBefore(start) && !date.isAfter(end);
    }
}
```

Теперь всё в порядке: `LocalDate` неизменяем, поля `final`, есть проверка инварианта в конструкторе. Снаружи ничего не сломать.

**Второй — защитное копирование.** Если по каким-то причинам нужно использовать именно `Date`, — копировать его при приёме и при выдаче:

```java
public DateRange(java.util.Date start, java.util.Date end) {
    this.start = new java.util.Date(start.getTime());
    this.end = new java.util.Date(end.getTime());
}

public java.util.Date getStart() {
    return new java.util.Date(start.getTime());
}
```

Теперь `DateRange` хранит **свои** копии, и изменение исходных `Date` снаружи на него не влияет. А геттер возвращает **новую** копию, и изменение её не влияет на внутреннее состояние. Это работает, но выглядит громоздко и легко забыть про копию в одном из методов.

**Мораль.** «Защищённость» класса зависит не только от `private` и геттеров, но и от того, **что за объекты** хранятся в полях. Если это изменяемые объекты — их нужно либо копировать, либо заменять на неизменяемые. `private` сам по себе не спасает, если объект внутри можно поменять снаружи. Об этом мы будем подробно говорить в уроке 12 про неизменяемые объекты.

## Самостоятельная задача

Спроектируйте класс `Article` для блога.

Поля (примерно): заголовок, текст, автор, дата публикации, количество просмотров, список тегов.

Подумайте:

- на какие поля нужны геттеры, а на какие — нет;
- на какие поля нужны сеттеры, а на какие — нет (и почему);
- какие поля должны быть `final` и инициализироваться в конструкторе;
- какие поля можно менять после создания (например, просмотры точно растут, а заголовок — вряд ли);
- какие геттеры должны возвращать копию или неизменяемое представление (подсказка: список тегов);
- как выразить «просмотры увеличиваются» — через `setViews(int)`, через `incrementViews()`, или как-то ещё.

Затем ответьте на вопрос: если у статьи есть метод `publish()`, который делает её видимой для читателей, — какие поля он меняет? И почему это лучше, чем `setPublished(true)`?

Готового ответа не будет. Если хотите свериться — загляните в следующий урок про валидацию: там мы разберём, как именно проверять значения в сеттерах и конструкторах, и как вести себя, если проверка не прошла. ## Что дальше

Мы разобрались, что геттеры и сеттеры — это не автоматическая инкапсуляция, а инструмент, который может быть полезным, а может — вредным. В следующем уроке — **«Валидация в сеттерах»** — мы поговорим о том, как именно проверять значения, и что делать, если проверка не прошла. Потому что «бросить исключение» — это только один из вариантов, и не всегда лучший.

А пока — маленькое упражнение на наблюдательность. Откройте любой класс в своём проекте (или в открытом проекте на Java), у которого есть геттеры и сеттеры. Для каждой пары задайте вопрос: **а что именно защищает этот сеттер?** Если ответ «ничего» — возможно, поле можно было бы сделать `public` и не тратить строки. А если ответ «защищает» — попробуйте сформулировать, что именно. Если не получается — возможно, защита не такая уж и надёжная. Просто посмотрите. Не меняйте. Понимание того, что «геттеры-сеттеры» — не синоним инкапсуляции, — уже большой шаг вперёд.

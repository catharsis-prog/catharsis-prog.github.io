# Практикум — Инкапсуляция

## Как это работает

Здесь семь задач. Первые три — разминка на закрытие полей и защиту внутреннего состояния. Следующие три — на подумать: валидация, неизменяемость, `record`. Последняя — проектное задание, которое можно решать несколько вечеров.

Решения лежат на [отдельной странице](./practice-solutions). Сначала попробуйте сами, потом сверяйтесь. Если ваше решение отличается от моего, но работает и понятно — оно тоже правильное. В инкапсуляции редко бывает один правильный ответ: многое зависит от того, какие инварианты вы хотите гарантировать и насколько строго.

Код пишите в файлах `.java`, запускайте, экспериментируйте. Особенно полезно **ломать** свои классы: попробуйте передать в сеттер `null`, отрицательное число, пустую строку. Если класс это принимает и не падает — возможно, ему не хватает валидации.

## Задача 1. Счёт с открытыми полями

Вот класс. У него всё открыто — и поля, и доступ к ним.

```java
class Account {
    public String owner;
    public double balance;
}
```

Переделайте его так, чтобы:

- поля стали `private`;
- появились геттеры для обоих полей;
- появился сеттер для `owner`, который не даёт установить `null` или пустую строку;
- вместо сеттера для `balance` появились методы `deposit(double)` и `withdraw(double)` с проверками: сумма должна быть положительной, а при списании — не превышать баланс;
- конструктор принимает владельца и начальный баланс и проверяет их.

Создайте счёт, пополните его, снимите деньги, попробуйте снять больше, чем есть, — и убедитесь, что класс ведёт себя как надо.

**Что проверяется:** понимаете ли вы разницу между «закрыть поле» и «взять на себя ответственность за то, что с ним происходит».

## Задача 2. Температура с инвариантом

Создайте класс `Temperature` с двумя полями: `value` (`double`) и `unit` (перечисление `Unit` с вариантами `CELSIUS`, `FAHRENHEIT`, `KELVIN`).

Инвариант: **температура не может быть ниже абсолютного нуля**. Для цельсия это −273.15 °C, для фаренгейта — −459.67 °F, для кельвина — 0 K.

Реализуйте:

- конструктор с проверкой;
- геттеры;
- метод `setValue(double newValue)` — проверяет, что новое значение не ниже абсолютного нуля **в текущей единице**;
- метод `setUnit(Unit newUnit)` — меняет единицу, **пересчитывая значение**. Например, 0 °C должно стать 32 °F или 273.15 K. Проверьте, что после пересчёта инвариант сохраняется (он должен сохраняться автоматически, но убедитесь);
- метод `toString()`, который печатает что-то вроде `"25.0 °C"`.

Создайте температуру, поменяйте единицу, поменяйте значение, попробуйте установить значение ниже абсолютного нуля — и убедитесь, что класс не даёт этого сделать.

**Что проверяется:** понимаете ли вы, что инвариант нужно проверять **на каждой границе**, где значение попадает в объект, и что при изменении одного поля может «поехать» другой инвариант.

## Задача 3. Плейлист с защитой коллекции

Создайте класс `Song` (можно простой: название и исполнитель, оба `String`, оба `private final`, с геттерами).

Создайте класс `Playlist` с полями:

- `name` (`String`);
- `songs` (`List<Song>`).

Требования:

- конструктор принимает имя и список песен; список копируется, чтобы снаружи его нельзя было изменить;
- геттер `getSongs()` возвращает **неизменяемое представление** или копию — но не сам внутренний список;
- метод `addSong(Song)` добавляет песню, но не даёт добавить `null` и не даёт добавить одну и ту же песню дважды (сравнивайте по ссылке, `equals` мы ещё не проходили);
- метод `removeSong(Song)` удаляет песню, если она есть;
- метод `getSongCount()` возвращает количество песен.

Создайте плейлист, добавьте песни, попробуйте изменить список снаружи через геттер, попробуйте добавить ту же песню дважды. Убедитесь, что класс защищён.

**Что проверяется:** понимаете ли вы, что `private` на поле-коллекции сам по себе ничего не защищает, если геттер возвращает саму коллекцию.

## Задача 4. Два типа исключений

Создайте класс `BankAccount` с приватными полями `owner` и `balance`. Реализуйте:

- конструктор с проверкой (владелец не пустой, баланс не отрицательный) — какие исключения бросать, решите сами;
- `deposit(double)` — отклоняет неположительные суммы;
- `withdraw(double)` — отклоняет неположительные суммы **и** суммы, превышающие баланс;
- `transferTo(BankAccount other, double amount)` — переводит деньги на другой счёт. Проверьте: `other` не `null`, `other` не тот же самый счёт, сумма положительная, средств достаточно;
- `getBalance()`, `getOwner()`.

Для каждого метода подумайте: это `IllegalArgumentException` или `IllegalStateException`? Обоснуйте выбор в комментарии.

Проверьте все сценарии: успешные и неуспешные. Убедитесь, что при неуспехе баланс **не меняется** ни на одном из счетов.

**Что проверяется:** понимаете ли вы разницу между «невалидный аргумент» и «неподходящее состояние», и умеете ли вы не оставлять объект в «полуизменённом» состоянии при ошибке.

## Задача 5. Неизменяемый диапазон дат

Создайте неизменяемый класс `DateRange` с полями `start` и `end` типа `java.time.LocalDate`.

Требования:

- класс `final`, поля `private final`, без сеттеров;
- конструктор проверяет, что `start` не позже `end`;
- методы `getStart()`, `getEnd()`;
- метод `contains(LocalDate)` — входит ли дата в диапазон (включительно);
- метод `overlaps(DateRange)` — пересекается ли с другим диапазоном;
- метод `lengthInDays()` — сколько дней в диапазоне;
- метод `shift(int days)` — возвращает **новый** `DateRange`, сдвинутый на указанное количество дней. Исходный не меняется.

Создайте диапазон, проверьте `contains` и `overlaps` на нескольких датах, сдвиньте его и убедитесь, что исходный не изменился.

**Что проверяется:** умеете ли вы писать неизменяемый класс «с нуля», и понимаете ли вы, что методы, которые «меняют» объект, в неизменяемом классе возвращают новый объект.

## Задача 6. Рефакторинг в record

Вот класс. Он длинный, скучный и содержит много boilerplate-кода.

```java
import java.util.Objects;

public final class UserCredentials {
    private final String username;
    private final String email;

    public UserCredentials(String username, String email) {
        this.username = username;
        this.email = email;
    }

    public String getUsername() { return username; }
    public String getEmail() { return email; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        UserCredentials that = (UserCredentials) o;
        return Objects.equals(username, that.username) && Objects.equals(email, that.email);
    }

    @Override
    public int hashCode() {
        return Objects.hash(username, email);
    }

    @Override
    public String toString() {
        return "UserCredentials[username=" + username + ", email=" + email + "]";
    }
}
```

Перепишите его как `record`. Добавьте компактный конструктор с проверками:

- `username` не `null`, не пустой, состоит только из букв, цифр и `_`, длина от 3 до 20;
- `email` не `null`, содержит `@`.

Проверьте, что после рефакторинга класс работает так же (создание, `equals`, `hashCode`, `toString`), а кода стало в разы меньше.

**Что проверяется:** умеете ли вы узнавать ситуации, где `record` уместен, и знаете ли вы, как добавить валидацию в `record`.

## Задача 7. Проект — Банковская система

Это большое задание. Его можно решать несколько вечеров. Здесь нужно применить **всё**, что мы прошли в модуле: и `private`, и валидацию, и неизменяемость, и `record`.

Спроектируйте модель банка на четырёх классах: `Customer`, `Account`, `Transaction`, `Bank`.

### Customer

Поля:

- `id` (`long`) — уникальный идентификатор, присваивается автоматически (через `static`-счётчик);
- `name` (`String`).

Требования:

- `id` и `name` — `private final`;
- в конструкторе проверить, что имя не пустое;
- геттеры без сеттеров — клиент не меняется после создания.

### Account

Поля:

- `accountNumber` (`String`) — уникальный номер счёта;
- `owner` (`Customer`);
- `balance` (`java.math.BigDecimal`) — баланс (используем `BigDecimal`, а не `double`, потому что это деньги);
- `transactions` (`List<Transaction>`) — история операций.

Требования:

- все поля `private`;
- `accountNumber` и `owner` — `final`;
- в конструкторе проверить, что `accountNumber` не пустой и `owner` не `null`, начальный баланс неотрицательный;
- `deposit(BigDecimal amount)` — пополнение, отклоняет `null` и неположительные суммы, добавляет транзакцию в историю;
- `withdraw(BigDecimal amount)` — списание, отклоняет `null`, неположительные суммы и суммы больше баланса, добавляет транзакцию;
- `getBalance()`, `getAccountNumber()`, `getOwner()`;
- `getTransactions()` — возвращает **неизменяемое представление** истории;
- при любой ошибке состояние счёта (баланс и история) **не меняется**.

### Transaction

Это `record` с полями:

- `type` (перечисление `TransactionType` с вариантами `DEPOSIT` и `WITHDRAWAL`);
- `amount` (`BigDecimal`);
- `timestamp` (`java.time.Instant`).

Требования:

- компактный конструктор проверяет, что `amount` не `null` и положительный;
- если `timestamp` не передан (например, есть второй конструктор без него) — ставится текущий момент.

### Bank

Поля:

- `customers` (`List<Customer>`);
- `accounts` (`List<Account>`).

Требования:

- все поля `private final`, инициализируются пустыми списками в конструкторе;
- `registerCustomer(String name)` — создаёт клиента и возвращает его;
- `openAccount(Customer, String accountNumber, BigDecimal initialBalance)` — открывает счёт, проверяет, что клиент зарегистрирован и номер счёта уникален;
- `findAccount(String accountNumber)` — возвращает `Optional<Account>` (да, мы ещё не проходили `Optional`, но здесь он уместен — можете вернуть `null`, если не хотите пока использовать `Optional`);
- `transfer(String fromNumber, String toNumber, BigDecimal amount)` — переводит деньги между счетами. Проверьте: оба счёта существуют, они разные, сумма положительная, средств достаточно. **При любой ошибке ни один счёт не должен измениться.**
- `printAllAccounts()` — печатает все счета и их балансы.

### Сценарий проверки

Напишите `main`, который:

1. Создаёт банк.
2. Регистрирует двух клиентов — Алису и Боба.
3. Открывает Алисе счёт `A-001` с балансом 1000, Бобу — `B-001` с балансом 500.
4. Алиса переводит Бобу 300.
5. Печатает все счета: у Алисы 700, у Боба 800.
6. Алиса пытается перевести 1000 — должна получить ошибку «недостаточно средств», и оба счёта должны остаться прежними.
7. Печатает историю транзакций по счёту Алисы — должно быть списание 300 и (после ошибки) ничего.
8. Пытается открыть счёт с уже существующим номером `A-001` — должна быть ошибка.
9. Печатает историю транзакций Боба — должно быть пополнение 300.

### Дополнительные требования

- Везде, где возможно, используйте `BigDecimal` вместо `double`.
- Везде, где нужно, обрабатывайте `null`.
- Если метод может не найти объект (например, счёт по номеру), — возвращайте `Optional` или `null`, но обрабатывайте это.
- Поля классов — `private`, доступ — только через методы.
- Неизменяемые данные (например, транзакции) — делайте `record` или `final`-классами.

**Что проверяется:** всё сразу. Умение проектировать классы с инкапсуляцией, писать валидацию, использовать неизменяемость, `record`, защитное копирование и аккуратно собирать из этого работающую систему. И — что важнее всего — умение не оставлять объекты в «полуизменённом» состоянии при ошибках.

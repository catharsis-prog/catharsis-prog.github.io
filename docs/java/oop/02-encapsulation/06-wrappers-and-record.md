# 6. Классы-обёртки и record

## Где вы это уже видели

В прошлом уроке мы говорили о неизменяемых объектах и о том, как их писать: `final`-класс, `private final`-поля, никаких сеттеров, защитное копирование. Всё это правильно, но требует довольно много кода ради довольно простой идеи — «объект, который хранит несколько значений и не меняется».

Сегодня мы посмотрим на две вещи, которые делают эту идею удобной: **классы-обёртки** (готовые неизменяемые типы из стандартной библиотеки) и **`record`** (способ писать свои неизменяемые классы данных почти без кода).

**Ситуация первая.** Вы пишете `List<Integer>` и не задумываетесь, почему там `Integer`, а не `int`. Коллекции в Java не умеют хранить примитивы — только объекты. И `Integer` — это класс-обёртка, который «притворяется» числом, но на самом деле объект. Вы с ним работаете как с обычным числом, а Java сама заворачивает и разворачивает значения.

**Ситуация вторая.** Вы сравниваете два `Integer` через `==` и получаете `true` для 100 и `false` для 1000. Это не баг, а следствие того, что `Integer` — объект, `==` сравнивает ссылки, а маленькие значения кэшируются. Классическая ловушка, на которой спотыкаются все.

**Ситуация третья.** Вы пишете класс `Point` с двумя координатами. Полей два, а кода — сорок строк: конструктор, геттеры, `equals`, `hashCode`, `toString`. И всё это ради того, чтобы хранить два числа, которые не меняются. Скучно, многословно, и легко ошибиться.

**Ситуация четвёртая.** Вы работаете с JSON. Сервер возвращает `{"name": "Алиса", "age": 30}`. Вам нужно превратить это в объект. Можно написать класс с полями, геттерами, сеттерами, `equals`, `hashCode`, `toString` — сорок строк ради двух полей. А можно написать `record User(String name, int age)` — и получить всё то же самое в одну строку.

**Ситуация пятая.** Вы пишете DTO для передачи данных между слоями. У класса пять полей, все `final`, все `private`, есть геттеры, конструктор, `equals`, `hashCode`, `toString`. Класс длиной в сотню строк. И вы ловите себя на мысли: а нельзя ли как-то короче? Ведь вся эта сотня строк — это шаблон, а не бизнес-логика.

**Ситуация шестая.** Вы видите в чужом коде `record Money(BigDecimal amount, String currency)` — и не понимаете, что это. Новый синтаксис? Какой-то фреймворк? Или что-то из стандартной библиотеки? И почему у него нет геттеров в привычном виде?

Если последняя ситуация вам знакома — этот урок для вас. Если остальные тоже — отлично, вы уже сталкивались с обеими темами, осталось связать их вместе.

## Классы-обёртки: зачем они нужны

В Java есть восемь примитивных типов: `byte`, `short`, `int`, `long`, `float`, `double`, `char`, `boolean`. Они хранят значения напрямую, работают быстро, но у них есть один недостаток: **они не объекты**. А значит, их нельзя использовать там, где нужны объекты.

А нужно это часто. Вот три главные причины.

**Коллекции.** `ArrayList`, `HashMap`, `HashSet` и все остальные работают только с объектами. Нельзя написать `List<int>` — только `List<Integer>`. Потому что коллекции внутри используют `Object` для хранения, а примитивы не наследуются от `Object`.

**Обобщения (generics).** То же самое: `List<T>`, `Map<K, V>`, `Optional<T>` — везде `T` должен быть ссылочным типом. Нельзя `Optional<int>` — только `Optional<Integer>`.

**Случаи, когда нужно именно «нет значения».** У `int` всегда есть значение, даже если вы его не задавали (это `0`). А иногда нужно выразить «значения нет» — и для этого используется `null`. Но `null` может хранить только ссылочный тип. Поэтому `Integer` может быть `null`, а `int` — нет.

Для каждой примитивной «вещи» в Java есть класс-обёртка:

| Примитив | Обёртка |
|---|---|
| `byte` | `Byte` |
| `short` | `Short` |
| `int` | `Integer` |
| `long` | `Long` |
| `float` | `Float` |
| `double` | `Double` |
| `char` | `Character` |
| `boolean` | `Boolean` |

Все они, кроме `Character` и `Boolean`, наследуются от `Number`. И все они — **неизменяемые**. `Integer` нельзя изменить после создания. Это делает их безопасными: их можно передавать куда угодно, и никто не сможет «подкрутить» значение.

## Автобоксинг и его ловушки

Когда вы пишете `Integer x = 5;`, Java автоматически создаёт объект `Integer` со значением 5. Это называется **автобоксинг** (autoboxing) — автоматическое «заворачивание» примитива в обёртку. Обратное — **автоупаковка** (unboxing) — происходит, когда вы пишете `int y = x;` (где `x` — `Integer`): Java автоматически «разворачивает» объект в примитив.

Автобоксинг делает код красивее: не нужно писать `new Integer(5)` вручную (кстати, этот конструктор устарел, использовать его не надо — есть `Integer.valueOf(5)`). Но у автобоксинга есть **ловушки**, и о них нужно знать.

### Ловушка 1: == сравнивает ссылки, а не значения

```java
Integer a = 100;
Integer b = 100;
System.out.println(a == b);   // true

Integer c = 1000;
Integer d = 1000;
System.out.println(c == d);   // false
```

Почему так? Потому что для значений от −128 до 127 Java **кэширует** объекты `Integer`. Когда вы пишете `Integer a = 100`, Java возвращает один и тот же объект из кэша. Поэтому `a == b` — это `true` (одна и та же ссылка). А для 1000 кэша нет, каждый раз создаётся новый объект, и `c == d` — `false`.

**Как правильно сравнивать:** через `.equals()`.

```java
System.out.println(c.equals(d));   // true
```

Это, кстати, общее правило для всех объектов: `==` сравнивает ссылки, `.equals()` — значения. Мы будем говорить об этом подробнее в уроке про `equals` и `hashCode` (если он будет в курсе) — но запомните главное: **для `Integer`, `Long`, `Double` и других обёрток используйте `.equals()`, а не `==`**.

### Ловушка 2: NPE при распаковке

```java
Integer x = null;
int y = x;   // NullPointerException
```

Если `Integer` равен `null`, а вы пытаетесь «развернуть» его в `int` — Java не знает, что делать, и бросает `NullPointerException`. Это особенно коварно, потому что выглядит как обычное присваивание, и ошибка возникает не там, где вы ожидали.

**Как избежать:** проверять на `null` перед распаковкой или использовать `Objects.requireNonNull` для валидации на границе.

### Ловушка 3: лишние объекты

```java
long sum = 0;
for (int i = 0; i < 1_000_000; i++) {
    sum += i;   // если sum — Long, каждый раз создаётся новый объект
}
```

Если в цикле используется обёртка вместо примитива, — на каждой итерации создаётся новый объект (или берётся из кэша). Для миллиона итераций это заметно. В горячем коде лучше использовать примитивы, а обёртки — только там, где без них не обойтись (например, в коллекциях).

## record: неизменяемые данные без boilerplate

Теперь про `record`. Это относительно новая возможность Java (появилась в Java 14 как preview, стала стабильной в Java 16). Идея простая: **если вам нужен класс, который только хранит набор значений и не меняется, — не пишите сорок строк, напишите одну**.

Вот как это выглядит:

```java
public record Point(int x, int y) {}
```

И всё. Это полноценный класс, у которого:

- есть два `private final` поля — `x` и `y`;
- есть конструктор `Point(int x, int y)`;
- есть геттеры `x()` и `y()` (без `get`, это важно);
- есть `equals`, `hashCode`, `toString` — все корректно реализованы;
- класс `final` — от него нельзя наследоваться;
- класс неизменяемый — полей изменить нельзя.

Всё, что мы в прошлом уроке писали руками, `record` генерирует автоматически. И генерирует **правильно**: `equals` сравнивает все поля, `hashCode` использует все поля, `toString` печатает все поля в формате `Point[x=3, y=5]`. Это огромная экономия и — что важнее — меньше шансов ошибиться.

Сравните:

```java
// Без record
final class Point {
    private final int x;
    private final int y;

    Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public int getX() { return x; }
    public int getY() { return y; }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Point point = (Point) o;
        return x == point.x && y == point.y;
    }

    @Override
    public int hashCode() {
        return 31 * x + y;
    }

    @Override
    public String toString() {
        return "Point[x=" + x + ", y=" + y + "]";
    }
}
```

```java
// С record
public record Point(int x, int y) {}
```

Разница очевидна. И, что важно: во втором варианте **невозможно** забыть про `equals` или сделать его неправильно. `record` генерирует всё корректно, и вам не нужно об этом думать.

## Что можно делать с record

`record` — это не «просто класс с автогенерацией». Это полноценный класс, и в нём можно:

### Добавлять методы

```java
public record Point(int x, int y) {
    public double distanceTo(Point other) {
        int dx = this.x - other.x;
        int dy = this.y - other.y;
        return Math.sqrt(dx * dx + dy * dy);
    }

    public Point translate(int dx, int dy) {
        return new Point(this.x + dx, this.y + dy);
    }
}
```

`distanceTo` — обычный метод. `translate` — метод, возвращающий **новый** `record` (потому что старый нельзя изменить).

### Реализовывать интерфейсы

```java
public record Point(int x, int y) implements Comparable<Point> {
    @Override
    public int compareTo(Point other) {
        int cmp = Integer.compare(this.x, other.x);
        if (cmp != 0) return cmp;
        return Integer.compare(this.y, other.y);
    }
}
```

`record` **не может** наследоваться от класса (потому что он сам `final`), но может реализовывать интерфейсы. Это важно: вы не можете «расширить» `record` через наследование, но можете дать ему контракт.

### Валидировать в компактном конструкторе

Если нужно проверить значения при создании, — используется **компактный конструктор**:

```java
public record Range(int from, int to) {
    public Range {
        if (from > to) {
            throw new IllegalArgumentException(
                "Начало диапазона не может быть больше конца: " + from + " > " + to);
        }
    }
}
```

Обратите внимание на синтаксис: `public Range { ... }` — без параметров. Java сама подставит все поля. Внутри вы можете их проверить, но **не можете присвоить** — присваивание происходит автоматически после тела компактного конструктора.

Компактный конструктор — это то место, где живёт **валидация** `record`. Он гарантирует, что объект не появится на свет в невалидном состоянии. Это ровно то, о чём мы говорили в уроке 4 (валидация в конструкторах) и в уроке 5 (неизменяемые объекты).

### Переопределять геттеры (редко)

Иногда нужно, чтобы геттер возвращал не то, что в поле. Например, для нормализации:

```java
public record Email(String value) {
    public Email {
        if (value == null || !value.contains("@")) {
            throw new IllegalArgumentException("Некорректный email");
        }
        value = value.toLowerCase().trim();   // нормализация в компактном конструкторе
    }
}
```

Обратите внимание: в компактном конструкторе можно присвоить **параметру** — и это повлияет на значение поля. Тонкость: это работает только в компактном конструкторе, не в обычном. Об этом полезно помнить.

## Чего record не умеет

`record` — мощный инструмент, но у него есть ограничения, и о них стоит знать.

**Нельзя наследоваться от класса.** `record` всегда `final`. Это логично: если бы можно было наследоваться, наследник мог бы добавить изменяемое поле и сломать неизменяемость. Но иногда это неудобно — например, если вы хотите сделать иерархию `Shape` с `Circle` и `Square`. Здесь `record` не подойдёт, придётся использовать обычные классы или запечатанные иерархии (sealed — это Java 17, выходит за рамки нашего курса).

**Все поля — `final`.** Нельзя сделать «`record` с изменяемым полем». Это принципиально: `record` — это про неизменяемость. Если нужно менять — используйте обычный класс.

**Нет сеттеров.** Только геттеры. Если нужно «изменить» — создавайте новый `record` (как в `translate` выше).

**Геттеры называются без `get`.** `point.x()`, а не `point.getX()`. Это сделано для краткости и для отличия от «настоящих» геттеров. Некоторые библиотеки (например, Jackson) это понимают; некоторые — нет, и приходится настраивать.

**`record` не может быть `abstract`.** Это следствие того, что он `final`.

Всё это — не «недостатки», а **свойства**. `record` создан для конкретной задачи: «неизменяемый набор данных». Если задача другая — `record` не подойдёт, и это нормально.

## Когда record уместен, а когда — нет

`record` — это не «замена класса», а инструмент для конкретной ситуации. Вот когда он уместен.

**DTO и value-объекты.** Если класс только хранит набор значений и не имеет поведения (или имеет очень простое), — `record`. `Point`, `Range`, `Money`, `UserCredentials`, `ApiResponse`.

**Возврат из методов.** Если метод возвращает несколько значений — например, результат операции с признаком успеха и сообщением — `record` идеален.

**Ключи для `Map`.** `record` автоматически имеет корректные `equals` и `hashCode`. Значит, его можно использовать как ключ в `HashMap`. Обычный класс для этого нужно было бы снабдить `equals`/`hashCode` вручную, и легко ошибиться.

**Промежуточные данные.** Если вы парсите JSON и хотите временно сложить результат в объект — `record` короче и безопаснее обычного класса.

Когда `record` **не** уместен.

**Класс с изменяемым состоянием.** Счётчик, корзина, соединение с базой — всё это должно быть обычными классами.

**Класс с богатым поведением.** Если у класса десять методов, которые активно работают с полями, — `record` может быть неудобен: он не даёт «спрятать» поля за приватными геттерами. Поля `record` всегда доступны через геттеры. Для value-объектов это нормально, но для «настоящего» класса с инкапсуляцией — не очень.

**Класс с наследованием.** Если нужна иерархия — `record` не подойдёт.

**Класс с ленивой инициализацией.** `record` инициализирует всё в конструкторе. Если вам нужно «вычислять при первом обращении» — это обычный класс.

Общее правило: **`record` — для данных, класс — для поведения и состояния**. Если ваш класс — это «мешок со значениями», который не меняется, — `record`. Если это «живая» сущность с изменяемым состоянием и сложным поведением — обычный класс.

## Аналогия, которая помогает

Хорошая аналогия — **паспорт и ежедневник**.

**`record` — это паспорт.** У него есть фиксированный набор полей: имя, фамилия, дата рождения, номер. Все они задаются при выдаче и не меняются. Вы не можете «дописать» в паспорт новое поле или исправить дату рождения. Если что-то меняется (например, фамилия) — вы получаете **новый** паспорт. Паспорт нельзя изменить, но можно создать новый на основе старого. И ещё: два паспорта с одинаковыми данными — это, по сути, один и тот же паспорт (для целей сравнения), хотя физически это два разных документа. Это `equals` и `hashCode` в действии.

**Класс-обёртка — это тоже паспорт, но попроще.** `Integer` — это «паспорт числа». Он хранит одно значение, которое не меняется. Вы не можете «поменять» `Integer` с 5 на 10; вы создаёте новый `Integer` со значением 10. И маленькие числа (от −128 до 127) выдаются «из запаса» — как будто у государства есть стопка готовых паспортов для типовых значений.

**Обычный класс — это ежедневник.** В нём можно писать, стирать, добавлять страницы, менять обложку. Он живой, он меняется. Для ежедневника `record` не подойдёт — он не даст вам менять записи.

И ещё одна параллель: **паспорт — это ценность сам по себе**. Вы можете передать его другому человеку, и он будет точно знать, что это ваш паспорт, а не чей-то ещё. Так же и `record` — это значение, которое можно безопасно передавать куда угодно: оно не изменится, и никто не сможет его «подкрутить». Это и есть смысл неизменяемости, о которой мы говорили в прошлом уроке.

## Микрозадача 1

Вот код. Что выведется в каждом `println`? Объясните результат.

```java
Integer a = 127;
Integer b = 127;
System.out.println(a == b);

Integer c = 128;
Integer d = 128;
System.out.println(c == d);

System.out.println(c.equals(d));
```

### Разбор

Выведется:

```
true
false
true
```

Разберём по шагам.

`Integer a = 127; Integer b = 127;` — 127 попадает в диапазон кэша (`−128..127`). Java возвращает один и тот же объект из кэша для обоих значений. Поэтому `a` и `b` — это **одна и та же ссылка**, и `a == b` даёт `true`.

`Integer c = 128; Integer d = 128;` — 128 **не** попадает в кэш. Java создаёт **два разных объекта**, хотя значения у них одинаковые. `c == d` сравнивает ссылки, а они разные, поэтому `false`.

`c.equals(d)` — сравнивает значения. 128 равно 128, поэтому `true`.

Это классическая ловушка. И именно поэтому **для обёрток всегда используйте `.equals()`, а не `==`**. Единственное исключение — когда вы точно знаете, что значения в диапазоне кэша (но полагаться на это не стоит: код может измениться, и значения выйдут за пределы).

Кстати, размер кэша можно настроить параметром JVM `-XX:AutoBoxCacheMax=...`, но в обычном коде на это лучше не рассчитывать.

## Микрозадача 2

Вот `record`. Что с ним не так?

```java
public record User(String name, java.util.List<String> roles) {
    public User {
        if (name == null || name.isEmpty()) {
            throw new IllegalArgumentException("Имя не может быть пустым");
        }
    }
}
```

### Разбор

Первая часть — в порядке: компактный конструктор проверяет `name`. Но есть проблема с `roles`.

`roles` — это `List<String>`. Он `final`, но `final` защищает только **ссылку**, а не сам список. Список можно менять. А значит, `record` **не является по-настоящему неизменяемым**.

Вот как это ломается:

```java
java.util.List<String> list = new java.util.ArrayList<>();
list.add("admin");

User user = new User("Алиса", list);
user.roles().add("superadmin");   // добавляем снаружи

System.out.println(user.roles());   // [admin, superadmin]
```

Мы изменили `record`, хотя он должен быть неизменяемым. Это та же проблема, что была в уроке 5 с `hobbies` у `Person`.

**Как исправить:** защитное копирование в компактном конструкторе.

```java
public record User(String name, java.util.List<String> roles) {
    public User {
        if (name == null || name.isEmpty()) {
            throw new IllegalArgumentException("Имя не может быть пустым");
        }
        roles = java.util.List.copyOf(roles);   // копия, которую никто не изменит
    }
}
```

`List.copyOf` создаёт **неизменяемую** копию. Теперь:

- снаружи нельзя изменить через исходный список — `record` хранит копию;
- снаружи нельзя изменить через геттер — копия неизменяемая (`add` выбросит `UnsupportedOperationException`).

**Мораль.** `record` автоматически делает **поля** `final`, но не делает **содержимое полей** неизменяемым. Если поле — изменяемый объект (список, массив, `Date`), — нужно защитное копирование. Это ровно то, о чём мы говорили в уроке 5, и `record` от этой проблемы не защищает. Он её **упрощает** (потому что конструктор один, и копирование достаточно сделать в одном месте), но не убирает.

Кстати, это же касается и геттеров: `record` автоматически генерирует геттер `roles()`, который возвращает **тот же** список, что лежит в поле. Если бы мы не сделали копию в конструкторе, — этот геттер «утекал» бы внутреннее состояние наружу. `record` не помогает с этим — он только генерирует геттер, а что именно возвращать — ваша забота.

Это мощный инструмент, но и опасный: им часто злоупотребляют, и в этом модуле мы разберёмся, когда наследование уместно, а когда — нет. Задайте вопрос: **а это `record`?** Если класс состоит только из `final`-полей, конструктора, геттеров и, может быть, `equals`/`hashCode`/`toString` — возможно, его стоило бы сделать `record`. Если класс имеет изменяемое состояние или сложное поведение — `record` не подойдёт. Просто посмотрите. Не переделывайте (пока). Понимание того, где `record` уместен, — уже большой шаг к более чистому коду.

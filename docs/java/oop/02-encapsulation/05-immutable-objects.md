# 5. Неизменяемые объекты

## Где вы это уже видели

До сих пор мы всё время исходили из того, что объект можно менять. Создали счёт — пополнили, списали, ещё раз пополнили. Создали пользователя — поменяли почту, потом ещё раз. Это естественно: вещи в жизни меняются, и объекты в программе тоже.

Но есть целый класс вещей, которые **не меняются после создания**. И чем дальше, тем чаще программисты ими пользуются — потому что это невероятно удобно. В этом уроке мы разберёмся, что такое неизменяемые объекты, зачем они нужны, и почему они часто оказываются **проще**, а не сложнее, чем изменяемые.

**Ситуация первая.** Вы пишете дату рождения в паспорт. Она не меняется. Никогда. Вы можете поменять фамилию, прописку, даже пол — но дата рождения остаётся той же. В программе это естественно выразить через неизменяемое поле: дата рождения задаётся один раз и больше не трогается. А если кто-то попытается её изменить — это ошибка, а не норма.

**Ситуация вторая.** Вы получаете чек в магазине. На нём — номер, дата, список товаров, сумма. Чек не меняется после печати. Вы можете его выбросить, можете сохранить, можете отсканировать — но сам чек остаётся тем же. Если бы чек можно было менять, он был бы бесполезен как документ: кто угодно мог бы дописать туда пару нулей.

**Ситуация третья.** Вы работаете с координатами на карте. Москва находится на 55.7558° северной широты и 37.6173° восточной долготы. Это координаты — они не меняются. Вы можете создать **новую** точку (например, «Москва, Кремль»), но координаты самой Москвы — константа. В программе это естественно выражается через неизменяемый объект `Point`.

**Ситуация четвёртая.** Вы отправляете письмо. Вы пишете его, запечатываете в конверт, наклеиваете марку, опускаете в ящик. После этого письмо **уже не изменить**. Если вы захотите что-то поправить — придётся писать новое письмо. Это не ограничение, это **гарантия**: получатель точно знает, что то, что он получил, — это ровно то, что вы отправили.

**Ситуация пятая.** Вы смотрите на ценник в магазине. Цена — 199 рублей. Вы не можете подойти и написать «99 рублей». Ценник неизменяем. Чтобы изменить цену, магазин печатает **новый** ценник. И пока новый не напечатан — все видят старый. Это свойство очень полезно: никто не может «подкрутить» цену в свою пользу.

**Ситуация шестая.** Вы пишете класс `Money` для работы с деньгами. У него есть поля «сумма» и «валюта». И вы ловите себя на мысли: а что если кто-то возьмёт объект «100 рублей», вызовет у него `setAmount(1000000)` — и на счету станет миллион? Хорошо бы, чтобы так было нельзя.

Если последняя ситуация вам знакома — этот урок для вас. Если остальные тоже — отлично, интуиция про «вещи, которые не меняются» у вас уже есть, осталось связать её с кодом.

## Что такое неизменяемый объект

**Неизменяемый объект** (immutable object) — это объект, состояние которого **не может измениться после создания**. Ни снаружи, ни изнутри. Совсем.

Вот как это выглядит в коде:

```java
final class Point {
    private final int x;
    private final int y;

    public Point(int x, int y) {
        this.x = x;
        this.y = y;
    }

    public int getX() { return x; }
    public int getY() { return y; }
}
```

Что здесь важно:

**Класс `final`.** Это значит, что от него нельзя отнаследоваться. Почему — объясню чуть ниже, но идея такая: если бы кто-то мог отнаследоваться, он мог бы добавить изменяемое поле и сломать неизменяемость.

**Поля `private final`.** `private` — чтобы снаружи не лезли. `final` — чтобы нельзя было присвоить повторно, даже изнутри класса. После конструктора поле уже не изменится.

**Нет сеттеров.** Есть только геттеры. И это принципиально: если бы был сеттер, объект был бы изменяемым.

Вот и всё. Объект `Point(3, 5)` — это точка с координатами (3, 5). Навсегда. Если вам нужна точка (4, 5), — вы создаёте **новый** объект, а не меняете старый.

```java
Point p1 = new Point(3, 5);
Point p2 = new Point(4, 5);   // новый объект, p1 не изменился

System.out.println(p1.getX());   // 3
System.out.println(p2.getX());   // 4
```

Это может показаться неудобным: чтобы «сдвинуть» точку на единицу вправо, нужно создавать новую. Но это **не неудобство**, а **гарантия**: никто не может изменить вашу точку за вашей спиной.

## Зачем это нужно

Неизменяемость кажется ограничением. «Что значит, я не могу поменять поле? А если мне нужно?» — это естественная реакция. Но у неизменяемости есть несколько очень весомых преимуществ, которые часто перевешивают неудобство.

### Безопасность в многопоточной среде

Это, пожалуй, главное. Когда несколько потоков работают с одним объектом, и объект можно менять, — возникает **состояние гонки** (race condition). Один поток читает значение, другой в это время пишет — и первый может увидеть «половину» изменения.

```java
class Counter {
    private int value;
    public void increment() { value++; }
    public int getValue() { return value; }
}
```

Если два потока одновременно вызовут `increment()`, значение может увеличиться на 1, а не на 2. Потому что `value++` — это не одна операция, а три: прочитать, прибавить, записать. Между ними может вклиниться другой поток.

С неизменяемым объектом такой проблемы нет: если объект нельзя изменить, — нечего и синхронизировать. Каждый поток работает со своей копией или с общим «снимком», и никто никому не мешает.

```java
final class Counter {
    private final int value;
    public Counter(int value) { this.value = value; }
    public Counter increment() { return new Counter(value + 1); }
    public int getValue() { return value; }
}
```

Теперь `increment()` возвращает **новый** объект, а не меняет старый. Два потока могут спокойно вызывать `increment()` у одного и того же `Counter` — каждый получит свой новый объект, и никакой гонки нет.

Это, кстати, одна из причин, почему неизменяемость так популярна в современном программировании: многопоточность — сложная, и всё, что её упрощает, — на вес золота. Но об этом мы поговорим подробно в модуле про многопоточность; пока что просто запомните: **неизменяемость — это способ не думать о гонках**.

### Безопасное использование в коллекциях

Если объект используется как ключ в `HashMap` или как элемент в `HashSet`, — его **нельзя менять**. Иначе коллекция «сломается»: хеш-код изменится, и элемент станет недоступен.

```java
class Point {
    private int x, y;
    // ... геттеры и сеттеры ...
}

Map<Point, String> map = new HashMap<>();
Point p = new Point(3, 5);
map.put(p, "Точка А");

p.setX(10);   // изменили объект, который уже в мапе
System.out.println(map.get(p));   // null — потому что хеш изменился
```

С неизменяемым `Point` такого не случится: объект нельзя изменить, и хеш-код всегда один и тот же. Это делает неизменяемые объекты идеальными ключами для `Map` и элементами для `Set`.

### Безопасная передача между компонентами

Если вы передаёте изменяемый объект в другой класс, — вы не знаете, что он с ним сделает. Может, прочитает, а может — изменит и вернёт «испорченным». С неизменяемым объектом такой проблемы нет: что бы с ним ни делали, — он останется тем же.

```java
class Order {
    private final List<Item> items;

    public Order(List<Item> items) {
        this.items = List.copyOf(items);   // копия, которую никто снаружи не изменит
    }

    public List<Item> getItems() {
        return items;   // неизменяемый список — можно отдавать
    }
}
```

Здесь `List.copyOf` создаёт неизменяемую копию. Внутри `Order` — свой список, снаружи — свой. Изменение внешнего не затронет внутренний.

### Простота рассуждений

Это, может быть, самое важное, хотя и самое незаметное. Когда объект неизменяем, вам не нужно думать о том, **кто и когда его изменил**. Вы создали `Point(3, 5)` — и знаете, что это всегда `(3, 5)`. Через минуту, через час, в другом потоке — всегда `(3, 5)`.

С изменяемым объектом всё сложнее: вы создали `Point(3, 5)`, а через минуту кто-то его поменял на `(10, 20)`. И вы не знаете, кто и зачем. Вам нужно проследить всю цепочку вызовов, чтобы понять, что произошло. В большом проекте это может занять часы.

Неизменяемость **убирает целый класс проблем**: не нужно искать, кто изменил объект, не нужно защищаться от concurrent modification, не нужно думать о defensive copying на каждом шагу. Объект — это просто значение, и он всегда один и тот же.

## Как сделать объект неизменяемым

Есть несколько правил, которые нужно соблюсти, чтобы объект был по-настоящему неизменяемым.

### Правило 1: все поля final

Если поле не `final`, — его можно переприсвоить изнутри класса. Даже если сеттера нет, кто-то может добавить метод, который это сделает.

```java
class Point {
    private int x;   // не final — уже не неизменяемый
    // ...
}
```

`final` гарантирует, что после конструктора поле не изменится.

### Правило 2: все поля private

Если поле `public`, — его можно изменить снаружи. `final` в этом случае не поможет: `final` запрещает **переприсваивание**, но не изменение самого объекта (если объект изменяемый). А для примитивов `final` действительно запрещает изменение. Но `public final int x` всё равно плохо: вы жёстко фиксируете представление, и завтра не сможете поменять `int` на `long`, не сломав всех клиентов.

### Правило 3: нет сеттеров

Если есть сеттер — объект можно изменить. Точка.

### Правило 4: класс final (или конструктор private)

Если от класса можно отнаследоваться, — наследник может добавить изменяемое поле и сломать неизменяемость. Пример:

```java
class Point {
    private final int x, y;
    // ...
}

class MutablePoint extends Point {
    private int x, y;   // своё, изменяемое
    // теперь MutablePoint — не неизменяемый, хотя Point — да
}
```

`final` на классе запрещает наследование и защищает от такой проблемы. Альтернатива — сделать все конструкторы `private` и создавать объекты через статические фабричные методы. Тогда отнаследоваться тоже нельзя (потому что наследник не сможет вызвать `super()`). О фабричных методах мы поговорим позже.

### Правило 5: защитное копирование изменяемых полей

Если поле — изменяемый объект (список, массив, `Date`), — `final` не спасёт: сам объект можно изменить, даже если ссылка на него неизменна.

```java
final class Order {
    private final java.util.List<Item> items;

    public Order(java.util.List<Item> items) {
        this.items = items;   // плохо: снаружи могут изменить
    }

    public java.util.List<Item> getItems() {
        return items;   // плохо: снаружи могут изменить
    }
}
```

Здесь `items` — `final`, но список можно менять. `order.getItems().add(...)` сработает, и объект «изменится».

**Решение** — копировать список при приёме и при выдаче:

```java
final class Order {
    private final java.util.List<Item> items;

    public Order(java.util.List<Item> items) {
        this.items = java.util.List.copyOf(items);   // копия при приёме
    }

    public java.util.List<Item> getItems() {
        return items;   // неизменяемый список — можно отдавать
    }
}
```

`List.copyOf` создаёт **неизменяемую** копию. Теперь список внутри `Order` нельзя изменить ни снаружи, ни через геттер.

Если по каким-то причинам нельзя использовать `List.copyOf` (например, используется `java.util.Date`), — копируйте вручную:

```java
public Order(java.util.Date date) {
    this.date = new java.util.Date(date.getTime());
}

public java.util.Date getDate() {
    return new java.util.Date(date.getTime());
}
```

Это и есть **защитное копирование** (defensive copying). Мы о нём говорили в уроке 10, но здесь оно критично: без него объект не будет по-настоящему неизменяемым.

### Правило 6: не «утекать» this в конструкторе

Тонкое правило, о котором часто забывают. Если в конструкторе вы передаёте `this` куда-то наружу (например, регистрируете объект в каком-то реестре), — снаружи могут получить доступ к объекту **до того, как он полностью инициализирован**. Это может привести к странным багам.

```java
final class Point {
    private final int x, y;

    public Point(int x, int y) {
        Registry.register(this);   // плохо: this «утекает» до инициализации
        this.x = x;
        this.y = y;
    }
}
```

В нашем случае это не так страшно (поля `final` и инициализируются сразу после), но в общем случае — избегайте. Об этом мы поговорим подробнее, когда будем разбирать многопоточность.

## String — неизменяемый по природе

Самый известный пример неизменяемого класса в Java — `String`. Строки неизменяемы: любая «модификация» создаёт новую строку.

```java
String s = "Привет";
s.toUpperCase();           // создаёт новую строку, s не меняется
System.out.println(s);     // Привет (а не ПРИВЕТ)

s = s.toUpperCase();       // теперь s указывает на новую строку
System.out.println(s);     // ПРИВЕТ
```

Обратите внимание: `s.toUpperCase()` **не меняет** `s`. Он возвращает **новую** строку. Чтобы «изменить» `s`, нужно присвоить результат обратно. И это не «изменение» исходной строки, а замена ссылки на новую.

Почему `String` сделали неизменяемым? Причин несколько.

**Безопасность.** Строки используются везде — в именах файлов, URL, SQL-запросах, путях к классам. Если бы их можно было менять, — злоумышленник мог бы подменить путь к файлу или SQL-запрос. Неизменяемость это предотвращает.

**Кэширование.** Строки часто кэшируются (например, в пуле строк). Если бы строку можно было изменить, — кэш бы сломался.

**Потокобезопасность.** Строки можно безопасно использовать в многопоточной среде, потому что их нельзя изменить.

**Хеширование.** `String` — идеальный ключ для `HashMap`: хеш-код вычисляется один раз и не меняется.

Именно поэтому `String` — это эталон неизменяемого класса в Java, и на него стоит ориентироваться, когда проектируете свои неизменяемые классы.

## Когда неизменяемость — плохая идея

Не бывает универсальных решений, и неизменяемость — не исключение. Есть случаи, когда она неуместна.

**Объекты с большим состоянием.** Если объект содержит гигабайт данных, и вы меняете в нём одно поле, — создавать копию всего объекта накладно. В таких случаях изменяемость оправдана.

**Объекты, которые часто меняются.** Если у вас счётчик, который увеличивается миллион раз в секунду, — создавать миллион новых объектов — расточительно. Изменяемый счётчик с синхронизацией может быть эффективнее.

**Объекты, которые представляют «процесс».** Например, `Connection` к базе данных, `Thread`, `FileInputStream`. Это не «значения», а «живые» сущности, и они меняются по своей природе. Делать их неизменяемыми — значит ломать их смысл.

**Когда важна производительность.** В некоторых случаях изменяемость даёт выигрыш. Например, в алгоритмах, где объекты переиспользуются (object pooling). Но это редко, и обычно не стоит того, чтобы усложнять код.

Общее правило: **начинайте с неизменяемости, а изменяемость добавляйте только там, где она действительно нужна**. Это проще, чем наоборот: добавить изменяемость к неизменяемому классу — легко (просто убрать `final`), а сделать изменяемый класс неизменяемым — большая работа (нужно найти всех, кто его меняет, и переписать).

## Аналогия, которая помогает

Хорошая аналогия — **печатная книга и доска с мелом**.

**Печатная книга** — это неизменяемый объект. Вы не можете изменить текст в ней. Можете читать, можете делать пометки на полях (но это не меняет книгу), можете купить вторую такую же — но сама книга всегда одна и та же. Если в книге опечатка, — её исправляют в **новом** издании, а старое остаётся с опечаткой. Это неудобно, но зато **надёжно**: у всех читателей один и тот же текст, и никто не может его «подкрутить».

**Доска с мелом** — это изменяемый объект. Вы можете писать, стирать, переписывать. Это удобно, но у этого есть цена: если на доске пишут двое, — они мешают друг другу. Если один стёр, а другой не заметил — путаница. И «что было на доске минуту назад» — уже не восстановить.

В программировании чаще всего хочется именно **печатную книгу**: стабильность, предсказуемость, безопасность. Доска с мелом нужна там, где действительно нужно быстро менять (счётчики, буферы, состояние интерфейса). Но по умолчанию — книга.

И ещё одна деталь: **книга может содержать вклейки с исправлениями**. Это аналог «изменяемого поля внутри неизменяемого объекта» — и это нормально, если вклейки тоже неизменяемые (например, `final`-поле, которое указывает на неизменяемый объект). Но если вклейку можно менять (дописать что-то от руки) — книга перестаёт быть надёжной. Это и есть проблема с изменяемыми полями внутри неизменяемого класса: они «пробивают» неизменяемость.

## Микрозадача 1

Вот класс. Определите, неизменяемый ли он. Если нет — что нужно исправить?

```java
class Money {
    private final double amount;
    private final String currency;

    public Money(double amount, String currency) {
        this.amount = amount;
        this.currency = currency;
    }

    public double getAmount() { return amount; }
    public String getCurrency() { return currency; }
}
```

### Разбор

Класс **почти** неизменяемый, но есть две проблемы.

**Первая: нет `final` на классе.** Кто-то может отнаследоваться и добавить изменяемое поле. Формально сам `Money` неизменяем, но наследник — нет. Это может привести к путанице: если вы передаёте `Money` куда-то, вы ожидаете неизменяемости, а получите наследника, который можно менять.

**Вторая: `double` для денег.** Это не про неизменяемость, а про корректность. `double` не подходит для денег: `0.1 + 0.2` даст `0.30000000000000004`, а не `0.3`. Для денег нужно использовать `BigDecimal` (или `long` с копейками). Это не делает класс изменяемым, но делает его **неправильным** — и это важнее, чем неизменяемость.

**Третья: нет валидации.** `new Money(-100, "RUB")` создаст объект с отрицательной суммой. Если такое допустимо (например, для долга) — нормально. Если нет — нужно проверять в конструкторе. Это тоже не про неизменяемость, но про корректность.

**Как исправить:**

```java
final class Money {
    private final java.math.BigDecimal amount;
    private final String currency;

    public Money(java.math.BigDecimal amount, String currency) {
        if (amount == null) {
            throw new IllegalArgumentException("Сумма не может быть null");
        }
        if (currency == null || currency.isEmpty()) {
            throw new IllegalArgumentException("Валюта не может быть пустой");
        }
        this.amount = amount;
        this.currency = currency;
    }

    public java.math.BigDecimal getAmount() { return amount; }
    public String getCurrency() { return currency; }

    public Money plus(Money other) {
        if (!this.currency.equals(other.currency)) {
            throw new IllegalArgumentException("Нельзя складывать разные валюты");
        }
        return new Money(this.amount.add(other.amount), this.currency);
    }
}
```

Теперь всё в порядке: `final` на классе, `BigDecimal` для денег, валидация в конструкторе, и метод `plus` возвращает **новый** объект, а не меняет старый. Это классический пример неизменяемого класса.

Обратите внимание на `plus`: это не сеттер, это операция, которая **создаёт новое значение**. Так и должно быть в неизменяемом классе: вместо `setAmount` — `plus`, вместо `setX` — `withX`, и все они возвращают новые объекты.

## Микрозадача 2

Вот класс. Он выглядит неизменяемым, но на самом деле нет. Найдите проблему.

```java
final class Person {
    private final String name;
    private final java.util.List<String> hobbies;

    public Person(String name, java.util.List<String> hobbies) {
        this.name = name;
        this.hobbies = hobbies;
    }

    public String getName() { return name; }
    public java.util.List<String> getHobbies() { return hobbies; }
}
```

### Разбор

Проблема в поле `hobbies`. Оно `final`, но `final` защищает только **ссылку**, а не сам объект. Список можно менять.

**Как это ломается:**

```java
java.util.List<String> list = new java.util.ArrayList<>();
list.add("Чтение");

Person p = new Person("Алиса", list);
p.getHobbies().add("Плавание");   // добавляем снаружи

System.out.println(p.getHobbies());   // [Чтение, Плавание]
```

Объект `Person` изменился, хотя должен был быть неизменяемым. И через исходный `list` тоже можно менять:

```java
list.add("Бег");
System.out.println(p.getHobbies());   // [Чтение, Плавание, Бег]
```

**Как исправить:**

```java
final class Person {
    private final String name;
    private final java.util.List<String> hobbies;

    public Person(String name, java.util.List<String> hobbies) {
        this.name = name;
        this.hobbies = java.util.List.copyOf(hobbies);   // копия при приёме
    }

    public String getName() { return name; }
    public java.util.List<String> getHobbies() { return hobbies; }   // неизменяемый — можно отдавать
}
```

`List.copyOf` создаёт неизменяемую копию. Теперь:

- снаружи нельзя изменить через исходный `list` — потому что `Person` хранит копию;
- снаружи нельзя изменить через геттер — потому что копия неизменяемая (`add` выбросит `UnsupportedOperationException`).

**Мораль.** `final` — это не про неизменяемость объекта, а про неизменяемость ссылки. Если поле — изменяемый объект, `final` не делает класс неизменяемым. Нужны либо копии, либо неизменяемые типы. Об этом мы говорили в уроке 10, но здесь это критично: без защитного копирования класс не будет по-настоящему неизменяемым.

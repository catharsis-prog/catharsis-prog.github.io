# 2. Модификаторы доступа

## Где вы это уже видели

В прошлом уроке мы говорили, зачем скрывать данные, и всё время повторяли слово `private`. Пора разобраться, что это за слово и какие ещё бывают.

В Java есть четыре уровня доступа. Они определяют, кто может видеть поле, метод или класс. Синтаксически это выглядит как одно слово перед объявлением — но за этим словом стоит целая система правил, и от неё зависит, насколько хорошо ваш код защищён.

Прежде чем идти в теорию, посмотрим, где эта идея встречается в жизни.

**Ситуация первая.** Вы работаете в офисе. У вас есть **личный стол** — туда никто не лезет без спроса. Есть **общий стол переговоров** в комнате совещаний — туда можно положить документы, и все увидят. Есть **доска объявлений в коридоре** — её видит вся компания. И есть **сайт компании в интернете** — его видит весь мир. Четыре уровня доступа, и каждый — для своего.

**Ситуация вторая.** Вы живёте в многоквартирном доме. В **вашей квартире** — только вы и ваша семья. В **подъезде** — соседи по подъезду. **Во дворе** — все жильцы дома. **На улице** — вообще кто угодно. Опять четыре уровня, и они вложены друг в друга как матрёшки: квартира ⊂ подъезд ⊂ двор ⊂ улица.

**Ситуация третья.** Вы пишете в гуглодоке. У документа есть настройки доступа: «только я», «только те, у кого есть ссылка», «все в домене компании», «все в интернете». Четыре варианта, и вы выбираете в зависимости от того, что это за документ. Черновик — «только я». Рабочий документ — «в домене». Пресс-релиз — «все».

**Ситуация четвёртая.** В семье есть понятие «семейное». Это что-то, что не показывают гостям, но все члены семьи знают. Не «личное» (это только твоё), не «публичное» (это все видят), а именно «для своих». Аналог `protected` в Java — доступ для «своих» (наследников), но не для всех.

**Ситуация пятая.** В компании есть **внутренние документы**, которые нельзя показывать клиентам, но можно — всем сотрудникам. Это не «личное» (документ не принадлежит одному человеку), не «публичное» (клиенты не должны видеть). Это аналог `package-private`: доступ внутри «пакета», то есть внутри компании.

**Ситуация шестая.** Вы смотрите на код и видите поле без модификатора:

```java
class User {
    String name;
}
```

— и не понимаете: это `private`? `public`? Или что-то ещё? И можно ли к нему обращаться из другого класса? Ответ зависит от того, в каком пакете этот другой класс — и это сбивает с толку больше всего.

Если последняя ситуация вам знакома — этот урок для вас. Если остальные тоже — отлично, интуиция про «вложенные уровни доступа» у вас уже есть, осталось связать её с синтаксисом Java.

## Четыре уровня доступа

В Java есть четыре модификатора доступа. Вот они, от самого строгого к самому мягкому.

### private

**Доступ только внутри класса.** Никто снаружи, даже из того же пакета, даже наследники — не могут обратиться к `private`-полю или методу.

```java
class User {
    private String password;

    private boolean checkPassword(String input) {
        return password.equals(input);
    }

    public boolean authenticate(String input) {
        return checkPassword(input);   // можно — внутри класса
    }
}
```

Снаружи `user.password` и `user.checkPassword(...)` не скомпилируются. Это самый строгий уровень, и **для полей это уровень по умолчанию**, который стоит выбирать, если нет причин сделать иначе.

### package-private (по умолчанию)

**Доступ внутри пакета.** Если не написать модификатор, поле или метод будут доступны всем классам в том же пакете. Из других пакетов — нет.

```java
package com.example.shop;

class Product {
    String sku;            // package-private
    int stock;             // package-private
}
```

Любой класс в пакете `com.example.shop` может обратиться к `product.sku`. Из пакета `com.example.users` — не может.

Этот уровень часто используется для вспомогательных классов и методов, которые нужны «своим» в пакете, но не должны быть частью публичного API. Но у него есть коварство: **если не написать модификатор, поле не будет закрыто**. Многие начинающие думают, что «по умолчанию — закрыто», и пишут просто `String name;`, ожидая, что это `private`. Это не так. `package-private` — это открытый доступ для всех в пакете.

### protected

**Доступ внутри пакета плюс наследники в других пакетах.** То есть `protected`-поле или метод видны всем классам в том же пакете (как `package-private`) **и** подклассам, даже если они в другом пакете.

```java
package com.example.base;

public class Animal {
    protected String name;   // видно в пакете com.example.base и во всех наследниках

    protected void eat() {
        System.out.println(name + " ест");
    }
}
```

```java
package com.example.zoo;

public class Dog extends Animal {
    public void bark() {
        System.out.println(name + " гавкает");   // можно — name protected и мы наследники
        eat();                                    // можно
    }
}
```

`protected` — самый хитрый уровень. Он используется, когда класс проектируется с расчётом на наследование: «это мои внутренности, но наследники должны иметь к ним доступ, чтобы расширять меня». Мы будем подробно говорить о нём в модуле про наследование. Пока что запомните: **`protected` — для наследников, а не для всех**.

### public

**Доступ отовсюду.** Любой класс из любого пакета может обратиться к `public`-полю или методу.

```java
class User {
    public String name;   // видно всем

    public void greet() {
        System.out.println("Привет, " + name);
    }
}
```

`public` — это «открыто миру». Для методов, которые составляют публичный API класса, это правильно. Для полей — почти всегда неправильно: открытое поле значит, что кто угодно может его испортить.

## Как это выглядит в виде таблицы

Удобно запомнить в виде таблицы, кто кого видит.

| Модификатор | Класс | Пакет | Наследник | Все |
|---|---|---|---|---|
| `private` | ✅ | ❌ | ❌ | ❌ |
| (без модификатора) | ✅ | ✅ | ❌* | ❌ |
| `protected` | ✅ | ✅ | ✅ | ❌ |
| `public` | ✅ | ✅ | ✅ | ✅ |

*Наследник в том же пакете видит `package-private`-члены, потому что он находится в том же пакете. Наследник в другом пакете — не видит.

Ещё одно правило, которое стоит запомнить: **модификатор доступа можно ослабить при переопределении метода, но нельзя усилить**. То есть если метод в родителе `public`, в наследнике он тоже должен быть `public` — нельзя сделать его `private` или `package-private`. Логика простая: наследник не должен «закрывать» то, что родитель открыл. Иначе полиморфизм сломался бы: код, который работал с родителем, не смог бы работать с наследником. Подробно — в модуле про наследование.

## Почему по умолчанию — private

Правило, которое стоит запомнить с самого начала: **поля делайте `private`, если у вас нет веских причин сделать иначе**. И для методов — тоже `private`, пока не доказано, что метод должен быть доступен снаружи.

Причина проста: **с каждым открытым членом класса вы берёте на себя обязательство**. Если поле `public`, вы обещаете, что оно будет существовать и вести себя определённым образом. Если завтра вы захотите поменять его тип или логику — придётся оглядываться на всех, кто его использует. Если поле `private`, вы можете менять его как угодно, и снаружи никто не заметит.

Это называется «минимизация публичного интерфейса». Идея: **чем меньше вы показываете, тем меньше вам придётся поддерживать**. Класс должен открывать ровно то, что нужно для взаимодействия с ним, и ни одним методом больше.

Вот пример. Класс `Stack` (стек) — структура данных «последним пришёл, первым вышел». Публичный интерфейс: `push` (положить), `pop` (взять), `peek` (посмотреть верхний), `isEmpty`. Четыре метода. А внутри — массив, индекс, операции с ним. Если массив открыть, кто-нибудь полезет в него напрямую и сломает инварианты стека. Если оставить закрытым — все взаимодействуют только через четыре метода, и стек всегда работает правильно.

Это правило иногда формулируют как «закон Деметры» (Law of Demeter) или «принцип наименьшего знания». Суть одна: **объект должен знать как можно меньше о внутренностях других объектов**. И `private` — это инструмент, который помогает этого добиться.

## Когда private — не подходит

Бывают ситуации, когда `private` — не лучший выбор. Их немного, но они есть.

**Вспомогательные методы для пакета.** Если у вас есть несколько классов в одном пакете, которые тесно работают вместе, — иногда имеет смысл сделать метод `package-private`. Например, класс `Order` и класс `OrderCalculator`: `OrderCalculator` знает, как считать заказ, и `Order` хочет это использовать. Если `OrderCalculator` в том же пакете — метод может быть `package-private`. Снаружи пакета он не нужен.

**Наследование.** Если класс проектируется с расчётом на расширение, — некоторые методы могут быть `protected`. Это значит «наследники могут это переопределить или использовать». Классический пример — `AbstractList` в стандартной библиотеке Java: там много `protected`-методов, которые наследники переопределяют, чтобы реализовать свою логику. Но это работает только если вы **действительно** проектируете класс для наследования; если нет — `protected` только связывает вам руки.

**Публичный API.** Если метод — часть контракта класса (например, `push` у стека), он должен быть `public`. Иначе класс бесполезен.

**Тесты.** Иногда для тестов нужно получить доступ к внутренним полям. Соблазн сделать их `package-private` велик — тесты часто лежат в том же пакете. Но это плохая практика: тесты не должны лезть во внутренности класса. Если они это делают — значит, класс недостаточно хорош. Лучше проектировать класс так, чтобы его можно было тестировать через публичный интерфейс.

Общий принцип: **начинайте с `private` и открывайте только то, что действительно нужно**. Открыть всегда проще, чем закрыть.

## Аналогия, которая помогает

Хорошая аналогия — **матpёшка**.

Представьте матрёшку. Внутри большой матрёшки — матрёшка поменьше, внутри неё — ещё меньше, и так далее. Каждый уровень вложен в следующий.

**`private`** — это самая внутренняя матрёшка. Вы можете добраться до неё, только если вы — её содержимое. Никто снаружи не может её открыть.

**`package-private`** — следующая матрёшка. Она открыта для всех «своих» — тех, кто в том же наборе. Но не для посторонних.

**`protected`** — следующая. Она открыта для «своих» **и** для «детей» (тех, кто произошёл от неё). Наследники в других наборах тоже могут её открыть.

**`public`** — самая внешняя матрёшка. Она открыта всем, кто держит её в руках. Кто угодно может заглянуть внутрь.

Логика вложенности важна: `private` ⊂ `package-private` ⊂ `protected` ⊂ `public`. То есть если что-то доступно на уровне `private`, оно доступно и на всех более мягких уровнях. И наоборот: если что-то `public`, оно доступно всем.

И ещё одна мысль, которую хорошо иллюстрирует эта аналогия: **не нужно открывать самую внутреннюю матрёшку, если вам нужна только внешняя**. Если классу нужен только публичный интерфейс — не открывайте внутренние поля. Если пакету нужен вспомогательный метод — не делайте его `public`. Каждый уровень — это своя степень доверия, и не стоит открывать больше, чем нужно.

## Микрозадача 1

Вот три класса в разных пакетах. Кто из них может обратиться к полю `value` класса `Box`?

```java
// Пакет A
package a;

public class Box {
    private int privateValue;
    int packageValue;
    protected int protectedValue;
    public int publicValue;
}
```

```java
// Пакет A
package a;

public class BoxHelper {
    void test(Box box) {
        // что здесь доступно?
    }
}
```

```java
// Пакет B
package b;

import a.Box;

public class BoxUser {
    void test(Box box) {
        // что здесь доступно?
    }
}
```

### Разбор

**`BoxHelper`** находится в том же пакете (`a`), что и `Box`, но не является его наследником. Ему доступны:

- `privateValue` — **нет**, `private` закрыто для всех, кроме самого класса;
- `packageValue` — **да**, тот же пакет;
- `protectedValue` — **да**, тот же пакет (protected включает package-private);
- `publicValue` — **да**, `public` доступно всем.

**`BoxUser`** находится в другом пакете (`b`) и не является наследником. Ему доступно:

- `privateValue` — **нет**;
- `packageValue` — **нет**, другой пакет;
- `protectedValue` — **нет**, другой пакет и не наследник;
- `publicValue` — **да**.

Итого: из другого пакета доступно только `publicValue`. Это и есть суть `public`: «открыто всем, всегда». Всё остальное — для «своих» в том или ином смысле.

Теперь добавим третьего:

```java
// Пакет B
package b;

import a.Box;

public class BoxChild extends Box {
    void test() {
        // что здесь доступно?
    }
}
```

`BoxChild` — наследник `Box` в другом пакете. Ему доступны:

- `privateValue` — **нет**;
- `packageValue` — **нет**, другой пакет;
- `protectedValue` — **да**, потому что наследник;
- `publicValue` — **да**.

Вот здесь и видна роль `protected`: он открывает доступ наследникам, даже если они в другом пакете. `package-private` так не умеет.

## Микрозадача 2

Вот код с ошибкой компиляции. Найдите её и объясните, почему она возникает.

```java
// Пакет A
package a;

public class Base {
    void doSomething() {
        System.out.println("Base");
    }
}
```

```java
// Пакет B
package b;

import a.Base;

public class Child extends Base {
    @Override
    void doSomething() {
        System.out.println("Child");
    }
}
```

### Разбор

Проблема в том, что метод `doSomething` в `Base` — `package-private` (нет модификатора). Это значит, что он доступен только внутри пакета `a`. Класс `Child` находится в пакете `b` — значит, он **не видит** `doSomething` родителя. Формально он не переопределяет метод, а объявляет новый, независимый. И аннотация `@Override` это ловит: компилятор говорит: «Здесь нечего переопределять».

Если убрать `@Override`, код скомпилируется, но это будет не переопределение, а «случайное совпадение имён». Вызов через ссылку типа `Base` попадёт в `Base.doSomething`, а через `Child` — в `Child.doSomething`. Это почти наверняка не то, что задумано.

**Как исправить.** Есть два варианта.

**Первый — сделать метод `protected`:**

```java
public class Base {
    protected void doSomething() {
        System.out.println("Base");
    }
}
```

Тогда наследники в любом пакете его видят и могут переопределять. Это правильный вариант, если метод действительно предназначен для переопределения.

**Второй — сделать метод `public`:**

```java
public class Base {
    public void doSomething() {
        System.out.println("Base");
    }
}
```

Тогда метод виден всем, и наследники тоже могут его переопределять. Это правильный вариант, если метод — часть публичного API.

Обратите внимание: **`package-private` плохо подходит для методов, которые предполагается переопределять**. Если вы проектируете класс для наследования, методы, которые наследники должны переопределять, должны быть как минимум `protected`. Иначе получится, что наследники в других пакетах не смогут их «подхватить», и полиморфизм сломается.

## Самостоятельная задача

Спроектируйте класс `BankAccount` с продуманной системой доступа.

Подумайте:

- какие поля должны быть `private` (почти все, я думаю);
- какие методы должны быть `public` (это API для клиентов банка);
- есть ли методы, которые должны быть `package-private` (например, для работы с другими классами того же пакета — `Transaction`, `Statement` и т. д.);
- есть ли методы, которые должны быть `protected` (например, если вы планируете наследников — `SavingsAccount`, `CreditAccount`);
- нужен ли метод, который мог бы быть `private`, но используется наследниками — и если да, как это выразить в коде;
- как быть с геттером `getBalance` — он точно `public`? Или только `package-private`?

Затем ответьте на вопрос: если вы делаете `BankAccount` с расчётом на наследование (`SavingsAccount extends BankAccount`), — какие методы имеет смысл сделать `protected`, а какие оставить `private`? Подумайте о разнице между «наследник должен это переопределить» и «наследник может это использовать».

Готового ответа не будет. Если хотите свериться — загляните в следующий урок про геттеры и сеттеры: там мы разберём, зачем они нужны, когда без них можно обойтись и почему «голые» геттеры-сеттеры — это не инкапсуляция. И вы увидите, насколько ваша интуиция про `public`/`private` совпала с тем, как это делают в реальном коде.

## Что дальше

Мы разобрались с четырьмя уровнями доступа и с тем, когда какой использовать. В следующем уроке — **«Геттеры и сеттеры»** — мы поговорим о самой частой паре методов в Java. Казалось бы, что тут сложного — вернуть поле и записать поле. Но у этой пары есть свои тонкости, и «голые» геттеры-сеттеры часто оказываются хуже, чем их отсутствие.

А пока — маленькое упражнение на наблюдательность. Откройте любой класс в своём проекте (или в стандартной библиотеке Java) и посмотрите, какие у него модификаторы доступа. Для каждого члена задайте вопрос: **а нужно ли ему быть именно таким?** Может быть, поле, которое `public`, вполне могло бы быть `private`? Может быть, метод, который `package-private`, на самом деле используется только внутри класса, и его стоило бы сделать `private`? Просто посмотрите. Не меняйте. Осознание того, что открыто больше, чем нужно, — уже первый шаг к тому, чтобы это исправить.

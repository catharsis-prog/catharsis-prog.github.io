# 4. Валидация в сеттерах

## Где вы это уже видели

В прошлых уроках мы несколько раз писали `if (amount <= 0) throw new IllegalArgumentException(...)`. Пора разобраться, что это за конструкция, зачем она нужна и почему «бросить исключение» — не единственный и не всегда лучший способ сказать «так нельзя».

**Ситуация первая.** Вы заполняете анкету на сайте. В поле «возраст» вводите `−5`. Сайт не говорит: «Спасибо, сохранили». Он пишет красным: «Возраст должен быть положительным числом». Это и есть валидация: проверка, что введённое значение имеет смысл, — до того, как оно куда-то попадёт.

**Ситуация вторая.** Вы переводите деньги через приложение. Вводите сумму больше, чем на счёте. Приложение не переводит. Оно говорит: «Недостаточно средств». Это тоже валидация, только не формата, а **состояния**: сумма валидна сама по себе (это положительное число), но она невалидна **в контексте** вашего баланса.

**Ситуация третья.** Вы регистрируетесь на сайте и вводите пароль `123`. Сайт говорит: «Пароль должен быть не короче восьми символов и содержать хотя бы одну цифру». Это составная валидация: несколько правил, каждое из которых должно быть выполнено.

**Ситуация четвёртая.** Вы наливаете воду в стакан. Стакан вмещает 300 мл. Если вы нальёте 400 — остальное выльется на стол. Это **физическое ограничение**: стакан не может принять больше, чем может. Хороший класс ведёт себя как стакан: не даёт принять бессмысленное состояние.

**Ситуация пятая.** Вы в библиотеке. Библиотекарь берёт у вас книгу и говорит: «Эту книгу мы не принимаем — она не из нашего фонда». Не потому что книга плохая, а потому что она не подходит по контексту. Класс `Library` мог бы принимать любые книги, но не принимает — и это правильно.

**Ситуация шестая.** Вы пишете класс, и кто-то вызывает у него `setAge(-5)`. Программа не падает, но через полчаса, когда вы пытаетесь вычислить что-то осмысленное с этим возрастом, — получаете странные результаты. Вы идёте по коду и находите источник. И думаете: почему класс не сказал сразу, что `-5` — это ерунда?

Если последняя ситуация вам знакома — этот урок для вас. Если остальные тоже — отлично, интуиция про «проверять на входе» у вас уже есть, осталось связать её с кодом.

## Зачем валидировать

Валидация — это проверка, что значение, которое приходит в класс, имеет смысл. Она нужна, чтобы класс не оказался в **невалидном состоянии** — то есть в таком, в котором его методы работают неправильно или не работают вовсе.

Вот что бывает без валидации.

**Методы падают с непонятными ошибками.** Вы установили `age = -5`, потом вызвали `isAdult()` — метод вернул `false`. Формально всё правильно (`-5 < 18`), но это не то, что вы хотели. А если бы класс не дал установить `-5`, вы бы сразу узнали, что что-то не так.

**Ошибки накапливаются.** Одно невалидное значение попадает в одно поле, потом в другое, потом вы получаете объект, который «выглядит нормально», но внутри у него мусор. И выясняется это через полчаса, когда вы уже забыли, откуда что пришло.

**Непонятно, кто виноват.** Если класс принял `-5`, значит, по мнению класса, `-5` — это нормально. И когда что-то сломается, виноват будет не тот, кто передал `-5`, а тот, кто написал класс. С точки зрения «кто виноват» это неправильно: класс не должен страдать за ошибки вызывающего кода.

**Инварианты нарушаются.** Помните, что такое инвариант? Это правило, которое всегда должно быть верно для объекта. Например, «баланс не может быть отрицательным». Если класс не проверяет это, инвариант может нарушиться — и тогда все методы класса работают с невалидным состоянием, и их поведение непредсказуемо.

Валидация решает все эти проблемы, но не бесплатно: она добавляет код и требует, чтобы вы думали о том, что считать «валидным». Часто это самая сложная часть проектирования класса.

## Где валидировать

Валидировать можно в трёх местах, и у каждого есть свои плюсы и минусы.

**В конструкторе.** Это первая точка входа объекта в мир. Если конструктор проверяет всё, что нужно, — объект не может появиться на свет в невалидном состоянии. Это **самое надёжное место**: если конструктор пропустил невалидное значение, дальше объект уже не «исправить» — он с самого начала неправильный.

```java
class User {
    private final String email;

    public User(String email) {
        if (email == null || !email.contains("@")) {
            throw new IllegalArgumentException("Некорректный email: " + email);
        }
        this.email = email;
    }
}
```

**В сеттерах.** Если поле можно менять после создания, — сеттер должен проверять новое значение. Иначе объект может «испортиться» уже после того, как был создан правильным.

```java
public void setEmail(String email) {
    if (email == null || !email.contains("@")) {
        throw new IllegalArgumentException("Некорректный email: " + email);
    }
    this.email = email;
}
```

**В методах, которые меняют состояние.** Иногда изменение — это не «присвоить значение», а «выполнить операцию». Например, `withdraw(amount)` уменьшает баланс. Проверять нужно не только `amount`, но и то, что после операции баланс не станет отрицательным.

```java
public void withdraw(double amount) {
    if (amount <= 0) {
        throw new IllegalArgumentException("Сумма должна быть положительной");
    }
    if (amount > balance) {
        throw new IllegalStateException("Недостаточно средств");
    }
    balance -= amount;
}
```

**Общее правило:** валидировать нужно **на каждой границе**, где значение попадает в объект. Конструктор — первая граница, сеттер — вторая, методы, меняющие состояние, — третья. Если хотя бы одна граница не защищена, объект может «протечь».

## Что значит «валидное»

Тут начинается самое интересное. «Валидное» — это не универсальное свойство. Оно зависит от класса и от предметной области.

**Формат.** Например, email должен содержать `@`, телефон — только цифры и знак `+`, ISBN — соответствовать формату. Это самая простая валидация: она проверяет **форму** значения, не заглядывая в контекст.

**Диапазон.** Например, возраст от 0 до 150, рейтинг от 1 до 5, температура выше абсолютного нуля. Это тоже простая валидация: значение должно попадать в известный интервал.

**Согласованность с другими полями.** Например, у `DateRange` начало должно быть раньше конца. У `Order` сумма должна равняться сумме стоимостей позиций. Это уже сложнее: нужно смотреть не только на само значение, но и на контекст.

**Согласованность с внешним миром.** Например, нельзя выдать книгу, которой нет в каталоге. Нельзя перевести деньги на счёт, которого не существует. Это самая сложная валидация: она требует обращения к другим объектам и может быть дорогой.

**Бизнес-правила.** Например, «нельзя отменить заказ, который уже доставлен», «нельзя повысить зарплату больше чем на 20% за раз». Это правила, которые нельзя вывести из формата или диапазона: они специфичны для конкретной предметной области.

Валидация обычно комбинирует несколько из этих уровней. И важно понимать, что **всё проверить невозможно**. Всегда найдётся что-то, что класс не может проверить сам — например, существует ли пользователь в базе. В таких случаях валидация либо делегируется другому слою (сервису, репозиторию), либо класс просто принимает значение «как есть» и полагается на то, что вызывающий код проверяет сам.

**Хорошее правило:** валидируйте то, что класс **может** проверить без обращения к внешнему миру. Всё остальное — не его забота.

## Как сообщать о невалидном значении

Есть несколько способов сказать «так нельзя». Каждый используется в своей ситуации.

### Исключение

Самый частый способ. Класс бросает исключение, и вызывающий код **обязан** его обработать (или явно проигнорировать, что тоже сигнал).

```java
public void setAge(int age) {
    if (age < 0 || age > 150) {
        throw new IllegalArgumentException("Возраст должен быть от 0 до 150");
    }
    this.age = age;
}
```

**Плюсы.** Ошибку нельзя проигнорировать случайно. Если кто-то передал `-5`, программа **упадёт**, и это сразу видно.

**Минусы.** Программа падает. Если невалидное значение пришло из пользовательского ввода, — падать в этом месте не всегда уместно. Иногда лучше обработать ошибку и попросить пользователя ввести заново.

**Когда использовать.** Когда невалидное значение — это **ошибка программиста**, а не пользователя. Например, `setAge(-5)` — это баг в коде, и лучше, чтобы он всплыл как можно раньше. А `setAge` из формы, куда пользователь ввёл `-5`, — это не баг, а обычная ситуация, и её надо обработать мягче.

### Возврат boolean

Метод возвращает `true`, если значение принято, и `false`, если нет.

```java
public boolean setAge(int age) {
    if (age < 0 || age > 150) {
        return false;
    }
    this.age = age;
    return true;
}
```

**Плюсы.** Не падает. Вызывающий код **может** проверить результат.

**Минусы.** Вызывающий код **может не проверить** результат. И тогда он будет думать, что значение установилось, а оно не установилось. Это классическая проблема «тихого отказа»: ошибка есть, но она не видна.

**Когда использовать.** Когда невалидное значение — это **обычная ситуация**, которую вызывающий код должен обработать. Например, `tryBorrow(book)` — «попытаться взять книгу», и `false` значит «не получилось, потому что уже выдана». Это не ошибка, это штатный сценарий.

Есть вариант — возвращать не `boolean`, а объект с результатом (например, `Result<T>` с полями «успех/неуспех» и «сообщение»). Это уже паттерн, и мы его разберём позже. Пока что `boolean` — простой и рабочий вариант.

### Optional

Метод возвращает `Optional<T>` — контейнер, который либо содержит значение, либо пуст.

```java
public java.util.Optional<Integer> parseAge(String input) {
    try {
        int age = Integer.parseInt(input);
        if (age < 0 || age > 150) {
            return java.util.Optional.empty();
        }
        return java.util.Optional.of(age);
    } catch (NumberFormatException e) {
        return java.util.Optional.empty();
    }
}
```

**Плюсы.** Явно говорит: «результата может не быть». Вызывающий код **обязан** как-то обработать пустой `Optional` — либо через `orElse`, либо через `ifPresent`, либо через `orElseThrow`.

**Минусы.** Это для «получения значения», а не для «установки значения». Для сеттеров `Optional` не очень подходит, потому что сеттер ничего не возвращает. Обычно `Optional` используется в геттерах и в методах поиска.

**Когда использовать.** Когда метод возвращает что-то, чего может не быть. Для валидации в сеттерах — редко.

### Логирование и игнорирование

Метод записывает предупреждение в лог и **не** меняет значение. Или меняет, но на «безопасное» (например, `0` вместо `-5`).

**Плюсы.** Программа не падает. Можно продолжать работу.

**Минусы.** Ошибка теряется в логах. Значение в объекте не то, что ожидал вызывающий код. Это самый плохой вариант с точки зрения отладки, но иногда уместный — например, в системах, где важнее «не упасть», чем «сделать правильно».

**Когда использовать.** Почти никогда. Только в очень специфических случаях: например, в системах реального времени, где падение недопустимо. В обычном коде — не надо.

### Какой выбрать

Общее правило такое: **исключение — для ошибок программиста, `boolean` — для штатных сценариев, `Optional` — для «может не быть»**.

Пример: `setAge(-5)` из кода — это ошибка программиста, кидаем `IllegalArgumentException`. `tryBorrow(book)` — штатный сценарий (книга может быть занята), возвращаем `boolean`. `findUserByEmail(...)` — может не найти, возвращаем `Optional<User>`.

## Типы исключений

Если вы решили бросать исключение, — какое именно? В Java есть два больших семейства: **checked** (проверяемые) и **unchecked** (непроверяемые).

**Checked-исключения** — наследники `Exception`, но не `RuntimeException`. Компилятор **требует**, чтобы вы их обработали (через `try/catch`) или объявили в `throws`. Примеры: `IOException`, `SQLException`.

```java
public void readFile(String path) throws IOException {
    // если файла нет — бросится IOException
}
```

**Unchecked-исключения** — наследники `RuntimeException`. Компилятор их не требует обрабатывать. Примеры: `IllegalArgumentException`, `IllegalStateException`, `NullPointerException`.

```java
public void setAge(int age) {
    if (age < 0) {
        throw new IllegalArgumentException("Возраст не может быть отрицательным");
    }
}
```

Для валидации в сеттерах и конструкторах обычно используют **unchecked-исключения**. Логика такая: если вы передали `-5` в `setAge`, — это ошибка **в вашем коде**, а не «внешнее обстоятельство». Ошибки в коде не надо заставлять обрабатывать: их надо **исправлять**. Компилятор не должен заставлять вас писать `try/catch` вокруг каждого `setAge` — это было бы невыносимо.

Какие unchecked-исключения использовать:

- **`IllegalArgumentException`** — если аргумент метода невалиден. `setAge(-5)`, `setEmail("не-почта")`, `withdraw(-100)`.
- **`IllegalStateException`** — если объект находится в состоянии, в котором операция невозможна. `withdraw(1000)` при балансе 500, `close()` у уже закрытого ресурса, `borrow(book)` у читателя, который уже взял 5 книг.
- **`NullPointerException`** — если передан `null`, а `null` недопустим. Обычно её не бросают вручную, а используют `Objects.requireNonNull`.
- **`UnsupportedOperationException`** — если операция в принципе не поддерживается (например, `add` у неизменяемого списка).

Разница между `IllegalArgumentException` и `IllegalStateException` важна: первое — «вы передали мне плохое значение», второе — «значение, может, и хорошее, но сейчас нельзя». `withdraw(-100)` — `IllegalArgumentException` (отрицательная сумма — ерунда). `withdraw(1000)` при балансе 500 — `IllegalStateException` (сумма нормальная, но состояние не позволяет).

## Аналогия, которая помогает

Хорошая аналогия — **фейс-контроль в клубе**.

Представьте, что класс — это клуб, а сеттеры и конструктор — это охрана на входе. Охрана проверяет, что вы соответствуете правилам: вам есть 18, вы не в нетрезвом виде, у вас есть билет. Если не соответствуете — вас не пускают.

**`IllegalArgumentException` — это «вам нельзя».** Вы не подходите по формальным признакам: возраст, состояние, наличие билета. Охрана говорит: «Извините, вам нельзя», — и вы уходите. Это не катастрофа, это нормальный отказ.

**`IllegalStateException` — это «сейчас нельзя».** Вы подходите по всем признакам, но в клубе уже полная посадка. Охрана говорит: «Извините, сейчас не можем пустить, приходите через час». Вы — тот же, правила — те же, но **момент** неподходящий. Это тоже нормальный отказ.

**`boolean` — это «не получилось, попробуйте позже».** Охрана говорит: «Извините, сейчас не получилось», — и вы понимаете, что попытка провалилась, но можете попробовать снова. Вы **знаете**, что не попали, и можете что-то с этим сделать.

**Логирование и игнорирование — это «охрана отвернулась».** Вы проходите, но правила не соблюдены. Формально вы в клубе, но вы сами понимаете, что что-то не так. Это самый плохой вариант: ошибка есть, но она не видна ни вам, ни охране.

И ещё одна деталь этой аналогии: **охрана не «исправляет» вас**. Она не может сделать вас старше или трезвее. Она просто не пускает, и это правильно: класс не должен «исправлять» значения, которые ему передают. Он должен либо принять их, либо отказать. «Исправление» — это скрытая логика, которая приводит к непредсказуемому поведению.

## Микрозадача 1

Вот класс. Определите, какие проверки здесь есть, чего не хватает, и какое исключение (или другой способ) лучше использовать в каждом случае.

```java
class BankAccount {
    private String owner;
    private double balance;

    public BankAccount(String owner, double initialBalance) {
        this.owner = owner;
        this.balance = initialBalance;
    }

    public void setOwner(String owner) {
        this.owner = owner;
    }

    public void deposit(double amount) {
        balance += amount;
    }

    public void withdraw(double amount) {
        balance -= amount;
    }
}
```

### Разбор

**Проблем много, и все — типичные.**

**Конструктор** не проверяет `owner` (может быть `null` или пустой) и `initialBalance` (может быть отрицательным). Это `IllegalArgumentException` — оба случая.

**`setOwner`** не проверяет ничего. Если `owner` должен быть непустым — `IllegalArgumentException`. Если `null` недопустим — тоже.

**`deposit`** не проверяет `amount`. Отрицательный «депозит» — это фактически списание, что странно. `IllegalArgumentException`.

**`withdraw`** не проверяет ни `amount` (может быть отрицательным, что превратит списание в пополнение), ни то, что после списания баланс не станет отрицательным. Первое — `IllegalArgumentException`, второе — `IllegalStateException`.

**Как исправить:**

```java
class BankAccount {
    private String owner;
    private double balance;

    public BankAccount(String owner, double initialBalance) {
        if (owner == null || owner.isEmpty()) {
            throw new IllegalArgumentException("Владелец не может быть пустым");
        }
        if (initialBalance < 0) {
            throw new IllegalArgumentException("Начальный баланс не может быть отрицательным");
        }
        this.owner = owner;
        this.balance = initialBalance;
    }

    public void setOwner(String owner) {
        if (owner == null || owner.isEmpty()) {
            throw new IllegalArgumentException("Владелец не может быть пустым");
        }
        this.owner = owner;
    }

    public void deposit(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Сумма пополнения должна быть положительной");
        }
        balance += amount;
    }

    public void withdraw(double amount) {
        if (amount <= 0) {
            throw new IllegalArgumentException("Сумма списания должна быть положительной");
        }
        if (amount > balance) {
            throw new IllegalStateException("Недостаточно средств");
        }
        balance -= amount;
    }
}
```

Обратите внимание: **`initialBalance` в конструкторе проверяется отдельно от `withdraw`**. Это не дублирование, а разные контексты. В конструкторе мы создаём счёт с нуля — там проверяется «начальное значение». В `withdraw` мы меняем существующий счёт — там проверяется «достаточно ли средств». Оба нужны.

**Мораль.** Валидация должна быть на **каждой границе**. Конструктор, сеттер, метод — везде, где значение попадает в объект, должна быть проверка. Если проверки нет хотя бы на одной границе — объект может «протечь».

## Микрозадача 2

Вот метод. Он выглядит нормально, но у него есть проблема. Найдите её.

```java
public void setAge(int age) {
    if (age < 0 || age > 150) {
        System.out.println("Некорректный возраст: " + age);
        return;
    }
    this.age = age;
}
```

### Разбор

Проблема в том, что метод **логирует и игнорирует**. Если передать `-5`, он напечатает сообщение и просто не установит значение. Вызывающий код **не узнает**, что что-то пошло не так, — он просто продолжит работу с объектом, у которого `age` остался прежним (или `0`, если это первое присваивание).

Чем это плохо:

**Вызывающий код не знает, что произошло.** Он думает, что установил `-5`, а на самом деле — нет. Через полчаса он удивляется, почему `age` не тот, что он передавал.

**Ошибка «тонет» в логах.** `System.out.println` — это не лог, а отладочный вывод. В реальной программе такие сообщения либо теряются, либо забивают консоль. И никто их не читает.

**Программа не падает.** Это значит, что баг в коде (передача `-5`) не всплывёт при тестировании. Он проявится потом, в самый неподходящий момент.

**Это «тихий отказ».** Самый плохой вид ошибки: что-то пошло не так, но никто об этом не знает. В отличие от исключения, которое «кричит» и требует внимания, тихий отказ «молчит» — и вы узнаете о проблеме только когда она превратится в катастрофу.

**Как исправить.** Зависит от контекста.

**Если `-5` — ошибка программиста** (например, `setAge` вызывается из кода, где возраст точно должен быть валидным), — бросить исключение:

```java
public void setAge(int age) {
    if (age < 0 || age > 150) {
        throw new IllegalArgumentException("Возраст должен быть от 0 до 150, получено: " + age);
    }
    this.age = age;
}
```

Программа упадёт при первой же попытке установить невалидный возраст. Это неприятно, но зато вы **узнаете** о проблеме сразу, а не через полчаса.

**Если `-5` — штатный сценарий** (например, `setAge` вызывается из обработчика формы, куда пользователь мог ввести что угодно), — вернуть `boolean`:

```java
public boolean setAge(int age) {
    if (age < 0 || age > 150) {
        return false;
    }
    this.age = age;
    return true;
}
```

И вызывающий код должен проверить результат и, например, показать пользователю ошибку.

**Что не надо делать** — это игнорировать. «Логирование и игнорирование» — это способ **скрыть** проблему, а не решить её. Единственный случай, где это уместно, — системы, в которых падение недопустимо (например, системы жизнеобеспечения, где «лучше работать с ошибкой, чем не работать вообще»). В обычном коде — не надо.

**Мораль.** Ошибка должна быть **видна**. Лучше пусть программа упадёт, чем будет работать неправильно и молчать об этом. «Тихий отказ» — это долг, который вы откладываете: рано или поздно придётся платить, и цена будет выше.

## Самостоятельная задача

Спроектируйте класс `Temperature` для хранения температуры.

Поля: значение (`double`) и единица измерения (`enum` с `CELSIUS`, `FAHRENHEIT`, `KELVIN`).

Подумайте:

- какие значения температуры валидны для каждой единицы (подсказка: для кельвинов — не ниже абсолютного нуля, то есть не ниже 0 K; для цельсия — не ниже −273.15; для фаренгейта — не ниже −459.67);
- где валидировать: в конструкторе, в сеттерах, или в методах изменения;
- что должно произойти, если попытаться установить температуру ниже абсолютного нуля;
- как быть с переводом единиц: если у вас `Temperature` в цельсиях, и вы хотите получить её в фаренгейтах, — это метод `toFahrenheit()` (возвращает новое значение) или `setUnit(FAHRENHEIT)` (меняет единицу)? И как это связано с инвариантом «значение всегда валидно для текущей единицы»?

Затем ответьте на вопрос: если класс позволяет менять и значение, и единицу, — как гарантировать, что после любого изменения температура остаётся валидной? Подумайте о порядке операций: что будет, если сначала установить значение `-300` в цельсиях (невалидно), а потом поменять единицу на кельвины (тоже невалидно)? Или наоборот?

Готового ответа не будет. Если хотите свериться — загляните в следующий урок про неизменяемые объекты: там мы разберём, как сделать так, чтобы объект **вообще нельзя было изменить** после создания, и почему это часто лучше, чем все эти проверки. И вы увидите, насколько ваша интуиция про «неизменяемость как защиту» совпала с тем, как это делают в реальном коде.

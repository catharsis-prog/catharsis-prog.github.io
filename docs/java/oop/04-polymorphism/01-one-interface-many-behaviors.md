# 1. Один интерфейс — много поведений

## Где вы это уже видели

Три модуля мы говорили о том, как устроен один класс (инкапсуляция) и как классы соотносятся друг с другом (наследование). Пора поговорить о том, ради чего всё это, собственно, и затевалось. Полиморфизм — это третья «кита» ООП, и именно он превращает наследование из «способа переиспользовать код» в настоящий инструмент проектирования.

Начнём с примеров. Полиморфизм — слово страшное, но идея за ним стоит очень простая, и вы с ней сталкиваетесь каждый день.

**Ситуация первая.** Вы нажимаете кнопку «Оплатить» в приложении. В одном приложении она спишет деньги с карты, в другом — с баланса телефона, в третьем — покажет QR-код. Вы **не знаете**, что именно произойдёт, когда нажимаете, — это зависит от приложения. Но вы знаете, что **что-то** произойдёт: деньги уйдут, заказ оформится. Одна кнопка, разные реализации.

**Ситуация вторая.** Вы говорите «Привет» коллеге, другу, начальнику, ребёнку. Слово одно, а интонация, громкость и контекст — разные. Вы не задумываетесь: «так, это начальник, надо формально; это ребёнок, надо мягко». Вы просто говорите «Привет» — и ваш мозг сам подбирает нужную «реализацию» под ситуацию.

**Ситуация третья.** Вы отправляете посылку. Можно отправить почтой, курьером, через пункт выдачи, через постамат. Для вас — это одно действие «отправить», хотя за ним стоят совершенно разные процессы. Вы не думаете: «так, теперь надо найти почтовое отделение, заполнить бланк, оплатить...». Вы говорите: «Отправьте это Пете» — и выбираете способ.

**Ситуация четвёртая.** Вы включаете музыку в машине. Источник может быть разный: радио, Bluetooth с телефона, USB-флешка, CD. Вы нажимаете «Play» — и играет то, что подключено. Кнопка одна, источник — разный.

**Ситуация пятая.** Вы работаете с документами. Вы нажимаете Ctrl+P — и печатается то, что открыто: текст, таблица, презентация, картинка. Для вас это одно действие «печать», хотя принтер и драйвер делают совершенно разные вещи для разных типов документов.

**Ситуация шестая.** Вы читаете код и видите:

```java
List<Animal> animals = List.of(new Cat(), new Dog(), new Cow());
for (Animal a : animals) {
    a.speak();
}
```

— и понимаете, что в цикле вызывается `speak()`, но **какой именно** `speak()` — зависит от того, кто там на самом деле. У кошки — «мяу», у собаки — «гав», у коровы — «му». Один вызов, разные поведения. Это и есть полиморфизм.

Если последняя ситуация вам знакома — урок для вас. Если остальные тоже — интуиция про «одно действие, разные реализации» у вас уже есть.

## Что такое полиморфизм

**Полиморфизм** (от греческого «много форм») — это возможность работать с объектами разных типов через **общий интерфейс**, не зная (и не желая знать) их конкретный тип.

Формально: **это когда один и тот же вызов метода приводит к разному поведению в зависимости от фактического типа объекта.**

Вот пример:

```java
class Animal {
    void speak() {
        System.out.println("...");
    }
}

class Cat extends Animal {
    @Override
    void speak() {
        System.out.println("Мяу");
    }
}

class Dog extends Animal {
    @Override
    void speak() {
        System.out.println("Гав");
    }
}

class Cow extends Animal {
    @Override
    void speak() {
        System.out.println("Му");
    }
}
```

Теперь можно написать:

```java
Animal a = new Cat();
a.speak();   // Мяу

a = new Dog();
a.speak();   // Гав

a = new Cow();
a.speak();   // Му
```

Переменная `a` имеет тип `Animal`, но в ней лежат разные объекты — и `speak()` вызывается **разный**. Компилятор не знает, какой именно `speak()` будет вызван (это решается во время выполнения), но **знает, что такой метод точно есть** у любого `Animal`. Это и есть полиморфизм.

Или ещё нагляднее — в цикле:

```java
Animal[] animals = { new Cat(), new Dog(), new Cow() };
for (Animal a : animals) {
    a.speak();   // Мяу, Гав, Му — разные, но через одну переменную
}
```

Здесь главное: **код цикла не знает**, какие именно животные лежат в массиве. Он просто вызывает `speak()` — и каждое животное отвечает по-своему. Если завтра добавится `Pig` с «Хрю», — цикл менять не придётся.

## Зачем это нужно

Полиморфизм кажется «красивой идеей», но за ней стоит очень практическая польза. Вот главные причины, зачем он нужен.

### Расширяемость без изменения

Самое важное. Если у вас есть код, который работает с `Animal`, — он работает **со всеми** `Animal`, включая тех, которых вы ещё не придумали. Завтра появится `Pig` — код цикла не изменится. Появится `Snake` — тоже не изменится.

Это огромное преимущество по сравнению с наследованием «ради кода». Без полиморфизма вам пришлось бы писать:

```java
for (Object o : items) {
    if (o instanceof Cat) {
        ((Cat) o).speak();
    } else if (o instanceof Dog) {
        ((Dog) o).speak();
    } else if (o instanceof Cow) {
        ((Cow) o).speak();
    }
    // ...
}
```

— и каждый раз, добавляя новое животное, дописывать новую ветку. С полиморфизмом — просто `a.speak()`, и всё.

### Упрощение кода

Код с полиморфизмом короче и понятнее. Вы не думаете «какой сейчас тип?», вы думаете «что этот объект умеет?». Это переключение с «проверки типов» на «использование контракта».

### Сокрытие сложности

Вызывающий код не знает, **как** `Dog.speak()` производит «Гав» — он просто знает, что **есть** `speak()`, и что он что-то делает. Внутренняя реализация может быть сложной, но снаружи — простой контракт.

### Замена во время тестирования

В тестах можно подменить настоящую реализацию на «заглушку»: если у вас есть `PaymentProcessor` с методом `pay()`, — в тесте можно подставить `FakePaymentProcessor`, который ничего не делает, но возвращает `true`. Код теста не меняется — он работает с `PaymentProcessor`, а какой именно — не важно.

## Как это работает

Технически полиморфизм опирается на **два механизма**.

**Первый — наследование (или интерфейсы).** Чтобы объект мог «притвориться» `Animal`, он должен быть **совместим** с `Animal`: либо наследовать его, либо реализовывать интерфейс. Об интерфейсах мы будем говорить подробно в уроке 3, но идея та же: «класс подписывается под контрактом».

**Второй — динамическое связывание.** Когда вы пишете `a.speak()`, где `a` — это `Animal`, — компилятор проверяет только, что у `Animal` есть метод `speak()`. **Какой именно** `speak()` будет вызван — решается **во время выполнения**, по фактическому типу объекта. Это называется **динамическим связыванием** (dynamic dispatch), и об этом будет отдельный урок 2.

Проще говоря: **вызов метода выбирается не по типу переменной, а по типу объекта, на который она указывает**. Переменная `a` может быть `Animal`, но если в ней лежит `Cat`, — вызовется `Cat.speak()`.

## Полиморфизм vs перегрузка

В уроке 4 модуля про наследование мы уже говорили о **перегрузке** (overloading). Важно не путать её с полиморфизмом.

**Перегрузка** — это несколько методов с одним именем, но разными параметрами, в одном классе (или в иерархии). Выбор версии — **по типу аргументов, во время компиляции**.

```java
class Printer {
    void print(String s) { System.out.println("String: " + s); }
    void print(int n) { System.out.println("int: " + n); }
}
```

**Полиморфизм** — это один метод (с точки зрения вызывающего кода), но разные реализации в наследниках. Выбор версии — **по типу объекта, во время выполнения**.

```java
class Printer {
    void print(String s) { System.out.println("Принтер: " + s); }
}

class ColorPrinter extends Printer {
    @Override
    void print(String s) { System.out.println("Цветной принтер: " + s); }
}
```

Иногда **перегрузку** тоже называют «полиморфизмом» (в широком смысле), но в Java-сообществе принято разделять: перегрузка — это «статический полиморфизм» (выбор во время компиляции), а полиморфизм через наследование — это «динамический полиморфизм» (выбор во время выполнения). В этом курсе мы будем использовать второе значение: полиморфизм — это про **наследование и интерфейсы**, а не про перегрузку.

## Аналогия, которая помогает

Хорошая аналогия — **пульт от универсального телевизора**.

Представьте, что у вас есть пульт, на котором есть кнопки: «Включить», «Громче», «Тише», «Канал +», «Канал −». Пульт **один и тот же** для любого телевизора. Но телевизоры — разные: обычный, умный, проектор, монитор.

Вы нажимаете «Включить»:
- на обычном телевизоре — включается экран;
- на умном — ещё и загружается приветственный экран;
- на проекторе — запускается лампа с задержкой;
- на мониторе — включается подсветка.

**Кнопка одна, поведение разное.** Пульт не знает, какой именно телевизор перед ним; он просто посылает сигнал «Включить», а телевизор сам решает, что делать. И если вы купите новый телевизор, — пульт всё равно будет работать: он не знает конкретной модели, он знает только, что у телевизора есть «Включить».

И ещё важная деталь: **пульт не нужно переделывать под каждый новый телевизор**. Вы не паяете в нём новые кнопки — вы просто нажимаете «Включить», и новый телевизор отвечает. Это и есть **расширяемость без изменения**: код пульта (цикла) не меняется, а новый телевизор (животное) — просто добавляется.

**Перегрузка** — это как если бы у пульта были **разные** кнопки «Включить» для разных моделей: «Включить Samsung», «Включить LG», «Включить Sony». Вы бы выбирали кнопку **до** нажатия, зная модель. Это не полиморфизм — это выбор по типу аргумента во время компиляции.

**Динамическое связывание** — это как если бы пульт **сам** определял, какой телевизор перед ним, и посылал нужный сигнал. Вы нажимаете «Включить», а пульт «знает», что это Samsung, и посылает сигнал Samsung. Вы не думаете об этом — вы просто нажимаете кнопку.

## Микрозадача 1

Вот код. Что выведется? Объясните, почему.

```java
class Animal {
    void speak() {
        System.out.println("Животное издаёт звук");
    }
}

class Cat extends Animal {
    @Override
    void speak() {
        System.out.println("Мяу");
    }

    void purr() {
        System.out.println("Мур-мур");
    }
}

Animal a = new Cat();
a.speak();
// a.purr();
```

### Разбор

`a.speak()` выведет:

```
Мяу
```

Потому что `speak()` переопределён в `Cat`, а `a` фактически указывает на `Cat`. Вызов метода выбирается по **фактическому типу объекта**, а не по типу переменной. Это и есть динамическое связывание.

`a.purr()` **не скомпилируется**. У `Animal` нет метода `purr()`, и хотя у `Cat` он есть, — компилятор смотрит на **тип переменной** (`Animal`), а не на тип объекта. Полиморфизм работает для **общих** методов (тех, что есть в базовом классе), но не «добавляет» новые методы наследников через ссылку родителя.

**Как заставить работать:**

- объявить `a` как `Cat`: `Cat a = new Cat();` — тогда `a.purr()` работает;
- привести тип: `((Cat) a).purr();` — работает, но некрасиво и опасно (если `a` на самом деле не `Cat` — будет `ClassCastException`);
- добавить `purr()` в `Animal` — тогда он станет частью общего контракта. Но это **не всегда** правильно: если `purr()` имеет смысл только для кошек, — не надо добавлять его в `Animal`. Лучше — вынести в отдельный интерфейс `Purrable`, о котором мы будем говорить в уроке 3.

**Мораль.** Полиморфизм работает **через общий контракт**: если метод есть у `Animal`, — его можно вызвать у любого `Animal`. Если метод есть только у `Cat`, — вызвать его можно только у `Cat`, и `Animal`-переменная не поможет.

## Микрозадача 2

Вот код. Он скомпилируется, но работает не так, как задумано. Найдите проблему.

```java
class Shape {
    double area() {
        return 0;
    }
}

class Circle extends Shape {
    private final double radius;

    Circle(double radius) {
        this.radius = radius;
    }

    @Override
    double area() {
        return Math.PI * radius * radius;
    }
}

class Square extends Shape {
    private final double side;

    Square(double side) {
        this.side = side;
    }

    @Override
    double area() {
        return side * side;
    }
}

public class Main {
    public static void main(String[] args) {
        Shape[] shapes = { new Circle(5), new Square(4) };
        double total = 0;
        for (Shape s : shapes) {
            total += s.area();
        }
        System.out.println(total);
    }
}
```

### Разбор

Формально код **правильный**: `Shape` имеет метод `area()`, наследники его переопределяют, полиморфизм работает. Но есть проблема: **`Shape` — не абстрактный**, и метод `area()` имеет реализацию по умолчанию `return 0`.

Что это значит? Что кто-то может создать `new Shape()` — и получить «фигуру с площадью 0». Это бессмысленно: фигура без площади — это не фигура. И ещё хуже: если кто-то отнаследуется от `Shape` и **забудет** переопределить `area()`, — он унаследует «0», и программа будет считать неправильно, но **не упадёт** и не сообщит об ошибке.

**Как исправить.** Сделать `Shape` абстрактным и `area()` — абстрактным:

```java
abstract class Shape {
    abstract double area();
}
```

Теперь:

- `new Shape()` не скомпилируется;
- любой конкретный наследник **обязан** переопределить `area()`, иначе не скомпилируется;
- программа не может «молча» считать площадь как `0` — ошибка будет видна на этапе компиляции.

**Мораль.** Реализация «по умолчанию» в базовом классе — это **скрытая ловушка**: она выглядит как «общее поведение», а на самом деле — «поведение, которого нет». Если метода **нет** у базового класса — наследник не сможет его «забыть»; компилятор заставит реализовать. Если метод **есть** с пустой реализацией — наследник может «забыть», и ошибка вылезет потом.

Правило простое: **если у метода нет осмысленной общей реализации, — сделайте его абстрактным**. Это и есть один из сценариев, где `abstract` спасает от багов. Об этом мы говорили в уроке 6 модуля 3, но здесь видно, как это связано с полиморфизмом: без абстрактных методов полиморфизм «протекает» — можно создать объект, у которого нет нужного поведения.

## Самостоятельная задача

Спроектируйте систему уведомлений для интернет-магазина.

Базовый класс (или интерфейс — решите сами) `NotificationSender` с методом `send(String recipient, String message)`, который ничего не возвращает.

Наследники (реализации):

- `EmailSender` — отправляет email. В реализации просто печатает `"[EMAIL] to [recipient]: [message]"`.
- `SmsSender` — отправляет SMS. Печатает `"[SMS] to [recipient]: [message]"`.
- `PushSender` — отправляет push-уведомление. Печатает `"[PUSH] to [recipient]: [message]"`.

Затем создайте класс `NotificationService` с полем `List<NotificationSender> senders` и методом `broadcast(String recipient, String message)`, который вызывает `send(...)` у **каждого** sender'а.

В `main`:

1. Создайте `NotificationService` и добавьте в него все три sender'а.
2. Вызовите `broadcast("Алиса", "Ваш заказ отправлен")`.
3. Убедитесь, что каждое уведомление отправилось своим способом.

Подумайте:

- что произойдёт, если завтра появится `TelegramSender`? Сколько файлов придётся менять?
- нужно ли делать `NotificationSender` абстрактным классом или интерфейсом? Обоснуйте.
- как в тестах подменить настоящий `EmailSender` на «заглушку», которая ничего не отправляет, но записывает вызовы? Это возможно благодаря чему?

Готового ответа не будет. Если хотите свериться — загляните в следующий урок про динамическое связывание: там мы разберём, **как именно** Java решает, чей метод вызывать, и вы увидите, насколько ваша интуиция про «выбор по фактическому типу» совпала с тем, как это устроено под капотом.

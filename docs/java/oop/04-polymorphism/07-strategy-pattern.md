# 7. Паттерн «Стратегия»

## Где вы это уже видели

Шесть уроков мы говорили о полиморфизме — о том, как один вызов метода приводит к разному поведению. Пора собрать всё вместе и посмотреть, как эта идея превращается в конкретный приём проектирования, который используют каждый день. Приём называется «Стратегия», и он, пожалуй, самый практичный из всего, что мы прошли в этом модуле.

**Ситуация первая.** Вы заказываете доставку в приложении. Вам предлагают выбрать способ: курьером, почтой, в пункт выдачи, самовывозом. Вы выбираете один — и дальше приложение само считает стоимость, срок и маршрут именно для этого способа. Вы не пишете `if (курьер) { ... } else if (почта) { ... }` — вы просто **говорите, какой способ**, и приложение применяет его. Это и есть стратегия: «способ доставки» — отдельный объект, который приложение подставляет.

**Ситуация вторая.** Вы платите в интернет-магазине. Способов много: картой, с баланса телефона, через СБП, наличными при получении, бонусами. Магазин не пишет `if (способ == КАРТА) { ... }` — он держит несколько «платёжных стратегий» и применяет ту, которую выбрали вы. Если завтра появится новый способ (например, оплата по QR), — магазин добавляет **одну** стратегию, и всё остальное работает без изменений.

**Ситуация третья.** Вы работаете с картой в навигаторе. Есть режимы: «быстрый», «короткий», «без пробок», «без платных дорог». Каждый режим — это свой алгоритм построения маршрута. Вы выбираете режим — и навигатор применяет соответствующую стратегию. Переключение мгновенное, а код навигатора не знает деталей каждого режима.

**Ситуация четвёртая.** Вы настраиваете сортировку в таблице. Можно сортировать по имени, по дате, по размеру, по цене. Каждый раз — свой алгоритм сравнения. Таблица не пишет `if (sortBy == ИМЯ) { ... }` — она держит «стратегию сортировки» и применяет её. Это, кстати, ровно то, как устроен `Comparator` в Java: `list.sort(comparator)` — это и есть стратегия.

**Ситуация пятая.** Вы играете в игру, и у персонажа есть оружие: меч, лук, посох. Каждое оружие наносит свой урон, имеет свою скорость, свой радиус. Персонаж не переписывается при смене оружия — он просто **держит** текущее оружие и применяет его. Это стратегия: «оружие» — отдельный объект, а персонаж — «контекст», который его использует.

**Ситуация шестая.** Вы смотрите на код и видите:

```java
double calculateDiscount(Order order) {
    if (order.getType() == REGULAR) {
        return order.getTotal() * 0.05;
    } else if (order.getType() == VIP) {
        return order.getTotal() * 0.15;
    } else if (order.getType() == PROMO) {
        return order.getTotal() * 0.25;
    } else if (order.getType() == BLACK_FRIDAY) {
        return order.getTotal() * 0.5;
    }
    return 0;
}
```

— и понимаете, что каждый раз, когда появится новый тип скидки, придётся менять **этот** метод. А таких методов в проекте может быть пять или десять. Знакомо? Тогда этот урок для вас.

## Что такое «Стратегия»

**Паттерн «Стратегия»** — это когда **поведение выносится в отдельный объект**, а «главный» объект держит ссылку на него и делегирует ему работу. Вместо того чтобы писать `if/else` внутри метода, — вы говорите: «сейчас я буду использовать вот эту стратегию», и метод просто вызывает её.

Формально паттерн состоит из трёх частей.

**Интерфейс стратегии.** Общий контракт для всех вариантов поведения.

```java
interface DiscountStrategy {
    double apply(Order order);
}
```

**Конкретные стратегии.** Реализации этого контракта — по одной на каждый вариант.

```java
class RegularDiscount implements DiscountStrategy {
    public double apply(Order order) {
        return order.getTotal() * 0.05;
    }
}

class VipDiscount implements DiscountStrategy {
    public double apply(Order order) {
        return order.getTotal() * 0.15;
    }
}

class BlackFridayDiscount implements DiscountStrategy {
    public double apply(Order order) {
        return order.getTotal() * 0.5;
    }
}
```

**Контекст.** Объект, который **использует** стратегию и не знает, какая именно она.

```java
class Checkout {
    private DiscountStrategy discount;

    Checkout(DiscountStrategy discount) {
        this.discount = discount;
    }

    void setDiscount(DiscountStrategy discount) {
        this.discount = discount;
    }

    double total(Order order) {
        return order.getTotal() - discount.apply(order);
    }
}
```

Теперь вместо длинного `if/else` в `calculateDiscount` — короткий вызов `discount.apply(order)`. Какой именно вариант сработает — зависит от того, что положили в `Checkout`. Хотите обычную скидку — `new Checkout(new RegularDiscount())`. Хотите VIP — `new Checkout(new VipDiscount())`. Завтра появится «студенческая скидка» — добавляете `StudentDiscount`, а `Checkout` **не меняется**.

**Ключевая идея:** раньше выбор поведения был **внутри** метода (через `if/else`), теперь он **снаружи** — в том месте, где создаётся или настраивается объект. Метод «поумнел» в одном смысле — он стал короче — и «поглупел» в другом: он больше не знает, какие скидки бывают. Он знает только, что у него есть стратегия, и умеет её применять.

## Как это заменяет if-else

Давайте сравним два подхода на примере.

**Без стратегии:**

```java
double calculateDiscount(Order order) {
    switch (order.getCustomerType()) {
        case REGULAR: return order.getTotal() * 0.05;
        case VIP:     return order.getTotal() * 0.15;
        case PROMO:   return order.getTotal() * 0.25;
        case BLACK_FRIDAY: return order.getTotal() * 0.5;
        default: throw new IllegalArgumentException("Неизвестный тип: " + order.getCustomerType());
    }
}
```

**Со стратегией:**

```java
interface DiscountStrategy {
    double apply(Order order);
}

class Checkout {
    private final DiscountStrategy discount;

    Checkout(DiscountStrategy discount) {
        this.discount = discount;
    }

    double total(Order order) {
        return order.getTotal() - discount.apply(order);
    }
}
```

Что мы получили и что потеряли.

**Получили:**
- **Открытость для расширения.** Новая скидка — новый класс, `Checkout` не трогаем. Это принцип «открыт для расширения, закрыт для изменения» (OCP), о котором будем говорить в модуле 6.
- **Тестируемость.** Каждую стратегию можно протестировать отдельно, без `Checkout`. И `Checkout` можно протестировать с «заглушкой»-стратегией, которая возвращает фиксированное значение.
- **Читаемость.** Каждая стратегия — маленький класс с понятным именем. Не нужно держать в голове всю таблицу `switch`.
- **Гибкость во время выполнения.** Стратегию можно поменять у объекта «на лету» — например, если пользователь ввёл промокод, — `checkout.setDiscount(new PromoDiscount())`. С `switch` пришлось бы пересчитывать всё заново.
- **Комбинируемость.** Из стратегий можно собирать композиции. Например, «VIP + чёрная пятница» — это `new CombinedDiscount(vipDiscount, blackFridayDiscount)`. Со `switch` такое сделать гораздо труднее.

**Потеряли:**
- **Больше классов.** Вместо одного метода — четыре класса и интерфейс. Для двух скидок это может быть overkill, но для двадцати — наоборот, спасение.
- **Сложнее найти все варианты.** Чтобы узнать, какие скидки бывают, нужно посмотреть, какие реализации `DiscountStrategy` есть в проекте. Со `switch` они были видны сразу.
- **Нужно где-то «собирать» стратегию.** Кто-то должен решить, какую стратегию создать. Обычно это фабрика или конфигурация. Об этом — в модуле 5.

**Правило:** если у вас `if/else` или `switch` по **типу** (а не по значению), и вариантов больше двух-трёх, — это, скорее всего, повод задуматься о стратегии. Если вариантов два и они стабильны (например, «включено/выключено»), — `if` нормально, не надо усложнять.

## Стратегия и полиморфизм

Обратите внимание: стратегия — это **чистый полиморфизм**, который мы проходили в уроках 1–5. Ничего нового в плане языка здесь нет. Есть интерфейс, есть реализации, есть переменная типа интерфейса, и вызов метода идёт по фактическому типу — динамическое связывание.

Разница в **намерении**. В уроках про полиморфизм мы говорили «вот как это работает». В этом уроке — «вот **как это использовать**». Стратегия — это полиморфизм, применённый для **инкапсуляции взаимозаменяемых алгоритмов**.

Именно поэтому стратегия так хорошо сочетается с `instanceof`. Помните урок 6? Мы говорили, что злоупотребление `instanceof` — это признак того, что полиморфизм «не доработал». Стратегия — это как раз **лекарство** от `instanceof`. Если у вас есть код:

```java
if (payment instanceof Card) {
    ((Card) payment).pay();
} else if (payment instanceof Sbp) {
    ((Sbp) payment).pay();
} else if (payment instanceof YooMoney) {
    ((YooMoney) payment).pay();
}
```

— это в точности то, что стратегия заменяет на:

```java
payment.pay();
```

где `payment` — это `PaymentStrategy`, а `Card`, `Sbp`, `YooMoney` — её реализации. Все `instanceof` исчезают, потому что тип «помнит» сам объект.

## Стратегия в стандартной библиотеке

Стратегия — настолько распространённый паттерн, что в Java она используется повсюду. Несколько примеров, которые вы уже, скорее всего, видели.

**`Comparator`.** `list.sort(comparator)` — это стратегия. `Comparator` — интерфейс стратегии, разные реализации — способы сортировки. `list.sort` — контекст, который применяет стратегию.

```java
List<String> names = new ArrayList<>(List.of("Боб", "Алиса", "Кэрол"));
names.sort(Comparator.naturalOrder());          // по алфавиту
names.sort(Comparator.reverseOrder());          // в обратном порядке
names.sort(Comparator.comparing(String::length)); // по длине строки
```

Никакого `if/else` — просто разные стратегии, которые подставляются в `sort`.

**`Runnable`.** `new Thread(runnable).start()` — это стратегия. `Runnable` — интерфейс стратегии, разные реализации — разные задачи. `Thread` — контекст, который выполняет стратегию в отдельном потоке. Об этом мы будем много говорить в модуле про многопоточность.

**`Predicate`, `Function`, `Consumer`.** Все функциональные интерфейсы из `java.util.function` — это стратегии. `list.removeIf(predicate)` — стратегия «что удалять». `stream.map(function)` — стратегия «как преобразовать». `stream.forEach(consumer)` — стратегия «что сделать с каждым».

**`Files.walkFileTree`.** Принимает `FileVisitor` — стратегию обхода файлового дерева. Разные реализации делают разное: подсчитывают файлы, копируют, удаляют.

Список можно продолжать долго. Смысл один: **если метод принимает функциональный интерфейс (или любой другой интерфейс с одним-двумя методами), — это, скорее всего, стратегия**. И вы, скорее всего, уже ей пользуетесь, даже не задумываясь.

## Аналогия, которая помогает

Хорошая аналогия — **переключатель на пульте**.

Представьте, что у вас есть пульт для умного дома. На нём есть кнопка «Сценарий». Вы нажимаете её — и происходит что-то: включается свет в гостиной, или запускается музыка, или опускаются шторы. **Одна кнопка, разные сценарии.**

**Кнопка «Сценарий»** — это контекст. Она не знает, какой именно сценарий сейчас выбран, — она просто «применяет его».

**Сценарий** — это стратегия. Он знает, **что** делать: «включи свет», «включи музыку», «опусти шторы». Разные сценарии — разные реализации.

**Меню сценариев** — это способ выбрать стратегию. Вы говорите: «сейчас хочу „кино“» — и пульт подставляет сценарий «кино». Завтра захотите «вечеринку» — подставите «вечеринку». Пульт при этом не меняется.

**Добавление нового сценария** — это добавление одной реализации. Пульт, кнопка, меню — не трогаются. Просто появляется новая строчка в меню, и она работает.

И ещё одна параллель: **сценарий можно поменять в любой момент**. Вы нажали «сценарий», но передумали — выбрали другой. Пульт применит уже новый. В коде это `setDiscount(newStrategy)` — стратегию можно поменять «на лету», и контекст сразу начнёт использовать новую.

**Без стратегии** это выглядело бы так: на пульте было бы **пять разных кнопок** — «включи свет», «включи музыку», «опусти шторы», и вам пришлось бы помнить, какую нажимать в какой ситуации. И если бы вы захотели добавить «сценарий для гостей», — пришлось бы паять новую кнопку. Неудобно, хрупко, не расширяемо.

## Микрозадача 1

Вот класс. Определите, что в нём «контекст», что «стратегия» и что «конкретные стратегии».

```java
interface SortStrategy {
    void sort(int[] array);
}

class BubbleSort implements SortStrategy {
    public void sort(int[] array) {
        // реализация пузырьковой сортировки
    }
}

class QuickSort implements SortStrategy {
    public void sort(int[] array) {
        // реализация быстрой сортировки
    }
}

class Sorter {
    private SortStrategy strategy;

    Sorter(SortStrategy strategy) {
        this.strategy = strategy;
    }

    void sort(int[] array) {
        strategy.sort(array);
    }
}
```

### Разбор

**Контекст** — `Sorter`. Он держит ссылку на стратегию и делегирует ей работу. Он не знает, какая именно сортировка сейчас используется, — он просто вызывает `strategy.sort(array)`.

**Интерфейс стратегии** — `SortStrategy`. Общий контракт для всех сортировок: «умеет отсортировать массив».

**Конкретные стратегии** — `BubbleSort` и `QuickSort`. Каждая реализует свой алгоритм. `BubbleSort` — медленный, но простой; `QuickSort` — быстрый, но сложнее. Обе реализуют `SortStrategy` и могут быть подставлены в `Sorter`.

Использование:

```java
Sorter sorter = new Sorter(new QuickSort());
sorter.sort(array);   // используется QuickSort

sorter = new Sorter(new BubbleSort());
sorter.sort(array);   // используется BubbleSort
```

**Ключевое наблюдение.** `Sorter` **не содержит** `if (тип == QUICK) { ... } else if (тип == BUBBLE) { ... }`. Он просто применяет стратегию. Если завтра появится `MergeSort`, — добавим один класс, `Sorter` не изменится.

Обратите внимание: `Sorter` — это **контекст**, но не «главный объект». Иногда контекст — это просто «сервис, который делает работу», а иногда — целая подсистема. Стратегия не привязана к «главности»; она привязана к **разделению «что» и «как»**.

## Микрозадача 2

Вот код, который использует `if/else` по типу. Перепишите его так, чтобы использовать стратегию (покажите структуру, без полной реализации всех методов).

```java
class NotificationService {
    void notify(User user, String message) {
        if (user.getPreferredChannel() == NotificationChannel.EMAIL) {
            // отправка email
        } else if (user.getPreferredChannel() == NotificationChannel.SMS) {
            // отправка SMS
        } else if (user.getPreferredChannel() == NotificationChannel.PUSH) {
            // отправка push
        } else {
            throw new IllegalArgumentException("Неизвестный канал: " + user.getPreferredChannel());
        }
    }
}
```

### Разбор

Разделим на три части.

**Интерфейс стратегии** — «как отправить уведомление»:

```java
interface NotificationSender {
    void send(User user, String message);
}
```

**Конкретные стратегии** — по одной на канал:

```java
class EmailSender implements NotificationSender {
    public void send(User user, String message) { /* email */ }
}

class SmsSender implements NotificationSender {
    public void send(User user, String message) { /* SMS */ }
}

class PushSender implements NotificationSender {
    public void send(User user, String message) { /* push */ }
}
```

**Контекст** — сервис, который держит стратегию и применяет её:

```java
class NotificationService {
    private final Map<NotificationChannel, NotificationSender> senders;

    NotificationService(Map<NotificationChannel, NotificationSender> senders) {
        this.senders = senders;
    }

    void notify(User user, String message) {
        NotificationSender sender = senders.get(user.getPreferredChannel());
        if (sender == null) {
            throw new IllegalArgumentException("Неизвестный канал: " + user.getPreferredChannel());
        }
        sender.send(user, message);
    }
}
```

Обратите внимание: я использовал `Map<NotificationChannel, NotificationSender>` вместо одного поля `NotificationSender`. Это **вариант** стратегии, который часто удобнее: стратегия выбирается по ключу (каналу), а не задаётся в конструкторе. Логика та же: `notify` не знает, какой sender сейчас в ходу, — он берёт его из `Map` по каналу и применяет.

Если бы `NotificationService` использовал только один канал за раз, — хватило бы одного поля, как в примере со скидкой. Оба варианта — правильные; выбор зависит от того, **сколько стратегий может быть активно одновременно**.

**Как это создавать.** В реальном коде `Map` заполняется фабрикой или DI-контейнером. Например:

```java
NotificationService service = new NotificationService(Map.of(
    EMAIL, new EmailSender(),
    SMS,   new SmsSender(),
    PUSH,  new PushSender()
));
```

Теперь добавление нового канала (например, `TELEGRAM`) — это `new TelegramSender()` и одна строчка в `Map`. `NotificationService` не меняется.

## Самостоятельная задача

Спроектируйте систему «расчёт стоимости доставки» с использованием паттерна «Стратегия».

Интерфейс `ShippingStrategy` с методом `double calculate(double weightKg, String address)`.

Конкретные стратегии:

- `CourierShipping` — курьером. Стоимость: `200 + weightKg * 15`. Доставка в пределах МКАД — бесплатно при заказе от 5000.
- `PostShipping` — почтой. Стоимость: `100 + weightKg * 8`. Без бесплатной доставки.
- `PickupShipping` — самовывоз. Стоимость: `50` (фиксированная).
- `ExpressShipping` — экспресс. Стоимость: `500 + weightKg * 30`. Срок — 1 день.

Класс `DeliveryCalculator` — контекст, который держит `ShippingStrategy` и умеет считать стоимость. Должен быть метод `setStrategy(ShippingStrategy)`, чтобы можно было менять стратегию «на лету».

В `main`:

1. Создайте `DeliveryCalculator` с `CourierShipping` и посчитайте стоимость для заказа весом 3 кг на адрес «Москва, Тверская, 1».
2. Поменяйте стратегию на `PostShipping` — посчитайте ту же доставку.
3. Поменяйте на `PickupShipping` — посчитайте.
4. Поменяйте на `ExpressShipping` — посчитайте.

Подумайте:

## Что дальше

Мы закончили модуль про полиморфизм. Разобрались, что такое полиморфизм, как работает динамическое связывание, чем интерфейсы отличаются от абстрактных классов, зачем нужны `default`-методы, как полиморфизм живёт в коллекциях, зачем нужно приведение типов, и как всё это собрать в паттерн «Стратегия».

В следующем модуле — **«Композиция и интерфейсы»** — мы поговорим о том, что «иметь» часто лучше, чем «быть». Что стратегия — это не единственный способ вынести поведение в объект. Что наследование, даже «честное», не всегда лучший инструмент, и что иногда класс, который **содержит** другой класс, — проще и надёжнее, чем класс, который от него **наследуется**.

А пока — маленькое упражнение на наблюдательность. Откройте любой свой проект (или открытый проект на Java) и найдите все `if/else` или `switch`, которые проверяют **тип** (а не значение — вроде `if (x > 5)`). Для каждого задайте вопрос: **это стабильно или это расширяется?** Если вариантов два и они не изменятся — оставьте. Если вариантов больше трёх и они могут расти — возможно, это кандидат на стратегию. Просто найдите. Не переделывайте (пока). Понимание того, где `if/else` — это «временное решение», а где — «долг», — уже большой шаг к более чистому коду.

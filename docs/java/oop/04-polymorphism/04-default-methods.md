# 4. default-методы

## Где вы это уже видели

В прошлом уроке мы говорили об интерфейсах как о «чистом контракте»: только объявления, без реализации. Так было до Java 8. Потом появились `default`-методы, и картина немного изменилась. Не сильно — интерфейсы по-прежнему остаются контрактами, — но достаточно, чтобы об этом стоило поговорить отдельно.

Идея `default`-методов кажется простой: «метод в интерфейсе с реализацией по умолчанию». Но за этой простотой стоит важная проблема, которую Java 8 решала, — и понимание этой проблемы объясняет, почему `default`-методы устроены именно так, а не иначе.

**Ситуация первая.** Вы выпустили библиотеку. Ею пользуются сто разработчиков, у каждого свой класс, реализующий ваш интерфейс. Проходит год, вы хотите добавить в интерфейс новый метод. И тут выясняется: если добавить его как абстрактный — **все сто классов перестанут компилироваться**, потому что они не реализуют новый метод. Вы не можете заставить сто человек переписать свой код. Что делать?

**Ситуация вторая.** Вы работаете в большой компании. Есть «общий интерфейс для всех контроллеров» — `Controller` с методами `handle()`, `validate()`, `log()`. Двести классов реализуют этот интерфейс. Вы хотите добавить метод `preHandle()`, который по умолчанию ничего не делает, но некоторые контроллеры могут его переопределить. Если добавить его как абстрактный — двести классов сломаются. Если не добавлять — не получится.

**Ситуация третья.** Вы пишете утилиту для работы со списками. У вас есть интерфейс `MyList` с методами `add()`, `get()`, `size()`. Вы хотите добавить метод `isEmpty()` — который просто проверяет, что `size() == 0`. Это **общая** логика для всех реализаций `MyList`, и писать её в каждом классе — бессмысленно. Но и абстрактным его делать не хочется — тогда все реализации должны его писать.

**Ситуация четвёртая.** Вы работаете с `Comparator`. Хотите отсортировать список в обратном порядке. Раньше приходилось писать отдельный класс `ReverseComparator`, который оборачивает другой компаратор. С Java 8 есть `comparator.reversed()` — метод, который возвращает «обратный» компаратор. И это `default`-метод в интерфейсе `Comparator`. Он не сломал ни один существующий компаратор, потому что у него есть реализация по умолчанию.

**Ситуация пятая.** Вы смотрите на код и видите:

```java
list.forEach(System.out::println);
```

— и не понимаете: `forEach` — это метод `List`? Вроде бы нет, `List` не объявляет его. Откуда он взялся? Ответ: это `default`-метод из `Iterable`, родительского интерфейса `Collection`, родительского для `List`. Он появился в Java 8 и работает для **всех** коллекций сразу — не сломав ни одну существующую реализацию.

**Ситуация шестая.** Вы пишете свой интерфейс, и у вас есть два интерфейса с одинаковым `default`-методом. Класс реализует оба. Что произойдёт? Компилятор скажет «конфликт», и вам придётся явно указать, какой из них использовать. Почему так — и как это разрешить — мы разберём в этом уроке.

Если последняя ситуация вам знакома — урок для вас. Если остальные тоже — интуиция про «добавить метод, не сломав код» у вас уже есть.

## Что такое default-метод

**`default`-метод** — это метод в интерфейсе **с реализацией по умолчанию**. Класс, реализующий интерфейс, может его не переопределять — тогда будет использована реализация из интерфейса.

Объявляется он так:

```java
interface Flyable {
    void fly();

    default void land() {
        System.out.println("Приземляюсь");
    }
}
```

Здесь `fly()` — обычный абстрактный метод (класс **обязан** его реализовать). `land()` — `default`-метод (класс **может** его не реализовывать, тогда сработает реализация из интерфейса).

Класс, реализующий `Flyable`, должен реализовать только `fly()`:

```java
class Bird implements Flyable {
    @Override
    public void fly() {
        System.out.println("Лечу!");
    }
    // land() не реализуем — используем default
}

Bird bird = new Bird();
bird.fly();    // Лечу!
bird.land();   // Приземляюсь (из default)
```

Если класс хочет **переопределить** `default`-метод — может:

```java
class Airplane implements Flyable {
    @Override
    public void fly() {
        System.out.println("Самолёт летит");
    }

    @Override
    public void land() {
        System.out.println("Самолёт садится в аэропорту");
    }
}
```

Теперь у `Airplane` своя реализация `land()`, а `Bird` использует `default`. Оба работают.

## Зачем это нужно: эволюция интерфейсов

До Java 8 интерфейсы были «чистым контрактом»: только объявления, без реализации. Это делало их простыми, но создавало большую проблему при **эволюции** — когда нужно добавить метод в уже существующий интерфейс.

Представьте, что в Java 7 у вас был интерфейс `Iterable` с одним методом `iterator()`:

```java
public interface Iterable<T> {
    Iterator<T> iterator();
}
```

Его реализуют сотни классов в стандартной библиотеке и тысячи — в пользовательском коде. Теперь вы хотите добавить `forEach()` — удобный метод для обхода. Что делать?

**Вариант 1: добавить как абстрактный метод.**

```java
public interface Iterable<T> {
    Iterator<T> iterator();
    void forEach(Consumer<? super T> action);   // новый метод
}
```

— и **все** реализации `Iterable` сломаются: они не реализуют `forEach()`. Придётся каждому добавить реализацию. В стандартной библиотеке — сотни классов. В пользовательском коде — тысячи. И это только один интерфейс.

**Вариант 2: не добавлять вообще.**

— и мы лишаемся удобного метода, который мог бы быть у всех. Плохо для пользователей.

**Вариант 3: сделать отдельный вспомогательный класс.**

```java
public class Iterables {
    public static <T> void forEach(Iterable<T> iterable, Consumer<? super T> action) {
        for (T item : iterable) {
            action.accept(item);
        }
    }
}
```

— и использовать как `Iterables.forEach(list, ...)`. Работает, но некрасиво: хочется `list.forEach(...)`, а не `Iterables.forEach(list, ...)`.

**Вариант 4 (Java 8): `default`-метод.**

```java
public interface Iterable<T> {
    Iterator<T> iterator();

    default void forEach(Consumer<? super T> action) {
        for (T item : this) {
            action.accept(item);
        }
    }
}
```

— и теперь `forEach()` **есть у всех** реализаций `Iterable` автоматически. Никто не сломался: классы, которые не переопределяют `forEach()`, используют `default`. Классы, которые хотят переопределить (например, `ArrayList` для оптимизации), — могут.

Это и есть **эволюция интерфейсов**: возможность добавлять методы в существующие интерфейсы, не ломая существующий код. Именно так в Java 8 добавили `stream()`, `forEach()`, `removeIf()` в коллекции, `Comparator.reversed()`, `thenComparing()` и многое другое.

## Как это работает под капотом

Технически `default`-метод — это обычный виртуальный метод, у которого есть реализация в интерфейсе. Когда класс не переопределяет его, — вызов идёт в интерфейс. Когда переопределяет — в класс.

JVM не различает «метод из интерфейса» и «метод из класса»: для неё это просто виртуальный метод, который надо найти по фактическому типу объекта. Если в классе есть реализация — берётся она. Если нет — ищется в интерфейсе.

Это значит, что `default`-методы **не ломают** динамическое связывание: всё работает так же, как с обычными методами. Просто «реализация по умолчанию» берётся из интерфейса, а не из класса.

## Конфликты default-методов

Тут начинается самая интересная часть. Что, если класс реализует **два** интерфейса, и в обоих есть `default`-метод с одинаковой сигнатурой?

```java
interface A {
    default void doSomething() {
        System.out.println("A");
    }
}

interface B {
    default void doSomething() {
        System.out.println("B");
    }
}

class C implements A, B {
    // ошибка компиляции: конфликт default-методов
}
```

Компилятор скажет: «`C` наследует неоднозначный `default`-метод `doSomething()` от `A` и `B`». Класс `C` **обязан** явно разрешить конфликт — переопределить метод:

```java
class C implements A, B {
    @Override
    public void doSomething() {
        A.super.doSomething();   // явно выбираем A
        // или B.super.doSomething();
        // или своя реализация
    }
}
```

Синтаксис `A.super.doSomething()` — это «вызвать `default`-реализацию из интерфейса `A`». Он позволяет явно указать, какой из двух вариантов использовать.

**Это не «diamond problem» в классическом смысле.** В C++ множественное наследование классов приводит к «ромбовидной» проблеме: если `D` наследует `B` и `C`, а те — от `A`, то непонятно, чью версию метода `A` использовать. В Java эта проблема **не возникает**, потому что:

- классы наследуются только от **одного** родителя;
- интерфейсы не имеют состояния (полей), поэтому «ромб» не создаёт неоднозначности данных;
- для `default`-методов Java требует явного разрешения конфликта.

Так что `default`-методы — это **не множественное наследование**, а «множественная реализация с явным разрешением конфликтов». Разница важная: в C++ программист может «случайно» получить неоднозначность, а в Java — компилятор **заставит** её разрешить.

## Правила и ограничения

У `default`-методов есть несколько ограничений, которые полезно знать.

**Первое: `default`-метод не может быть `final`.** Это логично: `final` запрещает переопределение, а `default` существует именно для того, чтобы его можно было переопределить. Компилятор не даст написать `default final`.

**Второе: `default`-метод не может быть `static`.** `static`-метод принадлежит классу, а не объекту, и не наследуется в обычном смысле. `default` — это «виртуальный метод с реализацией по умолчанию», и он должен быть нестатическим. Компилятор не даст написать `default static`.

**Третье: `default`-метод может обращаться только к другим методам интерфейса.** У интерфейса нет полей (кроме `static final`), поэтому `default`-метод не может работать с состоянием. Он может вызывать другие методы интерфейса — абстрактные или `default`.

**Четвёртое: `default`-метод может быть `private` (Java 9+).** Это полезно для вспомогательных методов внутри интерфейса, которые не должны быть видны снаружи. Об этом — чуть ниже.

**Пятое: если класс реализует интерфейс и наследует класс с одинаковым методом, — приоритет у класса.** Если `class C extends Base implements A`, и в `Base` есть `doSomething()`, а в `A` — `default doSomething()`, — приоритет у `Base.doSomething()`. Java считает, что «класс важнее интерфейса»: если у класса есть реализация, — она используется.

Это правило важно понимать: **`default`-методы — это «запасной вариант», а не «главный»**. Если есть реализация в классе (или в его родителе), — она выигрывает.

## static и private методы в интерфейсах

В Java 8 появились не только `default`-методы, но и **`static`-методы в интерфейсах**. В Java 9 — **`private`-методы в интерфейсах**. Они дополняют `default` и делают интерфейсы более выразительными.

**`static`-методы в интерфейсах** — это «утилитные» методы, привязанные к интерфейсу, но не к объекту. Например:

```java
interface Comparator<T> {
    int compare(T a, T b);

    static <T extends Comparable<T>> Comparator<T> naturalOrder() {
        return (a, b) -> a.compareTo(b);
    }
}
```

`Comparator.naturalOrder()` — `static`-метод, который возвращает «естественный» компаратор. Его не нужно реализовывать в классах; он просто «есть у интерфейса».

**`private`-методы в интерфейсах** (Java 9+) — это «вспомогательные» методы, которые используются внутри `default`-методов, но не видны снаружи:

```java
interface Greeter {
    void greet(String name);

    default void greetAll(List<String> names) {
        for (String name : names) {
            logGreeting(name);
            greet(name);
        }
    }

    private void logGreeting(String name) {
        System.out.println("Логируем приветствие для " + name);
    }
}
```

`logGreeting` — `private`, значит, его нельзя вызвать снаружи. Но `default`-метод `greetAll` может его использовать. Это позволяет избежать дублирования кода между `default`-методами, не открывая вспомогательные методы наружу.

Так что современный интерфейс — это не «только объявления», а:

- **абстрактные** методы (обязательные для реализации);
- **`default`** методы (с реализацией по умолчанию);
- **`static`** методы (утилитные, привязаны к интерфейсу);
- **`private`** методы (вспомогательные, для `default` и `static`).

Это гораздо богаче, чем «чистый контракт» Java 7, но и сложнее. Главное — использовать каждую возможность **по назначению**.

## Когда default-методы — плохая идея

`default`-методы — мощный инструмент, но у него есть тёмная сторона.

**Когда они «притворяются» общими, но на самом деле — частные.** Если `default`-метод подходит не всем реализациям, — это проблема. Например, `default void fly()` в `Animal` — плохо, потому что не все животные летают. Классы, которые не летают, вынуждены переопределять метод (например, бросать исключение), — а это уже «наследование, которое врёт», о котором мы говорили в модуле 3.

Правило: **`default`-метод должен подходить всем реализациям интерфейса без исключения**. Если есть хотя бы одна реализация, которой он не подходит, — это не «общая реализация», а «навязанная».

**Когда они «размывают» контракт.** Интерфейс — это контракт. `default`-методы делают контракт «мягче»: часть методов необязательна. Если в интерфейсе слишком много `default`-методов, — он становится «полуклассом», и теряется его главное преимущество — простота контракта.

**Когда они «прячут» проблему проектирования.** Иногда `default`-методы используются как «костыль»: чтобы добавить метод в интерфейс, не меняя классы. Но если метод нужен **всем** классам и **все** его реализуют одинаково, — возможно, это не «интерфейс с `default`», а **абстрактный класс**, который даёт общую реализацию.

Правило: **если у `default`-метода есть осмысленная общая реализация для всех — можно. Если это «костыль» — не надо**.

**Когда они создают конфликты.** Если вы пишете библиотеку и добавляете `default`-метод в интерфейс, — вы можете создать конфликт с `default`-методом из другого интерфейса, который реализует ваш класс. Пользователям придётся явно разрешать конфликт. Это не катастрофа, но неудобство.

**Когда они «замораживают» реализацию.** Если `default`-метод использует другие методы интерфейса и вы завтра поменяете эти методы, — `default` может сломаться. Это та же проблема хрупкого базового класса, о которой мы говорили в модуле 3, только теперь — на уровне интерфейса.

Общее правило: **`default`-методы — это инструмент эволюции интерфейсов, а не «способ добавить реализацию в интерфейс»**. Используйте их, когда нужно **добавить** метод, не ломая существующий код. Не используйте их, когда нужно «сделать интерфейс похожим на абстрактный класс».

## Аналогия, которая помогает

Хорошая аналогия — **стандартный договор с опциональными пунктами**.

Представьте, что у вас есть **стандартный договор аренды**. В нём есть обязательные пункты: «арендатор обязуется платить», «арендодатель обязуется предоставить помещение». И есть **опциональные** пункты: «арендатор имеет право держать домашних животных», «арендодатель обязуется делать ремонт раз в год». Эти пункты **уже прописаны** в стандартном договоре, но арендатор и арендодатель могут их «переопределить» — например, добавить «запрет на животных» или «ремонт раз в два года».

**`default`-метод — это опциональный пункт.** Он уже прописан (есть реализация по умолчанию), но стороны могут его изменить (переопределить в классе). Если не изменили — работает стандартный вариант.

**Абстрактный метод — это обязательный пункт.** Он должен быть явно прописан в каждом конкретном договоре, иначе договор недействителен.

**Конфликт `default`-методов — это как если бы у вас было два стандартных договора** (например, от разных юристов), и они противоречили бы друг другу в одном пункте. Вы не можете подписать оба «как есть» — придётся явно указать, какой пункт использовать.

**`static`-метод в интерфейсе — это как «приложение к договору»**: типовой документ, который прилагается к договору, но не является его частью. Вы можете им пользоваться, но он «не про вас конкретно».

**`private`-метод в интерфейсе — это как «внутренняя инструкция для юриста»**: она используется при составлении договора, но клиенту её не показывают.

И ещё одна мысль: **стандартный договор — это не «универсальный»**. Он подходит для типичных случаев, но если у вас особый случай — придётся его переделывать (переопределять). `default`-метод — то же самое: он для «типичного» случая, и если ваш случай не типичный, — переопределяйте.

## Микрозадача 1

Вот код. Что выведется? Объясните, почему.

```java
interface A {
    default void hello() {
        System.out.println("A.hello");
    }
}

interface B {
    default void hello() {
        System.out.println("B.hello");
    }
}

class C implements A, B {
    @Override
    public void hello() {
        A.super.hello();
        B.super.hello();
    }
}

new C().hello();
```

### Разбор

Выведется:

```
A.hello
B.hello
```

Разберём по шагам.

`A` и `B` имеют одинаковый `default`-метод `hello()`. Класс `C` реализует оба интерфейса, и **обязан** разрешить конфликт — иначе не скомпилируется.

`C` переопределяет `hello()` и явно вызывает **оба** варианта: `A.super.hello()` и `B.super.hello()`. Синтаксис `InterfaceName.super.method()` позволяет вызвать `default`-реализацию **конкретного** интерфейса.

Порядок вызовов: сначала `A.super.hello()` — печатает `A.hello`. Потом `B.super.hello()` — печатает `B.hello`. Итог: две строки.

**Что было бы, если бы `C` не переопределял `hello()`?** — ошибка компиляции: «`C` наследует неоднозначный `default`-метод `hello()` от `A` и `B`». Java **не даёт** «выбрать случайно» — нужно явное разрешение.

**Что было бы, если бы `C` переопределил `hello()` без `super`?** — работало бы, но печатало бы только то, что в `C.hello()`. `A.super.hello()` и `B.super.hello()` не вызывались бы.

**Мораль.** `default`-методы могут конфликтовать, и Java требует **явного** разрешения конфликта. Это сделано специально: лучше заставить программиста подумать, чем «молча выбрать один из двух» и получить непредсказуемое поведение. Синтаксис `InterfaceName.super.method()` — это способ сказать «я знаю, что делаю, вызови именно эту реализацию».

## Микрозадача 2

Вот код. Он выглядит правильным, но работает не так, как задумано. Найдите проблему.

```java
interface Animal {
    default void speak() {
        System.out.println("...");
    }
}

class Dog implements Animal {
    // ничего не переопределяет — использует default
}

class Cat implements Animal {
    @Override
    public void speak() {
        System.out.println("Мяу");
    }
}

Animal a = new Dog();
a.speak();   // ожидаем "..."
Animal c = new Cat();
c.speak();   // ожидаем "Мяу"
```

### Разбор

Код **компилируется и работает** так, как задумано: `a.speak()` печатает `...`, `c.speak()` печатает `Мяу`. Где же проблема?

Проблема — **концептуальная**, а не техническая. `default void speak()` в интерфейсе `Animal` — это **неправильное использование** `default`-метода.

Почему? Потому что `speak()` — это **не «общая реализация для всех животных»**. У кошки «мяу», у собаки «гав», у коровы «му». **Нет** «общего звука», который издают все животные. `...` — это не «реализация по умолчанию», а «заглушка», которая **не имеет смысла** для большинства животных.

Что произойдёт, если кто-то добавит `class Cow implements Animal { }` и забудет переопределить `speak()`? — корова будет молчать (`...`), хотя должна мычать. И **компилятор не поможет**: `default`-метод «удовлетворяет» требование, и ошибка не будет видна.

Это та же проблема, что мы обсуждали в уроке 2 (микрозадача 2): **«пустая реализация» скрывает ошибку**. Если `speak()` был бы абстрактным — `Cow` не скомпилировался бы, и программист сразу бы увидел, что забыл реализовать. С `default` — ошибка вылезет только в момент выполнения, когда корова «промолчит».

**Как исправить.** Сделать `speak()` абстрактным:

```java
interface Animal {
    void speak();   // абстрактный — все обязаны реализовать
}
```

Теперь `Dog`, `Cat`, `Cow` **обязаны** реализовать `speak()`. Компилятор проверит. Никто не забудет.

**Когда `default` был бы уместен?** Если бы у всех животных был **общий** звук, который некоторые переопределяют. Например:

```java
interface Animal {
    default void breathe() {
        System.out.println("Дышит");
    }
}
```

`breathe()` — общая реализация для всех животных (все дышат). `Dog`, `Cat`, `Cow` могут её не переопределять — она подходит. А если какое-то животное дышит по-особенному (например, лягушка «дышит кожей»), — оно переопределит.

**Мораль.** `default`-метод — это **не «реализация по умолчанию для всех»**, а «общая реализация, которую можно переопределить». Если метод **должен** быть разным у разных реализаций, — он должен быть **абстрактным**. `default` «скрывает» ошибки: класс может «забыть» реализовать метод, и это не будет видно компилятору.

# 3. Интерфейсы

## Где вы это уже видели

Два урока мы говорили о полиморфизме, и всё время через наследование: `Cat extends Animal`, `Dog extends Animal` — и `a.speak()` работает по-разному. Но у наследования есть жёсткое ограничение: **у класса может быть только один родитель**. А что делать, если нужно, чтобы объект умел сразу несколько вещей?

Вот тут на сцену выходят интерфейсы. Это вторая (и часто более удобная) форма полиморфизма.

**Ситуация первая.** Вы смотрите на сотрудника. Он **разработчик** (умеет писать код) и **тимлид** (умеет руководить командой) одновременно. Это не «разработчик, который **является** тимлидом» и не «тимлид, который **является** разработчиком». Это «человек, который умеет и то, и другое». В Java это выражается через интерфейсы: `class Person implements Developer, TeamLead`.

**Ситуация вторая.** Вы смотрите на утюг. Он **нагревается** (умеет нагревать) и **имеет терморегулятор** (умеет поддерживать температуру). Это две разные «способности», и утюг умеет обе. Через наследование это выразить нельзя (утюг не «является» нагревателем и не «является» терморегулятором — он **умеет** и то, и другое).

**Ситуация третья.** Вы смотрите на телефон. Он **звонит**, **фотографирует**, **показывает время**, **платит**, **слушает музыку**. Пять разных способностей — а объект один. Если бы каждая способность была «родителем», — телефон не смог бы «унаследоваться» от всех пятерых (в Java множественное наследование запрещено). Но через интерфейсы — легко: `class Phone implements Callable, Camera, Clock, Payable, MusicPlayer`.

**Ситуация четвёртая.** Вы смотрите на договор. У договора есть **контракт**: «поставщик обязуется поставить товар к такой-то дате, а заказчик — оплатить». Контракт не говорит, **как** именно поставщик будет поставлять (грузовиком? курьером? почтой?) — он только фиксирует **что** должно быть сделано. Это и есть интерфейс: «я обязуюсь уметь это, а как — моё дело».

**Ситуация пятая.** Вы смотрите на вакансию. Там написано: «Требуется разработчик с опытом Java, знанием SQL и английским». Это три **требования** к кандидату. Кандидат должен **уметь** все три вещи. Не «быть наследником» какого-то класса, а **уметь** то, что нужно. Это тоже интерфейс: «я соответствую требованиям».

**Ситуация шестая.** Вы пишете код и видите:

```java
class ArrayList<E> implements List<E>, RandomAccess, Cloneable, Serializable {
    // ...
}
```

— и не понимаете: `List`, `RandomAccess`, `Cloneable`, `Serializable` — это всё интерфейсы? Что они дают? И почему их четыре, а не один? И почему `ArrayList` — не «наследник» ни одного из них, а «реализует»?

Если последняя ситуация вам знакома — урок для вас. Если остальные тоже — интуиция про «способности» у вас уже есть.

## Что такое интерфейс

**Интерфейс** (interface) — это **чистый контракт**: набор методов, которые класс обязуется реализовать. Без реализации. Без полей. Только «что», без «как».

Объявляется он так:

```java
interface Flyable {
    void fly();
}
```

Здесь `Flyable` — интерфейс. У него один метод `fly()`. Без тела. С точкой с запятой.

Класс **реализует** интерфейс через `implements`:

```java
class Bird implements Flyable {
    @Override
    public void fly() {
        System.out.println("Лечу!");
    }
}
```

Теперь `Bird` **является** `Flyable`. Везде, где ожидается `Flyable`, — `Bird` подойдёт.

Можно реализовать **несколько** интерфейсов:

```java
class Duck implements Flyable, Swimmable, Quackable {
    @Override public void fly() { ... }
    @Override public void swim() { ... }
    @Override public void quack() { ... }
}
```

Теперь `Duck` умеет летать, плавать и крякать одновременно. И везде, где ожидается `Flyable`, `Swimmable` или `Quackable`, — `Duck` подойдёт.

## Ключевые отличия от абстрактного класса

Интерфейс и абстрактный класс похожи: оба не имеют (полной) реализации, оба используются для полиморфизма. Но есть несколько принципиальных отличий.

| Характеристика | Абстрактный класс | Интерфейс |
|---|---|---|
| Можно создать объект? | Нет | Нет |
| Можно наследоваться/реализовать? | Один родитель (`extends`) | Несколько (`implements`) |
| Может содержать поля? | Да (обычные, `static`) | Только `static final` (константы) |
| Может содержать конструкторы? | Да | Нет (нельзя создать объект) |
| Может содержать обычные методы? | Да | Да (начиная с Java 8 — `default`) |
| Может содержать абстрактные методы? | Да | Да |
| Может содержать `private`-методы? | Да | Да (начиная с Java 9) |

Главное отличие — **множественная реализация**. Класс может реализовать **сколько угодно** интерфейсов, но наследоваться — только от **одного** класса.

Второе важное отличие — **отсутствие состояния**. Интерфейс не может содержать обычных полей (только `static final` — константы). Это значит, что интерфейс — это **чистый контракт**, без общей реализации данных.

## Зачем нужны интерфейсы

Интерфейсы решают несколько задач, и все они — про **гибкость**.

### Множественная «принадлежность»

В отличие от наследования, класс может реализовать несколько интерфейсов. Это позволяет выразить «множественные способности» — как в примере с телефоном, который умеет звонить, фотографировать, показывать время, платить и слушать музыку.

### Разделение контракта и реализации

Интерфейс говорит: «вот **что** нужно уметь». Класс говорит: «вот **как** я это делаю». Эти две вещи можно менять независимо: если завтра вы захотите заменить `Bird` на `Airplane`, — интерфейс `Flyable` не меняется, а `Airplane` просто реализует его по-своему.

### Гибкость при проектировании

Вы можете проектировать **сначала** интерфейсы, а потом — реализации. Например, сначала описать «что должен уметь платёжный сервис» (`PaymentProcessor` с методом `pay()`), а потом — сделать реализации для Stripe, PayPal, Robokassa. При этом код, который работает с `PaymentProcessor`, можно писать **до** того, как появятся реализации, — и он будет работать с любыми реализациями, включая завтрашние.

### Тестирование

В тестах можно подменить настоящую реализацию на «заглушку». Если у вас есть интерфейс `PaymentProcessor`, — в тесте можно подставить `FakePaymentProcessor`, который ничего не делает, но возвращает `true`. Код теста работает с `PaymentProcessor` и не знает, что там заглушка.

### Множественное поведение без наследования

Если вам нужно, чтобы класс «умел» что-то, но не «являлся» кем-то конкретным, — интерфейс идеален. Например, `String implements CharSequence, Comparable<String>, Serializable` — `String` не «является» ни `CharSequence`, ни `Comparable` в смысле наследования; он **умеет** быть последовательностью символов, **умеет** сравниваться, **умеет** сериализоваться.

## default-методы — интерфейсы с реализацией

До Java 8 интерфейсы были **чистым контрактом**: только объявления методов, без реализации. В Java 8 появились `default`-методы — методы с реализацией **внутри интерфейса**.

```java
interface Flyable {
    void fly();

    default void land() {
        System.out.println("Приземляюсь");
    }
}
```

Теперь класс, реализующий `Flyable`, **обязан** реализовать только `fly()`. `land()` — необязателен: если не переопределить, — будет использована реализация по умолчанию.

**Зачем это нужно.** Представьте, что у вас есть интерфейс с десятью методами, и его реализуют сто классов. Вы хотите добавить одиннадцатый метод. До Java 8 пришлось бы добавить его во все сто классов — иначе не скомпилируется. С `default` — можно добавить метод в интерфейс с реализацией по умолчанию, и все сто классов продолжат компилироваться.

Это называется **эволюция интерфейсов**: возможность добавлять методы в существующие интерфейсы, не ломая существующие реализации. Именно так в Java 8 добавили `stream()`, `forEach()`, `removeIf()` в коллекции — без слома существующего кода.

**Ограничения.**

- `default`-метод не может быть `final` (его можно переопределить) или `static` (это не «метод класса»).
- `default`-метод не имеет доступа к полям (в интерфейсе нет полей, кроме `static final`).
- Если два интерфейса имеют одинаковый `default`-метод и класс реализует оба, — компилятор потребует **переопределить** метод в классе (иначе неоднозначность).

## Абстрактный класс vs интерфейс — что выбирать

Это, пожалуй, самый частый вопрос, и на него нет универсального ответа. Но есть несколько эвристик.

**Выбирайте интерфейс, если:**

- нужен **чистый контракт** без реализации;
- класс должен **уметь несколько** независимых вещей (множественная реализация);
- вы проектируете **API** для других разработчиков (интерфейс проще понять, чем абстрактный класс);
- вы хотите, чтобы класс мог реализовать несколько «способностей» одновременно;
- нет общего состояния, которое нужно хранить.

**Выбирайте абстрактный класс, если:**

- есть **общая реализация**, которую наследники должны использовать (а не просто «уметь»);
- есть **общее состояние** (поля), которое нужно хранить;
- вы хотите **частичную реализацию**: часть методов — общая, часть — абстрактная;
- иерархия — «единственная» (наследование от одного класса), без множественности;
- вы хотите контролировать, **как** наследники переопределяют методы (через `final`-методы с «шаблонным» поведением).

**Пример.** В стандартной библиотеке Java:

- `List`, `Set`, `Map` — **интерфейсы** (контракт: «это коллекция с такими-то методами»);
- `AbstractList`, `AbstractSet`, `AbstractMap` — **абстрактные классы** (частичная реализация, чтобы облегчить создание новых коллекций).

Авторы библиотеки выбрали интерфейс для «контракта» и абстрактный класс для «общей реализации». И это хороший пример: **интерфейс описывает, что умеет коллекция; абстрактный класс даёт каркас для её реализации**.

**Правило большого пальца:** **начинайте с интерфейса**. Если потом окажется, что нужна общая реализация, — добавьте абстрактный класс, который реализует интерфейс и даёт общую реализацию. Это стандартный паттерн, и в стандартной библиотеке Java он используется повсеместно.

## Вложенные и функциональные интерфейсы

Есть несколько разновидностей интерфейсов, которые полезно знать.

**Вложенные интерфейсы.** Интерфейс может быть объявлен внутри класса или другого интерфейса. Например, `Map.Entry` — вложенный интерфейс в `Map`. Это удобно для группировки: «вот `Map`, а вот `Entry` — запись в `Map`».

**Функциональные интерфейсы.** Это интерфейсы с **одним** абстрактным методом (плюс любое количество `default`/`static`). Начиная с Java 8, их можно реализовать лямбда-выражением:

```java
@FunctionalInterface
interface Greeter {
    void greet(String name);
}

Greeter greeter = name -> System.out.println("Привет, " + name);
greeter.greet("Алиса");
```

Функциональные интерфейсы — это основа лямбд и Stream API. Они заслуживают отдельного разговора, и мы их разберём, когда будем говорить о функциональном программировании (если будет такой модуль). Пока что запомните: **функциональный интерфейс = один абстрактный метод**, и он может быть реализован лямбдой.

**Маркерные интерфейсы.** Это интерфейсы **без методов вообще**. Они ничего не «требуют», а просто «помечают» класс. Например:

- `Serializable` — «этот объект можно сериализовать»;
- `Cloneable` — «этот объект можно клонировать через `clone()`»;
- `RandomAccess` — «этот список поддерживает быстрый доступ по индексу» (подсказка для алгоритмов).

Маркерные интерфейсы — это способ «пометить» класс для фреймворка или алгоритма. Сам по себе маркер ничего не делает; он только сообщает что-то во внешний код.

## Аналогия, которая помогает

Хорошая аналогия — **дипломы и сертификаты**.

Представьте, что у вас есть **диплом** о высшем образовании. Это «наследование»: вы **являетесь** бакалавром/магистром, у вас есть все знания и навыки, которые даёт эта программа. Диплом один (как и родитель в Java).

Теперь представьте, что у вас есть **сертификаты**: сертификат по Java, сертификат по SQL, сертификат по английскому. Это «интерфейсы»: вы **умеете** Java, SQL и английский, но не «являетесь» Java, SQL и английским. Сертификатов может быть сколько угодно (как и интерфейсов).

**Диплом** даёт вам «базу»: общие знания, которые есть у всех выпускников. Это как абстрактный класс с общей реализацией.

**Сертификаты** — это «контракты»: они говорят «я умею это», но не говорят «как именно я это делаю». Один человек может иметь десять сертификатов, и все они независимы.

**`default`-методы** — это как «стандартные курсы» в сертификате. Например, сертификат по Java может включать «стандартный курс по основам», который все обладатели сертификата проходят автоматически. Но если вы уже знаете основы, — можете «переопределить» этот курс своим опытом.

**Маркерные интерфейсы** — это как «печать в паспорте»: она ничего не говорит о навыках, но отмечает что-то важное (например, «гражданин РФ»). Это просто метка, которая помогает «внешнему миру» понять что-то о вас.

**Множественная реализация** — это ключевое преимущество: у человека может быть **один** диплом и **десять** сертификатов. В Java: **один** родитель и **десять** интерфейсов. Это гораздо гибче, потому что «уметь» можно много чего, а «быть» — только кем-то одним.

## Микрозадача 1

Вот код. Что произойдёт? Объясните, почему.

```java
interface Flyable {
    void fly();
}

interface Swimmable {
    void swim();
}

class Duck implements Flyable, Swimmable {
    @Override
    public void fly() {
        System.out.println("Утка летит");
    }

    @Override
    public void swim() {
        System.out.println("Утка плывёт");
    }
}

class Airplane implements Flyable {
    @Override
    public void fly() {
        System.out.println("Самолёт летит");
    }
}

Flyable[] flyables = { new Duck(), new Airplane() };
for (Flyable f : flyables) {
    f.fly();
}

Swimmable[] swimmables = { new Duck() };
for (Swimmable s : swimmables) {
    s.swim();
}
```

### Разбор

Выведется:

```
Утка летит
Самолёт летит
Утка плывёт
```

Разберём по шагам.

**`Flyable[] flyables = { new Duck(), new Airplane() };`** — массив типа `Flyable`. В него можно положить любой объект, который **реализует** `Flyable`. `Duck` реализует — можно. `Airplane` реализует — можно. А вот `Bird` (если бы он был, но не реализовывал `Flyable`) — нельзя.

**`for (Flyable f : flyables) { f.fly(); }`** — цикл по массиву `Flyable`. Для каждого элемента вызывается `fly()`. Какой именно `fly()` — зависит от фактического типа: у `Duck` — `Duck.fly()`, у `Airplane` — `Airplane.fly()`. Это полиморфизм через интерфейс: **код цикла не знает**, что там `Duck` или `Airplane`, — он работает с `Flyable` и вызывает `fly()`.

**`Swimmable[] swimmables = { new Duck() };`** — массив типа `Swimmable`. В него можно положить **только** `Duck` (потому что `Airplane` не реализует `Swimmable`). Если бы мы попытались добавить `Airplane` — компилятор не дал бы.

**`for (Swimmable s : swimmables) { s.swim(); }`** — цикл по `Swimmable`. Вызывается `swim()`. Работает, потому что `Duck` реализует `Swimmable`.

**Ключевая мысль.** Один и тот же объект `Duck` может быть использован **и как `Flyable`, и как `Swimmable`**. В первом цикле он «притворяется» `Flyable`, во втором — `Swimmable`. Код цикла не меняется, но «роль» объекта — разная. Это и есть множественная «принадлежность»: `Duck` **является** и `Flyable`, и `Swimmable`.

## Микрозадача 2

Вот код. Что произойдёт при компиляции? Объясните.

```java
interface A {
    void doSomething();
}

interface B {
    void doSomething();
}

class C implements A, B {
    @Override
    public void doSomething() {
        System.out.println("C");
    }
}
```

### Разбор

Код **скомпилируется**. И это правильно.

Что здесь происходит. У интерфейсов `A` и `B` есть **одинаковый** метод `doSomething()`. Класс `C` реализует оба интерфейса. Компилятор видит: «`C` должен реализовать `doSomething()` для `A` и для `B`». Но это **один и тот же метод** — `C.doSomething()`. Значит, `C` его реализует **один раз**, и это удовлетворяет **оба** интерфейса.

Вот почему это работает: **методы в интерфейсах — это «требования», а не «разные методы»**. Если у `A` и `B` одинаковое требование — оно одно, и его достаточно выполнить один раз.

**Когда это ломается.** Если у `A` и `B` есть `default`-методы с **разными** реализациями для одного и того же метода:

```java
interface A {
    default void doSomething() { System.out.println("A"); }
}

interface B {
    default void doSomething() { System.out.println("B"); }
}

class C implements A, B {
    // ошибка компиляции: конфликт default-методов
}
```

Здесь `C` не может выбрать — «наследовать» `doSomething()` от `A` или от `B`. Оба варианта «правильные», и компилятор не знает, какой выбрать. Решение: **переопределить** метод в `C` явно:

```java
class C implements A, B {
    @Override
    public void doSomething() {
        A.super.doSomething();   // явно выбираем реализацию A
        // или B.super.doSomething();
        // или своя реализация
    }
}
```

Синтаксис `A.super.doSomething()` — это «вызвать `default`-реализацию из интерфейса `A`». Он позволяет разрешить конфликт.

**Мораль.** Одинаковые **абстрактные** методы в интерфейсах не конфликтуют (это одно требование). А одинаковые **`default`** методы — конфликтуют (это две разные реализации). Компилятор требует явного разрешения конфликта.

## Самостоятельная задача

Спроектируйте систему для интернет-магазина с интерфейсами.

Интерфейс `Payable` с методом `void pay(double amount)`.

Интерфейс `Shippable` с методом `void ship(String address)`.

Интерфейс `Trackable` с методом `String getTrackingNumber()`.

Классы:

- `PhysicalProduct implements Payable, Shippable` — обычный товар (нужно оплатить и доставить);
- `DigitalProduct implements Payable` — цифровой товар (нужно оплатить, но не доставлять — он «скачивается»);
- `Subscription implements Payable, Trackable` — подписка (нужно оплатить, и можно отслеживать статус);
- `GiftCard implements Payable` — подарочная карта (только оплата).

В `main`:

1. Создайте по одному объекту каждого типа.
2. Создайте список `Payable[]` и положите туда все четыре — вызовите `pay(100)` у каждого.
3. Создайте список `Shippable[]` и положите туда только `PhysicalProduct` — вызовите `ship("Москва")`.
4. Создайте список `Trackable[]` и положите туда только `Subscription` — вызовите `getTrackingNumber()`.
5. Убедитесь, что `DigitalProduct` **нельзя** положить в `Shippable[]` (попробуйте — компилятор не даст).

Подумайте:

- почему `PhysicalProduct` может быть в трёх разных массивах? Что это говорит о множественной реализации?
- что было бы, если бы `Payable`, `Shippable` и `Trackable` были абстрактными классами вместо интерфейсов? Смог бы `PhysicalProduct` «наследоваться» от всех трёх?
- нужно ли делать эти интерфейсы абстрактными классами? Почему нет?
- что произойдёт, если завтра появится `Bundle implements Payable, Shippable, Trackable` — набор из нескольких товаров? Сколько файлов придётся менять?

Готового ответа не будет. Если хотите свериться — загляните в следующий урок про `default`-методы: там мы разберём, как добавлять методы в интерфейсы, не ломая существующий код, и вы увидите, насколько ваша интуиция про «эволюцию интерфейсов» совпала с тем, как это устроено в Java.

## Что дальше

Мы разобрались, что такое интерфейс, чем он отличается от абстрактного класса, и когда что выбирать. В следующем уроке — **«`default`-методы»** — мы поговорим о том, как добавлять методы в интерфейсы с реализацией, не ломая существующие классы. Это одна из главных «новинок» Java 8, и она сильно изменила то, как проектируются интерфейсы.

А пока — маленькое упражнение на наблюдательность. Откройте любой код, где есть `implements` (в своём проекте или в стандартной библиотеке). Посмотрите на класс и задайте вопрос: **почему именно эти интерфейсы?** Что он «умеет»? Можно ли было обойтись одним абстрактным классом? Если нет — почему? Просто посмотрите. Не меняйте (пока). Понимание того, **как** используются интерфейсы в реальном коде, — уже большой шаг к тому, чтобы применять их осознанно.

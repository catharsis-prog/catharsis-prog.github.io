# 6. Приведение типов и instanceof

## Где вы это уже видели

Пять уроков мы говорили о полиморфизме как о чём-то хорошем: работать с объектом через общий контракт, не зная конкретного типа. Но иногда возникает обратная ситуация: у вас есть переменная типа `Animal`, а вам **нужен** `Dog` — потому что только у `Dog` есть метод `bark()`. Что делать?

Ответ — **приведение типов** (type casting) и проверка типа через **`instanceof`**. Это инструменты, которые позволяют «вернуть» конкретный тип, когда полиморфизма недостаточно. Но у них есть тёмная сторона, и в этом уроке мы разберёмся, когда они оправданы, а когда — нет.

**Ситуация первая.** Вы работаете с зоопарком. У вас есть `List<Animal>`, и вы хотите «покормить только собак» — потому что у собак особый рацион. Вы проходите по списку и для каждого `Animal` проверяете: «А это `Dog`? Если да — кормить по-собачьему». Это `instanceof` в действии.

**Ситуация вторая.** Вы работаете с геометрическими фигурами. У вас есть `List<Shape>`, и вы хотите «повернуть все прямоугольники на 90 градусов». У `Shape` нет метода `rotate()`, но у `Rectangle` есть. Вы проверяете тип и вызываете `rotate()` только у прямоугольников.

**Ситуация третья.** Вы пишете обработчик событий. Приходит `Event`, и в зависимости от типа (`ClickEvent`, `KeyEvent`, `MouseEvent`) вы делаете что-то разное. Это классический `instanceof` — и, возможно, признак того, что обработчик стоит спроектировать иначе.

**Ситуация четвёртая.** Вы работаете с JSON. Приходит `Object` — а внутри может быть `String`, `Integer`, `List`, `Map`. Вы проверяете тип и обрабатываете соответственно. Здесь `instanceof` оправдан: JSON не типизирован, и вы вынуждены проверять.

**Ситуация пятая.** Вы пишете утилиту, которая принимает `Object` (например, `toString(Object)`) и пытается понять, что с ним делать. Если это `String` — вернуть как есть. Если `Number` — отформатировать. Если `null` — вернуть «null». Это `instanceof` — и здесь он тоже оправдан, потому что тип неизвестен заранее.

**Ситуация шестая.** Вы пишете код и видите:

```java
if (animal instanceof Dog) {
    ((Dog) animal).bark();
} else if (animal instanceof Cat) {
    ((Cat) animal).meow();
} else if (animal instanceof Cow) {
    ((Cow) animal).moo();
}
```

— и понимаете, что это **не полиморфизм**. Здесь нет «одного вызова — разных поведений»; здесь есть **явная проверка типов**. И каждый раз, добавляя новое животное, придётся дописывать новую ветку. Это то самое, от чего полиморфизм должен был избавить, — но по какой-то причине не избавил.

Если последняя ситуация вам знакома — урок для вас. Если остальные тоже — интуиция про «проверить тип и сделать что-то» у вас уже есть.

## Что такое instanceof

**`instanceof`** — это оператор, который проверяет, является ли объект экземпляром указанного класса (или его наследником, или реализует указанный интерфейс).

```java
Animal a = new Dog();
System.out.println(a instanceof Dog);     // true
System.out.println(a instanceof Cat);     // false
System.out.println(a instanceof Animal);  // true (Dog — это Animal)
System.out.println(a instanceof Object);  // true (всё — Object)
```

Синтаксис: `object instanceof ClassName`. Возвращает `boolean`: `true`, если объект можно привести к указанному типу, и `false` — если нет.

**Важно:** `instanceof` проверяет **фактический тип объекта**, а не тип переменной. В примере выше переменная `a` имеет тип `Animal`, но `a instanceof Dog` возвращает `true`, потому что объект на самом деле — `Dog`.

Если `a` — `null`, то `a instanceof Anything` всегда `false`:

```java
Animal a = null;
System.out.println(a instanceof Animal);   // false
```

Это удобно: не нужно проверять на `null` отдельно перед `instanceof`.

## Приведение типов

**Приведение типов** (type casting) — это преобразование значения одного типа к другому. В Java есть два вида: **расширяющее** (upcasting) и **сужающее** (downcasting).

**Расширяющее приведение** (upcasting) — от наследника к родителю. Безопасно, выполняется **автоматически**:

```java
Dog dog = new Dog();
Animal animal = dog;   // upcasting — автоматически
```

Это работает, потому что `Dog` **является** `Animal`. Никаких проверок не нужно, никаких исключений не бывает.

**Сужающее приведение** (downcasting) — от родителя к наследнику. **Опасно**, требует **явного** приведения:

```java
Animal animal = new Dog();
Dog dog = (Dog) animal;   // downcasting — явное приведение
```

Здесь мы говорим компилятору: «Я знаю, что там `Dog`, приведи». Если мы ошиблись (там `Cat`), — **во время выполнения** будет `ClassCastException`.

```java
Animal animal = new Cat();
Dog dog = (Dog) animal;   // ClassCastException во время выполнения
```

Это и есть главная опасность downcasting: **компилятор не проверяет**, что там на самом деле. Он доверяет вам. Если вы ошиблись — падение в момент выполнения.

## instanceof + cast: классическая связка

Чтобы избежать `ClassCastException`, downcasting обычно сочетают с `instanceof`:

```java
if (animal instanceof Dog) {
    Dog dog = (Dog) animal;   // безопасно: проверили, что это Dog
    dog.bark();
}
```

Теперь падения не будет: если `animal` не `Dog`, — мы просто не заходим в блок.

Начиная с Java 16, есть более короткий синтаксис — **pattern matching for instanceof**:

```java
if (animal instanceof Dog dog) {
    dog.bark();   // dog уже имеет тип Dog, приведение не нужно
}
```

Это то же самое, но короче: в скобках после `instanceof` объявляется переменная, которая автоматически получает приведённое значение. Удобно и безопасно.

Мы будем использовать оба синтаксиса: классический (`instanceof` + явное приведение) и новый (pattern matching). Если вы на Java 16+, — используйте pattern matching: он короче и безопаснее.

## Зачем нужен instanceof

`instanceof` нужен, когда **полиморфизма недостаточно**. Есть несколько ситуаций, где это оправдано.

### Работа с «нетипизированными» данными

Когда тип неизвестен заранее — например, при десериализации JSON, при работе с `Object` из рефлексии, при обработке событий от внешней системы. Здесь `instanceof` — единственный способ понять, что делать с объектом.

```java
Object fromJson = parseJson(input);
if (fromJson instanceof String s) {
    return "Строка: " + s;
} else if (fromJson instanceof Number n) {
    return "Число: " + n;
} else if (fromJson instanceof List<?> list) {
    return "Список из " + list.size() + " элементов";
}
// ...
```

### Работа с методами, которые возвращают `Object`

Например, `Object.equals(Object)`: параметр типа `Object`, и нужно проверить, что это «тот же тип», прежде чем приводить. Мы будем говорить об этом, когда будем разбирать `equals` и `hashCode`.

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (!(o instanceof Point p)) return false;   // проверка типа + приведение
    return x == p.x && y == p.y;
}
```

### Проверка «а это точно этот тип?» перед рискованной операцией

Иногда у вас есть объект, который **может** быть не того типа, и вы хотите «защититься»:

```java
void process(Shape shape) {
    if (shape instanceof Circle c) {
        // работаем с c как с кругом
    } else {
        // обрабатываем как-то иначе
    }
}
```

### Вспомогательные утилиты

Например, `toString(Object)`, которая форматирует объект по-разному в зависимости от типа:

```java
String format(Object o) {
    if (o == null) return "null";
    if (o instanceof String s) return "\"" + s + "\"";
    if (o instanceof Number n) return n.toString();
    if (o instanceof Collection<?> c) return "[" + c.size() + " элементов]";
    return o.toString();
}
```

## Когда instanceof — плохая идея

Теперь про тёмную сторону. `instanceof` — это **признак того, что полиморфизм не доработал**, и в большинстве случаев его можно (и нужно) избежать.

### Проблема 1: нарушение открытости/закрытости

Классический пример:

```java
double area(Shape shape) {
    if (shape instanceof Circle c) {
        return Math.PI * c.radius * c.radius;
    } else if (shape instanceof Rectangle r) {
        return r.width * r.height;
    } else if (shape instanceof Triangle t) {
        return heron(t.a, t.b, t.c);
    }
    return 0;
}
```

Что здесь плохо? **Каждый раз, добавляя новую фигуру**, нужно **менять** этот метод. Это нарушает принцип «открыт для расширения, закрыт для изменения» (OCP), о котором мы поговорим в модуле 6. Вы не можете «просто добавить» `Square` — нужно **изменить** код `area()`, добавив новую ветку.

**Правильное решение** — полиморфизм:

```java
abstract class Shape {
    abstract double area();
}

class Circle extends Shape {
    @Override
    double area() { return Math.PI * radius * radius; }
}
// ...
```

Теперь `area()` не нужно менять при добавлении фигуры. Новый класс просто реализует свой `area()`. Это и есть смысл полиморфизма.

### Проблема 2: дублирование

`instanceof` часто дублируется в разных местах. Если у вас есть `area(Shape)`, `perimeter(Shape)`, `describe(Shape)` — и в каждом `if/else if` по типам, — это **много дублирования**. Добавление новой фигуры требует изменения **всех** таких методов.

**Решение** — полиморфизм: методы `area()`, `perimeter()`, `describe()` объявляются в `Shape` и реализуются в каждом наследнике. Тогда добавление фигуры — это добавление **одного** класса, а не правка десяти методов.

### Проблема 3: instanceof «закапывает» знание о типах

Код с `instanceof` знает **все** типы, которые могут прийти. Это значит, что если завтра появится новый тип, — код сломается (или начнёт вести себя неправильно), но **компилятор не подскажет**. Ошибка будет «тихой».

**Решение** — полиморфизм: код не знает о конкретных типах, он работает с интерфейсом. Появление нового типа — это «просто ещё один класс, реализующий интерфейс». Существующий код работает с ним без изменений.

### Проблема 4: instanceof в иерархии с несколькими уровнями

Если у вас глубокая иерархия, — `instanceof` становится ещё хуже. Например, `instanceof Shape` вернёт `true` и для `Circle`, и для `Rectangle`, и для их наследников. А `instanceof Circle` — только для `Circle` и его наследников. Легко запутаться, какой именно тип вы проверяете.

**Решение** — полиморфизм: методы выбираются по фактическому типу, без явных проверок. Никакой путаницы.

### Проблема 5: instanceof нарушает инкапсуляцию

Код с `instanceof` знает **внутреннее устройство** других классов: какие у них есть подтипы, какие поля, какие методы. Это знание не должно «протекать» наружу. Если завтра `Circle` захочет стать `Ellipse` с равными осями, — код с `instanceof` может сломаться, хотя «снаружи» ничего не изменилось.

**Решение** — полиморфизм: код знает только о контракте (`Shape`), не о реализации.

**Правило:** **если вы пишете `instanceof` для объекта, тип которого вы контролируете, — это почти всегда признак плохого дизайна**. Полиморфизм справится лучше.

## Когда instanceof оправдан

Не всё так плохо. Есть ситуации, где `instanceof` — это **правильный** инструмент.

**Когда типы не под вашим контролем.** JSON, XML, внешние API — вы не можете «добавить метод в их классы». Вы вынуждены проверять тип.

**Когда метод принимает `Object`.** `equals`, `hashCode`, `toString`, `Comparator` — вы не контролируете тип параметра и проверяете его.

**Когда иерархия закрыта** (например, `sealed`-классы в Java 17). Если вы **точно знаете**, что подтипов ровно три, и они не изменятся, — `instanceof` может быть оправдан. Но это редкий случай.

**Когда нужна оптимизация.** Иногда `instanceof` используется для «быстрого пути»: если объект — `String`, обрабатываем быстрее, чем через общий интерфейс. Это оптимизация, и она должна быть обоснована (профилированием).

**Когда поведение «зависит от типа» сильно.** Если у вас есть `PaymentProcessor` с пятью реализациями, и каждая делает **совершенно** разные вещи (Stripe, PayPal, Robokassa — у каждого свой протокол), — иногда проще проверить тип и вызвать специфичный метод, чем пытаться втиснуть всё в общий интерфейс. Но это признак того, что интерфейс «неправильный»: возможно, стоит пересмотреть его.

## instanceof и дизайн

Вот важная мысль: **`instanceof` — это симптом, а не болезнь**. Если вы часто пишете `instanceof`, — проблема не в `instanceof`, а в **дизайне иерархии**. Скорее всего, интерфейс «не покрывает» все нужды, и вы вынуждены «спускаться» к конкретным типам.

Хороший дизайн: **интерфейс покрывает все типичные операции**, а специфичные — выносятся в **отдельные интерфейсы** или реализуются через **композицию**.

Например, вместо:

```java
if (animal instanceof Dog dog) {
    dog.bark();
}
```

— сделать:

```java
interface Barking {
    void bark();
}

class Dog extends Animal implements Barking {
    @Override
    public void bark() { ... }
}

void barkAll(List<Animal> animals) {
    for (Animal a : animals) {
        if (a instanceof Barking b) {   // проверяем интерфейс, а не класс
            b.bark();
        }
    }
}
```

Здесь `instanceof` всё ещё есть, но он проверяет **интерфейс**, а не конкретный класс. Это гораздо гибче: если завтра появится `Robot implements Barking`, — `barkAll` будет работать с ним без изменений.

**Ещё лучше** — если `bark()` есть у всех `Animal`, — просто сделать его методом `Animal` (абстрактным или с реализацией по умолчанию). Тогда `instanceof` вообще не нужен.

## Аналогия, которая помогает

Хорошая аналогия — **сортировка почты**.

Представьте, что вы работаете на почте. Приходят посылки, письма, бандероли. Вам нужно их как-то обрабатывать.

**Полиморфизм** — это когда у каждого типа почты есть **свой способ обработки**, и вы просто говорите: «Обработать». Письмо обрабатывается одним способом, посылка — другим, бандероль — третьим. Вы не проверяете тип — вы просто вызываете «Обработать», и каждый тип сам знает, что делать.

**`instanceof`** — это когда вы **вручную** проверяете: «Так, это письмо? Тогда в этот ящик. Это посылка? Тогда в тот ящик. Это бандероль? Тогда в третий». Работает, но:

- Вы должны **знать** все типы почты. Если появится новый (например, «экспресс-доставка»), — придётся переписать всю процедуру.
- Вы **дублируете** проверку в каждом месте. Если у вас три разных сортировочных пункта, — в каждом будет «if письмо / if посылка / if бандероль».
- Вы **привязаны** к типам. Если завтра письма и бандероли объединят в «плоские отправления», — придётся менять всё.

**Правильный подход** — полиморфизм: у каждого типа есть «как меня обработать», и вы просто вызываете «обработать». Новый тип — это новый класс с «как меня обработать», а ваша процедура не меняется.

**Когда `instanceof` оправдан** — когда вы **не контролируете** типы. Например, почта приходит от разных отправителей, и вы не можете «добавить метод» в их посылки. Тогда вы вынуждены проверять тип.

**Когда `instanceof` — плохо** — когда типы **под вашим контролем**, и вы могли бы спроектировать их так, чтобы полиморфизм работал.

## Микрозадача 1

Вот код. Что выведется? Объясните, почему.

```java
class Animal {
    void speak() { System.out.println("..."); }
}

class Dog extends Animal {
    @Override
    void speak() { System.out.println("Гав"); }
    void bark() { System.out.println("Гав-гав"); }
}

Animal a = new Dog();
System.out.println(a instanceof Dog);
System.out.println(a instanceof Animal);
System.out.println(a instanceof Object);

if (a instanceof Dog d) {
    d.bark();
}
```

### Разбор

Выведется:

```
true
true
true
Гав-гав
```

Разберём по шагам.

**`a instanceof Dog`** — `a` фактически указывает на `Dog`, поэтому `true`.

**`a instanceof Animal`** — `Dog` наследует `Animal`, поэтому `Dog` **является** `Animal`, и `true`.

**`a instanceof Object`** — любой класс наследует `Object`, поэтому `true`.

**`if (a instanceof Dog d)`** — pattern matching: проверяет, что `a` — `Dog`, и если да, — создаёт переменную `d` типа `Dog`, которая ссылается на тот же объект. В блоке вызывается `d.bark()` — печатает «Гав-гав».

**Ключевая мысль.** `instanceof` проверяет **фактический тип объекта**, а не тип переменной. Переменная `a` имеет тип `Animal`, но `a instanceof Dog` — `true`, потому что объект — `Dog`.

## Микрозадача 2

Вот код. Что произойдёт? Объясните, почему.

```java
Animal a = new Animal();
if (a instanceof Dog d) {
    d.bark();
} else {
    System.out.println("Не собака");
}
```

### Разбор

Выведется:

```
Не собака
```

Разберём по шагам.

`a` — это `Animal` (не `Dog`). `a instanceof Dog d` — проверяет, является ли `a` объектом `Dog`. Ответ: `false`. Значит, блок `if` не выполняется, и срабатывает `else` — печатает «Не собака».

**Что было бы без pattern matching:**

```java
Animal a = new Animal();
if (a instanceof Dog) {
    Dog d = (Dog) a;   // ClassCastException, если бы выполнилось
    d.bark();
} else {
    System.out.println("Не собака");
}
```

— тоже вывело бы «Не собака», потому что `if` не выполняется. Приведения не происходит.

**А вот что было бы, если бы мы сделали приведение без проверки:**

```java
Animal a = new Animal();
Dog d = (Dog) a;   // ClassCastException во время выполнения
d.bark();
```

— упало бы с `ClassCastException`, потому что `Animal` — не `Dog`.

**Мораль.** `instanceof` — это **защита** от `ClassCastException`. Если вы делаете downcasting, — всегда проверяйте тип через `instanceof` (или используйте pattern matching). Иначе рискуете получить падение в самый неподходящий момент.

## Самостоятельная задача

Вернитесь к иерархии фигур (`Shape`, `Circle`, `Rectangle`, `Triangle`). У `Shape` есть метод `area()`, но у `Circle` и `Rectangle` есть **дополнительные** методы: `getRadius()` у `Circle` и `getWidth()`/`getHeight()` у `Rectangle`.

Вот код, который «печатает детали» каждой фигуры:

```java
void printDetails(Shape shape) {
    if (shape instanceof Circle c) {
        System.out.println("Круг, радиус: " + c.getRadius() + ", площадь: " + c.area());
    } else if (shape instanceof Rectangle r) {
        System.out.println("Прямоугольник " + r.getWidth() + "x" + r.getHeight() + ", площадь: " + r.area());
    } else {
        System.out.println("Фигура, площадь: " + shape.area());
    }
}
```

Подумайте:

- что плохого в этом коде? Что произойдёт, если завтра появится `Triangle`?
- можно ли переписать этот код **без** `instanceof`? Как?
- если вы хотите, чтобы у каждой фигуры было «описание», — где должен быть метод `describe()`? В `Shape` (абстрактный) или в каждом наследнике? Почему?
- а если у `Circle` есть метод `getRadius()`, а у `Rectangle` его нет, — можно ли добавить `getRadius()` в `Shape`? Что это даст? Что сломает?
- если вам действительно нужно «получить радиус, если это круг», — как это сделать без `instanceof` в вызывающем коде?

Затем перепишите `printDetails` **без** `instanceof`. Подсказка: добавьте метод `describe()` в `Shape` (абстрактный) и реализуйте его в каждом наследнике. Каждая фигура знает, как себя описать.

## Что дальше

Мы разобрались, что такое приведение типов, зачем нужен `instanceof` и когда он оправдан, а когда — нет.
